# 版本、构建与发行

Standards 的发行集合版本由 [project.json](../project.json) 和 [当前发行单元](../releases/current.json) 共同固定。单份规范独立使用稳定 ID、准确版本、路径与 SHA-256；发行集合版本不能代替文档采用身份。

## 0.1.x 修订范围

0.1.x 用于修复错误引用和工具缺陷、澄清既有要求、补充正例/失败例/合法邻例，以及提供默认不强制启用的兼容指南与评测配置。公共消费面包括文档及条款 ID、义务含义、路径、登记格式、工具入口和结果语义。

新增默认强制义务、重定义授权或完成语义、删除稳定身份、引入不兼容的必填字段或替换既有格式，应单列迁移并评估进入 0.2.0。这个约定是 Standards 对初始开发阶段的项目承诺；不能仅凭三段版本号推导全面 SemVer 合规。

已发布同版本内容不替换。正文实质修订形成新文档版本，更新文件名、摘要、来源/依赖、译文和机器索引；未变正文保留原身份。采用项目按自己的固定版本决定升级，上游发行不会自动改变已有采用。

## 变更与审查

每版以分支和 PR 提交，列具体问题、受影响对象、兼容影响、正反例和实际验证。作者自查与独立审查分别绑定准确提交。审查者应独立核对机制与边界；候选改变后复核受影响部分。合并前处理开放阻断，集成结果按准确 tree 检查。

常规门禁包括规范/目录生成一致性、全仓合同校验、必要技术审查、回归测试、根许可分配及第三方例外核对。原始日志保存在源码目录外，PR 留下对应提交和结论；源码不打包审查过程流水。

## 精确提交构建

先在清洁的 Git 工作区固定已检查提交，再使用构建器的 `--source-commit` 参数。构建器逐文件核对该提交的 Git tree/blob 身份，并在构建后再次核对。输出目录位于源码之外。

发行交付包含：

- `Standards-v<version>-source.zip`：规范源码、指南、索引、工具与测试。
- `Standards-v<version>-agent-skill.zip`：Agent Skill、完整规范引用和离线检索脚本。
- `BUILD-REPORT.json`：实际来源提交/tree、集合身份和两个包的验证结果。
- `SHA256SUMS.txt`：覆盖两个 ZIP 和 BUILD-REPORT。

完整文件清单、字节数和 SHA-256 在构建时生成并随包交付。报告不记录自身摘要，避免自引用。构建后验证 ZIP、实际解包，再执行离线校验与 Skill 查询。

## Tag、Release 与实际发布

PR 只检查并构建候选制品。发布意图由受审查的[发行配置](../releases/current.json)固定：该文件合入 `main` 后触发发行工作流；维护者也可以在 `main` 手动运行工作流并显式选择 `publish=true`，默认值为 `false`。普通提交没有修改发行配置时不会自动发布。

工作流先在只读权限下检查准确来源提交、回归与四个制品。独立的发布 job 绑定 GitHub `release` 环境，并独占当前仓库的 `contents: write`、`id-token: write` 和 `attestations: write` 权限。该环境仅允许 `main`；仓库启用 immutable releases 后，将环境变量 `STANDARDS_IMMUTABLE_RELEASES_ENABLED` 设为 `true`，否则发布停止。四个发行制品分别生成 GitHub artifact provenance。

待发布提交须仍是当前 `main`，且制品身份一致。初次发行 `0.1.0` 的 `previous_version` 为 `null`，远端不得存在其他已发布版本；后续修订必须指定紧邻前版，核对其正式发行、标签及提交祖先关系。发布器先创建草稿，上传并读回核验附件，再正式发布；随后使用 `gh release verify` 和 `gh release verify-asset` 核对不可变发行及四个附件。已有标签不移动，已有发行不静默替换；重试先查询已存在对象，只接受完全相同的身份。

第三方 GitHub Action 固定到完整提交 SHA；Dependabot 每周归组检查 Action 更新，升级仍以完整 SHA 落库。

自动发行使用未签名附注标签，固定标签名、准确来源提交及发行说明摘要。tagger 明确标识为自动化，其时间取来源提交的 committer 时间以形成可重复的标签对象；实际发布时间以 Release 的发布时间为准。创建前计算标签对象身份，创建响应未知时先按同一身份读回，再核标签引用和最终提交。已发布版本也重新核对附注正文、tagger、时间、对象 SHA、标签引用和最终提交，并在附件读回后再次确认。轻量标签和同名不同对象均拒绝覆盖。

创建附注标签对象或引用后，发布器最多读回四次（含首次），间隔为 1、2、4 秒，单次网络操作沿用 60 秒超时。只对未读到对象及暂时性的读取故障重查；身份不符或权限错误直接失败。确认耗尽时停止后续发布，保留准确对象供同一发行恢复；确认过程不重复创建或移动标签。

自动发布依赖实际可用的 GitHub Actions 运行环境。运行环境不可用时，可从经审查的准确合并提交构建和验证四个制品，由维护者创建对应的新 Tag 和 Release。构建与发布分别记录实际状态。

发布后核对标签目标、实际附件集合和下载字节摘要。源代码已合并、包已构建、渠道已发布和下游已采用分别记录。正式发布状态以 [GitHub Releases](https://github.com/ranzevor/Standards/releases) 的真实对象为准。
