# 分支、提交与审查

变更前确认基线 commit、目标和写入范围，保留工作区中与本次变更无关的内容。文件版本和完整差异使用 Git tree 与 diff 取得；未提交候选使用实际工作区对应的 tree。多人或多实例修改共享对象时，使用明确的分支和预期版本检查。

## 提交消息

本仓库的新维护者提交、PR 标题及最终 squash 消息采用 [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/) 的消息结构。`type` 和 `scope` 使用稳定英文标识，主题与说明正文使用简体中文；路径、API、条款 ID 等准确技术标识保留原文。

```text
fix(references): 修正引用标签与实际文档身份错配

说明出现问题的条件、改变后的行为以及兼容影响。
记录实际验证和仍未执行的检查，不把计划写成完成。
```

`feat` 表示新增能力，`fix` 表示缺陷修复，纯文档修改使用 `docs`；其他类型按实际变化选用。范围描述受影响模块，例如 `release`、`references`、`behavior`、`eval` 或 `portability`。不使用“更新”“优化”等无法辨认具体改动的主题。

正文的深度与变更影响相称，说明具体问题、变更行为、影响范围和验证结果。存在不兼容变化时明确标记并给迁移说明，不能为保持小版本而隐藏影响。发行集合版本按[发行政策](RELEASE.md)和经过审查的发行配置确定；当前工作流不从 `feat` 或 `fix` 自动推导版本。

合并前核对最终消息与准确差异。采用 squash 时可以在保留 PR 审查历史的同时整理主线消息；已经共享或发布的历史不为修饰文字而重写。

## 独立审查

作者自查与独立审查分别记录。审查针对准确差异，覆盖核心机制、兼容、失败恢复、来源与许可；修改后的复核使用新对象及仍然有效的既有证据。由专门子代理审查时说明其未参与实现，记录准确提交和具体发现；同一账号代录 COMMENT 不冒充另一人类账号的批准。

复核深度与变更影响相称。排版变更核对内容、链接和生成物；权限、持久化、并发、对外契约与门禁逻辑需要相应反例和合法邻例。保留初始失败和修复复核，不以文字流畅或测试数量代替机制审查。

仓库提供 [CODEOWNERS](../.github/CODEOWNERS) 和 [质量工作流](../.github/workflows/quality.yml)，工作流由 Pull Request 或手动触发。管理员按实际协作需求配置分支保护和必需检查，并核对最终集成提交的检查结果。运行环境未执行检查时如实记录，合并不能绕过实际生效的保护规则。
