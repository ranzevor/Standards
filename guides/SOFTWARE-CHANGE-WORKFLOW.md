# 软件变更的开发与仓库流程

本指南供贡献者、审查者和维护者处理一项完整变更，衔接[软件仓库采用](SOFTWARE-REPOSITORY-ADOPTION.md)、[需求验收](../standards/project-governance/003-需求设计与验收追溯规范--v0.1.0.md)、[Git 工作区](../standards/project-governance/007-Git工作区与本地操作规范--v0.1.0.md)、[分支同步](../standards/project-governance/008-Git分支同步与冲突处理规范--v0.1.0.md)及[审查合并](../standards/project-governance/009-变更提案审查与合并规范--v0.1.0.md)。完整合成案例见[仓库流程示例](../examples/repository-process/README.md)。

## 1. 确定问题与准确基线

在现有 Issue、PR 或项目工单中记录触发条件、预期/实际、受影响合同、范围及验收方法。设计选择改变公共接口、数据、安全或兼容承诺时，先形成与影响相称的决定；简单修复可在同一记录中说明。

修改前识别目标仓库、工作区/索引/未跟踪项、目标分支、远端和当前授权。取得远端最新目标后，比较准确提交及本地差异，再从已核基线建立开发分支。已有他人修改先确定归属并保护内容。

已有 Git 历史的仓库可用 `git status --porcelain=v1 -uall`、`git diff`、`git diff --cached` 分辨三层状态，再按项目约定获取目标分支和核提交。新空仓没有 HEAD 是正常初态，不创建无业务用途的提交补齐状态；初始化及初次推送按 PGW-02 和项目授权执行。

## 2. 先确定验收，再修改实现

从真实需求独立定义输入、预期输出、状态与副作用，明确失败、边界及恢复。检查器的预期不从当前输出倒推；设计方法见[门禁指南](QUALITY-GATE-DESIGN.md)。

实现与受影响测试、配置、依赖和使用说明保持同一变更范围。当前版本由候选元数据确定，公开承诺、冻结协议和历史发行各保留准确身份。文件改名时追踪导入、构建、安装、链接及实际消费者；涉及安装按[生命周期指南](ARTIFACT-INSTALLATION-LIFECYCLE.md)处理。

## 3. 按影响选择验证

| 变化 | 本次检查 | 可复用的未受影响结果 |
| --- | --- | --- |
| 排版、同义标签、导航 | 语义、本地链接与必要呈现 | 源码、运行环境及证明命题未变的算法或实机结果 |
| 快速开始、安装命令 | 在干净消费者环境执行改变的命令，观察首次任务 | 未变接口的其他既有行为结果 |
| 行为或接口 | 正常、直接失败、合法边界及受影响消费者 | 不经过该路径且输入/环境未变的检查 |
| 依赖、构建或制品 | 锁定输入、独立预期成员、实际包与最小消费者 | 不依赖改变工具链或依赖的结果 |
| 权限、路径、身份、持久化或恢复 | 相关拒绝、并发/超时边界、恢复及原对象保护 | 仅限对象、环境和证明命题仍适用的结果 |

一项变更涉及多种影响时合并相应检查。失败先核原因及受影响范围，修复后重跑原失败和关联行为；测试自身判据错误时按独立需求修正，保留原失败依据。完成必要检查后，不重复等价验证来增加测试数量。

Standards 中的检查命令与完整回归要求见[验证入口](../governance/VALIDATION.md)和[发行政策](../governance/RELEASE.md)。其他采用项目填写自己的实际命令、环境、预期、结果及未执行范围。

## 4. 提交与 PR

逐路径暂存并审完整索引，确认只包含当前变更及必要测试、文档和配置。提交主题说明具体变化，正文交代触发条件、最终行为、兼容与有效验证。本仓采用[提交约定](../governance/BRANCHES-AND-REVIEW.md)，其他项目沿用自己的消息规则。

使用[通用 PR 模板](../templates/repository/PULL_REQUEST_TEMPLATE.md)记录目标分支、准确基线和候选、行为影响、风险/恢复及实际验证。小变更简洁填写即可；不重复复制已有工单和结果原件。

采用项目可在 GitHub 支持的仓库位置接入模板，或明确使用组织公共默认模板。已有模板应比对必要字段，避免生成第二套重复入口；仅在贡献指南放一段模板文字，还需确认 PR 创建入口实际能使用。仓库文件与平台默认配置分别核对。

作者自查和独立审查分别绑定候选。候选变化后说明新旧差异，并复核受影响范围；原审查仍适用的部分可复用，不能把作者自查写成独立批准。开放发现逐项修复或由相应责任人决定处置。

## 5. 合并与集成确认

有权维护者在合并前核目标 HEAD、最终候选、未关闭发现、平台规则、必需检查及批准状态。基线变化时按实际影响更新集成候选和必要检查，保留未受影响证据的适用理由。

PR 源提交与拟合并结果可能不同：前者用于来源和制品身份，后者用于与目标分支的集成行为。优化 CI 前先固定两类检查各自对象和用途，再合并真正重复的步骤；保留独立制品验证和必需检查名称的约束。

合并后核实际提交、tree、内容和必要检查。发现集成错误时按当前共享历史和授权选择新增修复或回退；已共享历史不为整理消息而重写。

## 6. 发行、维护与记录

合并授权与发行授权按项目流程分别确认。自动发行项目在合并前明确配置会触发什么版本、渠道及权限；已存在的有效自动发行授权按其范围执行。发行绑定准确源码、版本、标签、说明和制品，发布后从正式渠道核下载/安装和最小任务。

工作项以验收条件和实际集成/交付结果收尾，用户仍需采取的迁移及恢复动作写在相应使用文档。原始运行日志和审查过程存放源码目录外；仓库保留正式实现、合成回归、稳定入口及必要变更说明。
