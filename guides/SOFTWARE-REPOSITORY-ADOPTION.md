# 软件仓库采用指南

本指南把现有通用工程、项目治理、开源、CI 与供应链规范组合成软件仓库可直接采用的入口。规范义务仍以准确正文和条款为准；本指南只负责选择条件、仓库载体及验收关系。

需要机器检查时，将[软件仓库 profile 模板](../templates/repository/repository-profile.template.json)复制到目标项目并填写状态和实际文件。随后从 Standards 源码根目录运行 `python checks/software_repository.py --root <project-root> --profile <project-relative-profile.json>`。该检查使用当前 Standards 发行自带的 schema，不读取或改变平台配置。

## 1. 先固定仓库的真实状态

仓库可见性、分发授权、维护状态和发行状态分别判断，不能用其中一项推导其他项。

| 维度 | 常见状态 | 必须保持的区别 |
| --- | --- | --- |
| 可见性 | private / public | public 只表示可读取，不自动授予复制、修改或再分发许可 |
| 分发 | none / source-visible / open-source | open-source 必须有权利主体选择的许可证及实际覆盖范围 |
| 维护 | active / limited / unmaintained / archived | archived 不等于删除，也不自动终止既有许可 |
| 发行 | not-published / published / withdrawn | 合并、标签、制品上传和使用者可取得分别核对 |

私有开发仓库可以尚未选择许可证，但不得使用开源许可证徽章或公开安装承诺。公开可见而未授予许可的仓库应准确写明当前分发状态。正式发行需另外固定版本、源码、制品、许可、支持范围及取得入口。

## 2. 选择现有规范

所有持续开发的软件仓库先选择 [L3 通用工程规范](../standards/L3/001-通用工程规范--v0.1.0.md)中与实际工程类型相符的条款，并按项目组成选择 L4 领域与 L5 技术栈。仓库治理按触发条件增加下列专项：

| 触发条件 | 主要规范 |
| --- | --- |
| 建立目录、README、文档和内容归属 | [STD-PG-004](../standards/project-governance/004-仓库命名目录与内容归属规范--v0.1.0.md)、[STD-PG-005](../standards/project-governance/005-README品牌与徽章规范--v0.1.0.md)、[STD-PG-006](../standards/project-governance/006-文档编制与国际化规范--v0.1.0.md) |
| 使用 Git、分支、PR 和独立审查 | [STD-PG-007](../standards/project-governance/007-Git工作区与本地操作规范--v0.1.0.md)、[STD-PG-008](../standards/project-governance/008-Git分支同步与冲突处理规范--v0.1.0.md)、[STD-PG-009](../standards/project-governance/009-变更提案审查与合并规范--v0.1.0.md) |
| 配置检查、依赖、权限和证据保留 | [STD-PG-011](../standards/project-governance/011-测试质量门禁与证据规范--v0.1.0.md)、[STD-PG-012](../standards/project-governance/012-依赖配置与供应链规范--v0.1.0.md)、[STD-PG-013](../standards/project-governance/013-安全隐私与操作边界规范--v0.1.0.md)、[STD-PG-019](../standards/project-governance/019-文件缓存构建物与证据生命周期规范--v0.1.0.md) |

采用记录固定文档 ID、版本、路径、摘要、适用条款和验收责任；模板或仓库文件存在不等于已经采用或通过。

## 3. 将条款映射到仓库和平台

| 对象 | 仓库内契约 | 实际验收 |
| --- | --- | --- |
| 项目入口 | README 的用途、状态、支持范围、快速开始、文档导航和权利入口 | 从干净环境执行公开命令，观察实际首次使用结果 |
| 协作入口 | CONTRIBUTING、Issue 模板、PR 模板和行为准则 | 创建合成 Issue/PR，确认字段能承载复现、范围、风险、回退和审查 |
| 权利与安全 | LICENSE、材料/通知记录、SECURITY 及私密渠道说明 | 核实际分发清单、通知和平台私密报告入口 |
| 依赖与构建 | 运行时声明、锁文件、构建及验证命令 | 从锁定输入恢复依赖并构建准确候选 |
| 合并保护 | CI 工作流、CODEOWNERS 或项目等价责任入口 | 从托管平台读回规则集、必需检查、绕过主体和目标分支 |
| 发行 | 版本规则、变更记录、发行配置和恢复入口 | 从正式渠道读回标签、源码、制品、摘要和可安装结果 |
| 维护与归档 | 支持范围、维护状态、替代/迁移和最终身份 | 读回仓库归档状态，核必要历史及取得入口仍可用 |
| 验收证据 | 源码仅保留稳定检查入口和必要索引 | 原始日志、测试输出和审查材料保存到独立运行目录、CI 制品或授权证据存储 |

分支保护、安全功能、环境权限和私密报告渠道是平台状态，不能仅凭仓库中的策略文件判定已生效。[平台控制模板](../templates/repository/PLATFORM-CONTROLS.md)记录预期配置和读回方法，不保存令牌、截图或原始运行日志。

## 4. 最小实施顺序

1. 固定仓库状态、目标受众、公开接口、支持平台及不分发范围。
2. 从[软件仓库模板包](../templates/repository/README.md)选择实际需要的文件；需要机器检查时填写 profile。已有 Issue、PR 或项目记录可以直接承载，不建立重复状态。
3. 建立一个从干净检出可执行的安装、构建、测试入口；依赖和工具版本按实际生态锁定。
4. 在开发分支提交可审差异，PR 固定基线、候选、范围、兼容、风险、恢复和未执行项。
5. 从平台读回目标分支保护、必需检查、安全功能和发行环境；配置意图与实际状态分别保存。
6. 合并后重新核集成对象。正式发行再核标签、制品、下载及安装；归档再核最终身份、维护说明和替代入口。

日常变更按[开发与仓库流程](SOFTWARE-CHANGE-WORKFLOW.md)组织；检查器设计见[质量门禁](QUALITY-GATE-DESIGN.md)，发行与旧版恢复的职责见[安装生命周期](ARTIFACT-INSTALLATION-LIFECYCLE.md)。

## 5. 失败与合法邻例

- **直接失败：** README 宣称采用某开源许可证，但仓库没有有权主体选择的许可证或覆盖范围。
- **合法邻例：** 私有开发仓库明确不公开分发，包保持 private，许可证决定尚未作出；这不构成开源发行失败。
- **直接失败：** PR 模板只要求变更摘要，没有基线/候选、兼容、风险、恢复、未执行项和审查对象。
- **合法邻例：** 小型文档修订在同一 PR 中简要填写不适用项，不要求建立单独风险文档。
- **直接失败：** README 长期堆叠实施进度、内部交接和原始验证结果，当前用途与首次使用入口被历史过程淹没。
- **合法邻例：** CHANGELOG 保留与使用者有关的版本变化；原始输出位于独立证据存储，并由准确提交或发行身份关联。
- **直接失败：** 仓库文件写有“主分支受保护”，但平台实际允许未经必需检查直接写入。
- **合法邻例：** 不使用托管平台规则集的本地项目，以受控集成入口和可核预期提交实现等价保护。
- **直接失败：** 仓库归档后删除唯一源码、许可通知或迁移说明，并把网页不可写称为完成退役。
- **合法邻例：** 停止维护但继续保留准确源码、既有许可和替代说明。

三种完整合成状态见[软件仓库采用示例](../examples/repository-adoption/README.md)。
