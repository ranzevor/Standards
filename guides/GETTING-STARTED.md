# 从规范到项目验收

## 0. 获取当前发行

首次使用从 [GitHub Release](https://github.com/ranzevor/Standards/releases/tag/v0.1.1) 获取 Source 包和 `SHA256SUMS.txt`，核对摘要、解压并运行包内 `verify.py`。完整的 Windows PowerShell、Ubuntu 命令和最小查询见[离线分发与使用](OFFLINE.md#从公开发行入口首次使用)。Source 包无需安装第三方依赖或配置账号、凭据及环境变量。

## 1. 找到实际对象

从[规范目录](../INDEX.md)及[十六域](../README.md#十六技术领域)选择真实功能相关的基线/专题。项目治理负责项目全周期产物；L0–L3负责共同职责；L5只适配实际使用的技术栈，L6锁定项目参数与验收。无账号/无网络/单平台/纯理论等合法形态不因不存在其他能力而被强制新增功能。

## 2. 固定准确规范与适用范围

从[唯一登记](../registry/standards.json)取得ID、版本、路径和SHA-256；在[条款登记](../registry/requirements.json)定位稳定ID与完整章正文。逐条记适用、不适用的事实理由或未确定，必要消费依赖闭合。草案技术参考、草案试用、项目选择和体系正式采用不混为一个状态。

## 3. 建立可执行合同

使用[L6接口](../standards/L6/001-项目采用与实现验收接口规范--v0.1.0.md)、[采用模板](../templates/ADOPTION.md)和[六类合成例](../examples/adoption-contracts/README.md)。每个适用要求固定实施对象和环境、初态和输入、真实命令或工具、预期输出、终态、副作用数、失败或未知结果的恢复方法及合法邻例；实际值未得到时保持 `not-run`。具备相应权限的项目角色记录采用决定。

## 4. 运行本仓与目标检查

先在仓库根目录执行[README命令](../README.md#quick-start)。结果适用于所检查的文档、记录和有限模型。有引擎、浏览器、AT、服务或硬件要求时，按对应条款在获准环境运行并单独记录项目结果。

## 5. 审查、决定及维护

核来源的准确版本/章节与有限支持命题，按[技术审查模板](../templates/TECHNICAL-REVIEW.md)保留发现/修复与独立过程。真实有权主体对精确版本和范围作采用决定；许可/角色/支持/平台配置不从文件字段自动成立。升级时依据[兼容迁移](COMPATIBILITY.md)复核义务、依赖、数据和消费者，保留历史与未决影响。

小项目可复用已有版本化文件、Issue/PR或业务系统承载字段，不要求购买平台、制造多人角色或平行台账。

## AI 行为问题

遇到多余声明、反复确认、产物混入过程说明或无依据完成声明时，从[行为指南](AI-BEHAVIOR.md)选择相关专题，再按[采用、升级与反馈](ai-behavior/ADOPTION.md)固定配置、执行试验并开展独立审查。新增可选配置不会改变旧项目的既有采用范围。
