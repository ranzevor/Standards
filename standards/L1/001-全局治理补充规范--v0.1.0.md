# L1 全局治理补充规范

**文档ID：** STD-L1-001　**版本：** 0.1.0　**状态：** adopted　**生效日期：** 2026-10-30

**规范性强度与术语：** “必须/不得”在适用条件成立且该版本被选定采用时为必要要求；“应/建议”允许有理由且保留等价保障的偏离；“可/示例”不产生额外功能义务。主体是实际承担决定、执行或核验职责的人/系统；权威是能支持相应事实的原始系统，不是摘要或标签。输入未知、未执行和不适用不得互换。本规范不指定采购平台、真实人员或所有产品必须新增的技术能力。

## 定位与适用关系

本规范规定本体系的版本、适用、责任、冲突与例外管理。维护技术文本不等于拥有业务、数据、资金或生产权限；具体权限仍由具有对应权利的主体授予。个人、人类团队和Agent混合团队可按真实组织采用，不虚构审批角色。

## 一、规范权威与维护责任
1. **制度批准责任**：影响全组织的强制性规范，由有权决定其业务和治理范围的责任主体批准。不同主体分别决定实际拥有的业务、数据、知识产权、资金及生产发布权限。制定技术规范的人员或 Agent 只具备授权范围内的起草、审查和实施权。
2. **规范维护责任**：每份规范指定维护责任主体，负责收集适用问题、跟踪上游接口或法律政策变化、形成可审查修订；维护权不等于批准权。
3. **验收与登记责任**：规范生效前，应由批准责任主体或被明确授权的审查者核实适用范围、继承关系、差异、证据及计划实施的质量门禁；登记人员据真实批准结果更新状态。
4. **当前组织形态**：个人独立研发允许一人兼任维护、批准和执行职责，但不得为了形式制造多个名义审批角色。多人团队和人机混合团队可按职责细分；任务级岗位与交接由 L2 定义。

### GG-01 核验合同

- **适用条件与主体：** 维护者、批准者和登记者在提出或更新体系义务时。
- **输入、输出与权威：** 对象、真实权利依据、职责兼任关系和准确候选。输出为可追溯决定，登记只反映真实决定。
- **必要动作：** 必须履行本章全部适用要求；相同标识下的章正文与核验合同共同组成义务，合同不删除或降低前文要求。
- **失败、并发与恢复：** 主体或权限未知时该决定不成立；相关动作等待核实，其他已授权工作不受无关缺口影响。主体离任保留旧决定并迁移职责，不自动转移权利。
- **产物与验收：** 逐项能查到谁维护、谁决定、谁执行及谁审查；名称或角色字段不能自证真实权限。
- **正确案例：** 一人维护和批准范围内的个人规则，自审明确不独立。
- **直接失败反例：** 创建两个虚拟账号名称后宣布获得两名独立批准者。
- **合法邻例：** 真实外部测量可提供独立证据，但不能伪造不存在的人员。
- **检查入口与证据：** `python checks/validate_all.py` 核准确文本/登记/案例结构；技术审查按本条逐项走读并记录对象hash、判定理由与实际证据。具体项目依 L6 真实入口检验，本仓不替代目标系统执行。
- **来源与消费接口：** 本条为体系组织设计要求；外部资料仅提供术语与安全开发过程参照，不声称外部标准规定本体系分层或角色。其来源依据与有限边界见[共性编制与治理来源](../../sources/common-governance.md)。下游按准确版本/hash消费，项目治理规定仓库产物流程，L6固定项目适用及实际证据。

## 二、规范层级与项目适用决议
1. L1 负责跨项目治理；L2 规定人类与 Agent 的组织协作；L3 规定通用工程实践；L4 定义技术领域；L5 定义语言／框架／运行时；L6 固定单个项目实际采用的规范版本及特殊约束。L2—L5 为**可组合维度**，不以编号推导内容决定权。
2. 规范条目至少登记：名称、层级、版本、状态、适用角色／领域、维护责任、批准依据、适用起始日期、替代关系和执行或验证入口。未准备的字段保留待定状态，不以填充模板制造已获批准事实。
3. 项目决定适用规范时，先以实际需求、代码、部署环境、法律与第三方约束选取适用 L2—L5，再在 L6 记录版本、冲突裁决、必要例外与升级条件。技术选型变更须重新评估适用性；不得把全部领域强制套用到每个项目。
4. 新加入的团队成员或 Agent 按当前授权取得**适用于其任务的**有效规范及项目约束。规范库中可读到不代表该条款适用于所有环境；读取能力也不构成写入或发布授权。
5. 实际执行证据留在对应项目仓库、运行环境、科研结果或业务系统中；本规范体系保存规范版本和适用索引，不覆盖这些原始权威来源。

## 三、冲突裁决的正式程序
发现两项规则或决定无法同时满足时，由发现者提交下列信息：**冲突对象及操作、两侧原文和版本、真正拥有决定权的主体、受影响的数据／权利／环境、冲突发生的触发条件、可实施选项及其代价**。
- **法律、合同、许可、第三方权利**：先确定这些义务在对象、地域、合同和时间上的真实适用范围；任何内部批准均不得越过外部主体的权利。
- **业务与技术规则**：由具备相应内容、技术或发布决定权的主体分别判定。技术实现者无权把工程方便、旧代码状态或供应方默认值变为业务规则。
- **现行规则与新草案**：仍以已生效版本为准；草案不得成为自动的覆盖规则。若待审草案确有必要替代旧条款，须在批准记录中逐条指明替代范围。
- **同一项目多条可兼容要求**：同时满足；若在当前资源和时间条件下不可兼容，由相应责任主体批准实际取舍、补偿控制及影响，不能依赖简单的“最新文档优先”。
裁决记录包括批准者、结论、理由、范围、生效时间、被替代的具体条款及下次复核条件。争议只阻断可能越权或不可逆的相关操作，其他已授权工作继续进行。

## 四、授权制度的记录与生命周期
此节定义**授权治理的数据契约**；具体权限边界由真实有权主体决定并在项目 L6 记录，不由本规范自动授予。
- **最小授权记录**：授权主体及其权利依据、受权的人类／Agent／服务身份、允许的动作与数据用途、目标资源和环境、有效时间、预算／频次／影响上限（如适用）、前置批准条件、撤销方式及可查询的操作记录。
- **授权变更**：新增、扩权、跨环境、跨组织或对外传播时核对原授予主体的权限；工具安装、读取成功或持有密钥不能自动作为扩权证据。额度与风险变更以实际批准结果更新，不能由执行 Agent 自行提高上限。
- **长期授权**：既有授权未失效且任务未越界时直接使用，不为重复的同类低风险操作设置形式化逐次审批。授权已过期、撤销或对象变更时必须停止受影响操作。
- **主体离任或替换**：人类岗位移交、Agent 实例替换、第三方连接撤销时，维护可查询的权限映射、责任交接和最小必要访问，相关凭据的轮换和失效由对应授权系统完成。
- 具体的任务委派格式、角色-权限矩阵、多个 Agent 的共享资源写入协议、独立审查职责和交接流程由 L2 制定；各平台的可执行授权检查由 L3—L6 实现。

## 五、规范版本、状态与生效
- **草案**：内容可讨论与试验，无强制执行效力；未经批准不得自动注入团队或 Agent 的必遵规则。
- **待审核**：内容与相应基线完成差异审查、内容完整性及结构验证，等待拥有权利的主体进行业务／制度批准；“已技术验收”不能替代批准。
- **生效**：批准记录指定的版本、适用对象和生效日期可查，且与实际执行入口一致。若部署或集成尚未完成，应另行记录项目适配进度，不把“政策生效”等同于所有项目已改造。
- **修订中**：对有现行版本的规范形成候选改动；原生效版本在替代发布前继续适用。
- **已取代**：保留历史版本、被替代范围与引用路径；只从适用入口移除，不删除需要审计回溯的证据。
修订说明至少包括：变更原因、条款差异、权利／安全／质量影响、已有项目的迁移或豁免、批准人、目标版本、生效时点与回归验收。未改变义务的编辑可按授权的轻量流程处理，不要求等价的多轮重复审批。

## 六、规范例外与有效边界
例外登记必须具有：被例外覆盖的**具体已生效条款**、受影响项目与资源、必要原因、批准责任主体、起止时间、补偿控制、验证结果和到期恢复动作。例外仅在该条款及范围内有效，不向其他项目或 Agent 自动传播。
- 不能通过内部例外取消法律、客户合同、第三方授权与数据权利人的实际义务。
- 出现新风险或条件变化时，重新评估例外有效性；到期须回到适用规范或取得新的明确批准。
- 应急安排若由外部合同或应急程序另行规定，按其实际效力处理；本节不提供超出已有权限的紧急越权依据。

### GG-06 核验合同

- **适用条件与主体：** 已有适用义务需暂时偏离时的有权决定者与采用方。
- **输入、输出与权威：** 具体有效条款、对象、理由、风险、起止、补偿控制和恢复条件。输出为限定例外；草案试用偏离记试用选择而非伪造有效条款例外。
- **必要动作：** 必须履行本章全部适用要求；相同标识下的章正文与核验合同共同组成义务，合同不删除或降低前文要求。
- **失败、并发与恢复：** 到期或条件变化先复核适用，恢复原要求或取得新决定；内部例外不改变第三方权利。未知起止或无权主体的例外不能生效；并行延长须核当前决定。
- **产物与验收：** 边界内场景按补偿准则验，边界外不得继承；到期事件有明确恢复责任与可观察产物。
- **正确案例：** 仅测试环境暂缓某支持平台，记录期限与不能外推的范围。
- **直接失败反例：** 团队批准例外就宣称第三方数据许可或法律义务消失。
- **合法邻例：** 条款触发对象实际不存在属于不适用，不需要虚构例外审批。
- **检查入口与证据：** `python checks/validate_all.py` 核准确文本/登记/案例结构；技术审查按本条逐项走读并记录对象hash、判定理由与实际证据。具体项目依 L6 真实入口检验，本仓不替代目标系统执行。
- **来源与消费接口：** 本条为体系组织设计要求；外部资料仅提供术语与安全开发过程参照，不声称外部标准规定本体系分层或角色。其来源依据与有限边界见[共性编制与治理来源](../../sources/common-governance.md)。下游按准确版本/hash消费，项目治理规定仓库产物流程，L6固定项目适用及实际证据。

## 七、符合性审查与变更验收
规范治理验收应核对：
1. **来源有效**：项目实际采用的规范与L6契约未被未授权编辑、覆盖或重新标注为过期；引用均指向实际可访问的有效来源。
2. **职能边界**：L1 专注维护、批准、冲突、适用、例外和授权登记；任务执行、验证、环境管理等细节由L2协作、L3工程及L4—L6技术和项目契约承担。
3. **可执行性**：每条组织治理要求能指向负责主体、触发条件、最小登记信息和可查询证据；不新增无业务意义的审批。
4. **状态真实性**：设计完成、文本验收、批准生效、项目采用、上线运行分别报告；草案和待审核不自动成为 Agent 的强制规则。
5. **变更保护**：每次修订的保留、归并、下沉与删除均须从对应来源版本和差异记录核对；不能将其他版本的历史审查当作本版验收。

### GG-07 核验合同

- **适用条件与主体：** 维护者与审查者准备修订或声明符合时。
- **输入、输出与权威：** 原要求、逐条变化、源/依赖/案例/检查和真实执行证据。输出为保留/修改/新增/移除映射及本版本结论。
