# L3 通用工程规范

**文档ID：** STD-L3-001　**版本：** 0.1.0　**状态：** adopted　**生效日期：** 2026-10-30

## 定位与适用范围

本规范定义跨语言、框架、引擎与部署平台的通用工程实施契约。业务目标由项目需求决定。项目治理负责范围、采用、职责与变更流程；本规范负责实现边界、运行行为及工程验证。领域与技术栈规范提供专项约束，项目采用记录固定实际版本和验收目标。层级标识表示技术职责分类。

## 用语、状态与下游接口

本规范中的“须、必须、不得、禁止、要求”是在实际选择本规范、触发条件成立时的必要动作；“应、建议”为允许说明理由后偏离的建议；“可”与案例不新增功能义务。数字阈值、实际工具命令、支持版本和角色由L6固定，不以“由项目决定”取消已选择的安全或兼容最低要求。各章CE标识绑定本章完整条文，合同是核验接口而不是将本章缩减成七个字段。

“权威状态”指相应数据或操作合同承诺的事实来源，不必是单一物理服务器；“未知结果”表示现有证据不能区分已执行和未执行，不等于失败或未执行；“固定身份”包括准确版本、路径和摘要，不能单凭可变名称证明。技术负责人、需求负责人、实现者和验收者是职责，不虚构实际任命；作者检查不自称独立审查。

本规范不替代业务需求、专项协议、法律判断或真实项目采用。各CE合同的工程取舍为本体系组织设计，不冒称某个外部标准逐字强制；有限外部支持见[共性来源](../../sources/common-governance.md)。项目治理处理仓库产品与过程，L1处理制度选择，L2处理协作，L3处理工程行为；专项实现和工具限制由L4/L5提供，L6固定真实对象与可执行验收。

## 一、工程类型、风险与适用门禁
1. 每个项目或变更首先识别实际工程类型：探索实验、验证原型、持续开发的软件、面向用户的正式产品、生产运行服务，或多类型组合。类型表示**当前用途**，不会因将来计划而自动升级。
2. 选择检查深度时考虑：用户或客户影响、数据与资产价值、外部副作用、权限和资金、服务中断、可恢复性、已有兼容承诺、跨平台运行及计算成本。
3. **探索／隔离原型**：要求输入、方法、环境和结果可追溯；可只运行有意义的最小验证，不能用其通过情况声称达到生产品质。
4. **正式工程产品**：要求真实关键功能链路、兼容契约、异常恢复与目标平台验证完整；无法因为 CI 消耗、AI 工具限制或实施复杂度取消必要能力。
5. **有生产、资金、敏感数据或不可逆外部影响的变更**：须具有明确权利授权、原始状态与可恢复措施、真实安全和业务结果检查；不因修改行数少而降低级别。
6. L6 固定适用检查、所依据的目标以及例外审批；未被适用的领域专用门禁不得被误写成全组织统一强制项。

### CE-01 核验合同

- **适用条件：** 开始工程工作或用途/风险发生变化时
- **执行动作：** 登记当前用途、受影响资产、副作用、风险与选定门禁；缺项说明理由。
- **产物：** 范围与风险记录、检查计划
- **核验准则：** 逐项核对用途与真实入口，门禁能解释对应风险；数值阈值由项目固定。
- **正确案例：** 原型仅宣称在合成环境验证算法，不声称可生产使用。
- **错误案例：** 原型测试通过便把生产恢复门禁标为通过。
- **自动检查边界：** 自动工具核正文与合同登记的一致性；技术机制及目标行为分别按实质审查和适用环境验收，不以字段存在替代语义判断。

- **主体与权威：** 工程负责人核对当前实际用途、用户影响与资产；需求/风险记录为门禁选择权威，未来计划不是当前用途。
- **失败、并发与恢复：** 风险升高后旧门禁不再充分；并行变更合并其资产与副作用影响，保留旧分类，重新固定适用检查，不把已经发生的生产影响降格为原型。
- **合法邻例：** 未连接外部账户的隔离算法实验可以只验证方法和结果可追溯，不强制建立生产值班或支付恢复。
- **检查入口与边界：** 人工沿一个真实入口核范围、资产和风险，并对照L6选项；改变“仅合成数据”为“客户数据”后必须重新选门禁。
- **来源与消费接口：** 本章是组织合成工程要求；CG-01/02只解释规范性强度，CG-03仅有限支持职责、检查准则和代码访问；具体协议事实依实际L4/L5来源。下游L6必须固定本章适用场景、实施身份和观察点。

## 二、需求、角色任务与验收合同
1. 从真实业务／研究任务建立验收合同：目标角色、输入、状态、关键约束、输出、下游接收方、失败处理及完成责任。已确认需求、待验证假设与实施决定须分别标识；探索阶段可提出假设并设计验证，但不得把假设写成已经确认的业务承诺。
2. 分别表示必须交付的核心行为、兼容需求、非功能目标、运行／交付条件和明确排除范围。遇到目标缺口时先确定影响和负责的决策角色，不得通过精简领域模型或制造虚假的默认值让链路看似完整。
3. 核心验收场景根据需求而非现有实现确定；用合法输入验证应有差异，也用等价输入验证应有一致性。跨角色交付须明确必要字段及允许的转换。不得要求所有不同输入都产生不同结果。
4. 需求变更时核对既有行为、合同及数据是否受影响；将变更的实际后果传递到模型、API、页面、导出、通知、迁移、测试和发布。
5. **验收**：由需求负责人批准的场景可从真实入口执行到所需结果，且仍能追踪原始条件、权限和外部确认；仅有函数、Mock 或 UI 展示不算链路完成。

### CE-02 核验合同

- **适用条件：** 新增或改变可交付行为时
- **执行动作：** 固定输入、角色、状态、输出、失败语义和完成责任；区分已确认要求与探索假设。
- **产物：** 需求与验收场景、需求变更差异
- **核验准则：** 每个核心行为同时有合法路径和适用异常路径；期望来自需求而不是当前实现输出。
- **正确案例：** 不同编码的同一合法日期归一化为相同结果，非法日期明确拒绝。
- **错误案例：** 为了制造不同输出而破坏需求允许的输入等价性。
- **自动检查边界：** 自动工具核正文与合同登记的一致性；技术机制及目标行为分别按实质审查和适用环境验收，不以字段存在替代语义判断。

- **主体与权威：** 需求负责人给出可接受行为，实现者消费同一需求版本；未知假设与已确认承诺分别标识。
- **失败、并发与恢复：** 并发改需求或角色交接时固定变更前提，比较旧承诺和新增影响；期望未确定不能从实际输出反推，待有权需求判断后重做场景。
- **合法邻例：** 两个不同表示的同一日期按明确归一化规则得到相同结果是合法等价，不属于未实现输入差异。
- **检查入口与边界：** 人工从角色任务输入追到下游输出，对照独立期望；输入等价变换与语义不同变换分别运行并比较。
- **来源与消费接口：** 本章是组织合成工程要求；CG-01/02只解释规范性强度，CG-03仅有限支持职责、检查准则和代码访问；具体协议事实依实际L4/L5来源。下游L6必须固定本章适用场景、实施身份和观察点。

## 三、领域建模、架构与技术选型
1. 架构以真实功能、生命周期、并发与部署约束确定模块、数据所有权、接口和边界；可演化性与复杂度应与需要匹配，不提前假设微服务、事件驱动或某种流行框架是正确答案。
2. 明确稳定的领域概念、身份与关系、状态转移和不变量；关键业务计算不得被不同入口各自复制、悄悄改变或用不完整摘要替代。
3. 对高影响技术决定保留简洁的架构决策记录：问题、当前约束、可比较方案、理由、替代成本、兼容及回退条件；较小可逆决定允许在现有 Issue/PR 中直接记录。
4. 技术变更前识别对外接口、持久化、用户数据、部署过程与第三方依赖的影响；需要迁移时明确新旧版本并存、停止支持和数据回退的实际边界。
5. **验收**：架构图或文字可映射到实际代码与运行链路；无法实现的边界不得仅保存在文档中声称已满足。

### CE-03 核验合同

- **适用条件：** 引入或改变重要架构边界时
- **执行动作：** 明确数据所有权、状态不变量和方案权衡，并检查实际边界。
- **产物：** 架构决策记录、组件及运行关系
- **核验准则：** 从请求或数据入口追踪真实执行，所有受影响边界与记录一致；未实现部分明确标识。
- **正确案例：** 仅有一个部署组件的工具保持单体，记录其并发边界。
- **错误案例：** 为符合文档架构图宣称隔离，而代码仍无控制地共享状态。
- **自动检查边界：** 自动工具核正文与合同登记的一致性；技术机制及目标行为分别按实质审查和适用环境验收，不以字段存在替代语义判断。

- **主体与权威：** 架构负责人界定组件、数据所有权和状态不变量；实际代码/部署关系而非示意图是边界实现证据。
- **失败、并发与恢复：** 多个组件各自修改权威计算或并发共享状态时重新定位唯一决定点；迁移边界须支持新旧消费者，图与实现冲突先记未实现并修正其中错误。
- **合法邻例：** 一个进程内有清晰模块与事务边界的单体可满足隔离目标，不必为了分层图拆为微服务。
- **检查入口与边界：** 选择一个写入口和一个读消费者，人工/目标追踪工具核执行与所有权；故意绕过边界的调用应被禁止或被测试发现。
- **来源与消费接口：** 本章是组织合成工程要求；CG-01/02只解释规范性强度，CG-03仅有限支持职责、检查准则和代码访问；具体协议事实依实际L4/L5来源。下游L6必须固定本章适用场景、实施身份和观察点。

## 四、仓库、版本控制与贡献流程
1. 明确各源码组件、生成输入与制品的权威来源及固定身份。Git仓库使用commit/tree与diff管理版本和差异，未提交候选使用实际工作区对应的tree；离线交付使用构建生成并经核验的发行清单与摘要；多仓工程分别记录必要组件关系。声称远端当前状态时须重新读取目标，复现固定历史版本时不得强制替换为最新分支。
2. 在有权修改的范围内实行独立工作分支或等价隔离机制；变更应按可审查的目标组织，保留有必要的提交历史和可追溯来源。不要求任何项目机械采用同一分支名、提交频率或复杂 Git Flow。
3. 修改前检查目标基线、未完成协作、原权限、历史纠错和关联接口；提交前检查实际差异，避免同时纳入无关源码、凭据、构建缓存或诊断产物。
4. PR 或等价审查载体应载明真实功能／契约变化、风险、回归、必要的迁移或回滚条件及未验证部分；不能把 PR 创建或 Code Review 标记替代实际测试和交付。
5. 合并时确认目标分支当前状态、冲突的**语义**、已通过的检查及权限。多个 Agent 的共享资源写入按 L2 管理。
6. 仓库读取与写入通过项目认可且当前有权使用的入口完成，记录目标与操作结果。具体工具、平台及访问限制由项目环境策略确定；不得绕过访问控制。规范本身不指定会话、账户或某一插件为通用工程必需工具。
7. **验收**：源仓库、审核对象、实际变更提交和需要的 CI／独立验证能相互对应，未批准的发布不因代码合并而自动发生。

### CE-04 核验合同

- **适用条件：** 修改、审查、复现或交付源码时
- **执行动作：** 固定各组件与制品来源、内容身份及关联变更；按实际协作模式核对目标状态。
- **产物：** Git源码身份、构建生成的制品清单、固定摘要、审查与提交关系
- **核验准则：** 固定快照字节与登记一致；远端当前状态仅在确实重读后声称，离线摘要不证明来源授权。
- **正确案例：** 离线源快照以摘要验证；多仓构建分别固定组件。
- **错误案例：** 用最新分支替换历史输入后声称复现旧版本。
- **自动检查边界：** `checks/source_identity.py:verify_sources` 核验固定快照组件身份、字节摘要及有限路径边界；不核验远端最新状态或来源信任。

- **主体与权威：** 源码维护者和审查者固定各组件及制品身份；远端当前状态由当前读回证明，历史快照由对应摘要证明。
- **失败、并发与恢复：** 并发提交前核当前目标；结果未知先查询事实再决定重试，防止重复或覆盖。固定历史输入不替换为最新版本，来源身份不等于来源信任。
- **合法邻例：** 离线经核验的快照可用于复现，不要求为了复现历史再获取当前分支；多仓分别登记组件身份。
- **检查入口与边界：** 运行source_identity的正例/直接变异/合法多组件测试；当前远端状态另用项目认可入口读取，离线检查不证明远端新鲜度。
- **来源与消费接口：** 本章是组织合成工程要求；CG-01/02只解释规范性强度，CG-03仅有限支持职责、检查准则和代码访问；具体协议事实依实际L4/L5来源。下游L6必须固定本章适用场景、实施身份和观察点。

## 五、工程结构、工具链与构建复现
1. 保留清晰的源码、测试、配置、脚本、资源、迁移与文档边界。目录和模块划分以工程真实关系为依据，不为统一外观重排全部项目。
2. 明确受支持的运行时、编译器、包管理器、关键依赖版本和构建入口；使用对应生态的锁文件、校验或等价手段保证依赖可重复获得。
3. 构建脚本不得隐式依赖个人机器上的未登记状态；要求外部工具、模型权重、数据或大型资产时记录取得来源、校验方式和必要许可。
4. 按需提供最小可执行安装、开发与验证路径；包含环境前提、命令、重要输出、错误码和常见故障恢复。系统特有工具链和平台限制由 L5 指定。
5. 构建过程区分生成物与源文件；生成结果所需输入、版本和步骤应能追溯。不得让未授权的生成器、缓存或回退路径覆写权威源码。
6. **验收**：从干净且获准的环境按固定说明完成依赖解析、构建和必要测试；记录实际版本和可复算证据，缺失外部资源时准确记录受阻范围。

### CE-05 核验合同

- **适用条件：** 需要安装、构建或再生制品时
- **执行动作：** 固定运行时与依赖解析输入、命令、生成来源和外部资源条件。
- **产物：** 构建说明、锁定输入、版本记录、构建日志
- **核验准则：** 实际命令、环境和退出结果可对应到源版本；字节可重复性若被声称须额外比较制品。
- **正确案例：** 干净环境按说明得到可用产物；不可得资源明确记录阻塞。
- **错误案例：** 依赖个人未登记缓存，却声称其他人可重复构建。
- **自动检查边界：** 自动工具核正文与合同登记的一致性；技术机制及目标行为分别按实质审查和适用环境验收，不以字段存在替代语义判断。

- **主体与权威：** 构建维护者固定运行时、解析输入、资源和生成器；锁文件与实际解析/制品记录共同描述构建，不用个人缓存作隐含权威。
- **失败、并发与恢复：** 解析中断或制品生成一半不得覆盖最后可用产物；恢复核完整输入与摘要。并发生成使用隔离输出或发布前提；不可得资源记准确受阻而非成功。
- **合法邻例：** 不同平台有意生成不同二进制可以是可重复过程；若未承诺字节一致，不误用字节差异否认功能构建契约。
- **检查入口与边界：** 在获准干净环境按登记命令构建；故意移除个人缓存后仍满足依赖契约；声称字节可重复时另比较完整制品摘要。

4. 测试输入包括合法变化、边界、格式损坏、超时、重复请求、并发冲突、数据迁移与权限拒绝。测试数据不能冒充真实客户或实际生产记录。

6. 修复测试失败须先定位根因和失效链路。实现缺陷应修复实现；需求已变或测试本身错误时可修订测试，但须保存原失败、修订依据及需求差异，并验证仍适用的不变量。不得为隐藏失败而放宽阈值、删除有效断言、静默跳过或把缺陷固化为预期。
7. **验收**：测试的实际代码、版本、环境、输入、结果与记录可对应；区分测试已运行、测试未运行、预期跳过、环境不可用及真实业务验收未完成。

## 十三、性能、可靠性与资源成本
1. 依据真实用户负载和交付目的确定延迟、吞吐、启动、内存、存储、网络、显存、可用性、恢复时间和成本预算，按目标平台标识测量条件。

## 十五、可观测性、排障、恢复与事故证据

## 十六、版本、兼容性、发布与回滚
