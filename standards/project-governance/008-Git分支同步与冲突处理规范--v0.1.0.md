# Git分支同步与冲突处理规范

**文档ID：** STD-PG-008　**版本：** 0.1.0　**状态：** adopted　**生效日期：** 2026-10-30

**权威语言：** 中文；[英文全文](../../translations/en/project-governance/git-integration.md)保持相同条款ID。必须/不得为必要要求，应可经理由与等价保障偏离，可为可选。任何Git能力、分支名称或自动测试结果都不授予真实远端写入、发布或改写共享历史的权限。

## PGB-01 适用、角色、术语与分支命名

**输入与适用：** 适用于Git分支间和已核仓库间的同步、集成、冲突恢复、推送与历史保护；不规定每个项目必须使用GitFlow、固定主分支名或托管平台。操作者必须取得来源/目标仓库、分支完整ref、准确基线、写入范围、集成策略、共享情况及责任人。自动示例只涵盖完整本地合成仓，托管端权限/保护/排队、签名信任与真实LFS服务另验。

**角色与术语：** 贡献分支承载有限变更；集成分支接受已审内容；维护分支仅在确有多版本支持时需要。分支是可移动ref，远端跟踪分支是本地最近抓取的观察，不是远端实时锁；upstream是配置关系，不能从相似名称推断。快进意味着当前tip是目标tip祖先；分叉表示双方各有独有提交。共享历史包括已被他人使用的提交，不仅是主分支。

**动作/产物：** 项目应选择可解释的主题名，如`feature/parser`、`fix/cache-key`；维护角色命名按支持策略明确。必须先`git check-ref-format --branch feature/parser`核语法，再人工核语义、占用和负责人。语法合法不等于命名合理，单人单分支可合法采用。审查者负责内容取舍；集成者执行已定策略并交准确提交图；维护者管理共享历史与回退；允许一人兼任但不能把自审变独审。

**失败与验收：** 目标/权限/共享情况未知时保留待确认状态，不猜作私有可重写。自动`worktree`覆盖分支占用与合法邻例，角色意义及实际权限人工核。依赖为[工作区规范](007-Git工作区与本地操作规范--v0.1.0.md)、[领域总则](001-项目治理领域总则与职责接口--v0.1.0.md)、[质量与证据](011-测试质量门禁与证据规范--v0.1.0.md)、[采用与例外](020-规范采用例外与升级规范--v0.1.0.md)；独立采用须落实对应职责与证据接口，项目按准确版本记录采用范围。来源：GIT-REFNAME、GIT-BRANCH。

## PGB-02 集成前冻结可恢复状态

**前置与步骤：** 操作者必须确认当前分支、HEAD、索引、工作区及其他worktree；未提交内容按PGW-06/07保护。必须保存准确原tip及比较对象，不能仅依靠可能被后续操作改变的`ORIG_HEAD`。

```sh
git status --porcelain=v1 -uall
git branch --show-current
git rev-parse HEAD
git worktree list --porcelain
git log --graph --oneline --decorate --all
git branch backup/parser-before-integration <original-tip>
```

**输出与失败：** 记录原tip、目标tip、基线、干净状态、保存点和选定策略；备份分支应在本地、名字未占用且属于允许范围。发现他人写入、未解决merge/rebase或未知对象时不得继续叠加操作。分支备份保存提交，不保存从未提交的工作区。出错时先核实际状态再走对应abort或保存点恢复，禁止把硬重置作为一刀切。

**验收：** 自动`merge_conflict`、`rebase_conflict`分别验证干净前态和abort恢复；后者保存旧tip引用并核可达。人工确认未提交保护充分性和并发协调。合法邻例为在新worktree上试集成，原工作区保留；反例是用备份分支宣称已保存未提交草稿。来源：GIT-MERGE、GIT-REBASE、GIT-WORKTREE、GIT-BRANCH。

## PGB-03 fetch只更新所取对象与refs

**输入与动作：** 明确源和refspec，避免从未知配置推断目标。常规取主分支到远端跟踪ref：

```sh
git fetch --no-tags --no-recurse-submodules origin refs/heads/main:refs/remotes/origin/main
git rev-parse refs/remotes/origin/main
git rev-list --left-right --count HEAD...refs/remotes/origin/main
git log --graph --oneline HEAD refs/remotes/origin/main
```

**结果：** 该具体命令取得对象、更新指定跟踪ref与FETCH_HEAD，不将远端内容合入当前工作区。不得把它泛化为任意fetch refspec都不影响本地refs。`--no-tags`不声明项目无标签；未经决定不扩为`--all`、`--prune`或递归子模块。操作前后必须核当前HEAD、索引和文件；抓取成功不代表本地已同步。

**失败/恢复：** 抓取失败可能已有部分对象或某些状态变化；必须记录结果并重新核所需ref是否确实取得。身份不明、权限不足或连接中断时不反复盲试；结果未知先读状态。取回的提交还需内容与策略检查后才能集成。

**验收：** 自动`fetch_ff`在当前文件已暂存后又修改的状态下抓取，断言三层完全未变且跟踪tip更新；合法邻例是仅fetch后保留本地修改，反例是把fetch成功当已合入。人工核真实传输和refspec范围。来源：GIT-FETCH。

## PGB-04 显式选择快进、merge或rebase

**决策输入：** 已核两个tip、共同祖先、共享程度、项目历史策略和保存点。集成者必须在写前选一种策略并说明结果预期：

| 选择 | 命令入口 | 预期图变化 | 不得混淆 |
| --- | --- | --- | --- |
| 只接受快进 | `git merge --ff-only <target-tip>` | 若可快进则移动分支到目标，不新增merge提交；分叉拒绝 | 拒绝不等于内容冲突 |
| 保留双方历史 | `git merge --no-ff --no-commit <target-tip>`，审查后commit/continue | 非平凡合并保留双方父链，新增合并提交 | `--no-commit`单独不能阻止快进更新 |
| 重放未共享主题提交 | `git rebase <target-tip>` | 通常产生新提交身份并移动主题tip | 内容相近不等于提交身份未变 |

已在目标中而无新内容时不应强造提交。共享历史原则上merge或新增修复，不能仅因偏好线性图自行rebase。项目可选其他明确策略，但须另列其状态和验收，不借默认配置隐式改变选择。

**失败与恢复：** 无共同祖先、对象缺失或浅历史造成信息不足时记录原因，不默认允许无关历史。分叉拒绝后重新审图并按既定权限选择merge/rebase，不自动放宽为成功。未知实际副作用先核状态。

**验收：** 自动`fetch_ff`覆盖快进与分叉拒绝，`merge_conflict`检查双父，`rebase_conflict`检查新身份与新父；人工核策略适合性。合法邻例是私有主题重放；反例是改成`pull --no-rebase`绕过已指定ff-only，变异`pull-merge-instead-of-ff`实际生成合并并被原状态断言检出。来源：GIT-MERGE、GIT-REBASE、GIT-PULL。

## PGB-05 pull同时抓取和集成

**前置/动作：** 只在源、目标分支和策略已明确，未提交内容已保护时使用；必须给出策略，不依赖用户全局配置：

```sh
git pull --ff-only --no-recurse-submodules origin main
```

若项目决定合并或变基，可分别用`pull --no-rebase`或`pull --rebase`并明确相应其他选项；需要在抓取后审查精确tip时应拆为fetch再merge/rebase，而不是把pull当只读更新。

**状态、失败与恢复：** pull先fetch再尝试集成。ff-only拒绝分叉时当前分支/索引/工作区应保持前态，但跟踪ref或FETCH_HEAD可能已更新；必须分别核两阶段，不能报告“完全没发生任何变化”。若集成进入冲突，分别按PGB-06或07处理；不自动换策略重试。恢复后重新取实际图，不使用旧ahead/behind数。

**验收：** 自动`fetch_ff`验证线性快进内容、分叉拒绝、本地前态保留以及失败后跟踪ref已经更新；人工核真正远端和权限。合法邻例是ff-only在已同步或可快进时成功；反例是因抓取成功而将整个pull标通过。来源：GIT-PULL、GIT-FETCH。

## PGB-06 merge冲突解决与abort

**步骤：** 从已保护的干净状态执行选定merge。冲突时必须读取`git status`、`git ls-files -u`与冲突文件；普通双分支文本冲突可核三个索引阶段：

```sh
git show :1:path/to/file
git show :2:path/to/file
git show :3:path/to/file
# 编辑成符合两方需求的最终内容，然后：
git add -- path/to/file
git diff --cached
git ls-files -u
git merge --continue
```

阶段1为共同基底，2为当前侧，3为被合入侧；新增/删除类冲突可能缺某一阶段，不得把缺阶段当文件损坏。必须人工解释冲突取舍，检查无未合并项、无遗留标记，并运行受影响测试后才完成提交。盲目选ours/theirs或只删除标记不能证明语义正确。

**状态与恢复：** 未解决时HEAD仍在原tip，索引记录未合并阶段，工作区可能含标记，MERGE_HEAD记录另一父。放弃本次集成用`git merge --abort`，随后核HEAD、索引、文件及merge状态清除。若开始时带未提交内容，abort不保证重建全部原编辑；这正是前置保存必需的原因。不存在merge时不得盲发abort掩盖真正错误。

**验收：** 自动`merge_conflict`比较三个阶段的实际文本、冲突HEAD和MERGE_HEAD，验证abort完整回到干净前态，再重做并检查最终内容和两个准确父提交。`merge-ours-only`变异实际只保留当前侧，提交虽成功仍被最终内容断言拒绝。人工核业务合并正确性及非普通文本冲突。合法邻例为不同文件的merge无需手工冲突；反例是只看commit退出0便忽略丢掉对方功能。来源：GIT-MERGE。

## PGB-07 rebase冲突、continue与abort

**适用：** 已确认可重写的主题提交，原tip有保存引用，工作区干净。执行`git rebase <target-tip>`后，遇冲突必须逐提交读取当前补丁、未合并阶段和内容；rebase期间ours通常是新基底/已重放结果，theirs是正在重放的主题提交，不能机械沿用merge时“ours就是我的原分支”的想法。

```sh
git rebase --show-current-patch
git ls-files -u
# 人工解决当前冲突后：
git add -- path/to/file
git rebase --continue
# 若决定恢复本次rebase前的分支状态：
git rebase --abort
```

**结果与失败：** 解决后continue可能再遇下一提交冲突，必须重复核验到完成。`--skip`会舍弃当前重放补丁，不是通用解冲突；只有明确该补丁不应重放且记录其影响时才可选。`--quit`不等同abort，不恢复原HEAD。完成后必须比较新旧提交范围、最终内容、新父链、未处理改动及测试；内容等价不使旧审查的精确OID自动适用。

**恢复：** abort后核原分支与原tip、索引/工作区；若异常使abort失败，保留操作目录和文件，按保存引用逐项恢复，不删rebase状态目录伪装完成。共享情况未知则不能先做再补决定。

**验收：** 自动`rebase_conflict`验证冲突中HEAD、新基底/主题的阶段文本、abort原分支与三层、continue后新提交及旧tip仍可达；`skip-conflicting-commit`变异真实跳过补丁，被最终内容断言拒绝。人工核空提交、合并提交重放、重命名及业务等价。来源：GIT-REBASE、GIT-RESTORE。

## PGB-08 push范围与共享历史保护

**前置/步骤：** 必须核准确目的仓库、目标ref、已审本地OID及许可。推送应限定ref，不默认全部分支或全部标签：

```sh
git push origin <reviewed-commit>:refs/heads/feature/parser
```

成功后须读取目标ref确认准确OID；退出0不等于所有外部检查通过。非快进拒绝时应重新fetch、比较他人更新并集成，不能自动force。`--dry-run`只预演当时条件，不预留远端状态。

**例外机制：** 真正已获允许的私有主题改写，须列影响、受影响使用者和恢复OID。若使用lease，必须固定准确期望值，例如`git push --force-with-lease=refs/heads/feature/parser:<expected-old-oid> origin <new-oid>:refs/heads/feature/parser`。不带期望值的lease可能受后台fetch干扰；lease只保护ref并发条件，不判断改写是否许可或是否误删有效提交。未知共享关系不属于私有例外。

**失败与恢复：** 网络结果未知先查目标ref；禁止不核结果重复推送。目标仍旧值、已为预期新值、已被他人改为第三值分开处置。共享错误以新增修复或revert优先，禁止为了隐去错误改写证据。平台拒绝须按其真实原因处理，不绕开保护。

**验收：** 自动`push_history`在本地裸仓核非快进拒绝、陈旧精确lease拒绝、合并双方后普通push成功；`force-overwrite-shared`真的覆盖独立演示ref，由远端tip断言检出；另一私有演示ref验证准确lease机制可行。人工核真正平台保护、访问权和改写决定。来源：GIT-PUSH。

## PGB-09 revert、标签与失败回退

**动作与输出：** 撤销已共享普通提交的变更，应在干净状态执行`git revert --no-edit <bad-commit>`，审查新增提交、父链、内容和测试。它追加反向变更，不删除原提交。冲突时解决并`git revert --continue`，或`git revert --abort`后核前态。合并提交的revert须先选择并解释mainline及未来合并影响，不直接套普通提交例子。

准备候选标识时必须绑定准确提交并核标签对象及剥离目标：

```sh
git tag -a v0.1.0 -m "Candidate version" <reviewed-commit>
git rev-parse refs/tags/v0.1.0
git rev-parse 'v0.1.0^{commit}'
git cat-file -t refs/tags/v0.1.0
```

**边界与恢复：** 注释标签对象OID不同于被标记提交OID；轻量标签没有注释对象，不能声称已有签名。标签只是标识，不是发行批准。重名失败须核原标签不变，不能默认`tag -f`挪动已共享标签。错误候选可新增修正版标签及更正记录；推送标签、删除远端标签或发行另按真实权限。签名验证和信任链未运行时明确未验。

**验收：** 自动`revert_tag`检查原坏提交仍为祖先、新revert的父与内容、revert冲突abort及空提交失败；核注释对象类型、剥离身份和重名拒绝不变。`reset-shared-instead-of-revert`和`move-existing-tag`分别真实硬重置和强制挪标签，由新提交身份/标签不变断言检出。合法邻例为在新修复提交上创建新标签；反例是强改旧标签后声称旧验收仍对应当前内容。来源：GIT-REVERT、GIT-TAG。

## PGB-10 子模块与LFS适用性

**子模块输入与步骤：** 存在gitlink或`.gitmodules`时必须核每个仓库、路径、来源、所需提交及其独立权限；不能把父仓许可自动扩为全部递归源。核已授权路径后按需执行：

```sh
git submodule status -- deps/library
git ls-files --stage -- deps/library
git submodule update --init --checkout -- deps/library
git -C deps/library rev-parse HEAD
```

父仓保存mode 160000的提交指针，不保存子仓全部文件。默认checkout更新可取缺失对象并使子仓游离在已记录提交；`--remote`改用远端跟踪目标，不是锁定依赖恢复的同义词。子仓改动必须先在子仓审查与提交，再明确暂存父仓gitlink。更新失败、缺对象或子仓脏状态必须分别保留，不能force抹掉；无子模块且已核仓内容可登记不适用。

**LFS输入与边界：** 出现LFS属性/指针时必须确认扩展版本、真实对象可达性、存储/流量条件及许可。Git LFS是额外扩展；仅有Git提交或指针不证明大文件对象已取得。项目采用LFS须另有锁定版本操作说明，检查`.gitattributes`、实际文件内容/对象校验及另一工作区可恢复性。新增track模式不自动迁移历史对象；迁移历史属于另行评估的改写，不在普通pull恢复中顺手执行。

**输出/验收：** 自动`submodule_pointer`真实核gitlink、按记录提交检出及游离HEAD、子仓新增提交不自动改父索引、显式add后指针更新；不联网、不验证真实递归远端。LFS本套件未安装/运行，服务传输、配额和恢复均未验，不得写已通过。人工检查实际适用性：无LFS为合法邻例，已存在指针但插件缺失则是依赖待解决，不是不适用。来源：GIT-SUBMODULE、GIT-LFS（官方滚动介绍，仅有限机制命题）。

## PGB-11 验收入口、状态与交接

**可执行入口：**

```sh
python examples/project-governance/git_scenarios.py --scenario fetch_ff
python examples/project-governance/git_scenarios.py --scenario merge_conflict
python examples/project-governance/git_scenarios.py --scenario rebase_conflict
python examples/project-governance/git_scenarios.py --scenario all
python -m unittest tests.test_project_git_scenarios -v
```

模块为每次运行创建新的本地合成仓，隔离系统/全局Git配置，禁用hooks和非file协议；Python 3.10或以上的标准库加Git即可运行，本版实测Python 3.12.14和Git 2.52.0。该夹具隔离不是更改真实项目安全设置的建议。报告含命令、退出码、预期/实际、断言、图与内容；可用`--evidence-parent`指定已存在目录。成功报告落盘后回收临时合成仓，失败原件和日志保留；不得以预期失败命令非零就判整个场景失败，也不得忽略意外非零。

**交接必须包含：** 原tip与新tip、目标ref、策略、冲突取舍、未提交保存点、实际结果/退出码、受影响测试、未完成项、来源版本和责任接收者。执行者提供证据，审查者核内容与图语义，集成者核准确目标状态，采用者决定生效。没有真实远端结果时只声明本地完成；传输中断无法判断时保留未知。

**对应矩阵：** PGB-01/02→`worktree`及人工角色/前态；03/04/05→`fetch_ff`；06→`merge_conflict`；07→`rebase_conflict`；08→`push_history`；09→`revert_tag`；10→`submodule_pointer`及人工LFS；11→CLI报告/单元测试与人工交接。变异须触及命令语义，不能只改描述字段；合法邻例须仍通过。自动结果不能替代独立审查或采用决定。
