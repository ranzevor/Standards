# Git工作区与本地操作规范

**文档ID：** STD-PG-007　**版本：** 0.1.0　**状态：** adopted　**生效日期：** 2026-10-30

**权威语言：** 中文；[英文全文](../../translations/en/project-governance/git-workspace.md)使用相同条款ID。必须/不得表示适用时的必要要求；应表示可说明理由并提供等价保障的建议；可表示选项。软件具备能力不构成项目操作许可。

## PGW-01 适用、术语与责任接口

**输入与适用：** 适用于采用Git的普通完整工作区，包括初始化、克隆、检查、暂存、提交、暂存保存和多工作区。执行者必须取得目标路径、仓库身份、允许变更的文件和操作、基线提交、工具版本及责任人。新空仓的基线写“尚无提交”，不得伪填HEAD。裸仓没有普通工作区；子模块内部是另一仓库，按[分支规范 PGB-10](008-Git分支同步与冲突处理规范--v0.1.0.md#pgb-10-子模块与lfs适用性)另核。稀疏/浅/部分克隆、大型二进制过滤、文件系统大小写/符号链接差异不在本地示例的完整验收范围，必须单列适用性与补充检查。

**术语：** 工作区是磁盘上的当前文件；索引（暂存区）是下一次普通提交的候选树；HEAD通常引用当前分支，游离时直接指向提交，初始分支可尚无提交。提交对象标识不等于分支名；分支名可移动。未跟踪文件不在索引；忽略文件通常是不打算跟踪的匹配路径。干净指已按约定检查的索引、工作区与未跟踪项均无待处理变更，不等于无机密、无漏洞或测试通过。

**动作、输出与失败：** 操作者必须先记录上述输入；审查者确认逐路径差异和内容意图；集成者消费基线与提交身份；采用者决定适用条款及例外。缺权限、对象不明、操作在途、未知文件来源时不得猜测后继续写入，输出“未知/待解决”及所缺输入。可先完成不依赖该输入的检查。单人可兼任职责，但自查不得冒充独立审查。

**入口与边界：** PGW-02至09的命令和合成场景负责技术执行；人工核对象权利、采用决定、真实工作区及责任交接。依赖接口为[领域总则](001-项目治理领域总则与职责接口--v0.1.0.md)、[质量与证据](011-测试质量门禁与证据规范--v0.1.0.md)、[采用与例外](020-规范采用例外与升级规范--v0.1.0.md)；项目须明确这些接口的适用范围。独立采用时须先落实本条列明的等价接口，不要求购买平台。

**邻例：** 单人离线仓使用一份变更记录即可；反例是发现目录可写便视作允许覆盖他人文件。

## PGW-02 创建、克隆与初始身份

**前置：** 操作者必须确认新目录为空或不存在、来源已核、初始分支明确；不得把不明目录当成可重建目录。以下`repo`、`local.git`为受控示例路径，真实目标须逐项替换核验。

```sh
git --version
git init -b main repo
git -C repo symbolic-ref HEAD
git -C repo rev-parse --verify HEAD
git init --bare -b main local.git
git clone --no-local --no-recurse-submodules file:///absolute/local.git consumer
```

**状态与输出：** init建立仓库管理结构与尚无提交的分支；此时验证HEAD提交的非零退出是预期，不代表初始化失败。bare没有工作区。克隆空裸仓同样可无提交；克隆已有提交的仓库后必须核当前分支、HEAD、来源和检出内容，而不是只看目录已出现。`--no-recurse-submodules`不承诺扩展依赖已经可用。

**失败与恢复：** 克隆失败或部分检出必须保留错误和目标当前状态；不得因重试覆盖预存内容。确认失败目录仅含本次可回收临时输出后，才可选择新目录重试或按项目保留规则处置；已有仓库不明时只读识别。

**验收：** 自动入口`index_snapshot`验证未生分支，`fetch_ff`验证克隆后准确tip与内容；人工检查真实源、访问权、路径冲突及扩展依赖。合法邻例是空裸仓可被成功克隆但尚无提交；反例是将所有非零HEAD检查都判初始化失败。来源：GIT-INIT、GIT-CLONE。

## PGW-03 每次写前分清HEAD、索引和工作区

**输入：** 明确仓库根、分支或游离HEAD、待改路径、已知基线。操作者必须分别读取索引和工作区差异，并检查未跟踪与冲突项：

```sh
git status --porcelain=v1 -uall
git diff -- path/to/file
git diff --cached -- path/to/file
git ls-files --stage -- path/to/file
git ls-files -u
git rev-parse HEAD
```

**判读：** 无冲突时短格式第一列对应索引、第二列对应工作区；`MM`表示同一路径两层均有变化，`??`是未跟踪。冲突时状态含义不同，应读取未合并索引项而非套用普通两列解释。`diff`比较工作区与索引，`diff --cached`比较索引与HEAD；初始无HEAD时后者仍能显示新增暂存。脚本若接收任意文件名，必须使用NUL分隔格式并正确解析，不得按空格拆路径；本示例固定合成文件名不承担通用解析器验收。

**输出/恢复：** 输出基线、分支、三层差异与未处理路径清单。若读到未知改动或正在merge/rebase，先核归属与操作状态，不直接覆盖。观察期间他人修改时重新取样并重核，旧快照不是锁。

**验收：** 自动`index_snapshot`实际断言HEAD不变、索引内容、`MM`及两种diff；人工核文件语义和并发归属。合法邻例为同文件已暂存一个修复但另有未暂存实验；反例是仅检查`diff`为空便认定没有待提交内容。来源：GIT-STATUS、GIT-DIFF。

## PGW-04 逐路径暂存与提交

**前置：** 已检查当前索引全部内容，确认无他人或无关暂存；提交范围不由当前编辑器窗口决定。必须按允许路径暂存，复核暂存差异后再提交：

```sh
git add -- path/to/file
git diff --cached --stat
git diff --cached
git commit -m "Fix parser handling of empty records"
git show --stat --oneline HEAD
git status --porcelain=v1 -uall
```

**状态与输出：** `add`记录调用当时的内容；随后再编辑不会自动进入索引。普通无路径`commit`提交整个索引并更新HEAD；HEAD附着于分支时同时前移该分支，detached HEAD时不移动任何分支；必须验证新提交的父、树及剩余工作区。需要按块选择时可用`git add -p -- path/to/file`，选择后仍审暂存diff。`commit -- path`和`commit -a`具有不同内容选择语义，不能冒充已审索引的等价操作。

**失败与恢复：** 提交失败时必须核HEAD是否变化、索引是否仍在、工作区是否保留；不能只按提示重放。空变更提交被拒绝可以是合法结果，不应为了让命令成功制造空提交。暂存错路径但尚未提交时，已存在HEAD的仓库可`git restore --staged -- path`，此操作不丢工作区编辑；初始无HEAD须另核移出索引方案，不能直接套用。

**验收：** 自动`index_snapshot`以`base→staged→later-worktree`验证提交仅包含`staged`、无关b文件不被提交、工作区后改保留；`commit-all`变异实际改用`-am`并被内容断言拒绝。`revert_tag`验证空提交失败不改状态。人工检查提交原子性、内容与描述。来源：GIT-ADD、GIT-COMMIT、GIT-RESTORE。

## PGW-05 忽略规则不是移除跟踪或保密机制

**输入与动作：** 项目共享规则放`.gitignore`；仅本地辅助文件可用仓内`info/exclude`。必须先确认路径是否已跟踪，再检查具体匹配规则：

```sh
git ls-files -- path/to/file
git check-ignore -v -- path/to/untracked-file
git status --porcelain=v1 --ignored -uall
```

示例规则：

```gitignore
*.log
build/*
!build/keep.txt
```

**结果与失败：** 已跟踪的`tracked.log`仍可被修改并提交；匹配的未跟踪`ignored.log`不会因普通add而进入索引。忽略不清理历史，也不撤销已泄露秘密。不得为通过提交随意`add -f`；若确需跟踪例外，必须核真实内容、修改规则或记录明确例外再审差异。否定模式对父目录排除有约束，必须用实际路径测试，不能由字符串外观推断生效。

**输出/恢复：** 保存匹配来源、受影响路径及合法例外。误跟踪的文件须先核内容和所有者，再按允许范围移出索引并提交；若有敏感内容，转安全处置接口，不能宣称加ignore即消除传播。

**验收：** 自动`ignore_rules`验证既有跟踪仍可暂存、普通忽略拒绝、`build/keep.txt`合法邻例；`force-add-ignored`变异真正强行加入文件，由索引断言检出。人工核机密与排除范围。来源：GIT-IGNORE、GIT-ADD。

## PGW-06 未提交内容保护

**适用：** 切分支、合并、变基、恢复路径、删除工作区之前。操作者必须列出已暂存、未暂存、未跟踪和需要保留的忽略文件；针对每类选择已验证的本地保存方式，不得把“Git通常拒绝覆盖”当作完整备份。

**步骤与输出：** 先用PGW-03取样；已可独立提交的修改可形成经审本地提交；尚未完成的普通文本可按PGW-07保存；并行任务可按PGW-08开另一工作区。保存完成后验证内容、索引层与未跟踪项确已覆盖，再执行`git switch feature/parser`。默认stash不含未跟踪，`-u`不含被忽略文件；必须单独核后者是否需受控保存。

**失败与恢复：** 分支切换因覆盖风险失败时应核HEAD、索引和文件不变，而不是加force或`reset --hard`绕过。保存失败、容量不足、过滤器行为未知时，结果为未完成；保留原文件并解决保存条件。`clean`、强制checkout或硬重置均不是默认恢复步骤。

**验收：** 自动`dirty_switch`制造同路径未提交改动，断言switch非零且三层未变，再保存、切换、返回并恢复内容及未跟踪项；人工核被忽略文件、二进制和保存介质。合法邻例是创建独立worktree而不移动脏工作区；反例是为“同步”删掉尚未保存的本地草稿。来源：GIT-STASH、GIT-WORKTREE、GIT-SWITCH；保存充分性是项目要求，不是Git认证。

## PGW-07 stash保存、应用冲突与恢复

**前置/步骤：** 仓库已有提交且不在未解决冲突中。必须先检查现有stash，再记录本次保存的对象标识；数字位置可能随新stash移动。

```sh
git stash list
git stash push -u -m "Before parser integration"
git rev-parse refs/stash
git stash show -p -u 'stash@{0}'
git stash apply --index <saved-stash-oid>
```

**状态与输出：** 保存后核工作区、索引和未跟踪项；`apply`不从stash列表移除条目，`--index`尝试恢复暂存层。必须分别核内容与暂存边界，不把文件出现视作完全恢复。默认不优先用`pop`，以便验证完成前保留保存点。

**冲突恢复：** apply冲突时保留stash对象，记录未合并路径和文件；stash没有专用`--abort`。不要盲用merge abort。可在新工作区从保存点的第一父提交恢复，不动当前冲突原件：

```sh
git worktree add -b recovery/parser ../parser-recovery <saved-stash-oid>^1
git -C ../parser-recovery stash apply --index <saved-stash-oid>
```

确认原索引、工作区及未跟踪内容完整后，再人工整合冲突工作区并逐路径暂存/提交。需删除stash时，必须重新将列表条目解析为记录的OID，确认恢复验收及保留条件，再对准确条目`git stash drop 'stash@{n}'`；不得`clear`清空未知保存。`stash branch`成功时可能自动删除所用列表项，不应误当保留式恢复。

**验收：** 自动`stash_conflict`实际构造冲突，检查保存OID仍可读，并在新worktree恢复不同的索引/工作区文本和未跟踪文件；`dirty_switch`是无冲突合法邻例；`drop-save-before-verify`实际删除保存引用，由保留断言检出。人工核业务冲突取舍、忽略文件及删除许可。来源：GIT-STASH、GIT-WORKTREE。

## PGW-08 worktree并行与回收

**前置与动作：** 必须先读`git worktree list --porcelain`并确认分支与路径占用。新增另一分支或只读/实验游离工作区：

```sh
git worktree add -b feature/parser-check ../parser-check HEAD
git worktree add --detach ../inspect-candidate <commit-oid>
git -C ../parser-check status --porcelain=v1 -uall
```

**状态与输出：** 各worktree拥有各自HEAD和索引，但共享对象库与多数refs；不是独立克隆，也不是对共享分支写入的锁。一个分支已在别处检出时，普通add拒绝是保护，必须选择新分支或有意游离，不能常规加force。

**回收与恢复：** 先保存必要改动，核干净、提交有引用及保留条件，再`git worktree remove ../parser-check`；这不等于删除对应分支。脏工作区删除失败不得强制忽略。路径丢失或手工搬迁时先核实际位置与内容，可从主工作区运行`git worktree repair ../moved-parser-check`修复已核搬迁路径的管理关联。拟清理失效记录先运行`git worktree prune --dry-run --verbose`，确认不涉及离线保存点后才按保留规则执行实际prune；`prune`只处理失效管理项，不恢复文件，离线挂载不能仅凭不在磁盘就认作失效。

**验收：** 自动`worktree`验证重复分支拒绝、两索引独立、脏删除拒绝、提交后删除保留分支，以及游离合法邻例；`force-duplicate-worktree`实际绕过占用保护，由路径状态断言检出。自动范围不含离线挂载、repair/prune和含子模块worktree移动。人工核共享refs并发、挂载及回收许可。来源：GIT-WORKTREE。

## PGW-09 路径恢复与失败分类

**动作：** 操作者必须在恢复前明确来源和目标层，先保存待覆盖内容。已存在HEAD时：

```sh
git restore --staged -- path/to/file
git restore --source=<known-commit> --worktree -- path/to/file
git status --porcelain=v1 -uall
git diff -- path/to/file
git diff --cached -- path/to/file
```

**状态与输出：** 第一条仅将索引恢复到HEAD，保留工作区；第二条改变工作区为指定来源，不移动HEAD，可能覆盖编辑，且来源缺路径时可删除该已跟踪路径。必须核结果，不可称“只读撤销”。需要撤销已共享提交时使用PGB-09的新增revert提交，而非在此重写历史。

**失败/未知/恢复：** 退出非零必须同时读状态：预期保护拒绝、内容冲突、工具/磁盘失败分别记录；超时或连接断开导致结果未知时先核副作用再决定重试。不得自动把锁文件删除作为通用修复。已保存内容按其准确OID/路径恢复；没有保存点时明确恢复能力未知，不承诺reflog能找回从未入库的编辑。

**验收：** 自动`index_snapshot`验证仅取消暂存不丢工作区；`restore-worktree-instead-of-index`在暂存后再次编辑，错误恢复工作区实际丢掉后改内容并被断言检出。`revert_tag`验证失败提交与revert abort。其他指定来源覆盖、缺路径删除及真实故障恢复为人工适用检查，不由自动通过外推。合法邻例为有意恢复某文件到已审旧提交，且先保存现改；反例是无保存点执行覆盖后声称必能恢复。来源：GIT-RESTORE、GIT-REVERT。

## PGW-10 可执行验收与证据契约

**入口：** 在仓库根运行：

```sh
python examples/project-governance/git_scenarios.py --scenario index_snapshot
python examples/project-governance/git_scenarios.py --scenario all
python -m unittest tests.test_project_git_scenarios -v
```

模块要求Python 3.10或以上，仅用标准库，另需可执行Git；本版实测Python 3.12.14和Git 2.52.0。它为每场景新建合成目录和本地裸仓，隔离Git系统/全局配置，禁用hooks与非file传输；这属于示例夹具行为，不能套用于真实项目以绕开原有安全控制。命令不接收真实仓库或远端参数。可用`--evidence-parent <existing-directory>`指定日志父目录；`--min-free-bytes <n>`设置运行前空间底线，并预留8 MiB运行量。

**必须输出：** 准确版本、完整命令及退出码、预期与实际、断言ID、HEAD/索引/工作区/提交图摘要、错误、证据路径。成功场景先持久化报告再回收其临时仓；失败保留日志与原始场景，不覆盖失败后重跑。CLI全部通过返回0，场景失败返回1；运行前条件失败输出not-run并返回2，不应登记为测试通过。`--mutation commit-all --scenario index_snapshot`是有意失败，报告应在`index.commit-uses-reviewed-index`失败，而不是找不到Git或缺文件。

**判定与限制：** 每条适用要求必须关联实际检查或明确人工待核；通过、失败、未执行、未知、不适用分开。不适用须有条件证据，例如仓库无LFS对象；插件缺失不能据此把已使用LFS的项目判不适用。本套件证明有限合成Git状态转换，不证明真实项目内容正确、远端保护、凭据安全、独立审查或发布许可。

**来源与验收：** [来源命题表](../../sources/project-governance/git-operations.json)列出官方手册版本、章节及支持命题。发生版本入口重定向时，以实际文档版本为准。质量负责人核对中英文同 ID 条款、命令结果和待验项。合法邻例为自动场景通过但平台保护仍“未执行”；反例是测试数量直接等同全条款符合。
