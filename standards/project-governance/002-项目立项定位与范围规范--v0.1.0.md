# 项目立项定位与范围规范

**文档ID：** STD-PG-002　**版本：** 0.1.0　**状态：** adopted　**生效日期：** 2026-10-30

## 范围、术语和输入

适用于新项目、重大改向以及已有项目的范围变更；小修复可引用原立项并写差异，不重新立项。项目章程是问题、受众、业务终点、边界及进入/退出条件的记录，不是商业收益或资源承诺。决定者确认目的和范围，技术负责人判断方案与约束，执行者在所选范围内工作；未分配职责须如实标记。规范强度、唯一正文及四轴状态按[PGF](001-项目治理领域总则与职责接口--v0.1.0.md)。

## PGI-01 明确问题和业务终点

**输入与前置：** 问题来源、目标用户和现在的处理方式；尚无明确问题时处于discovery。

**操作步骤：** 1) 用一个可观察任务描述受众与问题；2) 写当前基线、交付后预期变化及不解决的相邻问题；3) 区分交付物与业务终点；4) 为成功条件给观察窗口、测量方式及来源，尚未测量的基线记unknown。

**输出与验收：** 章程中的problem、audiences、outcome、success_criteria能被同一场景解释；每个成功条件能判pass/fail/unknown，不把文件数量当用户结果。

**失败与恢复：** 没有可测数据时先列取得数据的方法或改成可观察的探索退出条件；不虚构提升比例。受众互相冲突时分组记录目标与优先级再决定范围。

**正例：** 离线CSV转换器的终点是用户可把指定编码文件转成已约定列顺序，非目标是云同步。

**直接失败反例：** “完成十个页面”被作为所有用户任务成功的唯一条件。

**合法邻例：** 可行性研究以获得可复现实验和明确可行/不可行边界为终点，不承诺正结果。

**检查入口：** `checks/project_governance.py`核成功条件身份、状态和测量字段；受众/问题和业务价值的真实性由决定者实审。

## PGI-02 划定边界及输入资源

**输入与前置：** 目标、已有系统/数据、参与者、环境、时间、预算或设备的真实可用情况。

**操作步骤：** 列in_scope、out_of_scope和约束；每项资源记提供方、可用状态、允许用途及缺失影响。区别技术依赖与外部决定，区分已承诺上限、估计和未知；输出、数据保留及支持范围也属于边界。

**输出与验收：** 每个主要交付物有范围归属；不能同一身份既列范围内又列排除。未知预算不自动当无限资源；待取得设备只阻断依赖它的活动。

**失败与恢复：** 资源失效时更新依赖和受阻范围，提出缩减/替代方案交决定者；不由执行者静默删掉已承诺功能。

**正例：** 输入仅为用户自行选择的本地文件，输出仅写目标目录，不需要账号系统。

**直接失败反例：** 因已有云SDK就自动加入付费托管和用户数据收集。

**合法邻例：** 预算未定的研究先执行已经具备条件的离线实验，其余活动blocked。

**检查入口：** 范围集合交叠、资源状态和依赖引用可自动核；使用权和资源承诺需原始决定。

## PGI-03 启动、暂停与退出条件

**输入与前置：** 范围、关键风险、负责人/待分配状态和阶段成果。

**操作步骤：** 为discovery、active、blocked、accepted、retired定义进入条件；启动至少有明确范围、当前可做工作及责任接口。退出条件分别写成功交付、不可行结论、取消或转交，不将取消记为成功交付。决定和状态事件带项目revision。

**输出与验收：** 当前状态有满足的进入依据；blocked指向具体缺失条件及解除方式；accepted必须满足所有必要成功条件。

**失败与恢复：** 关键前提变化时先保全已执行结果，记录影响，再由相应决定者调整阶段。外部未知结果未核实前不填写“没有执行”。

**正例：** 硬件不可用只阻断板上测量，文档与仿真工作仍有明确待办。

**直接失败反例：** 所有必要验收都是not-run，项目却因进度条满而accepted。

**合法邻例：** 项目以“不具备可行性”的证据满足预先定义的研究退出条件。

**检查入口：** 状态模型拒绝缺必要成果的accepted跃迁；是否应取消及谁可决定属人工事实判断。

## PGI-04 范围变更的差异与决定

**输入与前置：** 当前revision、原范围、 proposed_delta和需求来源；未改变目标的错字不作为范围扩张。

**操作步骤：** 逐项列新增/移除/修改、理由、受影响需求/接口/资源/成功条件和兼容风险。决定记录pending/approved/rejected及准确revision；批准后以预期revision比较更新范围，同时保留旧集合和决定，不只存最后一份文字。

**输出与验收：** 任一范围变化可回溯到旧新集合及决定；新revision与旧记录连续，陈旧并发更新被拒。

**失败与恢复：** revision不符时重新读取当前范围、合并差异并重新决定；批准结果丢失时核原决定身份，不创建重复变更。被拒的扩张不得通过改名为技术优化执行。

**正例：** 增加云同步前列账号、费用、数据和支持影响并获相应范围决定。

**直接失败反例：** 删除失败功能后覆写旧范围，宣布原目标100%完成。

**合法邻例：** 修正文档中的拼写不改变用户任务和成功条件，可按编辑流程处理。

**检查入口：** `apply_scope_change`有限模型核旧集合保全、决定状态及revision；批准真实性和变更必要性实审。

## PGI-05 风险、依赖与探索工作

**输入与前置：** 未知技术/业务条件、潜在影响、依赖的提供/消费关系。

**操作步骤：** 每项风险列触发、影响、监测方式、降低方法、剩余风险及处理责任。把未知转成有退出判据的验证工作；必要依赖列交付物和可接受状态。探索结果关联原风险，无效果数据时不得写已降低。

**输出与验收：** 关键风险有可执行的验证或处置；blocked工作能追到缺失依赖。依赖按[PGT](003-需求设计与验收追溯规范--v0.1.0.md)检查必要闭包。

**失败与恢复：** 实验否定假设时更新可行性和范围选择，不改写假设为事后符合结果；依赖永久取消时评估替代/退出。

**正例：** 先用脱敏合成文件测内存上界，再决定支持的最大输入。

**直接失败反例：** 把“待证明可行”改成“无风险”，但没有执行验证。

**合法邻例：** 已选用成熟库仍保留本项目独有的格式兼容验证，不要求重复上游全部研究。

**检查入口：** 核风险ID、依赖环和验证引用；影响程度、降低措施是否有效由专业审查判断。

## PGI-06 章程移交和采用接口

**输入与前置：** 已决定的章程、未决项、成功条件及后续负责人。

**操作步骤：** 将成功条件转成PGT稳定需求，向PGK交付工作项，向PGN提供治理条款适用依据。移交列接收范围、当前revision、待处理风险、资源访问交接及确认状态；没有接收人时标unassigned，不虚填团队。

**输出与验收：** 下游引用准确章程revision，能还原原问题/边界；接收确认不等于实现验收。

**失败与恢复：** 接收方无法取得输入时补交必要对象或保持blocked；离任者不通过删除历史来“清空责任”。

**正例：** 合成项目章程把SC-01映射到REQ-01和离线转换测试。

**直接失败反例：** 模板里的ExampleOwner被当作真实维护者已经确认。

**合法邻例：** 单人项目由本人承担立项和开发，独立审查事实另行处理。

**检查入口：** 模板及填妥实例见[项目治理实例](../../examples/project-governance/README.md)；工具核ID引用和状态，不认证真实交接。
