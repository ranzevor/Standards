# 体系架构与规范编制准则

**文档ID：** STD-L0-001　**版本：** 0.1.0　**状态：** adopted　**生效日期：** 2026-10-30

**规范性强度与术语：** “必须/不得”在适用条件成立且该版本被选定采用时为必要要求；“应/建议”允许有理由且保留等价保障的偏离；“可/示例”不产生额外功能义务。主体是实际承担决定、执行或核验职责的人/系统；权威是能支持相应事实的原始系统，不是摘要或标签。输入未知、未执行和不适用不得互换。本规范不指定采购平台、真实人员或所有产品必须新增的技术能力。 <a id="normative-strength-terms"></a>

## 架构

体系按以下职责分层：L0定义体系结构与编制方法；L1规定治理、适用、版本及例外；L2规定人类与Agent协作；L3规定通用工程实践；L4规定技术领域；L5规定语言、框架、引擎、运行时和平台实现约定；L6规定单个项目采用版本、具体参数、业务约束和实际验收。L1至L6为六层实施与治理结构，L0为结构说明；不得由编号推导无条件覆盖关系。

L2至L5可以组合采用，不以某个框架、组织规模或工具预设所有项目。领域序号仅分类，不表示业务优先级。个人、人类团队、Agent团队和混合团队均按实际职责与权限适用。

### ARC-01 核验合同

- **适用条件与主体：** 规范编制者及采用者；新增层级、领域或组成发生变化时。
- **输入、输出与权威：** 层级职责表、实际产品组成、适用决定。输出为职责与组合适用映射；权威是准确登记正文及真实采用决定，不是编号顺序。
- **必要动作：** 必须履行本章全部适用要求；相同标识下的章正文与核验合同共同组成义务，合同不删除或降低前文要求。
- **失败、并发与恢复：** 并行修订先固定共同基线，冲突按 L1 处理；未知适用性登记待判断，不默认全适用或全豁免。只有原组成与承诺仍不变时可复用旧映射。
- **产物与验收：** 逐个定位 L0–L6 和十六域，并从任一产品功能追到负责规范；两域共享对象须有提供/消费接口而非两个最终权威。
- **正确案例：** 只有离线 SQL 转换的工具不被要求增加云、账号和支付。
- **直接失败反例：** 按层号把 L4 草案自动置于已采用 L3 之上，或遗漏移动领域。
- **合法邻例：** 单一桌面产品只采用桌面与相关共性条款，移动能力不存在并有范围依据。
- **检查入口与证据：** `python checks/validate_all.py` 核准确文本/登记/案例结构；技术审查按本条逐项走读并记录对象hash、判定理由与实际证据。具体项目依 L6 真实入口检验，本仓不替代目标系统执行。
- **来源与消费接口：** 本条为体系组织设计要求；外部资料仅提供术语与安全开发过程参照，不声称外部标准规定本体系分层或角色。其来源依据与有限边界见[共性编制与治理来源](../../sources/common-governance.md)。下游按准确版本/hash消费，项目治理规定仓库产物流程，L6固定项目适用及实际证据。

## 编制与可检验性

每份规范至少明确：对象与适用分支、术语、不变量、机制、失败与恢复、合法邻例、检查入口、完成条件、来源及技术效力、上下层职责与变更触发。条件性机制不得被写成所有产品必须新增的功能。主题数量和关键词存在不能证明技术充分性。

需求—正文—检查—验收须以稳定条款身份关联。文本结构、抽象模型、单元/契约、集成/故障及真实业务验收分别报告。未执行、失败、部分通过、不适用和未知必须区分。每一结论绑定准确版本与证据；修改后复核受影响结果。

### ARC-02 核验合同

- **适用条件与主体：** 起草、合并或拆分基线/专题时的编制者与技术审查者。
- **输入、输出与权威：** 需求、已有正文、独立失效机制、验收对象和下游消费者。输出为稳定条款、条款到案例/来源/检查映射及专题边界。
- **必要动作：** 必须履行本章全部适用要求；相同标识下的章正文与核验合同共同组成义务，合同不删除或降低前文要求。
- **失败、并发与恢复：** 缺字段、主张无来源或案例不可判时退回修订；合并文须保留原义务、标识迁移及消费入口。并行改同条款先协调，不能靠附加同名合同覆盖。
- **产物与验收：** 对每条按输入到终态实际走读；变异只破坏关键机制时应失败，合法邻例只改变触发条件时应保留。工具仅核已实现的结构/模型。
- **正确案例：** 事务幂等专题定义意图/尝试、未知核对和可观察副作用次数，另一文只准确引用。
- **直接失败反例：** 把基线所有标题复制为十篇空专题，再以文件数宣告技术完备。
- **合法邻例：** 实验协议、随机性和统计可合并一文，若三类对象、失效与验收均有精确映射。
- **检查入口与证据：** `python checks/validate_all.py` 核准确文本/登记/案例结构；技术审查按本条逐项走读并记录对象hash、判定理由与实际证据。具体项目依 L6 真实入口检验，本仓不替代目标系统执行。
- **来源与消费接口：** 本条为体系组织设计要求；外部资料仅提供术语与安全开发过程参照，不声称外部标准规定本体系分层或角色。其来源依据与有限边界见[共性编制与治理来源](../../sources/common-governance.md)。下游按准确版本/hash消费，项目治理规定仓库产物流程，L6固定项目适用及实际证据。

## 生命周期

草案不自动生效。技术检查、独立审查、适用决定、实施采用及运行验收是不同事实。修订保留来源版本、差异、失败及替代关系；不以新的登记覆盖或抹除历史。任何规范制定均不自动授权费用、生产、数据共享、支付、签署或删除动作。

### ARC-03 核验合同

- **适用条件与主体：** 修改规范、登记审查、选择采用或声明实施结果的主体。
- **输入、输出与权威：** 准确版本/hash、差异、真实审查过程、采用决定、实际执行环境和原始结果。输出为互相独立的四轴记录。
- **必要动作：** 必须履行本章全部适用要求；相同标识下的章正文与核验合同共同组成义务，合同不删除或降低前文要求。
- **失败、并发与恢复：** 检查或审查对象变动则旧结论仅属旧hash；外部操作未知必须回查权威目标，保留原失败。结果更新使用版本前提，不让较旧回执覆盖新结果。
- **产物与验收：** 尝试把文档完整、独审通过、项目采用、实际实现通过互相替换均被拒；同一草案可内容待审而真实运行 not-run。
- **正确案例：** 编制完整的固件专题保持硬件验收未执行，并给台架输入/判据。
- **直接失败反例：** 文档全部有验收字段就将真实设备实现标pass。
- **合法邻例：** 纯排版且段落意义未变可轻量复核，但新文件hash、链接和生成物仍重新检查。
- **检查入口与证据：** `python checks/validate_all.py` 核准确文本/登记/案例结构；技术审查按本条逐项走读并记录对象hash、判定理由与实际证据。具体项目依 L6 真实入口检验，本仓不替代目标系统执行。
- **来源与消费接口：** 本条为体系组织设计要求；外部资料仅提供术语与安全开发过程参照，不声称外部标准规定本体系分层或角色。其来源依据与有限边界见[共性编制与治理来源](../../sources/common-governance.md)。下游按准确版本/hash消费，项目治理规定仓库产物流程，L6固定项目适用及实际证据。

## 领域分类

L4采用十六域：Web前端与用户交互；后端与分布式系统；数据库与数据工程；云基础设施与DevOps；AI应用与Agent系统；模型训练与AI科研；桌面与跨平台软件；移动应用；游戏开发与数字内容；CLI、SDK与开发工具；网络与实时通信；安全工程与身份系统；自动化与系统集成；嵌入式与边缘计算；商业交易与计费系统；开源项目与公共技术生态。跨域系统按真实组成组合适用，不强制实现不存在的能力。

### ARC-04 核验合同

- **适用条件与主体：** 新增领域、技术对象或跨领域接口时的体系维护者。
- **输入、输出与权威：** 十六域分类、已有领域边界、具体功能与权威数据。输出为领域覆盖矩阵和逐条提供/消费接口。
- **必要动作：** 必须履行本章全部适用要求；相同标识下的章正文与核验合同共同组成义务，合同不删除或降低前文要求。
- **失败、并发与恢复：** 未覆盖对象必须补足正文或明确有技术理由的映射；不能以未来计划关闭必要缺文。环形参考按共同接口和双方义务拆开，不构造相互批准环。
- **产物与验收：** 每域基线/专题可达且对象覆盖无空白；跨域案例从相同意图/状态走到同一权威事实，协议ACK不等业务提交。
- **正确案例：** 网络负责字节可靠性，交易负责付款状态，双方接口明确。
- **直接失败反例：** 因数据库已写持久化章节就省略桌面用户确认点与旧版本数据恢复。
- **合法邻例：** 游戏无交易能力时不强制引入账本，但其奖励持久性仍按实际状态要求验证。
- **检查入口与证据：** `python checks/validate_all.py` 核准确文本/登记/案例结构；技术审查按本条逐项走读并记录对象hash、判定理由与实际证据。具体项目依 L6 真实入口检验，本仓不替代目标系统执行。

## 验收

- 结构检查能定位各层职责和全部领域，不存在重复身份。
- 每条适用要求有检查入口和可观察完成条件；交换条款或证据时检查能报告错配。
- 未完成正文和未验证实现保持明确状态，不因索引已列出而声称完成。
- 真实工程、数据和业务证据保留在对应权威系统；规范目录只索引必要身份和结论，不汇入无关项目材料。

### ARC-05 核验合同

- **适用条件与主体：** 提交可审候选、迁移正文或更新检查工具时的编制/审查者。
- **输入、输出与权威：** 需求、完整正文、逐条来源、案例、检查入口、原始日志、独审与未执行目标合同。输出为精确可审版本。
- **必要动作：** 必须履行本章全部适用要求；相同标识下的章正文与核验合同共同组成义务，合同不删除或降低前文要求。
- **失败、并发与恢复：** 缺正文、未解析技术行、工具假通过、核心来源未核或实质阻断未闭环时不可登记完整待审；真实目标缺环境不冒充通过。修复后运行受影响与完整门禁并保留旧失败。
- **产物与验收：** 在准确候选运行登记/链接/结构/生成物/测试；逐条人工核机制、合法邻例和来源。外部目标以其真实命令/工具及判据另记 not-run/实际结果。
- **正确案例：** 工具对追加技术段直接解析并发现未登记，摘要变异另测。
- **直接失败反例：** hash先拒绝后声称解析器已识别错误案例互换。
- **合法邻例：** 合法空白换行可由规范化解析保留；需要内容重新绑定时不把语义等价误写成失效。
- **检查入口与证据：** `python checks/validate_all.py` 核准确文本/登记/案例结构；技术审查按本条逐项走读并记录对象hash、判定理由与实际证据。具体项目依 L6 真实入口检验，本仓不替代目标系统执行。

## 规范性用语定义接口

### ARC-06 规范性用语定义接口

- **适用条件与主体：** 编制者、解释规范的采用者及工具维护者；某文显式委托本规范的术语定义时适用。只消费本接口不意味着采用L0其余技术要求，不使草案或未决定采用的项目自动生效。
- **输入、输出与权威：** 输入为本规范的准确文档ID、版本、路径、全文SHA256、`ARC-06`及[唯一专门前言定义](#normative-strength-terms)。输出为`standards-definition-reference/1`引用：提供文档身份、接口ID、条款ID、定义锚点和完整段落SHA256；权威是该准确版本的前言正文，不是本文的转述、工具标签或另一份词典。
- **必要动作：** 先锁定提供文档与定义段，再由`python -m checks.definition_interfaces`导出引用。消费方声明采用的术语接口和触发条款，按该定义区分必要要求、有理由且保留等价保障的建议偏离、以及不新增功能义务的示例；本规范这一版本只保留前言一份定义。解释者仍须逐条判断适用条件与真实采用状态，不能仅由动词或接口存在推出执行权限。
- **失败、并发与恢复：** 缺失、重复锚点、错误提供条款、全文或段落身份不符时拒绝把引用登记为已解析；引用有效但项目适用/采用未知时保持未决定。先恢复准确规范或重新提出明确的新版本/摘要选择，不自动追随latest；并行修订以原身份为前提。旧版本按其保留快照解析，不借当前登记覆盖旧决定。
- **产物与验收：** 保存提供引用、消费者完整段落定位、逐条必要消费边及采用记录的适用事实。自动检查须在实际文件上区别缺提供方、同文错误条款和正确字典块；人工核读用语强度、范围和译文，不把段落摘要匹配当作词义正确。
- **正确案例：** 科研基线的各已选择条款消费本接口并锁定唯一前言；纯理论研究仍可不建训练流水线，必要要求只在其适用与采用条件成立时约束。
- **直接失败反例：** 因`ARC-02`也是合法L0条款，就把它作为词典提供者；即使文档版本与全文SHA256正确，接口解析仍须报告提供身份错误。删除提供引用后，不得以本地猜测补出词义并声称闭包完整。
- **合法邻例：** 两个消费者使用同一准确引用或仅重排引用JSON键，字典身份不变；消费者只引用这个解释接口，不因此被要求采购平台、增加训练或执行不适用的架构能力。
- **检查入口与证据：** `python -m checks.definition_interfaces`核稳定提供/定义块及必要消费集合；`resolve_definition`核实际引用端点。项目采用入口还须核选定提供条款及条件闭包。记录正常、缺失、错误条款和等身份邻例的原结果，真实采用与自然语言充分性另按相应审查准则判定。
- **来源与消费接口：** 中文术语是本体系的自定定义，单独保存在本规范专门前言；[RFC 8174第2节](https://www.rfc-editor.org/rfc/rfc8174.html#section-2)仅说明其英文大写关键词的特殊含义与一般英文的区分，不定义这些中文用语。下游通过准确文档/条款/锚点/段落身份消费，不复制规范正文到项目形成第二权威。
