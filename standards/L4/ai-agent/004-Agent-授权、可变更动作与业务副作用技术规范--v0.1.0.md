# L4 Agent 授权、可变更动作与业务副作用技术规范

**文档ID：** STD-L4-AI-AGENT-004　**版本：** 0.1.0　**状态：** adopted　**生效日期：** 2026-10-30

## 一、范围、执行权与领域分工

本专题约束模型产生的工具写入、外发邮件、发布、删除、支付、权限调整和产生额外费用等可变更外部状态行为。纯文本和真正只读应用无需引入审批平台、复杂协调引擎、收费服务或独立服务器。模型输出、工具调用提议、审批票据、目标服务受理、外部副作用与最终业务成功均为不同事实层级，不可互相推定。

组织级批准权以真实组织的制度权利与授权关系为依据。其他客户、数据所有者与外部财务动作按实际权利主体分别授权；不得虚构第二个组织审批人或将 Agent 自评当成人类批准。

## 三、40 项技术机制与验收

### 执行闭环与实现绑定

每条§适用时均由下表责任者在相应接受边界执行：输入须来自当前有效主体及权威状态；输出区分允许、拒绝、未知与已证实事实。模型提议、协议ACK、日志或摘要不能自签授权。并发接受使用预期版本/世代或等效条件；超时保留原逻辑操作、预算预留及核对责任。日志记录decision_id、输入/输出身份、原因和证据定位，不要求保存私有思维链。具体字段可复用既有系统。

| 组/条款 | 责任者及运行入口 | 权威输入 → 可观测输出 | 失败、并发、超时与恢复 | 兼容/合法边界 |
| --- | --- | --- | --- | --- |
| authorization-G01 / §01—§05 | 服务端鉴权责任者；`action.authorize` | 真实主体、对象方法及当前策略 → 限权能力或拒绝 | 等待后撤权立即影响接受边界 | 后台账号能力不等于用户能力 |
| authorization-G02 / §06—§10 | 动作规范化服务；`action.prepare` | 真实参数、收件方、后果及用途 → 稳定意图和参数摘要 | 目标漂移重新核权；未发提议不变事实 | 草稿与发送分权 |
| authorization-G03 / §11—§15 | 审批记录服务；`approval.issue/consume` | 有权人、对象、摘要及期限 → 绑定原操作的原子消费记录 | 双Resume只消费一次；ACK丢失可查原操作 | SDKsticky决定不覆盖当前业务权 |
| authorization-G04 / §16—§20 | 目标业务接受方；`action.accept` | 当前对象版本、ACL、票据及端点 → 权威拒绝或操作回执 | CAS解竞争；拒绝不切高权账号 | 原参数等价接续可用有效原许可 |
| authorization-G05 / §21—§25 | 副作用对账责任者；`effect.send/query` | operation_id、参数及目标幂等合同 → confirmed/unknown及真实收据 | HTTP未知不失败，过期去重窗不盲重发 | 供应方各端点语义分别登记 |
| authorization-G06 / §26—§30 | 多步业务协调者；`workflow.join/reconcile` | 每步操作与事件来源/版本 → 逐步结果及补偿待决集合 | 重复乱序不重复生效；补偿另有权 | 部分成功允许只补仍受权未完项 |
| authorization-G07 / §31—§35 | 委派及费用控制者；`delegate/resume/reserve` | 根权利预算和当前撤回 → 限权接续及守恒账本 | 恢复不清额度，不以事故提高权利 | 无依赖合法工作可继续 |
| authorization-G08 / §36—§40 | 业务验收责任者；`action.evaluate/accept` | 真实环境版本与业务合同 → 分层运行证据和真实业务结局 | 未测不以CI替代，关键越界独立失败 | 工程规范不制定经营资格 |

实现方将上述逻辑入口映射到[目标合同](../../../examples/ai-agent/target-contract.json)中的真实模块/命令，记录端点、准确版本、鉴权身份来源、输入输出与权威查询方式；无真实适配映射不声称目标已通过。有限参考模型及本地命令见[运行入口](../../../examples/ai-agent/README.md)，仅验证声明的控制不变量。

### 真实主体与最小工具授权

### §01 模型与真实身份分离
**机制：** 模型输出的 actor、admin、owner 等自报字段只是调用提议；执行器根据当前已认证用户、租户、工作空间和服务账号识别真实主体。

**验收：** 模型自称管理员仍无法删除其他租户的客户记录。

**执行绑定：** `authorization-G01`。**专用正例 P-authorization-01：** 服务认证主体决定权限。**直接失败 D-authorization-01：** 模型自报管理员却没有对应业务权限；预期：实际服务认证主体决定操作权。**合法邻例 N-authorization-01：** 模型actor字段仅作为候选数据。

### §02 方法与对象级能力
**机制：** 用户权限精确限定资源、操作、环境、方法、作用期限及副作用；Tool 名称、列表可见性或 SDK 设置都不能替代服务端鉴权。

**验收：** 只被许可查看订单的 Agent 无法修改其他用户订单。

**执行绑定：** `authorization-G01`。**专用正例 P-authorization-02：** 只读订单不能修改对象。**直接失败 D-authorization-02：** 订单只读授权被用于修改操作；预期：按对象和方法拒绝。**合法邻例 N-authorization-02：** 本人有权对象合法写可完成。

### §03 委派权限单调缩减
**机制：** 下游 Agent 的子任务、数据范围和工具调用权不得大于上游授权；全局访问令牌与财务身份不得为方便而直接传递。

**验收：** 翻译子 Agent 不能从上游拿到 Root Token 操作生产系统。

**执行绑定：** `authorization-G01`。**专用正例 P-authorization-03：** 翻译子任务不收RootToken。**直接失败 D-authorization-03：** 翻译子 Agent 请求上游全部管理能力；预期：委派缩权。**合法邻例 N-authorization-03：** 同域必要只读数据可受权传递。

### §04 服务账号与代表用户操作区分
**机制：** 后台服务账号具备的系统能力不等于当前用户具备这些能力；写操作须附属业务主体、租户和资源的真实授权上下文。

**验收：** 带有服务端高级凭据的 Agent 不能代表 A 用户修改 B 的账单。

**执行绑定：** `authorization-G01`。**专用正例 P-authorization-04：** 服务账号能力交集用户对象权限。**直接失败 D-authorization-04：** 服务账号代理客户跨租户操作；预期：真实用户与租户权限检查。**合法邻例 N-authorization-04：** 后台获准系统任务可用独立主体。

### §05 策略版本及当前授权
**机制：** 用户撤权、令牌过期、对象所有权更改、工具目录变化和审批等待使旧权限可能失效，每次实际动作前应重新核对。

**验收：** 已撤权客服的旧审批任务不能继续提交退款。

**执行绑定：** `authorization-G01`。**专用正例 P-authorization-05：** 排队后撤权使原票据失效。**直接失败 D-authorization-05：** 审批排队期间原用户撤权；预期：执行前复核当前策略。**合法邻例 N-authorization-05：** 权利未变的安全接续不重复确认。

### 动作规范化与副作用分类

### §06 行为提议与动作收据
**机制：** 模型自然语言、Tool JSON 参数、目标系统受理、外部实际改变和最终业务履约分别记录状态，不能靠模型自述改写权威系统事实。

**验收：** 只生成 send_email Call 参数不能报告邮件已送达。

**执行绑定：** `authorization-G02`。**专用正例 P-authorization-06：** send提议不当作送达收据。**直接失败 D-authorization-06：** 仅生成发送建议却标示通知已送达；预期：工具提议和结果分离。**合法邻例 N-authorization-06：** 已受理状态可真实报告处理中。

### §07 业务关键参数规范化
**机制：** 动作主体、目标对象、金额、币种、收件方、路径、URL、时间、环境和实际操作版本在审批前规范化并形成可追溯参数指纹。

**验收：** 审批 100 CNY 的请求不能变成 100 USD，也不能替换接收者。

**执行绑定：** `authorization-G02`。**专用正例 P-authorization-07：** 100CNY参数摘要绑定接收人。**直接失败 D-authorization-07：** 已批准参数中的金额和币种被改变；预期：批准和执行参数一致。**合法邻例 N-authorization-07：** 只改显示空白不改规范化含义。

### §08 真实副作用与可逆性分级
**机制：** 纯计算、只读、可重试写、外发、不可逆删除、权限变更和资金支出按后端真实后果分类；Tool Annotations 只作非权威提示。

**验收：** readOnlyHint=true 但实际 DELETE 的工具仍被禁止低权执行。

**执行绑定：** `authorization-G02`。**专用正例 P-authorization-08：** 真实删除受破坏权限闸。**直接失败 D-authorization-08：** 伪只读工具改变业务状态；预期：按实际方法限制副作用。**合法邻例 N-authorization-08：** 只读Hint不是危险动作赦免。

### §09 外部接收者与出站数据权利
**机制：** HTTP、邮件、Webhook、浏览器导航、HTML/Markdown 图片、重定向和附件均可能披露数据，服务端按真实接收目的地与可披露字段校验。

**验收：** 图片 URL 带客户 Token 不会因输出可渲染而被自动外发。

**执行绑定：** `authorization-G02`。**专用正例 P-authorization-09：** 渲染图片出口不带私密参数。**直接失败 D-authorization-09：** 渲染外部资源造成非必要信息披露；预期：出站目标和数据权利校验。**合法邻例 N-authorization-09：** 惰性纯文本链接可保留供分析。

### §10 最低必要动作选择
**机制：** 草稿、预览、模拟、只读查询与真实发送/发布/付费是不同权限等级；为完成普通任务不能自动添加新高影响能力或付费基础设施。

**验收：** 只读订单查询不会触发任何退款或创建收费云资源。

**执行绑定：** `authorization-G02`。**专用正例 P-authorization-10：** 草稿任务仅产生草稿。**直接失败 D-authorization-10：** 只读任务自动新增需要付费的操作；预期：限制在最小必要能力。**合法邻例 N-authorization-10：** 获准发送任务可执行必要外发。

### 真正人类审批与票据

### §11 审批精确对象及参数展示
**机制：** 涉及高影响动作时展示实际操作、对象、金额/币种、收件人、数据范围、环境、期限和影响，不接受含糊的“批准建议”代替业务批准。

**验收：** 用户批准保存草稿不等于允许群发客户邮件。

**执行绑定：** `authorization-G03`。**专用正例 P-authorization-11：** 确认画面与真实金额收件方一致。**直接失败 D-authorization-11：** 仅批准生成草稿却自动公开发送；预期：审批对象与操作级别对应。**合法邻例 N-authorization-11：** 同参数有效原批准可继续。

### §12 审批主体认证及资源权利
**机制：** 审批人的真实服务端身份和对具体对象的实际决定权都需核验；模型、外部网页、工具自述和虚构审批角色不能签发人类许可。

**验收：** 伪造“组织财务负责人已批准”的 Tool 文本不能通过资金门禁。

**执行绑定：** `authorization-G03`。**专用正例 P-authorization-12：** 真实审批人对该对象有决定权。**直接失败 D-authorization-12：** 工具文本声明某审批已通过；预期：从真实有权审批记录核验。**合法邻例 N-authorization-12：** 有权代理可按真实委托批准。

### §13 审批票据身份与原子消费
**机制：** 票据绑定 Action ID、参数摘要、真实主体、业务对象、批准人和时效；服务端原子占用/消费以避免并发 Resume 同一动作两次。占用绑定同一业务操作 ID；响应丢失后的恢复查询原操作和收据，不把已消费批准重新兑换为另一操作，也不因票据已占用而阻止原授权内的安全恢复。

**验收：** 两个 Worker 同时拿同一票据申请退款不能产生两笔有效退款。

**执行绑定：** `authorization-G03`。**专用正例 P-authorization-13：** 两个Resume只消费一个operation。**直接失败 D-authorization-13：** 两次并发消费同一审批票据；预期：原子消费限制重复操作。**合法邻例 N-authorization-13：** 同操作ACK丢失可查询安全恢复。

### §14 审批撤回、过期和参数漂移
**机制：** 用户撤回、接收人/金额/环境/工具变动或审批期限届满后，不得借原票据执行改变后的请求；必要时重新取真实有权主体许可。

**验收：** 批准给 A 汇款后，模型不能换成 B 收款仍重用批准。

**执行绑定：** `authorization-G03`。**专用正例 P-authorization-14：** 改接收人须新核原批准范围。**直接失败 D-authorization-14：** 审批完成后目标对象被替换；预期：参数变化重新批准。**合法邻例 N-authorization-14：** 原参数未变仍可复用有效票据。

### §15 SDK 人机中断与业务权利区分
**机制：** needsApproval、interruptions、alwaysApprove 是指定 SDK 的运行机制，不能替代应用服务端授权和 L6 商业/法定批准；不同 Tool 类型另核 Guardrail 的真实覆盖。

**验收：** alwaysApprove=true 不会自动允许生产环境清空数据库。

**执行绑定：** `authorization-G03`。**专用正例 P-authorization-15：** SDK自动批准不绕过服务权限。**直接失败 D-authorization-15：** SDK 自动批准机制绕过生产写限制；预期：服务端权限不得被绕过。**合法邻例 N-authorization-15：** 低风险工具可不启人机中断。

### 执行前最终授权及竞争条件

### §16 目标系统写入前最终门禁
**机制：** 无论审批前筛查、模型守卫或提示词结果如何，真实 Tool/业务服务在改变资源前仍按当前权限、对象及有效票据检查。

**验收：** 审批时有权、执行时失效的删除请求被拒绝且无副作用。

**执行绑定：** `authorization-G04`。**专用正例 P-authorization-16：** 目标写入前核最新对象ACL。**直接失败 D-authorization-16：** 批准有效但正式执行前权利已失效；预期：执行前最终鉴权。**合法邻例 N-authorization-16：** 读取展示完成不代表已可写。

### §17 审批前后守卫重新执行
**机制：** SDK 参数 Guardrail 和业务校验可能在审批前已通过；在等待后仍需于真正执行前按当前对象状态和有效参数重新评估，不只依据旧筛查缓存。

**验收：** 用户在等待中修改金额，旧输入校验不被当成新金额已获授权。

**执行绑定：** `authorization-G04`。**专用正例 P-authorization-17：** 等待后重验金额和对象状态。**直接失败 D-authorization-17：** 审批前校验通过，审批后金额变化；预期：执行前重验业务不变量。**合法邻例 N-authorization-17：** 无变化可复用有效结构校验。

### §18 对象版本与状态转换限制
**机制：** 退款、发货、删除和资源更新请求要包含必要前置版本/状态，采用条件写或等效保护拒绝竞争更新，避免两个 Agent 都宣称写入成功。

**验收：** 已取消的订单不会因旧版本计划继续发货。

**执行绑定：** `authorization-G04`。**专用正例 P-authorization-18：** 旧订单版本条件写返回冲突。**直接失败 D-authorization-18：** 旧状态版本尝试执行发货；预期：条件写和业务状态验证。**合法邻例 N-authorization-18：** 不同订单可独立并发。

### §19 拒绝时不得权限升级
**机制：** 鉴权失败、审批超时、无法核对对象或业务条件变化时进入明确拒绝/待核验状态，不能自动切换管理员账号、增大 Scope 或调用高权限备用工具。

**验收：** 403 Forbidden 后 Agent 不会为了“修复”而改用 Root 服务账号。

**执行绑定：** `authorization-G04`。**专用正例 P-authorization-19：** 403后不换Root备用身份。**直接失败 D-authorization-19：** 权限被拒后自动采用更高权限备用身份；预期：拒绝不能导致权限提升。**合法邻例 N-authorization-19：** 可在原权内修复无害参数。

### §20 工具/供应商更换应重新验权
**机制：** 更换 SDK、Tool Provider、支付服务、发送端或收件方时重新检查数据、权限、金额、费用和兼容性，旧审批不得自动跨实际接收者继承。

**验收：** 邮件工具切换到新外部网关后，不能沿用对旧供应商的客户数据外发许可。

**执行绑定：** `authorization-G04`。**专用正例 P-authorization-20：** 新网关接收客户数据重验许可。**直接失败 D-authorization-20：** 外部服务提供者变更仍沿用原接收许可；预期：新的接收者重验数据权利。**合法邻例 N-authorization-20：** 同供应方等价节点仍核能力。

### 幂等去重与真实回执

### §21 业务请求 ID 与参数同一性
**机制：** 对写操作以真实业务意图确定请求 ID、对象及参数摘要；同一 ID 改金额或收件方必须按不一致意图拒绝。

**验收：** 同一 payment request ID 改金额不能重复写入。

**执行绑定：** `authorization-G05`。**专用正例 P-authorization-21：** 同operation改金额拒绝。**直接失败 D-authorization-21：** 同一请求 ID 对应两组不同金额参数；预期：同键异参拒绝。**合法邻例 N-authorization-21：** 相同参数安全重试保留原意图。

### §22 幂等键保留期限
**机制：** API幂等有效期、错误缓存、参数比较、资源/账户范围和结果重试语义按具体供应商端点/API版本登记与实测；无明确保证不推定长期有效或所有方法通用。跨去重窗口、换提供商或结果未知时先查原逻辑操作与权威收据，不能仅凭同一Key承诺至多一次。

**验收：** 超出 Key 有效期的重试先查询权威支付状态。

**执行绑定：** `authorization-G05`。**专用正例 P-authorization-22：** 幂等键到期先核外部对象。**直接失败 D-authorization-22：** 幂等键过期仍被认为可以无限安全重试；预期：先核实外部实际资源状态。**合法邻例 N-authorization-22：** 端点无幂等能力明确未知处置。

### §23 超时与未知结果
**机制：** 网络断连、超时、502 和 HTTP 202 不证明外部 Side Effect 未发生；结果未知时先对账再安全恢复。

**验收：** 已受理付款响应丢失不能导致第二笔扣款。

**执行绑定：** `authorization-G05`。**专用正例 P-authorization-23：** 超时后保留unknown并对账。**直接失败 D-authorization-23：** 外部服务超时导致重复提交业务请求；预期：未知结果先对账。**合法邻例 N-authorization-23：** 确定原请求未发可安全派发。

### §24 受理、处理与最终完成
**机制：** HTTP/Tool ACK、处理中、资源已写、真实邮件送达与资金到账属于不同业务阶段。

**验收：** payment processing 不能报告客户已到账。

**执行绑定：** `authorization-G05`。**专用正例 P-authorization-24：** processing不报客户到账。**直接失败 D-authorization-24：** 异步处理中被报告为完成；预期：完成定义依权威业务结果。**合法邻例 N-authorization-24：** 目标合同只需受理时可报告受理。

### §25 业务回执真实性
**机制：** 必须从真实目标系统核对请求、对象、操作、时间、结果和收据；模型生成的 success 字符串不是回执。

**验收：** 伪造 JSON receipt 不会促使业务标为已结算。

**执行绑定：** `authorization-G05`。**专用正例 P-authorization-25：** 权威目标返回绑定操作回执。**直接失败 D-authorization-25：** 非权威消息自称操作成功；预期：查实目标服务的真实回执。**合法邻例 N-authorization-25：** 模型生成收据可作待核材料。

### 多步执行、部分成功与补偿

### §26 多步骤事实拆分
**机制：** 一个工作流的每个外部步骤分别记录真实结果与先后条件，不把任一步成功推定整个业务完成。

**验收：** 订单成功而通知失败时须分别报告。

**执行绑定：** `authorization-G06`。**专用正例 P-authorization-26：** 订单与通知两步骤分列状态。**直接失败 D-authorization-26：** 订单步骤成功、通知步骤失败；预期：多步结果分别记录。**合法邻例 N-authorization-26：** 可选通知失败不抹订单事实。

### §27 可补偿与不可逆副作用
**机制：** 支付、外发邮件、公开发布和数据泄露未必可以补偿，任务取消不代表已经发生的影响被撤销。

**验收：** 已群发邮件不能显示取消即撤回。

**执行绑定：** `authorization-G06`。**专用正例 P-authorization-27：** 取消不声称已群发邮件撤回。**直接失败 D-authorization-27：** 不可逆外发被任务取消误当撤销；预期：明确不可逆后果。**合法邻例 N-authorization-27：** 可逆动作可另获权执行补偿。

### §28 部分成功和待人工处理
**机制：** 多步任务分别记录成功、失败、未知和待确认，恢复/补偿决定依真实状态和有权人操作。批次恢复只允许未完成且仍获授权项继续生效；提供商幂等契约允许时可重放原批次请求，但已成功项不得再次生效，也不得为拆分批次随意更换原操作身份。

**验收：** 外部文章已发布、索引失败，重试前先核对文章 ID。

**执行绑定：** `authorization-G06`。**专用正例 P-authorization-28：** 已发布文章先查原ID不再创建。**直接失败 D-authorization-28：** 公开发布成功后索引失败触发重复发布；预期：查既有外部对象 ID。**合法邻例 N-authorization-28：** 有效批次去重可安全重放原批次。

### §29 Webhook 来源、去重及顺序
**机制：** 验证 Provider Webhook 来源/签名、事件业务 ID、重复与乱序，不能每收一次成功事件就再次发放权益。

**验收：** 同一订单成功通知三次只发放一次对应积分。

**执行绑定：** `authorization-G06`。**专用正例 P-authorization-29：** 重复webhook只发一次权益。**直接失败 D-authorization-29：** 外部业务通知重复到达引发重复发放；预期：签名来源与业务事件去重。**合法邻例 N-authorization-29：** 不同真实事件各自记账。

### §30 多执行者竞争
**机制：** Agent、人工及外部系统并行修改同一对象时采用条件状态变更、CAS 或等效业务冲突控制。

**验收：** 用户已取消订单后 Agent 不再按旧版本发货。

**执行绑定：** `authorization-G06`。**专用正例 P-authorization-30：** 人工取消先改版本阻旧发货。**直接失败 D-authorization-30：** 人工已变更业务状态、Agent 仍执行旧动作；预期：并发版本冲突控制。**合法邻例 N-authorization-30：** 无冲突对象可并行修改。

### 委派、持续授权和事件处理

### §31 委派权限归属
**机制：** 子 Agent 只继承实际获批的目标、对象、数据及期限，不得将“起草”改成“发送”或引入新高权工具。

**验收：** 下游准备客户邮件不会实际群发。

**执行绑定：** `authorization-G07`。**专用正例 P-authorization-31：** 起草委派不给发送能力。**直接失败 D-authorization-31：** 下游将起草子任务升级为发送；预期：委派权限范围不扩大。**合法邻例 N-authorization-31：** 已获发送委派可用限定对象权限。

### §32 恢复前重验
**机制：** 任务暂停、Checkpoint、重启和延迟执行后复查当前授权、撤销、外部实际结果及资源版本。业务授权有效期、执行许可租期与访问令牌期限分别核验，排队、重启和刷新 Token 不延长原业务授权；有效范围内的安全接续不增加同义审批。

**验收：** 旧 Checkpoint 不会恢复已取消的付款许可。

**执行绑定：** `authorization-G07`。**专用正例 P-authorization-32：** 旧快照恢复核当前撤回。**直接失败 D-authorization-32：** 恢复旧任务时忽略最新撤权决定；预期：恢复前重新鉴权。**合法邻例 N-authorization-32：** Token刷新不延业务授权期限。

### §33 支付与工具费用硬边界
**机制：** 按租户/任务/有权人批准的调用量、金额及服务费用限额停闸，重试、子任务和更换供应商不得绕过。

**验收：** 达额度上限时不创建额外付费资源。

**执行绑定：** `authorization-G07`。**专用正例 P-authorization-33：** 后代重试共享原根限额。**直接失败 D-authorization-33：** 重试和委派累积费用超过批准上限；预期：跨执行链硬预算。**合法邻例 N-authorization-33：** 不耗预算独立工作可继续。

### §34 审批执行证据隐私
**机制：** 审计包含真实批准主体、参数摘要、状态/回执关联和版本，不向公开 Trace 写入秘钥或客户敏感字段。

**验收：** 审计拒绝结果不泄露 Token 和银行卡号。

**执行绑定：** `authorization-G07`。**专用正例 P-authorization-34：** 审计参数摘要不写卡号Token。**直接失败 D-authorization-34：** 低权日志记录不必要的敏感业务内容；预期：审计最小化。**合法邻例 N-authorization-34：** 有权受控取证仍需最小范围。

### §35 事故停止与真实补救
**机制：** 发现越权或重复写入时停止关联能力、核对已发生 Side Effect 并按真实授权处理，而非仅修订 Prompt。

**验收：** 泄露发生后需追踪实际收件者和权限撤销。

**执行绑定：** `authorization-G07`。**专用正例 P-authorization-35：** 事故先核实际接收者及结果。**直接失败 D-authorization-35：** 外部操作事故仅靠修改提示词宣称修复；预期：处理实际副作用。**合法邻例 N-authorization-35：** 仅提议被拒不谎报已发生泄漏。

### 对抗回归与项目验收

### §36 能力导向攻击场景
**机制：** 实际写能力决定需覆盖的越权、重放、误发、费用、竞争及部分成功反例，而非用只读问答样本代替。

**验收：** 具有生产支付工具时必须检测真实对象权限和重复支付。

**执行绑定：** `authorization-G08`。**专用正例 P-authorization-36：** 写工具覆盖重放错参撤权。**直接失败 D-authorization-36：** 具写能力系统仅测试普通问答；预期：测试真实业务风险。**合法邻例 N-authorization-36：** 无写能力应用不用虚构支付测试。

### §37 模拟与真实阻断分级
**机制：** 静态条文、离线 Stub、真实 Auth、Provider 沙箱与 L6 生产各有独立验收，不用模型口头拒绝替代服务端执行阻断。

**验收：** 模型说拒绝但后台已外发时仍判防护失败。

**执行绑定：** `authorization-G08`。**专用正例 P-authorization-37：** 模型拒绝与后端拒绝分别取证。**直接失败 D-authorization-37：** 模型拒绝但工具真实执行了高影响动作；预期：以真实执行结果验收。**合法邻例 N-authorization-37：** Stub403只证明局部处理分支。

### §38 批准竞态和重放测试
**机制：** 覆盖票据双消费、审批后改参、撤权、幂等到期、乱序通知及外部未知状态的并发反例。

**验收：** 两个 Worker 不能都成功使用同一批准重复退款。

**执行绑定：** `authorization-G08`。**专用正例 P-authorization-38：** 并发票据与过期幂等组合测试。**直接失败 D-authorization-38：** 两个执行器同时使用相同批准完成业务；预期：审批原子消费和业务去重。**合法邻例 N-authorization-38：** 合法原操作安全恢复也需通过。

### §39 经营规则与技术规范分界
**机制：** 本专题不制定支付执照、银行入账、税务、售价与退款政策，实际经营责任在有权主体及 L6。

**验收：** L4 内容审批不能被作为个人账户可合法跨境收款的证明。

**执行绑定：** `authorization-G08`。**专用正例 P-authorization-39：** 经营许可由真实经营主体证明。**直接失败 D-authorization-39：** 工程技术合规被当成实际商户经营许可；预期：L4 不替代 L6 法律经营资格。**合法邻例 N-authorization-39：** 不涉及资金应用可不填银行条件。

### §40 工程交付与业务收据分离
**机制：** 源 SHA、真实部署版本、批准范围、权限检查和外部权威结果分别建证据；CI 合并不推定客户业务完成。

**验收：** CI Success 不能证明客户退款到账。

**执行绑定：** `authorization-G08`。**专用正例 P-authorization-40：** 源码部署与业务收据各自举证。**直接失败 D-authorization-40：** 工程 CI 成功但客户业务仍处于处理中；预期：真实业务收据另验。**合法邻例 N-authorization-40：** 仅交付文件时不虚构客户资金结果。

## 五、验证层级与真实业务条件

1. **静态与离线验收：** 固定真实角色、受保护对象、实际动作、审批参数摘要、调用 ID、状态版本和预期拒绝结果；包括撤权、参数改变、重复提交、未知结果和部分成功的测试。静态 Mock 不代替真实业务。
2. **L5 集成验收：** 在授权的隔离环境验证服务器的每次对象权限、批准票据原子消费、状态条件写、第三方幂等窗口、通知来源和外部事实对账。应保留准确 SDK、环境和版本；未批准生产资源不得被用于测试。
3. **L6 真实业务：** 只有具有实际财务、数据和运营权利的主体能批准生产、支付、退款、通知与资源变更。以真实外部系统状态和业务收据核验履约，不能将工程 CI 与账户/商户准入混淆。
4. **变化与事故：** 更换模型、工具提供者、用户权限、执行者、支付或数据接收方后应重验受影响的批准与业务条件；发生重复写入或数据泄露时，先暂停相关操作并核对外部影响。

## 六、生命周期与采用

项目按 L1 登记所采用的准确版本、适用条款和依赖关系。L5 选择并验证实际实现，L6 按真实权利及目标验收业务结果；实现验收以相应项目的执行证据为准。
