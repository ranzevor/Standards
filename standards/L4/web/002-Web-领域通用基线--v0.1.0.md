# L4 Web 领域通用基线

**文档ID：** STD-L4-WEB-002　**版本：** 0.1.0　**状态：** adopted　**生效日期：** 2026-10-30

## 规范范围与继承关系

适用于浏览器直接运行或呈现的 Web 网站、应用、后台界面、嵌入式 Web UI、PWA、SSR／SSG／CSR 混合前端，以及需向浏览器输出 HTML、CSS、JavaScript 或交互协议的系统。仅当实际项目存在相应功能时启用 SEO、离线、实时通信、公开无障碍指标等专项检查，不因为分类范围大而扩张业务功能。
内容必要性、权限、环境、科研／业务证据和交付责任由 L1 适用与权利决定、L2 协作、L3 证据与隔离及 L6 项目契约分别规定；规范治理按 [L1 全局治理补充规范](../../L1/001-全局治理补充规范--v0.1.0.md)；协作角色与 Agent 权限按 [L2 人类与 Agent 团队组织协作规范](../../L2/001-人类与-Agent-团队组织协作规范--v0.1.0.md)；通用架构、数据、源码、质量、发布与事故要求按 [L3 通用工程规范](../../L3/001-通用工程规范--v0.1.0.md)。本规范规定 Web 工程的跨技术通用约束和验收边界，是 **Web 领域通用基线**。HTML／DOM、CSS、浏览器运行时、页面渲染、状态系统、可访问性、安全等具体技术要求由相邻专题分别规定；框架、语言、工具链与版本相关实现规则归 L5。
Web 前端不自行决定商品权益、支付政策、客户合同、内容治理或数据使用目的。此类规则来自对应权利人批准的需求；浏览器界面将其准确实施，服务端或权威系统对敏感操作独立强制授权。

## 核验口径与消费接口

维护者负责落实本文机制，领域/API/存储提供者负责其权威保证，验收者从实际受支持入口观察结果。输入固定源码/构建、配置、数据/协议版本、角色/租户、目标平台、故障时序和预算；权威观察对象为**用户路径、DOM/可访问树、服务端业务收据与受支持客户端版本**。真实执行入口为**Browser DevTools Network/Accessibility/Performance、实际键盘/IME/AT、权威API查询**。逐章 P/F/N 分别为正常输入及判据、破坏该机制的直接失败变异、应继续成立的合法邻例；本章原有每项规则、原有验收与新增合同共同约束，不用单一通用案例替代具体子项。每个子项须在案例输入中保留其适用条件，并以自身原文规定的输出/不变量判定；复合章应拆记录各个观察量，不能以一个成功掩盖其他失败。

证据产物包括真实命令/用户动作、原始响应或事件、权威状态前后值、版本、时序、失败及恢复；尚无对应真实运行证据的场景状态为 `not-run`，标准库示例仅证明列明的局部边界。具体输入与命令见[执行入口](../../../examples/web-backend/RUNBOOK.md)，条款索引见[规范条款登记](../../../registry/requirements.json)，来源的有限支持命题见[逐命题来源映射](../../../sources/web-backend/claims.json)。

本文的跨组件约束与正例、失败反例、合法邻例由本规范综合定义；外部来源支持的机制及适用边界见来源表。项目架构、预算和业务规则由实际需求确定。L5 实现应映射到所选框架、SDK 或引擎；L6 按具体版本的提供者保证与受支持矩阵验收项目能力。

## 一、Web 项目需求与用户路径
1. 确定真实使用者、公开／登录／管理入口、主要任务和最终可观察结果；分别登记桌面、移动、键盘／辅助技术等确有支持需求的终端。
2. 对关键路径定义：入口 URL、身份／角色、前置数据、用户输入、状态转移、实际请求、成功结果、异常反馈、撤销或恢复路径与跨角色交付。
3. 业务字段和操作从领域契约中生成，不为简化界面任意遗漏金额、数量、版本、有效条件、来源、期限、权限或其他完成任务所需信息。
4. 不能仅以界面原型、静态截图、路由存在和页面成功加载证明真实用户任务完成。
5. 设计验收需包含合法差异样本，使输入变化在实际 UI、API、存储和后续导出中产生预期不同结果。

### WEB-001 核验合同

- **WEB-001-P · 输入/动作与合格判据：** 从直达URL以普通用户完成含金额/期限的任务→请求、持久结果和接收方一致。
- **WEB-001-F · 直接失败变异：** 只给首页截图且漏掉期限→拒绝任务完成结论。
- **WEB-001-N · 合法邻例：** 无账号的静态阅读页不增加登录流程。

## 二、浏览器运行与呈现架构
1. 根据流量形态、数据实时性、SEO、首屏性能、部署平台与安全边界选择 CSR、SSR、SSG、Streaming、增量生成或混合架构；不强制绑定某个前端框架。
2. 明确渲染责任、缓存责任和数据权威：HTML 预渲染内容、客户端再验证、远端数据和用户本地草稿各自有清楚来源与失效条件。
3. SSR 与客户端 Hydration 应使用一致的初始契约；日期、随机性、地域化格式、用户身份和异步数据不能无控制地产生首屏内容偏差及交互丢失。
4. 控制边界组件的状态与失败传播；复杂实时界面应识别高频更新区与低频区，避免无意义的整体重渲染。
5. 编译期、边缘运行时、服务器端和浏览器端的环境变量与可执行能力必须隔离，任何服务端密钥不能通过构建常量或源码映射进入浏览器产物。

### WEB-002 核验合同

- **WEB-002-P · 输入/动作与合格判据：** 同一路由按SSR/CSR各自约定启动→初值/密钥边界及失败隔离可查。
- **WEB-002-F · 直接失败变异：** 服务端秘密被替换进JS或首屏输入被接管清空→阻断。
- **WEB-002-N · 合法邻例：** 纯静态页不需Hydration。

## 三、组件设计、领域隔离与 UI 契约
1. 将业务领域行为、视图表现、请求／持久化适配器与设计系统职责分开，组件的抽象层次以实际重用和变化方向决定。
2. 共享组件以清晰的输入输出、焦点与键盘行为、错误状态和可访问语义约定为契约；组件封装不能侵吞调用方的业务决定。
3. 交互组件必须具备真实点击、键盘、禁用、加载、完成与失败行为；不允许只展示样式或跳转空入口。
4. CSS 组织和设计 Token 应可追溯到受批准的视觉规则；主题和动态样式不能破坏内容可读性、触控区域、对比度和系统缩放。
5. 对运行时插槽、富文本、Markdown、第三方 widget 等使用方注入内容，单独识别内容来源与 DOM 安全风险。

### WEB-003 核验合同

- **WEB-003-P · 输入/动作与合格判据：** 共享组件分别点击、键盘激活、禁用并注入富文本→契约一致且无越权DOM。
- **WEB-003-F · 直接失败变异：** 组件吞掉业务字段或只渲染无动作按钮→失败。
- **WEB-003-N · 合法邻例：** 无复用价值的局部组件不强制抽象层。

## 四、客户端状态与数据一致性
1. 区分服务器权威状态、URL 状态、表单未提交草稿、纯界面状态、持久本地数据及缓存副本，不混成一个全局可写数据源。
2. 关键业务动作由权威接口确认；浏览器本地修改、按钮动画或乐观更新不等于订单、资金、账户或真实数据已经成功变更。
3. 有乐观操作时定义失败回退、冲突重放、重复提交与被服务端拒绝的可见结果；对于不可逆业务动作不得凭乐观预测直接表示完成。
4. 多路并发请求以请求身份、版本或取消机制避免旧响应覆盖新状态；路由离开、组件卸载与用户撤销时核对残留异步操作。
5. 缓存键应包含影响结果的真实维度，如租户、账号、权限、语言、地区、查询参数或版本；跨身份切换必须清理或隔离原账号私有状态。

### WEB-004 核验合同

- **WEB-004-P · 输入/动作与合格判据：** 延迟A请求后切B身份并完成B查询→旧回包不得落入B视图。
- **WEB-004-F · 直接失败变异：** 只Abort但仍接受A迟到回包→失败。
- **WEB-004-N · 合法邻例：** 同账号不同对象的合法并行查询均可完成。

## 五、路由、导航与浏览器历史
1. 公开页面与登录页面的 URL 应明确资源身份与可分享参数，敏感一次性令牌不得随意写入可记录的查询参数。
2. 深链接、刷新、浏览器返回／前进、打开新标签、静态部署回退和不存在页面要有真实行为；禁止仅从某一 SPA 内部导航检查路由。
3. 用户离开未保存表单、切换租户、登录过期或外部回调完成时，按已批准业务规则决定状态保留、警告与恢复。
4. 页面转移时保持合理的焦点、标题、滚动位置和加载反馈，支持浏览器原生导航模型；不能以单页应用为理由破坏后退和深链。
5. 客户端导航的可访问性和后端权限校验分开验收：被隐藏的菜单不能替代实际鉴权。

### WEB-005 核验合同

- **WEB-005-P · 输入/动作与合格判据：** 直达/刷新/Back/Forward及离开草稿→URL/标题/焦点/保留策略一致。
- **WEB-005-F · 直接失败变异：** 仅内部push可用而深链404、返回跳错页→失败。
- **WEB-005-N · 合法邻例：** 外链/下载/新标签保留浏览器原生语义。

## 六、表单、输入与交易操作
1. 每个可编辑字段需有业务语义清楚的标签、单位、取值范围、默认条件、错误指向和可修正路径；必填校验、跨字段关系与服务端契约应一致。
2. 对真实时间、货币、数量、时区、国家和小数精度，输入及显示需与持久化含义一致；严禁通过前端格式化无提示地改变真实数值。
3. 提交时定义禁重策略、请求身份、服务器确认及错误恢复；按钮被禁用与幂等正确是不同层面的控制。
4. 附件、文件和批量导入需验证类型、大小、编码、字段语义、行级错误及用户可理解的导入结果；不可单靠扩展名与浏览器校验保证服务端安全。
5. 涉及金额、权限、删除和不可逆操作的确认机制以已批准业务规则决定，实际结果以服务端或对应外部平台为准。
6. 必需字段错误须能被定位和修复，不能仅变更输入框颜色或显示无法理解的技术枚举。

### WEB-006 核验合同

- **WEB-006-P · 输入/动作与合格判据：** IME输入金额与带附件重复提交→字段精度和服务端唯一结果可查。
- **WEB-006-F · 直接失败变异：** 禁按钮当幂等或格式化悄改金额→失败。
- **WEB-006-N · 合法邻例：** 只读表单不强制引入交易确认。

## 七、界面信息、反馈与状态表现
1. 每一页面只展示完成目标任务需要的业务信息、可用操作和必要条件；内部状态、堆栈、调试消息及工程流程不能通过空状态、提示框或异常路径进入用户界面。
2. 统一正常、空、加载、无权限、会话过期、网络失败、冲突、部分成功、恢复以及提交后回显状态的交互原则，不能将不同业务原因合并成“操作失败”且没有恢复方式。
3. 管理端同样遵循角色所需信息和操作准入，不因“后台”身份把工程内部诊断直接展示给非运维角色。
4. 重要变更和外部消息应区分已保存本地、已提交请求、已被服务端接受、已交付下游和真实生效，文案与实际业务阶段一致。
5. 异步更新必须给出合理反馈并避免无意义的消息噪声；Toast、模态框和轮询不能遮挡主要操作、打断输入或不断抢焦点。

### WEB-007 核验合同

- **WEB-007-P · 输入/动作与合格判据：** 受理后延迟完成并令一项失败→显示真实阶段和可操作错误。
- **WEB-007-F · 直接失败变异：** 队列ACK即显示已送达或向客户泄堆栈→失败。
- **WEB-007-N · 合法邻例：** 合法空集合不是网络失败。

## 八、可访问性与语义 HTML
1. 优先使用原生语义元素，保证页面结构、地标、标题层级、字段标签、表格头、按钮与链接的含义正确；ARIA 只用于补足原生 HTML 的实际语义缺口。
2. 所有可执行操作需有键盘可达路径、可见焦点、合理的焦点顺序与关闭／返回行为；对话框、下拉、选项卡、组合框、树形视图等复杂组件须按其真实交互模式实现。
3. 非装饰图像、图标按钮、媒体及状态变化需提供完成任务所需的文本替代或可访问通知；动态状态播报不得无故重复或打断用户。
4. 文字对比度、内容缩放、重排、触控目标、输入辅助和动画偏好应结合目标人群与可访问性验收覆盖。
5. **公共和正式交互产品的默认建议目标为 WCAG 2.2 Level AA**；项目 L6 按合同、法律与用户范围确认实际标准。未经相应完整页面和流程的检验，不得宣称通过 WCAG AA；并非所有隔离实验或内部临时可视化都需要同一认证程度。
6. 自动化辅助检查能发现部分语义与对比问题；真正的键盘操作、阅读器体验、页面缩放与动态控件仍需相称的手工或受控交互验证。原始规范：[W3C WCAG 2.2](https://www.w3.org/TR/WCAG22/)。

### WEB-008 核验合同

- **WEB-008-P · 输入/动作与合格判据：** 仅键盘及真实AT完成完整流程→名称、焦点、错误与替代内容可用。
- **WEB-008-F · 直接失败变异：** 自动扫描绿但对话框无法退出→失败。
- **WEB-008-N · 合法邻例：** 隔离无交互实验不虚构WCAG认证。

## 九、响应式布局、多设备与输入方式
1. 根据真实内容和操作密度定义布局变化，不以特定设备像素分辨率当作唯一断点；窄屏、缩放、长文本、系统字体放大和复杂表格应能使用。
2. 鼠标、触控、键盘及辅助技术的可用性按项目目标明确；不能把 hover 状态作为触屏和键盘用户获取必要信息的唯一途径。
3. 浮层、导航、表单、数据列表、图表、文件预览等在实际容器大小变化时避免被裁剪、遮挡或产生不可操作的横向滚动。
4. 固定导航、悬浮操作、虚拟列表和移动端软键盘需检验焦点、滚动位置、可见区域和页面恢复。
5. 当系统要求特定浏览器、嵌入容器或视图比例时，项目须记录范围与已验证环境，不能默认为跨平台通用。

### WEB-009 核验合同

- **WEB-009-P · 输入/动作与合格判据：** 长文本/窄容器/缩放/软键盘下提交→关键字段与按钮可达。
- **WEB-009-F · 直接失败变异：** hover唯一入口或overflow隐藏必需内容→失败。
- **WEB-009-N · 合法邻例：** 明确仅支持受控终端但仍实测该终端。

## 十、国际化、地域化和内容正确性
1. 使用产品实际批准的界面语言与术语，不把组织成员的语言习惯自动当作所有项目用户语言或内容策略。
2. 文案和动态业务值分离，支持复杂复数、数字、日期、时区、货币、地址、姓名以及符合目标语言的排序与断词，采用合适的本地化能力。
3. 语言切换、直接打开深链、错误信息、邮件／通知、导出与管理员界面的术语须按真实业务流程一致，不能只翻译静态按钮。
4. 文本扩展、不同字体、双向书写及对齐按目标语言处理；资产许可和字体加载策略独立核验。
5. 业务计算保持不受本地化显示形式影响；使用者输入的真实条件在格式转换后不丢失。

### WEB-010 核验合同

- **WEB-010-P · 输入/动作与合格判据：** 切语言、时区并导出同一业务值→计算含义不变、术语一致。
- **WEB-010-F · 直接失败变异：** 把本地化显示字符串重解析成不同金额→失败。
- **WEB-010-N · 合法邻例：** 不支持的语言不伪造翻译完成。

## 十一、API 请求、实时数据和错误恢复
1. 前端请求层对真实接口定义数据形状、身份与版本依赖、超时、错误分类、重试资格、取消与状态回读；不得吞掉重要业务条件、认证失败或协议错误。
2. 需要实时更新的页面明确 WebSocket、SSE、轮询或其他机制的选择依据，以及断线恢复、消息顺序、重复事件、重放窗口与视图一致性。
3. 按请求类型设置缓存、重试和限流逻辑：读取可以按条件重试，资金、订单、通知、权限等带副作用的操作必须遵守后端幂等与外部确认，不得浏览器自动盲重试。
4. 服务端权限错误、业务无效、版本冲突、网络故障与超时应映射为准确、必要的用户操作，而非暴露原始堆栈或数据库字段。
5. API 兼容、分页、过滤、排序和历史状态必须由真实协议保证；前端不能通过硬编码结果伪造可用性。

### WEB-011 核验合同

- **WEB-011-P · 输入/动作与合格判据：** 断流/乱序/超时后按操作键恢复→权威状态不重复。
- **WEB-011-F · 直接失败变异：** 所有5xx盲重试、硬编码API成功→失败。
- **WEB-011-N · 合法邻例：** 安全幂等读取按有限策略重试。

## 十二、浏览器安全与身份会话
1. 明确应用的 origin、身份体系、Cookie／Token 存储和会话撤销机制；所有敏感操作均依赖服务端或权威网关的实际鉴权，不以前端路由保护代替。
2. 会话 Cookie 应根据实际场景设置适当的 Secure、HttpOnly、SameSite、Path、有效期与轮换；选择跨域或第三方嵌入方案时核对浏览器限制及合法使用目的。
3. 按认证策略防止 CSRF，正确处理跨站凭据请求、Origin 等验证条件；CORS 是浏览器跨源读取机制，不能替代服务器侧资源授权。
4. 对 API 返回、用户输入、Markdown、富文本、插件输出和外部数据采用上下文正确的编码或净化；拒绝把不可信字符串直接当作 HTML／Script 或 URL 执行。
5. 能实施时配置最小化的 Content-Security-Policy，并按现有资源加载和外部集成条件测试；Trusted Types 可在支持环境降低 DOM XSS 注入风险，不得为兼容性方便默认开启不必要的 unsafe 脚本执行。
6. 按实际场景核对 HTTPS、混合内容、frame/iframe 嵌入、点击劫持、敏感 Referrer 泄露、跨窗口通信的 origin 与消息内容验证。
7. 第三方脚本和分析 SDK 需要明确来源、权限、注入范围、性能、隐私及被篡改风险；不能因为 SDK 由大型公司提供而默认信任。
8. 使用者输入和 Agent 工具返回均为不可信数据。安全基线参考 [OWASP ASVS 5.0](https://owasp.github.io/www-project-application-security-verification-standard/) 与 [MDN CSP](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy)，具体威胁和测试级别由 L6 与安全领域规范确认。

### WEB-012 核验合同

- **WEB-012-P · 输入/动作与合格判据：** 跨源/跨租户/富文本与撤销旧会话→后端拒绝无副作用。
- **WEB-012-F · 直接失败变异：** 隐藏菜单代鉴权或CORS放行即授权→失败。
- **WEB-012-N · 合法邻例：** 公开匿名资源可无会话读取。

## 十三、本地存储、离线与 PWA
1. 浏览器 localStorage、sessionStorage、IndexedDB、Cache Storage、Cookie、Service Worker 缓存的用途、保留与用户身份边界分别定义；不能把本地副本默认当作权威账本。
2. 跨租户／账号切换、登出、权限撤销和版本升级时，验证私有本地数据如何隔离、过期、清理和恢复；避免其他用户获取缓存内容。
3. 只有确有离线需求才使用离线表单、后台同步或 PWA 安装。必须明确离线可完成的动作、待同步状态、冲突合并、失败重试和用户确认。
4. Service Worker 版本与页面 JS／API 版本的兼容、旧缓存失效、更新回滚和首次安装情况需要测试；不使用无版本界限的缓存覆盖最新安全修复。
5. 触发通知、设备或后台能力时按真实用途获得所需浏览器和用户权限，不通过默认授权或外部脚本绕过。

### WEB-013 核验合同

- **WEB-013-P · 输入/动作与合格判据：** 离线换账号再联网→草稿、队列、缓存不跨身份投递。
- **WEB-013-F · 直接失败变异：** Worker旧缓存恢复A私有内容给B→失败。
- **WEB-013-N · 合法邻例：** 无离线需求不安装Worker。

## 十四、静态资产、字体和交付资源
1. 统一确认图片、图标、SVG、音视频、字体与第三方 UI 资源的来源、许可、版本及运行用途；生成资产的原始输入和派生路径必要时可追溯。
2. 按实际体验选用适当大小、格式、压缩、响应式资源和占位方式，避免破坏可识别性和产生 layout shift。
3. 字体加载关注体积、回退、许可和渲染偏差；跨语言字体不能仅以本机显示正常判断全部受支持语言已就绪。
4. 对无构建必要的大型资源使用有验收的加载策略；懒加载不能导致关键操作空白、图片错位或用户不可见的失败。
5. 构建产物与 source map、调试文件、敏感配置和测试资产分别管理；发行内容审查包含正常、异常与历史缓存路径。

### WEB-014 核验合同

- **WEB-014-P · 输入/动作与合格判据：** 字体/图片失败及旧缓存加载→主体可辨认、必需资源有版本来源。
- **WEB-014-F · 直接失败变异：** hash路径返回不同字节或source map泄密→失败。
- **WEB-014-N · 合法邻例：** 装饰资源失败可按任务风险降级。

## 十五、页面性能与真实用户体验
1. 性能目标由产品所面向设备、网络、页面交互、可访问性和业务优先级确定；对正式公共网站可采用 Core Web Vitals 作为基础体验指标。
2. 官方参考的 Core Web Vitals“良好”阈值：**LCP ≤ 2.5 秒、INP ≤ 200 毫秒、CLS ≤ 0.1**，以实际用户访问的第 75 百分位作衡量，移动和桌面适当分开。它们是参考目标，项目 L6 应声明是否采用及影响因素；单次本地 Lighthouse 评分不能证明真实访问达标。来源：[web.dev Web Vitals](https://web.dev/articles/vitals/)。
3. 识别首屏关键资源、Script 解析／执行、主线程长期任务、过量 Hydration、图片字体、布局抖动、过度动画和异步数据的实际瓶颈，优先基于 Profile／Trace 数据优化。
4. 使用切分与按需加载、合理缓存、预取／预加载等措施必须评估带宽、后台耗电、资源失效和重复请求，不将“更快”作为未经测量的结论。
5. 大表格、数据图、虚拟滚动和实时视图应评估频繁重绘、焦点保持、屏幕阅读器访问及可见结果稳定性，不以“FPS 高”替代任务可用性。
6. 目标用户网络环境、设备能力及业务页面数量不足以形成统计置信度时，采用可复算的受控性能测试与明确的测量限制，不制造虚假的群体分位数。

### WEB-015 核验合同

- **WEB-015-P · 输入/动作与合格判据：** 固定设备冷暖多样本并与RUM分开→任务耗时和统计口径可算。
- **WEB-015-F · 直接失败变异：** 单次Lighthouse分数宣称真实p75达标→失败。
- **WEB-015-N · 合法邻例：** 低样本项目报告受控测量而非虚构群体分位。

## 十六、跨浏览器与兼容策略
1. L6 明确支持的浏览器引擎、版本、操作系统、嵌入式 WebView／设备及退役政策，选择依据为用户要求、使用统计、平台能力与风险。
2. 新 Web API、实验特性、CSS 布局、WebGPU、权限接口等使用前检查目标兼容性；不能仅以某个浏览器支持就宣称所有用户可用。
3. Polyfill 和运行时特性检测需明确失败和降级方案，避免把不支持的关键业务功能静默变为无操作按钮。
4. 对重要界面执行至少一个非单一引擎的独立兼容检查，当实际只支持指定环境时须按项目决定登记且在对应场景实测。
5. 浏览器的无障碍缩放、隐私模式、第三方 Cookie 限制、存储配额、网络断线、严格 CSP 等会改变运行行为，按产品真实依赖测试。

### WEB-016 核验合同

- **WEB-016-P · 输入/动作与合格判据：** 支持矩阵各目标走主路径→版本/引擎/降级证据匹配。
- **WEB-016-F · 直接失败变异：** Chromium绿就宣布Safari真机通过→失败。
- **WEB-016-N · 合法邻例：** 单一受控浏览器按已定支持合同验收。

## 十七、SEO、分享、可发现性与公开内容
1. 仅对公开可索引站点启用搜索引擎有关的规范。认证后台、私人页面和隔离实验无需为 SEO 引入复杂渲染框架。
2. 公开页面的标题、摘要、结构化数据、Canonical、语言版本、站点地图和抓取控制需与真实内容、URL 和授权可见性一致；不能为搜索流量自动生成虚假业务声明。
3. 不在 HTML 元数据、预渲染缓存、机器人可见内容、OpenGraph 或预览图泄漏登录用户的私有数据。
4. 重定向、404、410、分页和国际化链接按实际部署的服务器响应与搜索索引行为验证；客户端页面看似可用不能替代 HTTP 响应正确。

### WEB-017 核验合同

- **WEB-017-P · 输入/动作与合格判据：** 匿名抓取公开URL及私密URL→状态/元数据不泄私有事实。
- **WEB-017-F · 直接失败变异：** SPA所有404返回可索引成功页→失败。
- **WEB-017-N · 合法邻例：** 登录后台无SEO需求。

## 十八、用户隐私、分析与反馈数据
1. 页面行为分析、错误监控、会话回放、A/B 实验和营销埋点先确认实际使用目的、采集字段、接收者、保留期限及适用的用户选择权。
2. 采集须避免把密码、Token、敏感表单、业务秘密、客户身份及内部运维状态经 URL、日志、像素或第三方脚本传播。
3. 统计指标应区分真实用户行为、自动化测试流量、爬虫和管理操作；实验或演示数据不能混入生产业务结算或产品指标。
4. 对法律要求的同意、撤回和数据删除机制，按实际地域、目的及合同规定执行；前端关闭开关须连接到实际收集停止或下游撤销。

### WEB-018 核验合同

- **WEB-018-P · 输入/动作与合格判据：** 撤回遥测选择并触发异常→实际停止对应采集且不泄字段。
- **WEB-018-F · 直接失败变异：** 前端开关关但SDK继续发送完整表单→失败。
- **WEB-018-N · 合法邻例：** 只保留有权且必要的诊断字段。

## 十九、Web 特有测试与质量门禁
1. 单元／组件检查重点验证可复用视觉逻辑与交互状态；协议检查验证字段与错误映射；浏览器集成和端到端检验从真实用户入口完成任务。
2. 主要流程至少覆盖导航、身份变化、表单、服务器失败与重试、历史数据、响应式、目标浏览器和必要的角色分离。对公共站点增加可访问性与所选性能指标。
3. 自动化检查应验证组件真实事件、API 请求和响应，而非仅测试事件处理函数存在；静态截图、DOM 快照和可访问性工具通过不等于完整可用性。
4. 对高风险业务还要覆盖快速重复点击、多标签并发、旧响应覆盖、新旧前后端版本共存、敏感数据跨身份缓存、离线重放和授权拒绝。
5. 对组件和 API 模拟结果，应明确未覆盖真实第三方平台和生产网络的部分；不能伪造外部交易、邮件送达或真实支付确认。
6. 所有回归与验收对应待合并的实际提交、构建包、目标浏览器和网络条件，并记录失败、条件性跳过与未执行项。

### WEB-019 核验合同

- **WEB-019-P · 输入/动作与合格判据：** 重复点击、多标签/旧响应/权限拒绝→真实请求和最终状态满足不变量。
- **WEB-019-F · 直接失败变异：** 只测函数存在或Mock支付即宣称外部到账→失败。
- **WEB-019-N · 合法邻例：** 等价且仍有效组件证据可复用。

## 二十、构建、发布、静态资源和回滚
1. 明确前端版本、构建依赖、运行环境、CDN 缓存、HTML 入口、后端 API、数据库 Schema 和 Worker／边缘脚本的兼容关系，确保可检验的发布版本标识。
2. 静态资源指纹与缓存策略应避免新 HTML 引用不存在的旧资源、旧 JS 调用不兼容 API、Service Worker 长期服务过期逻辑等跨版本故障。
3. 发布时检查真实用户入口、登录与深链、HTTPS 与回调、关键资源、静态托管重写规则、CSP 和重要接口授权。
4. 故障恢复考虑 CDN 缓存清理、浏览器旧标签、回滚时客户端／服务端的版本差异及不可逆外部写入；不能用“重新部署成功”替代真实用户可用性证明。
5. 正式产物中不要包含无关测试提示、内部工作流说明、真实凭据或不必要的开发依赖与工程诊断信息。

### WEB-020 核验合同

- **WEB-020-P · 输入/动作与合格判据：** 旧标签延迟import后发布/回退→资源、API、Worker兼容且草稿保留。
- **WEB-020-F · 直接失败变异：** 删旧chunk或回退代码即声称退款→失败。
- **WEB-020-N · 合法邻例：** 无构建静态站按真实文件身份发行。

## 二十一、发布验收矩阵
| 场景 | 验证入口 | 预期完成条件 |
| --- | --- | --- |
| 访客首次访问 | 新浏览器会话、直达 URL | 入口、页面语义和真实首屏内容完整 |
| 登录／角色变更 | 不同权限账户、切换与登出 | 服务端鉴权正确，私有视图及缓存不跨身份泄漏 |
| 正常表单提交 | 真实字段与服务端响应 | 必需字段保真、实际落库／处理结果准确反馈 |
| 无效或冲突提交 | 字段校验、409 类冲突、重复点击 | 准确错误、可修复状态、无重复副作用 |
| 网络断线／超时 | 中断请求、重新连接 | 显示真实状态、恢复逻辑和请求排重符合契约 |
| 导航与历史 | 深链、刷新、返回、未保存草稿 | URL 和焦点稳定，未保存内容按规则处理 |
| 屏幕尺寸变化 | 窄屏、放大、触控键盘 | 必要信息和操作不被遮挡或裁掉 |
| 辅助技术操作 | 键盘、阅读器、焦点与动态通知 | 达到项目选定可访问性标准及实际任务目标 |
| 国际化差异 | 目标语言、数字与时区 | 业务含义未变、重要提示完整且布局可用 |
| 不可信内容 | 富文本、外部响应、注入输入 | 无未授权脚本执行／泄密，权限边界不扩大 |
| 新旧版本共存 | 旧标签、CDN、Service Worker、API 更新 | 按兼容政策完成或准确提示恢复，不损害已提交数据 |
| 生产访问与运行 | 真实域名、证书、缓存与关键用户任务 | 目标版本可访问，接口接线、错误恢复与必要监控有效 |
## 二十二、验收材料与规范边界
技术专项目录见[规范登记](../../../registry/standards.json)；行业已有标准的引用与编制要求见[L0 体系架构](../../L0/001-体系架构与规范编制准则--v0.1.0.md)。本领域通用基线不替代这些具体规范的独立编制。
正式 Web 交付至少能关联：项目批准的角色／场景、实际源代码和构建版本、浏览器兼容范围、权限模型、API 与状态契约、业务关键路径、真实异常恢复、适用可访问性／性能目标、第三方资源来源、部署版本与运行证据。已有 PR、工单、CI 和发布系统能承载时直接复用，不另建平行台账。
本领域负责浏览器端及跨端 Web 交互契约；后端与数据权威、支付账本、基础设施、网络协议、安全系统的实现细则由各自 L4 领域规定。TypeScript、JavaScript、React、Vue、Svelte、Next、CSS 工具链和浏览器构建工具的具体版本和代码风格由 L5 规定，不把框架选择强加给无关项目。
22 个通用主题与 12 项静态场景的审查不等于完成 HTML／DOM、CSS、浏览器运行时或各技术框架的具体专项规范，也不等于真实浏览器、网络、服务端或客户任务验收。L4 技术子领域与 L5 具体技术栈仍需独立制定；项目 L6 选择适用条件并验证实际执行。
