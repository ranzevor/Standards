# L4 离线、缓存与 PWA 生命周期技术规范

**文档ID：** STD-L4-WEB-010　**版本：** 0.1.0　**状态：** adopted　**生效日期：** 2026-10-30

## 技术范围、适用条件与行业标准

本 L4 具体技术专题适用于明确需要**离线可用、可靠本地资源缓存、离线数据恢复、可安装 Web 应用或受限后台能力**的浏览器产品。网站仅需在线访问时，不因采用 Web 技术就必须实现 Service Worker、PWA 安装、Push 或离线写入。使用缓存而无离线业务需求的项目，仅采用实际涉及的资源与版本一致性约束。

- [MDN PWA Installability](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable)、[Storage Quotas and Eviction](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria) 与 [Web Platform Tests](https://wpt.fyi/)：安装行为、配额和兼容性指导；不代替产品实际运行验收。
浏览器内 Service Worker、Cache、IndexedDB 的使用方法属于本领域；特定框架 PWA 插件、生成清单、构建工具和运行时的具体 API 留给 L5。服务器事务、Push 服务、身份系统和云基础设施的权威实现由相应 L4 领域定义。项目 L6 必须确认真实功能、可用浏览器、设备与离线业务容忍度。

## 一、离线目标与能力契约
1. 在设计时分别确定**离线可阅读、离线可搜索、离线可编辑草稿、离线可提交到本地队列、网络恢复后可同步、安装到设备、允许推送通知**等目标。每项都要有真实使用者及业务验收条件，不把某项实现成功泛称“全站支持离线”。
2. 对核心离线页面明确哪些资源或数据在首次访问、首次完整下载、用户主动保存后才可用，列明未预先缓存的 URL、媒体、账户数据和外部 API 的真实限制。
3. 需要远端权威决定的价格、权限、余额、库存、订单与外部通知，即使本地能编辑或排队，也须区分“离线待提交”与“服务器已接受／业务已完成”。
4. 无需安装和后台能力的普通在线站点可沿用通用 Web 规范，按条件只采用缓存与版本验证，不产生形式性的 PWA 工作包。
5. **验收**：以产品承诺的用户路径、资源清单、初次联网状态和断网时机，证明各项离线能力及限制真实成立。

### WEB-001 核验合同

- **WEB-001-P · 输入/动作与合格判据：** 分别首次离线/下载后离线/本地排队→各项能力和限制准确。
- **WEB-001-F · 直接失败变异：** Shell显示当全站离线或本地入队即已提交→失败。
- **WEB-001-N · 合法邻例：** 纯在线站无需PWA功能。

## 二、安全上下文、注册、Scope 与控制权
1. Service Worker 需要符合平台的安全上下文与部署源约束，正式服务使用可验证 HTTPS；本地开发受信任回环地址的例外不能推广到生产 HTTP。
2. 明确 Worker 脚本 URL、注册 Scope、哪些页面将受控制、允许的路由和不能拦截的资源；不同站点或子路径共享 Worker 时避免错误覆盖其他应用。
3. 注册成功、active、controlling 某客户端是不同事实。首访页面可能在注册后仍未受到控制；不同已有标签可能由不同 Worker 版本控制。
4. 通过 Service-Worker-Allowed 等拓宽作用域的配置必须核对服务器授权、隔离目标与潜在跨应用影响，不能仅为避免部署问题随意覆盖整个域名。
5. **验收**：首次访问、刷新、新标签、路径越界、部署子目录和同源多应用分别验证实际 controller 与网络拦截范围。

### WEB-002 核验合同

- **WEB-002-P · 输入/动作与合格判据：** 子路径首访/刷新/新标签核controller→scope和实际控制一致。
- **WEB-002-F · 直接失败变异：** register成功当已控制或随意扩大根scope→失败。
- **WEB-002-N · 合法邻例：** 受信回环开发例外不等于生产HTTP许可。

## 三、安装、等待、激活与 Worker 生命周期
1. 设计注册、install、waiting、activate、redundant 与运行时停止／重启的状态转换，事件任务不得依赖单个 Worker 实例持续在内存存活。
2. 安装阶段的核心资源预缓存需要有失败处理。一个关键依赖失败时必须按发布契约决定整个版本是否可激活，不能留下混合版本且声称新版本完成安装。
3. **skipWaiting() 与 clients.claim() 会影响仍在运行的页面所受控制版本**，按 API／资源兼容、用户未保存草稿和当前操作决定是否立即激活，不默认对所有发布强制夺取旧客户端。
4. 使用 waitUntil 等事件生命周期延长机制只处理平台允许的有限任务；不能把它视作永久在线进程、精确任务调度器或无限运行保证。
5. **验收**：首访、重复注册、安装失败、等待新版本、多个旧标签、强制接管及 Worker 被浏览器停止后重启，资源与用户数据不损坏。

### WEB-003 核验合同

**必要机制补充：** skipWaiting使等待Worker可在旧客户端仍存在时进入激活；clients.claim使适用的未控制客户端被当前活动Worker控制。二者都不把已有页面JS自动替换成新版。监听controllerchange并核对页面/Worker协议，不能仅凭注册active就推断每页控制版本。

- **WEB-003-P · 输入/动作与合格判据：** install缺资源、waiting与强接管→旧版完整且任务可恢复。
- **WEB-003-F · 直接失败变异：** waitUntil当永驻、半缓存新版本仍报安装成功→失败。
- **WEB-003-N · 合法邻例：** 兼容且无在途写的版本可受控立即激活。

## 四、Fetch 事件与资源拦截
1. 选择拦截路径时区分页面导航、公开静态资产、公共数据读取、带身份的 API、文件上传、长时间流式响应及第三方请求；不能把所有请求默认经过同一缓存策略。
2. FetchEvent.respondWith 的响应由实际 API 契约决定，须关注是否及时挂接事件响应、网络失败、重定向、CORS／opaque Response 与无权读取的内容。
3. 对请求的 Method、mode、credentials、redirect、destination、URL 查询与必要业务头分别识别，特别处理带副作用的非 GET 请求，不让预取或缓存回放制造提交。
4. 自定义网络回退不得把真实 401、403、404、409、429、5xx 等服务器响应统统替换成“离线”页面；用户应该获得准确的业务状态及可恢复动作。
5. **验收**：真实网络响应、断线、明确拒绝、重定向、跨源 opaque 资源和提交等情形按实际策略交付正确结果，无额外业务副作用。

### WEB-004 核验合同

- **WEB-004-P · 输入/动作与合格判据：** 导航/API/上传/opaque请求分别拦截→状态不改写且respondWith及时注册。
- **WEB-004-F · 直接失败变异：** 把403/500一律缓存离线成功→失败。
- **WEB-004-N · 合法邻例：** 只拦公开静态GET可满足简单离线目标。

## 五、Cache Storage 与 HTTP Cache 的职责边界
1. CacheStorage 保存脚本显式操作的 Request／Response 对；HTTP Cache 遵循独立的 HTTP 缓存语义，数据查询库还有自己的业务 Query Cache。明确各自负责对象、优先级、失效与隔离，避免三个缓存来源相互覆盖。
2. Cache API 不负责自动依据 HTTP Cache-Control 维护业务新鲜度；使用 Cache.put、Cache.match 时必须由应用显式管理数据是否允许存入及何时更新。
3. Cache.match 的 ignoreSearch、ignoreMethod、ignoreVary 等选项可改变匹配语义；对带账号、租户、语言、区域或版本差异的资源不能无条件忽略查询与 Vary 头。
4. Cache.put 与 add/addAll 在允许的响应类型、状态及 opaque 行为上不同。不得缓存用户无权查看、错误或来源未知的内容并在之后作为可靠业务结果返回。
5. **验收**：不同身份、查询参数、响应类型、Vary 与缓存路径之间不会错误复用，Cache Storage 与 HTTP Cache 行为可以分开回读核验。

### WEB-005 核验合同

- **WEB-005-P · 输入/动作与合格判据：** CacheStorage/HTTP/Query逐层命中及Vary→身份和新鲜度不混用。
- **WEB-005-F · 直接失败变异：** Cache API被误当自动执行Cache-Control→失败。
- **WEB-005-N · 合法邻例：** 合法opaque缓存按API允许条件但不冒可读业务响应。

## 六、网络优先、缓存优先及失效策略
1. 根据真实数据类型选用 network-first、cache-first、stale-while-revalidate、只用网络或只用缓存等策略；不能因为“性能更好”就让交易、权限和更新操作离线复用过期数据。
2. 对 URL、浏览器身份、授权和时间敏感度明确缓存有效期、后台重新验证、缓存缺失与网络中断时的结果。缓存命中不表示内容已取得权威系统最新确认。
3. 静态指纹资源允许有相称的长缓存；HTML 入口、Service Worker 脚本、API 及数据 Schema 必须保证版本兼容，避免旧 HTML 引用已清除资源或新 UI 调用旧协议。
4. 网络返回 401／403、确实被删除的资源和用户权限撤销，需触发正确的权限与缓存更新。仍在使用的缓存副本不应因网络恢复而持续覆盖新事实。
5. **验收**：在联机、离线、断线恢复、资源已过期、服务器明确拒绝和跨版本更新时，命中的版本与可见内容符合项目契约。

### WEB-006 核验合同

- **WEB-006-P · 输入/动作与合格判据：** 联机/断线/过期/撤权重连→按资源策略选权威或受控陈旧。
- **WEB-006-F · 直接失败变异：** 过期权限/价格因cache-first继续用于写入→失败。
- **WEB-006-N · 合法邻例：** 指纹静态资产可长期cache-first。

## 七、Cache 的版本、容量与清理
1. 为 Cache namespace、资源列表、版本、适用身份／环境和迁移关联明确规则；不同业务产品与租户不能单凭相同路径或未分组命名共享同一可读缓存。
2. 新 Worker 激活时，可清除已经不受任何受支持版本使用的旧资源，但应先核实仍在运行的旧标签是否依赖相应 Cache，避免随意全量删除。
3. 浏览器缓存配额不可假定无限，按实际用户设备限制设置资源预算、旧数据淘汰优先级及缓存写入失败恢复。关键未同步草稿不得与可重新下载图片采用同等清理策略。
4. Service Worker.unregister() 取消注册，并不构成自动清理 Cache Storage、IndexedDB、HTTP Cache、离线队列与客户数据的完整操作。退出与清理须由相应权利条件和明确的迁移步骤完成。
5. **验收**：资源升级、Worker 取消注册、配额接近上限、数据删除和旧客户端仍在运行时，没有误删必需业务数据，也没有不必要地保留私有内容。

### WEB-007 核验合同

**必要机制补充：** 旧资源退役需覆盖受支持HTML/动态import/Worker/离线恢复的依赖闭包；仅当前clients列表为空或CDN一次清理不证明长期冻结客户端不再需要资源。依支持窗口保留可回源不可变字节或提供已验安全迁移。

- **WEB-007-P · 输入/动作与合格判据：** 旧标签延迟chunk、配额满与unregister→只清无依赖缓存且保护草稿。
- **WEB-007-F · 直接失败变异：** activate全删旧Cache或unregister当全站清除→失败。
- **WEB-007-N · 合法邻例：** 无受支持依赖的旧静态缓存可退役。

## 八、离线页面、降级与用户可见状态
1. 离线 Shell 只是能呈现的页面结构，必须与实际可取得的业务数据及可执行动作区分；服务端禁止的操作不能仅因缓存菜单可见就认为可执行。
2. 对首次离线访问、未缓存路由、过期账号、缓存缺失、网络波动和服务器处理未知，提供确实不同的可操作结果，不把一切错误合并为“您已离线”。
3. `navigator.onLine` 与 online/offline 事件只能作为连接状态线索，不能证明目标后端/API 实际可达。任务是否同步成功以真实请求及远端结果为准。
4. 在用户的语言、支持的辅助技术、缩放和设备上，离线状态、待同步数量、冲突与失败恢复必须可读取且不会阻止访问已有合法草稿。
5. **验收**：首次访问后突然断网、刷新未缓存页面、服务器 500 但网络仍在线、权限过期与重连场景的反馈真实、准确和可操作。

### WEB-008 核验合同

- **WEB-008-P · 输入/动作与合格判据：** onLine真但API500、首访未缓存→准确区分不可达/拒绝/无数据。

## 九、离线草稿与持久化数据模型
1. 对允许离线编辑的资源建立数据身份、提交快照、草稿版本、修改时间、对应账号／租户、权威服务端版本和同步状态，不能只保存无来源的表单文本。
2. 使用 IndexedDB 或其他适合存储保存离线工作时，事务、Schema 版本、迁移及回滚契约须与所选浏览器真实能力匹配；不要把本地数据当成生产账本。
3. 离线期间身份已变更、业务规则过期或数据保留权限改变时，禁止自动把旧身份草稿提交到新账号，需按实际合同恢复或交由用户重新确认。
4. 对敏感草稿或未同步内容评估存储环境、设备共用、XSS 威胁、存储过期、用户清理及本地泄漏风险；不能把浏览器侧加密包装成服务端数据权利或授权的替代品。
5. **验收**：长时间离线、标签关闭、设备空间不足、浏览器清理、Schema 升级、退出与再登录后，按事先声明的保证恢复或准确识别无法恢复，不虚报永久保存。

- **WEB-009-F · 直接失败变异：** 无身份草稿自动送到新账号→失败。
- **WEB-009-N · 合法邻例：** 无法保证设备故障恢复须准确说明而非虚报永久保存。

## 十、离线写入队列、幂等与最终确认
1. 只有项目确需离线操作的业务才建立**待发队列**；队列状态至少区分本地已保存、等待发送、已尝试、服务端已接受、业务最终完成、拒绝、结果未知及需要人工处置。
2. 每项待处理的外部写入具有稳定的业务唯一标识、授权主体、依赖与必要操作参数；发送后需通过对应服务端事务和幂等契约确认，不能由前端单独承诺“恰好一次执行”。
3. 离线重复编辑、撤回和操作排序需确认业务依赖；早于权限变化的写入可能需要重校验或拒绝，不自动批量重放资金、删除、客户通知等高影响动作。
4. 请求超时、页面关闭、Worker 被系统停止时，队列记录与服务器事实可能不一致；重试前查询权威结果并根据安全重试资格判断，不盲目重复产生副作用。
5. **验收**：离线排队、双标签同时发送、发送中断、服务器已提交但响应丢失、授权撤回与业务重复标识下，无重复写入及错误成功提示。

### WEB-010 核验合同

**必要机制补充：** 逻辑意图ID在安全重试间保持不变，每次发送另分配尝试ID；事务ID、事件ID、投递ID和Trace ID不得代替它。权威查询暂未发现记录、读副本落后、日志缺失、客户端超时均不证明原尝试不会随后提交。只有目标端对同意图实行覆盖所有在途/迟到尝试的原子唯一性，或有已安装的栅栏/终止与线性化屏障证明原尝试不再可生效，才可依合同重发；否则保持结果未知并继续有权核对，不新建意图绕过去重。有限去重保留窗须覆盖目标最后可能接受该意图的时刻、重放和恢复窗口；不能只比较本地派发时间。窗外仍可迟到时使用永久领域唯一性、目标拒旧期限/世代或有权人工核对。

## 十一、冲突检测、合并及数据保真
1. 离线客户端可能持有旧服务器版本；按业务对象采用版本条件、ETag/If-Match、服务器修订号、字段级冲突或其他已批准策略判定，不能将本地“最后写入”无条件覆盖服务器。
2. 自动合并仅适用于能够证明不变量不冲突的字段／操作；资金、权益、权限或有复杂领域依赖的数据需要权威服务器及相应责任主体处理。
3. 合并时不得丢失原始输入、修改者、有效条件、数量、时间、记录关系和必要审计证据；发生不可自动修复的冲突时，用户应获得明确的选择和恢复方式。
4. 多端与多标签的数据版本、清理、撤销及最终提交必须互相对应；不能因为某一标签显示“同步完成”就将所有待发动作删除。
5. **验收**：两个离线分支分别编辑、服务器同时更新、重连后的版本冲突、局部成功与人工冲突解决均保留真实业务差异。

## 十二、Background Sync 的受限能力
1. 一次性 Background Sync 只能在目标浏览器实际支持的环境中作为**提高重新联网后执行机会**的机制使用，不把它作为用户命令被系统持续处理的可靠保证。
2. Periodic Background Sync 属于更受限、实验性的浏览器功能，权限、平台实现和实际执行间隔由用户代理决定；即使注册成功，也不得承诺某个精确时刻或固定周期执行。
3. 对必须保证最终交付的业务，明确页面重新打开、用户触发重试、受权服务器侧任务、权威结果回读等实际可用的补充路径。离线任务只在用户设备中排队时，网站服务器不可能凭空取得未上传的数据。
4. Sync 事件可被重试、延迟或不触发。每次执行应遵从实际授权、幂等、有限执行时间和结果持久化约束；禁用或不支持时系统仍要给出准确状态与可用恢复入口。
5. **验收**：不同浏览器、仅前台可用、后台同步不可用、反复触发、系统限制、断网时间长及页面重开后，排队任务安全恢复且不虚报时间保证。

## 十三、安装清单、应用身份与启动
1. 项目确需可安装 PWA 时，根据已核实的 Web App Manifest Working Draft 确定 name、short_name、icons、id、start_url、scope、display、方向、颜色等实际被目标平台使用的配置；不要求所有网页有安装入口。
2. manifest 的 Scope、导航 Scope、Service Worker Scope、缓存作用域和后端数据权限可能不同，必须分别核实；用户通过安装图标启动的 URL 也需经过服务器授权。
3. 是否展示浏览器安装提示以及安装后的行为取决于平台、用户操作和浏览器政策。manifest 验证通过不保证 beforeinstallprompt 会触发，也不保证所有系统提供相同安装体验。
4. 安装、更新、卸载、快捷方式与浏览器普通标签并存时，核对用户身份、本地草稿、应用图标及发布版本；不能用 PWA 安装状态作为额外业务权限。
5. **验收**：在项目声明支持的 OS/浏览器上，从网站进入安装、直接启动、返回网页、升级／移除和深链访问，得到正确的页面与权限。

**来源与适用边界：** [Web Application Manifest，2026-10-16 Working Draft §1、§4、§5](https://www.w3.org/TR/2026/WD-appmanifest-20261016/) 支持启动元数据、应用/导航 scope 和可选安装交互；它不是 Service Worker scope、安装提示保证或后端授权协议。

## 十四、推送与通知（按需）
1. 仅对用户明确需要的消息、监控或业务事件启用 Push／Notification；客户端通知权限与服务器向某订阅推送的许可、订阅归属和用户选择须分别管理。
2. Web Push 的推送连接与载荷由适用协议及浏览器端 Push API 定义；Push API 最新公开版本为 W3C Working Draft，不可把草案发布状态记成正式 W3C Recommendation。
3. Push 事件和通知点击可能在页面不活跃时发生，实际 Service Worker 启动和设备限制由浏览器控制；不得依赖每次推送一定到达、按时到达或用户一定看到。
4. 推送设备、账号、租户或订阅被撤销时，服务器应停止无权发送和更新订阅状态；点击通知重开页面需重新执行身份／资源权限检查。
5. **验收**：用户拒绝通知、订阅失效、跨账号设备、服务暂不可用、重复 Push 和点击过期资源时，不泄漏消息内容、不虚报送达且有合理恢复。

## 十五、存储配额、持久化与设备失效
1. Cache Storage、IndexedDB 与其他浏览器存储共享与受用户代理约束的存储配额。estimate() 的 usage/quota 为估算，不构成真正可分配空间或永久保留契约。
2. 默认 best-effort 存储可能被回收。若确需重要离线数据可请求 persist() 并读取返回结果，但用户选择清理、浏览器策略、设备损坏或账号迁移仍会限制数据保证。
3. 各类缓存资源与用户原创未同步数据应有不同淘汰策略；缓存配额不足时优先清理可重新获取的内容，不随意销毁用户尚未提交的必要工作。
4. 无法满足本地持久化要求的产品应调整已批准的功能设计或提供真实的数据迁移／备份链路，不能只在文档里声称“离线数据永久保存”。
5. **验收**：低可用空间、persist() 被拒绝、隐私模式、站点数据删除、配额错误、浏览器升级及跨设备迁移，实际剩余数据与产品承诺一致。

### WEB-015 核验合同

- **WEB-015-P · 输入/动作与合格判据：** 配额耗尽/persist拒绝/清数据→保留策略与真实剩余数据一致。
- **WEB-015-F · 直接失败变异：** estimate数值当承诺可分配空间、persist当永不丢→失败。
- **WEB-015-N · 合法邻例：** 可下载图片优先淘汰不等同丢未同步草稿。

## 十六、账号变化、私有缓存及信息隔离
1. 同一 origin 的 Cache Storage 不是按登录账号自动隔离的私有缓存。缓存名称、URL 和匹配条件应包含实际授权维度或对敏感内容禁用共享缓存；不能把错误复用当作浏览器权限控制。
2. 用户退出、切换租户或服务端授权收紧后，应使不可再访问的数据不能从旧 Cache、IndexedDB、旧标签和通知入口继续被错误提供；必要清理须保护用户有权保留的未同步数据。
3. 带身份 SSR 页面、支付、账户和高风险 API 不应通过通用离线 fallback 返还其他账号或过时的敏感结果；动态资源的授权必须最终由服务器验证。
4. 第三方离线包、静态资产和 Web Worker 代码不能在未授权的背景网络通道向外传播用户私有资料；外部同步目的地及数据用途仍遵从现行 L1/L2 安全与权利约束。
5. **验收**：用户 A 保存后退出，B 登录同一设备，离线访问、恢复网络、推送点击及多标签场景均不会取到 A 的无权私有数据。

### WEB-016 核验合同

**必要机制补充：** 每次异步落地同时核对账号/租户世代、对象身份、查询/导航序号与必要数据版本；取消请求只是节约资源，不替代落地守卫。退出/换账号先推进世代并停止旧可见性，迟到Fetch、Worker、刷新令牌、IndexedDB读取、推送与多标签回调不得重新填入新账号缓存或队列。有权保留的旧账号草稿可隔离封存，不自动提交给新账号；对已经交付给外部主体的历史字节不宣称能通过登出物理撤回。

## 十七、新旧 Service Worker／客户端版本协作
1. 发布对象包括 HTML 入口、JS/CSS 指纹资源、Worker 脚本、预缓存清单、IndexedDB Schema、后端 API 和离线队列协议，所有需要共同运行的版本应有明确兼容窗口。
2. 新 Worker 不得在旧页面仍依赖旧资源时盲目删除全部旧 Cache；旧 Worker 与新 Worker 可能同时间存在于不同页面，必须按照实际客户端控制关系实施迁移和清理。
3. 如果必须使用 skipWaiting/clients.claim，应评估已打开页面的数据结构、Hydration 状态、运行中提交和未保存输入，必要时要求安全刷新、状态迁移或用户确认。
4. 对不可兼容的数据 Schema、授权策略或高风险安全修复，建立可检测的旧客户端降级、强制重新认证或受控迁移，而非偷偷重复提交或无条件丢弃未同步草稿。
5. **验收**：旧标签保持打开时发布、新标签启动、Worker 接管、强制刷新、切换服务器版本、旧缓存被清理及迁移失败等组合，用户数据与副作用符合已批准契约。

## 十八、发布撤销、卸载与恢复
1. 暂停或回滚服务端版本不自动回滚用户设备上的 Worker 与所有 Cache；事故恢复需要分别确定哪个客户端版本受控制、哪些本地数据存在以及如何修复错误缓存。
2. 下架 PWA、注销 Worker、关闭推送、禁用离线功能或停止原站点，应按实际权限、合法保留期和客户已产生的权益处理资源及待发队列；不能仅用 unregister() 宣称已完成所有离线数据清理。
3. 重要安全事件可能需要改变 Worker 脚本、缓存清理逻辑、会话验证和恢复提示，但不能在没有授权和证据的情况下强制删除所有用户数据。
4. 生产事件后要验证外部入口、真实用户版本、旧标签数据、离线队列与服务端状态，一次成功部署和单台设备刷新不代表问题全部消除。
5. **验收**：新版本失败回退、过期 Worker、卸载后重新访问、恶意或损坏缓存、离线队列仍有待提交项及权限撤销时可安全恢复。

## 十九、性能、资源与安装体验
1. 每个离线资源包及持久化数据结构须有可测的体积、安装／更新流量、缓存命中、首访成本、CPU、内存、磁盘与联网恢复预算；不能因为用户设备负责存储就认为没有运行成本。
2. 预缓存与预取需结合真实访问路径、设备网络及本地资源限制，不应默认下载应用所有路由、超大媒体或未获授权的数据。
3. Worker 在网络请求路径上的额外计算、长尾流式处理和不合理的缓存复制可能退化实际用户体验，需与不注册 Worker 的对照基线比较。
4. 定期后台能力受限时不允许通过无价值短周期页面轮询制造持续运行，耗费用户流量或绕过浏览器保护。
5. **验收**：在冷启动／暖启动、弱网、离线、低存储、旧设备、新旧版本并存条件下测量实际任务可完成率与资源消耗，不单看缓存命中百分比。

### WEB-019 核验合同

- **WEB-019-P · 输入/动作与合格判据：** 冷暖/弱网/低存储对照无Worker基线→任务完成及资源预算可算。
- **WEB-019-F · 直接失败变异：** 高命中率掩盖CPU/流量或后台无价值轮询→失败。
- **WEB-019-N · 合法邻例：** 只预缓存核心小资源包可合法满足范围。

## 二十、技术验证与发布静态场景矩阵
| 场景 | 故障／条件 | 实际合格证据 |
| --- | --- | --- |
| 首访与次访离线 | 尚无 Worker，随后完成预缓存 | 仅承诺已缓存部分可离线使用，首次离线失败反馈准确 |
| Scope 边界 | 同源不同应用或子路径 | Worker 只控制受权范围，不误拦截其他应用 |
| 安装与激活失败 | 核心资源缺失 | 不会发布半完整新资源集或破坏仍可用旧版 |
| 旧标签与新 Worker | skipWaiting／clients.claim | 旧操作、草稿、资源与 API 兼容或安全迁移 |
| 明确 HTTP 拒绝 | 403、404、500 但仍有网络 | 不会错误显示离线成功或缓存其他身份的结果 |
| 缓存键差异 | 语言、账号、参数、Vary | 无错误匹配、跨身份读和陈旧数据误用 |
| Cache 清理 | 卸载 Worker、缓存配额和版本迁移 | 可删资源适当清理，未同步草稿与业务证据按权利保留 |
| 离线草稿保存 | 断电／关标签／重启 | 达到已批准的保留级别，丢失限制可追踪 |
| 网络恢复重复写入 | 旧请求已提交但响应丢失 | 按业务身份查权威结果，安全幂等恢复 |
| 两个离线分支冲突 | 本地和服务器分别修改 | 无未经批准的最后写入覆盖，必要条件保真 |
| Background Sync 不支持 | 旧浏览器或受限制设备 | 前台恢复与用户操作路径仍可用 |
| Periodic Sync 延迟 | 浏览器忽略或推迟任务 | 不承诺精确调度，不虚报更新成功 |
| PWA 安装／启动 | Manifest、start_url、scope 与不同 OS | 安装行为符合声明，权限与深链真实有效 |
| Push 订阅撤销 | 用户拒绝或换账户 | 不向失效身份推送私有数据，不虚报送达 |
| 站点数据被清除 | 本地资源和草稿被移除 | 以真实存储状态呈现损失或可用恢复 |
| 用户 A 退出 B 登录 | CacheStorage／IndexedDB 缓存 | B 无法取得 A 的私有数据或待发动作 |
| Worker／API 跨版本 | 旧离线队列、新服务端模型 | 安全兼容或显式拒绝迁移，不重复写入 |
| 回滚与重新安装 | Worker 已部署至设备 | 客户端版本、队列及缓存真实复原 |
| 网络探测误判 | `navigator.onLine`=true 但 API 不可达 | 仅以实际接口响应判定同步成功 |
