# L4 跨浏览器兼容及测试技术规范

**文档ID：** STD-L4-WEB-011　**版本：** 0.1.0　**状态：** adopted　**生效日期：** 2026-10-30

## 技术范围、有效依据与外部标准

本规范是 Web 领域的**跨浏览器兼容与测试具体技术专题**，适用于浏览器原生能力、HTML/CSS/JavaScript、网络与存储、输入设备、辅助技术、自动化浏览器、移动终端、嵌入式 WebView 和新旧版本共存的工程交付。实际支持矩阵由项目用户、合同、运行渠道与风险共同确定；不强制每个项目适配全部浏览器、所有历史版本或所有设备。
组合技术依据：[L4 Web 领域通用基线](002-Web-领域通用基线--v0.1.0.md)（Web 领域通用基线）、[L4 浏览器文档、DOM 与交互组件技术规范](007-浏览器文档、DOM-与交互组件技术规范--v0.1.0.md)（HTML/DOM）、[L4 CSS 布局、视觉系统与响应式技术规范](001-CSS-布局、视觉系统与响应式技术规范--v0.1.0.md)（CSS）、[L4 渲染、路由与 Hydration 技术规范](009-渲染、路由与-Hydration-技术规范--v0.1.0.md)（渲染与路由）、[L4 客户端状态、表单与网络数据技术规范](006-客户端状态、表单与网络数据技术规范--v0.1.0.md)（客户端状态）、[L4 浏览器身份与应用安全技术规范](008-浏览器身份与应用安全技术规范--v0.1.0.md)（浏览器安全）、[L4 离线、缓存与 PWA 生命周期技术规范](010-离线、缓存与-PWA-生命周期技术规范--v0.1.0.md)（PWA）、[L4 可访问性与复杂控件技术规范](005-可访问性与复杂控件技术规范--v0.1.0.md)（可访问性）、[L4 前端性能与资源调度技术规范](004-前端性能与资源调度技术规范--v0.1.0.md)（前端性能），以及 L1—L3 对应规范。
现有技术标准和原始兼容数据仅引用权威来源，**不在本体系复制完整协议、测试套件或浏览器兼容数据库**：
- [MDN Baseline（Compatibility）](https://developer.mozilla.org/en-US/docs/Glossary/Baseline/Compatibility)：按指定核心浏览器集合区分 Newly available、Widely available、Limited availability。Widely available 表示已在 Baseline 浏览器中持续支持至少 2.5 年。**Baseline 不涵盖全部旧版本、全部 WebView 和辅助技术。**
- [WebDX web-features](https://github.com/web-platform-dx/web-features) 与 [MDN Browser Compatibility Data](https://github.com/mdn/browser-compat-data)：主流 Web 特性定义、版本支持元数据与 Baseline 计算依据，使用时记录数据版本与查验日期。
- [Web Platform Tests（WPT）](https://web-platform-tests.org/) 及 [WPT 测试编写指南](https://web-platform-tests.org/writing-tests/)；[wpt.fyi 测试结果](https://wpt.fyi/)：跨实现的标准一致性测试、reftest、testharness.js 等。WPT 结果不自动证明特定业务站点的端到端功能通过。
- [W3C WebDriver（2018-06-05 Recommendation）](https://www.w3.org/TR/2018/REC-webdriver1-20180605/)：规范性的浏览器远程控制协议；[WebDriver 修订版（2026-07-02 Working Draft）](https://www.w3.org/TR/2026/WD-webdriver2-20260702/) 与 [WebDriver BiDi（2026-10-08 Working Draft）](https://www.w3.org/TR/2026/WD-webdriver-bidi-20261008/)：仍在演进，不将其标记为正式 W3C Recommendation。
- [Playwright 官方浏览器运行说明](https://playwright.dev/docs/browsers)：Chromium、Firefox、WebKit、Chrome/Edge 品牌渠道等测试能力及浏览器二进制关联。Playwright 的补丁版 Firefox 或 WebKit **不等于**所有真实发布的 Firefox、Apple Safari 或 iOS Safari。
- [WHATWG HTML](https://html.spec.whatwg.org/multipage/)、[DOM](https://dom.spec.whatwg.org/)、[Fetch](https://fetch.spec.whatwg.org/)；[W3C CSS 规范模块目录](https://www.w3.org/Style/CSS/current-work)；[ECMAScript ECMA-262](https://tc39.es/ecma262/) 与 [ECMA-402 Intl](https://tc39.es/ecma402/)：具体平台行为的权威来源。
- [W3C WCAG 2.2](https://www.w3.org/TR/WCAG22/)：可访问性及辅助技术使用的标准边界；采用等级与完整流程验收仍由相邻无障碍专项及项目 L6 决定。
本规范只规定**支持范围、实际能力检测、降级与版本约束、浏览器测试体系、差异定位和证明标准**。特定框架、编译转译、polyfill、浏览器自动化库与 CI 配置由 L5 进一步制定，L6 决定项目目标矩阵、升级与退役规则及实际验收结果。

## 核验口径与消费接口

维护者负责落实本文机制，领域/API/存储提供者负责其权威保证，验收者从实际受支持入口观察结果。输入固定源码/构建、配置、数据/协议版本、角色/租户、目标平台、故障时序和预算；权威观察对象为**实际品牌/引擎/OS/驱动二进制与承诺任务，而非UA或工具名**。真实执行入口为**项目锁定Playwright/WebDriver脚本和二进制、品牌浏览器及所需真实设备/AT**。逐章 P/F/N 分别为正常输入及判据、破坏该机制的直接失败变异、应继续成立的合法邻例；本章原有每项规则、原有验收与新增合同共同约束，不用单一通用案例替代具体子项。每个子项须在案例输入中保留其适用条件，并以自身原文规定的输出/不变量判定；复合章应拆记录各个观察量，不能以一个成功掩盖其他失败。

证据产物包括真实命令/用户动作、原始响应或事件、权威状态前后值、版本、时序、失败及恢复；尚无对应真实运行证据的场景状态为 `not-run`，标准库示例仅证明列明的局部边界。具体输入与命令见[执行入口](../../../examples/web-backend/RUNBOOK.md)，条款索引见[规范条款登记](../../../registry/requirements.json)，来源的有限支持命题见[逐命题来源映射](../../../sources/web-backend/claims.json)。

本文的跨组件约束与正例、失败反例、合法邻例由本规范综合定义；外部来源支持的机制及适用边界见来源表。项目架构、预算和业务规则由实际需求确定。L5 实现应映射到所选框架、SDK 或引擎；L6 按具体版本的提供者保证与受支持矩阵验收项目能力。

## 一、浏览器支持策略与项目合同
1. 项目须按真实访问者、合同、法律、设备和发布渠道确定**浏览器品牌、引擎、操作系统、最低受支持版本和更新周期**；未声明的浏览器不自动作为强制兼容目标。
2. 对公开网站、内部管理系统、嵌入式 WebView、受控设备和科研原型分别确认支持边界。业务必需流程、降级允许程度及不可支持的功能要由有权需求主体确认，不凭开发者个人环境定义。
3. 明确主支持、有限支持、不支持和即将退役的状态，以及实际告知和版本迁移条件。不能将功能无法使用的旧版仅用静态提示伪装为“兼容”。
4. 支持范围调整应同时评估用户影响、风险、可行性、测试成本、可访问性及发布安排；不得静默降低项目已经批准的兼容承诺。
5. **验收**：L6 有可查的版本矩阵、关键任务、各目标环境完成条件、有效批准及确实执行的测试记录。

### WEB-001 核验合同

- **WEB-001-P · 输入/动作与合格判据：** 声明品牌/引擎/OS/最低版/用户主路径→实际证据匹配支持合同。
- **WEB-001-F · 直接失败变异：** 工具默认升级静默降低已承诺范围→失败。
- **WEB-001-N · 合法邻例：** 仅受控终端支持可明确且实测。

## 二、浏览器品牌、引擎与实际运行环境
1. 区分 Chromium、Gecko、WebKit 等引擎与 Chrome、Edge、Firefox、Safari 等品牌产品及移动分发版本；同引擎不代表媒体编解码器、政策、功能开关、操作系统能力和 Cookie 行为完全相同。
2. Playwright 内置 Chromium、补丁版 Firefox 和 WebKit 可以用于多引擎回归，但不可将 WebKit 构建的测试结果直接写成“真实 iOS Safari 已通过”，也不能将补丁版 Firefox 等同于全部发行渠道。
3. 对关键终端按需补充品牌稳定版、真实 Safari/macOS/iOS、Android 浏览器、企业托管浏览器或 WebView。是否需要真机取决于其独有能力及业务风险。
4. 记录 OS、浏览器发行渠道、构建号、用户代理环境、设备输入、硬件加速、字体/编码器和系统安全策略；不以 UA 字符串冒充完整能力验证。
5. **验收**：测试报告可准确说明“Chromium 构建”“Chrome 稳定版”“WebKit 自动化”“Safari 真机”等实际环境，不把一种证据扩大为另一种平台结论。

### WEB-002 核验合同

- **WEB-002-P · 输入/动作与合格判据：** 分别记录Playwright引擎与品牌真机→二进制/系统身份准确。
- **WEB-002-F · 直接失败变异：** WebKit自动化绿记为iOS Safari通过→失败。
- **WEB-002-N · 合法邻例：** 只宣称已测补丁引擎范围合法。

## 三、兼容信息来源及证据等级
1. Baseline、MDN BCD、WebDX web-features、WPT 和浏览器发行说明在兼容评估中分工不同：分别帮助判断支持广度、版本细节、平台一致性和实际变动。
2. Baseline Newly available 表示核心浏览器最新稳定版本支持；Widely available 表示已经持续广泛支持至少 2.5 年。这是**主流浏览器支持摘要**，不涵盖所有旧设备、WebView 或辅助技术。
3. BCD 中 partial implementation、behind flag、前缀与实现备注需要逐项核实；功能表“支持”不保证组合功能在用户实际环境下正确。
4. WPT 衡量相关平台规范的一致性；一个 WPT case 通过不代表你的组件、业务数据、权限和跨站任务已经通过端到端测试。
5. 实际产品验收依据是与目标版本匹配的运行证据。外部表格、上游 Issue、厂商宣称和自动扫描只作为选取、调查及补充证据。
6. **验收**：每项高影响新能力可回溯来源、版本、实际适用浏览器、降级策略和项目实测。

### WEB-003 核验合同

- **WEB-003-P · 输入/动作与合格判据：** 核Baseline/BCD/WPT到实际case→版本、部分实现和盲区可查。
- **WEB-003-F · 直接失败变异：** Baseline广泛可用冒所有WebView/AT兼容→失败。
- **WEB-003-N · 合法邻例：** 官方表可作选测线索不作应用验收。

## 四、特性检测与渐进增强
1. 优先通过**真实能力特征**检测判断是否可以使用相关 API／语法，必要时结合受控功能测试，而不是仅由浏览器品牌与 UA 推断。
2. 存在 API 对象并不保证其所有选项、事件和边界行为可用；对实验性 Web API、权限、事件或安全上下文，还要核对调用实际结果。
3. 渐进增强先保证项目批准的最小有用功能，再在支持的浏览器中提升体验。不能以“不支持最新动画”让用户失去不可替代的提交与内容访问。
4. 对确实无法在目标环境实现的关键能力，必须说明影响、可用替代或经批准的支持范围限制；不允许不可用按钮、无响应菜单或隐藏数据冒充成功。
5. **验收**：分别在功能支持、缺失、权限拒绝、版本部分实现情况下，核对用户任务、错误反馈和数据一致性。

### WEB-004 核验合同

- **WEB-004-P · 输入/动作与合格判据：** API存在但拒权/不支持选项时走真实回退→基本任务完成。
- **WEB-004-F · 直接失败变异：** 只typeof检测后无响应按钮→失败。
- **WEB-004-N · 合法邻例：** 装饰新动画缺失可无害降级。

## 五、HTML、DOM、组件与事件兼容
1. 语义结构、原生表单、dialog、popover、自定义元素、Shadow DOM、Pointer/Keyboard/Composition Event、焦点和页面生命周期按相邻 DOM 专项实施；本节专门检查不同引擎的实际实现差异。
2. 事件路径、监听器参数、默认动作、输入法组合、表单提交和异步 DOM 更新的兼容性应以真实交互验证；合成 dispatchEvent 不完全代表用户键盘或触摸。
3. Custom Elements、ElementInternals、slot、焦点、Shadow DOM composed 事件及第三方组件跨版本差异需按项目是否使用逐项检查。
4. **验收**：普通/复杂控件在实际目标浏览器完成键盘、鼠标、IME、事件取消、焦点返回及组件销毁；与原生语义及业务契约一致。

### WEB-005 核验合同

- **WEB-005-P · 输入/动作与合格判据：** 目标引擎真实Enter/IME/dialog/Shadow与卸载→事件和原生任务一致。
- **WEB-005-F · 直接失败变异：** dispatchEvent冒真实键盘/默认动作→失败。
- **WEB-005-N · 合法邻例：** 未用Custom Elements不增加其全套验证。

## 六、CSS 布局、视觉及兼容回退
1. Flex、Grid、subgrid、Container Queries、动态视口、字体、色彩空间、逻辑属性及新 CSS 规则的正式来源按 CSSWG 模块核对，不能仅根据某工具支持编译就推断目标浏览器渲染正确。
2. 只有项目使用该机制时才要求对应特性检查。CSS @supports 可检测特性解析，不足以证明组合布局的语义正确、文本不被裁切或焦点可达。
3. Vendor prefix、CSS 预处理器与构建转换只能作为明确解决已测差异的工具；禁止无限叠加全局补丁或修改业务显示内容来掩盖不支持问题。
4. 窄屏、缩放、字体回退、RTL、强制颜色和不同 DPR 下的样式差异需区分无害像素偏移与关键业务视觉失效。
5. **验收**：重点布局在各目标引擎有真实截图与交互核对、明确降级和可复现的差异，不以单张开发机视觉稿宣布全部兼容。

### WEB-006 核验合同

- **WEB-006-P · 输入/动作与合格判据：** 实际构建布局在窄屏/RTL/字体回退→内容和焦点不丢。
- **WEB-006-F · 直接失败变异：** 编译器接受新CSS就认为浏览器组合可用→失败。
- **WEB-006-N · 合法邻例：** 抗锯齿微差可按任务视为等价。

## 七、JavaScript、Intl 与转译边界
1. ECMAScript 和 Intl 的新语法、内建对象、格式化行为按 ECMA-262／ECMA-402 及目标浏览器实际支持核对；语法解析失败会使代码根本无法开始执行，无法依赖运行到后续检测再修复。
2. 编译目标、transpile、polyfill、必要的 runtime shim 以项目实际浏览器矩阵配置。**语法转换与运行时 API polyfill 是不同职责**，也不能把不可能 polyfill 的平台安全或硬件能力伪装成等价。
3. 日期、时区、Intl 数字格式、排序、Unicode 字形、正则及浮点差异涉及真实用户业务语义时，不得依赖浏览器默认 Locale 和机器环境推断。
4. 不默认引入所有兼容垫片而增加固定包体积、性能或供应链风险；缺少目标用户及风险依据时按明确项目需求选择。
5. **验收**：对实际发行构建执行语法解析、依赖加载、重点 Intl 样例及失败回退；不能只在本机较新 Node 或开发服务器中通过测试。

### WEB-007 核验合同

- **WEB-007-P · 输入/动作与合格判据：** 最低目标浏览器解析发行包并跑Intl边界→语法和API都可用。
- **WEB-007-F · 直接失败变异：** 语法先解析失败却指望后续polyfill修复→失败。
- **WEB-007-N · 合法邻例：** 无需新API的构建不引入全套垫片。

## 八、响应式视口、输入与设备环境
1. 浏览器视口、动态工具栏、软键盘、安全区域、缩放、触控与鼠标精度差异由设备/浏览器共同决定，模拟 viewport 大小不足以证明真机输入和布局兼容。
2. 对 touch、pointer、hover、keyboard、wheel、drag 等实际支持的交互方式建立合理替代路径；不把 hover 唯一入口和触屏多点手势当作所有用户必备能力。
3. 屏幕旋转、字体放大、系统强制对比、减弱动画、RTL 与输入法需要按目标用户群体和界面功能纳入矩阵。
4. **验收**：真机或有事实对应的设备环境可完成已承诺的表单、导航、弹层和数据操作，软键盘不会永久遮挡关键控件。

### WEB-008 核验合同

- **WEB-008-P · 输入/动作与合格判据：** 真实设备软键盘/旋转/触控/放大→提交可达。
- **WEB-008-F · 直接失败变异：** 只模拟viewport冒真机IME/安全区通过→失败。
- **WEB-008-N · 合法邻例：** 可信模拟可单列其实际覆盖。

## 九、路由、SSR 与跨引擎 Hydration
1. 对 CSR、SSR、SSG、Streaming 与 Hydration 按相邻渲染专项选择真实用例，核对不同引擎对 HTML 解析、事件、路由与加载时序的差异。
2. 深链刷新、History 与 Navigation API 兼容、跨文档导航、bfcache、表单未保存内容及旧客户端缓存需要区分真实 HTTP 入口和仅在 SPA 内部可用的路由。
3. 不同浏览器的 Locale、时间、自动生成 ID 或 HTML 纠错行为可能触发服务端与客户端首轮树不匹配，不能用静默抑制 Hydration 警告当作修复。
4. Streaming 的 Shell 提交后状态码不可任意更改。错误恢复、超时、取消和用户提前输入按项目实际运行验证，而不能只在框架演示页面中成功。
5. **验收**：直达、刷新、前进后退、不同响应速度和旧版本前端共存时，关键路径没有错路由、私有数据泄露、输入丢失或不可交互控件。

### WEB-009 核验合同

- **WEB-009-P · 输入/动作与合格判据：** 跨引擎直达/Back/慢JS/旧资源→解析、路由、输入和授权正确。
- **WEB-009-F · 直接失败变异：** 吞Hydration告警或头发送后假改状态→失败。
- **WEB-009-N · 合法邻例：** 无Hydration页面无需框架接管测试。

## 十、Fetch、HTTP、网络与安全策略差异
1. 跨浏览器测试须明确支持的 Fetch、Streams、AbortSignal、CORS、Cookie、TLS、HTTP 缓存、重定向与服务器协议行为；请求是否发送成功不代表业务已完成。
2. 当浏览器拒绝跨源读取、禁用第三方 Cookie 或不支持某请求模式时，不得解释为服务器已取消写入；实际外部副作用需回读权威服务端。
3. 网络代理、企业策略、证书、压缩、HTTP/2 或 HTTP/3、WebSocket/SSE 等条件需按项目真实依赖选择，有必要时对移动数据网络和企业受控网络执行实测。
4. 错误类别至少区分浏览器平台限制、权限拒绝、跨源拒绝、网络中断、协议响应错误与真实业务拒绝，提供正确用户恢复。
5. **验收**：不同来源和身份、真实服务器响应以及网络异常条件下，接口权限、数据和业务结果保真，未形成浏览器差异导致的越权路径。

### WEB-010 核验合同

- **WEB-010-P · 输入/动作与合格判据：** 跨源拒绝/网络断流/服务端已提交→各错误分类且回读权威。
- **WEB-010-F · 直接失败变异：** 浏览器CORS拒绝当服务端回滚→失败。
- **WEB-010-N · 合法邻例：** 纯服务器消费者不适用浏览器CORS限制。

## 十一、Cookie、Storage、IndexedDB 与私有缓存
1. 第三方 Cookie 策略、同站机制、Partitioned Cookie、本地存储配额、IndexedDB、Cache Storage、Private Browsing 与站点数据清理各有浏览器/设备差异。
2. 存储是否可使用、持久化是否批准、数据是否被回收、登录后身份是否切换，需要在实际目标环境验证；不能因为 API 存在就保证持久数据永不丢失。
3. SSR HTML、离线 Worker、旧标签及 bfcache 可能继续持有过期的个人数据；浏览器前端清理不替代权威服务器身份撤销。
4. **验收**：旧身份登出、新身份登录、隐私模式、配额耗尽、浏览器升级和设备存储清理后，私有数据隔离与业务操作仍符合现行安全及 PWA 规范。

### WEB-011 核验合同

- **WEB-011-P · 输入/动作与合格判据：** 隐私模式/配额/清站点数据/换账号→存储限制真实且隔离。
- **WEB-011-F · 直接失败变异：** API存在即永久持久或旧SSR泄露→失败。
- **WEB-011-N · 合法邻例：** 允许丢的公开缓存可重建。

## 十二、Service Worker、PWA 与后台功能兼容
1. 只有项目实际提供 PWA、离线或 Push 时，才核查 Worker 注册、Scope、缓存、安装、后台同步、通知权限、客户端接管及版本恢复。
2. Background Sync、Periodic Background Sync 和部分安装 API 等能力支持存在重大差异；注册成功不代表任务一定在后台触发、推送按时到达或所有系统展示安装按钮。
3. Worker 与网页版本、缓存和服务端数据 Schema 共存时需要实测，新 Worker 不能错误夺取旧页面控制权并丢失未提交草稿。
4. **验收**：项目真实支持环境内，首访、二次访问、离线、恢复、更新、权限撤销及不能支持后台能力时仍提供准确状态和可靠恢复。

### WEB-012 核验合同

- **WEB-012-P · 输入/动作与合格判据：** Sync不支持/旧Worker/新页/撤权→前台恢复和版本兼容。
- **WEB-012-F · 直接失败变异：** 注册后台任务即保证定时或强接管丢草稿→失败。
- **WEB-012-N · 合法邻例：** 在线无PWA产品不强制后台能力。

## 十三、媒体、字体、Canvas 与图形能力
1. 浏览器编解码器、字体引擎、音视频自动播放限制、WebGL/WebGPU、Canvas、色域和图像解码在品牌浏览器与平台间可能不同；仅对产品实际使用能力纳入兼容性矩阵。
2. 通过能力探测结合真实媒体文件和目标设备确认是否可播放、绘制与交互。API 可见或格式名被声明支持，不等于真实源文件可用及用户能够完成任务。
3. 图形后端、GPU 驱动和字体 fallback 会影响关键内容清晰度、布局、焦点及内存占用，不能用单一截图或引擎跑分证明所有设备兼容。
4. **验收**：音视频、字幕、图片字体、Canvas/图表/游戏画面在适用目标设备上正常呈现，缺失功能有可操作回退，核心业务信息不丢失。

### WEB-013 核验合同

- **WEB-013-P · 输入/动作与合格判据：** 目标编码器/字体/GPU真实资源→播放/绘制及替代完整。
- **WEB-013-F · 直接失败变异：** API或格式名支持就当实际文件可用→失败。
- **WEB-013-N · 合法邻例：** 未使用媒体不承担解码器矩阵。

## 十四、Accessibility Tree 与辅助技术矩阵
1. HTML/ARIA 规范和 WCAG 成功准则由现行无障碍专项负责；本专题检查同一控件在不同引擎、OS 与屏幕阅读器的角色、名称、状态、焦点和公告差异。
2. 引擎自动化可读取的 Accessibility Tree 与真实辅助技术听到或操作到的内容有关联，但并非完全等同；自动化断言不构成所有阅读器和语音操作的通过证据。
3. Dialog、Combobox、Grid、Tree、动态 Live Region、跳转后的焦点、复杂表单在受支持的浏览器/AT 组合中必须有实际交互证据；存在不同合理交互模式时按所选业务与规范判断。
4. **验收**：按照 L6 的辅助技术矩阵证明可读、可聚焦、可操作、可恢复；不要求从未声明支持的所有阅读器环境获得虚构认证。

### WEB-014 核验合同

- **WEB-014-P · 输入/动作与合格判据：** Dialog/Combobox/Grid/live在声明AT组合→可读可操作可恢复。
- **WEB-014-F · 直接失败变异：** 只读AX树就宣称所有读屏正常→失败。
- **WEB-014-N · 合法邻例：** 没有声明支持的所有AT无需虚构认证。

## 十五、WebView、内嵌浏览器与企业环境
1. App 内 WebView、社交媒体内置浏览器、桌面宿主 WebView2 和企业策略控制的浏览器不被 MDN Baseline 的主流版本集合完整代表。
2. 嵌入环境可能限制 Cookie、OAuth 回调、外部导航、文件选择、媒体能力、Push、权限 API、下载与窗口打开；测试需反映宿主版本、桥接权限与生命周期。
3. 与宿主 Native Bridge、postMessage 和深链接的通信要遵守实际适用的安全及数据权利边界，不能因测试兼容而默认允许跨域、跳过认证或复用生产凭据。
4. **验收**：只对项目实际支持的宿主渠道形成可复核目标版本、回调、登录、页面恢复和必要系统能力测试记录。

### WEB-015 核验合同

- **WEB-015-P · 输入/动作与合格判据：** 宿主版本/桥/回调/权限/进程恢复→实际WebView任务可行。
- **WEB-015-F · 直接失败变异：** Baseline代宿主能力或为兼容跳过鉴权→失败。
- **WEB-015-N · 合法邻例：** 未发布嵌入渠道不强制桥接测试。

## 十六、性能、功耗与旧设备回退
1. 同一代码在不同浏览器中可能存在解析、主线程调度、渲染、GPU、内存及网络策略差异。兼容性不仅是“可加载”，还应按既定项目要求检查可操作的延迟和资源消耗。
2. 对弱网、低 RAM、老旧 CPU、后台节流和高缩放环境，允许经批准的降低装饰或按需加载，但不能去掉核心业务功能、权限校验和可访问性。
3. 使用 Polyfill、兼容构建或不同渲染路径时要记录额外 Bundle、解析时间、维护及安全成本，避免为了极小用户范围引入无边界长期负担。
4. **验收**：受支持旧版本或低端设备满足相应任务预算；不足时给出实际限制、替代路径和已批准版本退役安排。

### WEB-016 核验合同

- **WEB-016-P · 输入/动作与合格判据：** 受支持旧CPU/弱网/后台节流→核心任务预算和可访问能力保持。
- **WEB-016-F · 直接失败变异：** 删安全校验/字段换速度→失败。
- **WEB-016-N · 合法邻例：** 按合同降低非关键装饰合法。

## 十七、多引擎自动化测试与执行器
1. 根据 L6 目标矩阵选择跨引擎自动化工具，如 Playwright、Selenium/WebDriver 或经批准的等价入口；工具版本、浏览器二进制、容器依赖、浏览器 Channel 和运行环境都应可复现。
2. W3C WebDriver 2018 Recommendation 为正式远程控制协议，2026 年 WebDriver 修订稿与 BiDi 仍为 Working Draft；使用实验或新协议功能必须以真实驱动及浏览器实现为准。
3. Playwright Chromium、Firefox、WebKit 可用于主流引擎回归，但必须标注其修补与品牌/平台差异。对真实 Safari、iOS、企业插件、编解码器等相关能力，必要时另用真机或品牌浏览器补验。
4. Headless、headed、模拟移动屏幕与真实系统浏览器可能在焦点、输入、媒体、窗口、权限和动画上存在差异；不将 CI 绿色冒充所有平台的真实交互通过。
5. **验收**：每项自动化结果有测试脚本/版本、真实执行引擎及二进制、OS、依赖、输入、输出和失败证据。

### WEB-017 核验合同

**必要机制补充：** 自动化内置补丁WebKit/Firefox只证明该二进制；涉及Safari/iOS、系统IME、语音/屏幕阅读器、企业策略时另绑定实际品牌、设备及辅助技术。

- **WEB-017-P · 输入/动作与合格判据：** 固定驱动/二进制/OS/channel运行脚本→结果绑定实际执行器。
- **WEB-017-F · 直接失败变异：** headed/headless和真机混为同等级证据→失败。
- **WEB-017-N · 合法邻例：** W3C正式协议与实验BiDi可分开采用。

## 十八、WPT、一致性与应用端到端的分层
1. WPT 的 testharness.js、reftest 和浏览器协议测试用于验证 Web 平台实现是否遵守相应规范；阅读 [wpt.fyi](https://wpt.fyi/) 结果时应确认测试编号、浏览器版本、运行模式、历史时间及已知失败。
2. 对涉及平台兼容缺陷，可选取对应 WPT 或设计最小规范复现案例，以分离浏览器实现问题与应用代码错误；不得为了使当前应用测试通过而修改标准期望。
3. 产品端到端验收仍必须覆盖页面入口、身份、实际 API、数据、交互、权限、错误恢复及下游成果，不能由通用 WPT 通过率替代。
4. 项目可为真实缺陷添加独立回归并向上游反馈，但不得要求每个项目以贡献 WPT 作为验收前置条件。
5. **验收**：标准符合性证据与业务 E2E 证据分别登记；二者都指向可复算的实际版本和条件。

### WEB-018 核验合同

- **WEB-018-P · 输入/动作与合格判据：** 最小规范复现+业务E2E分别记录→平台/应用结论分开。
- **WEB-018-F · 直接失败变异：** 修改WPT标准期望让应用变绿→失败。
- **WEB-018-N · 合法邻例：** 项目无需把上游贡献当验收前提。

## 十九、测试数据、稳定性与环境隔离
1. 跨引擎测试的夹具需固定真实业务输入、账号角色、权限、时区、语言、分辨率、网络、时钟及关键数据快照，降低环境干扰；但不能用 Mock 隐藏必须由真实服务端决定的业务结果。
2. 测试之间必须隔离用户 Session、Cookies、Storage、Service Worker、缓存、浏览器 Profile、权限设置及外部请求副作用。并行共享同一真实账户或数据库时按已批准的资源写入策略管理。
3. 异步操作以可观察条件等待，不使用固定睡眠时间当作业务完成证明。性能或兼容测试中需要人为等待时，须区分为控制条件而非真实结果确认。
4. 浏览器二进制更新、操作系统补丁、字体、证书、沙箱权限和外部服务变化，应记录变更及其对测试可复现性的影响。
5. **验收**：同一版本可重复执行，偶发失败可以定位根因，失败截图/Trace/日志能与真实目标浏览器和场景对应。

### WEB-019 核验合同

- **WEB-019-F · 直接失败变异：** 固定sleep当业务完成或并行共享账号互相覆盖→失败。
- **WEB-019-N · 合法邻例：** 受控等待可作为注入时序条件而非结果证明。

## 二十、视觉对比与非像素等价
1. 不同浏览器的字体光栅化、抗锯齿、原生控件外观、滚动条和渲染管线存在无害差异；绝对像素一致通常不是跨浏览器交付的合理默认目标。
2. 视觉回归需要关注用户所需文字、操作状态、布局、可读性、重要图表、错误反馈与交互可达性。固定截图环境应标注 DPR、字体、主题、Locale、视口和浏览器版本。
3. 对容差、遮罩和基准图片更新，要区分合法装饰差异与真实缺陷；不得通过广泛隐藏、过大差异容忍或更新错误快照让重大业务显示损失通过。
4. 对交互控件、动画、焦点和辅助技术，截图不足以证明功能；应结合真实事件及用户路径检查。
5. **验收**：每次视觉基线变更都对应已核实内容与行为差异，跨引擎差异有实际影响判断与必要回归。

### WEB-020 核验合同

- **WEB-020-P · 输入/动作与合格判据：** 固定字体/DPR对照并真实操作→重大内容损失阻断。
- **WEB-020-F · 直接失败变异：** 大遮罩/宽容差/错误基线更新掩盖缺陷→失败。
- **WEB-020-N · 合法邻例：** 原生控件和字形光栅微差可合法等价。

## 二十一、差异定位、浏览器缺陷与回归
1. 出现单一浏览器失败时，首先固定浏览器品牌、引擎、完整版本、OS、环境开关、请求和实际业务输入，确定是本地实现、标准解释、自动化测试还是浏览器已知缺陷。
2. 通过最小可复现页面、官方规范、WPT 结果、浏览器厂商问题跟踪及原仓库代码，尽量缩小影响面；不得凭一次沙箱启动失败推断整个浏览器或工具不可用。
3. 针对真实缺陷建立回归用例。兼容补丁优先限制作用域，并具备未来浏览器修复后的撤除条件；不能无限叠加 UA hack、全局 CSS 覆盖或错误业务特殊分支。
4. 如果上游浏览器或自动化驱动确有缺陷，保留真实失败证据及受影响用户路径，必要时调整已批准的支持范围；不得通过删除检查或人为更新错误期望报告通过。
5. **验收**：每项重大兼容问题有复现版本、真实影响、根因或明确未定位状态、修复差异、回归结果及后续复核条件。

### WEB-021 核验合同

- **WEB-021-P · 输入/动作与合格判据：** 固定失败版本做最小复现和回归→根因/未定位及补丁撤除条件可查。
- **WEB-021-F · 直接失败变异：** 一次沙箱启动失败就推断全工具不可用→失败。
- **WEB-021-N · 合法邻例：** 已证实上游缺陷保留证据和受限替代。

## 二十二、浏览器升级、弃用与兼容窗口
1. 项目应针对 Stable/Beta、长期支持环境及企业固定版本确定追踪策略，按真实用户量与风险选择回归周期；不要求所有项目测试所有 Nightly 或无关老旧版本。
2. 关注浏览器新版本可能影响的 DOM、样式、Cookie、存储、权限、媒体、网络与安全默认值；对项目实际使用的新特性设置回归和回滚边界。
3. 某个能力从实验/前缀转入标准实现，或因安全风险被弃用时，评估旧版本兼容、构建转译、Polyfill 清理、第三方组件及 API 迁移。
4. 终止支持旧环境必须由有权产品和项目负责人决定，记录最后有效版本、受影响真实用户、替代入口及必要告知；不得由构建工具默认目标变化静默改变支持合同。
5. **验收**：浏览器或工具链升级产生的行为变化有明确版本、回归结果和用户影响判定，退役决策有授权及必要迁移证据。

### WEB-022 核验合同

- **WEB-022-P · 输入/动作与合格判据：** Stable/Beta或企业固定版升级→行为变化有回归和退役决定。
- **WEB-022-F · 直接失败变异：** 新默认target静默删旧客户端支持→失败。
- **WEB-022-N · 合法邻例：** 无关Nightly不必所有项目持续跑。

## 二十三、风险匹配的测试矩阵与成本控制
1. 对浏览器矩阵分层：全体支持目标的最低必要主路径、关键能力受影响的专题测试、真正具有品牌/设备特有风险的真机用例。不能只在单一 Chromium 环境通过后就宣布 Safari、Firefox 或 WebView 全部兼容。
2. 自动测试可以复用有效基线、WPT 标准证据和已验证组件契约；仅在关键变更与既有证明不等价时增加昂贵真机/云浏览器检查，不进行无价值重复跑数。
3. 支付、身份、数据隔离、上传、离线迁移和不可逆副作用等高风险业务必须按适用浏览器和真实接口验证，即使通用 UI 小改动不需要完整跨平台大矩阵。
4. 测试阶段应区分提交前快速回归、合并验收、渠道发行与生产实际使用，按 L3 的工程质量职责实施，不设与项目目标无关的统一浏览器/CI 配额。
5. **验收**：每个声明的受支持浏览器都有对应的必要行为检查与已知限制；未测项、失败与正式例外明确，不以“成本已优化”代替能力验证。

### WEB-023 核验合同

- **WEB-023-P · 输入/动作与合格判据：** 按支持目标主路径/高风险专题/真机分层→每项承诺有证据。
- **WEB-023-F · 直接失败变异：** 只Chromium通过或以成本优化省略关键身份流程→失败。
- **WEB-023-N · 合法邻例：** 有效且等价旧证据可复用避免重复。

## 二十四、跨浏览器专项验收场景矩阵
| 测试场景 | 关键输入或失效条件 | 项目需要的实际验收结果 |
| --- | --- | --- |
| 支持版本变化 | 同一品牌不同稳定版与旧版 | 按 L6 矩阵核对基础任务与已声明的差异 |
| Baseline Newly available | 最新版本支持、旧版本无能力 | 按旧版本检测与降级，不误认为所有用户支持 |
| BCD 部分实现 | 功能 behind flag 或 partial support | 运行正确的能力探针，避免静态兼容表误判 |
| 同引擎不同品牌 | Chromium 与 Chrome/Edge 编解码器/政策 | 依真实品牌需求使用匹配渠道或产品版验证 |
| WebKit 与真实 Safari | 自动化 WebKit 与 macOS/iOS Safari | 正确区分测试环境，必要场景真机复验 |
| CSS 布局差异 | Grid/Container Query/长文本与 RTL | 内容、焦点及必要操作真实可达 |
| JS 新语法与 API | 旧浏览器无法解析或缺少运行时能力 | 发行包可解析且适当转译/Polyfill/降级 |
| Intl 与本地化 | 时间、货币、排序和不同 Locale | 业务语义稳定、不误读数字及单位 |
| 自定义组件事件 | Shadow DOM、键盘、IME 组合输入 | 事件、焦点、提交与用户输入一致 |
| 软键盘与视口 | 移动工具栏/旋转/输入法 | 关键字段、错误与提交控件可见可操作 |
| SSR/Hydration 差异 | HTML 解析及初始 Locale/时钟不同 | 客户端接管无损、服务端数据权限保持 |
| History/Navigation API | 深链、返回、旧浏览器不支持 | 原生或兼容路由恢复正确状态和焦点 |
| Cookie/Storage 受限 | 第三方 Cookie 禁用、隐私模式、配额 | 登录及数据恢复准确，不跨身份读取 |
| 跨源协议差异 | CORS 失败但请求可能已送达 | 服务器授权及外部副作用独立确认 |
| WebView 与宿主桥接 | 内置浏览器登录/下载/Native Bridge | 仅在受支持宿主内实际验证且无越权 |
| Service Worker 更新 | 旧标签、新 Worker 与缓存版本 | 数据不丢、权限正确、能安全恢复 |
| 媒体/Canvas 能力 | Codec/GPU/字体版本差异 | 关键内容可用并提供必要降级 |
| 辅助技术组合 | 不同引擎 Accessibility Tree、读屏 | 能完成实际控件和完整用户任务 |
| Headless 与 headed | 自动化模式下焦点/媒体行为不同 | 关键真实浏览器交互按风险补充验证 |
| 视觉回归差异 | 字体抗锯齿、滚动条和 DPR | 容差有依据，不遮蔽业务视觉故障 |
| 不稳定自动化 | 竞态/等待/数据共享导致偶发失败 | 根因可复现，不删用例、不用固定睡眠掩盖 |
| 浏览器自动更新 | 新 Stable/Beta 更改默认安全策略 | 按影响范围回归、保留兼容/迁移措施 |
| 性能与低端设备 | 弱网/低 RAM/旧 GPU | 核心任务、可访问性及数据正确性保留 |
| WPT 通过但业务失败 | 规范 API 测试绿、登录表单 E2E 失败 | 清楚区分标准一致性与真实业务交付 |
## 二十五、专项批准与项目接入边界
1. 本规范只针对**Web 平台跨浏览器兼容和测试**补充支持矩阵、功能检测、降级、标准符合性证据、自动化方法及发布回归。HTML、CSS、网络、路由、身份、性能、无障碍和 PWA 的技术语义继续由各自技术规范及官方标准负责。
2. WebDriver 2018 Recommendation、WebDriver 2026 Working Draft、WebDriver BiDi 2026 Working Draft、WPT 测试工具、MDN Baseline/BCD 以及 Playwright 官方工具文档均按其**实际规范地位**使用，不能简单称它们为同一等级的正式强制标准，也不复制平台协议全文。
3. L5 明确 Playwright/Selenium 具体版本、浏览器执行器、构建转译、Browserslist 与 Polyfill 的技术栈实现；L6 固定实际用户浏览器及 WebView、支持期限、关键场景、辅助技术、资源预算、门禁、已测版本及正式例外。
本文技术条款及场景的文本覆盖，不代表项目已执行跨浏览器、WebView、真机或业务 E2E 测试；不能仅凭 WPT/Baseline 或自动化工具存在宣称实际项目跨浏览器达标。
