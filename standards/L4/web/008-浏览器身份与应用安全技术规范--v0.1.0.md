# L4 浏览器身份与应用安全技术规范

**文档ID：** STD-L4-WEB-008　**版本：** 0.1.0　**状态：** adopted　**生效日期：** 2026-10-30

## 适用范围、继承与外部标准

本具体技术专题面向 Web 浏览器的身份登录、会话、跨源、动态内容、第三方脚本、嵌入、缓存、凭据与敏感操作。并不要求所有项目都引入用户登录、Passkey、OAuth、嵌入组件或额外的安全功能；实际采用按业务入口、平台和风险确定。
有效依据：[L4 Web 领域通用基线](002-Web-领域通用基线--v0.1.0.md)（Web 通用基线）；[L4 浏览器文档、DOM 与交互组件技术规范](007-浏览器文档、DOM-与交互组件技术规范--v0.1.0.md)（HTML/DOM）；[L4 渲染、路由与 Hydration 技术规范](009-渲染、路由与-Hydration-技术规范--v0.1.0.md)（导航/SSR）；[L4 客户端状态、表单与网络数据技术规范](006-客户端状态、表单与网络数据技术规范--v0.1.0.md)（客户端状态/请求）；[L3 通用工程规范](../../L3/001-通用工程规范--v0.1.0.md)（L3 工程）；[L2 人类与 Agent 团队组织协作规范](../../L2/001-人类与-Agent-团队组织协作规范--v0.1.0.md)（L2）；[L1 全局治理补充规范](../../L1/001-全局治理补充规范--v0.1.0.md)（L1）。
行业规范直接引用原文，并区分标准与指南：
- [OWASP ASVS v5.0.0](https://owasp.org/projects/asvs)：当前稳定版本，引用适用控制时使用带版本标识。
- [RFC 10017：OAuth 2.0 for Browser-Based Applications](https://www.rfc-editor.org/rfc/rfc10017.html)：2026 年 8 月 IETF Best Current Practice；[RFC 9700：OAuth 2.0 Security BCP](https://www.rfc-editor.org/rfc/rfc9700.html)：2025 年 1 月 IETF BCP。
- [W3C WebAuthn Level 3](https://www.w3.org/TR/2026/REC-webauthn-3-20260825/)：2026-08-25 正式 W3C Recommendation。
- [WHATWG Fetch](https://fetch.spec.whatwg.org/) 和 [WHATWG HTML](https://html.spec.whatwg.org/multipage/)：浏览器同源、请求、页面和嵌入机制；属于 Living Standards。
- [MDN Set-Cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie)、[CORS](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS)、[CSP](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy)、[Trusted Types](https://developer.mozilla.org/en-US/docs/Web/API/Trusted_Types_API)：实施及兼容资料。
- [OWASP CSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)、[XSS Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html)、[Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)：技术指南，不视为 W3C/IETF 同类正式规范。
本专题明确浏览器和服务端之间的具体实现及验收契约。真正认证、对象级授权、租户隔离、账本与数据处置由权威后端、身份系统和其他 L4 领域负责；L5 定义框架安全 API 与构建工具，L6 指定真实项目的风险、版本和测试范围。

## 核验口径与消费接口

维护者负责落实本文机制，领域/API/存储提供者负责其权威保证，验收者从实际受支持入口观察结果。输入固定源码/构建、配置、数据/协议版本、角色/租户、目标平台、故障时序和预算；权威观察对象为**服务器有效会话/对象许可、浏览器来源、Cookie与受控输出**。真实执行入口为**真实身份测试账户、DevTools Cookie/Network/CSP、服务端拒绝及副作用查询**。逐章 P/F/N 分别为正常输入及判据、破坏该机制的直接失败变异、应继续成立的合法邻例；本章原有每项规则、原有验收与新增合同共同约束，不用单一通用案例替代具体子项。每个子项须在案例输入中保留其适用条件，并以自身原文规定的输出/不变量判定；复合章应拆记录各个观察量，不能以一个成功掩盖其他失败。

证据产物包括真实命令/用户动作、原始响应或事件、权威状态前后值、版本、时序、失败及恢复；尚无对应真实运行证据的场景状态为 `not-run`，标准库示例仅证明列明的局部边界。具体输入与命令见[执行入口](../../../examples/web-backend/RUNBOOK.md)，条款索引见[规范条款登记](../../../registry/requirements.json)，来源的有限支持命题见[逐命题来源映射](../../../sources/web-backend/claims.json)。

本文的跨组件约束与正例、失败反例、合法邻例由本规范综合定义；外部来源支持的机制及适用边界见来源表。项目架构、预算和业务规则由实际需求确定。L5 实现应映射到所选框架、SDK 或引擎；L6 按具体版本的提供者保证与受支持矩阵验收项目能力。

## 一、浏览器资产、身份和信任边界
1. 按页面及实际数据路径识别身份、Session、Token、第三方 JS、iframe、管理员入口、公开资源和私有数据。凡不应暴露给浏览器的秘密必须保留在获授权的服务端。
2. 对公开网页、子域、外部脚本、第三方回调、浏览器扩展及 Agent 输入分别判定实际来源可信度；获得 DOM 访问能力不构成额外的业务授权。
3. 选用 OWASP ASVS v5.0.0 中与项目风险相关的控制，并使用版本化控制标识；不得因文档写了“采用 ASVS”就报告完全符合。
4. **验收**：交付真实域名和数据流的信任边界、身份及资源责任，并能关联到跨界拒绝测试。

### WEB-001 核验合同

- **WEB-001-P · 输入/动作与合格判据：** 追踪页面/iframe/SDK数据流→每个来源与接收者权限明确。
- **WEB-001-F · 直接失败变异：** DOM访问能力被当业务授权→失败。
- **WEB-001-N · 合法邻例：** 公开静态资产可匿名加载。

## 二、Origin、Site 与服务端最终授权
1. 区分同源、同站、子域及跨源。相同注册域的子域不必然可信，Origin 与 Site 也不等价。
2. 浏览器菜单、页面路由、隐藏按钮和本地角色标签只控制用户体验，不能替代权威后端对每个对象、权限和动作的服务器端检查。
3. CORS 是否允许浏览器读取某响应，与服务器是否有权处理该请求分属不同控制。
4. **验收**：以未授权用户、不同租户、直接 API URL、猜测对象 ID 和不同来源请求检查拒绝结果。

### WEB-002 核验合同

- **WEB-002-P · 输入/动作与合格判据：** 同站不同源与直连API换租户→对象授权独立成立。
- **WEB-002-F · 直接失败变异：** CORS读取许可被当写入授权→失败。
- **WEB-002-N · 合法邻例：** 已授权跨源读取可正常成功。

## 三、Cookie 和会话边界
1. 明确使用服务端会话、浏览器 OAuth 客户端或 Backend-for-Frontend（BFF）等真实身份架构，不能因框架模板使用某种 Cookie/Token 就自动沿用。
2. Session Cookie 按实际架构审查 Secure、HttpOnly、SameSite、Path、Domain、Max-Age 和 __Host- 等作用域；跨站及 Partitioned Cookie 依浏览器兼容与项目用途选择。
3. HttpOnly 阻止 JavaScript 读取对应 Cookie，但不能阻止浏览器带 Cookie 发送请求；Cookie 作用域本身不构成 CSRF 防护或对象授权。
4. 登录、重新验证、会话轮换、超时、退出、密码变更和权限撤销须在服务端有效，前端显示更新只是其结果。
5. **验收**：两个浏览器身份、登录／退出、续期／吊销、旧标签、浏览器恢复及不同 Cookie 作用域都能反映真实有效会话。

**来源与适用边界：** [RFC 6265 §4.1.2、§4.2.2、§8.2](https://www.rfc-editor.org/rfc/rfc6265.html) 支持 Domain/Path、Secure/HttpOnly 和环境式认证风险；不支持从该旧RFC推断 SameSite、__Host-、Partitioned 或当前第三方 Cookie 政策。这些能力按目标浏览器和身份系统的实际契约核验。

### WEB-003 核验合同

- **WEB-003-P · 输入/动作与合格判据：** 登录/轮换/登出/旧标签重用Cookie→服务端会话真实收敛。
- **WEB-003-F · 直接失败变异：** HttpOnly误称可防CSRF或Domain扩到不可信子域→失败。
- **WEB-003-N · 合法邻例：** 合法跨站方案按用途与浏览器限制选Cookie。

## 四、Token 暴露、秘密和浏览器持久化
1. 浏览器脚本可读取的内存、localStorage 与 IndexedDB 均非不可窃取的秘密仓库。按授权范围、XSS 风险、客户端类别选择令牌持有方式。
2. 适当架构可通过 BFF 或服务端持有上游访问令牌；真正需要浏览器调用外部 API 时，必须按所选公共客户端与身份提供方协议保护 Token 和作用域。
3. 服务端凭据不得进入 JS 发行包、构建常量、Source Map、URL、公开错误、监测数据或可访问的缓存。
4. 并发刷新、失效和撤销遵循同一权威会话，防止旧 Token、旧页面和跨身份缓存恢复访问。
5. **验收**：核对浏览器发行产物、存储、网络和回调日志，不包含超出项目授权的长期敏感凭据。

### WEB-004 核验合同

- **WEB-004-P · 输入/动作与合格判据：** 检查构建包/map/存储/刷新竞态→无服务端秘密及跨身份复活。
- **WEB-004-F · 直接失败变异：** 旧refresh回包覆盖新账号凭据→失败。
- **WEB-004-N · 合法邻例：** 公共客户端可按协议持有有限作用域Token。

## 五、CSRF 与有状态敏感请求
1. 对会自动携带认证凭据的写入，依据适用威胁模型实施实际服务器侧 CSRF Token、Origin 检查、Fetch Metadata 或其他有效控制及回归。
2. SameSite 和 CORS 不是完整 CSRF 替代品；Cookie 自动附带、同站不可信子域、登录回调和状态更改请求应分别检查。
3. GET 请求不应暗含未授权的付费、删除、授权或其他破坏性状态更改，用户误访问链接不能执行越权写入。
4. 对资金和账户安全相关不可逆动作按已批准业务需求追加真实身份确认，浏览器模态确认本身不构成服务端权限检查。
5. **验收**：合法同源写入与跨站伪造、无有效 CSRF 证明或错误 Origin 的请求得到正确的服务器端区分。

### WEB-005 核验合同

- **WEB-005-P · 输入/动作与合格判据：** 合法同源与跨站伪造写入→服务器验证CSRF且无未授权副作用。
- **WEB-005-F · 直接失败变异：** SameSite/CORS作为唯一跨威胁防护→失败。
- **WEB-005-N · 合法邻例：** 安全GET的访问日志/既定流量计量非用户请求的扣款命令。

## 六、跨源资源共享与凭据
1. 将允许访问的真实 Origin、凭据模式、请求方法和响应字段列入应用契约；不能为方便调试对外开放所有来源。
2. 带凭据的 CORS 响应不得配合 Access-Control-Allow-Origin: \*；动态返回具体受允许 Origin 时评估缓存的 Vary: Origin，防止 CDN 混淆。
3. 预检成功只说明浏览器允许相应网络交互，不能代替目标对象的鉴权／授权。
4. CORS 错误不保证服务器没有执行副作用；任何资金或写入动作须回读权威结果而非凭浏览器报错判断回滚。
5. **验收**：允许与拒绝的来源、带凭据与无凭据、预检和真实请求、缓存与跨租户均有可复核结果。

### WEB-006 核验合同

- **WEB-006-P · 输入/动作与合格判据：** 凭据CORS允许/拒绝Origin并经缓存→浏览器读取与业务写权分开。
- **WEB-006-F · 直接失败变异：** ACAO星号带凭据或CORS报错当未提交→失败。
- **WEB-006-N · 合法邻例：** 明确公开无凭据资源可允许通配来源。

## 七、OAuth/OIDC 与第三方登录回调
1. 浏览器 OAuth 架构参照 RFC 10017 与 RFC 9700 的当前 BCP，根据实际采用的 BFF／浏览器公共客户端确定凭据传递和安全模型。
2. 授权码流程对需要的客户端类型启用 PKCE，并核对一次性 state、Redirect URI、授权服务器标识以及需要时的 OIDC nonce；所有回调均绑定正确用户与事务。
3. 用户在第三方授权页同意、浏览器成功跳转或获得授权码，不自动代表本系统的合法账户已认证；须经过正确的服务器验证、授权与会话建立。
4. 回调重复、换身份提供方、授权拒绝、授权码重放或跨账号绑定失败时应拒绝错误状态并保留可操作恢复，不自动授予内部管理员权限。
5. **验收**：合法授权、无效 state/PKCE、错误回调来源、取消授权及重复回调均按实际服务器结果处理。

### WEB-007 核验合同

- **WEB-007-P · 输入/动作与合格判据：** 合法/错state/PKCE/issuer与重复回调→绑定同一认证事务。
- **WEB-007-F · 直接失败变异：** 跳转或授权码到手即授内部管理员→失败。
- **WEB-007-N · 合法邻例：** BFF和公共客户端可采用不同合规架构。

## 八、WebAuthn / Passkey
1. 需要 Passkey 时，以 2026-08-25 WebAuthn Level 3 Recommendation 为技术标准，按所选 RP、Origin、验证器及目标浏览器确定能力范围。
2. 浏览器凭据创建与断言需由后端验证 Challenge、RP ID、Origin、用户验证要求及账户绑定，不能只根据客户端 API 成功便认定用户认证成功。
3. 凭据增加、迁移、移除、恢复和高风险重认证按账户实际权利与批准的恢复流程处置，不以“便于登录”为理由提供绕过证明的后门。
4. **验收**：成功、取消、验证器不可用、挑战过期、错误 RP ID、账户切换和旧凭据吊销后均得到正确服务器侧结果。

### WEB-008 核验合同

- **WEB-008-P · 输入/动作与合格判据：** 新challenge与旧challenge、取消/错RP/换账号→后端验证断言。
- **WEB-008-F · 直接失败变异：** API resolve即认定认证或复用挑战→失败。
- **WEB-008-N · 合法邻例：** 不使用Passkey的产品不强制WebAuthn。

## 九、对象级授权与租户隔离
1. 浏览器发送的用户、租户、对象、文件和账单 ID 均只能是请求条件，不构成对资源拥有权的证据；后端必须逐项核对访问者的真实权限。
2. 普通用户、管理员、外部客户、合作伙伴等不同角色的菜单、页面、API 与导出操作保持一致，但不能依赖前端隐藏完成隔离。
3. 权限变更后重新使用旧 URL、旧缓存、历史标签或未过期访问令牌时，应按服务端权威拒绝已经撤销的操作。
4. **验收**：跨身份直接访问、同一用户不同角色、跨租户资源和历史下载链接均有真正的服务端拒绝／允许证据。

### WEB-009 核验合同

- **WEB-009-P · 输入/动作与合格判据：** 交换合法对象ID并直接下载/导出→每个对象和字段被授权。
- **WEB-009-F · 直接失败变异：** UUID难猜或隐藏菜单代替授权→失败。
- **WEB-009-N · 合法邻例：** 正式共享对象可按批准范围跨主体访问。

## 十、XSS、富文本和动态输出
1. API 响应、URL、富文本、Markdown、模型内容和第三方插件输入均按实际信任等级处理。普通文本优先以文本节点显示，确需 HTML 时使用符合实际上下文的编码与净化。
2. HTML、属性、URL、CSS 与 JavaScript 上下文的安全要求不同；仅过滤 script 标签或使用通用字符串替换不足以构成安全保证。
3. 框架通常提供默认转义，但手动使用危险 HTML 插入、srcdoc、直接拼接脚本或不可信第三方渲染时须单独验证。
4. HttpOnly 保护 Cookie 可降低泄漏风险，但同源恶意脚本仍可能在受害者权限下触发合法浏览器请求；须结合其他防护。
5. **验收**：使用合规、无害的测试输入对真实富文本与动态页面路径检查，证明不触发未授权脚本、敏感读取或内容丢失。

### WEB-010 核验合同

- **WEB-010-P · 输入/动作与合格判据：** HTML/属性/URL探针和合法富文本→净化/编码按上下文且无信息损失。
- **WEB-010-F · 直接失败变异：** 仅过滤script或认为框架默认转义覆盖危险sink→失败。
- **WEB-010-N · 合法邻例：** 纯文本无需解释成HTML。

## 十一、CSP 与 Trusted Types
1. Content-Security-Policy 按部署和第三方资源实际需求制定，宜从可观测的 Report-Only 阶段逐步验证，并区分最终执行策略与仅记录策略。
2. 评估脚本来源、Nonce、Hash 及动态脚本，避免为兼容旧依赖而默认放开全部 unsafe-inline/unsafe-eval 和不必要的第三方加载。
3. Trusted Types 可在支持环境限制 DOM 注入 sink；require-trusted-types-for 与 trusted-types 指令承担不同职责。相关能力进入 Baseline 2026，但旧版本浏览器仍需兼容验证。
4. 建立 Trusted Types policy 不会自动让不可信内容变安全，安全净化及实际业务内容保真仍必须单独核对。
5. **验收**：目标浏览器中正常功能、注入边界与 CSP 违规测试符合预期，正常脚本不会因安全头错误而不可用。

### WEB-011 核验合同

- **WEB-011-P · 输入/动作与合格判据：** 执行CSP与Report-Only对照、严格Trusted Types→正常功能和拒绝证据分开。
- **WEB-011-F · 直接失败变异：** Report-Only当阻断或policy直通不可信输入→失败。
- **WEB-011-N · 合法邻例：** 旧引擎无TT仍需上下文安全处理。

## 十二、HTTPS 与安全响应头
1. 正式公开入口和敏感操作应使用经实际验证的 HTTPS/TLS、合法证书与受控代理配置，不能仅凭浏览器显示锁图标推断所有内部链路安全。
2. 按实际站点拓扑选择 HSTS、Referrer-Policy、nosniff、CSP、frame-ancestors 等机制；涉及 HSTS 子域继承或预加载时先评估回滚及域名影响。
3. 授权码、一次性恢复 Token 和私密身份信息不应通过无关 Referrer、分享 URL、第三方脚本和错误上报泄漏。
4. **验收**：真实域名／子域及回调链的传输、资源、重定向、响应头和异常场景均具备可核验证据。

### WEB-012 核验合同

- **WEB-012-P · 输入/动作与合格判据：** 真实域名/回调/子域链→证书、Referrer、混合内容和安全头符合拓扑。
- **WEB-012-F · 直接失败变异：** HSTS扩域导致受支持子域不可用或泄恢复Token→失败。
- **WEB-012-N · 合法邻例：** 回环开发HTTPS例外不扩成生产政策。

## 十三、iframe、postMessage 与跨窗口信任
1. 嵌入式组件应明确父窗口、子窗口、外部 Origin、沙箱权限、所允许的设备功能以及真实业务权利。
2. postMessage 接收方验证 Origin、消息类型、数据结构与当前会话；发送方避免使用无约束目标 Origin 传输敏感资料。
3. iframe sandbox、Permissions Policy 与 frame-ancestors 的责任各不相同，不能以其中一个代替跨窗口身份／授权验证。
4. OAuth／支付等外部嵌入在第三方 Cookie 受限制时，须按真实支持的外部回调或跳转流程恢复，不能自动扩大浏览器权限。
5. **验收**：合法／非法嵌入、外部伪造消息、跨站 Cookie 禁用和权限撤销均保持数据与动作隔离。

### WEB-013 核验合同

**必要机制补充：** 接收postMessage时除origin还核对实际source窗口、消息结构、当前身份/导航世代和预期事务相关标识；相同origin的旧窗口不能凭来源字符串更新新会话。

- **WEB-013-P · 输入/动作与合格判据：** 父子窗口伪造origin/source/type并换账号→消息与会话绑定。
- **WEB-013-F · 直接失败变异：** 只验origin不验来源窗口/相关nonce导致旧窗口注入→失败。
- **WEB-013-N · 合法邻例：** 非敏感广播可按公开协议限定消息结构。

## 十四、第三方脚本与浏览器能力
1. 第三方分析、客服、支付 SDK、脚本、微前端或字体资源均需确定来源、许可、可见的用户数据、执行上下文与外部网络目的地。
2. 按适用场景使用版本锁定、SRI、受控 iframe 或隔离域；这些机制不能替代对供应商、隐私和数据再使用权的核实。
3. 摄像头、剪贴板、定位、推送等能力必须服务于已批准的实际功能，在需要时请求用户授权，并有拒绝／撤销后的可操作路径。
4. **验收**：第三方资源失败、授权撤销、资源版本变化和脚本异常时，不泄露额外数据，也不无故破坏核心流程。

### WEB-014 核验合同

- **WEB-014-P · 输入/动作与合格判据：** SDK失败/权限拒绝/撤销和资源变化→功能降级且无额外外传。
- **WEB-014-F · 直接失败变异：** SRI当供应商授权或摄像头失败偷偷扩权→失败。
- **WEB-014-N · 合法邻例：** 无实际硬件需求不请求设备权限。

## 十五、身份相关的本地存储与页面恢复
1. 会话 Cookie、JS 内存、localStorage、IndexedDB、Cache Storage 与 HTTP 缓存的作用域和生命周期不同；按权限与数据敏感性制定跨账号和过期策略。
2. 登出须使服务器授权失效，本地 UI 清理只是体验措施，不能代替撤销实际会话。
3. bfcache、旧标签、用户切换和离线缓存可能仍显示旧受限数据；重新操作前应检查当前有效的服务器权限与用户身份。
4. 个人化 SSR、CDN 和缓存密钥应保持不同用户的 HTML 和敏感状态隔离。
5. **验收**：登出后后退、跨账号切换、权限收紧、缓存清理与旧客户端恢复均无不当访问或新请求越权。

### WEB-015 核验合同

**必要机制补充：** 每次异步落地同时核对账号/租户世代、对象身份、查询/导航序号与必要数据版本；取消请求只是节约资源，不替代落地守卫。退出/换账号先推进世代并停止旧可见性，迟到Fetch、Worker、刷新令牌、IndexedDB读取、推送与多标签回调不得重新填入新账号缓存或队列。有权保留的旧账号草稿可隔离封存，不自动提交给新账号；对已经交付给外部主体的历史字节不宣称能通过登出物理撤回。

- **WEB-015-P · 输入/动作与合格判据：** 登出Back、B登录、旧异步存储回调→旧资料不再提供给B。
- **WEB-015-F · 直接失败变异：** 只清当前DOM而旧Cache/回包复活→失败。
- **WEB-015-N · 合法邻例：** 有权保留草稿可隔离封存不必全删。

## 十六、登录、退出、凭据重置和账户恢复
1. 登录、注销、密码修改、MFA、Passkey 注册、账户恢复和高风险操作再认证应以真实服务器结果为准；网页跳转与 Toast 只表示客户端动作。
2. 需要恢复码、重置链接或一次性授权时，按照实际合同和身份服务避免凭据经日志、第三方跳转或分享渠道泄漏。
3. 身份失败反馈应保护不必公开的账户信息，同时提供真正有助于合法用户恢复操作的内容，保持已要求的可访问性。
4. **验收**：正常与失败登录、重置成功、令牌重用、会话吊销和旧会话继续请求均可按实际权威验证。

### WEB-016 核验合同

- **WEB-016-P · 输入/动作与合格判据：** 登录/重置/令牌复用与旧会话请求→服务器事实和恢复路径一致。
- **WEB-016-F · 直接失败变异：** Toast成功即称凭据已重置或泄一次性Token→失败。
- **WEB-016-N · 合法邻例：** 隐藏资源存在性可配合可访问恢复指引。

## 十七、资源滥用与服务端限流
1. 对账号登录、身份恢复、敏感查询和外部付费写入，服务端落实真正的速率、账号、资源与成本上限；前端延迟、禁按钮和验证码只是辅助。
2. 人机验证和反滥用规则应评估真实用户、辅助技术、隐私、性能及收费影响，不因单一机器人检测而假设已防止身份滥用。
3. 对 429、Retry-After、临时拒绝和会话到期，按真实协议提供恢复路径，不用无限自动重试或绕过限制。
4. **验收**：允许的正常频次、受控高频模拟及真实后端拒绝证据符合项目批准的阈值。

### WEB-017 核验合同

- **WEB-017-P · 输入/动作与合格判据：** 正常频次/受控超限/Retry-After→服务器拒绝和成本有界。
- **WEB-017-F · 直接失败变异：** 前端禁按钮当服务端限额或多账号绕限→失败。
- **WEB-017-N · 合法邻例：** 明确合法无状态读取无须人机挑战。

## 十八、隐私、日志、遥测及事件响应
1. 前端日志、会话重放、错误上报与安全告警必须按合法目的与最小收集范围处理，禁止无授权采集恢复码、密码、会话 Token 或客户私有记录。
2. 对外只显示用户完成任务必要的认证、拒绝、恢复与安全信息；底层安全事件及调查证据存于获授权的审计渠道。
3. 登录异常、权限撤销、会话失效、第三方身份失败与安全故障，前端显示须与服务端实际状态一致，不凭隐藏错误推断业务恢复。
4. **验收**：测试异常会话与身份事件时，同时核对真实日志保护、用户反馈和业务操作权。

### WEB-018 核验合同

- **WEB-018-P · 输入/动作与合格判据：** 异常身份事件与日志/遥测一起核对→最小字段和真实反馈。
- **WEB-018-F · 直接失败变异：** 会话回放采到密码或隐藏错误当恢复→失败。
- **WEB-018-N · 合法邻例：** 有权运维渠道可保留必要诊断。

## 十九、技术安全门禁与独立验证
1. 针对项目实际使用的身份、跨源、富文本和嵌入入口，从 ASVS 5.0.0 选取适用版本化控制；不将“已有 ASVS 链接”当作全量合规证明。
2. 依赖扫描、Lint、单元测试、CSP 报告和自动化弱点检查各有覆盖范围；必须结合服务端对象级授权、真实浏览器 Cookie、CSRF 与跨租户请求等实际验证。
3. 多 Agent 安全审查应采用独立数据或测试，不把同一模型自我总结包装成第二个审查者；风险与权限按现行 L1/L2。
4. **验收**：工具版本、测试环境、请求与响应、权限条件、失败和未执行场景均可回溯，不能只报告安全工具绿色状态。

### WEB-019 核验合同

- **WEB-019-P · 输入/动作与合格判据：** 从真实入口组合Cookie/CSRF/租户/富文本→拒绝且权威副作用数为0。
- **WEB-019-F · 直接失败变异：** 扫描绿色或同模型复述当完整安全证明→失败。
- **WEB-019-N · 合法邻例：** 按风险选ASVS控制不伪造全量认证。

## 二十、专项静态场景与验收矩阵
| 情形 | 主要验证对象 | 实际合格条件 |
| --- | --- | --- |
| 普通用户请求管理资源 | 对象及角色授权 | 服务器拒绝未获授权的操作 |
| 跨租户资源或文件访问 | 对象身份、缓存隔离 | 无不同租户数据泄漏 |
| 登录、续期与退出 | Session Cookie、吊销 | 身份状态与后端一致 |
| 退出后旧标签与 bfcache | 重新校验权限 | 旧身份不能继续敏感写入 |
| 跨站伪造写入 | CSRF 与来源 | 非法请求被服务端拒绝 |
| 跨源带凭据请求 | CORS、Origin、Vary | 仅授权来源能读取允许的数据 |
| OAuth 异常回调 | PKCE、state、issuer | 错误请求不能建立会话 |
| Passkey 错误 Challenge | WebAuthn RP、服务器验证 | 非法凭据不能认证成功 |
| 不可信富文本输入 | 输出编码、XSS、CSP | 不执行未授权脚本 |
| Trusted Types 不兼容 | 策略及降级保护 | 旧浏览器功能可用且无危险放行 |
| 非法窗口消息 | postMessage Origin | 不触发额外数据写入或发送 |
| 第三方脚本能力 | 执行范围、数据权限 | 脚本不获取不允许的数据 |
| 私人 SSR 被 CDN 缓存 | 缓存和租户会话 | 不会跨账号响应个人数据 |
| 密码重置和令牌轮换 | 吊销旧会话 | 旧 Token 不恢复权限 |
| 跨源 iframe 身份回调 | Cookie 与嵌入边界 | 授权回调和失败恢复真实可靠 |
| 账号切换的本地缓存 | IndexedDB／Storage | 旧账户数据无法被新身份误用 |
| 异常高频登录 | 后端限流 | 限额与合法恢复都正确 |
| 敏感安全错误日志 | 监控与遥测 | 秘密不会传播到无关日志 |
## 二十一、规范性来源与版本选用
1. ASVS v5.0.0、RFC 10017、RFC 9700、WebAuthn Level 3 分别具有其发布状态和适用边界；采用具体控制与能力时注明所选版本及项目范围。
2. OWASP Cheat Sheets、MDN 的实施说明与兼容信息应作为指南和参考资料，不自动具有与 W3C Recommendation、IETF RFC 相同的强制属性。
3. L6 必须记录 OAuth Client 类型、实际用户／租户、Cookie 及浏览器范围、身份提供方、ASVS 适用控制和安全测试门禁；未采用某功能时不建立形式性检查。
4. L4 安全工程与身份系统等后续专项负责身份服务、鉴权和安全治理的完整技术实现；本专题仅规定 Web 浏览器端实施和验收关系。
## 二十二、审批及项目采用边界
本文的22个技术专题与18项静态场景用于选择项目测试；ASVS、OAuth BCP、WebAuthn及漏洞、授权与端到端验收须分别绑定适用版本、真实输入、预期和实际结果。
实际部署时应检验所采用的会话、权限、跨源、注入、第三方脚本及浏览器兼容规则。
