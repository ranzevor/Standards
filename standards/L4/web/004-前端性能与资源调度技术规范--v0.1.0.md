# L4 前端性能与资源调度技术规范

**文档ID：** STD-L4-WEB-004　**版本：** 0.1.0　**状态：** adopted　**生效日期：** 2026-10-30

## 技术范围与标准来源

本规范是 Web 领域下的具体技术专题，覆盖真实用户性能、资源加载、主线程调度、首屏与交互、布局稳定性、缓存和长期运行。实际性能门禁依据用户任务、目标设备、网络及业务风险选定。性能优化不得删减已批准的功能、安全、可访问性及必要业务内容。
技术参考：[L4 Web 领域通用基线](002-Web-领域通用基线--v0.1.0.md)（Web 通用基线）、[L4 浏览器文档、DOM 与交互组件技术规范](007-浏览器文档、DOM-与交互组件技术规范--v0.1.0.md)（DOM）、[L4 CSS 布局、视觉系统与响应式技术规范](001-CSS-布局、视觉系统与响应式技术规范--v0.1.0.md)（CSS）、[L4 渲染、路由与 Hydration 技术规范](009-渲染、路由与-Hydration-技术规范--v0.1.0.md)（渲染路由）、[L4 客户端状态、表单与网络数据技术规范](006-客户端状态、表单与网络数据技术规范--v0.1.0.md)（客户端状态）、[L4 离线、缓存与 PWA 生命周期技术规范](010-离线、缓存与-PWA-生命周期技术规范--v0.1.0.md)（PWA）、[L4 可访问性与复杂控件技术规范](005-可访问性与复杂控件技术规范--v0.1.0.md)（可访问性）以及相应 L1—L3 规范。
行业现有标准直接引用原文，组织规范不重写标准计算算法和 API 定义：
- [web.dev Core Web Vitals](https://web.dev/articles/vitals)：行业体验指标建议，目前“良好”参考目标 LCP ≤2.5 秒、INP ≤200 毫秒、CLS ≤0.1；按移动/桌面分组的真实用户页面访问第 75 百分位评估。不是 W3C Recommendation，也不自动成为所有项目的强制阈值。
- [W3C Resource Timing（2026-09-01 Candidate Recommendation Draft）](https://www.w3.org/TR/2026/CRD-resource-timing-20260901/)；[Largest Contentful Paint（2026-08-26 Working Draft）](https://www.w3.org/TR/2026/WD-largest-contentful-paint-20260826/)；[Long Animation Frames API（2026-04-28 First Public Working Draft）](https://www.w3.org/TR/2026/WD-long-animation-frames-20260428/)。
- [Navigation Timing 2](https://www.w3.org/TR/navigation-timing-2/)、[Performance Timeline 2](https://www.w3.org/TR/performance-timeline-2/)、[User Timing](https://www.w3.org/TR/user-timing/)：测量协议及接口，版本与成熟度依官方页面核对。
- [WHATWG HTML](https://html.spec.whatwg.org/multipage/)、[WHATWG Fetch](https://fetch.spec.whatwg.org/) 和 [RFC 9111](https://www.rfc-editor.org/rfc/rfc9111.html)：资源与 HTTP 缓存。
- [MDN fetchpriority](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Attributes/fetchpriority)、[modulepreload](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Attributes/rel/modulepreload)、[Prioritized Task Scheduling](https://developer.mozilla.org/en-US/docs/Web/API/Prioritized_Task_Scheduling_API)、[Speculation Rules](https://developer.mozilla.org/en-US/docs/Web/API/Speculation_Rules_API) 与 [Performance API](https://developer.mozilla.org/en-US/docs/Web/API/Performance_API)：实施及兼容资料，scheduler.postTask 与 Speculation Rules 仍存在 Limited availability。
本专题约束跨框架浏览器性能的可观察结果。具体框架、编译器、图像服务和监测 SDK 归 L5；L6 记录项目采用的性能目标、设备、真实业务路径与验证证据。

## 核验口径与消费接口

维护者负责落实本文机制，领域/API/存储提供者负责其权威保证，验收者从实际受支持入口观察结果。输入固定源码/构建、配置、数据/协议版本、角色/租户、目标平台、故障时序和预算；权威观察对象为**任务时间原点/终点、原始性能条目、总体分布与业务正确性**。真实执行入口为**DevTools Performance/Network、PerformanceObserver、受控Lab与有权RUM分段**。逐章 P/F/N 分别为正常输入及判据、破坏该机制的直接失败变异、应继续成立的合法邻例；本章原有每项规则、原有验收与新增合同共同约束，不用单一通用案例替代具体子项。每个子项须在案例输入中保留其适用条件，并以自身原文规定的输出/不变量判定；复合章应拆记录各个观察量，不能以一个成功掩盖其他失败。

证据产物包括真实命令/用户动作、原始响应或事件、权威状态前后值、版本、时序、失败及恢复；尚无对应真实运行证据的场景状态为 `not-run`，标准库示例仅证明列明的局部边界。具体输入与命令见[执行入口](../../../examples/web-backend/RUNBOOK.md)，条款索引见[规范条款登记](../../../registry/requirements.json)，来源的有限支持命题见[逐命题来源映射](../../../sources/web-backend/claims.json)。

本文的跨组件约束与正例、失败反例、合法邻例由本规范综合定义；外部来源支持的机制及适用边界见来源表。项目架构、预算和业务规则由实际需求确定。L5 实现应映射到所选框架、SDK 或引擎；L6 按具体版本的提供者保证与受支持矩阵验收项目能力。

## 一、任务级性能目标与预算
1. 将首屏可读、真实操作可执行、搜索稳定、表单完成、跨页面恢复等用户任务分别定义开始时刻、结束条件、输入规模及其需要保留的完整业务结果。
2. 任务预算至少区分初始加载、交互响应、页面导航、长期运行和错误恢复；请求已完成、Loading 消失、服务器已接受和业务最终生效不得混为一个计时终点。
3. 按已批准的用户群体、设备、浏览器、网络、可访问性和风险选择关键指标，按项目决定阈值与容差；不强迫原型和生产交易应用采用相同性能门禁。
4. **验收**：每项强制指标能关联真实任务、目标用户/设备、测量方法、预算来源、失败处理及实际测试证据。

### WEB-001 核验合同

- **WEB-001-P · 输入/动作与合格判据：** 固定任务入口/输入和权威终点计时→加载/交互/恢复预算分开。
- **WEB-001-F · 直接失败变异：** Loading消失当外部业务已完成→失败。
- **WEB-001-N · 合法邻例：** 原型可选择相称预算而不套生产指标。

## 二、实验室测试与真实用户监测
1. Lab 使用固定版本、浏览器、CPU、网络、冷/暖缓存和输入数据复现问题；RUM 观察用户真实访问环境和行为分布。两者的适用范围和结论分别报告。
2. Core Web Vitals 的用户分位数应按实际移动与桌面访问分组，记录样本量、采样窗口、地域及站点流量变化；不能以单次 Lighthouse 分数证明真实访问 p75 合格。
3. 对登录/未登录、不同语言、不同页面、老旧设备及复杂应用导航分别定义实际覆盖；指标未观测到、浏览器 API 不支持和测试没有运行需要明确区分。
4. **验收**：实验可重放，RUM 样本与统计口径可核查；只有相同对象与真实条件的测试结果才适合直接比较。

### WEB-002 核验合同

- **WEB-002-P · 输入/动作与合格判据：** 同构建冷暖Lab及分组RUM→样本/窗口/流量来源清楚。
- **WEB-002-F · 直接失败变异：** 单次Lab分数当真实p75或缺失当零→失败。
- **WEB-002-N · 合法邻例：** 无足量RUM时仅报告受控实验。

## 三、浏览器测量 API、版本与盲区
1. PerformanceObserver、Navigation/Resource/User Timing、LCP、Event Timing、Layout Shift、Long Tasks/Long Animation Frames 的行为及目标浏览器支持程度分别核查，不以 API 名称相似推断功能等价。
2. 支持时检查 PerformanceObserver.supportedEntryTypes、buffered 参数、缓冲区上限和注册时机；某些性能条目不能单靠 getEntriesByType 回放完整结果。
3. 跨源 Resource Timing 的细粒度字段可能因隐私限制返回零，必要时由资源权利方按需提供 Timing-Allow-Origin，不能把受限值直接当作真实零耗时。
4. 普通导航、SPA 软导航、bfcache 恢复和页面隐藏时的计时起点不同，测量规则必须避免重复采样和错误拼接。
5. **验收**：所报指标带有实际支持环境、时间原点、采样限制、缺失原因和可复核归因。

### WEB-003 核验合同

**必要机制补充：** 指标缺失、不支持、缓冲溢出、页面隐藏/恢复等分别编码为未观测原因，不填为零。跨来源受限计时与用户访问完整性不能通过虚构采样补齐。

- **WEB-003-P · 输入/动作与合格判据：** 核supportedEntryTypes/注册时刻/跨源TAO→条目盲区和时间原点标出。
- **WEB-003-F · 直接失败变异：** 受限Resource Timing零值当零耗时→失败。
- **WEB-003-N · 合法邻例：** 不支持的API可明确not-observed而非失败指标。

## 四、首访导航与服务端 TTFB 分段
1. 对资源导航识别重定向、DNS、连接、请求、响应首字节、下载、解析与浏览器呈现阶段，不能看到慢首屏就单方面假定数据库或前端脚本为唯一根因。
2. CDN 命中、客户端缓存、SSR 数据查询、后端排队及地理网络延迟需按可取得的原始证据分别归因；需要时关联受权 Server-Timing 或实际后端追踪。
3. 预连接、协议升级、边缘缓存等优化须在真实入口测量，并考虑额外连接、误命中和第三方流量成本。
4. **验收**：冷/暖访问、不同网络、重定向和真实服务端响应具有可追溯的阶段耗时与改进效果。

### WEB-004 核验合同

- **WEB-004-P · 输入/动作与合格判据：** 冷暖导航含DNS/重定向/CDN/SSR→分段证据定位真实瓶颈。
- **WEB-004-F · 直接失败变异：** 慢首屏直接归因数据库→失败。
- **WEB-004-N · 合法邻例：** 有权Server-Timing可补充而不泄敏感内部值。

## 五、LCP 元素与首屏关键资源
1. 记录页面实际 LCP 候选、首要业务内容及对应资源发现、排队、加载、绘制的时间；不能只因缩小图片或降低 Bundle 体积就认定首屏已更快。
2. 对 CSS 背景、JS 动态插入、SSR 延迟与需 Hydration 后出现的资源，按真实瀑布判断可提前发现的部分，而非机械添加 preload。
3. 对应首屏的文字、图片、字体和 API 内容不应被错误 lazy loading、永久 Skeleton、不可读 fallback 或无控制的脚本工作推迟。
4. **验收**：候选元素、关键请求、网络时序和最终可见业务内容保持一致，实际 LCP 及任务完成结果均有证据。

### WEB-005 核验合同

- **WEB-005-P · 输入/动作与合格判据：** 记录实际LCP候选和资源发现瀑布→首要内容及时可读。
- **WEB-005-F · 直接失败变异：** 压Bundle即宣称LCP改善或关键图lazy到永不见→失败。
- **WEB-005-N · 合法邻例：** LCP候选与业务关键内容不同可另记任务指标。

## 六、资源优先级、预连接与预加载
1. fetchpriority、preload、modulepreload、preconnect 和 dns-prefetch 只在明确关键依赖时使用；优先级是浏览器提示而非传输完成保证。
2. 将所有脚本、图片与字体设置为最高优先级会造成争抢，必须衡量关键 CSS、LCP 资源和首屏数据接口的实际时序及影响。
3. 检查模块图、跨源凭据模式、资源类型、预加载实际使用率、重复下载、缓存复用与加载失败后的正确回退。
4. 第三方资源的提前连接与加载要按真实同意、数据用途和隐私边界决定。
5. **验收**：关键资源确实提前可用，没有使其他必需资源、弱网体验或业务动作退化。

### WEB-006 核验合同

- **WEB-006-P · 输入/动作与合格判据：** 匹配as/type/credentials预加载并看瀑布→实际复用、无争抢重复下载。
- **WEB-006-F · 直接失败变异：** 把所有资源high或跨源凭据错配→失败。
- **WEB-006-N · 合法邻例：** 无明确关键依赖不需要preload。

## 七、JavaScript 编译执行与 Hydration 开销
1. 分别衡量脚本传输、解压、解析、编译、执行、初始状态恢复、事件附着和第一次可交互时刻；“代码包变小”不等于整个操作更快。
2. 按真实路由与功能拆包，防止动态导入引入级联网络瀑布、必要按钮始终缺代码、旧缓存和新资源版本不兼容。
3. SSR、流式 HTML、部分 Hydration 与 CSR 的选择遵循相邻渲染规范；性能优化不得丢失用户提前输入、焦点、服务端授权和重要内容。
4. **验收**：慢网络与低端 CPU 下，接管前后页面关键功能、草稿、网络结果与错误反馈完整且时序正确。

### WEB-007 核验合同

- **WEB-007-P · 输入/动作与合格判据：** 慢CPU/JS下载时提前输入→解析/接管成本可见且输入不丢。
- **WEB-007-F · 直接失败变异：** 仅字节变小当可交互更快→失败。
- **WEB-007-N · 合法邻例：** 纯CSR不需报告Hydration阶段。

## 八、INP 与事件、呈现的真实延迟
1. 将慢交互分为输入排队延迟、事件回调执行耗时和后续画面呈现延迟，利用 Trace、Event Timing、Long Tasks 或 Long Animation Frames 识别真正瓶颈。
2. 选取连续键盘输入、搜索建议、复杂表单、滑动列表、组合控件和快速多次点击等代表性用户操作，不能只测空页面首个按钮。
3. 大 DOM、主线程同步转换、组件重绘和布局抖动可能延迟下一帧；选择任务拆分、Worker 或局部更新必须有实际数据支持。
4. **验收**：INP 变化能关联具体控件和真实用户结果，不能通过删去必需功能、延迟错误消息或牺牲可访问性交互制造达标。

### WEB-008 核验合同

- **WEB-008-P · 输入/动作与合格判据：** 连续输入/快速点击Trace→排队/处理/呈现分段且最终动作完成。
- **WEB-008-F · 直接失败变异：** 隐藏错误/删除功能把INP压低→失败。
- **WEB-008-N · 合法邻例：** 未产生可观测交互不能伪造INP零值。

## 九、任务调度、优先级与中断
1. 区分直接响应用户输入、下一帧可见更新、后台计算和可延后工作。每种任务应有优先级、版本有效性、取消条件和资源预算，不能在组件卸载后无条件提交过期结果。
2. scheduler.postTask、scheduler.yield 等 Prioritized Task Scheduling API 目前不支持所有主流浏览器；项目要核实支持情况、明确替代路径和预期调度公平性。
3. requestAnimationFrame 用于帧关联的视觉更新；requestIdleCallback、计时器或后台节流不能承诺服务器写入、外部交易与用户通知会按时发生。
4. **验收**：持续键盘输入、弱设备、后台标签、旧浏览器和大量待运行任务中，关键交互能获得及时处理，后台任务可取消和恢复。

### WEB-009 核验合同

- **WEB-009-P · 输入/动作与合格判据：** 持续输入与后台任务换世代→关键输入不饿死、旧结果不落地。
- **WEB-009-F · 直接失败变异：** timer/rIC当业务准确期限或缺scheduler后无动作→失败。
- **WEB-009-N · 合法邻例：** 可用原生事件循环替代新scheduler API。

## 十、Web Worker 与并行计算
1. 对大数据解析、搜索索引、图表预处理或复杂计算，先比较 Worker 的启动、结构化克隆、Transferable 消息成本和总内存，再决定是否迁出主线程。
2. Web Worker 不直接操作 DOM；异步返回必须关联实际查询、用户身份和数据版本，不能把过期结果写入当前界面。
3. OffscreenCanvas、SharedArrayBuffer 等能力按实际浏览器及跨源隔离要求采用；不能因提升性能降低安全、兼容或数据权利约束。
4. **验收**：Worker 前后测试覆盖耗时、输入响应、消息频率、内存峰值、取消、崩溃及回退，不以线程数增多推断体验改善。

**来源与适用边界：** [HTML §10.1、§10.2](https://html.spec.whatwg.org/multipage/workers.html) 定义 Worker 后台全局、消息与终止；[DOM Document](https://dom.spec.whatwg.org/#interface-document) 的 Window 暴露与 WorkerGlobalScope 区分页面 DOM 边界。身份/版本关联和过期结果拒绝是本规范的工程要求，不是原生表单算法。

### WEB-010 核验合同

- **WEB-010-P · 输入/动作与合格判据：** Worker传大数据/取消/崩溃→克隆成本、内存、当前身份检查正确。
- **WEB-010-F · 直接失败变异：** 旧Worker回包写新账号或线程数当性能证据→失败。
- **WEB-010-N · 合法邻例：** 小计算留主线程可更便宜。

## 十一、布局、绘制及合成
1. 按 DevTools 或等价时间轴区分 Style Recalculation、Layout、Paint、Composite 与重排抖动；正确定位强制同步测量、反复读写和过大 DOM 的实际成本。
2. CSS contain、content-visibility、will-change、虚拟列表、GPU 合成和动画仅在有实测收益时启用，须保留真实滚动、焦点、DOM 语义和辅助技术可访问性。
3. 设备刷新率差异影响帧预算，不能把 60Hz 的约 16.7ms 固定写成全部终端的唯一门槛。
4. **验收**：长文本、复杂表格、图表和动态布局在目标设备上实际渲染更好，同时关键内容和操作没有被裁切或隐藏。

### WEB-011 核验合同

- **WEB-011-P · 输入/动作与合格判据：** 目标刷新率长表滚动Trace→layout/paint/composite收益且语义保留。
- **WEB-011-F · 直接失败变异：** 60Hz帧阈值套所有终端或虚拟化丢焦点→失败。
- **WEB-011-N · 合法邻例：** 无瓶颈不强制GPU合成。

## 十二、CLS 与视觉稳定性
1. CLS 计算和会话窗口沿用官方指标；不能自己重新发明算法，也不能将用户可预期的主动布局变化和非预期位移混为相同失败。
2. 字体回退、图片尺寸、广告位、异步数据、组件占位和列表插入都需要按真实布局预留合理空间，避免移动用户即将点击的关键控件。
3. 禁止通过全局 overflow:hidden、隐藏错误消息、裁切重要业务字段或固定不可滚动高度来人为压低布局位移。
4. **验收**：按目标浏览器记录实际位移贡献与触发条件，验证优化后的键盘焦点、点击命中和用户必要信息仍然正确。

### WEB-012 核验合同

- **WEB-012-P · 输入/动作与合格判据：** 字体/媒体/异步占位带真实位移记录→会话窗和任务可操作。
- **WEB-012-F · 直接失败变异：** overflow隐藏字段来压CLS→失败。
- **WEB-012-N · 合法邻例：** 允许的用户主动位移按指标定义分类。

## 十三、图片、媒体和字体资源预算
1. 以目标语言、设备和用户任务决定图片分辨率、DPR、srcset/sizes、格式和裁切；压缩后不能损害图标和重要主体的辨认。
2. Web 字体考虑子集、font-display、CJK/RTL 字形、回退宽度、文件体积和首屏呈现，不能用隐藏文字换取较低 CLS 或加载时间。
3. 视频、Canvas、动态图表需评估下载、解码、GPU/内存、滚动与资源释放，对目标辅助技术保持已批准的可访问替代路径。
4. **验收**：资源加载成功/失败、弱网、字体缺字和图片高 DPR 下，性能和信息完整性同时有证据。

### WEB-013 核验合同

- **WEB-013-P · 输入/动作与合格判据：** 目标DPR/缺字/失败资源→尺寸/解码/性能和替代内容兼顾。
- **WEB-013-F · 直接失败变异：** 隐藏文字或压缩到关键图不可辨→失败。
- **WEB-013-N · 合法邻例：** 装饰媒体可降质量但不损关键信息。

## 十四、HTTP、CDN 与缓存性能
1. 正确区分 RFC 9111 所定义的 HTTP Cache、Service Worker CacheStorage 与前端 Query Cache，缓存新鲜度须按真实资源、身份、租户和业务版本处理。
2. 对公开指纹资产、HTML Shell、私有 SSR 内容、API 和多语言响应分别选择压缩、缓存、ETag、Vary 和失效规则；提高命中率不能导致泄露或错用个人化数据。
3. 统计请求数、重复下载、响应体、协议连接、CDN 回源和重定向成本；长缓存策略须容忍旧客户端标签与新资源/API 版本共存。
4. **验收**：冷热访问、账号切换、服务器缓存和回滚场景中，性能收益与真实权限、兼容和内容一致。

### WEB-014 核验合同

- **WEB-014-P · 输入/动作与合格判据：** 跨身份冷暖访问及旧标签回退→三类缓存分清且权限不丢。
- **WEB-014-F · 直接失败变异：** 命中率更高但私人HTML共享→失败。
- **WEB-014-N · 合法邻例：** 公开hash静态资源可长缓存。

## 十五、远端查询、实时数据与网络请求
1. 依据数据依赖优化瀑布、重复读取、分页和后台轮询。并行请求与预测加载应核对权限、正确顺序、真实使用率与资源成本。
2. 数据查询库缓存和 HTTP 缓存具有不同的新鲜度逻辑；资金、库存、权限和外部结果不得因减少延迟直接使用过期快照作为决策权威。
3. 高频 SSE/WebSocket 更新应结合版本、聚合与重绘成本处理；削减频率不可丢失用户必需的警报、业务差异和错误信息。
4. **验收**：请求图、真正的服务端结果、用户可见更新、网络与 CPU 开销可复核，未知提交状态不会被当成已完成。

### WEB-015 核验合同

- **WEB-015-P · 输入/动作与合格判据：** 并行数据依赖/实时更新限速→结果新鲜度、请求和CPU都可查。
- **WEB-015-F · 直接失败变异：** 过期余额当权威或合并掉必需告警→失败。
- **WEB-015-N · 合法邻例：** 可交换的非关键视觉采样可合并。

## 十六、推测性预取与导航预渲染
1. 分清资源 prefetch、应用内预加载和整页 prerender 的触发时机、缓存、副作用、流量成本和用户授权。
2. Speculation Rules API 目前仍有浏览器支持限制，应使用实际特性检测并为其他浏览器提供普通导航或经验证的降级。
3. 任何 hover/预测导航或预渲染不能无用户实际授权而执行支付、删除、账户修改、通知等外部副作用，也不得未获许可传播个人化数据。
4. **验收**：预测命中/未命中、弱网、身份改变及旧浏览器条件下，加载效率和业务正确性分别成立。

### WEB-016 核验合同

- **WEB-016-P · 输入/动作与合格判据：** 预测命中/未命中/身份变化→只预取有权读取且预算内。
- **WEB-016-F · 直接失败变异：** hover预渲染执行购买/发送→失败。
- **WEB-016-N · 合法邻例：** 不支持Speculation Rules时普通导航可用。

## 十七、长期运行、内存与生命周期恢复
1. SPA、数据仪表板与管理系统要对长时间使用的监听器、Observer、定时器、Socket、Worker、组件卸载和大型对象引用进行实际观察；首次渲染流畅不等于持续运行健康。
2. bfcache、标签冻结、恢复、旧标签、账号切换与网络重连的影响由相邻路由和 PWA 规范定义；性能实现不得重新创建无数后台订阅或错用原身份数据。
3. 浏览器内存诊断的采集范围和支持情况不同；使用 Chrome 专有指标时注明适用边界，设备低存储时也不能静默丢失有权保留的草稿。
4. **验收**：多小时重复操作、离开/返回和账号变更后，内存、网络连接、交互和重要数据保持在项目要求内。

### WEB-017 核验合同

- **WEB-017-P · 输入/动作与合格判据：** 长时重复挂卸/冻结/Back/换账号→监听、内存、连接回归稳定。
- **WEB-017-F · 直接失败变异：** 初始化重复订阅或借清缓存丢草稿→失败。
- **WEB-017-N · 合法邻例：** 专有内存指标只声称对应浏览器范围。

## 十八、第三方脚本与组件开销
1. 分析、支付、地图、客服、身份 SDK、字体和媒体服务需纳入加载、执行、内存、网络和隐私预算；三方造成的慢交互也影响真实用户任务。
2. 延迟、移除或沙箱化第三方脚本前必须核对真实业务依赖、供应商协议、授权用途和安全边界；不能靠禁用支付或身份校验让跑分变绿。
3. 第三方版本升级、资源失败、过期 CDN 和执行阻塞需纳入回归，不能把供应商宣称的“高性能”作为本项目客观证据。
4. **验收**：真实第三方慢响应或不可用时，关键业务有准确结果与恢复路径，主线程和请求成本可测。

### WEB-018 核验合同

- **WEB-018-P · 输入/动作与合格判据：** 三方慢响应/失败对照→关键业务恢复且开销可测。
- **WEB-018-F · 直接失败变异：** 禁用身份/支付校验换绿分→失败。
- **WEB-018-N · 合法邻例：** 非关键装饰SDK可按功能合同延迟。

## 十九、低端设备、弱网与辅助技术
1. 根据目标用户选取真实或可信模拟的慢 CPU/GPU、低内存、低带宽、高 RTT、移动浏览器、输入法、系统字体及必要辅助技术组合。
2. 页面放大、forced-colors、阅读器和减弱动效可能改变浏览器工作量；优化不能禁止缩放、隐藏信息或取消已批准的无障碍能力。
3. 电量限制与后台节流会改变预取、动画和任务调度；对确有离线/恢复业务要求的功能必须保留实际可用的路径。
4. **验收**：目标设备上的真实任务耗时、可达性、错误反馈及数据完整性满足已批准范围。

### WEB-019 核验合同

- **WEB-019-P · 输入/动作与合格判据：** 低RAM/高RTT/缩放/AT真实任务→预算和可达性同时成立。
- **WEB-019-F · 直接失败变异：** 禁缩放或隐藏通知换速度→失败。
- **WEB-019-N · 合法邻例：** 可信模拟证据不冒充特定真机结论。

## 二十、性能监测的隐私与统计约束
1. RUM 的 URL、资源路径、设备与交互时间等字段可能包含敏感信息。采样、传输、聚合、保留期限与第三方接收者必须符合真实授权和用户数据使用目的。
2. 不把 Cookie、令牌、私有订单标识、完整用户输入和无权传播的诊断内容发送给性能分析供应商。
3. p75 与回归判断需保留统计窗口、分段、样本量与发布版本；流量变化、客户端升级和样本缺口可能影响结论，不能将相关性直接当作性能优化的因果证明。
4. 监控脚本本身也消耗 CPU、内存和网络；Observer 订阅和上报频率须可控，不能为了采集而使用户体验退化。
5. **验收**：隐私、样本和监测开销均可核实，未观测的用户群体和指标有准确说明。

### WEB-020 核验合同

- **WEB-020-P · 输入/动作与合格判据：** 采样窗口/发布分段/撤回选择→统计可复算且采集最小化。
- **WEB-020-F · 直接失败变异：** 完整私有URL外发或相关性冒因果→失败。
- **WEB-020-N · 合法邻例：** 无授权RUM时保留本地受控测量。

## 二十一、性能质量门禁与工程回归
1. 每个项目按批准的核心任务选择 RUM、Lab、资源、交互、视觉、长期运行和必要业务性能目标；不设全部语言、框架和业务统一的 Lighthouse 分数或固定 Bundle 上限。
2. 待审查版本应在相同设备、网络、浏览器、字体、缓存和数据集上与有效基线进行多轮对照；测量波动较大时采用合理统计，不用单次偶然通过或失败替代完整结论。
3. 回归必须定位资源加载、JS、主线程任务、CSS、第三方 SDK 或服务器阶段的真实原因。不得通过放宽阈值、删测试、隐藏错误或删减必要功能制造通过。
4. 高成本测试可在已有证据等价且覆盖当前风险时复用；工具或 CI 额度限制不构成省略关键业务路径的理由。
5. **验收**：独立区分文本标准、构建检查、性能 Lab、RUM、生产发布和真实用户任务达标状态。

### WEB-021 核验合同

- **WEB-021-P · 输入/动作与合格判据：** 相同条件多轮候选/基线→回归因果及边界可解释。
- **WEB-021-F · 直接失败变异：** 放宽阈值/删失败/删功能制造通过→失败。
- **WEB-021-N · 合法邻例：** 有效等价证据可复用无需无价值重复跑数。

## 二十二、专项性能验收矩阵
| 场景 | 关键输入或失效模式 | 实际合格条件 |
| --- | --- | --- |
| RUM 与 Lab 不一致 | 设备、流量、缓存与样本分布变化 | 按适用人群报告，分位数和样本局限真实 |
| Performance API 不支持 | LoAF/Event Timing 条目缺失 | 只使用实际可观察的数据，标注未知或合理降级 |
| 跨源资源计时受限 | Timing-Allow-Origin 不存在 | 不将受限零值冒充零耗时 |
| 导航加载瓶颈 | CDN、重定向、TTFB 混合延迟 | 按真实阶段归因并完成正确首屏 |
| 关键资源发现太晚 | CSS 背景主图、JS 延迟插入 | LCP 改善且首屏信息完整 |
| 过量预加载 | preload/fetchpriority 抢占带宽 | 其他重要资源及输入交互不退化 |
| 大 Bundle 与 Hydration | 弱网、慢 CPU、提前交互 | 页面可见及输入/焦点接管正确 |
| 高 INP 与长任务 | 输入、事件处理、下一帧阻塞 | 定位根因并保留真实交互行为 |
| 调度 API 受限 | 旧浏览器、后台标签 | 可取消、继续与降级，不永久阻塞必要任务 |
| Worker 返回过期数据 | 快速搜索后异步回调 | 不覆盖新数据，资源正常释放 |
| 重绘与虚拟滚动 | 大列表、复杂 CSS | 渲染更快，屏幕阅读器及业务字段仍可访问 |
| CLS 与文字跳动 | 字体延迟、图片尺寸不定 | 位移减少且必要信息不被裁剪 |
| 资源失效/弱网 | 图片缺失、字体回退 | 主内容仍可读，性能与内容完整性兼顾 |
| 旧客户端缓存 | 旧 HTML、JS 与新 API | 版本一致、权限正确且能恢复 |
| 重复实时请求 | 轮询/推送频繁刷新 | 资源使用下降而数据仍保真 |
| 预渲染的外部副作用 | Speculation Rules 预测导航 | 预取阶段不执行未授权交易/通知 |
| 长时间运行 | Listener、Observer、Worker 泄漏 | 内存和响应无持续异常退化 |
| 第三方 SDK 阻塞 | 支付或身份资源超时 | 不删除必要业务与安全能力 |
| 低端设备及辅助功能 | 放大、读屏、低网速 | 目标任务实际完成且输入可用 |
| 合成跑分与生产背离 | CI 通过但 RUM 退化 | 保留真实结果，不虚报生产达标 |
## 二十三、职责边界、审批及项目接入
1. 平台 API、计量算法和正式协议由 W3C、WHATWG 及 IETF 对应来源规定；Core Web Vitals 是 Google 的行业指标建议。本规范只补充可执行的技术决策、测量归因、资源调度和验收，不能误将 Working Draft、MDN 指南或行业建议变成全部项目的强制义务。
2. 相邻 DOM、CSS、渲染、客户端数据、PWA、浏览器身份和无障碍专项继续负责自身领域的实际功能与安全要求，优化不得绕过其约束。
3. 特定框架调度器、构建系统、CDN、图片管线与性能采样 SDK 由 L5 细化；L6 固定每个项目的设备、网络、用户任务、统计方式、门禁阈值和实际测试结果。
本文技术条款、场景与官方来源的文本审查，不能推断任何真实网站已经达到 Core Web Vitals、用户任务响应或跨浏览器性能标准；实际项目仍须按 L6 选择目标并完成运行验证。
