## 技术范围与权威依据

本规范约束浏览器侧的数据状态、表单草稿、网络请求生命周期、远端查询缓存、用户操作提交、冲突与失败恢复，以及需要明确的数据保留与客户端持久化。适用于 CSR、SSR、混合渲染和嵌入式 Web 应用；不要求所有项目采用状态管理库、离线同步或某种 API 协议。

- [WHATWG URL Standard](https://url.spec.whatwg.org/)：URL 与查询参数的规范语义。

本规范只补充组织对**状态权威、并发竞争、输入和错误处理、缓存及真实业务结果确认**的工程约束。各框架的 store、hook、signals、query cache、form package 等具体实现由 L5 定义；后台事务、账本、授权与网络协议属于对应 L4 技术专题；项目 L6 指定技术选型、用户目标与验收范围。

## 核验口径与消费接口

维护者负责落实本文机制，领域/API/存储提供者负责其权威保证，验收者从实际受支持入口观察结果。输入固定源码/构建、配置、数据/协议版本、角色/租户、目标平台、故障时序和预算；权威观察对象为**草稿快照、查询来源/版本、当前身份世代与权威业务操作收据**。真实执行入口为**DevTools Network/Application、真实表单/IME、双标签并发与权威API查询**。逐章 P/F/N 分别为正常输入及判据、破坏该机制的直接失败变异、应继续成立的合法邻例；本章原有每项规则、原有验收与新增合同共同约束，不用单一通用案例替代具体子项。每个子项须在案例输入中保留其适用条件，并以自身原文规定的输出/不变量判定；复合章应拆记录各个观察量，不能以一个成功掩盖其他失败。

证据产物包括真实命令/用户动作、原始响应或事件、权威状态前后值、版本、时序、失败及恢复；尚无对应真实运行证据的场景状态为 `not-run`，标准库示例仅证明列明的局部边界。具体输入与命令见[执行入口](../../../examples/web-backend/RUNBOOK.md)，条款索引见[规范条款登记](../../../registry/requirements.json)，来源的有限支持命题见[逐命题来源映射](../../../sources/web-backend/claims.json)。

本文的跨组件约束与正例、失败反例、合法邻例由本规范综合定义；外部来源支持的机制及适用边界见来源表。项目架构、预算和业务规则由实际需求确定。L5 实现应映射到所选框架、SDK 或引擎；L6 按具体版本的提供者保证与受支持矩阵验收项目能力。

## 一、数据所有权与状态分类
1. 项目需要能够辨认六类状态：服务器／第三方系统权威业务状态、查询结果快照及缓存、URL 可分享状态、用户尚未提交的表单草稿、纯展示交互状态、获准保留的本地持久化数据。它们的修改权、失效条件和可传播范围不同。
2. 对订单、资金、权限、库存、用户权益、跨设备配置等外部事实，不得将浏览器变量、乐观预测或本地缓存当作已生效的最终记录。
3. 同一业务对象的不同视图优先共享稳定的身份与数据来源；局部展示变换可派生，不得由于多个 store 各自维护可写副本而长期产生矛盾。
4. 状态字段与 UI 标签须保持真实业务条件和必要字段，不得用简化类型、遗漏判定条件或技术状态代替产品要求的区别。
5. **验收**：给出每项关键状态的权威来源、修改者、有效期间和刷新/清理触发条件；证明来源变化能正确传播到受影响的用户路径。

### WEB-001 核验合同

- **WEB-001-P · 输入/动作与合格判据：** 同一订单在URL/草稿/查询/服务端读取→来源与修改权可区分。
- **WEB-001-F · 直接失败变异：** 乐观余额当账本或双store可写副本永久冲突→失败。
- **WEB-001-N · 合法邻例：** 局部纯展示可从权威输入派生。

## 二、状态转移、派生数据与不变量
1. 对有业务含义的交互状态，明确允许的起点、操作、成功结果、失败结果、取消和恢复。网络加载态、保存中、已确认、部分成功、提交结果未知等不得用单一布尔变量制造不可能的组合。
2. 派生值由能够核实的输入计算。排序、过滤、展示数量、金额与权限视图不能从彼此已过期的缓存独立拼出貌似真实的业务结果。
3. 同一事件在相同版本和输入条件下应有可解释的结果；重复回调、重试和组件重挂载不得在未经授权的情况下重复执行业务写入。
4. 需要回放、撤销、重做或多步骤工作流时，明确动作是否可逆、是否只改变本地草稿，以及对远端真正的补偿条件。
5. **验收**：针对允许与拒绝转移、重复事件、过期响应及资源销毁构造状态转换测试，检查不变量和最终可见结果。

### WEB-002 核验合同

- **WEB-002-P · 输入/动作与合格判据：** 重复事件/取消/部分成功交错→仅允许转移且未知独立可查。
- **WEB-002-F · 直接失败变异：** 单boolean同时表示失败与已提交→失败。
- **WEB-002-N · 合法邻例：** 无需撤销业务不制造undo流程。

## 三、服务端数据读取、查询与身份维度
1. 查询由实际资源身份、查询参数、有效用户／租户、地区／语言、权限条件及接口版本决定；缓存与去重键必须纳入影响结果的维度，不允许跨身份误复用。
2. 分页、过滤、排序、汇总和细节查询应与权威接口契约保持一致。数据集变动时不得把不同时间或权限条件的页面随意拼接成完整结果。
3. 对实时性和准确性有明确要求的数据，定义新鲜度窗口、重新验证触发、用户可见过期条件和操作时的最终确认。旧快照可供浏览，不等于具有当前交易资格。
4. 读取失败需要区分“没有数据”“尚未加载”“用户无权访问”“读取失败”“上游部分数据缺失”；这些状态对用户的决策影响不同。
5. **验收**：不同用户、不同查询条件、分页变动与权限收紧后，查询及缓存无交叉污染，重要业务差异不被丢失。

### WEB-003 核验合同

- **WEB-003-P · 输入/动作与合格判据：** A/B租户同ID、分页中授权收紧→查询键隔离且缺失/无权不同。
- **WEB-003-F · 直接失败变异：** 把超时缓存为空或拼不同快照成完整集→失败。
- **WEB-003-N · 合法邻例：** 授权相同的公开共享查询可共用缓存。

## 四、HTTP 请求生命周期与响应归类
1. 每项远端调用记录有意义的请求身份、目标、方法、预期响应结构、认证作用域、超时条件和允许副作用。由 Fetch/XHR/WebSocket 等具体接口负责的网络机制以对应官方标准为准。
2. **Fetch 收到 4xx 或 5xx HTTP 响应通常会正常履行 Promise**，不自动抛出“网络错误”。调用方必须判断 HTTP 状态、协议正文与业务处理结果；不能只靠 catch 分支判断操作是否成功。
3. 明确处理真正的网络不可达、主动取消、超时、HTTP 错误、成功状态但响应格式不符、有效空响应、业务拒绝和下游处理仍进行中等不同结果。
4. 2xx 响应不自动代表支付、外部通知或异步任务最终完成。对 202 Accepted 以及后续业务状态变化，需要按真实 API 的跟踪契约查询结果。
5. 对响应体区分 JSON、文本、文件、流和无正文的成功响应；不能默认所有结果均可调用 JSON 解析。
6. **验收**：覆盖真实网络故障、HTTP 拒绝、解析错误、空正文、业务条件拒绝、未知后续结果和异步处理，映射到正确的客户端状态和恢复动作。

### WEB-004 核验合同

- **WEB-004-P · 输入/动作与合格判据：** 返回500、204、202、坏JSON和断网→HTTP/解码/业务阶段各归类。
- **WEB-004-F · 直接失败变异：** 仅catch判断500或对204强行json→失败。
- **WEB-004-N · 合法邻例：** 合法非JSON下载不强制转JSON。

## 五、取消、超时与资源生命周期
1. 用户离开、组件卸载、查询条件变化或新导航开始时，能够取消不再需要的请求、订阅、读取器与计时；AbortController 等实现按目标运行环境规范使用。
2. **取消客户端请求不等于撤回已到达服务器的副作用**。被中止的保存、支付、通知或删除必须通过对应权威系统确认实际结果，不能展示“已取消交易”或盲目重发。
3. 网络超时不总能区分请求未送达、服务器已提交和响应丢失，需将结果未知作为独立状态，结合业务唯一标识、安全重试和结果查询处理。
4. 流式响应取消应释放不再需要的流消费资源；已触发的有权后台工作是否继续，需要由原业务契约决定。
5. **验收**：快速离开页面、超时、中断后恢复、重复提交、页面隐藏及取消流读取，不出现悬挂加载、重复副作用或过期响应覆盖当前视图。

### WEB-005 核验合同

**必要机制补充：** 逻辑意图ID在安全重试间保持不变，每次发送另分配尝试ID；事务ID、事件ID、投递ID和Trace ID不得代替它。权威查询暂未发现记录、读副本落后、日志缺失、客户端超时均不证明原尝试不会随后提交。只有目标端对同意图实行覆盖所有在途/迟到尝试的原子唯一性，或有已安装的栅栏/终止与线性化屏障证明原尝试不再可生效，才可依合同重发；否则保持结果未知并继续有权核对，不新建意图绕过去重。有限去重保留窗须覆盖目标最后可能接受该意图的时刻、重放和恢复窗口；不能只比较本地派发时间。窗外仍可迟到时使用永久领域唯一性、目标拒旧期限/世代或有权人工核对。

- **WEB-005-P · 输入/动作与合格判据：** 在发送前/提交后Abort、取消流→释放本地资源且业务未知可回读。
- **WEB-005-F · 直接失败变异：** 显示已撤销交易或超时新建意图重发→失败。
- **WEB-005-N · 合法邻例：** 独立持久后台任务可按合同继续。

## 六、竞态、顺序与版本冲突
1. 对搜索建议、异步筛选、快速切换用户记录、多次保存及后台刷新，使用请求序号、资源身份、版本前提或适用的取消机制解决迟到响应，不假设请求总按发出顺序完成。
2. 取消旧请求可减少浪费，但若旧请求已完成或者服务端已处理，不足以单独保证一致性；提交结果必须有版本／资源前提核查。
3. 多标签、多个浏览器或多 Agent 写同一业务资源时，需要对应服务端的条件更新、乐观并发版本、事务或冲突合并规则；前端本地状态锁只能限制当前 UI 的重复操作。
4. 使用 ETag、If-Match、412 等 HTTP 机制必须遵守真实接口与 RFC 语义，不能假设所有服务端支持条件请求。
5. **验收**：设计 A→B→C 快速变化、同对象并发保存、标签交叉修改、版本过期及响应乱序的场景，验证不会把合法新状态覆盖为旧状态。

### WEB-006 核验合同

**必要机制补充：** 每次异步落地同时核对账号/租户世代、对象身份、查询/导航序号与必要数据版本；取消请求只是节约资源，不替代落地守卫。退出/换账号先推进世代并停止旧可见性，迟到Fetch、Worker、刷新令牌、IndexedDB读取、推送与多标签回调不得重新填入新账号缓存或队列。有权保留的旧账号草稿可隔离封存，不自动提交给新账号；对已经交付给外部主体的历史字节不宣称能通过登出物理撤回。

- **WEB-006-P · 输入/动作与合格判据：** 查询A/B/C反序返回并双标签保存→世代/对象/版本守卫落地。
- **WEB-006-F · 直接失败变异：** 只Abort便接受已排队旧回调或仅内存比较版本→失败。
- **WEB-006-N · 合法邻例：** 同世代不同对象并行无需互斥。

## 七、表单草稿与受控、非受控输入
1. 草稿字段有明确的初值、当前输入、修改标记、有效性、服务端原始值及提交快照。是否采用受控或原生非受控模式由实际复杂度与框架能力决定，不能强制全应用使用单一方案。
2. 服务端异步返回初始值时，不得无意覆写用户已经输入的草稿。编辑多步骤或复用同一表单时，区分切换对象、保留未保存内容与主动重置。
3. 原生表单的 name、disabled、readonly、required、FormData、submitter、自动填充、IME 合成输入等机制直接按 WHATWG HTML；DOM 事件与焦点按相邻规范。
4. 一次提交使用稳定快照而非在发送期间继续读取不断变化的输入值；服务端返回字段规范化或默认值时，按项目规则决定是否替换草稿、提醒用户或保留继续编辑状态。
5. **验收**：异步加载、连续输入、中文输入法、浏览器自动填充、字段切换、表单重挂载、离开页面与恢复时，不丢失合法草稿、不错发字段。

### WEB-007 核验合同

- **WEB-007-P · 输入/动作与合格判据：** 异步初值晚到时IME输入并提交快照→草稿不被覆盖且字段准确。
- **WEB-007-F · 直接失败变异：** 请求发送中继续读取不断变化字段→失败。
- **WEB-007-N · 合法邻例：** 原生非受控表单是合法实现。

## 八、客户端校验、服务端校验与错误定位
1. 客户端即时提示主要改善用户体验；服务端或权威接口独立执行与权利、价格、权限、唯一性、业务约束相关的最终校验，浏览器验证不能替代服务端。
2. 区分字段格式、跨字段规则、尚待服务器核实、业务冲突及没有权限。异步校验结果必须与当前字段值和请求身份对应；过期结果不可把当前有效输入判成错误。
3. 错误反馈明确到可修改的具体字段、字段组合或整体操作，使用对用户有意义的真实原因和下一步动作，保留对应业务语义；不能把数据库字段或内部枚举直接当作文案。
4. 对服务端校验错误，客户端按被批准的协议映射到表单，不允许静默忽略服务端新增的重要条件。RFC 9457 只在 API 实际采用其格式时引用，不强制全部服务切换。
5. **验收**：空值、边界、条件依赖、远端冲突、字段错误顺序、无效数据与网络异常具有正确定位和可修正路径，键盘及辅助技术可获取错误信息。

### WEB-008 核验合同

- **WEB-008-P · 输入/动作与合格判据：** 字段异步校验反序、服务端跨字段冲突→仅当前值被标错且错误可定位。
- **WEB-008-F · 直接失败变异：** 过期校验覆盖新合法值或忽略新增条件→失败。
- **WEB-008-N · 合法邻例：** API未用Problem Details可保留合法错误格式。

## 九、提交状态、幂等与不可逆操作
1. 提交过程至少区分“本地草稿”“正在发送”“服务端已接受”“业务处理完成”“部分完成”“结果未知”“明确失败”；不要求每项业务都有全部状态，但不得省略影响真实决策的阶段。
2. 对重复点击、浏览器刷新、超时后重试，结合实际后端请求标识、幂等键、事务或业务唯一约束做跨请求保护。单纯禁用按钮不能保证交易只发生一次。
3. 提交成功后应从权威结果更新页面、相关查询和缓存；若后续外部交付尚未完成，不应提前展示“已送达”“已付款”或类似终态。
4. 删除、退款、账户权限更改等不可逆或高影响操作的确认、取消、恢复与结果展示必须来自获批准的业务规则及实际服务端权力校验。
5. **验收**：多次并行提交、超时后结果查询、旧标签重发与服务器部分处理，真实副作用与可见结果一致且可审计。

### WEB-009 核验合同

- **WEB-009-P · 输入/动作与合格判据：** 并发同意图、重载、受理后断线→服务端唯一结果和未知查询一致。
- **WEB-009-F · 直接失败变异：** 禁按钮当唯一保障或202显示已交付→失败。
- **WEB-009-N · 合法邻例：** 只读操作不强制业务写账本。

## 十、乐观更新、撤销与补偿
1. 只对适合立即给出临时反馈的动作采用乐观更新，并标记其未经权威确认的性质。对于支付完成、权限授予、外部发送等重要事实，不能使用乐观提示伪装已经生效。
2. 发生冲突或失败时，回退必须只撤销与该次操作对应的临时补丁；有其他写入已经成功的情况下，不得用过期整体快照覆盖最新权威状态。
3. 乐观列表新增、排序、计数、分页与详情视图之间需要一致身份和临时实体映射；服务器确认时替换临时 ID，不产生重复记录。
4. 用户撤销本地修改与服务器完成真实补偿是不同动作，不能因为 UI 消失就认为订单、资金或通知已撤回。
5. **验收**：两个乐观操作交错、前一个失败后一个成功、服务端返回不同规范化数据、离线恢复等情况下，最终状态和权利事实不丢失。

### WEB-010 核验合同

- **WEB-010-P · 输入/动作与合格判据：** 乐观操作甲失败乙成功并交错确认→仅撤甲补丁、临时ID映射唯一。
- **WEB-010-F · 直接失败变异：** 整旧快照回滚覆盖乙成功→失败。
- **WEB-010-N · 合法邻例：** 服务器补偿与本地undo明确不同。

## 十一、远端查询缓存、失效与重新验证
1. 缓存的有效性由对象身份、参数、租户、授权身份、语言、地区、接口版本与业务新鲜度条件共同决定。缓存机制选自浏览器 HTTP、数据查询库或本地持久化时，应明确分别由谁负责。
2. mutation 成功、身份变化、权限收紧、对象删除及重要外部事件后，明确哪些查询需要失效、更新或重新验证，不能仅靠时间 TTL 等待用户看到新状态。
3. 使用 HTTP 缓存标头、ETag、条件请求或 stale 规则时遵从 RFC 9111 和目标接口行为；前端 Query Cache 的 staleTime 不等于服务器缓存的 max-age。
4. 需要 stale-while-revalidate 类体验时，明确用户可见的旧数据、新数据切换与可执行动作的新鲜度限制，不将旧库存、余额、权益或权限自动用于不可逆操作。
5. **验收**：重复导航、重新聚焦、用户切换、权限撤销、不同查询条件和版本升级后，缓存刷新符合合同且不会泄露其他身份的数据。

### WEB-011 核验合同

- **WEB-011-P · 输入/动作与合格判据：** mutation/撤权/切语言再查→相关层失效且旧快照不用于资格判断。
- **WEB-011-F · 直接失败变异：** Query staleTime冒HTTP max-age或只TTL等撤权→失败。
- **WEB-011-N · 合法邻例：** 允许陈旧的公开展示可带版本继续读。

## 十二、URL 状态、搜索参数与可分享条件
1. 适合分享、收藏和刷新恢复的查询条件可保存在 URL；仅本地的临时草稿、未批准交易、秘密和大型敏感数据不得仅为了便利而放入 URL。
2. 搜索词、分页、过滤、排序与筛选集合的编码、重复键和默认规则应使用 WHATWG URL 的实际解析语义及项目路由契约。
3. URL 发生变化时，相关数据请求和页面状态应与之同步；导航中旧响应不得覆盖新查询结果。刷新与深链访问应能恢复项目声明支持的条件。
4. 用户或权限切换时，合法 URL 也需由服务端鉴权，不能凭“查询参数正确”推断数据可读。
5. **验收**：复制链接、带多个筛选值的 URL、空查询、分页过期与跨身份访问，筛选和真实结果保持一致。

### WEB-012 核验合同

- **WEB-012-P · 输入/动作与合格判据：** 重复查询键/Unicode/空参数URL刷新返回→解析和资源身份一致。
- **WEB-012-F · 直接失败变异：** 把秘密写URL或旧回包覆盖新URL→失败。
- **WEB-012-N · 合法邻例：** 不可分享的本地草稿无需放URL。

## 十三、分页、增量数据与列表一致性
1. 根据数据集变动频率、稳定排序能力和后端契约选择 offset、cursor、时间窗口或增量同步；不能默认客户端序号即为稳定的业务身份。
2. 处理加载更多、滚动追加、重复项、删除、迟到页、筛选变化及排序时，建立明确的身份和版本去重机制，避免漏页、重复、错序或丢失重要差异。
3. 列表数量与总量、查询范围和当前页的关系必须可追溯；不以当前已加载部分直接冒充完整数据集统计。
4. 批量操作应区分全部成功、部分成功与各项失败结果，并保留完成任务必须的详细条件、数量和恢复动作。
5. **验收**：边加载边修改、分页途中筛选、重复事件、跨页相同记录、权限变化和空末页均得到稳定且可操作的结果。

### WEB-013 核验合同

- **WEB-013-P · 输入/动作与合格判据：** 边翻页边增删/重复事件→稳定身份、范围与部分结果明细正确。
- **WEB-013-F · 直接失败变异：** 已加载条数冒全量或批次失败全量重发→失败。
- **WEB-013-N · 合法邻例：** 后端只承诺有限窗口不虚构全局快照。

## 十四、客户端持久化、配额和数据生命周期
1. 根据实际用途选择内存、sessionStorage、localStorage、IndexedDB 或其他可用浏览器存储；不要把它们默认为永久可靠的多设备数据库，也不能因此自动扩大用户数据用途。
2. 缓存、草稿与数据快照需要有来源版本、身份作用域、过期条件和显式的清理／恢复行为。浏览器存储配额、清除站点数据、隐私模式及用户拒绝持久化都可能使数据不可用。
3. 大型结构化数据需要迁移与 schema 兼容，按采用的 IndexedDB 版本和浏览器事务能力实现；W3C IndexedDB 3.0 当前为 Working Draft，不以此声称所有平台完全符合。
4. 对本地存储中的私有数据，应确认实际敏感性、设备共享风险、跨租户切换、登出和数据保留约束。浏览器脚本可读的存储不应成为服务端机密或无权令牌的默认保管处。
5. 完整离线产品与 Service Worker 的缓存一致性、后台同步和安装更新交由后续 L4 离线／PWA 专项；本节规定草稿和状态持久化的基础约束。
6. **验收**：重载、关闭标签、存储配额不足、浏览器清理、版本升级、切换账号及撤销权限，按项目声明的保留和恢复策略运行。

### WEB-014 核验合同

**必要机制补充：** IndexedDB单个request success不等于整个事务complete，更不等于设备掉电后绝不丢失；按实际事务完成事件、durability选项及平台保证报告保存等级。升级时处理versionchange/blocked，通知旧连接在保护草稿后关闭；迁移失败不发布半升级数据。

- **WEB-014-P · 输入/动作与合格判据：** 配额错误、versionchange阻塞、清站点数据→迁移/恢复边界准确。
- **WEB-014-F · 直接失败变异：** 单个IDB request success即宣称整个事务持久完成→失败。
- **WEB-014-N · 合法邻例：** best-effort缓存可丢但未上传草稿不能冒永久保证。

## 十五、实时事件与后台数据变化（按需）
1. 仅当业务确实需要推送更新、实时监测或协作时启用 SSE、WebSocket、轮询或其他实时机制；各传输协议的时序、心跳和恢复由后续网络专项规定。
2. 在状态消费侧必须识别事件资源身份、版本、去重与过期条件；收到事件不意味着它已经通过业务授权或可以无条件覆写当前草稿。
3. 断线、事件缺口与多页面同时消费时，根据后端支持的重放标识、增量查询或完整重新验证恢复，不能默认每个流都具有完全一次性处理语义。
4. **验收**：断连与重连、乱序事件、用户切换和未提交表单并存时，实时更新不覆盖草稿、未泄露权限及保持真实业务状态。

### WEB-015 核验合同

- **WEB-015-P · 输入/动作与合格判据：** 实时事件乱序/缺口/切账号且草稿未提交→按版本回读不覆盖输入。
- **WEB-015-F · 直接失败变异：** 每次重连当完整补齐或默认exactly-once→失败。
- **WEB-015-N · 合法邻例：** 无实时需求可用受控普通查询。

## 十六、错误协议与用户反馈
1. 将网络失败、超时、取消、HTTP 401/403、404、409/412、429、5xx、响应解码失败、业务验证失败与部分成功映射到确实不同的恢复条件。具体 HTTP 语义与应用响应类型由实际 API 合同决定。
2. 对服务器给出的错误字段、类型、恢复条件，先经过协议解析和受众转换，再以必要的业务语言及动作呈现；不要直接显示堆栈、SQL 信息、内部记录标识或供应商工程流水。
3. 若 API 采用 RFC 9457，按已声明的 type、status、detail 和扩展字段映射，避免依赖可翻译的 title 文案作为稳定机器错误代码。未采用的 API 不被强制套用该格式。
4. 对 Retry-After 或其他重试提示，应核对该操作是否可以安全重试、当前授权和预算以及服务端实际结果；不能将所有 429 或 5xx 无限重试。
5. **验收**：错误原因对用户的下一步操作有实际影响时，界面提供准确条件与恢复路径；关键未知结果可查询并不会虚报业务成功。

### WEB-016 核验合同

- **WEB-016-P · 输入/动作与合格判据：** 401/403/409/412/429、Retry-After和未知结果→不同恢复、预算有界。
- **WEB-016-F · 直接失败变异：** 可翻译title当稳定代码或5xx无限重试→失败。
- **WEB-016-N · 合法邻例：** 明确安全的读取可有限退避。

## 十七、文件和流式数据的前端消费
1. 附件上传、下载、流式生成和批量导入应定义类型、大小、进度、编码、取消、业务结果标识和分段失败后的可恢复性；浏览器进度与服务端完成是不同事实。
2. 对分块响应与 Streams，区分响应头接收、流中途错误、解析完成、业务对象全部收到和实际处理完成。部分字节不自动意味着文件或报表可使用。
3. 大量数据不得毫无界限地聚集在主线程内存，需按实际输入规模和支持环境采用分块、背压、Worker 或服务端转换等合适方案。
4. 不可信文件内容与 MIME、文件名和业务元数据需按真实授权和数据安全策略使用；前端校验不代替服务器侧扫描和权限控制。
5. **验收**：网络中断、取消、重复分块、格式损坏、内存限制和局部成功情况下，用户能获取准确任务状态，已完成的外部副作用可复核。

### WEB-017 核验合同

- **WEB-017-P · 输入/动作与合格判据：** 半截流/重复块/取消上传→字节校验与服务端任务终态分别核对。
- **WEB-017-F · 直接失败变异：** 进度100%即报导入完成或主线程无界聚合→失败。
- **WEB-017-N · 合法邻例：** 合法空文件按接口约定接受。

## 十八、性能、渲染和状态传播成本
1. 将用户实际输入响应、请求次数、缓存命中、状态派生成本、渲染规模、内存保留和主线程阻塞对应到业务路径；不能只按 store 数量或组件渲染次数作“性能达标”判断。
2. 需要性能优化时，基于真实 Profile 和输入规模处理高频输入、自动搜索、复杂筛选、大型列表和多重订阅。去抖、节流及取消不能吞掉最终值或必要提交。
3. 状态粒度、选择器、memoization、结构共享等框架实践由 L5 定义，本节只要求实际更新有界、数据正确、没有无意义的跨模块重绘。
4. **验收**：在项目目标设备与网络条件下，对真实输入和反馈测量时间、存储及资源使用，确保优化不损害业务差异和可访问性。

### WEB-018 核验合同

- **WEB-018-P · 输入/动作与合格判据：** 大列表/快速输入限速前后→最终值、主线程预算与可访问操作保留。
- **WEB-018-F · 直接失败变异：** 去抖吞掉最终提交或以删字段换速度→失败。
- **WEB-018-N · 合法邻例：** 无瓶颈的简单store不强制memo化。

## 十九、状态生命周期与交付验证矩阵
| 静态审查场景 | 技术输入／故障 | 完成验收需要的实际结果 |
| --- | --- | --- |
| 用户／租户快速切换 | 同一资源不同身份、旧缓存 | 不跨身份展示或重用私有数据 |
| 同一输入快速搜索 | 连续查询、旧响应迟到 | 最后有效条件与显示结果一致 |
| 多次提交与断线重试 | 请求已可能送达但响应丢失 | 先查权威结果，再依真实幂等规则恢复，不重复副作用 |
| HTTP 失败正常响应 | fetch 返回 4xx/5xx Response | 明确校验状态并映射真实失败，不当作网络抛异常 |
| 异步初值覆盖表单 | 用户已输入、服务器迟到返回 | 保留有效草稿，按授权规则合并 |
| 多语言输入法与自动填充 | IME composition、浏览器 autofill | 字段与服务器实际提交值一致 |
| 服务端校验冲突 | 字段无效、跨字段条件、权限拒绝 | 错误定位、纠正动作及字段保真 |
| 两个乐观写入交错 | 前者失败、后者成功 | 只回退失败补丁，不覆盖成功权威状态 |
| 对象条件更新失败 | ETag 过期、并发冲突 | 显示真实冲突及重新加载／合并选择，不静默覆盖 |
| 缓存与服务端不同步 | mutation 成功后旧列表 | 受影响缓存失效或正确同步 |
| 分页中记录被更新 | 滚动加载、删除、重复页 | 稳定身份与排序，无重复／遗漏关键数据 |
| URL 深链和筛选条件 | 查询参数、刷新及返回 | 筛选与数据结果一致，私有状态未写入 URL |
| 浏览器持久化失效 | 存储配额、清理、版本迁移 | 按真实草稿保存策略恢复或准确说明状态 |
| 实时事件乱序 | 重复通知、断线重连 | 权威版本与当前草稿不被乱序事件破坏 |
| 错误与重试边界 | 401/403/409/412/429、错误格式变化 | 权限、冲突、可重试性与恢复对应真实接口 |
| 部分文件或流响应 | 取消、半截传输、格式损坏 | 不把部分字节标记为完整业务产物 |
## 二十、项目接入与生效界限
项目 L6 应选择实际表单复杂度、网络协议、缓存新鲜度、用户身份、并发与数据恢复规则、实际支持浏览器以及需要的可访问性和性能门禁。应在正确版本的真实前后端或明确授权的测试环境验证重要数据读写，不将 Mock 测试冒称真实事务交付。
在本规范中，原生表单机制按相邻 HTML／DOM 专项；导航和 Hydration 期间的数据生命周期按渲染／路由专项；服务器事务、接口数据所有权、安全授权、支付账本和网络传输协议分别由其他 L4 技术专项负责。React、Vue、Svelte、Redux、TanStack Query、表单库或其他具体框架的使用约束由后续 L5 规定，不将软件包的默认行为升格为全组织标准。
20 个技术章节、16 项静态场景与行业标准来源核验属于规范文本审查，不代表任何实际浏览器、请求、存储或业务交付已经测试达标；项目实施证据仍以权威工程系统及 L6 验收为准。
