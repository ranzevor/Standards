# L4 渲染、路由与 Hydration 技术规范

**文档ID：** STD-L4-WEB-009　**版本：** 0.1.0　**状态：** adopted　**生效日期：** 2026-10-30

## 技术范围、权威来源与继承关系

本专题面向 Web 应用的 CSR、SSR、SSG、流式 HTML、客户端接管（Hydration）、路由和会话历史、页面切换、缓存版本及发布恢复。静态站点、内部门户、公开内容站、复杂交互应用可按实际用途选择对应条款；并不要求所有 Web 项目都采用 SSR、JavaScript Router、Streaming 或 Hydration。
有效上层：[L4 Web 领域通用基线](002-Web-领域通用基线--v0.1.0.md)（Web 领域通用基线）、[L4 浏览器文档、DOM 与交互组件技术规范](007-浏览器文档、DOM-与交互组件技术规范--v0.1.0.md)（HTML／DOM 与交互）、[L4 CSS 布局、视觉系统与响应式技术规范](001-CSS-布局、视觉系统与响应式技术规范--v0.1.0.md)（CSS 与呈现）、[L3 通用工程规范](../../L3/001-通用工程规范--v0.1.0.md)（L3 通用工程）、[L2 人类与 Agent 团队组织协作规范](../../L2/001-人类与-Agent-团队组织协作规范--v0.1.0.md)（L2）及 [L1 全局治理补充规范](../../L1/001-全局治理补充规范--v0.1.0.md)（L1）。
行业现有规范与实现文档直接引用，不能把框架示例误认成所有技术栈的强制标准：
- [WHATWG HTML — Navigation and session history](https://html.spec.whatwg.org/multipage/browsing-the-web.html) 与 [Navigation and history APIs](https://html.spec.whatwg.org/multipage/nav-history-apis.html)：浏览器导航、文档生命周期、History 与 Navigation API；均属于持续更新的 HTML Living Standard。
- [WHATWG URL Standard](https://url.spec.whatwg.org/)：URL 解析、序列化与相对地址处理。
- [WHATWG Streams Standard](https://streams.spec.whatwg.org/)：数据流、背压、取消和错误的基础流模型；SSR 如何产生 HTML 由项目所用运行时／框架确定。
- [IETF RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html) 与 [RFC 9111 HTTP Caching](https://www.rfc-editor.org/rfc/rfc9111.html)：HTTP 状态、缓存和重新验证的协议基础。
- [MDN Navigation API](https://developer.mozilla.org/en-US/docs/Web/API/Navigation_API)、[History API](https://developer.mozilla.org/en-US/docs/Web/API/History_API) 与 [pageshow](https://developer.mozilla.org/en-US/docs/Web/API/Window/pageshow_event)：实施与兼容资料。Navigation API 属于 Baseline 2026 的较新能力，旧浏览器需要核对支持或采用其他导航实现。
- [React hydrateRoot](https://react.dev/reference/react-dom/client/hydrateRoot) 与 [React renderToPipeableStream](https://react.dev/reference/react-dom/server/renderToPipeableStream)：特定框架的参考实现，不代表 Vue、Svelte 或原生 Web 的必用接口。
- [W3C WCAG 2.2](https://www.w3.org/TR/WCAG22/) 与 [Web Platform Tests](https://wpt.fyi/)：按项目范围引用的可访问性与平台兼容资料。

## 核验口径与消费接口

维护者负责落实本文机制，领域/API/存储提供者负责其权威保证，验收者从实际受支持入口观察结果。输入固定源码/构建、配置、数据/协议版本、角色/租户、目标平台、故障时序和预算；权威观察对象为**有效导航世代对应的URL/DOM/身份、框架接管状态和服务端结果**。真实执行入口为**地址栏导航、Back/Forward、DevTools限速/断流、浏览器控制台与框架错误钩子**。逐章 P/F/N 分别为正常输入及判据、破坏该机制的直接失败变异、应继续成立的合法邻例；本章原有每项规则、原有验收与新增合同共同约束，不用单一通用案例替代具体子项。每个子项须在案例输入中保留其适用条件，并以自身原文规定的输出/不变量判定；复合章应拆记录各个观察量，不能以一个成功掩盖其他失败。

证据产物包括真实命令/用户动作、原始响应或事件、权威状态前后值、版本、时序、失败及恢复；尚无对应真实运行证据的场景状态为 `not-run`，标准库示例仅证明列明的局部边界。具体输入与命令见[执行入口](../../../examples/web-backend/RUNBOOK.md)，条款索引见[规范条款登记](../../../registry/requirements.json)，来源的有限支持命题见[逐命题来源映射](../../../sources/web-backend/claims.json)。

本文的跨组件约束与正例、失败反例、合法邻例由本规范综合定义；外部来源支持的机制及适用边界见来源表。项目架构、预算和业务规则由实际需求确定。L5 实现应映射到所选框架、SDK 或引擎；L6 按具体版本的提供者保证与受支持矩阵验收项目能力。

## 一、渲染模式及实际选型
1. 根据公开可发现性、首屏有用内容、交互强度、数据新鲜度、目标设备、边缘／服务器能力及运行预算，确定 CSR、SSR、SSG、混合渲染或 Streaming 的实际用途与边界；选择不等于承诺全项目使用同一机制。
2. 静态页面可以完全无 Hydration；动态且高度私有的应用可能采用纯 CSR；需要首屏可读或公开内容的页面可考虑 SSR／SSG。具体框架推荐不是本规范的默认业务选择。
3. 为每类路由记录渲染责任、数据权威、是否缓存、交互激活方式、目标环境及降级行为。不能因使用了 SSR 就默认首屏可交互，也不能因 CSR 加载成功就认为页面的核心数据已完成。
4. 对边缘渲染、按需生成或增量重验证等框架特有策略，只规定可观察的数据新鲜度与运行约束，不在 L4 预先指定某种框架 API。
5. **验收**：抽取代表性路由核对真实响应内容、数据来源、实际可交互状态、运行负载及目标用户路径；证明选择符合需求，而非仅能启动框架 Demo。

### WEB-001 核验合同

- **WEB-001-P · 输入/动作与合格判据：** 按路由分别直读SSR/CSR/静态输出→责任、数据新鲜度、激活边界可查。
- **WEB-001-F · 直接失败变异：** HTML有按钮即称已可交互→失败。
- **WEB-001-N · 合法邻例：** 纯静态无交互页无需Hydration。

## 二、URL、路由与资源身份
1. 路由约定必须明确地址路径、动态片段、查询参数、fragment 和资源身份。共享 URL 应能表达授权范围内必要的可分享状态；不可在 URL 中泄漏密码、令牌或应保密的用户资料。
2. 参数解析、编码、Unicode、大小写、尾斜杠、路径前缀、base path、相对 URL 与 canonical 形式应遵循实际 URL 标准及部署策略；不能靠字符串切割或不受控重定向绕过权限。
3. 路由优先级、动态路由冲突、历史别名、永久／临时跳转和找不到的资源都需要有确定行为。路由匹配不自动赋予资源读取权。
4. 站点部署在子路径、CDN、代理或多个域名下时，前端生成的链接和服务端入口必须一致；不可仅验证框架内部跳转正常。
5. **验收**：从复制的真实地址独立打开、刷新、跨标签访问，资源、身份、参数、HTTP 结果和最终内容一致。

### WEB-002 核验合同

- **WEB-002-P · 输入/动作与合格判据：** 编码/Unicode/base path/别名深链独立打开→匹配与授权一致。
- **WEB-002-F · 直接失败变异：** 字符串拼接开放重定向或子路径资源404→失败。
- **WEB-002-N · 合法邻例：** 合法外链由原生导航处理。

## 三、浏览器导航与会话历史
1. 清楚区分同一 Document 内的页面状态切换和跨 Document 导航，决定何时由路由器拦截链接、何时遵守浏览器原生导航、下载、外部站点或特殊目标窗口行为。
2. History API 的 pushState／replaceState 更新历史状态时，不会自动触发 popstate；实现不能错误等待 popstate 才刷新当前视图。浏览器返回／前进、fragment 跳转与滚动恢复需单独验证。
3. 使用较新的 Navigation API 时核对目标浏览器支持、可拦截的导航类型、状态、取消和导航生命周期；对旧版本保留准确的 History API 或原生导航方案。
4. 路由跳转不可破坏打开新标签、复制链接、浏览器返回、跨域跳转、锚点、下载和用户中断导航等常规行为。
5. **验收**：直接跳转、push、replace、back、forward、reload、跨源及同源导航分别验证真实地址、焦点、滚动与内容一致性。

### WEB-003 核验合同

- **WEB-003-P · 输入/动作与合格判据：** push/replace/back/forward/hash/reload→历史、URL和视图同步。
- **WEB-003-F · 直接失败变异：** 等待pushState自动popstate或拦截下载/新标签→失败。
- **WEB-003-N · 合法邻例：** 无下一项forward可合法无操作。

## 四、深链、HTTP 状态与交付入口
1. 独立访问嵌套路由时，服务器／静态托管必须返回可被客户端正确接管的内容；不能仅依靠 SPA 内部导航绕开服务端的 404 或错误重写。
2. 不存在的资源、无权限资源、需身份认证、永久／临时迁移及服务故障必须按真实业务和 HTTP 语义表达；不能为了 SPA 路由回退让所有错误 URL 在外部渠道伪装成成功内容。
3. 需区分站点公开的资源不存在与该用户无权知晓其存在，具体对外状态由已批准产品和安全约定决定；不能单纯以显示错误页面表示服务端响应已正确。
4. 资源的 HTML、数据加载端点、静态文件和框架内导航需要各自可追溯状态及重定向行为。机器人索引与分享预览需要的状态由实际公开页面要求决定。
5. **验收**：从地址栏发起 GET、刷新和客户端跳转都能获得一致的授权后内容、正确状态或按契约说明的行为差异。

### WEB-004 核验合同

- **WEB-004-P · 输入/动作与合格判据：** 地址栏GET不存在/无权路由→HTTP与内容按合同一致。
- **WEB-004-F · 直接失败变异：** SPA fallback对所有URL虚报200成功→失败。
- **WEB-004-N · 合法邻例：** 资源存在性敏感可按安全合同统一404。

## 五、服务器渲染的数据快照和作用域
1. 为 SSR／SSG 生成的内容说明何时读取数据、哪个账号／租户可读、缓存作用域、所用语言／地区、版本及失效条件；不能在服务端数据和客户端再请求之间无提示更换业务含义。
2. 请求级上下文、会话、授权及本地化信息应保持请求隔离，避免进程级缓存或可变单例将甲用户的数据写入乙用户首屏。
3. 服务端初始结果与客户端将要使用的初始状态应来自可对照的数据快照或有明确定义的变化策略，避免页面刚出现便错误闪烁、覆盖用户操作或暴露过期权限。
4. 构建时生成页面的部署版本与内容新鲜度应可追踪；对必须实时确认的余额、库存、权限、支付及其他高风险结果，不能把静态 HTML 当成最终权威。
5. **验收**：分别以不同租户、登录状态、语言、时间和数据版本访问 SSR 页面；核对内容与授权、缓存和客户端初始状态的一致性。

### WEB-005 核验合同

- **WEB-005-P · 输入/动作与合格判据：** 并发A/B租户SSR及客户端再验证→请求隔离、快照含义一致。
- **WEB-005-F · 直接失败变异：** 进程单例混入A私有初值给B→失败。
- **WEB-005-N · 合法邻例：** 公开SSG可缓存但不承担实时余额权威。

## 六、HTML 响应、序列化及安全边界
1. 预渲染 HTML、嵌入初始 JSON、内联脚本和资源提示必须保持上下文正确的转义、权限及内容边界。普通数据不应由于字符串拼接而成为可执行脚本。
2. 服务端可访问的凭据、服务内部对象、请求头和调试信息不得序列化到客户端；记录哪些字段可进入浏览器、哪些字段只能通过独立授权接口读取。
3. 需要 Content-Security-Policy、Nonce、Trusted Types 等保护时由安全领域与项目威胁模型确定，SSR／Streaming 产物与脚本插入必须遵守实际政策。
4. 代理、压缩、CDN 缓存和字符编码的处理不得破坏文档结构、资源引用或序列化数据完整性。
5. **验收**：对不可信文本、特殊标记、不同编码、敏感数据和第三方资源进行实际 HTML 输出核查，确认浏览器解析结果与授权业务内容一致。

### WEB-006 核验合同

- **WEB-006-P · 输入/动作与合格判据：** 输出含尖括号/脚本边界/私有对象→解析安全且字段最小化。
- **WEB-006-F · 直接失败变异：** 序列化凭据或未转义结束script标记→失败。
- **WEB-006-N · 合法邻例：** 纯文本特殊字符仍完整显示。

## 七、Hydration 的初始内容一致性
1. 只有在服务端／构建端已生成可复用 HTML 并且客户端需要接管互动时才适用 Hydration；纯 CSR 和纯静态无交互页面不得为了统一术语假定也经历了 Hydration。
2. 服务端初始 HTML 与客户端首轮渲染之间需要满足所选框架的匹配契约。时间、时区、语言、随机数、自动生成 ID、feature flag、身份和不稳定排序等动态因素必须采用确定性输入或明确的二次更新机制。
3. 非法的 HTML 嵌套、缺失资源、不同环境变量和服务端／客户端差异化组件结构可能触发 Hydration 不一致；不得以吞掉日志、泛化抑制警告或重建整棵页面作为默认修复。
4. 故意延迟的客户端内容须有稳定的初始占位和真实更新策略，不丢失焦点、已经输入的文字和必要业务状态；框架级错误与具体回退实现由 L5 制定。
5. **验收**：慢 JS、慢网络、不同语言、登录差异、随机性、动态时间与错误 HTML 结构下，核对浏览器控制台、DOM 一致性、输入保持和实际用户交互。

### WEB-007 核验合同

**必要机制补充：** 框架接管失败须有可观察错误及可用的替代路径；回退重建前核对草稿/焦点与已发业务意图，不能用全页自动重载重复提交未知写入。React特定hydrateRoot约束不推及其他框架。

- **WEB-007-P · 输入/动作与合格判据：** 时区/随机ID/非法嵌套/慢脚本→首轮契约匹配或受控错误恢复。
- **WEB-007-F · 直接失败变异：** 全局抑警告掩盖结构错配并丢输入→失败。
- **WEB-007-N · 合法邻例：** 明确客户端二次更新可先用稳定占位。

## 八、交互激活与局部接管
1. 将“HTML 已显示”“资源已下载”“事件处理已接管”“用户完成操作”分开衡量，不因 SSR 输出出现按钮就宣称该按钮已可执行。
2. 局部或分阶段 Hydration、Islands 和可见区域优先激活属于可选架构，须记录交互延迟、事件保留、调度次序、激活失败及回退行为，不强制所有应用采用。
3. 对未完成接管时发生的点击、输入、键盘操作及表单提交，必须确认所选框架与组件是否支持保留或重新处理事件，不能假设所有框架都具备相同事件重放能力。
4. 重复初始化、路由切换、旧 JS 与新 HTML 共存或局部边界异常时，不能重复注册关键提交操作或使局部内容永久不可操作。
5. **验收**：在限速条件下先交互再完成 Hydration，核对用户输入、焦点、重复副作用、失败回退和状态可见性。

### WEB-008 核验合同

**必要机制补充：** 原生默认动作、框架事件排队/重放与失败重试要共享业务意图边界；不支持事件重放的框架不得假定会保留提前操作。

- **WEB-008-P · 输入/动作与合格判据：** 接管前点击/IME、随后初始化失败→动作不丢不双写且回退可用。
- **WEB-008-F · 直接失败变异：** 原生默认提交与框架事件重放重复执行→失败。
- **WEB-008-N · 合法邻例：** 框架不支持事件重放时可暂不可交互并明确提示。

## 九、Streaming 与服务端失败恢复
1. 流式响应只有在真实首屏可用、资源依赖或长尾数据可以分阶段到达时才启用；选择边界须包含首屏 Shell、后续片段、数据错误、客户端取消和资源预算。
2. 基础流读取与背压、取消和错误处理依 WHATWG Streams 或所在运行时的有效 API 定义；不得无界缓冲、无视中断导致资源持续占用。
3. **HTTP 响应头／状态一经实际发送就不能再修改**。发生 Shell 生成失败与 Shell 已发送后失败属于不同恢复场景：前者可设置正确 HTTP 错误状态并响应替代页面，后者需在既有响应中呈现正确的失败信息并保留可追踪服务器证据。
4. 按实际需求决定是否流式发送局部占位、资源提示和后续数据。包含敏感数据、非公开错误和 CSP 限制时，不能将方便的插入脚本作为自动豁免。
5. 网络中断或客户端导航取消时终止不再需要的计算、读取及资源，或明确仍需继续的有权后台任务；不能让已中止页面继续产生未批准的外部副作用。
6. **验收**：测试生成前失败、首段已发送后失败、长尾数据超时、传输中断、客户端取消以及代理缓冲场景，核对状态、可见回退、日志和资源释放。

### WEB-009 核验合同

- **WEB-009-P · 输入/动作与合格判据：** 分别在Shell前/后抛错并断流→状态/可见失败/资源清理正确。
- **WEB-009-F · 直接失败变异：** 头已发后宣称改500或无界缓冲→失败。
- **WEB-009-N · 合法邻例：** 已授权独立后台任务不必随连接取消。

## 十、客户端导航的竞争与异步生命周期
1. 导航开始应明确先后关系、路由匹配、数据加载、权限检查、可见加载状态与完成条件；新请求不能被旧请求迟到结果无意覆盖。
2. 多次快速切换路由、同一路由参数变化、取消或重定向时，结合导航标识、AbortSignal、版本条件或一致性机制取消过期工作并防止错误提交。
3. 预加载／预取只是可能发生的读取，不构成实际浏览或购买；不得因 hover、后台预取、预测模型访问而执行支付、删除、权限授予和其他副作用。
4. 路由过渡中的错误、权限失效与会话过期应展示真实可操作状态，不把空页面、无限 Loading、错误 URL 或静默回首页作为普遍回退。
5. **验收**：快速 A→B→C 导航、重复返回、参数变更、请求超时及用户中断后，URL、页面标题、数据权威、资源清理和提交副作用均符合最后有效动作。

### WEB-010 核验合同

**必要机制补充：** 每次异步落地同时核对账号/租户世代、对象身份、查询/导航序号与必要数据版本；取消请求只是节约资源，不替代落地守卫。退出/换账号先推进世代并停止旧可见性，迟到Fetch、Worker、刷新令牌、IndexedDB读取、推送与多标签回调不得重新填入新账号缓存或队列。有权保留的旧账号草稿可隔离封存，不自动提交给新账号；对已经交付给外部主体的历史字节不宣称能通过登出物理撤回。

- **WEB-010-P · 输入/动作与合格判据：** A/B/C导航反序返回及取消→仅当前导航世代提交视图。
- **WEB-010-F · 直接失败变异：** hover预取执行购买或旧回包改新标题→失败。
- **WEB-010-N · 合法邻例：** 独立只读预取可在预算内继续。

## 十一、bfcache 与文档恢复
1. 浏览器前进／后退缓存（bfcache）恢复可能跳过完整页面重载，不能将一次性初始化事件作为每次页面重新展示时必定执行的依据。
2. 使用 pageshow／pagehide 等文档生命周期事件区分新建页面与恢复页面，按照浏览器兼容和项目实际依赖检查 persisted 状态；避免依赖可能干扰 bfcache 的不必要 unload 行为。
3. 页面从缓存恢复时，已变化的身份、敏感权限、订单或账户状态必须按对应权威来源重新确认；恢复滚动与本地草稿不意味着可以直接重用旧权限。
4. 多标签、系统冻结／恢复和离线重连也可能使客户端缓存过期；无权限的资料不能因历史页面被浏览器恢复而被继续提交或外传。
5. **验收**：正常返回／前进、bfcache 恢复、系统冻结、登出后返回和长时间暂停后恢复分别验证实际状态与权限边界。

### WEB-011 核验合同

**必要机制补充：** 每次异步落地同时核对账号/租户世代、对象身份、查询/导航序号与必要数据版本；取消请求只是节约资源，不替代落地守卫。退出/换账号先推进世代并停止旧可见性，迟到Fetch、Worker、刷新令牌、IndexedDB读取、推送与多标签回调不得重新填入新账号缓存或队列。有权保留的旧账号草稿可隔离封存，不自动提交给新账号；对已经交付给外部主体的历史字节不宣称能通过登出物理撤回。

- **WEB-011-P · 输入/动作与合格判据：** pageshow persisted与普通重载、登出后返回→草稿恢复和当前权威重新验证。
- **WEB-011-F · 直接失败变异：** 初始化只跑一次导致旧权限复活→失败。
- **WEB-011-N · 合法邻例：** 不涉及私有数据的历史页可恢复滚动。

## 十二、导航中的表单、草稿与外部动作
1. 用户离开含未保存草稿的页面、提交中路由跳转、第三方身份回调或重放表单时，必须按已有业务约定决定内容保留、取消、再次提交或外部结果确认。
2. 客户端草稿、浏览器历史 state、URL 查询参数和服务端已提交结果是不同状态；不得把浏览器 history.state 当作客户订单、余额或真实持久化记录。
3. 有服务端副作用的表单在跳转、刷新和重试后需有业务唯一标识和实际外部状态检查；路由过渡完成不代表第三方处理完成。
4. **验收**：离开未提交表单、提交期间刷新、跨标签重复提交和身份回调后，数据未无授权丢失、重复处理或错误展示“成功”。

### WEB-012 核验合同

- **WEB-012-P · 输入/动作与合格判据：** 未存草稿离开、提交中刷新与回调重放→本地/远端状态分清。
- **WEB-012-F · 直接失败变异：** history.state当真实订单或导航完成即到账→失败。
- **WEB-012-N · 合法邻例：** 合法放弃本地草稿不冒远端撤单。

## 十三、HTTP 缓存、CDN 与个人化隔离
1. 为 HTML Shell、公开静态资产、服务器渲染结果和带用户权限的数据分别定义缓存策略。HTTP 缓存新鲜度、重新验证和 stale 规则以 RFC 9111 为准。
2. 公共缓存的 SSR HTML 不得携带账户、租户、订单、Cookie 衍生的个人数据；需要个性化时明确 private/no-store 等合适控制、缓存键和代理配置，不把框架默认缓存视为合规保证。
3. 由 Locale、设备差异、权限、动态查询或版本改变真实响应内容时，需要考虑相应的缓存变体及其真实效力；不得依赖前端显示纠错来掩盖 CDN 泄漏。
4. 指纹静态资源、入口 HTML、API、Service Worker 和客户端路由要形成跨版本契约，避免旧入口引用已删除资产、旧 JS 不兼容服务端或旧权限界面复活。
5. **验收**：两个账户与不同语言的连续访问、CDN 命中与回源、版本升级、旧标签页和撤销权限后返回，均无跨身份污染及关键资源缺失。

### WEB-013 核验合同

- **WEB-013-P · 输入/动作与合格判据：** 两身份CDN命中及旧HTML请求chunk→隔离和资源兼容。
- **WEB-013-F · 直接失败变异：** private数据被公共缓存或删旧hash资源→失败。
- **WEB-013-N · 合法邻例：** 公开指纹资源可长缓存。

## 十四、路由切换的焦点、滚动和可访问性
1. 客户端路由改变时，应按所选用户体验明确页面标题、主内容焦点、滚动位置、锚点跳转和辅助技术所需的内容变化通知；不是每次导航都自动移到页面顶部。
2. 异步数据延迟、页面骨架替换、路由错误边界和多次重定向不能使键盘焦点落在已卸载节点、隐藏元素或无法继续操作的位置。
3. 恢复历史记录时按业务与浏览器行为区分需要恢复的滚动、草稿和筛选状态，以及必须重新确认的权限和服务器结果。
4. **验收**：键盘、屏幕阅读器及目标浏览器的前进／后退、局部路由切换和失败返回路径能完整完成原任务。DOM 与 ARIA 的具体控件行为继续由相邻专项规定。

### WEB-014 核验合同

- **WEB-014-P · 输入/动作与合格判据：** 键盘/AT导航失败重定向后→有效标题、焦点、滚动与内容通知。
- **WEB-014-F · 直接失败变异：** focus指向卸载节点或每次导航强制页顶打断→失败。
- **WEB-014-N · 合法邻例：** 历史恢复可保持用户原滚动。

## 十五、公开内容与 SEO（按实际功能启用）
1. 只为真实对外公开、需要搜索发现或分享预览的路由启用相关验收；登录后台、私有研究原型无需因为 SSR 技术存在而增加 SEO 产品需求。
2. 公开内容的 HTTP 状态、标题、Canonical、元数据、语言版本、结构化信息及最终 HTML 必须与真实页面一致，不应仅在客户端运行完 JS 后才形成外部渠道需要的唯一版本。
3. 静态生成或缓存不得把无权限内容和会话状态写入公开 HTML、搜索索引、机器人预览和分享图片。
4. **验收**：使用实际线上响应或可信预发布环境核对直达请求、重定向、404、HTML 数据、索引控制和内容可见性。

### WEB-015 核验合同

- **WEB-015-P · 输入/动作与合格判据：** 匿名抓取公开与私密页面→元数据和状态真实且无私有泄漏。
- **WEB-015-F · 直接失败变异：** 私密初值进入分享预览→失败。
- **WEB-015-N · 合法邻例：** 登录研究后台不需SEO。

## 十六、加载性能、Hydration 成本与实际测量
1. 分别衡量服务器响应、首段 HTML、首次可见内容、可交互准备、主线程阻塞、Hydration 工作、完整任务操作和用户真实结果；某一指标改善不自动表示用户任务更快。
2. 依据实际 Trace 检查客户端 JS 体积、服务端数据瀑布、阻塞脚本、资源预加载、串行嵌套请求、重复渲染及长期挂起请求。流式发送和选择性 Hydration 的收益须通过测量证明。
3. 框架级资源优先级、边缘运行时、预取与增量构建优化须保留正确数据权限和缓存策略；不能为了漂亮的 LCP 或 TTFB 数值跳过核心用户路径。
4. **验收**：使用目标网络、设备、访问状态和已批准的性能预算，对加载／交互／导航分别记录版本、样本及结果；禁止用单次本地 Lighthouse 分数替代真实业务性能。

### WEB-016 核验合同

- **WEB-016-F · 直接失败变异：** 只看LCP而删权限校验或吞错误→失败。
- **WEB-016-N · 合法邻例：** 低样本可报告可复算实验指标。

## 十七、客户端／服务器版本协调与发行恢复
1. 标记 HTML、JS/CSS 指纹资源、API、序列化数据结构和必要服务端模型的兼容关系；上线过程应考虑旧浏览器标签仍运行旧 JS 的情况。
2. 部署、CDN、边缘缓存、灰度分配、Service Worker（若启用）和预渲染页面之间可能存在版本漂移；明确可检测的失败形式和恢复路径。
3. 对安全修复、协议变更、强制登录／登出、重大数据迁移等，需定义过期客户端如何安全退出或刷新，不得无故删除用户未提交但有权保留的草稿。
4. 不能对已发送的第三方通知或交易保证通过回滚前端版本即可逆转，需遵循真实服务端和业务补偿契约。
5. **验收**：新旧前端交叉运行、新旧 API、旧缓存、无网络、强制刷新及部署中断恢复时，用户任务及隐私边界可验证。

### WEB-017 核验合同

- **WEB-017-F · 直接失败变异：** 回退前端即宣称撤销外部通知→失败。

## 十八、领域安全与跨端内容边界
1. 浏览器路由守卫可改善用户体验，但不能替代真正的服务器鉴权。直接加载、SSR 数据读取、客户端导航和外部 API 请求均须从权威系统执行相应权限验证。
2. 不可信 URL 片段、重定向参数、动态路由和来自第三方的数据，不得被当成 HTML、脚本、跨域跳转或额外权限指令直接执行；开放重定向与脚本注入风险须对应核查。
3. 用户会话、服务端机密、初始序列化状态、日志及缓存必须有可追踪数据使用权限；SSR 与 Streaming 发生失败时不得把完整内部异常或其他租户信息写入浏览器输出。
4. **验收**：包含恶意但无害的参数、两种不同授权身份、直接深链和缓存命中场景，核对未发生权限升级、跨身份 HTML 泄露或开放重定向。

### WEB-018 核验合同

- **WEB-018-P · 输入/动作与合格判据：** 恶意URL/直达SSR/客户端API与错租户→各入口后端授权。
- **WEB-018-F · 直接失败变异：** 路由守卫当鉴权或异常泄别租户数据→失败。
- **WEB-018-N · 合法邻例：** 匿名公开内容不加无谓登录。
