# L4 前端发行与客户端版本协调技术规范

**文档ID：** STD-L4-WEB-003　**版本：** 0.1.0　**状态：** adopted　**生效日期：** 2026-10-30

## 技术对象、适用边界与有效依据

本 L4 具体技术专题覆盖浏览器前端从**可复现构建、发行产物、HTML 入口、静态资源、边缘/CDN 缓存、前后端跨版本共存、灰度发布，到旧标签页恢复和故障回退**的完整技术链路。适用于静态站点、CSR、SSR/SSG、混合渲染、PWA、嵌入 WebView 和其他确有浏览器发行需求的 Web 项目。无需发布渠道或有状态客户端的探索原型，只选取与其交付直接相关的检查；实际授权、生产操作和外部交易权限以既有规范及项目合同为准。
本规范组合采用 [L4 Web 领域通用基线](002-Web-领域通用基线--v0.1.0.md)（Web 通用基线）、[L4 渲染、路由与 Hydration 技术规范](009-渲染、路由与-Hydration-技术规范--v0.1.0.md)（渲染/路由/Hydration）、[L4 客户端状态、表单与网络数据技术规范](006-客户端状态、表单与网络数据技术规范--v0.1.0.md)（客户端数据）、[L4 离线、缓存与 PWA 生命周期技术规范](010-离线、缓存与-PWA-生命周期技术规范--v0.1.0.md)（PWA/离线）、[L4 浏览器身份与应用安全技术规范](008-浏览器身份与应用安全技术规范--v0.1.0.md)（浏览器身份/安全）、[L4 跨浏览器兼容及测试技术规范](011-跨浏览器兼容及测试技术规范--v0.1.0.md)（跨浏览器）、[L4 前端性能与资源调度技术规范](004-前端性能与资源调度技术规范--v0.1.0.md)（性能）、[L3 通用工程规范](../../L3/001-通用工程规范--v0.1.0.md)（通用工程），以及 L1/L2 的治理和协作契约（按实际采用状态适用）。
**已有行业标准直接引用原文**，不在本规范重写完整 HTTP、缓存和 Service Worker 算法：
- [RFC 9110 — HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110.html)、[RFC 9111 — HTTP Caching](https://www.rfc-editor.org/rfc/rfc9111.html)：状态码、缓存、条件请求、Vary、验证器、共享与私有缓存的规范性依据。
- [WHATWG HTML Living Standard](https://html.spec.whatwg.org/multipage/)、[Fetch Living Standard](https://fetch.spec.whatwg.org/)：前端资源加载、脚本和浏览器请求的基础语义。
- [W3C Service Workers — 2026-09-17 Candidate Recommendation Draft](https://www.w3.org/TR/2026/CRD-service-workers-20260917/)：新旧 Worker、客户端控制、Fetch 和 CacheStorage；**仍为草案**。
- [W3C Subresource Integrity — 2016-06-23 Recommendation](https://www.w3.org/TR/2016/REC-SRI-20160623/)：按内容摘要验证适用的脚本和样式资源。
- [MDN Cache-Control](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cache-Control)、[HTTP Caching](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching)、[SRI 实施说明](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Subresource_Integrity)、[Clear-Site-Data](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Clear-Site-Data)、[Service Worker skipWaiting](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerGlobalScope/skipWaiting) 和 [clients.claim](https://developer.mozilla.org/en-US/docs/Web/API/Clients/claim)：浏览器实施与兼容性参考，**不与 RFC/W3C Recommendation 混为同等规范地位**。
前端发行的具体 Bundler、框架、包管理器、CDN 平台、CI 工具、部署脚本及配置版本由 L5 指定；真实项目的业务版本约束、浏览器渠道、缓存策略、发布批准人、风险、质量门禁和验收证据由 L6 定义。本专项只制定跨技术栈的前端**版本传播、兼容性和可逆／不可逆结果**的具体工程契约。

## 核验口径与消费接口

维护者负责落实本文机制，领域/API/存储提供者负责其权威保证，验收者从实际受支持入口观察结果。输入固定源码/构建、配置、数据/协议版本、角色/租户、目标平台、故障时序和预算；权威观察对象为**入口/不可变资产/API/Worker/本地Schema的实际版本组合**。真实执行入口为**正式构建清单、资源GET及摘要、旧标签延迟import、多层缓存回读**。逐章 P/F/N 分别为正常输入及判据、破坏该机制的直接失败变异、应继续成立的合法邻例；本章原有每项规则、原有验收与新增合同共同约束，不用单一通用案例替代具体子项。每个子项须在案例输入中保留其适用条件，并以自身原文规定的输出/不变量判定；复合章应拆记录各个观察量，不能以一个成功掩盖其他失败。

证据产物包括真实命令/用户动作、原始响应或事件、权威状态前后值、版本、时序、失败及恢复；尚无对应真实运行证据的场景状态为 `not-run`，标准库示例仅证明列明的局部边界。具体输入与命令见[执行入口](../../../examples/web-backend/RUNBOOK.md)，条款索引见[规范条款登记](../../../registry/requirements.json)，来源的有限支持命题见[逐命题来源映射](../../../sources/web-backend/claims.json)。

本文的跨组件约束与正例、失败反例、合法邻例由本规范综合定义；外部来源支持的机制及适用边界见来源表。项目架构、预算和业务规则由实际需求确定。L5 实现应映射到所选框架、SDK 或引擎；L6 按具体版本的提供者保证与受支持矩阵验收项目能力。

## 一、发行单元与产物身份
1. 每次前端发行应能关联权威源码版本、锁定的依赖、构建配置、目标运行环境、静态文件清单、相关后端协议版本和发布渠道。单一页面的 HTML、JS、CSS、图片、字体、Worker 脚本可能由不同发布组件管理，不能假定它们天然原子更新。
2. 对需审计或可复现的发行，保留可核实的源码提交、构建作业、产物摘要或签名、构建时间及发布记录；摘要可以证明字节一致性，但不能自动证明程序安全、许可或业务有效性。
3. 明确哪些文件属于本版、哪些由外部系统长期提供、哪些是运行时动态数据。将构建产物、迁移脚本及已部署配置之间的对应关系记录在项目的原有权威系统中，不另造平行发布台账。
4. **验收**：从用户正在加载的 HTML 和资源 URL 能回溯到真实构建及已授权发行版本；不存在混合未批准构建或来自开发机的未追踪资产。

### WEB-001 核验合同

- **WEB-001-P · 输入/动作与合格判据：** 从用户HTML/资源回读到源码/构建/渠道→发行身份可追溯。
- **WEB-001-F · 直接失败变异：** 单HTML版本号掩盖混合未审资产→失败。
- **WEB-001-N · 合法邻例：** 外部长供资源可独立版本记录。

## 二、构建可复现性与环境边界
1. 构建应使用受支持的语言/工具链、锁文件或等价依赖固定机制，区分构建期、服务端运行期及浏览器运行期配置；生产秘密不得因构建常量替换进入公开脚本。
2. 无法从清洁且获授权的环境重建关键发行产物时，必须记录缺失的外部资产、生成器、工具版本及其实际限制，不用本地残留缓存冒充可复现。
3. 对依赖外部资源的构建要校验来源、许可与可用性；在有供应链风险的环节按相邻安全规范实施相称的审查，不因页面看似正常而省略实际发行资源检查。
4. **验收**：可对应源码与构建入口产生适用于目标平台的产物，完整性检查通过，实际发布文件与审查文件一致。

### WEB-002 核验合同

- **WEB-002-P · 输入/动作与合格判据：** 清洁锁定环境构建并审包/map→产物与源码对应且无秘密。
- **WEB-002-F · 直接失败变异：** 本机残留缓存冒可复现或秘密替换进JS→失败。
- **WEB-002-N · 合法邻例：** 无法字节复现须准确列依赖限制而非虚报。

## 三、客户端与服务端版本关系
1. 记录 HTML 入口版本、JS/CSS 构建版本、API 契约版本、持久数据模型、身份会话和可选 Service Worker 版本之间的依赖，避免以单个可读版本号代替完整运行状态。
2. 评估同一时间内可能出现的**旧标签+新后端、新标签+旧边缘缓存、新 HTML+旧资源、离线客户端恢复、灰度组不同服务端**等组合，并定义真正受支持的兼容窗口。
3. 版本约束优先表现为可核验接口能力与数据契约，不仅使用数字比较；版本相同不等于用户权限、配置或业务规则未变化。
4. **验收**：旧新前端与实际发布顺序中的后端配置组合可以按批准要求正常运行或安全失败，不误用数据、不引发未授权外部写入。

### WEB-003 核验合同

- **WEB-003-P · 输入/动作与合格判据：** 旧标签新后端/新HTML旧边缘等组合→能力契约兼容。
- **WEB-003-F · 直接失败变异：** 数字版本相同即认为权限/数据未变化→失败。
- **WEB-003-N · 合法邻例：** 无相关组件可缩小真实矩阵而不虚造。

## 四、构建产物清单与资源依赖图
1. 对需长期缓存或多版本并存的项目，发行产物应能标识入口 HTML、入口模块、动态 import chunk、样式、字体、预加载资源、源映射的受控渠道和可选 Worker/Manifest。
2. HTML 中引用的路径必须在其可访问生命周期内存在；动态 chunk 和按需加载页面需与主文件具有真正可兼容的依赖关系，不能只验证首页打包成功。
3. 资源名称采用内容哈希、版本路径或等价的不可变身份时，要求同一资源地址在允许缓存期限内始终代表同一字节；修改资源必须生成新身份。
4. **验收**：根据实际产物清单逐项验证 URL、完整性、MIME、压缩与跨源属性，无法由当前 HTML 找到的必需资源不能标记为完整交付。

### WEB-004 核验合同

- **WEB-004-P · 输入/动作与合格判据：** 逐入口/动态import/字体/Worker清单请求→URL/MIME/完整性都可验。
- **WEB-004-F · 直接失败变异：** 只首页构建成功但按需chunk不存在→失败。
- **WEB-004-N · 合法邻例：** 无动态chunk可用简单清单。

## 五、HTML 入口与缓存新鲜度
1. 对承担“选择当前前端版本”职责的 HTML 入口，按实际用户与部署机制确定是否需要每次重新验证。`no-cache` 允许缓存存储但要求重验证；`no-store` 禁止缓存存储；两者不能混用为同一个技术含义。
2. 对静态/公共 HTML、认证后的 SSR HTML、不同租户/语言入口分别配置相应缓存与响应头；私有数据不得由于共享 CDN 缓存而越权传播。
3. 入口 HTML 可以被旧标签、代理、bfcache、PWA CacheStorage 或浏览器历史机制以不同方式保留；缓存标头的变更不会立刻刷新每台已有页面。
4. **验收**：冷访问、普通刷新、强制刷新、代理缓存命中、登录状态变化时，入口引用的实际资源版本和响应权限正确，未出现永久加载旧主页或跨身份内容。

### WEB-005 核验合同

- **WEB-005-P · 输入/动作与合格判据：** 普通/强刷/代理/bfcache访问HTML→入口版本和私有范围正确。
- **WEB-005-F · 直接失败变异：** no-cache误当no-store或新头自动刷新旧内存→失败。
- **WEB-005-N · 合法邻例：** 公开静态HTML可按实际策略缓存。

## 六、不可变静态资源与保留周期
1. 对内容哈希或真实版本路径的静态资源，长期缓存按 RFC 9111；`immutable` 按 [RFC 8246 §2](https://www.rfc-editor.org/rfc/rfc8246.html#section-2) 仅在响应新鲜期内使用，并核对浏览器支持，前提是相同 URL 字节不可改变且有旧客户端仍可用的资源保留策略。
2. 不得在旧 URL 下悄然覆盖不同字节的 JS/CSS；不以 CDN 清理作为修复有冲突的不可变资源的唯一办法。资源更新应关联新的内容身份及对应入口版本。
3. 清理旧资源前应检查仍在运行的旧标签、动态导入、PWA、离线环境、回退版本、内嵌 WebView 和缓存失效后的回源。无法证明客户端均已结束时按风险保留相称兼容窗口。
4. **验收**：不同旧入口在其支持期内仍可以按需获取依赖，长缓存生效时无同名异内容、资源 404、错误 MIME 和不可预测的浏览器缓存结果。

### WEB-006 核验合同

**必要机制补充：** 资源保留窗覆盖旧入口和运行页面的完整动态依赖闭包；不可变URL不得覆写。无法证明旧客户端全部结束时不得仅以在线心跳缺失立即清理仍支持资源。

- **WEB-006-P · 输入/动作与合格判据：** 旧页延迟import且缓存过期回源→旧hash字节仍存在。
- **WEB-006-F · 直接失败变异：** 同URL覆新字节或部署即删全部旧资源→失败。
- **WEB-006-N · 合法邻例：** 依赖窗结束的旧公开资产可退役。

## 七、CDN、多层缓存与发布传播
1. 明确浏览器 HTTP Cache、代理、CDN 边缘、源站、Service Worker CacheStorage 及 Query Cache 的不同缓存键、失效与控制权；一次 CDN Purge 不会自动清理所有浏览器资源或旧标签内存。
2. 对缓存键的 URL、Vary、编码格式、语言、授权、查询参数和 Host 维度作实际配置核对；错误省略身份维度会引发内容交叉，错误包含高基数维度会破坏缓存效率。
3. 发布与撤回按实际提供商的清理能力、传播延迟、节点回源和错误重试进行设计，不能仅由管理 API 返回成功就断定全球边缘已经一致。
4. **验收**：从不同网络/区域及实际终端回读入口、关键 chunk、HTTP 响应头和缓存身份，核对清理传播、回源及用户最终页面，记录未同步节点。

### WEB-007 核验合同

- **WEB-007-P · 输入/动作与合格判据：** 不同区域边缘命中/回源/清理传播→每层版本可读。
- **WEB-007-F · 直接失败变异：** Purge API成功即称全球浏览器清完→失败。
- **WEB-007-N · 合法邻例：** 不使用CDN不强制多区边缘测试。

## 八、个人化 HTML、SSR 和授权缓存
1. 对含登录用户、租户、权限、订单、个性化推荐等私有数据的 HTML、预渲染片段和边缘响应，根据实际服务端授权选取 private/no-store 或可证明安全的受限缓存策略。
2. 共享/私有缓存的适用类别，以及Cache-Control指令public/private、no-cache、no-store和s-maxage 具有不同协议效果；不得为提高边缘命中率未经许可将私有 SSR 响应标成公共缓存。
3. 每个缓存命中都必须满足实际对象身份和授权前提。UI 的页面数据是否匿名不可凭页面外观推断，需同时核对接口字段和嵌入序列化状态。
4. **验收**：用户 A 的登录页面、B 的身份、语言和租户切换，以及会话撤销和 API 权限收紧后，不出现私有 HTML 交叉或错误旧权限复活。

### WEB-008 核验合同

- **WEB-008-P · 输入/动作与合格判据：** 两个租户SSR/序列化初值及撤权→私有内容不共享。
- **WEB-008-F · 直接失败变异：** 页面外观匿名就把私人JSON公共缓存→失败。
- **WEB-008-N · 合法邻例：** 合法公开表示可安全共享。

## 九、API 契约与新旧前端共存
1. 后端接口的字段、默认值、错误语义、鉴权和业务状态不因前端发布瞬时改变；新旧客户端并存时应有明确兼容/能力协商策略，避免“新 API 只为新页面服务”导致旧标签直接损坏。
2. 破坏性接口改动按权威后端/业务规则先处理受影响消费者，必要时采用扩展再收缩、版本化接口、兼容适配或受控淘汰。发布顺序取决于真实依赖，不一律指定“后端先发”。
3. 对轮询、SSE/WebSocket、文件传输和后台异步结果等长连接，应核对老客户端对新事件或缺失字段的行为；不能因未知值自动变成有权限的成功状态。
4. **验收**：代表性的旧/新客户端与当前可访问服务端共同测试真实用户操作、错误恢复和必要数据保真，并记录不兼容矩阵与退役时点。

### WEB-009 核验合同

- **WEB-009-P · 输入/动作与合格判据：** 旧新前端调当前API及旧SSE事件→字段/默认/错误语义兼容。
- **WEB-009-F · 直接失败变异：** 未知枚举默认为有权成功→失败。
- **WEB-009-N · 合法邻例：** 部署顺序可依真实依赖选择不一律后端先发。

## 十、数据结构变更与客户端迁移
1. 发布前核实本地 IndexedDB、离线队列、URL 持久状态、表单草稿和远端 Schema 是否有需要共同迁移的版本约束。真正的服务端数据库迁移由对应后端/数据领域执行。
2. 某一方向无法回滚的数据结构变化，应明确 forward fix、双读、迁移幂等、旧版只读或正式停止旧客户端的策略；不能承诺单纯回退前端 JS 即恢复旧数据形态。
3. 数据迁移期间涉及权限、财务、外部通知与客户权益时，客户端只能展示权威系统确认结果，不以缓存、草稿或本地数据转换冒充业务提交。
4. **验收**：旧版已存数据、迁移中断、同账号多标签与新旧 API 同时运行时，必要数据及交易身份可追溯，未发生重复写入、数据丢失或越权重放。

### WEB-010 核验合同

- **WEB-010-P · 输入/动作与合格判据：** 旧IDB/草稿/队列迁移中断并多标签→必要数据/意图保留。
- **WEB-010-F · 直接失败变异：** 回退JS当数据自动回旧格式→失败。
- **WEB-010-N · 合法邻例：** 不可逆迁移可合法前滚或旧版只读。

## 十一、动态加载 Chunk 的跨版本故障
1. 已运行的 JS 可能在用户点击新路由后才请求动态 chunk。若部署时立即清理旧 hash 文件，旧标签会遇到资源 404、解析错误或错误类型的响应。
2. 对 ChunkLoadError、网络中断、HTML fallback 被错误作为 JS 返回、完整性不匹配等情况，应提供准确诊断和可控恢复；不能无条件无限刷新或要求用户丢弃未保存表单。
3. 可采用足够的旧产物保留期、版本提示与安全刷新等方式保障兼容，取舍由项目浏览器与发行策略决定。对需要强制刷新完成安全修复的情形，必须兼顾数据保护和授权。
4. **验收**：发布中打开旧标签，延时进入此前未加载的路由，再验证错误识别、数据保存、资源回源与重启后可用性。

### WEB-011 核验合同

- **WEB-011-P · 输入/动作与合格判据：** 旧标签发后未载路由chunk→缺资源有受控恢复且草稿不丢。
- **WEB-011-F · 直接失败变异：** 404返回HTML作JS、无限刷新掩盖错误→失败。
- **WEB-011-N · 合法邻例：** 明确安全刷新可在保草稿后实施。

## 十二、Service Worker 与客户端更新窗口
1. Service Worker 的注册、waiting、activation、controller、CacheStorage 等平台机制按相邻 PWA 专项和 W3C Service Workers 规范执行；本节专门核查**发行时新旧脚本、HTML、API 与多个客户端的版本交错**。
2. skipWaiting 和 clients.claim 会影响旧页面由谁控制，不能默认无损立即接管；在未保存草稿、正在提交、旧队列和不兼容 JS/Worker 协议存在时，应设明确的允许接管条件。
3. Worker 脚本更新、预缓存清单发布、旧资源清理与版本回滚须遵循顺序，不能出现“新 Worker 激活、旧 HTML 资源被删除、新 HTML 尚未完成发布”的混合状态。
4. **验收**：多标签、首次注册、等待激活、立即接管、卸载/重装与旧客户端长期离线恢复，均能在所选浏览器完成用户任务或明确安全失败。

### WEB-012 核验合同

- **WEB-012-P · 输入/动作与合格判据：** W1旧页/W2等待/claim与在途提交→控制和兼容条件可查。
- **WEB-012-F · 直接失败变异：** 强接管导致重复提交或先删旧Cache→失败。
- **WEB-012-N · 合法邻例：** 证明协议兼容后可即时激活。

## 十三、bfcache、旧标签与长期会话
1. 浏览器 bfcache、普通导航、SPA 内路由、页面隐藏及冻结恢复具有不同的生命周期；服务端或前端完成发布并不会强迫浏览器已打开的标签立刻加载最新代码。
2. 旧页面恢复时按风险核对当前 Session、对象权限、API 版本、正在执行的请求、用户草稿与显示数据是否仍有效；页面看见旧内容不构成对新敏感操作的授权。
3. 需要新版本才能继续的操作提供明确版本冲突、草稿保存/导出、重新验证或合法替代路径；不能在未知服务器结果时自动重发支付、删除和通知。
4. **验收**：旧标签数小时后恢复、bfcache 返回、用户登出再返回、不同账号复用浏览器及 API 变更后，状态刷新与操作结果保持正确。

### WEB-013 核验合同

- **WEB-013-P · 输入/动作与合格判据：** 旧标签数小时恢复/登出Back/换账号→会话与数据重新核实。
- **WEB-013-F · 直接失败变异：** 发布完成当客户端全加载新代码→失败。
- **WEB-013-N · 合法邻例：** 合法本地滚动与草稿可独立恢复。

## 十四、灰度、分组和渐进发布
1. 若业务影响和回滚成本需要分阶段验证，可按用户、会话、租户、地域或请求入口确定相称的灰度群体，保证前端 HTML、静态资源和后端功能能力正确对应。
2. 灰度分组应有稳定性条件及用户/租户隔离，不允许一个操作在多次请求中无控制地跨越不兼容版本。部分区域/CDN 节点的上线状态应可观察。
3. 先确认小规模实际业务链路与错误、性能和资源指标，再按批准的观察窗口扩大流量；低风险可逆静态站点可采用简单直接发布，不强制复杂流量编排。
4. **验收**：灰度组、对照组和回退组的构建身份可查，各组用户从直达 URL 到真实业务结果均使用相容版本，无跨组数据丢失。

### WEB-014 核验合同

- **WEB-014-P · 输入/动作与合格判据：** 灰度/对照/回退组从URL走业务→构建分组稳定且兼容。
- **WEB-014-F · 直接失败变异：** 同一操作随机跨不兼容组→失败。
- **WEB-014-N · 合法邻例：** 低风险静态站可直接发布。

## 十五、功能开关、兼容门禁与禁用能力
1. 功能开关可用于协调前端新 UI、后端 API 和用户启用阶段，但必须明确默认值、来源、缓存时间、开关范围、审计及停止条件；不能以临时开关偷偷改变已批准业务规则。
2. 代码发布与功能生效是不同状态；关闭前端交互不等于后端资源、收费操作和数据权限已被撤销。安全或资金相关限制仍必须在权威服务端强制执行。
3. 需要快速停止故障功能时，确认旧客户端对开关的获取和行为，不能仅更新最新 Bundle 就宣称所有用户停止使用旧功能。
4. **验收**：不同版本、不同开关分组、网络不可达及开关翻转时，关键功能可按照实际权限安全停止/恢复，没有未获批准的外部副作用。

### WEB-015 核验合同

- **WEB-015-P · 输入/动作与合格判据：** 开关翻转/离线旧Bundle→权威服务端禁用和当前配置真实。
- **WEB-015-F · 直接失败变异：** 隐藏新按钮即宣称所有旧客户端停写→失败。
- **WEB-015-N · 合法邻例：** 代码已发布但功能未启用是合法分态。

## 十六、发布顺序与双向兼容检查
1. 针对接口或数据迁移列出前端、服务端、数据库、缓存、鉴权、第三方 SDK 和 Worker 的实际依赖图；选择可降低不可逆失败的先后顺序，保留必要兼容窗口和已确认的回滚边界。
2. 对可回滚变更准备新旧版本兼容与数据校验；对无法无损回滚的后端持久化或第三方动作建立前向修复和补偿方案，按真实业务权利批准。
3. 需要停止旧客户端支持时，先核对已批准的支持期限、用户分布和可操作迁移入口，不因为新代码合并成功便立即删除所有旧 API。
4. **验收**：按真实发布拓扑模拟各步骤暂停、失败与重复执行，能够识别允许继续/停止的条件和最终真实用户版本。

### WEB-016 核验合同

- **WEB-016-P · 输入/动作与合格判据：** 按依赖各步骤暂停/失败/重跑→支持窗与回退界限有证据。
- **WEB-016-F · 直接失败变异：** 未经兼容验证提前删旧API→失败。
- **WEB-016-N · 合法邻例：** 不可逆状态可选择批准前向修复。

## 十七、预发布验证与实际发行入口
1. 预发布环境应使用与拟发布版本对应的真实构建产物、资源路径、运行配置和必要 API 契约；不能用开发模式的热更新服务器代替正式编译和 CDN/静态托管路径验证。
2. 根据实际渠道核对 HTTPS、域名、base path、SPA 静态回退、404/410、重定向、SSR 入口、文件 MIME、脚本类型、CSP、安全头、跨域资源与身份回调。
3. 真实用户入口可能包含公开索引、认证后台、嵌入 WebView、PWA 安装入口和深链。只有项目存在的入口才纳入相应发布门禁，不让不相关功能增加固定成本。
4. **验收**：从目标 URL 或渠道独立发起访问，构建版本、配置、API、身份、必要动态资源和核心交互确实可用；模拟页面截图或部署 API 成功不等于发布验收。

### WEB-017 核验合同

- **WEB-017-P · 输入/动作与合格判据：** 用正式编译包经真实域名/base path/回调→外部入口可用。
- **WEB-017-F · 直接失败变异：** 开发HMR或部署API绿冒实际发行验收→失败。
- **WEB-017-N · 合法邻例：** 项目没有的渠道无需虚构。

## 十八、发行完整性、第三方资源与安全策略
1. 浏览器静态 JS/CSS、外部 SDK 和 CDN 资源需与已审查构建及实际使用许可对应。适用时按 W3C Subresource Integrity Recommendation 配置资源摘要，并检查跨源加载所需 CORS 关系。
2. 内容哈希文件名用于缓存身份，SRI 用于浏览器验证响应内容，两者的验证目的与边界不同；不能把文件名包含 hash 当作浏览器已经执行 SRI。
3. 部署时 CSP Nonce/Hash、完整性属性、modulepreload、动态 import 路径及代理压缩可能互相影响，应同时验证正常资源载入与拒绝篡改内容的行为。
4. 对 Source Map、调试配置、第三方代码、依赖许可、生产凭据和测试产物进行发行边界核查，明确哪些只留在获授权的内部监测与调试系统。
5. **验收**：真实渠道加载正确并安全拒绝内容不匹配，未泄露密钥或用户私有数据，旧新资源的完整性记录可追溯。

### WEB-018 核验合同

- **WEB-018-P · 输入/动作与合格判据：** SRI/CSP/modulepreload与篡改对照→正确资源加载、错误字节拒绝。
- **WEB-018-F · 直接失败变异：** 文件名带hash当浏览器SRI验证→失败。
- **WEB-018-N · 合法邻例：** 未使用SRI须仍满足实际供应链安全合同。

## 十九、登录会话及第三方回调的发布兼容
1. 版本切换可能改变 OAuth 回调 URL、Cookie Domain/SameSite、Session 格式、Passkey RP ID、支付 SDK 初始化和其他第三方嵌入。相关修改须由实际适用的身份及业务规则确认并安排兼容迁移。
2. 发布前评估用户已打开的登录/授权页面及尚未完成的支付/业务任务，不能在版本切换期间错误建立新会话或将同一外部结果处理两次。
3. 若第三方回调跨越旧前端/新后端版本，仍需通过权威业务标识、事务与权限核验，不将浏览器地址跳转成功当作登录或结算最终结果。
4. **验收**：旧版启动的登录/交易在升级前后可按已批准合同完成或安全失败，回调、会话、账户和外部结果无交叉、丢失或重复确认。

### WEB-019 核验合同

- **WEB-019-P · 输入/动作与合格判据：** 旧版本开启OAuth/支付后升级回调→业务ID/主体/会话无交叉。
- **WEB-019-F · 直接失败变异：** 回调跳转成功即认结算或新会话→失败。
- **WEB-019-N · 合法邻例：** 合法重复回调可返回原处理结果。

## 二十、发布监测、暂停与自动门禁
1. 发布后的观察应关联实际前端构建、CDN 地点、浏览器版本、用户分组、API 错误、动态 chunk、登录失败、核心任务、性能与资源异常；进程存活或静态文件返回 200 不代表用户可以完成任务。
2. 是否扩大灰度、暂停或回退依已批准的错误预算、影响范围、关键业务失败和真实用户路径决定；对资金、敏感数据与越权风险不应等待流量样本达到统计显著才采取获授权的保护措施。
3. 客户端诊断可以保留构建 ID、受限的错误类别和关键版本关系，不将 Token、恢复链接、客户业务字段或完整私有 URL 发送给无权分析平台。
4. **验收**：可明确定位哪个构建/灰度组/设备受影响、真实前后端版本与恢复动作。告警已触发、修复提交和生产恢复分别记录。

### WEB-020 核验合同

- **WEB-020-P · 输入/动作与合格判据：** 构建/区域/浏览器/组故障监测→影响和恢复可定位。
- **WEB-020-F · 直接失败变异：** 200静态文件或告警触发当用户任务完成→失败。
- **WEB-020-N · 合法邻例：** 重大越权风险可按已有保护策略不等统计显著。

## 二十一、故障回滚、前向修复与补偿
1. 前端静态产物回滚可以恢复可访问的入口和代码，但不能自动撤销已迁移的数据库、已发送通知、已发生交易、用户设备上的 Worker 或正在运行的旧标签。
2. 回滚方案需分别考虑 HTML、CDN、旧 chunk、Worker、服务端 API、身份 Session 与本地持久化 Schema 的实际协调，不能通过清空全部浏览器存储作为普遍恢复手段。
3. 若旧客户端已加载新的不可兼容数据模型，优先采用获准的兼容适配、只读恢复或前向修复；不可逆外部副作用由真正有权的业务系统实施补偿。
4. **验收**：发布失败、部分节点更新、新旧浏览器共存和数据迁移后，用户关键任务可恢复，未丢失有权保留的草稿、记录与必要审计证据。

### WEB-021 核验合同

- **WEB-021-P · 输入/动作与合格判据：** 部分发布失败且新本地Schema→HTML/CDN/Worker/API分别恢复。
- **WEB-021-F · 直接失败变异：** 清空全存储或前端回退宣称撤回邮件→失败。
- **WEB-021-N · 合法邻例：** 合法只读兼容/前向修复可替代全回滚。

## 二十二、资源退役、缓存清理与发布留存
1. 只有确认不再被受支持的旧 HTML、动态 chunk、Worker、缓存回退与用户客户端依赖时，才能按批准策略删除旧静态资源或相关 API 兼容路径。
2. 浏览器 `Clear-Site-Data` 可按支持情况清理指定类型的站点数据，但其作用范围、浏览器差异和潜在草稿损失须谨慎评估；它**不负责自动清除所有 CDN 共享缓存**，也不是全部用户数据清理的无条件保证。
3. Service Worker unregister、删除 CDN 对象、更新 HTTP Cache-Control、废弃资源 URL 是不同操作；各自的旧客户端行为和安全范围要分别核验，不能将一种成功冒充全部系统退役完成。
4. 根据用户支持窗口、资产许可、回退责任和历史审计需求决定发布包、旧资源、源映射、签名/摘要与上线证据的保留期限，不无限存储敏感数据，也不无授权删除可追溯结果。
5. **验收**：退役后仍在支持期的客户端可正常获取所需资源或安全更新，最终清理范围与权利、成本及用户数据保证相符。

### WEB-022 核验合同

- **WEB-022-P · 输入/动作与合格判据：** 退役前查旧HTML/chunk/Worker/备份依赖→保留闭包成立。
- **WEB-022-F · 直接失败变异：** Clear-Site-Data当全球CDN清除或unregister当删全部数据→失败。
- **WEB-022-N · 合法邻例：** 支持窗结束且权利允许的旧资源可受控删除。

## 二十三、发行及客户端版本协调的静态验收矩阵
| 独立场景 | 输入与故障条件 | 真实项目需要的合格证据 |
| --- | --- | --- |
| 发行版本身份 | 目标 HTML、JS/CSS、构建清单版本不一致 | 可追踪实际构建与批准发行对象，错误组合阻断或安全恢复 |
| 内容哈希资源更新 | 同一路径被覆写为新 JS 字节 | 同一 URL 在声明的缓存期内保持字节不可变，更新使用新资源身份 |
| 旧标签动态加载 | 发布后删除旧 hash chunk，用户晚点击 | 旧支持客户端仍能加载对应 chunk 或提示安全刷新，草稿保留 |
| HTML/资源发布竞态 | 新 HTML 先曝光，指纹文件未同步 | 所有必需依赖在入口曝光时可访问，禁止半完整发行 |
| CDN 多边缘不一致 | 部分边缘缓存新 HTML，其他仍旧 | 兼容窗口成立、真实区域观察和必要回源/清理记录 |
| no-cache 与 no-store | 入口误认为 no-cache 禁止存储 | 响应策略符合 RFC 9111 实际语义，预期重验证/保密边界成立 |
| 304 与 ETag 误用 | 旧验证器错误返回 304 | 内容及版本正确重验证，不把过期实体默认为最新 |
| 共享缓存私有 SSR | 用户 A 的登录 HTML 被 CDN 返回给 B | 身份隔离，错误缓存失效，权威服务端权限不扩大 |
| Vary / Locale 缓存 | 语言或压缩/账号变体未分组 | 重要资源与业务数据对应真实请求条件 |
| JS chunk 的 MIME 错误 | SPA fallback 让 .js 返回 HTML | 明确检测并正确恢复，不无提示显示空白页面 |
| Hydration 与灰度版本 | SSR HTML 和客户端 Bundle 来自不同分组 | 满足初始视图契约或安全降级，数据和输入不被覆盖 |
| API 缺字段 | 旧客户端调用新版 API 后必需字段缺失 | 兼容或明确拒绝，不把数据缺失转换为合法默认业务规则 |
| API 语义变化 | 相同字段改变权限/状态/单位 | 按权利人批准的迁移策略协调前后端，旧用户无静默误处理 |
| 数据迁移不可逆 | 旧前端无法读取新数据库结构 | 提供已验证兼容/前向修复，不承诺无法实现的简易回滚 |
| 客户端本地 Schema 升级 | IndexedDB 或离线队列被新包迁移 | 旧支持客户端不会破坏持久化数据，必要迁移完整 |
| 功能开关翻转 | 旧标签继续使用关闭的资金入口 | 服务端实际停止未授权动作，前端显示及时且可恢复 |
| 灰度组不稳定 | 同一用户跨请求切至不兼容后端 | 分组与接口可协同，实际业务流程不因频繁切换损坏 |
| 旧 Worker 接管 | skipWaiting / claim 改变页面控制者 | 旧标签、草稿、离线数据及资源协议仍可用 |
| Service Worker 更新失败 | 安装资源缺失或半缓存 | 不会接管为不可用版本，旧可用版本可恢复 |
| bfcache 恢复旧页面 | 发布/退出后用户点击返回 | 重新校验敏感权限，浏览器旧数据不产生新越权操作 |
| PWA 离线多日后重连 | 新 API 与旧 Worker/队列协议不兼容 | 旧数据可安全迁移或保留，外部写入不重复 |
| OAuth 回调跨版本 | 用户在旧版开始登录，新版处理回调 | state/redirect/session 均正确，不误建立账号或重复回调 |
| 第三方 SDK/SRI | CDN 脚本内容与 integrity 摘要不符 | 按安全策略拒绝错误代码，必要任务有受控失败反馈 |
| CSP / 构建脚本错误 | 新页面 nonce/动态脚本与策略不符 | 真实渠道中正常资源加载且恶意注入不能执行 |
| 预发布与真实域名差异 | 测试 URL 成功但生产 base path 和 HTTPS 失败 | 域名、路由、资源、回调在生产实际入口正确 |
| 部署监测假阳性 | 首页 200 但动态功能、后端或授权失败 | 关键用户路径的运行证据独立于静态存活检查 |
| 回滚后新旧混合 | 旧 HTML、新缓存/Worker、新后端持久状态 | 恢复兼容、必要数据与业务结果保真，不盲目删除 |
| Clear-Site-Data 误伤 | 为修复缓存无授权清除本地未提交草稿 | 清理经批准且范围精确，重要有权数据保留或按约恢复 |
| 旧资源退役过早 | 有效支持客户端仍引用已删除旧资源 | 退役依据真实使用窗口、可靠兼容或显式安全迁移 |
| 嵌入 WebView 长期停留 | 宿主无法自动更新、新旧脚本运行数周 | 按目标宿主渠道支持期正确降级，鉴权与数据真实 |
## 二十四、规范批准与实际项目接入
1. 本规范是 Web 领域下关于**发行产物、客户端多版本共存、静态资源、CDN/浏览器缓存、灰度发布和前端故障恢复**的具体技术专项；它不取代 L3 的通用版本/CI/运维契约，也不重新定义后端数据库迁移、Service Worker 算法、HTTP 缓存规范、浏览器身份或资金交易规则。
2. 已有行业规则一律引用 RFC/W3C/WHATWG 官方原文，MDN 仅作为浏览器兼容与实施资料。L5 负责实际框架、构建器、CDN、CI、服务提供者和部署工具配置，L6 决定每个项目的支持版本组合、缓存期、权限、灰度、恢复窗口、正式发布门禁及有效证据。
3. 项目按实际采用的能力验证 CDN 清理、浏览器旧缓存、旧标签、OAuth/支付回调、Service Worker、灰度及端到端流程，并记录目标版本、环境和结果。
4. 项目采用范围须明确记录；具体项目的发布安全、实际用户可用性、长期缓存兼容和业务结果仍由 L6 根据项目真实环境及授权逐项验收。
