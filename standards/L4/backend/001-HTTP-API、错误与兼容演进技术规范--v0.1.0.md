# L4 HTTP API、错误与兼容演进技术规范

**文档ID：** STD-L4-BACKEND-001　**版本：** 0.1.0　**状态：** adopted　**生效日期：** 2026-10-30

## 适用对象与官方标准

本专题约束公开 HTTP API、Web/移动后端、内部服务 HTTP 入口、Webhook、面向 Agent/MCP 的 HTTP 服务及管理接口。接口技术契约以真实消费者、业务授权与版本支持窗口确定，不用“REST”字样替代对业务语义的核验。
组合技术依据：[L4 后端与分布式系统领域通用基线](007-后端与分布式系统领域通用基线--v0.1.0.md)（后端领域通用基线）、[L4 领域模型与服务边界技术规范](013-领域模型与服务边界技术规范--v0.1.0.md)（领域模型与服务边界）、[L3 通用工程规范](../../L3/001-通用工程规范--v0.1.0.md)（L3 工程）、[L2 人类与 Agent 团队组织协作规范](../../L2/001-人类与-Agent-团队组织协作规范--v0.1.0.md)（L2）、[L1 全局治理补充规范](../../L1/001-全局治理补充规范--v0.1.0.md)（L1）。实际权限和环境依项目 L6 契约确定。浏览器 CORS 实现、数据库事务算法、消息和安全协议由对应专项负责，框架 SDK 细则在 L5，项目适用在 L6。
**行业标准直接引用原文，不平行抄写协议条款：**
- [RFC 9110 HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110.html)、[RFC 9111 HTTP Caching](https://www.rfc-editor.org/rfc/rfc9111.html)：正式 HTTP 语义与缓存标准。
- [RFC 9205 / BCP 56 — Building Protocols with HTTP](https://www.rfc-editor.org/rfc/rfc9205.html)：Best Current Practice，属于 HTTP API 设计规范性实践指导。
- [RFC 9457 — Problem Details](https://www.rfc-editor.org/rfc/rfc9457.html)：已取代 RFC 7807；只有选择该错误表示时才作为相应接口契约。
- [OpenAPI Specification v3.2.1](https://spec.openapis.org/oas/v3.2.1.html)：2026-09-10 正式版本；客户端、网关与工具链实际使用的版本须项目锁定。
- [RFC 6585](https://www.rfc-editor.org/rfc/rfc6585.html)（428、429 等）、[RFC 8288 Web Linking](https://www.rfc-editor.org/rfc/rfc8288.html)、[RFC 9745 Deprecation](https://www.rfc-editor.org/rfc/rfc9745.html)（Standards Track）、[RFC 8594 Sunset](https://www.rfc-editor.org/rfc/rfc8594.html)（Informational）、[RFC 5789 PATCH](https://www.rfc-editor.org/rfc/rfc5789.html)。
- [RFC 9112 HTTP/1.1](https://www.rfc-editor.org/rfc/rfc9112.html)：当网关、代理和消息分帧相互影响时适用。
- [IETF Idempotency-Key 工作组草案 -08](https://datatracker.ietf.org/doc/html/draft-ietf-httpapi-idempotency-key-header-08)，2026-10-22发布、2027-04-25到期，所选状态为**Active Internet-Draft，未成为RFC**。实现可参考该准确草案版本，但对外必须明确具体服务确认的键作用域、指纹、时效和处理状态，不能宣称存在统一的已批准强制标准。

## 核验口径与消费接口

维护者负责落实本文机制，领域/API/存储提供者负责其权威保证，验收者从实际受支持入口观察结果。输入固定源码/构建、配置、数据/协议版本、角色/租户、目标平台、故障时序和预算；权威观察对象为**真实HTTP状态/表示/条件写和独立业务操作结果**。真实执行入口为**curl或锁定SDK经真实代理调用、响应头/正文、权威存储和外部结果查询**。逐章 P/F/N 分别为正常输入及判据、破坏该机制的直接失败变异、应继续成立的合法邻例；本章原有每项规则、原有验收与新增合同共同约束，不用单一通用案例替代具体子项。每个子项须在案例输入中保留其适用条件，并以自身原文规定的输出/不变量判定；复合章应拆记录各个观察量，不能以一个成功掩盖其他失败。

证据产物包括真实命令/用户动作、原始响应或事件、权威状态前后值、版本、时序、失败及恢复；尚无对应真实运行证据的场景状态为 `not-run`，标准库示例仅证明列明的局部边界。具体输入与命令见[执行入口](../../../examples/web-backend/RUNBOOK.md)，条款索引见[规范条款登记](../../../registry/requirements.json)，来源的有限支持命题见[逐命题来源映射](../../../sources/web-backend/claims.json)。

本文的跨组件约束与正例、失败反例、合法邻例由本规范综合定义；外部来源支持的机制及适用边界见来源表。项目架构、预算和业务规则由实际需求确定。L5 实现应映射到所选框架、SDK 或引擎；L6 按具体版本的提供者保证与受支持矩阵验收项目能力。

## 一、API 消费者及版本责任
1. 为每个 API 明确调用主体和目的：公共第三方、已发行客户端、内部服务、管理端、Web、Agent、批处理或合作伙伴。
2. 固定接口的身份及权限前提、正常结果、异常路径、数据含义、外部副作用、维持兼容的真实消费群体和支持期限。
3. 低风险单次原型可以最小化门禁，但正式承诺的客户端、资金操作及持久化 API 必须具备可测试的完整接口契约。
4. **验收**：以真实客户端调用到已批准业务终点，不以 Swagger 页面存在、Mock 成功或路由可访问证明整个结果已经生效。

### BE-001 核验合同

- **BE-001-P · 输入/动作与合格判据：** 真实受支持SDK完成授权任务→身份/版本/终点明确。
- **BE-001-F · 直接失败变异：** Swagger或Mock绿冒业务完成→失败。
- **BE-001-N · 合法邻例：** 一次性低风险原型可最小合同。

## 二、URI、资源身份与链接
1. 资源身份来自领域模型和授权关系，不由路径层级、数据库自增 ID 或前端变量名自动决定。
2. 定义 URI 编码、大小写、重定向、路径／查询语义、资源不存在及迁移后身份保持；不能将可猜测 URL 误视为访问授权。
3. 如使用 Link 首部导航关系，以 RFC 8288 为正式定义，项目仅补充分页或关联资源的实际消费条件。
4. **验收**：空 ID、百分号编码、Unicode、不同租户的同号资源、旧链接和代理路径重写均得到一致而授权正确的结果。

### BE-002 核验合同

- **BE-002-P · 输入/动作与合格判据：** Unicode/编码/旧链接/同号跨租户→URI身份和权限一致。
- **BE-002-F · 直接失败变异：** 可猜路径或深层URL当授权→失败。
- **BE-002-N · 合法邻例：** Link仅在实际采用时按关系定义。

## 三、方法安全性与幂等性的差异
1. 按 RFC 9110 区分安全方法与幂等方法；GET、HEAD 等不得由客户端请求触发收费、删除或不可逆业务写入，日志等非请求目标副作用另按标准语义处理。
2. PUT、DELETE 的协议幂等不等同于业务付款或通知恰好执行一次。POST/PATCH 是否允许安全重试取决于具体操作契约与去重机制。
3. 垃圾请求清理、搜索爬取或浏览器预取可能自动发起安全方法，服务端不能利用看似查询的 URL 执行危险变更。
4. **验收**：重复请求、成功后断线、方法改写及预取情形均不能违反实际业务不变量。

### BE-003 核验合同

**必要机制补充：** 安全方法禁止将用户请求的语义设计为扣款、删除等非安全命令；访问日志、修订历史及符合既定合同的附带流量/广告计量不因存在旁效应而自动违反RFC安全/幂等定义。

- **BE-003-P · 输入/动作与合格判据：** GET预取及PUT/DELETE重传→用户预期效果幂等且无危险写。
- **BE-003-F · 直接失败变异：** GET参数执行删除或PUT重试双扣款→失败。
- **BE-003-N · 合法邻例：** 日志/修订史与既定计量可按安全方法允许的旁效应存在。

## 四、表示、媒体类型和内容协商
1. 明确请求和响应的 Content-Type、Accept、字符编码、支持的媒体格式、字段类型及缺省值。
2. 按实际服务的格式范围使用 415 或 406 等合法处理，不能为了兼容而静默吞掉所有媒体类型冲突。
3. 需要对时间、货币、数量、精度、枚举和二进制内容确定传输表示，不用 JavaScript Number、格式化字符串或 JSON 空值自动定义业务含义。
4. **验收**：错误 Content-Type、未知类型、显式 null、缺字段、编码不合法、未知枚举和精度边界得到明确的消费者行为。

### BE-004 核验合同

- **BE-004-P · 输入/动作与合格判据：** Accept/Content-Type/null/未知枚举/大金额→协商和精度明确。
- **BE-004-F · 直接失败变异：** 所有格式静默接收或JS Number损金额→失败。
- **BE-004-N · 合法邻例：** API只支持一种声明格式也合法。

## 五、HTTP 状态码与真实进度
1. 返回码必须真实反映 HTTP 操作：区分创建完成、受理但未完成、无内容、部分内容、条件缓存命中、业务错误和服务端故障。
2. 201、202、204、206、304 不可互换。尤其 202 Accepted 不表示异步任务已完成，304 适用于满足条件的缓存验证，不用于表示普通空列表。
3. 4xx 不总意味着无需修复的永久错误；5xx 或超时也不能证明原先状态变更未提交，客户端必须遵守实际恢复契约。
4. **验收**：为被使用的各状态码绑定可实际复现的服务端条件和客户端后续动作，不把全部结果隐藏在返回 JSON 的自定义 success 布尔中。

### BE-005 核验合同

- **BE-005-P · 输入/动作与合格判据：** 201/202/204/206/304实际条件→客户后续动作正确。
- **BE-005-F · 直接失败变异：** 202当完成或304当空列表→失败。
- **BE-005-N · 合法邻例：** HTTP层成功与异步业务待完成可同时成立。

## 六、输入、字段与领域状态校验
1. 将协议格式、Schema、领域不变量、权限、资源存在性和事务前提分别验证，不能只依赖前端表单或 API Gateway。
2. 400、409、412、422、428 等按它们真实语义和项目选定用法使用，不能用固定 HTTP 200 包住无法判断的错误类型。
3. 对文件、查询、头、正文与跨字段约束检查大小、重复、类型、合法范围和来源，避免无界计算和将内部异常泄漏给普通 API 消费者。
4. **验收**：合法差异、非法值、格式损坏、权限不足、旧版本与实际状态冲突都有可诊断的结果，拒绝时没有未授权写入。

### BE-006 核验合同

- **BE-006-P · 输入/动作与合格判据：** 坏Schema/非法范围/旧版本/无权限→拒绝无额外写。
- **BE-006-F · 直接失败变异：** 网关校验通过就略领域约束→失败。
- **BE-006-N · 合法邻例：** 合法不同业务值应保留而非统一默认。

## 七、RFC 9457 错误详情模型
1. 项目选择 Problem Details 时，定义稳定的 type URI、title、status、detail、instance 和必要的扩展字段，并明确哪些字段是机器判别依据。
2. 机器消费者不应依赖被本地化或易变的标题／详情文本；type 定义及扩展字段改变需经兼容审查。
3. 实际 HTTP 状态与错误正文协调，不以错误对象覆盖代理已经返回的真实状态。
4. 不公开调试堆栈、SQL、凭据、跨租户实例标识、敏感客户数据或内部路由。
5. **验收**：同一问题类型在多语言、多个服务及经代理转发后仍可识别、恢复，不把既有合法自定义错误格式强制立即替换为新格式。

### BE-007 核验合同

- **BE-007-P · 输入/动作与合格判据：** 同type不同语言经代理→机器识别稳定且HTTP状态不被正文覆盖。
- **BE-007-F · 直接失败变异：** 按title文案分支或泄SQL栈→失败。
- **BE-007-N · 合法邻例：** 未采用Problem Details的合法错误格式保留。

## 八、列表分页及遍历正确性
1. 依据数据变化频度、规模和消费者类型选择偏移、游标或快照；对实时变化数据明确稳定排序、去重、缺失及遍历一致性范围。
2. 若使用 Link 首部描述 next 等关系，按 RFC 8288 实现并核对调用者；游标不能跨用户、租户和已失效授权任意重放。
3. 列表总数、精确度、过滤范围与数据新鲜度应有明确承诺，不能从一页长度伪造全量数量。
4. **验收**：分页期间插入删除、同排序值、无权限条目、跨账号游标、末页、失效游标和上限页大小真实可处理。

### BE-008 核验合同

- **BE-008-P · 输入/动作与合格判据：** 同排序值/插删/末页/跨账号cursor→遍历契约与授权保持。
- **BE-008-F · 直接失败变异：** 一页长度冒全量、游标跨租户复用→失败。
- **BE-008-N · 合法邻例：** 仅承诺有限一致分页可明确而不装全局快照。

## 九、查询过滤、排序及字段选择
1. 允许的查询条件、类型、单位、排序方向、空值及默认行为由业务用途固定。
2. 客户端输入不自动成为内部 SQL 列名、搜索语法或 ORM 字段，必须有真实授权、资源成本及注入防护。
3. 字段投影、省略和聚合仍须保留消费者任务必需的数量、条件、来源与权限信息；缓存和索引的时效单独说明。
4. **验收**：组合筛选、长文本、边界数据、字符排序、隐藏字段、空结果和恶意昂贵查询不会泄漏或错误重释领域数据。

### BE-009 核验合同

- **BE-009-P · 输入/动作与合格判据：** 组合筛选/隐藏字段/昂贵查询→范围/成本/必要字段正确。
- **BE-009-F · 直接失败变异：** 外部字段直接拼SQL或投影省掉关键条件→失败。
- **BE-009-N · 合法邻例：** 有界合法过滤无需固定某种查询语言。

## 十、ETag、If-Match 与条件修改
1. 对会被多个用户修改的资源，结合实际持久状态采用 ETag/If-Match、版本条件或相应领域一致性机制，避免旧状态覆盖已完成写入。
2. 若 If-Match 先决条件不成立，按 RFC 9110 的语义使用 412 等符合实际的响应；如果接口要求条件请求但消费者没有提供，可采用 RFC 6585 的 428。
3. 409 用于实际领域冲突，不把它、412、428 混成同一种协议含义；响应要让有权用户知道如何刷新或重新提交。
4. 使用弱/强实体标签与 If-None-Match 时遵循相应方法的比较语义，不把前端视图的缓存标签视为数据库事务全局锁。
5. **验收**：两位编辑者并发修改、旧缓存、错版本和同一资源多种表示，不能静默丢失用户已批准的修改。

### BE-010 核验合同

- **BE-010-P · 输入/动作与合格判据：** 两个编辑者同旧ETag写→强比较在权威更新边界生效。
- **BE-010-F · 直接失败变异：** 只内存比较或弱标签承担If-Match强保护→失败。
- **BE-010-N · 合法邻例：** 不需要HTTP条件头的等价CAS可保护同一不变量。

## 十一、业务幂等键及未知提交
1. 对带副作用的 POST 等定义业务操作身份、租户作用域、请求指纹、键保留时间、处理中／完成／失败和重放行为。
2. 客户端无法得知提交结果时，服务端必须提供可核对的结果或安全恢复路径；不能把超时误当未提交并直接再次扣费或发送通知。
3. 同一键与不同载荷冲突、并发同键请求、键过期以及不同身份复用需要明确拒绝和查询契约，且在持久层或等价权威位置有可靠一致性保证。
4. IETF Idempotency-Key -08（2026-10-22，2027-04-25 到期）仍为 Internet-Draft，项目可借鉴但必须独立批准具体协议；不能暗示所有第三方自动认可同名头。
5. **验收**：成功后断线、重复请求、重复消费者、存储与队列局部失败均不产生未经批准的额外业务效果。

### BE-011 核验合同

**必要机制补充：** 逻辑意图ID在安全重试间保持不变，每次发送另分配尝试ID；事务ID、事件ID、投递ID和Trace ID不得代替它。权威查询暂未发现记录、读副本落后、日志缺失、客户端超时均不证明原尝试不会随后提交。只有目标端对同意图实行覆盖所有在途/迟到尝试的原子唯一性，或有已安装的栅栏/终止与线性化屏障证明原尝试不再可生效，才可依合同重发；否则保持结果未知并继续有权核对，不新建意图绕过去重。有限去重保留窗须覆盖目标最后可能接受该意图的时刻、重放和恢复窗口；不能只比较本地派发时间。窗外仍可迟到时使用永久领域唯一性、目标拒旧期限/世代或有权人工核对。

- **BE-011-P · 输入/动作与合格判据：** 同键同参并发/冲突参/提交丢响应→意图唯一且可查。
- **BE-011-F · 直接失败变异：** 查无记录就新键重发，而旧尝试仍能迟到提交→失败。
- **BE-011-N · 合法邻例：** 有效去重窗内同意图重传返回原收据。

## 十二、PATCH 与部分更新
1. 明确完整替换、部分字段变化、JSON Merge Patch、JSON Patch 和领域命令的差异；不能用“请求体只含部分字段”暗示自动符合具体补丁协议。
2. 如果使用 PATCH，依据 RFC 5789 和选定的补丁媒体类型执行，处理不合法路径、重复补丁、null 与缺失、数组变化及实际事务原子性。
3. 有版本竞争风险时与 If-Match/领域版本结合，失败前后确保没有半完成写入。
4. **验收**：旧版本、非法字段、重复应用和两个消费者并发修改时，业务状态要么有效完成，要么可恢复地拒绝。

### BE-012 核验合同

**必要机制补充：** PATCH对一个补丁文档的整组更改按RFC 5789应原子应用；不能应用失败后留下半个补丁，也不得把非幂等补丁无条件重复应用。

- **BE-012-P · 输入/动作与合格判据：** Merge/Patch不同null/数组/重复/并发→媒体类型和原子语义准确。
- **BE-012-F · 直接失败变异：** 半完成补丁失败仍留部分写→失败。
- **BE-012-N · 合法邻例：** 领域命令可不采用PATCH。

## 十三、HTTP 缓存、私有响应与条件验证
1. 根据 RFC 9111 定义新鲜度、响应可缓存性、验证器、Vary、共享及私有缓存，明确 no-cache 需要重验证与 no-store 限制缓存存储的不同语义。
2. 缓存键包括真实影响结果的租户、身份、权限、地区、语言、资源版本与查询条件；认证响应不应因为某个 CDN 默认值意外公开。
3. 旧 ETag、304、CDN/浏览器双层缓存和登录切换必须真实核验，缓存首部不能替代源服务鉴权。
4. **验收**：不同用户、权限撤销、历史缓存、缓存代理与敏感业务结果不会跨身份泄漏或过期伪成功。

### BE-013 核验合同

- **BE-013-P · 输入/动作与合格判据：** 真实代理/两个账号/撤权/304→缓存控制与表示身份正确。
- **BE-013-F · 直接失败变异：** no-cache当禁止存储或认证响应误公共共享→失败。
- **BE-013-N · 合法邻例：** 明确公开可缓存认证请求按RFC实际条件处理。

## 十四、异步 HTTP 任务与 202
1. 对提交后延迟完成的 API 定义任务身份、权限、状态查询、结果及错误、回收期、取消以及真实业务终态。
2. 202 代表受理，不代表交易完成、文件导入成功或第三方消息送达；后台队列 ACK 同样不是业务结果。
3. 轮询、SSE、回调或通知的重试、乱序、超时及任务重复需要与权威状态保持一致。
4. **验收**：后台重启、排队超时、重复任务和客户端断线后，可继续查询到真实成功、失败、部分完成或有权撤销的结果。

### BE-014 核验合同

- **BE-014-P · 输入/动作与合格判据：** 202后重启/取消/排队超期→任务ID可查成功/部分/未知。
- **BE-014-F · 直接失败变异：** 队列ACK冒文件导入完成→失败。
- **BE-014-N · 合法邻例：** 同步已完成动作可用正确2xx不强制异步任务。

## 十五、文件请求、下载与部分内容
1. 上传文件要验证大小、格式、内容类型、路径、编码、来源和访问权限；客户端扩展名仅是线索。
2. 对下载及媒体资源依据使用需求提供 Content-Type、Content-Disposition、Range、206 或 416 等合法语义，并遵守私有文件的缓存与鉴权要求。
3. 断开流或客户停止下载不代表此前已发生的业务写入自动撤销，必要时提供续传、校验和失败报告。
4. **验收**：超限上传、损坏分块、非法范围、跨用户资源、长文件名和中途断流处理正确且不泄漏隐私。

### BE-015 核验合同

- **BE-015-P · 输入/动作与合格判据：** 损坏/超限上传、Range/断流/跨用户下载→内容与授权可查。
- **BE-015-F · 直接失败变异：** 扩展名代扫描或传输进度代业务提交→失败。
- **BE-015-N · 合法邻例：** 不支持Range时按RFC可合法忽略并返回完整表示。

## 十六、API 身份、资源级权限与字段隔离
1. 用户认证、服务身份、角色权限、对象级操作许可、字段访问权及第三方再使用许可分别核对。
2. 不能只在浏览器界面隐藏菜单或仅根据 JWT 有效性就允许任意对象 ID 的读取、更新、导出与统计查询。
3. 401/403/404 的具体呈现要考虑调用方可知的信息与资源存在性泄漏风险，机器错误详情不能反向扩权。
4. **验收**：跨租户、管理接口直连、过期 Token、权限变更、批量查询及旧异步回调不会越权。

### BE-016 核验合同

- **BE-016-P · 输入/动作与合格判据：** 普通/管理/服务身份换对象与字段→每入口授权。
- **BE-016-F · 直接失败变异：** JWT有效即允许所有导出→失败。
- **BE-016-N · 合法邻例：** 为隐藏存在性可按合同对无权资源返回404。

## 十七、速率限制、429、Retry-After
1. 区分第三方平台速率、项目服务容量、用户套餐权益、账号预算和反滥用限制，分别建立有权配置的计数与恢复契约。
2. 如使用 429，按 RFC 6585 表达请求过多；Retry-After 遵循 RFC 9110 头部语法，不能随意将平台自定义配额头冒称通用标准。
3. 重试与退避还须满足业务幂等、真实副作用和配额要求，不用更换账户／身份绕过已发生的官方限流。
4. **验收**：并发配额、过期、上游限流、重试放大、用户退订及权限变化时能稳定拒绝和恢复。

### BE-017 核验合同

- **BE-017-P · 输入/动作与合格判据：** 并发预算/429/Retry-After/退订→有界恢复不绕平台限额。
- **BE-017-F · 直接失败变异：** 换账号绕限或5xx无限重试→失败。
- **BE-017-N · 合法邻例：** 明确安全读取可有限退避。

## 十八、浏览器跨源及代理请求上下文
1. 有浏览器消费者时按实际信任边界配置 CORS、Credentials、预检和 Cookie 策略；CORS 不等于服务端对象授权。
2. Gateway/反向代理转发的 Host、Forwarded、Origin、Proto 等标头需明确哪些来自受信任代理，不能让外部任意请求伪造内部来源。
3. Cookie 会话对 CSRF、SameSite、域范围与 CORS 的影响与 Web 安全领域联合验收；服务端到服务端的权限仍独立强制。
4. **验收**：恶意 Origin、非法凭据、代理路径重写及回调 Host 伪造不能绕过权限或暴露私有内容。

### BE-018 核验合同

- **BE-018-P · 输入/动作与合格判据：** 错Origin/Host/Forwarded经可信和不可信代理→来源边界保持。
- **BE-018-F · 直接失败变异：** 外部X-Forwarded-Proto升级信任→失败。
- **BE-018-N · 合法邻例：** 服务器到服务器无浏览器CORS强制。

## 十九、Webhook 与外部回调契约
1. 规定发送和接收角色、认证与签名来源、事件身份、重放窗口、ACK/重试、失败储存及字段版本。
2. 客户端收到 2xx 或 HTTP 请求完成不代表下游外部事件全部业务生效，必须有真实完成或待恢复状态。
3. 旧客户端、合作方接收地址与事件格式演进须按合同保留支持，权限和客户数据不能因为内部集成方便而超范围传播。
4. **验收**：伪造回调、签名轮换、重复投递、乱序、超时和已写入未返回确认时不造成二次费用或状态错乱。

### BE-019 核验合同

- **BE-019-P · 输入/动作与合格判据：** 签名轮换/乱序/重复/丢确认Webhook→身份和业务操作相关。
- **BE-019-F · 直接失败变异：** HTTP2xx当外部事件全生效→失败。
- **BE-019-N · 合法邻例：** 合法重复同事件应幂等接收而非一概攻击。

## 二十、版本策略、兼容窗口与消费者
1. 选择 URI、媒体类型、版本参数或其他机制需有真实旧客户端数量、渠道更新能力、服务约束及客户承诺的依据，不强制 /v1/ 路径模式。
2. 响应字段或类型、未知枚举、默认值、排序、权限、状态码和错误类型变化可能破坏既有消费者，即使 Schema Diff 显示仅新增字段。
3. 支持窗口内对真实消费者版本和新旧服务器组合做兼容性回归；未获得业务决定权时不得通过升级协议删减客户必需能力。
4. **验收**：旧 SDK、批处理、Webhooks、Agent/MCP 及长期在线客户端能安全使用或执行明确的迁移方案。

### BE-020 核验合同

- **BE-020-P · 输入/动作与合格判据：** 旧SDK/新服务/默认值变化→支持窗语义兼容。
- **BE-020-F · 直接失败变异：** Schema只新增即忽略权限/排序破坏→失败。
- **BE-020-N · 合法邻例：** 版本机制不必固定/v1路径。

## 二十一、Deprecation、Sunset 及停止服务
1. 正式废弃前确定具体受影响接口、旧消费者、替代能力、迁移期限、信息保真、需要通知的外部主体及对应批准权。
2. RFC 9745 Deprecation 是 Standards Track 的接口废弃响应头规范；RFC 8594 Sunset 属 Informational，表达预计停止可用的时间提示，不能承诺时间之前必然可用。
3. 弃用通知与文档完成不等于已完成替代实现或用户迁移；回滚、旧接口仍在线的风险必须有可核查方案。
4. **验收**：支持期内客户端可完成承诺任务，期满后按真实安全及业务条件返回可理解的状态与必要迁移入口。

### BE-021 核验合同

- **BE-021-P · 输入/动作与合格判据：** 弃用前旧客户端走替代路径→支持窗和下线提示有效。
- **BE-021-F · 直接失败变异：** Deprecation标头当立即停止或Sunset当可用保证→失败。
- **BE-021-N · 合法邻例：** 无外部消费者的内部变更可简化通知。

## 二十二、数据类型、精度与多语言 SDK
1. JSON 数值、日期与时区、货币精度、二进制编码、字符串规范化及枚举扩展均需定义真实传输语义。
2. 未知字段、缺字段、显式 null、可选变必填和未知枚举在各语言 SDK 中可能有不同处理方式，不允许凭 JavaScript 或某 ORM 的默认行为推断通用兼容。
3. 变更后端格式或 API 生成器时核验原业务金额、数量、权限与时间条件在所有受支持消费者中保持完整。
4. **验收**：跨语言 SDK、最大合法数量、精度边界、历史对象和新字段组合能一致解析或安全失败。

### BE-022 核验合同

- **BE-022-P · 输入/动作与合格判据：** 多语言SDK读最大数/null/缺失/未知枚举→值含义一致。
- **BE-022-F · 直接失败变异：** 各生成器默认零值吞原义→失败。
- **BE-022-N · 合法邻例：** 未知枚举可按合同安全拒绝而非默认成功。

## 二十三、代理解析与 HTTP 消息安全
1. 对多级网关的 URI、请求长度、重复头、编码、请求分帧和响应转换统一解析策略，避免前后端对同一请求得出不同身份和边界。
2. HTTP/1.1 解析、连接复用及 request smuggling/response splitting 的底层细则依据 RFC 9112 和网络／安全专项，不在此复制协议算法。
3. 不可信代理头不能升级为受信任的身份、租户或来源；错误响应与日志不能携带其他用户的私有数据。
4. **验收**：冲突消息长度、异常编码、恶意 Host、重复认证头与代理路径差异不会产生越权请求或资源混淆。

### BE-023 核验合同

- **BE-023-P · 输入/动作与合格判据：** 重复认证头/CL-TE/异常编码经多级代理→一致拒绝无越权。
- **BE-023-F · 直接失败变异：** 前后解析不同造成请求走私或任意Host回调→失败。
- **BE-023-N · 合法邻例：** 合法不同header大小写按协议等价。

## 二十四、OpenAPI 描述和生成客户端
1. 当实际使用 OpenAPI 时锁定 OAS 版本及可用工具，对请求/响应、参数、认证、错误、分页、上传和异步操作提供适合消费者的接口定义。
2. 源码实现、网关和生成 SDK 应与冻结的契约对应，不能只凭规范文件通过 Lint 就宣布实际 API 已实现。
3. 对无法由规范文件完整表达的外部回调、缓存、幂等语义、长期兼容或业务状态保留必要独立测试及文档。
4. **验收**：真实版本的 OpenAPI、生成客户端、服务实现、不同权限及典型错误和业务完成路径互相匹配。

### BE-024 核验合同

- **BE-024-P · 输入/动作与合格判据：** 冻结OpenAPI配生成SDK调真实服务→实现/权限/错误吻合。
- **BE-024-F · 直接失败变异：** Lint绿当事务与业务均通过→失败。
- **BE-024-N · 合法邻例：** 未采用OpenAPI不强制引入生成器。

## 二十五、追踪、审计与错误可观测性
1. 外部请求 ID、业务操作键、错误类型、内部 Trace 和数据库事务身份各有用途，不能混用以至于失去权限边界。
2. 对成功、被拒、已提交、已入队、已送达与已完成业务目标分别记录可查询证据；仅 HTTP 200/202 比例不能证明用户业务成功。
3. 关联信息按运维权限保留真实根因证据，错误体和日志链路中不输出密钥、完整私人请求或客户秘密。
4. **验收**：能从真实受权请求对应到接口版本、领域决策、响应及最终存储／下游结果，已知和未知状态准确标注。

### BE-025 核验合同

- **BE-025-P · 输入/动作与合格判据：** 业务键追到提交/入队/外部终点→阶段与受众权限明确。
- **BE-025-F · 直接失败变异：** Trace ID当幂等键或200率当履约率→失败。
- **BE-025-N · 合法邻例：** 诊断缺失仍能通过权威业务查询核对。

## 二十六、兼容、故障与端到端测试门禁
1. 按风险组合单元、Schema、协议合同、真实数据库、网关、身份、安全、缓存、并发、回调和端到端业务测试，不要求每个原型连接全部外部服务。
2. 对有历史消费者的 API 构造“客户端版本 × 服务版本 × 权限 × 合法业务条件”的代表性组合，保留旧行为的真正语义回归。
3. Mock、OpenAPI Lint 和测试生成器只能证明受测边界，不能代替真实支付、外部 Webhook、持久事务或客户可用性。
4. **验收**：失败和成功都能指向真实代码版本、输入、返回状态、运行环境与权威业务结果；不能靠删除失败旧用例虚构兼容。

### BE-026 核验合同

- **BE-026-P · 输入/动作与合格判据：** 旧新消费者×权限×故障真实回归→正确版本证据齐。
- **BE-026-F · 直接失败变异：** 删失败旧测试或Mock支付冒真实第三方通过→失败。
- **BE-026-N · 合法邻例：** 低风险无外部能力不强制连接全部平台。

## 二十七、静态验收场景矩阵
| 典型场景 | 主要验证机制 | 最低正确结果 |
| --- | --- | --- |
| 预取 GET 导致扣费 | 安全方法与领域规则 | 没有不被授权的交易副作用 |
| 相同 PUT 重试 | 协议幂等与数据版本 | 预期资源状态保持一致 |
| POST 成功后网络中断 | 幂等键、状态回读 | 无重复支付或订单 |
| 同幂等键对应不同载荷 | 请求指纹及身份范围 | 歧义被拒绝，不返回错误旧结果 |
| 两个用户编辑同一资源 | ETag、If-Match、412 | 无静默丢失更新 |
| 必需条件更新时缺请求前提 | 428 条件要求 | 正确拒绝并说明合法重试条件 |
| 缓存验证无内容变化 | If-None-Match、304 | HTTP 缓存语义正确 |
| 错误响应包含堆栈 | RFC 9457、信息最小化 | 仅合法错误类型及修正信息可见 |
| 不同语言解析 Problem Type | 机器类型与展示文案 | 不受本地化标题改变影响 |
| 新增未知枚举或变必填字段 | 旧客户端兼容性 | 在支持窗口安全使用或可迁移 |
| 分页过程中新增和删除记录 | 排序、游标及数据身份 | 符合已声明的重复与遗漏契约 |
| 跨租户重放分页游标 | 游标作用域与对象授权 | 拒绝越权及数据泄露 |
| 路径双重编码导致路由混淆 | URI 解码、代理和授权 | 实际资源一致且权限正确 |
| Content-Type 和 Accept 不匹配 | 内容协商、415／406 | 按已公布支持范围处理 |
| 货币精度被客户端 JSON 转换改变 | 精度与字段类型 | 原始合法数值含义不变 |
| 共享 CDN 缓存暴露私人 API 响应 | RFC 9111、Vary、Cache-Control | 租户和账号隔离有效 |
| no-cache 被误当 no-store | HTTP 缓存指令 | 存储与重新验证各自正确 |
| 202 被显示为订单已完成 | 受理和结果阶段 | 客户可查询真正完成状态 |
| 429 与带副作用重试并发 | 限流、Retry-After、幂等 | 无绕过配额和额外副作用 |
| Webhook 重复与伪造 | 来源签名、业务事件 ID | 越权拒绝且业务不重复 |
| 移动端旧 SDK 遇新版本 | 版本化契约 | 支持窗口内安全工作 |
| 废弃通知无有效替代入口 | RFC 9745 与迁移 | 提供真实完整且受权的迁移路径 |
| Sunset 期限已到仍有调用 | RFC 8594 与实际响应 | 提供与合同一致的退出行为 |
| 网关和应用对消息长度理解不同 | RFC 9112、请求走私 | 不存在请求边界越权 |
| 私有文件 Range 下载被截断 | 206／416 与对象权限 | 部分内容正确、无未经授权访问 |
| OpenAPI 合同绿色但真实接口不兼容 | Schema、生成 SDK、集成 E2E | 真实消费者请求及错误契约达标 |
## 二十八、批准与项目采用规则
本 L4 具体专题仅制定 HTTP API 的资源、方法、表示、错误、条件更新、缓存、消费者版本和对外兼容的工程约束。数据库事务、队列、服务身份与安全、RPC 流式传输等更深技术由相邻 L4 专项处理；Spring、Go、Node.js、Python 等具体框架／库与生成器版本由 L5 处理。
IETF 正式 RFC、BCP、Informational 文档、OpenAPI 版本和 Idempotency-Key Internet-Draft按实际权威级别引用，不重写协议条文；项目 L6 明确所需消费者、缓存、幂等、错误与兼容门禁。文本验收和行业规范引用均不构成制度生效，也不能证明真实 API、SDK、网关、缓存或用户业务结果已通过；具体项目按 L6 独立实施验证。
