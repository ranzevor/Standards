# L4 服务流量治理与故障隔离技术规范

**文档ID：** STD-L4-BACKEND-008　**版本：** 0.1.0　**状态：** adopted　**生效日期：** 2026-10-30

## 适用对象、权威依赖与版本

本规范适用于单体服务、边缘 Worker、API 服务、RPC 调用链、同步与异步任务、服务网关及多服务架构中实际需要的准入、限流、并发上限、超时、重试、背压、隔离、摘流、降级与恢复。根据服务风险和负载决定采用范围；不强制引入微服务、Service Mesh、集中配额或多区域集群。
现行依据：[L4 后端与分布式系统领域通用基线](007-后端与分布式系统领域通用基线--v0.1.0.md)（后端领域基线）、[L4 领域模型与服务边界技术规范](013-领域模型与服务边界技术规范--v0.1.0.md)（领域边界）、[L4 HTTP API、错误与兼容演进技术规范](001-HTTP-API、错误与兼容演进技术规范--v0.1.0.md)（HTTP API）、[L4 RPC、流式接口与长连接技术规范](002-RPC、流式接口与长连接技术规范--v0.1.0.md)（RPC）、[L4 服务身份、对象授权与 API 安全技术规范](009-服务身份、对象授权与-API-安全技术规范--v0.1.0.md)（身份授权）、[L4 事务隔离、并发与业务幂等技术规范](003-事务隔离、并发与业务幂等技术规范--v0.1.0.md)（事务并发）、[L4 消息事件与可靠交付技术规范](010-消息事件与可靠交付技术规范--v0.1.0.md)（消息）、[L4 分布式业务工作流与一致性技术规范](004-分布式业务工作流与一致性技术规范--v0.1.0.md)（工作流）、[L4 缓存、一致性与衍生查询状态技术规范](011-缓存、一致性与衍生查询状态技术规范--v0.1.0.md)（缓存）以及 L1—L3、现行跨项目执行规范。领域业务状态、访问授权、持久副作用和外部结算各由原有权威负责；本专项负责流量控制机制、故障隔离和组合策略的实际可验证边界。
## 正式协议、草案及产品实施资料
- [RFC 9110 HTTP Semantics §10.2.3、§15.6.4](https://www.rfc-editor.org/rfc/rfc9110.html)：IETF Standards Track（2022），Retry-After 与 503 语义；只约束实际采用 HTTP 的调用接口。
- [RFC 6585 §4 Too Many Requests](https://www.rfc-editor.org/rfc/rfc6585.html)：IETF Standards Track（2012），429 及可选 Retry-After；限额识别与计算策略不由该 RFC 统一规定。
- [draft-ietf-httpapi-ratelimit-headers-11](https://datatracker.ietf.org/doc/draft-ietf-httpapi-ratelimit-headers/)：2026-05 的 IETF Internet-Draft（2026-11-24 到期），RateLimit-Policy、RateLimit 仅为草案契约；**不是已生效的正式 RFC**，按实际目标实现与双方确认决定是否采用。
- [gRPC Deadlines](https://grpc.io/docs/guides/deadlines/)、[Retry](https://grpc.io/docs/guides/retry/)、[Request Hedging](https://grpc.io/docs/guides/request-hedging/)：gRPC 官方实现指南，Deadline、透明重试、策略重试与并发复制请求的实际功能按所用 SDK、方法和 Service Config 版本核实。
- [Envoy Circuit Breaking](https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/upstream/circuit_breaking)、[Outlier Detection](https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/upstream/outlier)、[Overload Manager](https://www.envoyproxy.io/docs/envoy/latest/configuration/operations/overload_manager/overload_manager)、[Global Rate Limiting](https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/other_features/global_rate_limiting)：Envoy 维护方动态产品文档；局部断路、异常节点摘除、网关自身过载保护及全局配额机制不可互相替代。
- [Kubernetes Liveness, Readiness and Startup Probes](https://kubernetes.io/docs/concepts/configuration/liveness-readiness-startup-probes/)：Kubernetes 产品机制指南；只有项目采用 K8s/等价平台时映射到实际部署，Probe 通过不构成业务完成证明。
- [AWS Builders' Library: Timeouts, Retries, and Backoff with Jitter](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/)：供应商工程经验与设计指南，不属于 IETF 规范或强制通用标准。
外部来源审查日期为 2026-10-14。IETF 标准与草案的发布效力、产品实施文档及厂商建议应分级使用。动态实现资料不可在未评估兼容与风险时改变 L5/L6 锁定版本或原业务责任。

## 核验口径与消费接口

维护者负责落实本文机制，领域/API/存储提供者负责其权威保证，验收者从实际受支持入口观察结果。输入固定源码/构建、配置、数据/协议版本、角色/租户、目标平台、故障时序和预算；权威观察对象为**根业务预算、准入承诺、资源/配额账、目标端已发生效果**。真实执行入口为**真实代理/服务压测、入站/各层尝试计数、排队年龄、外部限额及业务对账**。逐章 P/F/N 分别为正常输入及判据、破坏该机制的直接失败变异、应继续成立的合法邻例；本章原有每项规则、原有验收与新增合同共同约束，不用单一通用案例替代具体子项。每个子项须在案例输入中保留其适用条件，并以自身原文规定的输出/不变量判定；复合章应拆记录各个观察量，不能以一个成功掩盖其他失败。

证据产物包括真实命令/用户动作、原始响应或事件、权威状态前后值、版本、时序、失败及恢复；尚无对应真实运行证据的场景状态为 `not-run`，标准库示例仅证明列明的局部边界。具体输入与命令见[执行入口](../../../examples/web-backend/RUNBOOK.md)，条款索引见[规范条款登记](../../../registry/requirements.json)，来源的有限支持命题见[逐命题来源映射](../../../sources/web-backend/claims.json)。

本文的跨组件约束与正例、失败反例、合法邻例由本规范综合定义；外部来源支持的机制及适用边界见来源表。项目架构、预算和业务规则由实际需求确定。L5 实现应映射到所选框架、SDK 或引擎；L6 按具体版本的提供者保证与受支持矩阵验收项目能力。

## 一、流量治理必要性与业务服务目标
1. 按真实流量尖峰、请求延迟、失败代价、资源消耗和第三方合同，选择直接扩容、边界限流、并发预算、排队、隔离或故障降级；单体低负载系统不强制引入网格、全局限流服务或独立服务发现组件。
2. 为每条业务路径区分允许拒绝、允许排队、禁止丢失、可重新请求和必须保存权威操作结果；明确控制范围、边际成本和故障时负责的主体。
3. **验收**：对正常、突发、下游慢及第三方配额耗尽分别给出需求所允许的处理模式与可核查的用户结果。

### BE-001 核验合同

- **BE-001-P · 输入/动作与合格判据：** 正常/突发/慢依赖/配额耗尽→拒绝/排队/承诺边界明确。
- **BE-001-F · 直接失败变异：** 单体低负载强装Mesh却漏业务恢复→失败。
- **BE-001-N · 合法邻例：** 足够的简单并发限额可成立。

## 二、入口、代理及端到端流量拓扑
1. 绘制浏览器/API/MCP/批任务到边缘入口、WAF、CDN、Gateway、负载均衡器、Service/Worker、RPC、Broker 及第三方接口的真实请求与异步执行链。
2. 每个跳点记录终止 TLS、转发身份、限额、超时、重试、缓冲、连接池、故障域、路由回退及响应来源；不能只在网关设置保护而忽略服务内部任务或直连入口。
3. **验收**：绕过一层代理、不同协议入口及直接内部调用时，流控和授权边界一致且无未授权写入。

### BE-002 核验合同

- **BE-002-P · 输入/动作与合格判据：** 入口经各代理到异步/第三方并直连服务→每跳策略与信任可查。
- **BE-002-F · 直接失败变异：** 只网关限额内部入口绕过→失败。
- **BE-002-N · 合法邻例：** 实际无代理路径可简化拓扑。

## 三、请求性质、优先级与不可损失业务
1. 区分幂等只读、可幂等变更、非幂等外部副作用、交易确认、通知、上传、长连接和异步履约；对拒绝和重试的合法条件分别定义。
2. 不得按用户体验性能优先级直接丢弃已经正式接受的订单、资金、权益或客户履约责任；非关键流量可以受控丢弃但必须符合已批准的产品合同。
3. **验收**：对一个普通查询与一个已经受理的资金处理任务施加相同拥塞，仍能识别任务承诺和可恢复状态。

### BE-003 核验合同

- **BE-003-P · 输入/动作与合格判据：** 普通读与已受理订单同拥塞→可丢与欠履约分开。
- **BE-003-F · 直接失败变异：** 丢掉持久承诺订单换低延迟→失败。
- **BE-003-N · 合法邻例：** 非关键遥测可按合同丢弃。

## 四、准入控制及受理阶段证据
1. 在执行高成本工作前根据输入合法性、身份／业务权限、预算、并发和容量控制准入；分别记录被拒、被排队、已受理、已完成，不混用 HTTP 接收和业务持久提交。
2. 在边缘、服务和异步入口明确谁有最终准入决定权；受理后的失败必须能回读、重驱动或依法恢复，不能静默转换成拒绝；拒绝前不得提前扣费或产生越权副作用。
3. **验收**：流量达到控制阈值时拒绝和正式接受具有可区分的证据，重复调用不能产生额外真实交易。

### BE-004 核验合同

- **BE-004-P · 输入/动作与合格判据：** 阈值前后重复请求→拒/排队/持久受理可区别。
- **BE-004-F · 直接失败变异：** 准入前扣费或受理失败悄改拒绝→失败。
- **BE-004-N · 合法邻例：** 纯读取可无持久受理账本。

## 五、并发上限、资源预算与动态容量
1. 把 CPU、内存、线程、数据库连接、文件描述符、HTTP/2 Streams、排队容量与外部并发配额分离为可测量资源；并发数、请求速率与业务吞吐不是同一单位。
2. 基于目标延迟、服务耗时、热点程度和真实瓶颈分配每实例与共享资源预算；扩容不自动增加数据库容量或第三方额度，不用无界协程／队列掩盖过载。
3. **验收**：通过慢依赖、进程高并发和连接池耗尽的目标负载，检查预算确实限制在资源保护范围。

### BE-005 核验合同

- **BE-005-P · 输入/动作与合格判据：** 慢依赖耗池→各实例与共享资源上限生效。
- **BE-005-F · 直接失败变异：** 无界协程/队列掩盖过载→失败。
- **BE-005-N · 合法邻例：** 扩副本仅能增加其实际独立容量。

## 六、本地与全局速率限制的选择
1. 区分单实例令牌桶、滑动窗口等局部算法和跨副本共享额度；根据实际需求选本地粗粒度拦截、集中全局配额、分布式租约或分级组合。
2. 明确窗口、突发能力、租户／主体／API 方法作用域、配额一致性与故障时的允许偏差；多实例本地限流不能声称自动满足全局统一额度。
3. **验收**：添加节点、分区与突发请求后仍符合约定总速率或显式误差容忍范围。

### BE-006 核验合同

- **BE-006-P · 输入/动作与合格判据：** 扩副本/分区/突发→全局限额或显式误差被遵守。
- **BE-006-F · 直接失败变异：** 每实例100就声称全局100→失败。
- **BE-006-N · 合法邻例：** 局部粗限流可明确不承担全局严格配额。

## 七、HTTP 过载响应与重试提示
1. 按 RFC 6585 §4 表达 429；按 RFC 9110 §15.6.4 和 §10.2.3 表达 503 与 Retry-After，区分恶意／无权访问、请求无效、资源满及暂时服务不可用。
2. 明确限额响应的当前条件、重新尝试窗口和项目协议；IETF RateLimit 字段在 2026-10-14 仍处于 draft-ietf-httpapi-ratelimit-headers 草案阶段，不作为已发布正式 RFC 的通用保证。旧 X-RateLimit-\* 仅依真实供应商合同。
3. **验收**：429、503、有效与无效 Retry-After、客户端重试及中间缓存行为分别通过真实 HTTP 合同测试。

### BE-007 核验合同

- **BE-007-P · 输入/动作与合格判据：** 429/503及合法/非法Retry-After→分类与客户端恢复正确。
- **BE-007-F · 直接失败变异：** 草案RateLimit字段冒普遍正式协议保证→失败。
- **BE-007-N · 合法邻例：** 厂商自定义头仅按其真实合同。

## 八、租户、用户、操作与共享配额公平性
1. 区分匿名访问、已授权用户、租户、业务团队、组织及上游外部账户的配额，界定单个用户与共享租户是否消耗同一资源预算及费用。
2. 避免以可伪造 IP、客户端 Header 或单一 Gateway 身份替代真实租户／操作授权；多租户高基数键需限内存与拒绝规避配额的多身份拆分。
3. **验收**：恶意热点租户不能耗尽其他合法租户的已承诺容量，管理员和后台批任务也受相应预算。

### BE-008 核验合同

- **BE-008-P · 输入/动作与合格判据：** 热点租户/后台任务/伪IP→公平预算基于可信主体。
- **BE-008-F · 直接失败变异：** 可伪Header切身份绕共享额度→失败。
- **BE-008-N · 合法邻例：** 同租户共享配额可按明确合同。

## 九、负载丢弃、过载保护与恢复门槛
1. 按实际资源压力对新请求采用受控拒绝、并发削减、暂时降低非关键功能成本或停止接受连接；区分请求限流和 Envoy 等产品的 Overload Manager。
2. 过载阈值需有进入、退出条件和滞后防抖；不得在负载短时波动中不断开闭，也不得通过丢弃已接受并持久承诺的订单冒充负载治理成功。
3. **验收**：CPU、内存和连接压力逐渐上升及恢复时不出现抖动放大、非法业务丢失或长期自封锁。

### BE-009 核验合同

- **BE-009-P · 输入/动作与合格判据：** 压力上升后恢复→进入/退出阈值与滞后防抖。
- **BE-009-F · 直接失败变异：** 短波动反复开闭或丢已承诺业务→失败。
- **BE-009-N · 合法邻例：** 非关键功能可经允许brownout。

## 十、有界排队、排队期限与饥饿控制
1. 区分到达率、最大排队长度、每类优先级、预计等待、最晚可执行时刻和队列实际持久性；请求排队超过业务期限时应拒绝或转可恢复异步受理。
2. 普通内存排队不提供持久任务交付；排队指标不能只看长度，要检查等待年龄、长期饥饿、排队的上下文失效和调度公平性。
3. **验收**：输入负载长期超过处理能力时不会无限占用内存，超时排队任务不在取消后非法履约。

### BE-010 核验合同

- **BE-010-P · 输入/动作与合格判据：** 持续输入大于处理能力→队长/等待年龄有界不饿死。
- **BE-010-F · 直接失败变异：** 只看长度、取消后过期任务仍履约→失败。
- **BE-010-N · 合法邻例：** 持久异步受理可有不同等待合同。

## 十一、异步任务入口的削峰与接线
1. 对后台异步负载，明确生产者、Broker、消费者与资源瓶颈之间的准入、背压和持久受理位置；复用消息候选专项处理确认、死信、重投和 Outbox。
2. 缩放消费者不能无上限打爆下游；已有持久受理记录不可随队列满而消失；消息积压及实际业务截止时间必须分别管理。
3. **验收**：Broker 突然积压、消费者扩容、生产者断线、恢复重放和重复消息时，正式受理任务不丢、不重复副作用。

### BE-011 核验合同

- **BE-011-P · 输入/动作与合格判据：** Broker积压/扩消费者/下游慢→背压和已受理任务可恢复。
- **BE-011-F · 直接失败变异：** 扩消费者打爆外部配额→失败。
- **BE-011-N · 合法邻例：** 小负载可不设独立削峰队列。

## 十二、端到端期限预算和多跳传播
1. 每条同步调用链先确认从用户入口到业务确认的预算，按网关排队、连接、RPC 执行、依赖时间和响应保留合理余量。
2. 使用 gRPC 时依据实际语言 SDK 配置 Deadline、传播与取消；不能各跳都重新给满额 Timeout 导致总耗时倍增，时钟偏差优先以剩余持续时间处理。
3. **验收**：三跳慢链路、已有排队耗时和重试叠加时不超过已承诺的总体响应预算。

### BE-012 核验合同

- **BE-012-P · 输入/动作与合格判据：** 三跳且首跳已排队→剩余期限递减并留响应余量。
- **BE-012-F · 直接失败变异：** 每层timeout重置总时间→失败。
- **BE-012-N · 合法邻例：** 不同步业务保留期可独立于请求时限。

## 十三、连接、读写、空闲与总体超时
1. 分别定义 DNS/连接/TLS 建立、连接池等待、首字节、读写空闲、整次请求和整组尝试的时限；长连接心跳和服务健康检查不是业务完成凭证。
2. 区分硬性 Deadline 与暂时网络失联；避免只设置 Socket Timeout 而遗漏 DNS 或队列等待；流式连接不能误套普通短请求的整体期限。
3. **验收**：慢 DNS、半开连接、延迟响应体、读空闲与流式正常运行均能按各自契约恢复或停止。

### BE-013 核验合同

- **BE-013-P · 输入/动作与合格判据：** DNS/TLS/池等待/读空闲分别拖慢→各时限可观察。
- **BE-013-F · 直接失败变异：** Socket timeout漏掉DNS和排队→失败。
- **BE-013-N · 合法邻例：** 正常长流可有独立空闲而非短总期限。

## 十四、取消传播与已经产生的副作用
1. 取消仅能终止可中断的进一步计算或等待；已提交本地事务、已发送外部资金指令和已被下游接受的持久任务不会因取消自动回滚。
2. 发送取消前记录调用的业务操作键，必要时做结果回读、幂等续作或合同允许的补偿；多层代理断开和客户端超时不能覆盖真实外部成功。
3. **验收**：用户断连、Deadline 到期和下游提交同时发生时，结果仍有权威可查询的已完成、未知或待恢复状态。

### BE-014 核验合同

**必要机制补充：** 逻辑意图ID在安全重试间保持不变，每次发送另分配尝试ID；事务ID、事件ID、投递ID和Trace ID不得代替它。权威查询暂未发现记录、读副本落后、日志缺失、客户端超时均不证明原尝试不会随后提交。只有目标端对同意图实行覆盖所有在途/迟到尝试的原子唯一性，或有已安装的栅栏/终止与线性化屏障证明原尝试不再可生效，才可依合同重发；否则保持结果未知并继续有权核对，不新建意图绕过去重。有限去重保留窗须覆盖目标最后可能接受该意图的时刻、重放和恢复窗口；不能只比较本地派发时间。窗外仍可迟到时使用永久领域唯一性、目标拒旧期限/世代或有权人工核对。

- **BE-014-P · 输入/动作与合格判据：** 取消与提交同时发生→未知/提交结果可查。
- **BE-014-F · 直接失败变异：** 连接断开自动宣称远端撤销→失败。
- **BE-014-N · 合法邻例：** 可中断计算可及时释放资源。

## 十五、失败分类与重试合法性
1. 区分连接建立失败、明确未被服务器处理、已处理但响应未知、限流、业务拒绝、授权失败、协议不兼容及不可逆事务；只对明确允许且安全的情形重试。
2. 重试需要业务幂等身份、目标授权重新判断、可查询结果和合同条件，不能仅以状态码或 SDK 默认策略判定同一资金指令可重复执行。
3. **验收**：500/503/429、授权撤销、付款请求已到达后回执丢失分别产生不同重试或核对动作。

### BE-015 核验合同

- **BE-015-P · 输入/动作与合格判据：** 500/503/429/撤权/回执丢失→只允许安全重试。
- **BE-015-F · 直接失败变异：** 所有错误码统一重发付款→失败。
- **BE-015-N · 合法邻例：** 明确未到执行逻辑的失败可有限再试。

## 十六、跨层重试预算与指数放大控制
1. 控制客户端、网关、服务 SDK、RPC、代理和 Broker 的重试嵌套；为实际单个业务操作设置跨层总尝试数、累计执行时间和额外上游负载预算。
2. 禁止每层按自己的尝试数无限乘法放大；已配置透传自动重试的产品也须核对实际版本行为与禁用方法，预算耗尽必须保留真实未完成结果。
3. **验收**：模拟三层同时重试、服务恢复、反复 503 的依赖场景，验证总发送量及对第三方计费调用处于预算内。

### BE-016 核验合同

**必要机制补充：** 根业务操作预算由各实际重试层消费，恢复/改节点不能重置根尝试数、累计时长和费用；预算耗尽保留未知或待恢复事实，不伪造未发生。

- **BE-016-P · 输入/动作与合格判据：** 客户端/网关/SDK三层重试→根业务尝试与成本有总预算。
- **BE-016-F · 直接失败变异：** 3层各3次形成27次而无根上限→失败。
- **BE-016-N · 合法邻例：** 单层承担重试其余透传可简化。

## 十七、退避、抖动与服务端 Pushback
1. 可重试故障应使用有限、随机化的退避和总截止时间；HTTP Retry-After 在适用时应优先与客户端自身预算协调，gRPC Server Pushback 按具体产品支持实现。
2. 不会把服务器允许的最早重试时间误解为可以绕过整体业务截止；绝对时间与相对延迟转换考虑时钟差和链路等待。
3. **验收**：千客户端同时被限流后的恢复窗口不形成同步重试洪峰，早到、过期和负 Pushback 正确处理。

### BE-017 核验合同

- **BE-017-P · 输入/动作与合格判据：** 千客户端限流后恢复/负pushback→有界抖动不早于允许且不越deadline。
- **BE-017-F · 直接失败变异：** Retry-After当可以延长原授权期限→失败。
- **BE-017-N · 合法邻例：** 明确无重试提示仍可按允许策略退避。

## 十八、请求 Hedging 与重复副作用
1. 只有高尾延迟、高可重试安全性且实际后端容量充足时可采用 Hedging；配置启动间隔、总尝试数、截止时间、抑制预算和取消策略。
2. 取消迟到的另一次尝试不保证外部写入未执行；非幂等命令、付款和发货禁止未经业务保护就使用并发复制请求。
3. **验收**：多副本竞速、首个响应超时、两份请求都已到达处理逻辑时不发生重复有害副作用。

### BE-018 核验合同

- **BE-018-P · 输入/动作与合格判据：** 竞速两副本均到处理层→只允许安全幂等意图。
- **BE-018-F · 直接失败变异：** 取消慢尝试就断言其未付款→失败。
- **BE-018-N · 合法邻例：** 独立只读hedging可在预算允许时采用。

## 十九、舱壁隔离、共享池与高优先级保留
1. 为实际冲突资源建立请求类、租户或依赖维度的独立连接池、执行池、并发信号量和排队边界；共享资源可用容量须同时受总池限制。
2. 单个慢依赖或热点租户耗尽某个局部池后，不应拖垮无关关键业务；隔离策略避免资源碎片化导致正常负载利用不足。
3. **验收**：慢报告任务与正常订单处理并发时，后者仍保持项目目标且前者受控拒绝。

### BE-019 核验合同

- **BE-019-P · 输入/动作与合格判据：** 慢报表与订单共享池→关键资源保留且总容量不超。
- **BE-019-F · 直接失败变异：** 局部池预算相加超过共享DB上限→失败。
- **BE-019-N · 合法邻例：** 不冲突小服务可共用有界池。

## 二十、熔断器状态、阈值与恢复
1. 对目标依赖定义 Closed/Open/Half-Open 或选用平台等价状态、错误窗口、触发条件、冷却与探测许可；失败阈值应区分业务拒绝与服务故障。
2. 半开探测必须限并发，恢复判定要有成功样本及防抖；断路时提供与真实副作用状态一致的可恢复响应，不用业务退款或权限拒绝反向触发熔断。
3. **验收**：故障、恢复、业务 4xx 与偶发网络波动组合下，熔断能隔离且不会永久锁死或误隔离全部目标。

### BE-020 核验合同

**必要机制补充：** 通用Closed/Open/Half-Open是可选应用策略，不等同Envoy按资源计数的circuit breaking；Envoy各限制及每主机保留连接等例外须按所用版本核实际边界，不能无条件当严格全局连接硬上限。

- **BE-020-P · 输入/动作与合格判据：** Closed/Open/Half-Open与业务4xx交错→限探测且恢复不抖。
- **BE-020-F · 直接失败变异：** 权限拒绝都触发熔断或半开无限并发→失败。
- **BE-020-N · 合法邻例：** 产品等价状态模型可不用同名三态。

## 二十一、被动健康与异常实例摘除
1. 按负载均衡后端统计网络失败、真实上游 5xx、延迟与样本门槛，使用 Envoy Outlier Detection 等产品能力识别异常实例。
2. 区分本地网络错误与业务请求失败；摘除比例、持续时间、恢复探测和最低健康节点必须防止所有实例被误踢，避免小样本造成错误排除。
3. **验收**：一个后端间歇性超时、另一个长期 4xx 业务拒绝、全部节点压力增大时，实例选择与恢复符合声明规则。

### BE-021 核验合同

- **BE-021-P · 输入/动作与合格判据：** 异常一个节点/低样本/全体过载→摘除上限和恢复正确。
- **BE-021-F · 直接失败变异：** 小样本踢光所有节点或把业务拒绝当网络故障→失败。
- **BE-021-N · 合法邻例：** 明确受控零健康时可安全拒绝。

## 二十二、启动、存活、就绪与业务能力探测
1. 区分容器存活、可接收新流量、已启动完成、具体业务能力和客户实际履约；Kubernetes Liveness、Readiness、Startup 或等价机制各自承担不同职责。
2. 避免把暂时过载或下游不可用直接作为重启理由形成级联雪崩；就绪探测应根据合法接流条件改变路由，而不借此掩盖永久业务缺陷。
3. **验收**：慢启动、缓存预热、数据库不可用、业务功能故障时探针及路由准确表达对应状态。

### BE-022 核验合同

- **BE-022-P · 输入/动作与合格判据：** 慢启动/依赖失败/业务坏→startup/liveness/readiness职责分明。
- **BE-022-F · 直接失败变异：** 下游慢触发全体重启雪崩→失败。
- **BE-022-N · 合法邻例：** 不采用K8s可实现等价探测。

## 二十三、负载均衡策略、热点与会话亲和
1. 基于调用耗时、连接成本、状态性及局部热点，选择实际支持的轮询、最少请求、权重、哈希或同类策略；不能把平均 QPS 等分当所有副本负载均衡。
2. 会话粘滞不得代替共享持久业务状态和权限；伸缩、失效或替换副本时必须能恢复合法用户状态。
3. **验收**：节点负载不均、热键、延迟异常、扩缩容和旧连接共存时请求分配不违反业务隔离。

### BE-023 核验合同

- **BE-023-P · 输入/动作与合格判据：** 热键/长连接/扩缩容→真实负载分配及持久状态正确。
- **BE-023-F · 直接失败变异：** 平均QPS等分当负载平衡或粘性代持久数据→失败。
- **BE-023-N · 合法邻例：** 无状态请求可无粘性。

## 二十四、服务发现、端点收敛与故障转移
1. 明确 DNS、注册发现、Endpoint 管理、健康状态与实际调用缓存的更新时间和所有权；排除目标后旧连接可能仍然存在。
2. 不能单靠 DNS TTL 认定已收敛，需在实际传输层处理长连接和过期端点；零健康节点情况下应安全失败而非随机路由到未经授权服务。
3. **验收**：目标下线、解析失败、端点更新与复活旧 IP 时不会向错租户或旧环境发送业务数据。

### BE-024 核验合同

- **BE-024-P · 输入/动作与合格判据：** 端点下线但旧连接尚在/旧IP复活→实际路由收敛可查。
- **BE-024-F · 直接失败变异：** DNS TTL到期当所有连接已切换→失败。
- **BE-024-N · 合法邻例：** 无健康节点可安全拒绝不随机选错服务。

## 二十五、跨区域路由、恢复和外部系统限额
1. 多区域系统定义合法写主、故障转移门槛、数据版本和区域配额关系；跨区 fallback 前必须校验目标拥有的业务读取和写入权限。
2. 流量切换不等于状态同步或外部结算完成；双活/单活切换后旧地区恢复需防止未授权双写以及重放过期操作。
3. **验收**：区域故障、DNS 未收敛、备用区容量不足和旧区回归时关键域状态无非法冲突。

### BE-025 核验合同

- **BE-025-P · 输入/动作与合格判据：** 区切换/容量不足/旧区恢复→写主/权限/状态不双写。
- **BE-025-F · 直接失败变异：** 切流即称数据同步或旧区仍可写→失败。
- **BE-025-N · 合法邻例：** 单区服务不强制多区成本。

## 二十六、连接池复用、协议多路复用与资源释放
1. 连接数、HTTP/2 并发流、HTTP/3 连接以及代理到上游的连接池分别计量；客户端短请求与长连接需不同资源约束。
2. 正确处理连接空闲、GOAWAY、半关闭、重连暴增与资源泄漏；增大连接池可能降低数据库可用性，不能无条件用高并发来修复堵塞。
3. **验收**：连接池耗尽、服务端主动关闭、网络抖动后无连接泄漏或重连风暴。

### BE-026 核验合同

- **BE-026-P · 输入/动作与合格判据：** 池耗尽/GOAWAY/半关闭/重连→连接与流数分开且无泄漏。
- **BE-026-F · 直接失败变异：** 扩大池无上限压垮DB→失败。
- **BE-026-N · 合法邻例：** 短请求和长流可使用不同有界池。

## 二十七、流式背压与慢消费者资源管理
1. 对 SSE、WebSocket、gRPC Streaming 和类似实时推送明确生产速率、缓冲上限、流级/连接级流控、取消及慢消费策略；协议流控遵从 RPC 候选专项。
2. 高频推送不因一个慢消费者无限增长内存；不能把丢帧策略用于必须持久交付的付款回执或订单状态事实。
3. **验收**：慢读取、断线、重连和重放中资源有界且关键业务信息不被非法合并或丢失。

### BE-027 核验合同

- **BE-027-P · 输入/动作与合格判据：** 慢消费者/恢复重放→缓冲有界且关键事实不丢。
- **BE-027-F · 直接失败变异：** 丢帧策略用于付款回执→失败。
- **BE-027-N · 合法邻例：** 非关键视觉采样可合并。

## 二十八、边缘网关、Mesh 与应用策略叠加
1. 列出 WAF、CDN、Gateway、Service Mesh、负载均衡、应用与 SDK 实际生效的限额、重试、Timeout、熔断、认证和请求转发顺序。
2. 重复策略需要共同预算和真实测试；透传 X-Forwarded-\*、Retry-After、错误码和对象身份时按边界验证，入口成功不自动证明内部授权或业务完成。
3. **验收**：同一请求在各层走正常、超时、回退与失败分支时，流量放大与数据权限可追溯。

### BE-028 核验合同

- **BE-028-P · 输入/动作与合格判据：** 多层WAF/Mesh/应用超时重试→共同预算与错误来源可查。
- **BE-028-F · 直接失败变异：** 代理成功冒内部授权或嵌套指数放大→失败。
- **BE-028-N · 合法邻例：** 无重叠策略可保持简单透传。

## 二十九、降级能力、Brownout 和安全回退
1. 按有效需求决定在故障时可跳过的推荐、统计、非核心装饰和可延期通知；必须保存权威交易、授权、安全检查及关键字段。
2. 降级须有触发、恢复、最大持续时间、用户可执行的当前操作和实测结果；不能用旧缓存、默认成功、匿名越权或静默删减核心功能换取表面可用。
3. **验收**：推荐服务不可用时核心交易正确执行；身份服务不可用时拒绝危险越权操作而不伪造已授权。

### BE-029 核验合同

- **BE-029-P · 输入/动作与合格判据：** 推荐坏/身份坏分别降级→仅获允许的非核心能力削减。
- **BE-029-F · 直接失败变异：** 匿名默认成功或旧权限保活交易→失败。
- **BE-029-N · 合法邻例：** 非关键装饰可暂时关闭。

## 三十、第三方 API、供应商配额与付费预算
1. 第三方服务按真实账户、租户、端点、时窗和计费单元设置调用限额；本地并发限额不表示供应商一定准入。
2. 供应商临时 429/503、未知提交和永拒需要不同恢复；费用预算与幂等操作身份共同限制重试、Hedging、缓存回源和批处理放大。
3. **验收**：第三方持续限流、响应丢失与恢复后，未重复购买或重复付款且账单成本处于约定预算。

### BE-030 核验合同

- **BE-030-P · 输入/动作与合格判据：** 第三方持续限流/未知提交→根预算和目标幂等共同限制。
- **BE-030-F · 直接失败变异：** 换账号绕限或恢复后重复购买→失败。
- **BE-030-N · 合法邻例：** 无收费依赖可只计实际资源预算。

## 三十一、过载保护、滥用防护与安全授权界限
1. 流量治理控制资源供给和公平性，业务身份与对象授权由安全专项决定；WAF、DDoS 防御及攻击检测归安全／基础设施领域，按需共同实施。
2. 不得因拥有未用完的配额推断对资源有访问权；拒绝异常流量时对真实正常请求的错误分类和隐私日志保留应受安全规则限制。
3. **验收**：非授权客户端即使通过限流也不得读写受保护对象，正常客户不被恶意客户端通过伪造 Header 耗尽额度。

### BE-031 核验合同

- **BE-031-P · 输入/动作与合格判据：** 无权请求有剩余额度→仍拒对象操作。
- **BE-031-F · 直接失败变异：** 通过限流即视为有权→失败。
- **BE-031-N · 合法邻例：** 合法正常客户不因可伪造身份被恶意耗额。

## 三十二、动态策略、生效版本与变更保护
1. 每份策略记录目标入口、规则版本、阈值来源、适用租户和时间、决策人、发布范围与退回版本；多层配置联动需按实际生效顺序核实。
2. 动态热修改与短时开关可在授权运维范围内执行，但不得越权放宽客户付费权益或防护要求；避免灰度版本不同引发全局配额计算错误。
3. **验收**：同时运行新旧代理配置与限流规则，分流、回滚后业务合同和成本不产生未批准差异。

### BE-032 核验合同

- **BE-032-P · 输入/动作与合格判据：** 混跑新旧策略/回滚→实际生效版和全局计数正确。
- **BE-032-F · 直接失败变异：** 热更新悄改客户权益/价格→失败。
- **BE-032-N · 合法邻例：** 已授权运维范围可动态调资源阈值。

## 三十三、滚动发布、节点摘流与优雅关闭
1. 下线服务前先停止接受新请求，再按实际连接和业务时间预算完成或交接现有工作，长连接要有协议化的关闭与恢复语义。
2. Pod readiness、LB 摘流、连接 GOAWAY、任务租约与客户端重试存在独立时间窗；不能在收到 SIGTERM 后立即丢掉已接受且需要恢复的工作。
3. **验收**：滚动发布、实例被终止、旧客户端仍连接时无非法业务遗漏、重复提交或永久断链。

### BE-033 核验合同

- **BE-033-P · 输入/动作与合格判据：** 摘流/长连接/SIGTERM/任务交接→受理工作完成或耐久转交。
- **BE-033-F · 直接失败变异：** readiness变false即认为旧连接全停→失败。
- **BE-033-N · 合法邻例：** 可中断只读请求可明确重试。

## 三十四、过载、拒绝与业务结果的可观测证据
1. 区分入口拒绝、路由失败、熔断、排队超时、依赖错误、业务提交、外部受理及用户最终结果；实际日志和指标应在授权范围内关联这些阶段。
2. 监测每类限额耗尽、队列最长等待、In-Flight、错误来源、重试放大倍数、熔断状态和实例摘除率，不能以成功响应数量或进程存活证明交易完成。
3. **验收**：给定具体业务请求可区分 HTTP 429、上游 503、调用方超时和已提交结果，并找到相应权威证据。

### BE-034 核验合同

- **BE-034-P · 输入/动作与合格判据：** 具体请求429/503/超时但已提交→阶段证据正确。
- **BE-034-F · 直接失败变异：** HTTP成功率当真实业务完成率→失败。
- **BE-034-N · 合法邻例：** 最小有权业务关联可不记录敏感正文。

## 三十五、延迟、吞吐、公平性和资源验收
1. 在用户确定的 SLO、负载曲线、数据规模及资金/外部 API 单位成本下评估入站 QPS、有效业务吞吐、P95/P99、并发、拒绝与恢复时间。
2. 成本和性能目标不可代替业务正确性；不将任意厂商默认阈值写成跨项目强制数值，通用可观测性与容量建模由后续 L4 专项独立深化。
3. **验收**：正常、峰值、长尾、恶意热点与供应商配额变化情况下，关键成功率、权限隔离、延迟与成本有真实可复核数据。

### BE-035 核验合同

- **BE-035-P · 输入/动作与合格判据：** 峰值/恶意热租户/配额变化→尾延迟/公平/费用/正确性同时测。
- **BE-035-F · 直接失败变异：** 厂商默认阈值当全项目统一预算→失败。
- **BE-035-N · 合法邻例：** 低流量可用相称受控负载。

## 三十六、故障注入与级联放大专项检查
1. 建立连接超时、包丢、慢响应、半开、反复限流、实例摘除、服务发现失效、CPU/内存压力和区域切换的受控故障矩阵；预期应是完整业务链正确性。
2. 单元、合同、代理集成、真实服务 E2E 分开运行；假数据、模拟器只能证明覆盖对应分支，不证明生产等价故障恢复。
3. **验收**：对每个关键失效输入记录环境、策略版本、异常注入、客户端观察、依赖实际效果与恢复结果。

### BE-036 核验合同

- **BE-036-P · 输入/动作与合格判据：** 慢DNS/半开/重试/摘除/区域切换→故障半径内真实结果可核。
- **BE-036-F · 直接失败变异：** 单元模型冒真实服务恢复→失败。
- **BE-036-N · 合法邻例：** 无区域部署不需实际跨区注入。

## 三十七、恢复后重驱动与已受理义务核对
1. 过载缓解后的恢复须核查被拒请求、已受理待完成任务、超时未知提交、Broker 积压及下游结算义务是否得到真实归档或继续处理。
2. 不能仅凭代理错误率下降或队列清空标记故障恢复；已承诺业务结果应依据权威数据对账，异常恢复路径沿用事务、消息和工作流规范。
3. **验收**：多层熔断全部解除之后，所有已受理资金或订单请求仍有逐项可核实结果，未知项不消失。

### BE-037 核验合同

- **BE-037-F · 直接失败变异：** 队列空、错误下降就全收尾→失败。
- **BE-037-N · 合法邻例：** 明确入口拒绝且无副作用无需补做订单。

## 三十八、租户配置、操作授权和管理面隔离
1. 网关管理 API、策略发布、租户配额配置与真实用户业务是不同权限域；策略操作必须绑定真实组织授权、环境和审计证据。
2. Agent、平台管理员或客户自助管理仅在明确授予的限额内修改规则，不得借运维入口改价格、用户权益或外部账户额度；测试流控数据不写回生产业务。
3. **验收**：越权修改限额、跨租户管理操作和调试环境配置传播至生产均能阻止并保留有权审查证据。

### BE-038 核验合同

- **BE-038-P · 输入/动作与合格判据：** 跨租户管理限额/调试配置→管理权限与业务权限隔离。
- **BE-038-F · 直接失败变异：** 管理员Token借限流配置改价格/外部额度→失败。
- **BE-038-N · 合法邻例：** 客户自助可在明确授权限额内配置。

## 三十九、长任务、代理断开与流程交接
1. 长时间业务任务和已经被持久接受的操作不能由同步 HTTP 期限决定生存期；受理后向异步任务转移应提供可查询的权威业务操作身份及恢复责任。
2. 入口超时、网关切流和客户端取消应按工作流／消息协议处理继续、暂停、取消或补偿，不把连接断开视为已撤销远端业务。
3. **验收**：从长任务 HTTP 连接超时切换为异步查询后，状态连续并不重复真实外部副作用。

### BE-039 核验合同

- **BE-039-P · 输入/动作与合格判据：** HTTP长任务超时转异步查询→原意图和状态连续。
- **BE-039-F · 直接失败变异：** 重连创建新任务或断连即撤销→失败。
- **BE-039-N · 合法邻例：** 只读临时计算可随调用取消。

## 四十、生效范围、L5/L6 参数与专项验收
1. 本 L4 专项仅建立服务流量准入、限额、重试、背压、隔离、流量切换及降级的技术安全契约；HTTP/RPC、身份、事务、消息、缓存、数据库内核和支付分别由现行相关专项负责。
2. 项目 L6 选择对应实现、依赖版本、限额算法、入口、负载、SLO、故障预算与真实验收方法；本规范批准与 CI、实际服务运行及客户业务结果是独立状态。
3. **验收**：有可核查的策略版本、真实场景配置、自动门禁及业务端到端测试，与相邻规范无无权变更或重复执行。

### BE-040 核验合同

- **BE-040-P · 输入/动作与合格判据：** 实际L6策略参数/版本/负载门禁→领域职责不冲突。
- **BE-040-F · 直接失败变异：** 规范草案或CI通过冒真实服务验收→失败。
- **BE-040-N · 合法邻例：** 不采用的网格/协议组件不强制引入。

## 四十二、生效、分层及项目接入条件
1. 本专项管理应用侧准入、限额、故障重试预算、过载与熔断、流量切换及降级的组合可靠性；HTTP/RPC 方法语义、身份与交易权利、消息持久性、数据内核、业务工作流、具体框架及云部署工具保留相邻 L4/L5 的独立职责。
2. 本规范包含 40 个独立技术机制主题与 48 项典型失效场景；适用范围为本版技术条文，实际流量控制、RPC、代理、业务与生产故障验收继续按 L6 独立执行。
3. L6 依据项目实际入口、资源预算、协议版本、权限、SLO、故障和恢复责任选择启用条款，记录真实配置、源码、测试输入和输出；文本静态覆盖、规范批准、实际运行与真实业务达成独立验收。
