# L4 消息事件与可靠交付技术规范

**文档ID：** STD-L4-BACKEND-010　**版本：** 0.1.0　**状态：** adopted　**生效日期：** 2026-10-30

## 技术对象、权威来源与适用条件

本 L4 具体技术专项适用于具有实际**异步事件、任务队列、消息消费者、发布订阅或可重放消息日志**需求的系统；包括模块化单体内可靠任务和跨服务事件集成。与实时 WebSocket/SSE/RPC 的连接交互不同，消息队列必须独立说明**存储、交付、确认、消费、副作用与恢复**。一次性同步请求、无需留存的通知或无持久业务变化的原型可以不用部署消息基础设施。
既有技术参考：[L4 后端与分布式系统领域通用基线](007-后端与分布式系统领域通用基线--v0.1.0.md)（后端通用基线）、[L4 领域模型与服务边界技术规范](013-领域模型与服务边界技术规范--v0.1.0.md)（领域模型）、[L4 事务隔离、并发与业务幂等技术规范](003-事务隔离、并发与业务幂等技术规范--v0.1.0.md)（事务并发及幂等）、[L4 服务身份、对象授权与 API 安全技术规范](009-服务身份、对象授权与-API-安全技术规范--v0.1.0.md)（服务身份和授权）、[L4 RPC、流式接口与长连接技术规范](002-RPC、流式接口与长连接技术规范--v0.1.0.md)（RPC 与长连接），并沿用 L1—L3 和现行跨项目执行规范。领域规则和数据使用权由真正拥有该业务及权利的主体决定，L5 负责具体 SDK／中间件实现，L6 负责真实项目的版本和运行质量门禁。
**已有行业标准与厂商文档直接引用原文，不重写其协议算法：**
- [CloudEvents v1.0.2 规范](https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/spec.md) 与 [版本化协议绑定](https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/bindings/kafka-protocol-binding.md)：CNCF 发布的事件描述与可选传输绑定。不是持久化、Exactly-Once 或事务安全的自动证明。

- [NATS JetStream Consumer Documentation](https://docs.nats.io/learn/jetstream/pull-consumers)：官方当前使用说明，拉取消费、确认与重投递依具体配置；不是所有 NATS Core 消息都具备持久回放。

## 一、使用消息系统的必要性与收益
1. 依据异步削峰、可靠延迟执行、多消费者事件广播、持久重放、隔离下游故障等实际需求选择消息平台，不因“分布式最佳实践”要求每个系统引入 Kafka 或 RabbitMQ。
2. 简单后台任务也可使用具有真实持久化与恢复契约的现有数据库／队列；必须标明它的吞吐、保留与故障边界。
3. 与同步 RPC 比较时量化新增的一致性成本、运行责任、故障时延、观察困难及最小运维费用。
4. **验收**：能说明消息化解决的真实问题及失败后的恢复路径；不通过增加 Broker 数量削弱已有业务功能。

### BE-001 核验合同

- **BE-001-P · 输入/动作与合格判据：** 同任务比较直调与消息链→收益、恢复主体和成本明确。
- **BE-001-F · 直接失败变异：** 简单读接口强引Broker却漏恢复→失败。
- **BE-001-N · 合法邻例：** 单进程无消息需求可不采用。

## 二、事件、命令、任务与通知语义
1. **领域事件**描述已发生且具有明确业务意义的事实；**命令**要求有权处理者执行动作；**任务**表示待完成工作；**通知**面向下游接收者。项目须区分各自允许的失败、重放和消费者责任。
2. 领域事件与对外**集成事件**可以不同，后者应使用经权限和版本审查的稳定表示，不直接泄漏私有 ORM 实体和无授权用户字段。
3. 事件发布成功只是传输链某一阶段，不代表客户端收到通知、财务到账或业务目标已达成。
4. **验收**：消费者面对历史重放和重复事件仍能判断命令是否应再执行，不对历史事件重复收费。

### BE-002 核验合同

- **BE-002-P · 输入/动作与合格判据：** 重放历史事件与新命令→事实/任务/通知语义分开。
- **BE-002-F · 直接失败变异：** 历史订单事件再触发一次收费→失败。
- **BE-002-N · 合法邻例：** 可容忍重复通知可按合同放宽。

## 三、消息信封、身份与因果关系
1. 定义事件唯一身份、来源、类型、发生时间、Schema 版本、关联业务操作及分区／排序键；使用 CloudEvents 时按实际选定格式和绑定填充，不制造与原始事件身份不同的伪唯一键。
2. 消息身份、业务操作键、客户资源 ID、Broker Offset、投递尝试编号和 Trace ID 各有用途，不应互相替代。
3. 同一事件重投递保持足以去重的身份；纠错重新发出的新业务事实应保留与原事实的明确关联。
4. **验收**：重复、重试、跨分区和通过转换服务后都能追溯源业务事实及消息合法语义。

### BE-003 核验合同

**必要机制补充：** CloudEvents v1.0.2以source+id标识不同事件的唯一性；同一事件重投保持身份，多个来源可合法使用相同字面id。specversion字段为1.0，不写成补丁发布号1.0.2。

- **BE-003-P · 输入/动作与合格判据：** 同事件重投及转换→source+id、业务intent、attempt、offset分开。
- **BE-003-F · 直接失败变异：** 每次投递换新事件id绕过去重→失败。
- **BE-003-N · 合法邻例：** 纠错新事实可新id但关联原事实。

## 四、Topic、队列、Subject 与消费者拓扑
1. 明确单播任务、竞争消费、广播订阅、分区日志、按键顺序处理和临时监听之间的真实差别。
2. 记录谁拥有主题和事件 Schema、谁能创建生产者与订阅者、Topic 命名、租户隔离、环境分离、消费者组及订阅退役条件。
3. 对广播与竞争模型区别消费进度和扇出影响，不能因为两个 Worker 收到数据就自动把消息归为广播事件。
4. **验收**：多个消费者及新增下游接入时，消息不会意外丢给不相干业务角色或被所有副本重复执行一次性操作。

### BE-004 核验合同

- **BE-004-P · 输入/动作与合格判据：** 竞争组/广播订阅新增Worker→实际拓扑和消费责任正确。
- **BE-004-F · 直接失败变异：** 每副本都执行一次性命令或误投租户→失败。
- **BE-004-N · 合法邻例：** 多个合法消费者各有独立处理权。

## 五、本地事务与事件发布的原子边界
1. 写领域数据并产生事件时，明确数据库提交与 Broker 发布之间的真实原子性空隙；不能凭单个 Service 方法或 try/catch 声称两者已形成分布式事务。
2. 对不能容忍“提交成功但事件丢失”的场景选择 Outbox、事务性日志／CDC、同资源原子队列或经验证的等价协调设计，标识事件待发布、已受理、未知或失败状态。
3. Outbox 发布仍可能重复，消费端要有相称的幂等与重放控制；具体数据库锁、隔离和 CDC 实现遵从相邻事务／数据库规范。
4. **验收**：数据库先提交后进程崩溃、Broker 暂不可用、重复发布及回填任务并行时，事件可恢复且源领域数据不被错误改写。

### BE-005 核验合同

**必要机制补充：** Outbox记录与产生它的领域修改在同一实际数据库事务中一起提交/回滚；后续发布确认与消费者提交不在该事务内，允许重复发布但不允许静默丢失。Inbox唯一键至少区分租户、业务消费范围和源事件身份；去重登记、目标本地业务修改及需要产生的下一步Outbox在同一实际事务完成。外部付款/发信不被该本地原子边界包围，须继续使用目标接受的意图键、收据与未知结果核对。

- **BE-005-P · 输入/动作与合格判据：** 领域写与Outbox同事务前后崩溃→要么都有要么都无。
- **BE-005-F · 直接失败变异：** 领域先commit后另事务记Outbox造成静默缺口→失败。
- **BE-005-N · 合法邻例：** 事务日志CDC可作有证明的等价实现。

## 六、生产者发布、确认与未知结果
1. 区分应用已写入发送缓冲、连接已提交字节、Broker 已接受、满足所选持久化条件、目标消费者已处理及下游业务真正生效。
2. 对依赖 Broker ACK／发布者 Confirm 的平台，要按其真正定义和队列模式确认所能保证的阶段；RabbitMQ Publisher Confirm 与 Consumer Acknowledgement 相互独立。
3. 当 Confirm 超时或连接丢失时发布结果可能未知，发布者须按事件身份、日志状态及允许的重发行为回读，而非认定“没有发送”。
4. **验收**：Confirm 丢失、Broker ACK 后副本宕机、不可路由事件及上游断线时，不发生永久静默丢失或无证据的重复业务动作。

### BE-006 核验合同

- **BE-006-P · 输入/动作与合格判据：** Confirm丢失/不可路由/副本失败→发布未知与消费完成分清。
- **BE-006-F · 直接失败变异：** 缓冲写成功或Confirm当客户已收讫→失败。
- **BE-006-N · 合法邻例：** 事件同身份可按目标保证安全重发。

## 七、队列持久性、复制与数据留存
1. 根据容忍的数据丢失窗口、恢复时间、容量成本和业务保留义务选择非持久队列、持久队列、复制日志或不同保留策略；不把设置 durable 名称当作一切数据已安全持久化。
2. 确认消息持久标志、Broker 持久化成功条件、复制副本数量、故障域、日志清理、TTL 及配额耗尽时真实行为。
3. 队列保存时间须与最久允许的消费者离线时间、审计／业务补偿窗口和重放能力协调，不能让仍承诺的旧消费者引用已被删掉的消息。
4. **验收**：Broker 单点退出、重启、磁盘满、复制节点损坏及消息过期时，已承诺保留范围能够恢复或准确表明实际无法恢复的界限。

### BE-007 核验合同

- **BE-007-P · 输入/动作与合格判据：** 磁盘满/复制故障/重启/TTL→耐久范围与留存承诺准确。
- **BE-007-F · 直接失败变异：** durable名义当所有消息已复制落盘→失败。
- **BE-007-N · 合法邻例：** 允许损失的临时队列可明确选择。

## 八、投递保证与端到端业务效果
1. 分开传输层最多一次、至少一次、特定平台内部事务与**跨数据库／资金／客户交付的实际业务效果**。平台声明 Exactly-Once 不意味着外部支付平台或另一个存储系统也被同一事务包围。
2. 当系统具有重复交付可能时，消费者使用权威业务身份和原子检查避免重复扣费、发货、邮件及资产转移；只有可容忍重复的通知或统计才可适当放宽。
3. 对确实允许丢失的非关键遥测明确损失容忍范围，不将这种链路用于承诺必达的权益变化。
4. **验收**：相同事件跨 Broker 重投、消费者重启与多次回放后的业务数据及外部副作用，符合明确承诺的正确性。

### BE-008 核验合同

- **BE-008-P · 输入/动作与合格判据：** 跨Broker重复/消费者崩溃/外部API→业务副作用受原子去重保护。
- **BE-008-F · 直接失败变异：** Kafka内部事务冒跨银行exactly-once→失败。
- **BE-008-N · 合法邻例：** 非关键遥测可有明确损失容忍。

## 九、消费 ACK、事务提交与失败回退
1. 将消息已拉取、处理逻辑开始、数据库提交、外部业务确认、消费者 ACK 和 Broker 删除／推进进度分开记录。
2. ACK 时机按需要的可靠性交付边界选择；若 ACK 先于持久业务提交，消费者宕机会丢失处理，若 ACK 在提交之后失败则需要可靠重复处理。
3. 手动 ACK、自动 ACK、NACK、重入队和 Pending 状态按实际平台与消费者组配置使用，不假定不同 Broker 等价。
4. **验收**：任意处理阶段退出或重启后，消息不会被无证据丢弃，也不触发两次收费或错误领域状态。

### BE-009 核验合同

- **BE-009-P · 输入/动作与合格判据：** 处理各阶段退出后重投→ACK和持久业务边界正确。
- **BE-009-F · 直接失败变异：** 先ACK后commit丢任务或晚ACK无去重双执行→失败。
- **BE-009-N · 合法邻例：** 允许丢消息模式可按显式业务合同。

## 十、消费者去重与 Inbox 契约
1. 对需要按事件身份去重的消费者，定义消费范围、消费者名称／版本、去重主键、状态占用、有效期及处理结果，确认本地数据提交与去重登记的原子边界。
2. 一个消息被多个合法业务消费者处理时，不能用全局事件 ID 强制阻止全部订阅方，各消费者具有自己的合法处理记录。
3. 去重记录必须覆盖相关消息重放窗口；过早删除可能导致历史消息再次产生外部副作用。
4. **验收**：同一订阅组多 Worker、重复消息、请求崩溃、去重写入与业务事务中途失败时都能一致判断处理结果。

### BE-010 核验合同

**必要机制补充：** Outbox记录与产生它的领域修改在同一实际数据库事务中一起提交/回滚；后续发布确认与消费者提交不在该事务内，允许重复发布但不允许静默丢失。Inbox唯一键至少区分租户、业务消费范围和源事件身份；去重登记、目标本地业务修改及需要产生的下一步Outbox在同一实际事务完成。外部付款/发信不被该本地原子边界包围，须继续使用目标接受的意图键、收据与未知结果核对。

- **BE-010-P · 输入/动作与合格判据：** 同组双Worker、不同消费方同事件→Inbox与业务同原子边界。
- **BE-010-F · 直接失败变异：** 全局id阻止第二合法订阅方或分事务登记→失败。
- **BE-010-N · 合法邻例：** 消费者语义版本升级可明确迁移消费身份。

## 十一、顺序保证、分区键与并发
1. 确定业务需要的是单对象局部顺序、分区内顺序、每个订阅者的可见顺序还是无序可并行处理，不能笼统声称“消息按顺序投递”。
2. 分区键应匹配需要连续处理的领域身份及真正冲突范围，避免把全部消息绑定单分区而意外制造吞吐瓶颈。
3. 发生重试、并行消费者、重平衡或分区扩容时，检查乱序对状态机、余额、库存和时间有效性的真实影响。
4. **验收**：同实体连续变化、不同实体并行、旧版本事件迟到、分区重分配和网络抖动后的业务状态保持正确。

### BE-011 核验合同

**必要机制补充：** 按事件类型区分完整快照与增量：旧快照可按版本拒绝，增量不可仅丢旧序号而漏掉缺口。不可交换增量遇缺版时有限缓冲、补取缺失或回读权威；可交换增量需证明其去重与归并不变量。

- **BE-011-P · 输入/动作与合格判据：** 同实体旧事件迟到/异实体并行/分区扩容→局部顺序守卫有效。
- **BE-011-F · 直接失败变异：** 以时间戳全局排序或所有事件单分区强串行→失败。
- **BE-011-N · 合法邻例：** 无共享不变量的实体可无序并行。

## 十二、Consumer Group、游标与偏移量
1. 区分 Broker Offset、订阅组消费位置、消息持久化、应用业务检查点以及下游成功确认；提交偏移量不自动说明外部副作用真正成功。
2. 消费者组扩缩容、重平衡、离线与恢复要有明确的任务接管、所有权交接和幂等检查。
3. 不同业务订阅方可有独立游标；不能通过删除或重置一个订阅者的进度使另一方丢失必要历史事件。
4. **验收**：重启、组成员增减、游标提前提交、手工回退及并行处理时，没有永久漏处理和无授权重放。

### BE-012 核验合同

**必要机制补充：** 并发消费提交offset/checkpoint时，只推进每个分区已耐久处理的连续前缀；完成后段不能跳过尚未完成的前段。

- **BE-012-P · 输入/动作与合格判据：** 组重平衡/手调offset/并行处理→应用checkpoint和broker位置可对账。
- **BE-012-F · 直接失败变异：** 先推全批offset导致未完成项漏掉→失败。
- **BE-012-N · 合法邻例：** 不同订阅者可独立游标。

## 十三、临时失败、重试分类与退避预算
1. 将网络暂时故障、Broker 暂不可用、幂等冲突、限流、数据格式永久错误、业务拒绝、权限撤销和消费者 BUG 区分处理。
2. 可重试事件应有退避、抖动、总次数／持续时间预算、最大并发、幂等与取消条件，不让失败重试占满高优先级正常任务。
3. 对永久 Schema 错误、未授权事件及违反领域规则的命令不能无限重试或默默吞掉；转入有权审核的隔离与修复渠道。
4. **验收**：毒消息、Broker 限流、第三方 API 拒绝、系统恢复和业务不可逆动作均在受控预算内处理并保留真实未完成项。

### BE-013 核验合同

- **BE-013-P · 输入/动作与合格判据：** 毒消息/限流/永拒/撤权→分类预算且未决保留。
- **BE-013-F · 直接失败变异：** 永久schema错无限重试占满正常队列→失败。
- **BE-013-N · 合法邻例：** 临时故障可有限退避恢复。

## 十四、死信队列、隔离与人工处理
1. 死信／隔离队列（DLQ）是可管理的未处理结果集合，**不等于业务已经完成或问题已经修复**。
2. 应保留必要事件身份、原消费者、失败类别、尝试次数、来源版本、重新投递限制和有权恢复的处置入口，避免泄露客户私有内容与凭据。
3. 设计可解释的修复、重放、补偿、审批及错误关闭条件；批量重新投递应确认 Schema、幂等和业务权益。
4. **验收**：毒消息不会永久阻断正常消费者，DLQ 不被未经授权销毁或循环放回原队列，未解决业务结果可追踪。

### BE-014 核验合同

- **BE-014-P · 输入/动作与合格判据：** 毒消息隔离后修复/回放→DLQ保留身份与有权处置。
- **BE-014-F · 直接失败变异：** 入DLQ就业务完成或无审查循环回灌→失败。
- **BE-014-N · 合法邻例：** 确认合法无需处理的消息可按合同关闭留证。

## 十五、延时任务、定时交付与消息过期
1. 定时执行须定义“最早可处理时间、最终到期时间、实际时间基准”及目标平台支持的精度；定时触发并不等于业务效果已提交。
2. 区分 Event Time、Produced At、Queued At、Delivery Attempt Time 和 Business Effective Time，不能用服务器当前时间覆盖原发生时间或合同截止时间。
3. 延时队列、TTL、消息到期和业务任务取消由独立契约决定；已过期的指令有时只能安全拒绝，历史事实事件可仍需审计保留。
4. **验收**：时区／夏令时、时钟漂移、队列积压、长时间停机、延迟重投递及已取消任务重新出现时能正确处理。

### BE-015 核验合同

- **BE-015-P · 输入/动作与合格判据：** 最早时间/截止/长停机/时钟差→时间语义与过期规则正确。
- **BE-015-F · 直接失败变异：** TTL到期当外部业务已取消→失败。
- **BE-015-N · 合法邻例：** 历史事实可过指令期限后仍保留审计。

## 十六、历史回放、重建与修复
1. 明确消息日志保留、快照、全量重建、局部重放与消费者补偿的用途及权威来源；需要回溯而超出保留期时须有其他数据源或明确可接受的数据缺口。
2. 历史事件重放一般不是重新执行收费、邮件和外部通知；必须通过回放模式、业务身份或输出权限隔离来阻断重复副作用。
3. 重建投影与恢复业务真相属于不同操作；投影可以重算，已经发生的外部付款或合同事实不能仅通过删掉日志就撤销。
4. **验收**：消费者离线超过保留窗、旧版本快照和错误重放时，数据可正确重建或准确说明恢复边界。

### BE-016 核验合同

- **BE-016-P · 输入/动作与合格判据：** 旧快照/留存窗外/回放模式→投影重建而非重做外效。
- **BE-016-F · 直接失败变异：** 重放事件再次发邮件/扣费→失败。
- **BE-016-N · 合法邻例：** 隔离输出的纯投影回放可重复。

## 十七、Schema 版本与事件兼容演进
1. 每种事件载荷记录拥有者、版本、字段类型、精度、单位、默认值、可空与不变量；公开事件契约不是数据库当前表结构的直接镜像。
2. 新增／删除字段、枚举扩展、事件语义变化、旧消费者和多语言序列化需分别审核。即便 Schema 语法兼容，也可能产生危险的业务语义变化。
3. 升级前考虑同时存在的老生产者、老消费者、历史消息和离线重放；如需转换旧事件，保留可复核转换规则及原来源。
4. **验收**：真实支持的“生产者版本 × 消费者版本 × 历史事件”组合解析准确且没有必需业务字段损失。

### BE-017 核验合同

- **BE-017-P · 输入/动作与合格判据：** 旧生产者/消费者/历史事件→Schema与业务精度兼容。
- **BE-017-F · 直接失败变异：** 新增字段语法兼容就改单位或未知枚举当成功→失败。
- **BE-017-N · 合法邻例：** 明确不支持格式可安全隔离并保欠处理。

## 十八、CloudEvents 与 AsyncAPI 的采用边界
1. 采用 CloudEvents 的系统遵守所选 v1.0.2 核心属性及具体协议绑定。CloudEvents 规定可互操作的事件表示，不规定每个业务消费者的授权、幂等账本或事务边界。
2. 采用 AsyncAPI 的系统按实际 3.0.0 或锁定版本描述 Channel、Operation、Message、Schema 和安全要求，平台实际 Topic、Broker 权限及消费者仍需要独立配置验证。
3. 没有采用这些标准的消息系统只需满足真正的产品契约，不强行引入不必要的事件格式适配层。
4. **验收**：描述文件、生产者真实消息、代理绑定、消费者反序列化与业务状态一致，不以 Schema 文档存在表示队列已交付。

### BE-018 核验合同

- **BE-018-P · 输入/动作与合格判据：** 实际CloudEvents/AsyncAPI绑定到Broker→封套/描述与运行分开。
- **BE-018-F · 直接失败变异：** Schema文件存在即称消息可靠交付→失败。
- **BE-018-N · 合法邻例：** 未采用这些格式可按真实协议实现。

## 十九、消息来源可信性与租户授权
1. 识别生产者身份、来源主题、Broker ACL、消费权限、授权租户、数据用途和跨组织转发范围；收到消息不代表其中标注的角色或用户身份可信。
2. 异步消费者在真正执行带副作用动作时按契约验证所需权限有效性，防止撤销后的旧指令仍因队列缓存获得新的能力。
3. 每个消费者只能看到有权处理的负载、标签与头信息；不同租户共享 Topic 时按实际可验证的订阅隔离与应用对象鉴权处理。
4. **验收**：伪造事件、跨租户重放、非法生产者、旧凭据和无权导出均无法触发越权业务写入。

### BE-019 核验合同

- **BE-019-P · 输入/动作与合格判据：** 伪生产者/跨租户/撤权旧命令→来源和执行对象授权成立。
- **BE-019-F · 直接失败变异：** 收到消息就信body自称角色→失败。
- **BE-019-N · 合法邻例：** 已合法完成事实可按权限被多个消费者读取。

## 二十、事件数据保护与最小化传播
1. 按数据必要性确定消息中的直接标识、客户私有字段、文件引用、PII、订单／支付详情和保留期；不要为了方便下游让所有订阅者获取完整源领域对象。
2. Broker 持久化、备份、DLQ、指标、追踪与重放缓存都可能保留消息副本，删除或撤销必须考虑这些真实存储位置与合法审计需要。
3. 选择加密、签名和密钥轮换时记录谁能验证、解密、撤销及恢复；不把 JWT、OAuth 或 API Token 原样放在可长期保留的事件体。
4. **验收**：新消费者加入、DLQ 查询、日志导出、客户删除请求和备份恢复都不会扩大数据可见性或遗漏必要的权利处理。

### BE-020 核验合同

- **BE-020-P · 输入/动作与合格判据：** 新订阅者/DLQ导出/备份恢复→字段、用途、删除传播受控。
- **BE-020-F · 直接失败变异：** 把长期Token放事件或全对象广播→失败。
- **BE-020-N · 合法邻例：** 合法审计保留按受限规则不等于公开。

## 二十一、事件与任务截止时间、取消
1. 将取消请求、Broker 消息删除、Worker 停止与外部业务撤销区分；后者可能根本不可逆。
2. 对长任务设置取消令牌、有效期限及恢复检查；在多个 Worker 间迁移执行时确认是否已发生部分副作用，避免盲目重新开始。
3. 定时到期、用户撤销授权及外部资金动作的取消机制须由真正权利人批准，不因队列支持删除消息就默认客户事务已撤销。
4. **验收**：取消与提交同时发生、执行完成后取消、Worker 换代及超时自动清理不会虚报业务终态。

### BE-021 核验合同

- **BE-021-P · 输入/动作与合格判据：** 取消与提交/完成后取消/Worker换代→未知和补偿分清。
- **BE-021-F · 直接失败变异：** 删Broker消息即宣布退款/撤单→失败。
- **BE-021-N · 合法邻例：** 只读计算可在取消后停止资源。

## 二十二、积压、背压与公平性
1. 对消息生产速率、消费者吞吐、队列滞留、延迟、单条大小、分区倾斜、重试波峰建立与真实资源预算匹配的流控和背压机制。
2. 根据平台能力选用消费者预取、拉取批次、最大并发、流式限制和优先级，确认不同租户与关键业务在资源紧张时的公平性。
3. 不能为追求吞吐随意加大批次导致单个消息失败后全部业务重复执行；也不能因排队延迟延长消息保留而遗漏隐私和成本评估。
4. **验收**：突发洪峰、慢订阅者、Broker 配额已满和下游限流时，仍能确认重要任务的实际接受与恢复状态。

### BE-022 核验合同

- **BE-022-P · 输入/动作与合格判据：** 突发/慢订阅/满配额/下游限流→接受与恢复可查且资源有界。
- **BE-022-F · 直接失败变异：** 批次扩大导致单条失败重做全部不可逆项→失败。
- **BE-022-N · 合法邻例：** 允许合并的视觉样本可按合同丢弃。

## 二十三、Broker 故障域与数据恢复
1. 按实际需求选取持久化、复制、副本确认、故障切换和灾备策略，区分单机开发实例与生产可靠性承诺。
2. RabbitMQ Quorum Queue、Kafka 副本、NATS JetStream 存储及其他平台采用不同复制和确认语义；根据官方版本核对实际部署、磁盘失败与网络分区行为。
3. 故障恢复中的重新选主、读写隔离与恢复窗口可能导致重复或暂不可用，应用必须按来源消息身份做正确消费决定。
4. **验收**：Broker 节点故障、存储耗尽、网络分区和灾后恢复后，保证范围与未恢复缺口可由证据说明。

### BE-023 核验合同

- **BE-023-P · 输入/动作与合格判据：** Broker节点/磁盘/网络分区/灾后→实际队列语义和应用结果对账。
- **BE-023-F · 直接失败变异：** 单机演示冒生产副本耐久保证→失败。
- **BE-023-N · 合法邻例：** 小原型可明确单机损失范围。

## 二十四、消费者租约、重平衡与旧 Worker
1. 消费者迁移、Lease／AckWait 超时或分区 Rebalance 后，旧 Worker 可能仍在执行已获取的任务。仅一个组员持有分区不代表旧执行者的远端写入自动停止。
2. 对有危险共享写入的任务，按实际冲突范围使用持久化操作键、版本条件、可验证的所有权令牌或 fencing 机制，避免旧执行者覆盖新结果。
3. 若某个平台允许迟到 ACK 成功，还要区分 Broker 接受确认和该 Worker 的业务写入是否合法生效。
4. **验收**：重复领取、锁租约过期、旧 Worker 恢复、重新分配分区和并发 ACK 后关键不变量不受损。

### BE-024 核验合同

**必要机制补充：** 执行世代只有在目标写入/效果边界被验证才构成栅栏：先原子安装新世代，再允许新执行者写入，旧世代检查与写入处于同一受控原子边界。本地租约到期、取消请求发出、Worker进程失联或代理断开都不证明旧在途操作已停止；已发外部操作仍按原意图查询。

- **BE-024-P · 输入/动作与合格判据：** lease过期旧Worker恢复/迟ACK→目标fence和业务唯一约束拒旧写。
- **BE-024-F · 直接失败变异：** 组所有权转移当旧远端调用已停→失败。
- **BE-024-N · 合法邻例：** 迟ACK可被Broker接受但不改变业务授权判定。

## 二十五、外部副作用与跨系统协调
1. 发邮件、创建支付、发货、云资源分配和调用第三方 API 时，识别接收方的真实操作身份、幂等机制、提交状态和可补偿性。
2. Broker 与外部业务存储或支付系统往往不共享同一原子事务；平台内部 Exactly-Once 不能直接升级为外部业务 Exactly-Once。
3. 对无法可靠回滚的外部动作，提供可查的订单／请求结果、合法补偿动作和人工业务确认，且遵守原权利主体批准的资金与客户合同。
4. **验收**：消息重投、服务中断与支付响应丢失后外部副作用不重复，未知状态明确并可恢复。

### BE-025 核验合同

- **BE-025-P · 输入/动作与合格判据：** 外部响应丢失后重投→目标操作身份、查询与补偿明确。
- **BE-025-F · 直接失败变异：** 本地Inbox记录就宣称外部邮件/支付必exactly-once→失败。
- **BE-025-N · 合法邻例：** 无法查询且无去重目标保留unknown待有权核对。

## 二十六、监测、追踪与可靠交付证据
1. 将**业务提交、待发布、Broker 确认、消费领取、处理提交、消费 ACK、外部接收与用户业务终态**分别定义可观测事件，不以队列剩余消息为零表示所有业务成功。
2. 对采用 OpenTelemetry 的项目使用锁定的 Messaging Semantic Conventions 版本、Span Link／Trace 关系及采样策略；当前部分约定可能仍处于发展中，升级应兼容旧观测数据。
3. 为积压、长期未 ACK、DLQ 增长、重复率、重试率、延迟和不可恢复事件建立有实际解释的可查询指标；日志保留必要 ID 而非全部敏感消息。
4. **验收**：从源业务状态到指定消费者和外部下游结果可追踪，存在数据缺口与未知时能定位真实责任及恢复条件。

### BE-026 核验合同

- **BE-026-P · 输入/动作与合格判据：** 队列归零仍有下游未履约→各阶段独立可追踪。
- **BE-026-F · 直接失败变异：** ACK计数当客户业务成功率→失败。
- **BE-026-N · 合法邻例：** 日志可采样但权威业务结果不依随机采样。

## 二十七、性能成本与容量计划
1. 基于实际工作负载决定队列分区、并发消费者、消息大小、复制数量、保留周期、重放成本与峰值预算，不强制研发原型建立昂贵集群。
2. 测试吞吐同时观测尾延迟、堆积、磁盘、GC、CPU、网络、业务重复率及权限隔离，不能以 Broker 自身高 TPS 代表客户结果达标。
3. 面向突发成本的队列与外部 API 调用，按项目预算与授权限制重试规模和最大滞留，避免消费者故障导致付费调用爆炸。
4. **验收**：在目标数据形态和实际平台执行相称负载与恢复测试，记录真实版本、成本、错误与业务结果。

### BE-027 核验合同

- **BE-027-P · 输入/动作与合格判据：** 目标大小/复制/重放/热点负载→吞吐、尾延迟、成本与正确性同时验。
- **BE-027-F · 直接失败变异：** Broker TPS高冒客户结果达标→失败。
- **BE-027-N · 合法邻例：** 研发原型不强制昂贵集群。

## 二十八、实际测试门禁与项目接入
1. 按系统风险选取发布确认、队列耐久、消费者 ACK、去重、重平衡、死信、版本兼容、重放、权限、积压、恢复和端到端业务测试。
2. 合同／Mock 测试可验证事件 Schema 和局部控制；涉及真实数据存储、Broker、支付、第三方发信等重要链路时，应保留相应真实集成与外部确认。
3. 针对历史丢消息、双发、无限重试、跨租户泄漏、重复收费等缺陷保留防复发用例，不通过删除断言或缩短测试范围伪装完整交付。
4. **验收**：执行过的测试具有明确输入、版本、Broker 配置、结果及覆盖边界，真实业务生效与规范批准分开报告。

### BE-028 核验合同

- **BE-028-P · 输入/动作与合格判据：** 提交/Confirm/ACK/重平衡/DLQ/版本组合实测→输入配置结果绑定。
- **BE-028-F · 直接失败变异：** Mock合同冒真实Broker或删除历史反例→失败。
- **BE-028-N · 合法邻例：** 有效局部证据只在等价边界复用。

## 二十九、消息交付静态验收矩阵
| 失效场景 | 主要检查边界 | 预期真实结果 |
| --- | --- | --- |
| 源数据库提交后发布者立即崩溃 | Outbox/原子边界 | 未丢失待发事件；能安全补发 |
| 写入 socket 后生产者未收到 Broker Confirm | 未知发布结果、重投与去重 | 不直接判定未投递；不重复业务效果 |
| RabbitMQ Confirm 已返回而消费者未 ACK | 生产者与消费者确认区分 | 只确认已达到的各阶段 |
| Broker 宕机后未持久化消息消失 | 持久性与恢复承诺 | 实际丢失范围可查，不虚报耐久 |
| 消息无法路由到任何订阅目标 | 拓扑配置、强制路由与错误 | 不把无消费者的 Confirm 视作业务完成 |
| 同事件投递给两个不同合法订阅方 | 事件身份与消费者范围 | 各自合法处理一次，不用全局去重吞掉一方 |
| 消费者业务提交成功后 ACK 丢失 | 消费幂等与回读 | 重投不造成重复外部效果 |
| 消费 ACK 早于数据库事务成功 | 确认时机及事务边界 | 不永久丢弃未处理任务 |
| 消费者处理一半事务回滚 | 消息和本地事务协调 | 状态受保护且可再次处理 |
| 单实体消息跨分区乱序 | 业务顺序和分区键 | 状态机不倒退或使用权威恢复 |
| 分区重平衡旧 Worker 尚在提交 | 租约/版本/fencing | 旧实例不能覆盖有效新结果 |
| 幂等键在重放窗口内被过早清除 | 保留期和去重 | 历史回放不产生重复收费 |
| 消息永久 Schema 不兼容反复重试 | 异常分类和 DLQ | 隔离并报告，不产生无限毒消息循环 |
| DLQ 被自动重新投入主队列 | 隔离、授权与恢复 | 按核对过的规则受控回放 |
| 外部上游限流导致指数级任务重试 | 重试预算、背压和公平性 | 遵守配额，必要业务可恢复 |
| 消费者离线七天而日志仅保留一天 | 保留窗与快照补偿 | 明确缺失并按批准来源恢复 |
| 历史事件重放触发旧邮件和付款 | 重放模式和副作用权限 | 只重建所需数据，不重发真实交易 |
| 旧消费者不认识新增枚举 | Schema/语义演进 | 支持窗口内正确消费或安全失败 |
| CloudEvents 格式通过但事件含私有令牌 | 事件格式与数据最小化 | 不泄露凭据、用户资料 |
| 非授权生产者往受保护 Topic 发指令 | Broker ACL 和业务鉴权 | 拒绝越权执行并留审计 |
| 用户撤销访问后排队命令才被处理 | 执行时授权复核 | 超期行为不再越权生效 |
| 多个租户误订阅同一私有 Subject | 租户隔离与主题策略 | 非目标租户无法接收 |
| 消息 TTL 到期但用户订单仍未完成 | 消息到期与业务补偿 | 保留真实业务欠交付状态 |
| 定时任务在取消之后被旧 Worker 再执行 | 取消与执行身份 | 无非法重复或误报撤销 |
| Kafka 内部 EOS 被用作外部扣费担保 | 事务保障范围 | 外部支付仍具备业务幂等和结果回读 |
| MQTT QoS 2 被当作数据库恰好一次 | 传输层与业务层区别 | 外部数据库操作需独立一致性保证 |
| NATS AckWait 到期发生重投且迟 ACK | 租约与 ACK 时序 | 业务效果不重复 |
| Broker 磁盘满导致写入拒绝 | 持久存储和流控 | 真实未接收状态清晰且安全恢复 |
| 队列清空但下游系统未确认业务 | 阶段证据与外部结果 | 不能宣称客户目标完成 |
| 性能优化提高吞吐却丢弃关键字段 | 信息保真、容量与回归 | 速度改进不能破坏业务正确性 |
## 三十、专项分层、批准及实际项目接入
1. 本规范 属于后端具体消息事件与可靠交付专项，约定应用级发布、确认、消费、重投、回放、权限与可观测性。领域事实和业务权利以经项目有权确认的领域模型为准；事务隔离及业务幂等以前项专项为准；Kafka／RabbitMQ／NATS／Redis 内核参数、OASIS 协议实现、安全身份体系、云基础设施、数据库 Schema、L5 语言 SDK 均有独立技术职责。
2. 不强制没有消息需求的项目采用事件总线，也不将日志平台宣传的 Exactly-Once 自动扩张为跨存储或对外交易的业务承诺。所有行业规范按发布状态、版本与实际采用范围引用，不重复写成另一套协议全文。
3. L6 项目契约选取真实的 Broker 与协议、消费者身份、可靠性、权限、数据保留、并发容量、消息 Schema、幂等边界和测试工具，按项目权威运行证据验收。
组织规范的批准与静态审查，不代表任何实际 Broker、持久事务、消费程序、付款或用户业务终点已运行通过；实际项目仍按 L6 验收。
