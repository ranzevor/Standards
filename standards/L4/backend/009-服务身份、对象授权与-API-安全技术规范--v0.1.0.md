# L4 服务身份、对象授权与 API 安全技术规范

**文档ID：** STD-L4-BACKEND-009　**版本：** 0.1.0　**状态：** adopted　**生效日期：** 2026-10-30

## 范围、依赖与原始标准

本 L4 具体技术专题适用于后端 HTTP API、RPC、任务消费者、管理接口、跨服务调用、Agent/MCP 调用入口及对外 Webhook 的**认证、服务身份、资源／字段／操作授权和租户隔离**。无登录要求的公开数据接口仅启用与其实际威胁和外部责任相关的控制；不强制所有项目引入 OAuth、身份平台、服务网格或多租户组织结构。
相应依据：[L4 后端与分布式系统领域通用基线](007-后端与分布式系统领域通用基线--v0.1.0.md)（后端领域通用基线）、[L4 领域模型与服务边界技术规范](013-领域模型与服务边界技术规范--v0.1.0.md)（领域模型与服务边界）、[L4 HTTP API、错误与兼容演进技术规范](001-HTTP-API、错误与兼容演进技术规范--v0.1.0.md)（HTTP API）、[L4 RPC、流式接口与长连接技术规范](002-RPC、流式接口与长连接技术规范--v0.1.0.md)（RPC 与流式）、[L3 通用工程规范](../../L3/001-通用工程规范--v0.1.0.md)（L3）、[L2 人类与 Agent 团队组织协作规范](../../L2/001-人类与-Agent-团队组织协作规范--v0.1.0.md)（L2）、[L1 全局治理补充规范](../../L1/001-全局治理补充规范--v0.1.0.md)（L1）。业务、资金、隐私与第三方权利以真实有权主体的有效决定为准，并在项目 L6 固定适用范围及证据。

- [RFC 8725 / BCP 225 — JWT Best Current Practices](https://www.rfc-editor.org/rfc/rfc8725.html)（IETF BCP）、[RFC 9068 — JWT Access Token Profile](https://www.rfc-editor.org/rfc/rfc9068.html)（Standards Track）。JWT 的具体格式及访问令牌 Profile 仅在实际采用时适用。
- [RFC 9449 — DPoP](https://www.rfc-editor.org/rfc/rfc9449.html)、[RFC 8705 — OAuth Mutual TLS](https://www.rfc-editor.org/rfc/rfc8705.html)、[RFC 7662 — Token Introspection](https://www.rfc-editor.org/rfc/rfc7662.html)、[RFC 7009 — Token Revocation](https://www.rfc-editor.org/rfc/rfc7009.html)、[RFC 8414 — Authorization Server Metadata](https://www.rfc-editor.org/rfc/rfc8414.html)、[RFC 8693 — OAuth 2.0 Token Exchange](https://www.rfc-editor.org/rfc/rfc8693.html)；仅在所选 OAuth 配置实际需要时引用。

- [OWASP ASVS v5.0.0](https://github.com/OWASP/ASVS/tree/v5.0.0)（稳定版应用安全验证标准，2025）与 [OWASP API Security Top 10 2023](https://api-security.owasp.org/editions/2023/en/0x11-t10/)（风险分类参考，非合规认证）。

## 核验口径与消费接口

维护者负责落实本文机制，领域/API/存储提供者负责其权威保证，验收者从实际受支持入口观察结果。输入固定源码/构建、配置、数据/协议版本、角色/租户、目标平台、故障时序和预算；权威观察对象为**issuer/subject/actor/audience/purpose、当前对象授权与实际副作用**。真实执行入口为**低权测试账户真实API/RPC/队列入口、令牌错误矩阵和权威副作用计数**。逐章 P/F/N 分别为正常输入及判据、破坏该机制的直接失败变异、应继续成立的合法邻例；本章原有每项规则、原有验收与新增合同共同约束，不用单一通用案例替代具体子项。每个子项须在案例输入中保留其适用条件，并以自身原文规定的输出/不变量判定；复合章应拆记录各个观察量，不能以一个成功掩盖其他失败。

证据产物包括真实命令/用户动作、原始响应或事件、权威状态前后值、版本、时序、失败及恢复；尚无对应真实运行证据的场景状态为 `not-run`，标准库示例仅证明列明的局部边界。具体输入与命令见[执行入口](../../../examples/web-backend/RUNBOOK.md)，条款索引见[规范条款登记](../../../registry/requirements.json)，来源的有限支持命题见[逐命题来源映射](../../../sources/web-backend/claims.json)。

本文的跨组件约束与正例、失败反例、合法邻例由本规范综合定义；外部来源支持的机制及适用边界见来源表。项目架构、预算和业务规则由实际需求确定。L5 实现应映射到所选框架、SDK 或引擎；L6 按具体版本的提供者保证与受支持矩阵验收项目能力。

## 一、身份、授权与业务权利的独立性
1. 区分外部请求的调用者身份（who）、被代表的业务主体（on behalf of）、具体操作（action）、资源（object）、租户（tenant）、上下文（conditions）及有权批准者。
2. 身份认证成功、拥有有效 OAuth Scope、在内网、持有 Agent 工具权限、拥有系统账号均**不自动授予**某个对象或资金动作的业务权利。
3. 应按产品实际用户任务定义匿名可访问、普通登录、服务账户和内部管理入口的必要能力；不得因安全工程简化需要删除已批准功能。
4. **验收**：同一身份对不同资源、不同动作、不同租户得到不同且符合真实业务规则的结果。

### BE-001 核验合同

- **BE-001-P · 输入/动作与合格判据：** 同身份换资源/动作/租户→认证、委派与业务权分别判定。
- **BE-001-F · 直接失败变异：** 有效scope或内网Token即任意付款→失败。
- **BE-001-N · 合法邻例：** 匿名公开资源可无需登录。

## 二、真实身份主体与稳定关联标识
1. 区分自然人、组织、租户、服务进程、OAuth 客户端、Agent 实例、设备、第三方委派账号；一个请求可同时关联多个主体，身份编号需说明 Issuer、命名空间及生命周期。
2. OIDC 中的 sub 等标识须结合真实 Issuer 理解，不以邮箱、显示名或易变手机号单独作为跨组织权利主键。
3. 创建、解绑、合并、离任、设备更换、租户转移时保留必要历史身份映射及审核权利，不以复制旧会话令牌实现交接。
4. **验收**：同名、跨 Issuer 同 sub、改邮箱、删除账号后重建、角色变更等情况无身份混淆和越权继承。

### BE-002 核验合同

- **BE-002-P · 输入/动作与合格判据：** 跨issuer同sub/改邮箱/账号重建→主键和生命周期无混淆。
- **BE-002-F · 直接失败变异：** 显示名或邮箱无权合并身份→失败。
- **BE-002-N · 合法邻例：** 合法主体合并可保留批准映射。

## 三、信任边界与入口身份验证
1. 确定公开 API、网关、边缘 Worker、内部 RPC、队列任务及系统回调的身份边界；实际入口根据合同验证其应接受的身份来源、凭据类型及防伪机制。
2. 来自客户端的 X-User、X-Tenant、Forwarded、Role 等名称不因看起来像内部头就成为受信任数据，必须在已认证的代理与明确变换策略下使用。
3. 对匿名公开数据、授权用户和内部工具实行相称的独立检查；网关验证通过不能替代领域对象操作权限。
4. **验收**：绕过公开入口直连内部端点、伪造代理身份头及错误租户上下文均不能获得额外能力。

### BE-003 核验合同

- **BE-003-P · 输入/动作与合格判据：** 绕网关直连/伪X-User/X-Tenant→入口验证且领域授权仍强制。
- **BE-003-F · 直接失败变异：** 内部名字Header自动受信→失败。
- **BE-003-N · 合法邻例：** 已认证代理可按明确变换传递身份。

## 四、用户登录、OAuth 与 OIDC 的实际选型
1. 项目按自身认证需求选择会话、OIDC、OAuth 或既有受支持身份平台。OAuth 是授权框架；选择 OIDC 时才按其身份层判断用户认证声明。
2. 引入 OAuth 时按所选 Provider 与 RFC 9700 检查授权码、PKCE、Redirect URI、颁发方混淆及授权回调，禁止因容易开发使用已明确不安全的流程。
3. 浏览器端 Cookie、存储、CSRF、跨源限制按相邻规范 Web 安全专项实现；本规范聚焦服务端接入、身份与访问决定。
4. **验收**：错误 Redirect、不同 Issuer、伪造认证成功、重放授权码和权限变化不能变成合法后端访问。

### BE-004 核验合同

- **BE-004-P · 输入/动作与合格判据：** 错PKCE/issuer/redirect/重放code→非法会话不能建立。
- **BE-004-F · 直接失败变异：** OAuth授权码到手当认证全完成→失败。
- **BE-004-N · 合法邻例：** 已有受支持会话方案不强制OAuth。

## 五、Access Token、ID Token 与 Token 类型
1. 接口必须声明真实接受的令牌类型、用途、受众和签发者。OpenID Connect ID Token 与 OAuth Access Token 不能因为都是 JWT 就互相代用。
2. 自包含 JWT 与不透明引用令牌采用不同验证方式。采用 RFC 9068 Profile 的 JWT Access Token 时按其 typ、iss、aud、exp 等相应规范验证；不强制所有 OAuth 服务器颁发 JWT。
3. 访问令牌不要携带下游无须知道的完整用户档案、长期凭据或超出用途许可的客户秘密；跨服务传递另核对适用受众。
4. **验收**：以 ID Token 访问 API、错误 audience／issuer、过期／未生效令牌、跨资源服务器重用均不得获得授权。

### BE-005 核验合同

- **BE-005-P · 输入/动作与合格判据：** ID Token当API Token/错aud/过期→类型用途和受众验证。
- **BE-005-F · 直接失败变异：** 都是JWT就互换→失败。
- **BE-005-N · 合法邻例：** 不透明引用令牌可用其真实验证方式。

## 六、JWT 验证与签名密钥边界
1. 接受 JWT 的资源服务在实际验证配置内核对签名或规定的其他保护、允许算法、密钥所属 Issuer、用途和相关时间声明；禁止让令牌未验证的 header 自行决定验证算法或受信任密钥 URL。
2. 算法与密钥的选择按 RFC 8725 的安全原则及具体令牌 Profile 决定。不同用途的 JWT 应避免 token confusion，禁止默认接受所有令牌库可解析的格式。
3. JWK/JWKS 获取有明确来源、信任域、缓存、密钥轮换和异常恢复规则；远端 Key ID、URL 或 Header 参数不得成为任意网络获取、SSRF 或跨租户签名接受入口。
4. **验收**：签名错误、算法替换、kid 注入、密钥轮换、跨 Issuer 混用和类型冒用均被正确拒绝。

### BE-006 核验合同

- **BE-006-P · 输入/动作与合格判据：** 坏签名/算法替换/kid URL/轮换→按信任issuer和允许算法拒绝。
- **BE-006-F · 直接失败变异：** 未验证header决定任意JWKS网络抓取→失败。
- **BE-006-N · 合法邻例：** 不同用途JWT可有隔离验证配置。

## 七、令牌生命周期、撤销与会话变化
1. 固定 Access/Refresh Token 的到期、轮换、撤销、重认证、注销、身份暂停和风险提升后所能继续执行的请求范围。
2. 采用 RFC 7662 Introspection、RFC 7009 Revocation 或自包含令牌短有效期等方案时，明确撤销传播延迟、离线状态、缓存失效和服务错误时的授权策略。
3. 不能因为旧 JWT 在加密意义上仍有效，就自动授予一个已经被撤销、移出租户或取消付费权益的主体继续操作资源。
4. **验收**：角色撤销、账号停用、设备遗失、Refresh Token 重放、服务端网络故障与身份退出后，真正的资源操作范围正确收敛。

### BE-007 核验合同

- **BE-007-P · 输入/动作与合格判据：** 撤权/离租户/refresh重放/鉴权服务故障→访问按约定时限收敛。
- **BE-007-F · 直接失败变异：** 签名未过期就永久沿用旧权益→失败。
- **BE-007-N · 合法邻例：** 已合法提交的独立合同义务可按明确边界继续。

## 八、Scope、Role、Entitlement 与资源权限
1. 明确 OAuth Scope、应用角色、业务权益、组织岗位、对象 ACL、租户成员和具体资源/动作许可各自语义，不能用单一 admin 布尔值替代全部规则。
2. 一个 Scope 可能只允许访问某个 API 能力类别，实际操作还须验证当前资源的所有者、状态、动作、时间和付款／合同条件。
3. 对同一角色实际拥有的业务功能按批准定义实施，避免自行增加无意义的人为二次审批或悄悄缩减已批准权利。
4. **验收**：拥有 read Scope 但不属于该对象、有管理界面但非对应租户管理员、已到期权益仍持旧 Token 等情况不会越权。

### BE-008 核验合同

- **BE-008-P · 输入/动作与合格判据：** read scope但非对象成员/到期权益→具体动作许可正确。
- **BE-008-F · 直接失败变异：** admin布尔替代全部条件→失败。
- **BE-008-N · 合法邻例：** 同角色不同对象可有不同权限。

## 九、对象级授权与 BOLA
1. 对路径、查询、Body、事件负载、文件名和 RPC 字段中的每个外部对象身份，在实际数据读取或状态更改处校验主体对该对象和动作的权限。
2. UUID、雪花 ID、复杂资源路径或列表筛选不能替代授权；必须防止横向越权、跨租户重复 ID 及直接引用内部对象的绕过。
3. 列表查询、聚合结果、文件下载与批处理也须对结果集合执行正确过滤与授权，不只检查单条详情 API。
4. **验收**：不同用户交换合法对象 ID、组合过滤、越权分页、批量导出及已撤销对象权限时均不可获取或更改他人数据。

### BE-009 核验合同

- **BE-009-P · 输入/动作与合格判据：** 交换合法ID/列表/下载/批量导出→逐对象与集合授权。
- **BE-009-F · 直接失败变异：** UUID不可猜当授权→失败。
- **BE-009-N · 合法邻例：** 批准共享范围内可允许交叉访问。

## 十、对象属性级授权及 Mass Assignment
1. 对对象读取和修改分别定义可见／可写属性，不得把 ORM 实体或所有字段自动序列化作为公开 API 返回。
2. 用户能更改地址、昵称等字段不代表能修改 ownerId、tenantId、账户余额、已支付标志、审批状态、角色及其他受保护属性。
3. 采用显式字段白名单、声明式 Schema 或等价映射，并保护跨字段一致性；动态 PATCH、批量导入或生成 SDK 不得绕过限制。
4. **验收**：在请求 Body 中加入管理员字段、尝试重写归属关系及通过字段投影读取隐藏属性时被正确拒绝。

### BE-010 核验合同

- **BE-010-P · 输入/动作与合格判据：** Body追加owner/paid/role及隐藏字段投影→拒绝或忽略按合同且无越权写。
- **BE-010-F · 直接失败变异：** ORM整体绑定Mass Assignment→失败。
- **BE-010-N · 合法邻例：** 允许用户改昵称不应误拒全部字段。

## 十一、操作级授权与管理接口
1. API 的功能权限与对象权限分开，尤其是导入、批量修改、发布、角色管理、资金、客户数据导出、日志检索与生产运维操作。
2. 管理功能隐藏在非管理 Controller、改路径、使用 POST 或内部网段并不能成为授权机制。每个独立入口必须由服务端强制校验。
3. 对高影响或不可逆动作按 L1 权限契约保留审批及有效执行证据，不能通过给 Agent 一个运维 Token 自动承接资金决策。
4. **验收**：普通用户调用未公开管理端点、修改方法、绕过 UI 或直接 RPC 均不会获得权限。

### BE-011 核验合同

- **BE-011-P · 输入/动作与合格判据：** 普通用户直调管理RPC/变更方法→功能与对象检查均成立。
- **BE-011-F · 直接失败变异：** 改路径或POST当管理防护→失败。
- **BE-011-N · 合法邻例：** 真实管理员仍按环境和对象范围执行。

## 十二、多租户、组织、项目与成员边界
1. 明确租户身份的真实来源、允许的成员关系与项目归属；同一主体跨多个组织时按此次请求选择且验证的租户生效，不能使用最近一次 UI 选择代替授权。
2. 服务端查询、缓存、后台任务、审计及搜索索引必须保持租户作用域；一个租户管理员不自动对其他组织或供应商数据拥有决定权。
3. 跨租户共享、协同与数据转移应有真实权利主体批准及明确的可读写范围；不得为“保守默认”无依据封死已批准共享能力。
4. **验收**：合法多组织切换、跨租户相同标识、旧会话、共享工作区、组织解散与邀请过期均产生正确隔离和授权结果。

### BE-012 核验合同

- **BE-012-P · 输入/动作与合格判据：** 合法多组织切换/相同ID/共享/解散→租户源与关系有效。
- **BE-012-F · 直接失败变异：** 最近UI租户选择代服务端鉴权→失败。
- **BE-012-N · 合法邻例：** 批准跨租户协作不应一律封死。

## 十三、RBAC、ABAC、ReBAC 与规则表达
1. 选择 RBAC、ABAC、ReBAC、ACL、策略引擎或领域规则函数应以实际授权关系复杂度和维护性决定，不引入无必要的全组织策略平台。
2. 明确资源、主体、动作、环境、业务状态和关系证据的来源与版本；拒绝规则、允许规则及默认策略必须无二义，复杂策略有可复核的决策路径。
3. 策略版本演进须考虑旧客户、管理员权利及异步事件；不能通过修改权限脚本悄悄改变已经批准的产品服务范围。
4. **验收**：冲突角色、时效、关系撤销、业务状态变更及多层组合条件在同一输入下稳定给出正确决定。

### BE-013 核验合同

- **BE-013-P · 输入/动作与合格判据：** 冲突角色/关系撤销/时效/业务状态→版本化策略可解释。
- **BE-013-F · 直接失败变异：** 默认异常允许或脚本静默扩权→失败。
- **BE-013-N · 合法邻例：** 简单规则函数可替代独立策略平台。

## 十四、策略执行点与可信计算位置
1. 识别 API 网关、服务入口、领域动作、数据读取与任务执行的策略强制点，避免所有权限只在前端或单个网关路由声明。
2. 如果使用独立 PDP/PEP 或授权服务，定义主体/资源来源、策略版本、决策缓存、不可用时的行为及审计；拒绝与异常不可静默转为允许。
3. 允许合理缓存不会快速变化的决定，但需按权限撤销、租户、对象状态与时间条件进行失效；缓存不能把读权限误扩为写权限。
4. **验收**：绕过中间层、断开策略服务、过期授权缓存、不同服务重复校验的结果保持一致。

### BE-014 核验合同

- **BE-014-P · 输入/动作与合格判据：** 断PDP/绕PEP/旧缓存→受控拒绝或既定合法路径。
- **BE-014-F · 直接失败变异：** 策略服务错误自动allow→失败。
- **BE-014-N · 合法邻例：** 不快速变化决定可有明确定期缓存。

## 十五、服务身份与工作负载认证
1. 区分机器工作负载、应用 Client、服务账号和业务委托人，按实际架构采用限定目的的服务身份。网络内可访问、容器名相同、持有静态共享密钥不自动等于彼此有权调用。
2. 如采用 SPIFFE/SVID、mTLS 或平台工作负载身份，核对信任域、签发、验证、证书轮换、工作负载标签、调用者身份及失效处理。
3. SPIFFE Workload API 分发身份材料并不自动决定业务对象的权限。客户端身份与 user-delegated 身份须分别保存，不允许内部服务偷换真实业务主体。
4. **验收**：伪造服务证书、跨信任域复用、令牌轮换及被下线工作负载重连时不产生额外数据访问权。

### BE-015 核验合同

- **BE-015-P · 输入/动作与合格判据：** 错信任域/服务证书/下线工作负载→身份验证和业务权分开。
- **BE-015-F · 直接失败变异：** SVID有效就任意读客户数据→失败。
- **BE-015-N · 合法邻例：** 未采用SPIFFE可用其他受支持身份方案。

## 十六、服务到服务授权与多跳委派
1. 跨服务调用必须明确是服务自身权利、代表用户的委派还是外部客户授权，按最小目的传递适合接收方的受众、范围和可追溯来源。
2. 采用 Token Exchange 时按实际支持的 RFC 8693、发行方协议和授权决议核验原主体、实际执行者、目标受众及授予的权限范围。受众限定或其他委派也必须遵守真实许可，不能直接将用户原始 Access Token 不加判断广播到所有下游，也不能借交换动作扩大原委派权限。
3. 异步消息、回调、Webhook 或 Agent 子任务的再委派不得获得比原授权更广的资源和动作；被撤销的委派按可执行控制及时失效。
4. **验收**：调用链 A→B→C 中 C 不能越过真实用户、租户与 B 的权限条件，不用 B 的管理员服务令牌隐藏越权。

### BE-016 核验合同

- **BE-016-P · 输入/动作与合格判据：** A代表用户调用B再C→actor/subject/aud与许可不扩大。
- **BE-016-F · 直接失败变异：** 广播原Token或B用管理员令牌掩盖越权→失败。
- **BE-016-N · 合法邻例：** 服务自身有独立合法权利须明确而非冒委派。

## 十七、OAuth 客户端和授权服务器元数据
1. 使用 OAuth 的系统按实际客户端类别区分公共、机密和服务端应用，维护真实 Redirect URI、Client ID、授权方式与密钥的权威配置。
2. 根据 RFC 9700 和实际提供方契约核对 PKCE、防混淆、发行方与重定向、防令牌泄漏等措施；不能将 OAuth 2.1 未完成的草案声称为已发布的强制 RFC。
3. 若选用 RFC 8414 元数据，核对信任的 Issuer、发现地址、认证端点、受支持方法和密钥轮换；恶意声明的 Discovery URL 不得成为自动授权或 SSRF 入口。
4. **验收**：多提供方、错 Issuer、重放 Code、错误回调和密钥被撤销时不成功建立非法会话。

### BE-017 核验合同

- **BE-017-P · 输入/动作与合格判据：** 多IdP/恶意Discovery/旧code→issuer与端点信任固定。
- **BE-017-F · 直接失败变异：** 用户给URL自动抓发现并信任→失败。
- **BE-017-N · 合法邻例：** 不使用发现机制可固定官方端点。

## 十八、令牌重放、防冒用与发送方约束
1. 高风险或盗用影响较大的令牌按照真实威胁和平台支持选择短生命周期、受众限制、DPoP、mTLS-bound Token 或其他具备真实证明的手段；不强制所有原型引入复杂持证机制。
2. 采用 RFC 9449 DPoP 时核对有效证明、HTTP 方法及 URI 绑定、密钥指纹、jti/时间与实际重放防护；采用 RFC 8705 时核对客户端证书与令牌绑定。
3. 使用 Bearer Token 的系统应清楚其被取得即可被持有者使用的风险，严格控制存储、日志、URL 和跨域传播，并遵守服务端撤销和权限检查。
4. **验收**：窃取的 Access Token 跨目标服务器重放、无有效 DPoP Proof、证书不匹配、证明重放都不能越过所选安全契约。

### BE-018 核验合同

- **BE-018-P · 输入/动作与合格判据：** DPoP错htu/htm/jti/密钥或mTLS证书不匹配→拒绝重放。
- **BE-018-F · 直接失败变异：** Bearer窃取风险被签名有效掩盖→失败。
- **BE-018-N · 合法邻例：** 低风险不需强制所有原型发送方约束。

## 十九、Webhook、任务事件与异步授权延续
1. 对队列任务和外部 Webhook 保存必要来源、主体、授权或业务委派事实、时间与动作范围；签名有效只证明发送方控制相应密钥，不自动使消息中的资源操作获得权限。
2. 实际运行时核对权限是否需要重新确认：撤销、离职、组织移除、订单失效和敏感操作延迟执行的条件不得因排队而冻结为永久授权。
3. 对必须在原权限有效时继续完成的合同操作，记录明确批准的业务事务条件和撤销边界；不能把所有异步动作简单粗暴改为“停掉”损害已发生权益。
4. **验收**：任务积压、消费者重放、签名过期、业务主体撤销与跨租户消息重复时均无未授权副作用。

### BE-019 核验合同

**必要机制补充：** 执行世代只有在目标写入/效果边界被验证才构成栅栏：先原子安装新世代，再允许新执行者写入，旧世代检查与写入处于同一受控原子边界。本地租约到期、取消请求发出、Worker进程失联或代理断开都不证明旧在途操作已停止；已发外部操作仍按原意图查询。

- **BE-019-P · 输入/动作与合格判据：** 积压旧任务/撤权/重复签名→执行时许可和事务边界正确。
- **BE-019-F · 直接失败变异：** 签名有效即冻结永久权限→失败。
- **BE-019-N · 合法邻例：** 已受理独立合同义务可按显式规则续作。

## 二十、长连接、流式订阅与权限变化
1. WebSocket、SSE 和 gRPC 长流必须在握手或初始化时验证身份及资源访问权，同时定义连接存活期间的权限、成员关系、账户状态更新处理。
2. 订阅哪个租户、项目或主题是受保护的业务决定，连接建立后再切换资源不能直接沿用旧订阅的许可。
3. Token 到期或角色撤销后，依据项目的实时性与风险决定重新认证、限期、主动断开或减少可见数据；不能无限使用失效身份持续接收敏感流。
4. **验收**：订阅后被移除组织、恢复旧连接、Reconnect 变换账号和请求其他频道时无跨用户泄露。

### BE-020 核验合同

- **BE-020-P · 输入/动作与合格判据：** 流中移除组织/换频道/重连错账号→资源可见性及时收敛。
- **BE-020-F · 直接失败变异：** 握手一次允许无限期敏感订阅→失败。
- **BE-020-N · 合法邻例：** 同主体合法多个频道独立授权。

## 二十一、批量接口、搜索和字段输出
1. 对批量 API、分页、按条件删除、搜索、聚合、导出和异步报表统一适用对象与字段权限，不允许通过查询条件枚举未授权 ID。
2. 返回集合应按授权主体及实际数据许可过滤，统计数量若本身敏感则应考虑其业务可见性，不以过滤后返回空列表掩盖系统权限绕过。
3. 批量更新中已授权和未授权对象混用时，按项目事务及业务合同明确全部拒绝、部分成功或明细报告，不进行静默非法修改。
4. **验收**：用户只能访问自己的详情却可按列表读所有人、导出隐藏字段、批量修改他人对象等路径均应被定向测试和阻断。

### BE-021 核验合同

- **BE-021-P · 输入/动作与合格判据：** 详情仅自有但列表/聚合/批改混他人→集合/字段同样授权。
- **BE-021-F · 直接失败变异：** 列表绕过对象检查或静默批量越权→失败。
- **BE-021-N · 合法邻例：** 合同允许部分成功时给逐项结果。

## 二十二、资源层和属性层的序列化防护
1. 服务端 DTO、ORM、序列化、GraphQL Resolver、对象映射和字段投影都要有真实的权限裁剪，不能靠前端不显示或禁用输入控件处理。
2. 更新操作对受控字段、关联关系、权限状态、金额和服务内部版本实行白名单或等价的显式契约，不将绑定的请求体对象直接整体写回权威模型。
3. 操作信息保真与敏感信息最小化同时满足：有权用户需要的关键业务条件必须保留，未授权用户不应收到无关的私人字段。
4. **验收**：新增内部模型字段后、修改 serializer、上传 GraphQL 查询片段、批量 PATCH 时不产生 Mass Assignment 或过度数据暴露。

### BE-022 核验合同

- **BE-022-P · 输入/动作与合格判据：** 新增模型字段/GraphQL片段/动态PATCH→输出和写入白名单保持。
- **BE-022-F · 直接失败变异：** 模型全量序列化漏隐私字段→失败。
- **BE-022-N · 合法邻例：** 有权用户必需条件不因最小化被删。

## 二十三、授权审计与可查询证据
1. 对重要数据读取、权限修改、对外共享、生产管理及不可逆操作，记录足以复核的业务主体、实际执行身份、资源、动作、规则版本和授权结果。
2. 调试日志、追踪 ID 和运营分析不是面向所有客户可公开的内容；日志本身应受权限和保留策略控制，不得包含原始访问令牌与长期密钥。
3. 对 Agent 的工具调用区分用户批准、Agent 受权执行、服务端对象授权和最后外部系统完成，不以模型自述填充审计记录。
4. **验收**：在有限的授权查询范围内，可定位一个越权拒绝、一次真实批准及相应版本，并避免因记录本身泄露敏感资料。

### BE-023 核验合同

- **BE-023-P · 输入/动作与合格判据：** 追一拒绝/一批准到规则版本和实际执行→审计可查且受控。
- **BE-023-F · 直接失败变异：** Agent自述填真实批准或日志带原Token→失败。
- **BE-023-N · 合法邻例：** 最小证据不需公开完整私有请求。

## 二十四、异常处理、拒绝状态及资源存在性
1. 身份失败、权限不足、对象不存在、业务状态冲突、租户禁止和第三方授权失效应按真实合同区分，不统一对外返回可以泄漏敏感实现细节的任意错误。
2. 401、403、404 及 RFC 9457 错误细节的使用须与相邻规范 HTTP API 专项一致；根据权限选择是否暴露资源存在性，不伪造已完成操作。
3. 策略评估器、身份提供方和密钥服务故障时，保持可见的受控失败或事先批准的可继续业务路径，不能任意放宽授权。
4. **验收**：无效令牌、过期用户、未授权资源、丢失 IdP 连接、错误 JWT 类型及异常权限缓存均有可诊断但不越权的响应。

### BE-024 核验合同

- **BE-024-P · 输入/动作与合格判据：** 401/403/404/IdP断连/错Token→信息最小且不虚报完成。
- **BE-024-F · 直接失败变异：** 错误缓存或异常放宽授权→失败。
- **BE-024-N · 合法邻例：** 为保护存在性可统一有权定义的错误外观。

## 二十五、策略与密钥的版本迁移和回收
1. 授权策略、JWT 颁发方、密钥/证书、租户模型或身份系统升级前固定消费者、旧 Token 支持、会话存续、长期任务和安全风险窗口。
2. 对密钥轮换、证书废止、Token Revocation、异常登录、成员离任和数据转移设置明确的实际执行与回滚／前向修复措施，不能凭文档更新宣称旧凭据失效。
3. 权限收窄应保护已合法完成业务操作和保存证据，权限扩张必须具备对应权利主体批准；“工具安装”不导致任何服务端隐式扩权。
4. **验收**：新旧令牌与服务交错、签名密钥轮换、撤销传播和缓存重建时，合法业务不中断且越权不会恢复。

### BE-025 核验合同

- **BE-025-P · 输入/动作与合格判据：** 旧新Token/密钥轮换/撤销/回滚→合法重叠窗与强制失效都可证。
- **BE-025-F · 直接失败变异：** 文档改了就声称凭据已失效→失败。
- **BE-025-N · 合法邻例：** 有权解密历史数据与允许旧凭据新写是不同权利。

## 二十六、运行测试与安全门禁
1. 按对象、属性、函数、租户、服务身份、委派、撤销和异步延续组合设计负向测试，尽量从资源与操作真实入口执行，而不是只测试一个权限工具类。
2. 高影响调用按项目风险选择合同检查、API/集成、跨租户 E2E、恶意字段输入、日志审查、令牌错 Issuer、密钥轮换与长连接测试。
3. OWASP ASVS 5.0.0 和 API Top 10 属可选用的安全验证框架与风险参考，项目需明确自身被批准采用的控制项及真实测量范围，不能因静态安全工具报告通过而宣称 ASVS 全面合规。
4. **验收**：每项高风险拒绝测试必须包括**实际没有发生副作用**的证据；无法运行真实系统时报告未执行，不以文本场景覆盖假装完成防渗透验收。

### BE-026 核验合同

- **BE-026-P · 输入/动作与合格判据：** 所有实际入口做负向调用并查权威→无副作用证据完整。
- **BE-026-F · 直接失败变异：** 只测权限工具类或扫描绿冒渗透通过→失败。
- **BE-026-N · 合法邻例：** 按风险选ASVS控制不虚构全量认证。

## 二十七、静态失效场景矩阵
| 失效条件 | 实际需要的独立证明 | 应满足的授权结果 |

## 二十八、规范边界、批准与项目采纳
1. 本 L4 具体专题负责服务端**身份、JWT/OIDC/OAuth 使用、资源/属性/功能授权、跨租户与服务间委派、权限变更和相关 API 安全验收**；不取代 Web 浏览器登录 UI、HTTP 状态/缓存语义、RPC 流式协议算法、密码学底层、密钥管理平台和安全治理等邻接领域规范。
2. OAuth 和身份体系的官方资料只按实际选用的协议版本及正确适用范围直接引用；不引入未获批准的支付门槛、账户流程或客户共享限制，不强制业务简单的项目部署 OAuth Server 或 SPIFFE。
3. L5 对 Spring Security、Keycloak、Authlib、Go/Rust/Node.js 相关 SDK、OIDC 中间件、JWT 库、反向代理及具体工具链提供实现指南和版本核验；L6 明确角色、资源、租户、Issuer、Token 生命周期、权限政策及风险门禁，并实际测试。
