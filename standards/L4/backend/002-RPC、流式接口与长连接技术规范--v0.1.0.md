# L4 RPC、流式接口与长连接技术规范

**文档ID：** STD-L4-BACKEND-002　**版本：** 0.1.0　**状态：** adopted　**生效日期：** 2026-10-30

## 技术对象、协议依据与生效边界

本规范适用于**具有实际 RPC 或长连接需求**的后端：Unary RPC、服务端流、客户端流、双向流、浏览器 WebSocket、SSE、以及经代理暴露的流式接口。它规范跨网络调用的**方法契约、消息边界、生命周期、流控、失败与恢复、身份、版本和测试**；不强制将普通 HTTP API 改写为 gRPC，也不因产品需要实时反馈就默认建设 WebSocket 服务。
相应依据：[L4 后端与分布式系统领域通用基线](007-后端与分布式系统领域通用基线--v0.1.0.md)（后端领域通用基线）、[L4 HTTP API、错误与兼容演进技术规范](001-HTTP-API、错误与兼容演进技术规范--v0.1.0.md)（HTTP API）、[L4 领域模型与服务边界技术规范](013-领域模型与服务边界技术规范--v0.1.0.md)（领域模型）、[L3 通用工程规范](../../L3/001-通用工程规范--v0.1.0.md)（L3）、[L2 人类与 Agent 团队组织协作规范](../../L2/001-人类与-Agent-团队组织协作规范--v0.1.0.md)（L2）、[L1 全局治理补充规范](../../L1/001-全局治理补充规范--v0.1.0.md)（L1）。实际权限和环境依项目 L6 契约确定。
**技术原始来源直接引用：**
- [gRPC Core Concepts](https://grpc.io/docs/what-is-grpc/core-concepts/)、[gRPC over HTTP/2 Wire Protocol](https://github.com/grpc/grpc/blob/master/doc/PROTOCOL-HTTP2.md)、[Flow Control](https://grpc.io/docs/guides/flow-control/)、[Cancellation](https://grpc.io/docs/guides/cancellation/)、[Retry](https://grpc.io/docs/guides/retry/)、[Keepalive](https://grpc.io/docs/guides/keepalive/)、[Status Codes](https://grpc.io/docs/guides/status-codes/)、[Health Checking](https://grpc.io/docs/guides/health-checking/)：gRPC 官方协议或实现指南，须区分协议内容与不同版本 SDK 的实现能力。
- [Protocol Buffers Edition Guide](https://protobuf.dev/programming-guides/editions/)：采用 protobuf 时固定消息字段及 wire 兼容要求，不强制所有 RPC 使用 protobuf。
- [RFC 6455 WebSocket](https://www.rfc-editor.org/rfc/rfc6455.html)、[RFC 8441 WebSocket over HTTP/2](https://www.rfc-editor.org/rfc/rfc8441.html)、[RFC 9220 WebSocket over HTTP/3](https://www.rfc-editor.org/rfc/rfc9220.html)：IETF Standards Track，不同 HTTP 版本连接建立机制不可混用。
- [WHATWG HTML Living Standard — Server-sent events](https://html.spec.whatwg.org/multipage/server-sent-events.html)：EventSource、text/event-stream、事件 ID 与重连；属于持续更新规范，采用时检查目标浏览器与代理。
- [gRPC-Web 官方指南](https://grpc.io/docs/platforms/web/basics/)：浏览器使用 gRPC-Web 时的生成客户端和代理模式；不得将浏览器 gRPC-Web 等同原生 gRPC over HTTP/2 全能力或默认支持客户端／双向流。
协议级互操作、业务确认、资金与对象授权分别由对应权威承担。L5 固定编程语言、SDK、反向代理和运行时版本；L6 固定实际支持的客户端与验收条件。

## 核验口径与消费接口

维护者负责落实本文机制，领域/API/存储提供者负责其权威保证，验收者从实际受支持入口观察结果。输入固定源码/构建、配置、数据/协议版本、角色/租户、目标平台、故障时序和预算；权威观察对象为**RPC终态/消息序列/期限与独立持久业务操作收据**。真实执行入口为**锁定SDK双端流脚本或grpcurl、代理日志、慢读/半关闭/取消、业务结果查询**。逐章 P/F/N 分别为正常输入及判据、破坏该机制的直接失败变异、应继续成立的合法邻例；本章原有每项规则、原有验收与新增合同共同约束，不用单一通用案例替代具体子项。每个子项须在案例输入中保留其适用条件，并以自身原文规定的输出/不变量判定；复合章应拆记录各个观察量，不能以一个成功掩盖其他失败。

证据产物包括真实命令/用户动作、原始响应或事件、权威状态前后值、版本、时序、失败及恢复；尚无对应真实运行证据的场景状态为 `not-run`，标准库示例仅证明列明的局部边界。具体输入与命令见[执行入口](../../../examples/web-backend/RUNBOOK.md)，条款索引见[规范条款登记](../../../registry/requirements.json)，来源的有限支持命题见[逐命题来源映射](../../../sources/web-backend/claims.json)。

本文的跨组件约束与正例、失败反例、合法邻例由本规范综合定义；外部来源支持的机制及适用边界见来源表。项目架构、预算和业务规则由实际需求确定。L5 实现应映射到所选框架、SDK 或引擎；L6 按具体版本的提供者保证与受支持矩阵验收项目能力。

## 一、通信方式选型与必要性
1. 按调用方向、消息频率、数据体积、延迟与双向性、断线恢复、设备网络和部署限制，在 HTTP 请求响应、SSE、WebSocket、gRPC 等方案间作有证据的选择。
2. 只需要低频状态查询时可使用普通 HTTP；仅服务端推送到浏览器时考虑 SSE；真正持续双向交互才考虑 WebSocket 或双向 RPC。对浏览器无法直接支持的 gRPC 传输能力，应评估 gRPC-Web／兼容代理或替代协议。
3. 协议选择应记录连接代理限制、身份与会话、资源成本、旧客户端、可维护性和业务终点；不得用“实时”“高性能”宣传词代替测量。
4. **验收**：在目标平台和预计负载下，从实际入口完成同一业务任务，确认选择的协议确有必要且无隐藏的数据完整性损失。

### BE-001 核验合同

- **BE-001-P · 输入/动作与合格判据：** 目标平台同任务比较HTTP/SSE/双向RPC→必要性和成本有证据。
- **BE-001-F · 直接失败变异：** 只因实时宣传引入长连接却漏恢复→失败。
- **BE-001-N · 合法邻例：** 低频状态读取可普通HTTP。

## 二、服务与方法契约
1. 每个 RPC 方法或流入口定义调用方、权限、输入消息、错误类型、完成条件、是否允许部分结果、是否有外部副作用和取消后的处理职责。
2. 方法名称、服务版本与业务命令身份不得互相替代。传输方法的成功仅说明相应调用契约成立，不等于所有异步下游或商业结算完成。
3. 对 gRPC 明确使用 unary、server-streaming、client-streaming、bidirectional-streaming 哪一种；客户端和服务端消息边界、结束方式和可观察结果必须一致。
4. **验收**：针对实际消费方的 IDL、实现与业务端到端结果核对；生成 Stub 编译通过不能替代双端合同测试。

### BE-002 核验合同

- **BE-002-P · 输入/动作与合格判据：** IDL真实双端正常/部分/错误调用→输入、身份、终点一致。
- **BE-002-F · 直接失败变异：** Stub编译绿当外部业务完成→失败。
- **BE-002-N · 合法邻例：** 无部分结果的unary可简化流状态。

## 三、IDL 与消息版本兼容
1. 如采用 protobuf，遵循项目锁定版本的字段编号、字段存在性、默认值、oneof、枚举、未知字段及 wire 格式约束，已对外发布的字段编号不得重用；删除旧字段时保留 reserved 编号及适用名称。
2. 类型、精度、货币、时间、来源、租户及业务状态含义由真实领域契约决定，不得因代码生成器的语言默认值而改变含义。
3. 扩展或退役消息字段须测试项目支持的旧／新客户端及服务端组合；protobuf wire 兼容不等于业务语义、JSON 映射或网关转换必然兼容。
4. 对其他 IDL 或二进制协议同样按其正式来源和项目支持的工具版本实施契约演进，不强制 protobuf。
5. **验收**：旧生成客户端解析新消息、新服务解释旧消息、未知枚举、缺省值、被移除字段和历史事件重放均满足承诺。

### BE-003 核验合同

- **BE-003-P · 输入/动作与合格判据：** 旧新proto/JSON/未知枚举/删除字段→编号和语义兼容。
- **BE-003-F · 直接失败变异：** 重用字段号或wire兼容冒JSON也兼容→失败。
- **BE-003-N · 合法邻例：** 其他IDL可按其版本合同实现。

## 四、gRPC over HTTP/2 传输及调用终态
1. 原生 gRPC over HTTP/2 的请求与响应按项目选定版本和官方 Wire Protocol 检查 Content-Type、消息包封、metadata 与 trailers；不可简单将 HTTP 200 等同于 gRPC 业务成功。
2. 确认收到最终 gRPC status、结束标识和实际消息序列，再判断 RPC 层已完成；中间代理剥离 trailers、错误转译或不符合 gRPC 的响应须按客户端契约处理。
3. 压缩与消息长度限制、header/trailer 容量、TLS 和代理 h2 配置应与实际客户端与服务器版本一致；不能通过泛用 HTTP/1.1 代理自动假设完整原生 gRPC。
4. **验收**：正常流结束、Trailers-Only、非 gRPC 错误页、代理重置流、提前断开和最终错误码均能被目标 SDK 正确识别。

### BE-004 核验合同

- **BE-004-P · 输入/动作与合格判据：** Trailers-Only/HTTP200但grpc-status非0/代理去trailers→SDK识别终态。
- **BE-004-F · 直接失败变异：** 只HTTP200即判RPC成功→失败。
- **BE-004-N · 合法邻例：** 合法无消息成功流按实际方法契约处理。

## 五、RPC Deadline、超时与传播
1. 由调用目标与资源成本制定 deadline/timeout，上游超时不能让所有下游调用无限等待；对子调用传递剩余预算并检查排队消耗。
2. Deadline 到达时，客户端观察到的 DEADLINE_EXCEEDED 不足以证明服务端未曾提交事务或外部副作用；要有结果回读或业务幂等方案。
3. 按不同操作类型区分连接握手时间、首字节时间、流空闲时间、整体执行期限与业务任务保留期，不把单一 Socket Timeout 当作全部生命周期。
4. **验收**：慢下游、多级 RPC、客户端断网、队列拥塞及时钟差异时，最终可用时间预算真实生效，外部副作用不会被重复触发。

### BE-005 核验合同

- **BE-005-P · 输入/动作与合格判据：** 三跳排队+剩余deadline传递→总预算不重置。
- **BE-005-F · 直接失败变异：** 每跳给满timeout或超时当未提交→失败。
- **BE-005-N · 合法邻例：** 独立异步任务的业务保留期可长于RPC。

## 六、取消与已经发生的副作用
1. gRPC 取消、HTTP Abort 和 WebSocket 关闭都属于传输或计算意愿的改变，不能自动撤回已经写入数据库、扣费、发送消息或对外下单的结果。
2. 按项目合同决定取消哪些计算、清理哪些资源、保留哪些异步工作流；重要的不可逆副作用通过权威操作 ID 查询实际状态。
3. 长链路取消应在有权范围内向下游传播，但不得由代理取消导致其他主体独立拥有的业务任务被无授权销毁。
4. **验收**：取消发生于读取前、处理途中、已提交后以及响应传输途中，均有确定的可查询状态、资源释放和重试条件。

### BE-006 核验合同

**必要机制补充：** 执行世代只有在目标写入/效果边界被验证才构成栅栏：先原子安装新世代，再允许新执行者写入，旧世代检查与写入处于同一受控原子边界。本地租约到期、取消请求发出、Worker进程失联或代理断开都不证明旧在途操作已停止；已发外部操作仍按原意图查询。

- **BE-006-P · 输入/动作与合格判据：** 在读取前/提交中/提交后取消→资源清理与业务结果分开。
- **BE-006-F · 直接失败变异：** Cancel即显示付款撤回→失败。
- **BE-006-N · 合法邻例：** 其他主体独立任务不能被代理取消销毁。

## 七、Unary RPC 的错误和恢复
1. 对正常请求、格式无效、业务状态冲突、权限不足、资源不存在、资源耗尽、临时不可用与 Deadline 分别选择真实 gRPC Status，不把所有失败转为 UNKNOWN 或 INTERNAL。
2. gRPC Status 与 HTTP Status 不可用机械数值互换；网关进行 JSON/HTTP 错误转换时必须建立对应的公开契约和异常语义。
3. 如需详细错误字段，按具体项目采用的 gRPC 错误细节机制与版本固定，不公开内部堆栈、客户信息及敏感 metadata。
4. **验收**：旧生成客户端对正常、错误和代理中断情况能正确修复或安全停止，不误重复执行写入。

### BE-007 核验合同

- **BE-007-P · 输入/动作与合格判据：** 业务拒绝/无权/资源耗尽/代理断流→状态和恢复分清。
- **BE-007-F · 直接失败变异：** 所有错误UNKNOWN或机械互换HTTP数值→失败。
- **BE-007-N · 合法邻例：** 有权详细错误可用已定扩展机制。

## 八、服务端流的消息与终态
1. 定义流消息的领域含义、序列号或业务身份、是否允许部分进度、终止状态和客户端如何确认完成；收到首条或最后一条消息不必然表示业务已提交。
2. 长流断线时区分已展示的信息、已持久交付的消息与尚未产生的内容，选择快照重拉、游标重放或明确从头开始。
3. 对业务数据有顺序要求时明确**单条流内可保障的顺序**以及跨连接／跨分区是否还有额外顺序契约；不把单流顺序推导为全系统全局顺序。
4. **验收**：消息中途断线、服务端尾部报错、慢消费者、重新订阅和权限变化后，用户状态准确且无信息错配。

### BE-008 核验合同

- **BE-008-P · 输入/动作与合格判据：** 流末尾错误/缺口/重订阅→部分数据和最终结果不混。
- **BE-008-F · 直接失败变异：** 收到最后内容片即认定成功→失败。
- **BE-008-N · 合法邻例：** 不承诺重放可用权威快照重拉。

## 九、客户端流的接收、累计和提交
1. 对客户端连续发送的流定义每个消息的大小、编码、校验和、业务操作 ID、截止与结束标记、部分接收失败和最终确认。
2. 明确是“收到部分即可产生合法效果”，还是“完整接收后一次原子提交”；尤其对文件、订单批次和模型输入不能由传输分块数决定业务提交数。
3. 当客户端半关闭写方向后等待最终响应时，服务端必须按照已批准合同完成或受控拒绝，不把半关闭误认为整个会话不可用。
4. **验收**：迟到消息、重复分块、客户端异常退出、空流、超大流和完成响应丢失后，服务端可验证是否执行过副作用。

### BE-009 核验合同

- **BE-009-P · 输入/动作与合格判据：** 空流/重复块/半关闭/最终响应丢失→累计与提交身份可查。
- **BE-009-F · 直接失败变异：** 按分块数决定业务提交数→失败。
- **BE-009-N · 合法邻例：** 允许合法逐块效果时记录各块结果。

## 十、双向流的独立读写生命周期
1. 双向流的两个方向各自有输入、输出、背压、顺序和结束条件，不能假设服务器只能在全部请求收完后开始响应，或必须逐条一问一答。
2. 对互动式协议定义关联 ID、并发中的消息归属、过期响应处理、半关闭、异常终止和资源清理；不要仅凭传输次序推断业务匹配关系。
3. 如果双向流中不同请求可能引发持久业务操作，每条操作仍应有独立领域身份、授权和幂等约束，不以连接 ID 替代。
4. **验收**：交错输入输出、独立方向结束、突发消息、双方同时取消、重连与旧响应迟到时，实际业务状态可复核。

### BE-010 核验合同

- **BE-010-P · 输入/动作与合格判据：** 双向交错/两端半关闭/旧响应→每条操作关联正确。
- **BE-010-F · 直接失败变异：** 连接ID替代所有业务意图或一问一答死等→失败。
- **BE-010-N · 合法邻例：** 方法可在请求未全部结束时响应。

## 十一、消息封装、大小和压缩
1. 按实际 SDK 与代理合同规定单消息最大大小、metadata 大小、压缩方式、解压后负载上限与序列化失败处理；避免以网络帧界限误当应用层消息完整界限。
2. 对不可任意装入内存的大对象选择分块流或外部对象存储引用；分块是否被最终确认由业务协议决定。
3. 压缩与 CPU、内存、延迟、安全及隐私之间的权衡应通过真实测量；高压缩比、深嵌套、异常编码和非法帧需有受控拒绝机制。
4. **验收**：最大合法消息、超限、损坏压缩、混合编解码版本和恶意消息不会造成资源失控或隐藏的数据丢失。

### BE-011 核验合同

- **BE-011-P · 输入/动作与合格判据：** 最大合法/超限/坏压缩/非法帧→解压后资源也有界。
- **BE-011-F · 直接失败变异：** 网络帧边界当业务消息边界→失败。
- **BE-011-N · 合法邻例：** 大对象可分块或引用而非全装内存。

## 十二、流量控制与反压机制
1. 结合 gRPC 官方流控及传输层窗口理解发送调用的含义：应用向 SDK 写入成功**不必然表示消息已离开进程，更不代表已被对方业务消费**。
2. 当消费者处理速度下降时，实施可证实的有界缓冲、请求/响应流控、消费速率反馈、任务降载或拒绝策略；禁止无界队列让流长期占用内存。
3. 队列满或负载超过预算时明确丢弃、合并、持久化与重放的允许范围；金融、权限、审计和用户关键数据不能未经批准被当作可丢弃的实时样本。
4. **验收**：慢消费、瞬时高吞吐、负载恢复与异常取消后缓冲数量、资源消耗、消息总量和实际业务状态可核对。

### BE-012 核验合同

**必要机制补充：** 双向流双方大量同步写而不读可能死锁。读写任务应能持续推进，明确手动流控许可、队列上限与取消；不能以扩无界缓冲作为解除死锁的方案。

- **BE-012-P · 输入/动作与合格判据：** 双方大写且慢读→有界背压、可持续并行读写无死锁。
- **BE-012-F · 直接失败变异：** 两端只同步大量写不读或write返回当已消费→失败。
- **BE-012-N · 合法邻例：** 流控不适用于强行给unary加手动读窗。

## 十三、长连接资源与公平调度
1. 对每连接／租户／客户端并发流数、内存、发送缓冲、订阅数量、心跳与最大空闲时长设置与真实负载相称的预算，防止少量滞留连接耗尽服务容量。
2. 处理半开连接、网络地址变化、反向代理长时间无数据、移动端后台及防火墙空闲清理，不能将 Socket 存活当作用户仍有权限或订阅仍有效。
3. 多租户共享连接时每个消息和订阅都应核对对应可见性和配额，不能仅在最初握手做一次永久授权。
4. **验收**：长期空闲、高并发重连、慢客户端、用户登出与令牌失效时服务容量和权限不被破坏。

### BE-013 核验合同

- **BE-013-P · 输入/动作与合格判据：** 空闲/半开/高并发重连/撤权→连接租户预算和权限收敛。
- **BE-013-F · 直接失败变异：** socket活着就永久订阅权→失败。
- **BE-013-N · 合法邻例：** 合法多连接不应无依据一律拒绝。

## 十四、重试、透明重试与业务幂等
1. gRPC 的默认透明重试和可配置重试策略按当前官方实现理解；缺省没有统一的业务安全重试策略，开启特定 Status 重试前必须评估服务端是否已实际执行。
2. 对写入或外部副作用调用使用真实的操作身份、幂等键或结果查询，不凭 UNAVAILABLE、Deadline 等错误码推断可无条件重新执行。
3. 设置重试次数、间隔、Backoff、抖动、整体 Deadline 和上游配额，避免服务故障时重试风暴扩大事故。
4. **验收**：服务端已提交但客户端未收到 Trailers、透明重试、部分流重传和重复请求均无未经批准的二次写入。

### BE-014 核验合同

**必要机制补充：** 逻辑意图ID在安全重试间保持不变，每次发送另分配尝试ID；事务ID、事件ID、投递ID和Trace ID不得代替它。权威查询暂未发现记录、读副本落后、日志缺失、客户端超时均不证明原尝试不会随后提交。只有目标端对同意图实行覆盖所有在途/迟到尝试的原子唯一性，或有已安装的栅栏/终止与线性化屏障证明原尝试不再可生效，才可依合同重发；否则保持结果未知并继续有权核对，不新建意图绕过去重。有限去重保留窗须覆盖目标最后可能接受该意图的时刻、重放和恢复窗口；不能只比较本地派发时间。窗外仍可迟到时使用永久领域唯一性、目标拒旧期限/世代或有权人工核对。

- **BE-014-P · 输入/动作与合格判据：** 服务提交后丢trailers再重试→同意图去重且总预算有限。
- **BE-014-F · 直接失败变异：** UNAVAILABLE/Deadline直接新意图重写→失败。
- **BE-014-N · 合法邻例：** 明确从未到业务逻辑的透明重试按SDK条件允许。

## 十五、Keepalive、健康检查与业务就绪
1. 将连接 Keepalive（如 gRPC HTTP/2 PING）与服务 Health Checking、下游可用性及真实业务完成信号分开；PING 往返仅说明连接层可应答。
2. 客户端心跳频率须与服务端许可、LB/NAT 超时和容量预算协调。服务端不许可过于频繁的 PING 时可能通过 GOAWAY 拒绝，不能无限缩短间隔“修复”连接。
3. gRPC Health Check 如启用，其 SERVING/NOT_SERVING 应依据实际是否接受相应服务调用；后台异步业务和资金结果仍须独立检查。
4. **验收**：代理空闲、服务内核健康但领域依赖失败、服务优雅退出和连接重建时客户端可以区别连接状态、服务就绪与任务终态。

### BE-015 核验合同

- **BE-015-P · 输入/动作与合格判据：** PING成功但领域依赖失败/GOAWAY→连接/就绪/业务分清。
- **BE-015-F · 直接失败变异：** 缩短心跳无限追击或PING当业务完成→失败。
- **BE-015-N · 合法邻例：** 未采用health服务可定义等价就绪合同。

## 十六、WebSocket 握手与 HTTP 版本
1. 采用 RFC 6455 的 WebSocket 必须核对握手、Upgrade 或扩展 CONNECT、Origin、Subprotocol、TLS、代理和服务端身份合同；不能将 HTTP/1.1 的 101 握手机制原样套用于 HTTP/2。
2. HTTP/2 使用 RFC 8441 的扩展 CONNECT 前要确认服务器与中间代理协商并实际支持；HTTP/3 对应 RFC 9220，亦须按实际支持环境确定，不假定任何 CDN 自动兼容。
3. WebSocket 连接建立只确认传输通道与相应握手成功，不授予任何永久业务资源权限，也不表示已完成业务动作。
4. **验收**：跨 HTTP 版本、跨代理、错误 Origin、协议不匹配、TLS 配置变化与旧浏览器建立连接时符合协议并安全拒绝未授权请求。

### BE-016 核验合同

- **BE-016-P · 输入/动作与合格判据：** H1/H2/H3经真实代理握手→Upgrade或扩展CONNECT按协商。
- **BE-016-F · 直接失败变异：** 把H1的101原样要求H2→失败。
- **BE-016-N · 合法邻例：** 不支持扩展CONNECT可用明确受支持替代。

## 十七、WebSocket 应用消息与确认
1. WebSocket 文本或二进制帧、消息分片、Ping/Pong 与关闭码按 RFC 6455 原文实现，不在组织规范重复帧级算法；浏览器应用对控制帧的访问能力按实际浏览器 API 核对。
2. 为真实业务消息定义类型、版本、业务 ID、相关操作、请求—响应匹配、应用层 ACK、错误、授权和最大大小；WebSocket 连接内消息按序到达不构成跨重连全局业务可靠性。
3. 对发送成功、服务端收到、写入成功、下游最终完成分别有可核验状态；无 ACK 的业务命令不能因 send() 调用返回便报“已生效”。
4. **验收**：分帧、突发、多命令交错、客户端重连、重复业务消息及非法类型均得到符合契约的确认或安全拒绝。

### BE-017 核验合同

- **BE-017-P · 输入/动作与合格判据：** 分片/交错/非法消息/重传→应用ACK与领域操作对应。
- **BE-017-F · 直接失败变异：** send返回即报命令已生效→失败。
- **BE-017-N · 合法邻例：** 允许无可靠ACK的遥测需明确不承担必达任务。

## 十八、WebSocket 断线重放与会话恢复
1. 连接恢复需要区分**恢复身份**与**恢复订阅状态**，不得复用已经撤销的资源权限；旧连接未超时期间建立新连接要解决双订阅与重复消息。
2. 重连使用事件序列号、业务操作 ID、快照游标或服务权威查询来决定已处理和未处理部分；是否需要历史重放及保留期限须由产品实际要求决定。
3. 若服务不保证历史重放，应明确告诉客户端如何重新获取状态，不能从 TCP/WebSocket 的传输可靠性自动推断跨断线不丢失数据。
4. **验收**：网络闪断、移动设备恢复、多终端登录、客户端消息积压及服务升级期间旧连接存在时，状态、权限和业务幂等保持正确。

### BE-018 核验合同

- **BE-018-P · 输入/动作与合格判据：** 重连时旧连接尚存/错账号/窗口过期→身份和订阅恢复分开。
- **BE-018-F · 直接失败变异：** WebSocket可靠传输被推成断线零缺口→失败。
- **BE-018-N · 合法邻例：** 无历史服务时可重新取快照。

## 十九、SSE 的单向推送与事件 ID
1. 按 WHATWG EventSource 及 text/event-stream 描述服务器到客户端的单向事件流；客户端向服务端发送命令应另走受权 HTTP/RPC 入口，不把 SSE 宣称为双向协议。
2. 对 event、data、id、retry 与事件边界采用官方语法；如果实际使用 Last-Event-ID 重新连接，其值只提供恢复线索，服务端是否保留历史、支持重放仍要明确实现。
3. 事件负载如果表示订单、告警或生产状态，必须携带足够的业务身份、版本与授权条件；事件已经推送不等于事件后面的持久化或客户处理已经完成。
4. **验收**：单事件、多行 data、不同 event 名称、空 ID、重复 ID、断线重新连接与保留窗口过期时客户端能正确解释或安全恢复。

### BE-019 核验合同

- **BE-019-P · 输入/动作与合格判据：** 多行data/空ID/重复ID/Last-Event-ID→事件解析与恢复契约正确。
- **BE-019-F · 直接失败变异：** Last-Event-ID冒服务端必有持久历史→失败。
- **BE-019-N · 合法邻例：** SSE命令通过独立授权HTTP发送。

## 二十、SSE 代理缓冲、心跳与授权
1. 需核对真实代理/CDN 的响应缓冲、压缩、超时、缓存和连接数限制，保持流式数据按项目所需的节奏可见；不能因为服务器写入了 bytes 就假定浏览器已收到事件。
2. EventSource 的凭据模式、CORS、Cookie、CSRF 及 token 失效按所选浏览器与安全边界处理；不要将长期密钥放进可记录 URL 查询参数以弥补浏览器 API 限制。
3. 当服务端仅使用注释心跳或无业务数据时，客户端和运维必须区分传输存活与真实领域事件；服务端可在允许场景以受控状态关闭、重试或重新认证。
4. **验收**：反向代理默认缓冲、移动网络切换、身份过期、多标签同时订阅、超限连接和禁用缓存时实际流与权限可核对。

### BE-020 核验合同

- **BE-020-P · 输入/动作与合格判据：** 代理缓冲/心跳/过期Cookie/多标签→真实事件到达和权限可查。
- **BE-020-F · 直接失败变异：** 服务器write即认为浏览器已收到或Token放URL→失败。
- **BE-020-N · 合法邻例：** 注释心跳只表传输活性。

## 二十一、浏览器 gRPC-Web 与协议网关
1. gRPC-Web 在浏览器使用时按项目锁定的客户端、代理和服务器版本实现，不能假设普通浏览器可以直接访问原生 HTTP/2 gRPC 帧、trailers 与客户端／双向流全部能力。
2. 对转换层明确 HTTP 与 gRPC 状态、metadata、trailers、CORS、压缩、流式响应及错误的映射；必要时按应用真实需求改用 WebSocket/SSE 或一般 HTTP。
3. 浏览器与服务端分别验证身份、对象授权和跨版本协议语义；代理具有认证能力不自动获得支付、租户数据或领域决定权。
4. **验收**：gRPC-Web 与后端版本差异、代理意外转码、缺 trailers、错误响应、Web 客户端只支持部分流模式时不会默默显示虚假业务完成。

### BE-021 核验合同

- **BE-021-P · 输入/动作与合格判据：** gRPC-Web缺trailers/部分流模式经网关→映射正确且功能真实。
- **BE-021-F · 直接失败变异：** 假定浏览器原生支持全套gRPC双向流→失败。
- **BE-021-N · 合法邻例：** 业务可选SSE/WebSocket替代不支持模式。

## 二十二、代理、负载均衡与 TLS 入口
1. 从最终公网或内部受权入口核对 HTTP/2、WebSocket Upgrade／CONNECT、SSE 分块、gRPC trailers、反向代理超时及 TLS 终止，不能凭本机直连成功推断 CDN 路由可靠。
2. 对长连接的负载均衡、会话粘性、订阅分发及跨节点事件恢复明确真实保证；稳定连接不等于全局消费排序，也不等于重新连入同一节点。
3. 公开入口的 Host/Forwarded/Origin 等标头只能按可信代理范围使用，身份转发、回调地址与私有数据不得由任意客户端数据控制。
4. **验收**：代理重启、LB 节点切换、证书更新、长时间空闲、反压和 gRPC trailers 转发时，业务流结果及授权边界实际成立。

### BE-022 核验合同

- **BE-022-P · 输入/动作与合格判据：** 正式入口LB换节点/证书更新/反压→状态和授权贯穿。
- **BE-022-F · 直接失败变异：** 本机直连成功当公网链路可靠→失败。
- **BE-022-N · 合法邻例：** 不需粘性时可无状态负载分配。

## 二十三、身份、授权和跨租户流隔离
1. 在握手或 RPC 建立时核验身份，持久长连接中还应根据项目业务规则处理 token 过期、用户注销、角色撤销及事件订阅范围变化。
2. RPC metadata、WebSocket 子协议、SSE 查询参数和消息体中的自称管理员字段均不直接产生业务写入权限，重要操作按权威领域接口重新验证授权。
3. 发布订阅、消息重放、跨租户过滤和审计日志应严格保持租户作用域，不能从一个共享连接中向错误受众推送任何敏感信息。
4. **验收**：用户切换、直接猜测订阅标识、内部 Service Token 滥用、多连接同租户及异步补发时，都无越权推送或执行。

### BE-023 核验合同

- **BE-023-P · 输入/动作与合格判据：** 流中换租户/撤销成员/重放→每资源权限按合同收敛。
- **BE-023-F · 直接失败变异：** 握手一次即永久看所有频道→失败。
- **BE-023-N · 合法邻例：** 同租户合法多个订阅可独立继续。

## 二十四、优雅退出、滚动发布和旧客户端
1. 服务端关闭或滚动部署需明确停止接收新流、通知仍存活的调用者、允许已授权工作完成或转交、释放流资源及发布窗口。
2. gRPC 的 GOAWAY、WebSocket close、SSE 断开和业务任务取消各有不同含义，必须按实际协议和业务状态实施，不能都映射“任务失败”或“系统已回滚”。
3. 旧客户端所用消息版本、订阅字段、鉴权机制和运行平台在承诺支持期内仍需兼容或安全迁移，长期打开的页面不能假定全部自动刷新。
4. **验收**：滚动发布期间有进行中的双向流、慢消费者、旧 proto 客户端、旧标签页及待发消息，服务升级后的最终状态仍可复核。

### BE-024 核验合同

- **BE-024-P · 输入/动作与合格判据：** 滚动退出时慢流/旧proto/待发消息→排空/交接/重连可查。
- **BE-024-F · 直接失败变异：** GOAWAY一律任务失败或SIGTERM丢受理任务→失败。
- **BE-024-N · 合法邻例：** 可中断只读流可受控重连。

## 二十五、监控、追踪和流式业务指标
1. 按协议收集连接数、活跃流、消息吞吐、缓冲占用、重连率、最终 status、关闭原因、延迟与尾部等待；只看 TCP/HTTP 连接数会漏掉真实领域故障。
2. 区分 gRPC transport status、WebSocket close code、SSE error event、服务端事务结果和下游业务完成；可通过已批准的追踪标准关联，但不能将 Trace ID 当认证凭据。
3. 监控抽样和消息日志严格限制客户内容与隐私，过量日志不得拖慢流式请求或泄漏密钥；真实业务审计需要保留有权限的必要证据。
4. **验收**：从目标用户一次流式任务可追踪消息来源、重试、实际完成与未知部分，在流结束前中断仍能复原关键事实。

### BE-025 核验合同

- **BE-025-P · 输入/动作与合格判据：** 断流后以业务键追确认/重试/未知→各层status分清。
- **BE-025-F · 直接失败变异：** close code或Trace代付款事实→失败。
- **BE-025-N · 合法邻例：** 日志最小化不必记录完整敏感消息。

## 二十六、性能预算、容量与测试负载
1. 依据并发连接数、每流消息速率、传输窗口、TLS、代理、网络断连、CPU、内存和商业成本确定资源预算；不要采用所有项目统一的强制连接上限。
2. 对高频推送、海量消费者、慢客户端及双向流并发以真实环境做背压和资源使用测试，不能凭本机少量连接下的吞吐替代目标规模。
3. 在需要可靠保存的业务信息与允许丢弃的实时视觉更新之间明确定义不同队列策略，不以性能优化悄悄省略关键领域事件。
4. **验收**：受控负载、断网重连、网络限速和服务降载的资源峰值、尾延迟、消息损失条件及业务状态都可复算。

### BE-026 核验合同

- **BE-026-P · 输入/动作与合格判据：** 目标连接数/速率/慢消费者/恢复→峰值资源与业务损失边界可算。
- **BE-026-F · 直接失败变异：** 本机少量连接TPS冒容量达标→失败。
- **BE-026-N · 合法邻例：** 可丢视觉更新与必达事实可有不同队列策略。

## 二十七、静态验收案例矩阵
| 故障场景 | 重点机制 | 合格业务结果 |
| --- | --- | --- |
| 无双向需求却引入 WebSocket | 协议选型、资源成本 | 选择相称方案，不增加无必要复杂度 |
| 原生 gRPC 的 HTTP 200 掩盖错误 | Trailers、grpc-status | 按真实 RPC 终态正确处理 |
| 代理剥离 gRPC Trailers | 代理和 wire contract | 客户端受控失败，拒绝虚报成功 |
| 旧 proto 字段号被重用 | 字段编号和 reserved | 历史消费者解析无歧义和数据泄露 |
| RPC Deadline 之后任务仍扣费 | 超时与副作用 | 以操作 ID 查询，避免重复扣费 |
| 取消时数据库已提交 | 取消传播、事务 | 不虚构“已回滚”，真实状态可查 |
| 单向流收到部分进度便显示完成 | 部分消息与最终 status | 按实际完成契约呈现 |
| 客户端流中途断连 | 半关闭、分块和提交 | 业务完成或失败清晰，不误接收残片 |
| 双向流消息交错错配到客户 | 相关 ID 与授权 | 每条消息属于实际操作与租户 |
| 慢消费者造成缓冲无限增加 | 背压、限额 | 有界资源和有证据的降级 |
| 消息写入 SDK 但未送出 | 流控与实际确认 | 不因 enqueue 成功声明客户已接收 |
| 压缩异常导致内存耗尽 | 消息限制与解压预算 | 拒绝异常输入，不破坏其他请求 |
| 重试 gRPC 写入造成两次外部下单 | 透明重试、幂等 | 只保留有权且合法的业务效果 |
| 过频 Ping 收到 GOAWAY | Keepalive 协商 | 尊重服务端许可，不引发重连风暴 |
| 健康检查通过但下游全失败 | Transport vs business readiness | 准确区分连接、服务和业务结果 |
| WebSocket HTTP/2 握手使用旧 101 | RFC 8441 Extended CONNECT | 选定版本按真实握手协议工作 |
| WebSocket 未校验 Origin | 握手与跨站权限 | 拒绝未授权跨源操作 |
| WebSocket 断线重连重复发送命令 | 应用 ACK、消息 ID | 重复控制、持久结果回读成立 |
| WebSocket 全局广播泄漏其他租户 | 消息级订阅授权 | 严格租户隔离 |
| SSE 最后事件缺空行分隔 | text/event-stream 解析 | 按规范处理，不错误假定消息已发送 |
| SSE 重连 Last-Event-ID 无服务端历史 | 持久重放支持范围 | 按合同恢复快照或明确缺口 |
| 代理缓冲 SSE 推送数分钟 | 缓冲和实时性 | 流实际可见且性能符合目标 |
| 浏览器无法使用原生 gRPC 双向流 | gRPC-Web 支持矩阵 | 选择可用模式或替代协议，不伪装可用 |
| 长连接期间令牌过期 | 重新认证与权限更新 | 无过期身份继续推送或执行 |
| 滚动发布关闭流导致重复交易 | Drain、重连、幂等 | 业务结果唯一且可查询 |
| 服务健康但队列事件未消费 | 流式状态与真实业务完成 | 分别报告连接和最终业务结果 |
## 二十八、专项边界与审批条件
1. 本专项仅深入**RPC 方法与流式通信、WebSocket、SSE、长连接生命周期、传输状态与恢复**。领域规则归相应领域模型，HTTP API 通用语义归相邻规范 HTTP 专项，存储事务、消息可靠交付、服务身份及网络协议内核由相应 L4 专项处理。
2. 技术文本直接引用 IETF RFC、WHATWG Living Standard、gRPC/Protobuf 官方协议与指南，不建立重写版本；不同技术来源的规范地位和不同 SDK 的能力范围保持可核查。
3. L5 负责特定 gRPC/Protobuf 版本、SDK、WebSocket 库、服务器框架、代理和编译器配置；L6 确定具体支持的协议、流方向、旧客户端、负载和运行时质量门禁。
文本检查不意味着真实代理、浏览器、服务端流、数据库提交或用户业务结果已通过；制度批准及项目 L6 的实际运行验收分别登记。
