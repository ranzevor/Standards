# L4 缓存、一致性与衍生查询状态技术规范

**文档ID：** STD-L4-BACKEND-011　**版本：** 0.1.0　**状态：** adopted　**生效日期：** 2026-10-30

## 技术对象、上层权威和适用条件

本 L4 专项覆盖用于加速或派生读取的浏览器/HTTP 缓存、CDN、进程与分布式缓存、读副本、搜索索引、物化视图、聚合报表、CQRS 查询投影和变更流驱动的衍生状态。仅在系统实际上采用此类机制时启用对应条款。数据库物理复制内核、存储 Schema/索引/备份归数据库领域 L4；具体 Redis、PostgreSQL、Elasticsearch、SDK 和云服务配置归 L5；项目允许的陈旧程度、租户权限、服务目标及故障测试归 L6。
技术依赖：[L4 后端与分布式系统领域通用基线](007-后端与分布式系统领域通用基线--v0.1.0.md)（后端通用基线），[L4 领域模型与服务边界技术规范](013-领域模型与服务边界技术规范--v0.1.0.md)（领域和来源权威），[L4 事务隔离、并发与业务幂等技术规范](003-事务隔离、并发与业务幂等技术规范--v0.1.0.md)（提交及并发），[L4 消息事件与可靠交付技术规范](010-消息事件与可靠交付技术规范--v0.1.0.md)（消息交付），[L4 分布式业务工作流与一致性技术规范](004-分布式业务工作流与一致性技术规范--v0.1.0.md)（分布式工作流），[L4 服务身份、对象授权与 API 安全技术规范](009-服务身份、对象授权与-API-安全技术规范--v0.1.0.md)（身份与对象授权），以及 L1—L3。项目须选择准确版本并记录采用范围与决定。缓存层不得重新决定权威业务规则，也不得在性能与可用性选择中取消业务不变量。
## 正式协议、厂商资料与版本界限
- [RFC 9111 HTTP Caching — IETF Standards Track, 2022](https://www.rfc-editor.org/rfc/rfc9111.html)：采用 HTTP Cache-Control、shared/private、no-store、新鲜度及失效语义时适用；该协议不保证应用多层缓存的业务一致性。
- [RFC 9110 HTTP Semantics — IETF Standards Track, 2022](https://www.rfc-editor.org/rfc/rfc9110.html)：采用 ETag、If-None-Match、If-Match、条件写及表示身份时适用。
- [RFC 9211 Cache-Status — Proposed Standard, 2022](https://www.rfc-editor.org/rfc/rfc9211.html)：仅在 HTTP 缓存诊断需要时作为可选响应头规范，非业务结果证据。
- [RFC 5861 Stale Content — Informational, 2010](https://www.rfc-editor.org/rfc/rfc5861.html)：说明 stale-while-revalidate 与 stale-if-error，须依据实际部署缓存兼容性与业务允许陈旧窗口选用；并非 Standards Track。
- [Redis Keyspace Notifications — 当前厂商技术资料](https://redis.io/docs/latest/develop/pubsub/keyspace-notifications/)：官方明确 Pub/Sub 断线事件丢失，不能据此声称可靠全局失效。
- [Redis Client-side Caching — 当前厂商技术资料](https://redis.io/docs/latest/develop/clients/client-side-caching/)：Client Tracking 失效与重连清空的实际接口契约，须核对客户端版本。
- [Redis Key Eviction — 当前厂商技术资料](https://redis.io/docs/latest/develop/reference/eviction/)：内存、逐出策略与写入拒绝按部署版本和配置生效。
- [PostgreSQL 18 Logical Replication — 固定版本官方资料](https://www.postgresql.org/docs/18/logical-replication-subscription.html)：复制槽与初始数据同步、重建及 WAL 保留的实现边界，非所有数据库的统一行为。
- [PostgreSQL 18 Materialized View Refresh — 固定版本官方资料](https://www.postgresql.org/docs/18/sql-refreshmaterializedview.html)：并发刷新条件及替换语义只适用实际 PostgreSQL 版本与配置。
- [Elasticsearch PIT / Near real-time — 当前厂商技术资料](https://www.elastic.co/docs/api/doc/elasticsearch/operation/operation-open-point-in-time)：采用 Elasticsearch 时的搜索一致分页与可见性；近实时刷新另核对 [https://www.elastic.co/docs/manage-data/data-store/near-real-time-search](https://www.elastic.co/docs/manage-data/data-store/near-real-time-search) 。
所见版本、读取日期与有限支持命题见来源映射。IETF 正式协议、Informational RFC、固定版本产品文档与持续更新的产品指南分类引用。具体项目按实际产品版本、运行配置、实施章节与必要复核条件锁定，不让上游资料动态更新直接改写批准的项目契约。

## 核验口径与消费接口

维护者负责落实本文机制，领域/API/存储提供者负责其权威保证，验收者从实际受支持入口观察结果。输入固定源码/构建、配置、数据/协议版本、角色/租户、目标平台、故障时序和预算；权威观察对象为**源版本/删除墓碑/授权版本、各层命中与投影水位**。真实执行入口为**真实缓存/索引/CDC客户端、源库对照、受控读填充交错与失效断线**。逐章 P/F/N 分别为正常输入及判据、破坏该机制的直接失败变异、应继续成立的合法邻例；本章原有每项规则、原有验收与新增合同共同约束，不用单一通用案例替代具体子项。每个子项须在案例输入中保留其适用条件，并以自身原文规定的输出/不变量判定；复合章应拆记录各个观察量，不能以一个成功掩盖其他失败。

证据产物包括真实命令/用户动作、原始响应或事件、权威状态前后值、版本、时序、失败及恢复；尚无对应真实运行证据的场景状态为 `not-run`，标准库示例仅证明列明的局部边界。具体输入与命令见[执行入口](../../../examples/web-backend/RUNBOOK.md)，条款索引见[规范条款登记](../../../registry/requirements.json)，来源的有限支持命题见[逐命题来源映射](../../../sources/web-backend/claims.json)。

本文的跨组件约束与正例、失败反例、合法邻例由本规范综合定义；外部来源支持的机制及适用边界见来源表。项目架构、预算和业务规则由实际需求确定。L5 实现应映射到所选框架、SDK 或引擎；L6 按具体版本的提供者保证与受支持矩阵验收项目能力。

## 一、选型、成本与必要性
1. 只有实际读取延迟、读扩展、搜索或聚合需求证明收益时采用缓存或衍生视图。记录直接查询权威库、数据库索引与分页、预计算、缓存、只读副本及专用搜索的成本和维护取舍，不强制每个项目引入 Redis 或搜索引擎。
2. 按业务正确性、最坏延迟、数据规模、更新频率、基础设施费用及故障恢复成本选择方案；缓存故障不能使本来正确的源业务被视作不存在。
3. **验收**：按真实负载对照直读与衍生读的结果、尾延迟、成本及恢复路径。

### BE-001 核验合同

- **BE-001-P · 输入/动作与合格判据：** 同真实负载直读/缓存对照→正确性、尾延迟和恢复成本明确。
- **BE-001-F · 直接失败变异：** 缓存故障显示源业务不存在→失败。
- **BE-001-N · 合法邻例：** 没有收益可直接查权威库。

## 二、权威事实、衍生状态与读写责任
1. 明确每个字段／资源的唯一权威来源及允许的写入角色；浏览器缓存、CDN、应用内存、共享缓存、只读副本、搜索索引、报表物化和 CQRS 投影均是具体用途的衍生状态，除非业务正式将该存储定义为权威。
2. 不得以缓存命中或读副本持有某条数据推断最新业务承诺；订单、支付、权限、库存等重要动作仍以有权事务状态和外部结果为准。
3. **验收**：断开全部缓存时权威状态可查；缓存与搜索不一致时能指出谁负责修复。

### BE-002 核验合同

- **BE-002-P · 输入/动作与合格判据：** 断开缓存再读源→每字段权威可查。
- **BE-002-F · 直接失败变异：** 搜索命中当已付款、缓存擅升账本→失败。
- **BE-002-N · 合法邻例：** 业务正式将耐久存储定义权威时另验其保证。

## 三、一致性需求与逐操作契约
1. 为每类读操作选择并定义线性化读取、写后读、单会话单调读取、按已知版本不倒退、有限陈旧、最终收敛或允许过期的展示语义；不能用“最终一致”概括不同业务。
2. 写前资格校验、授权、扣费和发货按实时权威条件判定，允许延迟的搜索或统计须显式设置最大延迟与不可陈旧的字段范围；不同用户和操作可采用不同级别。
3. **验收**：同一业务变更后立即直读、跨节点及故障恢复，检验实际承诺的新鲜度和非法旧值阻断。

### BE-003 核验合同

- **BE-003-P · 输入/动作与合格判据：** 写后立即跨节点/分区读→选定一致性可观察。
- **BE-003-F · 直接失败变异：** 所有操作笼统称最终一致而无陈旧界限→失败。
- **BE-003-N · 合法邻例：** 公开统计可有明确有限陈旧。

## 四、写后读、会话水位与单调可见性
1. 对要求写后立即可见的操作，使用有权主读、版本令牌、服务端会话下界或经证明追上的读副本；仅靠固定 sleep 或随意重试不保证正确。
2. 携带并核对源变更版本、提交序号或对应安全水位，版本无法证明达到要求时等待受控、回源或明确失败；用户切换、租户变更不得共享水位。
3. **验收**：写入后跨多个服务节点读取，验证不会返回低于该操作已确认写入版本的状态。

### BE-004 核验合同

- **BE-004-P · 输入/动作与合格判据：** 带已确认版本下界跨节点读→不低于水位或回源/失败。
- **BE-004-F · 直接失败变异：** 固定sleep当副本已追平→失败。
- **BE-004-N · 合法邻例：** 不要求写后读的展示可按陈旧窗。

## 五、多级缓存拓扑与责任边界
1. 枚举浏览器、Service Worker、CDN、反向代理、API Gateway、进程 L1、分布式 L2 与数据库读副本；为每层记录拥有者、键、有效期、失效通道、传播时延及绕行入口。
2. L2 刷新不意味着每个 L1、浏览器和 CDN 已更新；清除路径必须覆盖实际存在的层，不得将某层的命中率代替整体用户可见性。
3. **验收**：命中不同缓存层和源库的请求在更新与撤权后均满足各自的有效性契约。

### BE-005 核验合同

- **BE-005-P · 输入/动作与合格判据：** 逐层命中L1/L2/CDN/浏览器→失效责任覆盖真实层。
- **BE-005-F · 直接失败变异：** 清L2就宣称所有客户端更新→失败。
- **BE-005-N · 合法邻例：** 不存在的缓存层不强加部署。

## 六、缓存键、变体与版本身份
1. 键必须覆盖真实决定结果的业务对象、租户、主体权限／可见范围、过滤排序、分页参数、语言时区、数据契约版本和必要的环境边界；不得直接把未可信的外部输入拼成可越权共享的键。
2. 同一资源在不同可见范围或版本下不能共用私有响应；超长、高基数和可控键空间须设置大小预算及拒绝恶意扩大。
3. **验收**：不同租户、不同权限、搜索条件、时区和版本组合不发生相互命中和错答。

### BE-006 核验合同

- **BE-006-P · 输入/动作与合格判据：** 同对象不同租户/语言/权限/版本→键变体隔离。
- **BE-006-F · 直接失败变异：** 未可信tenant输入直接拼共享键→失败。
- **BE-006-N · 合法邻例：** 相同授权的公共表示可共用。

## 七、表示结构、数据精度与业务保真
1. 缓存值和投影保留金额精度、计量单位、时区、枚举、状态来源、版本、合法空值及复杂领域差异；禁止以缩短序列化或高吞吐为由丢弃业务字段。
2. 序列化需要包含可识别 Schema 与必要来源版本，不能将空缺、零、未授权、未知和已删除压成同一默认值；压缩和聚合不改业务含义。
3. **验收**：单变量对照源数据、缓存、搜索及导出，关键字段精度与状态语义保持一致。

### BE-007 核验合同

- **BE-007-P · 输入/动作与合格判据：** 金额/null/未知/已删经序列化→原义和Schema可辨。
- **BE-007-F · 直接失败变异：** 默认零值混淆无权与不存在→失败。
- **BE-007-N · 合法邻例：** 无害压缩可不改变业务语义。

## 八、缓存读写策略与持久化边界
1. 按数据性质选择 cache-aside、read-through、write-through、write-around、write-behind 或只读 projection；不能将写回缓存当作数据库已提交，除非该缓存被确立为真实权威并有相应耐久协议。
2. write-behind 的丢失窗口、顺序、重复写与恢复必须被实际业务允许；涉及资金或权威事实的变更优先由已有事务专项保护，衍生写失败不倒置权威关系。
3. **验收**：更新时中断缓存、写队列、数据库连接并重启，验证权威写入和可恢复事实不丢失。

### BE-008 核验合同

- **BE-008-P · 输入/动作与合格判据：** 写缓存/队列/源库各点故障→权威提交边界清楚。
- **BE-008-F · 直接失败变异：** write-behind返回即称主库持久→失败。
- **BE-008-N · 合法邻例：** 业务允许且有耐久协议的写回可明确选用。

## 九、写入提交与缓存失效竞态
1. 源事务提交、失效消息发布与缓存填充间存在竞态。按范围选择版本校验、事务内 Outbox、提交后失效、代际键或带条件的更新，明确操作先后与未知结果恢复。
2. 旧读取在新提交之后才填充缓存时，不得把旧版本覆盖新数据；先删缓存再写数据库不能被当作自动原子一致性；失败需有补偿或可重建通道。
3. **验收**：注入读—写—失效—填充交错与发布失败，确保不会永久恢复旧业务值。

### BE-009 核验合同

**必要机制补充：** 防旧读回填需要在缓存写入点比较源版本/世代下界；失效后保留必要墓碑或版本栅栏，避免缓存逐出/TTL到期清除防护后旧读重新注入。保留窗覆盖最大在途读取/复制/回放延迟；无法证明窗口时回源或不服务敏感旧值。

- **BE-009-P · 输入/动作与合格判据：** 旧读暂停、新写失效、旧读回填→版本栅栏拒旧填充。
- **BE-009-F · 直接失败变异：** 仅删缓存后旧读取重填过期值→失败。
- **BE-009-N · 合法邻例：** 安全新版本回填可替代空缓存。

## 十、TTL、新鲜度与失效责任
1. 分别定义业务数据的有效性期限、缓存存活 TTL、最大可接受陈旧时间、强制失效条件和重新校验入口；过期不是业务事实删除，刷新也不能无条件延长无效授权。
2. TTL 是安全边界的补充，不替代及时撤权、业务取消或删除；关键数据可采用不缓存或每次复核；按热度及成本设计 TTL 抖动避免同一时刻大规模失效。
3. **验收**：时间回拨、暂停、到期、提前撤权和 TTL 风暴下的真实可见结果符合契约。

### BE-010 核验合同

- **BE-010-P · 输入/动作与合格判据：** 回拨时钟/到期/撤权与TTL风暴→新鲜度与业务时效分开。
- **BE-010-F · 直接失败变异：** TTL刷新延长已撤销授权→失败。
- **BE-010-N · 合法邻例：** 公开可陈旧数据可采用TTL抖动。

## 十一、失效通知的交付保证与断线恢复
1. 识别本地通知、Redis Pub/Sub、客户端 Tracking、Broker、数据库 CDC、管理清除接口的实际交付语义；明确订阅者离线、消息丢失、通知乱序和重新连接后的修复方式。
2. Redis Keyspace Notifications 的 Pub/Sub 是 fire-and-forget，不能作为唯一可靠的权限或业务失效证明；需持久修订版本、补偿扫描、断线清空本地缓存或经验证的等价同步。
3. **验收**：断开客户端失效连接、丢弃通知并重连，验证不会无限期提供已撤销旧数据。

### BE-011 核验合同

- **BE-011-P · 输入/动作与合格判据：** 失效订阅断线丢消息后恢复→清空/版本追赶或扫描。
- **BE-011-F · 直接失败变异：** Redis PubSub当耐久唯一撤权通道→失败。
- **BE-011-N · 合法邻例：** 持久失效日志可补齐离线窗口。

## 十二、缓存击穿、穿透和并发重建
1. 缓存未命中时对相同键设计受控并发回源、singleflight／按键限流、排队或准许的短期复用；锁的过期、旧填充者与故障切换需要版本核验。
2. 不得无限锁等待或采用跨租户复用保护值；高代价数据计算与远端配额需有预算，慢填充不得覆盖较新的源提交。
3. **验收**：热点键同时过期、一万并发请求与回源限流时源库、业务结果和缓存版本保持受控。

### BE-012 核验合同

- **BE-012-P · 输入/动作与合格判据：** 同热键并发未命中且旧填充者恢复→源负载有界且不覆新值。
- **BE-012-F · 直接失败变异：** 全局锁无限等待或跨租户复用保护值→失败。
- **BE-012-N · 合法邻例：** singleflight可按键合并合法并发读。

## 十三、空值、404 与错误缓存
1. 对不存在资源、合法空集合、权限拒绝、临时故障和未知查询结果规定独立表示与缓存范围；负缓存只在不存在状态可短时复用且能追赶新建操作时采用。
2. 禁止因权限错误被缓存为公共 404、因为源库超时被保存为“不存在”、或把认证失败结果跨主体共享；错误缓存须按协议与业务约束区分。
3. **验收**：资源被创建、权限授予、临时源错误恢复后，旧负缓存不会阻止合法读取。

### BE-013 核验合同

- **BE-013-P · 输入/动作与合格判据：** 缓存404后创建、权限授予/源超时恢复→空/无权/错误分开。
- **BE-013-F · 直接失败变异：** 源库超时存成不存在或私有拒绝公共共享→失败。
- **BE-013-N · 合法邻例：** 合法短期负缓存可追赶新建版本。

## 十四、权限撤销与受限数据一致性
1. 授权、租户成员、权益和字段可见性变化为独立强制失效对象。对高风险响应，查询时重新鉴权或以权威授权版本比对；合法用户的旧缓存读取不得绕过撤权。
2. 身份验证成功不意味着缓存内容已通过对象权限；共享 CDN、浏览器缓存、导出与后台管理入口必须分别处理越权风险，不凭 TTL 推断安全。
3. **验收**：撤销角色和对象权限后，旧键、旧 Token、边缘缓存和搜索结果均无法泄露受限数据。

### BE-014 核验合同

- **BE-014-P · 输入/动作与合格判据：** 撤销角色后用旧键/旧Token/索引读→拒受限字段。
- **BE-014-F · 直接失败变异：** 只等TTL而敏感数据继续供给→失败。
- **BE-014-N · 合法邻例：** 已授权公开字段可继续返回。

## 十五、删除、保留及隐私传播
1. 删除业务对象或个人数据时清理或隔离所有有权控制的缓存、搜索、队列、物化、日志和可恢复备份，区分业务删除、合法保留与法定义务。
2. 删除墓碑与保留期要覆盖延迟回放和搜索重建，避免历史 CDC 或快照将已删除数据再生成；缓存不能成为不受权限控制的长期副本。
3. **验收**：删除后执行增量重放、灾备恢复、权限切换及旧备份检索，禁止被删除数据非法再出现。

### BE-015 核验合同

**必要机制补充：** 删除墓碑/水位的清理须证明所有受支持快照、CDC、回放和恢复源不再能生成旧值；一次清缓存不是删除传播闭包。

- **BE-015-P · 输入/动作与合格判据：** 删除后旧CDC/备份重建→墓碑和保留规则防复活。
- **BE-015-F · 直接失败变异：** 旧快照回填已删除私人数据→失败。
- **BE-015-N · 合法邻例：** 法定保留可受限隔离且明确范围。

## 十六、HTTP 缓存标准适用与响应范围
1. 使用 HTTP 缓存时直接遵守 RFC 9111 的新鲜度、存储限制、private、no-store、no-cache、共享缓存鉴权和 unsafe 方法失效语义；区分公共静态内容与用户专属结果。
2. no-store 与 private 作用不同；非 GET 修改产生的规范内失效不保证全球所有缓存键均自动失效；组织需要的关联列表/聚合清除另立可靠机制。
3. **验收**：真实 CDN、网关与浏览器在认证请求、私有响应、变更后访问等情况下符合采用的协议与用户可见性。

### BE-016 核验合同

- **BE-016-P · 输入/动作与合格判据：** 实际HTTP共享/私有/认证请求→Cache-Control按协议生效。
- **BE-016-F · 直接失败变异：** private当no-store或修改自动清全球关联键→失败。
- **BE-016-N · 合法邻例：** 客户端private缓存仍须遵守其余缓存条件。

## 十七、HTTP 校验器、Vary 与条件请求
1. 采用 ETag、Last-Modified、If-None-Match、If-Match、304 和 Vary 时，分别依 RFC 9110/9111 保持表示版本与请求变体的正确关系；弱校验不能承担要求强写保护的业务版本 CAS。
2. 不得因 304 而复活已撤权字段；条件写依旧由领域权限和事务保障，缓存元数据不能取代业务主记录版本。
3. **验收**：测试语言、压缩、用户范围和代理之间的 ETag／Vary 变化及 304/412 的实际含义。

### BE-017 核验合同

- **BE-017-P · 输入/动作与合格判据：** 语言/编码/权限变化及304/412→验证器对应表示且鉴权仍强制。
- **BE-017-F · 直接失败变异：** 弱ETag当If-Match强CAS或304复活撤权字段→失败。
- **BE-017-N · 合法邻例：** If-None-Match可按其弱比较语义验证读取。

## 十八、允许陈旧的响应与降级策略
1. 仅对真正允许陈旧的结果配置 stale-while-revalidate、stale-if-error 或平台等价机制，按资源设置安全的最大陈旧窗口；RFC 5861 是 Informational，实施按实际缓存产品能力验证。
2. 不能对授权判断、当期价格与权益、资金状态及删除后的私人数据用“可用性”掩盖错误旧值；陈旧响应须有具体版本或用户可理解的实际时刻。
3. **验收**：源站超时、缓存重新校验失败与撤权同时发生时，不越过项目允许的陈旧边界。

### BE-018 核验合同

- **BE-018-P · 输入/动作与合格判据：** 源超时且撤权→只用合同允许的陈旧数据。
- **BE-018-F · 直接失败变异：** stale-if-error覆盖权限或删除事实→失败。
- **BE-018-N · 合法邻例：** 公开行情展示可标时刻不当交易权威。

## 十九、预热、缓存填充与发布切换
1. 部署、流量迁移与热门数据预热采用版本隔离、受控回源和容量预算；不要直接向正式键空间灌入未验收的过时快照。
2. 预热期间源数据变化需能按版本／水位补齐，失败时不把不完整预热切换为正式响应；数据与应用版本独立管理。
3. **验收**：灰度发布、高并发预热、源数据在预热中变化与回滚时没有冷启动雪崩或旧版本误答。

### BE-019 核验合同

- **BE-019-P · 输入/动作与合格判据：** 预热中源并发更新与失败回退→追水位后才切换。
- **BE-019-F · 直接失败变异：** 不完整旧快照灌正式键→失败。
- **BE-019-N · 合法邻例：** 无预热必要可冷启动加受控回源。

## 二十、多实例、地域与副本一致性
1. 跨实例或地域明确缓存复制、读写路由、故障域、最高可忍延迟、区域变更与主从切换的实际保障；不默认所有节点都已看见已确认的源提交。
2. 对需要会话单调性的请求采用按区域版本下界、回源或保持源区域；网络分区时不可用权威读应安全失败，不能凭旧副本擅自兑现或撤销权益。
3. **验收**：复制滞后、跨区路由、旧主恢复及分区期间不出现越权、非法写入或版本倒退。

### BE-020 核验合同

- **BE-020-P · 输入/动作与合格判据：** 跨区滞后/旧主/分区→写主和单调范围明确。
- **BE-020-F · 直接失败变异：** 旧副本擅自兑现权益或合法新值倒退→失败。
- **BE-020-N · 合法邻例：** 允许陈旧的跨区展示按合同标版。

## 二十一、变更版本、水位与因果顺序
1. 衍生状态标明来源流、源快照、对象版本、事件操作身份、事务序号及分区水位；不同分区或来源的 Offset 不能无定义地直接相减或声称同一全局时刻。
2. 定义证明“已应用到哪个来源提交”的可查指标，必要时用源端屏障或版本下界校验；源重分区和序号重置必须有可恢复身份。
3. **验收**：消息重投、偏移回退、跨分区和读副本切换时衍生状态水位有清晰可验证含义。

### BE-021 核验合同

- **BE-021-P · 输入/动作与合格判据：** 跨来源/分区offset回退/重置→水位带来源世代。
- **BE-021-F · 直接失败变异：** 不同分区offset直接相减称全局已追平→失败。
- **BE-021-N · 合法邻例：** 单流明确顺序可用该流位点下界。

## 二十二、CDC 启动快照与增量衔接
1. 使用数据库变更捕获时保证初始快照与持续增量之间无不可解释缺口，说明 Snapshot 边界、提交顺序、日志位置及重复记录处理；具体逻辑复制槽、WAL 与权限按数据库领域／L5 选型执行。
2. 首次复制、网络失联、Schema 变化和 CDC 重启会带来缺失、重复或滞后；过期复制槽或日志不足应进入受控重建，不能跳过中间提交假装已追平。
3. **验收**：初始全量同步时并发写入、复制槽失联、日志保留不足与 CDC 重放仍产生正确衍生结果。

### BE-022 核验合同

- **BE-022-P · 输入/动作与合格判据：** 全量快照并发写+CDC重启→快照增量无缺口可去重。
- **BE-022-F · 直接失败变异：** 日志不足直接跳到最新位点当完整→失败。
- **BE-022-N · 合法邻例：** 受控重建并明确缺口可替代不可能续传。

## 二十三、投影消费幂等与状态归并
1. 投影消费者应按来源与业务对象划分去重／顺序作用域，应用增量时记录已消费版本并更新衍生状态的原子边界；重复事件不能让金额、计数和权益翻倍。
2. 无法天然交换的事件必须按合法顺序、实体版本或域状态回读处理；消费者处理成功与流偏移提交的先后依既有消息专项执行。
3. **验收**：至少一次消息、乱序、重复消费、投影崩溃及多个 Worker 同写不造成计数错误和状态倒退。

### BE-023 核验合同

- **BE-023-P · 输入/动作与合格判据：** 重复增量/乱序/双Worker→projection和消费位置原子。
- **BE-023-F · 直接失败变异：** 计数翻倍或旧版本覆盖新→失败。
- **BE-023-N · 合法邻例：** 可交换操作可按已证规则无序归并。

## 二十四、物化视图与增量刷新
1. 区分数据库物化视图、应用聚合缓存和增量投影；记录刷新触发、源事务边界、版本、结果原子可见性以及查询可用性；PostgreSQL REFRESH CONCURRENTLY 的特定条件不得向其他引擎推广。
2. 全量替换与增量维护应按业务依赖支持删除、更新、负值修正及对账；刷新中的多版本可见窗口须满足数据正确性承诺。
3. **验收**：刷新期间源数据修改、并发查询、刷新失败和独立事务重复执行时结果完整且一致。

### BE-024 核验合同

- **BE-024-P · 输入/动作与合格判据：** 物化刷新时并发读写/刷新失败→完整版本原子可见。
- **BE-024-F · 直接失败变异：** PG并发刷新条件套所有引擎→失败。
- **BE-024-N · 合法邻例：** 普通全量刷新可按可用性要求采用。

## 二十五、搜索索引与近实时可见性
1. 明确搜索引擎与权威数据库之间的更新时间、refresh 可见性、索引文档版本、更新／删除及权限筛选策略；Elastic 近实时 Search refresh 不代表业务提交完成后立即可搜。
2. 查询精确业务事实与搜索排名属于不同语义；不使用搜索索引代替权限执行点、库存或支付权威，滞后时应回源或阻断高风险动作。
3. **验收**：数据库提交后立即搜索、索引延迟、删除及异步重建时符合已承诺的可见窗口。

### BE-025 核验合同

- **BE-025-P · 输入/动作与合格判据：** 提交后立即搜索/删除/索引延迟→NRT窗口及回源正确。
- **BE-025-F · 直接失败变异：** refresh当数据库提交ACK或搜到就授权→失败。
- **BE-025-N · 合法邻例：** 搜索排名可滞后但不得承担交易资格。

## 二十六、读模型与 CQRS 投影契约
1. 按真实查询和读侧性能需求维护查询模型的拥有者、Schema、映射、异常与可重建源；命令侧真相与只读投影分离，读侧不能无审批反向修改写模型。
2. 不同业务消费者可以有不同投影，不能用一个无权的全局副本填充所有租户；投影丢失须能从可用权威来源重建。
3. **验收**：读写模型对业务合法差异、删除、权限与历史事件变更的映射没有信息损失。

### BE-026 核验合同

- **BE-026-P · 输入/动作与合格判据：** 不同消费者投影/丢失重建→可重算且不反写权威。
- **BE-026-F · 直接失败变异：** 全局无权副本服务所有租户→失败。
- **BE-026-N · 合法邻例：** 无CQRS需求无需多套模型。

## 二十七、跨来源聚合与一致快照
1. 跨订单、库存、财务或第三方数据的聚合需定义每个来源时间和版本，说明能否取得同一逻辑截点；无法提供全局快照时应列清各来源水位及可接受时差。
2. 不得将不同时间点的金额加总伪称某时刻权威财务余额；统计与业务资格判断需分流，高风险校验必须回到合适事务或权威系统。
3. **验收**：在各来源更新不同步、其中一个重试或删改期间，聚合不会生成无法解释的权威承诺。

### BE-027 核验合同

- **BE-027-P · 输入/动作与合格判据：** 两来源异步更新时聚合→各自时点/水位明确。
- **BE-027-F · 直接失败变异：** 跨时金额拼成某时权威余额→失败。
- **BE-027-N · 合法邻例：** 统计可显示明确时差和不确定范围。

## 二十八、统计口径、精度与可重现性
1. 聚合查询固定指标口径、分母、去重单位、时间窗口、币种、税费、精度、时区及缺失数据策略；近似计算应有经产品批准的误差用途，不混为真实金额。
2. 缓存分片、增量补偿、回填和负数冲销均须保护数学不变量；同一合法输入范围应能从原始权威数据重算并对账。
3. **验收**：对缺数、退单、重复事件、跨时区和四舍五入场景做单变量对照，保留结果差异。

### BE-028 核验合同

- **BE-028-P · 输入/动作与合格判据：** 退单/重复/时区/舍入→口径分母去重与精度可复算。
- **BE-028-F · 直接失败变异：** 近似统计当真实账面金额→失败。
- **BE-028-N · 合法邻例：** 误差有批准用途的近似搜索可合法。

## 二十九、分页、排序与查询快照
1. 分页查询的过滤、排序、数据权限、分页 Token 和源索引版本应一致；对深分页和持续变化列表设计稳定排序键及必要快照。使用 Elasticsearch PIT/search_after 时遵照实际接口合同。
2. 跨分页索引刷新不得产生未解释的丢项、重项；PIT 不能替代用户会话授权，也不能承诺页面无限期有效。
3. **验收**：高频写入下翻页、撤权、排序字段变化和 PIT 过期后，返回正确的可续查状态。

### BE-029 核验合同

- **BE-029-P · 输入/动作与合格判据：** 高频写翻页/同排序值/PIT到期→稳定顺序和权限保持。
- **BE-029-F · 直接失败变异：** PIT当永久会话许可或漏重项无解释→失败。
- **BE-029-N · 合法邻例：** 游标失效可明确要求重开查询。

## 三十、全量重建、回填与版本切换
1. 重建从明确权威快照或水位开始，增量追赶与回填必须防止快照期间写入被遗漏；双索引或影子投影经过功能、权限和数据对账后再以受控原子切换或等价路由生效。
2. 构建失败、旧新 Schema 不兼容、时间范围不足或删除墓碑缺失时不得替换健康索引；保存失败恢复和回切路径及当期数据差异。
3. **验收**：回填中高并发写入、回放重复、切换前后查询与回滚后旧版本重启均不倒退关键状态。

### BE-030 核验合同

- **BE-030-P · 输入/动作与合格判据：** 回填中写入/墓碑/重复/切换回滚→对账后原子切到完整版本。
- **BE-030-F · 直接失败变异：** 构建失败仍替换健康索引→失败。
- **BE-030-N · 合法邻例：** 双索引不是唯一方案，等价路由切换可用。

## 三十一、Schema、语义版本与跨版本兼容
1. 缓存/投影 Schema 改动要与生产源事件、应用版本、旧查询方、序列化、重建流程和历史数据支持期协调；字段新增兼容不代表单位或枚举业务语义兼容。
2. 版本键空间和读路径必须能识别旧格式并安全升级或淘汰；不以代码回滚自动撤销已产生的新版本源数据或完成的外部事实。
3. **验收**：旧新应用并行、部分缓存键升级及历史事件回放时，业务字段不丢失且旧客户端安全处理。

### BE-031 核验合同

- **BE-031-P · 输入/动作与合格判据：** 新旧Schema/历史事件/旧应用→识别格式和语义版本。
- **BE-031-F · 直接失败变异：** 同字段类型就默认单位不变→失败。
- **BE-031-N · 合法邻例：** 不兼容格式可安全拒绝并保恢复入口。

## 三十二、备份、故障转移与旧快照回灌
1. 缓存恢复、数据库主从切换及投影索引备份各有独立 RPO/RTO；恢复旧快照不能让权威已撤销权限、已删除数据和已支付状态重新出现。
2. 源库故障时不允许以可淘汰缓存提升为未经批准的权威业务数据；必须保留失效检查、读降级与重建优先级。
3. **验收**：恢复落后的 Redis／索引／读副本并重新播放变更后，最新源权威与安全删除状态一致。

### BE-032 核验合同

- **BE-032-P · 输入/动作与合格判据：** 恢复落后缓存/读副本再放流→源权威和删除状态补齐。
- **BE-032-F · 直接失败变异：** 源故障把可淘汰缓存擅升主库→失败。
- **BE-032-N · 合法邻例：** 缓存全丢可从完整源重建。

## 三十三、一致性校验、反熵与自动修复
1. 按资源或关键字段周期性比对权威读取与衍生数据的版本、计数、校验摘要、租户范围与业务不变量；差异按可安全重算、需暂停授权读、需人工决议分类。
2. 修复必须保留真实来源和错误影响，不通过简单清空缓存掩盖源数据破坏或外部欠交付；支持孤儿记录、缺失删除和跨分区错序的针对性扫描。
3. **验收**：人为制造多条重复、漏掉一次删除、失效通知丢失及旧版本覆盖，检测后可恢复并留下客观对账结果。

### BE-033 核验合同

- **BE-033-P · 输入/动作与合格判据：** 制造重复/漏删/旧覆盖→反熵定位并受控修复。
- **BE-033-F · 直接失败变异：** 清缓存掩盖源数据损坏或欠履约→失败。
- **BE-033-N · 合法邻例：** 可安全重算的投影差异可自动修复留证。

## 三十四、容量、热点、逐出与费用控制
1. 为命中率、源库回源预算、对象大小、缓存内存、索引增量负载、CDC/WAL 保留、消息积压、可用空间及第三方数据处理费用设容量目标；真实驱逐策略按产品版本核对。
2. Redis 的逐出、内存满和 noeviction 行为与服务承诺独立，不能把缓存驻留当作强持久化；热点租户、重建任务和普通查询按风险配置公平性与限速。
3. **验收**：内存满、热键、恶意高基数查询、CDC 积压和索引重建时延迟与权威写入保持在批准边界内。

### BE-034 核验合同

- **BE-034-P · 输入/动作与合格判据：** 内存满/高基数/热键/重建→源库和费用预算受控。
- **BE-034-F · 直接失败变异：** noeviction当永驻耐久或逐出丢账本→失败。
- **BE-034-N · 合法邻例：** 允许淘汰的可重建资源可被驱逐。

## 三十五、可观测性与衍生结果的可证实阶段
1. 分别记录命中层、源版本、缓存生成时间、变更水位、失效与重建、搜索可见性及用户实际接收时间；指标如 miss、stale、lag、rebuild age、授权旧值告警必须有业务可解释的来源。
2. RFC 9211 Cache-Status 可在选择的 HTTP 场景帮助追踪缓存处理，但不是业务正确性凭证；指标和日志不得泄漏用户隐私与凭据，也不把代理状态当源数据完整性。
3. **验收**：从源业务操作到衍生写入、缓存命中和用户读取可在权限内还原证据，发现缺口能定位影响范围。

### BE-035 核验合同

- **BE-035-P · 输入/动作与合格判据：** 业务键到命中层/源版/失效/水位→阶段能还原。
- **BE-035-F · 直接失败变异：** Cache-Status当源数据正确凭证→失败。
- **BE-035-N · 合法邻例：** 最小诊断字段足够不需泄完整私有值。

## 三十六、真实合同、集成与故障验证门禁
1. 按 L6 风险组合缓存键/格式单测、HTTP 合同、授权多租户、源数据库读写、真实缓存与 CDC/索引集成、并发交错、断线恢复、版本迁移、重建、性能与用户路径测试；必须覆盖历史纠错触发条件。
2. 静态文档、Mock、合成指标和运行时验证分开报告；每项证据保留源码版本、配置、业务对象、故障点、实际结果与未验证边界，不因降低测试成本删减应有的业务保障。
3. **验收**：对项目启用的每个缓存层和投影验证正确性、权限、时效、性能及重建；业务结果另以权威事实验收。

### BE-036 核验合同

- **BE-036-P · 输入/动作与合格判据：** 对所有启用层/投影做真实并发/权限/恢复→证据与未测分开。
- **BE-036-F · 直接失败变异：** Mock/静态覆盖冒Redis/CDC真实验证→失败。
- **BE-036-N · 合法邻例：** 无缓存的服务不强制缓存测试。
