# L4 事务隔离、并发与业务幂等技术规范

**文档ID：** STD-L4-BACKEND-003　**版本：** 0.1.0　**状态：** adopted　**生效日期：** 2026-10-30

## 技术对象与官方依据

本规范是后端领域具体专项，管理事务隔离、原子写入、竞态、锁、未知提交结果和业务幂等；按真实状态写入和副作用风险选择适用机制，不对无状态服务强制建分布式锁或幂等账本。

## 核验口径与消费接口

维护者负责落实本文机制，领域/API/存储提供者负责其权威保证，验收者从实际受支持入口观察结果。输入固定源码/构建、配置、数据/协议版本、角色/租户、目标平台、故障时序和预算；权威观察对象为**真实引擎事务/约束/提交点、逻辑意图、尝试与永久领域唯一性**。真实执行入口为**固定引擎双连接屏障交错、SQL及事务参数、进程退出/提交断线和权威回读**。逐章 P/F/N 分别为正常输入及判据、破坏该机制的直接失败变异、应继续成立的合法邻例；本章原有每项规则、原有验收与新增合同共同约束，不用单一通用案例替代具体子项。每个子项须在案例输入中保留其适用条件，并以自身原文规定的输出/不变量判定；复合章应拆记录各个观察量，不能以一个成功掩盖其他失败。

证据产物包括真实命令/用户动作、原始响应或事件、权威状态前后值、版本、时序、失败及恢复；尚无对应真实运行证据的场景状态为 `not-run`，标准库示例仅证明列明的局部边界。具体输入与命令见[执行入口](../../../examples/web-backend/RUNBOOK.md)，条款索引见[规范条款登记](../../../registry/requirements.json)，来源的有限支持命题见[逐命题来源映射](../../../sources/web-backend/claims.json)。

本文的跨组件约束与正例、失败反例、合法邻例由本规范综合定义；外部来源支持的机制及适用边界见来源表。项目架构、预算和业务规则由实际需求确定。L5 实现应映射到所选框架、SDK 或引擎；L6 按具体版本的提供者保证与受支持矩阵验收项目能力。

## 一、适用事务与业务风险
按是否有并发更新、业务唯一性、持久结果、外部副作用与数据权利选择保护强度。每个机制要明确防止何种真实错误及代价；无持久写入时不得制造无意义的跨系统协调器。

### BE-001 核验合同

- **BE-001-P · 输入/动作与合格判据：** 列并发/唯一/持久/外部效果风险→每机制保护的错误明确。
- **BE-001-F · 直接失败变异：** 无状态只读强造分布式锁→失败。
- **BE-001-N · 合法邻例：** 无持久写入可不设幂等账本。

## 二、领域不变量的写入权威
明确余额、库存、配额、对象身份、状态转换、操作权限和多记录关联的约束以及唯一可信写入者。缓存、界面和异步投影不是默认权威。

### BE-002 核验合同

- **BE-002-P · 输入/动作与合格判据：** 并发改余额/库存/配额→权威不变量始终成立。
- **BE-002-F · 直接失败变异：** 缓存或UI当唯一写入权威→失败。
- **BE-002-N · 合法邻例：** 可重建展示投影可异步。

## 三、事务生存期与提交判定
区分事务开始、修改、提交、回滚、HTTP 回应与下游生效；应用函数结束不等于数据库已提交，本地 COMMIT 不会撤销远端通知或扣费。必须能追溯实际提交结果。

### BE-003 核验合同

- **BE-003-P · 输入/动作与合格判据：** 提交前后杀进程并另连接回读→commit与response分开。
- **BE-003-F · 直接失败变异：** 函数return或远端通知当本地提交→失败。
- **BE-003-N · 合法邻例：** 本地回滚不能自动撤销已发通知。

## 四、隔离级别与引擎实现
SQL 标准与 PostgreSQL、InnoDB、SQLite 对同名隔离和锁可能存在差异；按实际需要防止的脏读、不可重复读、幻读、写偏斜和序列化异常选型。验收用固定版本双事务交错测试。

### BE-004 核验合同

**必要机制补充：** 固定引擎/版本/隔离/索引和事务模式：PostgreSQL18 RR阻止幻读但仍可序列化异常；InnoDB8.4普通一致性读与锁定读/UPDATE的读视图和范围锁不同；SQLite WAL读快照升级写可能SQLITE_BUSY_SNAPSHOT且写者串行。不得把SQLite本地测试当其他引擎写偏斜证明。

- **BE-004-P · 输入/动作与合格判据：** 固定PG/InnoDB/SQLite各用双事务交错→按各引擎判定异常。
- **BE-004-F · 直接失败变异：** 同名RR一律当同保证→失败。
- **BE-004-N · 合法邻例：** 只采用SQLite时不伪造PG实测。

## 五、Read Committed 下的读后写
同一事务内的两次查询可能读取不同提交状态，先检查再写入需要真实受控条件。验收另一个事务在检查与提交之间变更相关数据时的行为。

### BE-005 核验合同

- **BE-005-P · 输入/动作与合格判据：** RC检查后另一连接改值再写→原子前提保护。
- **BE-005-F · 直接失败变异：** 先查后写无条件导致超卖→失败。
- **BE-005-N · 合法邻例：** 无竞争且原子更新的路径不需先查。

## 六、Repeatable Read 和快照写偏斜
稳定快照不必然保护两个事务分别写入不同记录时的全局约束；PostgreSQL RR、InnoDB 一致性读与 SQLite WAL 快照不能简单等同。对多记录不变量配置有效的原子/序列化机制。

### BE-006 核验合同

- **BE-006-P · 输入/动作与合格判据：** 两个快照各改不同记录→多行不变量保护。
- **BE-006-F · 直接失败变异：** 稳定快照被当全局约束保护→失败。
- **BE-006-N · 合法邻例：** 不同对象无共享不变量可合法并行。

## 七、Serializable 与序列化失败
真正需要全事务序列化语义的操作按引擎选择相应隔离；出现 serialization_failure 时重新执行**完整事务逻辑**，重新读取业务条件，避免只重放末条 SQL 或重复非事务副作用。

### BE-007 核验合同

**必要机制补充：** 整事务重试重新读取守卫并保持原逻辑意图；序列等非回滚行为和事务外副作用单独处理，Serializable不为远端外效提供原子回滚。

- **BE-007-P · 输入/动作与合格判据：** 制造serialization_failure→整事务重读再决定。
- **BE-007-F · 直接失败变异：** 仅重放末条SQL或重复事务外邮件→失败。
- **BE-007-N · 合法邻例：** 明确永久业务拒绝不应循环重试。

## 八、悲观锁的选择与释放
按实际资源与锁冲突范围选择行、表、范围或谓词约束，按引擎确认共享／排他、锁定读、等待及超时。多锁申请顺序应稳定，避免死锁和不必要的大范围阻塞。

### BE-008 核验合同

- **BE-008-P · 输入/动作与合格判据：** 相反顺序锁与等待超时→释放/错误分类和恢复正确。
- **BE-008-F · 直接失败变异：** 无限等待或误以锁行等于锁未来范围→失败。
- **BE-008-N · 合法邻例：** 无需悲观锁的原子CAS可成立。

## 九、乐观版本与原子条件
使用在数据库真实生效的版本条件更新、受影响行数、唯一约束或 CAS 进行并发协调。客户端传递 ETag／If-Match 后必须转换为权威写入条件，不能仅由应用内存比较旧状态。

### BE-009 核验合同

- **BE-009-P · 输入/动作与合格判据：** 双连接同旧version更新→仅合法一方影响行数为1。
- **BE-009-F · 直接失败变异：** 只应用内存比较ETag→失败。
- **BE-009-N · 合法邻例：** 不同对象当前版本可并行成功。

## 十、唯一性、竞争创建与索引语义
真正要求唯一的业务键须由受控持久化条件保证；先 SELECT 不存在再 INSERT 不能单独防竞争。NULL、字符排序、分区和部分索引的具体实现必须按真实引擎检验。

### BE-010 核验合同

- **BE-010-P · 输入/动作与合格判据：** 并发同业务键insert及NULL/排序规则边界→真正唯一性成立。
- **BE-010-F · 直接失败变异：** SELECT无记录后双建→失败。
- **BE-010-N · 合法邻例：** 业务允许多个NULL时不强改语义。

## 十一、范围读、幻读和缺失记录
资源分配和“条件不存在”查询需要防范并发插入／删除。范围锁、间隙锁、谓词锁随引擎及索引而变化；锁住现存记录不能自动证明锁住未来可能出现的对象。

### BE-011 核验合同

- **BE-011-P · 输入/动作与合格判据：** 范围读后并发插删→分配/不存在约束守住。
- **BE-011-F · 直接失败变异：** 锁现存行就认定锁未来记录→失败。
- **BE-011-N · 合法邻例：** 无需范围约束的点查可不持范围锁。

## 十二、多记录原子性与业务转移
转账、库存扣减、配额调整、资源预留在已批准条件中必要时必须一起成功或失败。允许分步的业务需明确合法中间状态和恢复；不能向用户虚报全部完成。

### BE-012 核验合同

- **BE-012-P · 输入/动作与合格判据：** 转账两写故障→守恒且整体成功或明确合法中间态。
- **BE-012-F · 直接失败变异：** 拆批次破坏必须原子的跨行约束→失败。
- **BE-012-N · 合法邻例：** 经业务允许的分步预留可有可恢复中间态。

## 十三、嵌套事务、Savepoint 与事务传播
Savepoint、子事务和独立事务提交的实际语义取决于数据库及框架。内层成功、外层回滚与外部副作用交错时必须验收持久结果；不能仅凭事务注解名称断言原子性。

### BE-013 核验合同

- **BE-013-P · 输入/动作与合格判据：** 内Savepoint成功外回滚/独立事务提交→按真实持久结果判定。
- **BE-013-F · 直接失败变异：** 框架注解名称当跨资源原子性→失败。
- **BE-013-N · 合法邻例：** 内层独立事务可按明确合同保留提交。

## 十四、数据库连接池及会话隔离
连接归还前必须处理未提交事务、隔离设置、会话状态和租户上下文；跨请求或线程复用不能继承旧事务和身份。失效连接及取消处理应保证可恢复。

### BE-014 核验合同

- **BE-014-P · 输入/动作与合格判据：** A请求留事务后归还连接给B→事务/隔离/租户清净。
- **BE-014-F · 直接失败变异：** 连接池复用旧租户session→失败。
- **BE-014-N · 合法邻例：** 驱动自带正确reset可复用但须核实际配置。

## 十五、长事务与资源成本
在数据库锁持有期间应避免无必要等待用户输入、外部 HTTP、AI 生成或文件传输。按真实事务必要范围选择检查点和超时，避免长期锁、MVCC 回收积压与连接池耗尽。

### BE-015 核验合同

- **BE-015-P · 输入/动作与合格判据：** 锁内慢外部HTTP/用户等待→有限持锁和资源释放。
- **BE-015-F · 直接失败变异：** 无限等AI导致池耗尽→失败。
- **BE-015-N · 合法邻例：** 真实需要短受控锁区间可继续使用事务。

## 十六、死锁与错误分类
区分死锁、序列化失败、唯一性冲突、资源繁忙、永久业务拒绝与网络未知提交。PostgreSQL 常见 40001、40P01 只属于特定引擎错误码，不能充当所有数据库通用标准。

### BE-016 核验合同

- **BE-016-P · 输入/动作与合格判据：** 死锁/40001/唯一冲突/断线分类→对应恢复而非一律重试。
- **BE-016-F · 直接失败变异：** PG码当所有引擎标准→失败。
- **BE-016-N · 合法邻例：** SQLite忙错误按自己的版本语义处理。

## 十七、重试时的重新授权和重读
重试前库存、余额、有效权限、外部价格及时间条件可能变化；哪些请求参数固定、哪些状态必须重读由批准的业务规则决定。对失败事务不能重用已失效的临时决定。

### BE-017 核验合同

- **BE-017-P · 输入/动作与合格判据：** 重试前库存/权限/价目已变→固定意图参数与当前守卫重判。
- **BE-017-F · 直接失败变异：** 复用失败事务旧授权和旧余额→失败。
- **BE-017-N · 合法邻例：** 原操作固定金额不可擅自变成新价格。

## 十八、未知提交与断线后回读
提交成功但响应丢失属于可发生情况。通过持久业务操作身份、结果收据和权威存储查询区分已提交、未提交、尚未知晓；未经确认不得无差别重扣费。

### BE-018 核验合同

**必要机制补充：** 逻辑意图ID在安全重试间保持不变，每次发送另分配尝试ID；事务ID、事件ID、投递ID和Trace ID不得代替它。权威查询暂未发现记录、读副本落后、日志缺失、客户端超时均不证明原尝试不会随后提交。只有目标端对同意图实行覆盖所有在途/迟到尝试的原子唯一性，或有已安装的栅栏/终止与线性化屏障证明原尝试不再可生效，才可依合同重发；否则保持结果未知并继续有权核对，不新建意图绕过去重。有限去重保留窗须覆盖目标最后可能接受该意图的时刻、重放和恢复窗口；不能只比较本地派发时间。窗外仍可迟到时使用永久领域唯一性、目标拒旧期限/世代或有权人工核对。

- **BE-018-P · 输入/动作与合格判据：** COMMIT后丢响应、回读暂未见记录→保留unknown与原意图。
- **BE-018-F · 直接失败变异：** 查无记录即认定原尝试永不提交并新扣→失败。
- **BE-018-N · 合法邻例：** 目标唯一键覆盖迟到尝试时同意图重传可安全。

## 十九、HTTP 幂等与业务幂等的区别
RFC 9110 对 PUT、DELETE 等方法的幂等只描述其请求预期效果，不能保证支付、邮件、积分或其他外部操作恰好一次。按业务独立定义需要保护的副作用和结果。

### BE-019 核验合同

- **BE-019-P · 输入/动作与合格判据：** 重复PUT含通知→区分请求预期效果和业务外效。
- **BE-019-F · 直接失败变异：** 方法幂等即宣称邮件exactly-once→失败。
- **BE-019-N · 合法邻例：** 每请求各记访问日志不违反HTTP幂等。

## 二十、幂等键的存储与原子占用
需要去重的操作用可竞争安全的唯一键、调用者、请求摘要、处理状态、可信结果与有效期。仅“先查键没有、执行、最后存键”的非原子流程会导致多实例重复执行。

### BE-020 核验合同

**必要机制补充：** Outbox记录与产生它的领域修改在同一实际数据库事务中一起提交/回滚；后续发布确认与消费者提交不在该事务内，允许重复发布但不允许静默丢失。Inbox唯一键至少区分租户、业务消费范围和源事件身份；去重登记、目标本地业务修改及需要产生的下一步Outbox在同一实际事务完成。外部付款/发信不被该本地原子边界包围，须继续使用目标接受的意图键、收据与未知结果核对。

- **BE-020-P · 输入/动作与合格判据：** 双Worker竞争同键/事务崩溃→占用、账本、结果原子。
- **BE-020-F · 直接失败变异：** 先查执行后记键双发→失败。
- **BE-020-N · 合法邻例：** 已完成同指纹重传返回原收据。

## 二十一、冲突指纹、TTL 与跨租户
相同键不同金额、资源或操作者必须按协议拒绝误复用；跨租户不共享私有操作结果。TTL 过期不能自动允许永久有效的支付、订单或权益再次生效。

### BE-021 核验合同

- **BE-021-P · 输入/动作与合格判据：** 同键不同金额/跨租户/TTL后旧请求→冲突拒绝且永久身份受保护。
- **BE-021-F · 直接失败变异：** 去重TTL过期默认允许再交易→失败。
- **BE-021-N · 合法邻例：** 不同租户合法同字面键结果彼此隔离。

## 二十二、HTTP 条件写与业务操作键
If-Match 与 ETag 防丢失更新，业务幂等键防重复副作用；必要时同时采用。412／428／409 的 HTTP 使用遵循相邻规范 HTTP 专项，写入前置条件须落到原子持久操作。

### BE-022 核验合同

- **BE-022-P · 输入/动作与合格判据：** 同意图且旧ETag并发写→去重和条件更新分别生效。
- **BE-022-F · 直接失败变异：** If-Match替代操作键或反向替代版本保护→失败。
- **BE-022-N · 合法邻例：** 已完成同意图重放可返回原结果但不再次写。

## 二十三、批量任务和部分提交
明确批次整体事务与逐项事务的区别、结果清单、可恢复检查点和重试规则。已完成的项目不得因批次中断而无条件重新处理，必须原子保护的跨行不变量不得任意切碎。

### BE-023 核验合同

- **BE-023-P · 输入/动作与合格判据：** 逐项批任务中断→完成集稳定、未完成可恢复。
- **BE-023-F · 直接失败变异：** 整批重发已成功不可逆项→失败。
- **BE-023-N · 合法邻例：** 真正整体原子批次不能任意切碎。

## 二十四、跨数据库与外部交易
本地事务不能使远端 API、消息中间件或支付平台自动原子提交。实际有需求时选择受控 Outbox／Inbox、工作流补偿或事务协调，具体可靠交付由后续 L4 专项完善。

### BE-024 核验合同

- **BE-024-P · 输入/动作与合格判据：** 本地提交后远端API失败→Outbox/协调或补偿闭环。
- **BE-024-F · 直接失败变异：** 本地事务包装远端当全局原子→失败。
- **BE-024-N · 合法邻例：** 单资源事务无需分布式协调。

## 二十五、消息 ACK 和重复消费者
消息平台的投递保证不同于业务效果保证。ACK 丢失、Worker 崩溃与消息重放后，去重记录与业务结果应有实际可验证的一致性，不得重复发放权益或扣减库存。

### BE-025 核验合同

- **BE-025-P · 输入/动作与合格判据：** 业务提交后ACK丢失再投→业务和去重同边界。
- **BE-025-F · 直接失败变异：** 先ACK后提交宕机永久漏处理→失败。
- **BE-025-N · 合法邻例：** 允许丢的遥测可用不同确认等级。

## 二十六、锁租约与旧执行者
分布式锁超时不保证旧 Worker 已停止。必要时在持久化端验证版本或 fencing token，防止恢复执行的旧持有者覆盖较新合法状态。锁本身不能替代领域权限和唯一约束。

### BE-026 核验合同

**必要机制补充：** 执行世代只有在目标写入/效果边界被验证才构成栅栏：先原子安装新世代，再允许新执行者写入，旧世代检查与写入处于同一受控原子边界。本地租约到期、取消请求发出、Worker进程失联或代理断开都不证明旧在途操作已停止；已发外部操作仍按原意图查询。

- **BE-026-P · 输入/动作与合格判据：** 租约过期旧Worker恢复写→目标端fence拒旧epoch。
- **BE-026-F · 直接失败变异：** 仅本地lease检查而目标仍接受旧写→失败。
- **BE-026-N · 合法邻例：** 不冲突独立对象当前世代可并行。

## 二十七、重试、热点和性能预算
监测锁等待、长事务、死锁、序列化失败、重试放大、连接池利用和热键争用。优化要同时验收吞吐、尾延迟、资源成本与业务不变量，不能以丢失金额精度换取速度。

### BE-027 核验合同

- **BE-027-P · 输入/动作与合格判据：** 热点重试/长事务压测→尾延迟/放大/成本及正确性同时可查。
- **BE-027-F · 直接失败变异：** 删CAS换高TPS→失败。
- **BE-027-N · 合法邻例：** 无瓶颈不强制锁优化。

## 二十八、审计和最小可复核状态
记录有权查看的业务操作 ID、提交版本、事务结果、幂等身份、请求与重试次数、关键失败及恢复动作。Trace ID、数据库事务 ID、HTTP 请求 ID 与幂等键用途不同，日志不可包含生产密钥和不必要的个人数据。

### BE-028 核验合同

- **BE-028-P · 输入/动作与合格判据：** 操作ID/attempt/tx/event/trace分别追踪→可核对且无秘密。
- **BE-028-F · 直接失败变异：** Trace当幂等主键或日志缺失当未发生→失败。
- **BE-028-N · 合法邻例：** 有权限最小字段足以复核无需全量个人数据。

## 二十九、并发测试和故障注入
用实际数据库版本、隔离参数、多连接受控交错、失败注入、提交时断线、多实例并发和未知结果恢复测试验收。Mock 或单线程单测不能证明事务隔离。报告已执行、未执行、失败样例及可复核证据，避免无效重复 CI。

### BE-029 核验合同

- **BE-029-P · 输入/动作与合格判据：** 多连接故障/提交断线/重启→真实引擎证据与模型分开。
- **BE-029-F · 直接失败变异：** 单线程Mock冒隔离与耐久证明→失败。
- **BE-029-N · 合法邻例：** 有限SQLite示例仅声称其本地覆盖。

## 三十、30 个静态失效场景
| 故障场景 | 关键机制 | 正确完成标准 |
| --- | --- | --- |
| 同一订单被同时创建 | 唯一约束与操作身份 | 不生成不合法重复订单 |
| 最后一件库存被双重扣减 | 条件写与原子性 | 无超卖 |
| 两个事务跨行写偏斜 | 快照与领域约束 | 不变量成立 |
| RC 两次读见不同提交 | 语句快照与重读 | 决策条件正确 |
| RR 快照导致范围约束破坏 | 隔离与锁选择 | 规则仍受保护 |
| Serializable 提交冲突 | 整事务重试 | 无额外副作用 |
| 两个用户以旧版本更新 | CAS 版本条件 | 不静默覆盖 |
| 先查无记录再并发插入 | 存储唯一索引 | 业务对象唯一 |
| 查询范围后出现新行 | 幻读与谓词保护 | 范围条件不破坏 |
| 相反锁顺序引起死锁 | 错误分类和恢复 | 无孤立部分提交 |
| 连接池残留未提交状态 | 会话清理 | 无跨用户泄漏 |
| Savepoint 局部成功但外层失败 | 传播与回滚 | 实际提交合法 |
| 提交成功而响应丢失 | 权威结果回读 | 不重复扣费 |
| 同键携带新的付款金额 | 幂等键指纹 | 拒绝错误复用 |
| 跨租户同键被重用 | 键作用域 | 无信息串用 |
| TTL 到期重放旧交易 | 永久领域身份 | 无二次交易 |
| 双 Worker 争同一操作键 | 原子占用 | 受权结果唯一 |
| 租约过期旧 Worker 继续写 | fencing／版本 | 新提交不被覆盖 |
| 过期 ETag 被接受 | If-Match 原子执行 | 条件失败不写入 |
| PUT 重试发出两次通知 | 业务幂等 | 无非预期外部副作用 |
| 批量任务中途失败 | 逐项检查点 | 已完成项不重复 |
| 事务提交后事件未发出 | 跨资源一致性 | 可查询及恢复交付 |
| 消费者 ACK 丢失后重放 | 消费去重 | 业务不重复执行 |
| 补偿事务再次失败 | 未完成状态 | 保留有权恢复路径 |
| 取消请求但远端已完成 | 不可逆副作用 | 不虚报撤销 |
| 长事务等待外部模型 | 锁与资源预算 | 可控超时和回收 |
| 序列化重试复用旧余额 | 重读业务事实 | 按新状态重新决定 |
| 切换不同数据库引擎 | 隔离差异验证 | 有对应引擎测试 |
| 性能优化删除关键条件更新 | 质量与成本双门禁 | 吞吐改善仍正确 |
| CI 通过但客户权益未生效 | 交付结果追踪 | 技术与业务状态分开 |
## 三十一、批准和项目接入
本专项只规定事务隔离、并发写入、未知提交和业务幂等的工程契约；领域身份由领域模型决定，HTTP 状态由 HTTP 专项决定，消息可靠交付与分布式工作流由对应独立 L4 专项处理，具体数据库内核及 Schema 归数据库领域、语言事务工具归 L5。项目 L6 固定实际数据库版本、风险、操作键、锁/隔离、事务边界和故障验收。
静态案例与标准引用均不等于真实数据库、资金、消息或项目端到端验证已通过；实际接入及结果由 L6 分项目确认。
