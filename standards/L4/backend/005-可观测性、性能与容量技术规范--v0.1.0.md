## 官方标准及版本、引用性质
- [W3C Trace Context Recommendation](https://www.w3.org/TR/trace-context/)：W3C Recommendation 2021，跨 HTTP 服务 Trace Context 的正式协议格式。
- [W3C Trace Context Level 2](https://www.w3.org/TR/trace-context-2/)：2024 Candidate Recommendation Draft，不能替代正式已采用版本。
- [OpenTelemetry Specification 1.61.0](https://opentelemetry.io/docs/specs/otel/)：官方规范索引；不同信号及具体章节有各自稳定级别。
- [OTLP Specification 1.11.1](https://opentelemetry.io/docs/specs/otlp/)：Metrics/Logs/Traces 传输 Stable，Profiles 为 Development。
- [OTel Metrics Data Model](https://opentelemetry.io/docs/specs/otel/metrics/data-model/)：Temporality、Histogram、时间戳等指标数据语义。
- [OTel Logs Data Model](https://opentelemetry.io/docs/specs/otel/logs/data-model/)：日志的标准数据模型，关联 Context/Resource 的实现参考。
- [OTel Trace SDK](https://opentelemetry.io/docs/specs/otel/trace/sdk/)：追踪采样与 SDK 的产品版本契约。
- [OTel Profiles](https://opentelemetry.io/docs/specs/otel/profiles/)：Alpha，不应自动当成已稳定的跨语言保障。
- [Prometheus Metric Naming](https://prometheus.io/docs/practices/naming/)：Prometheus 维护方指标、单位和标签指南。
- [Prometheus Native Histograms](https://prometheus.io/docs/specs/native_histograms/)：v3.8 起稳定支持，但 Scrape/Remote Write 条件按部署版本核对。
- [Google SRE Workbook: SLO](https://sre.google/workbook/implementing-slos/)：SLO/预算制定实践，不属于强制协议。
- [Google SRE Workbook: Alerting](https://sre.google/workbook/alerting-on-slos/)：多窗口 Burn Rate 经验指南，阈值由具体业务批准。
- [Grafana k6 Open/Closed Load Models](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/)：负载工具指导，不代替真实项目目标确定。
- [OTel Collector Internal Telemetry](https://opentelemetry.io/docs/collector/internal-telemetry/)：采集器队列、导出失败与观测链路自身健康参考。
所见版本、读取日期与有限支持命题见来源映射。W3C Recommendation、Candidate Recommendation Draft、OTel 规范不同信号的 Stable/Development/Alpha 及产品实践指南按发布性质引用；L5/L6 实际采用时锁定工具、SDK、部署版本和可用性。

## 核验口径与消费接口

维护者负责落实本文机制，领域/API/存储提供者负责其权威保证，验收者从实际受支持入口观察结果。输入固定源码/构建、配置、数据/协议版本、角色/租户、目标平台、故障时序和预算；权威观察对象为**业务权威分母/终点、原始信号/时间与可复算统计**。真实执行入口为**固定事件集复算、OTLP真实接收/查询、原始直方图、负载到达与完成记录**。逐章 P/F/N 分别为正常输入及判据、破坏该机制的直接失败变异、应继续成立的合法邻例；本章原有每项规则、原有验收与新增合同共同约束，不用单一通用案例替代具体子项。每个子项须在案例输入中保留其适用条件，并以自身原文规定的输出/不变量判定；复合章应拆记录各个观察量，不能以一个成功掩盖其他失败。

证据产物包括真实命令/用户动作、原始响应或事件、权威状态前后值、版本、时序、失败及恢复；尚无对应真实运行证据的场景状态为 `not-run`，标准库示例仅证明列明的局部边界。具体输入与命令见[执行入口](../../../examples/web-backend/RUNBOOK.md)，条款索引见[规范条款登记](../../../registry/requirements.json)，来源的有限支持命题见[逐命题来源映射](../../../sources/web-backend/claims.json)。

本文的跨组件约束与正例、失败反例、合法邻例由本规范综合定义；外部来源支持的机制及适用边界见来源表。项目架构、预算和业务规则由实际需求确定。L5 实现应映射到所选框架、SDK 或引擎；L6 按具体版本的提供者保证与受支持矩阵验收项目能力。

## 一、范围与必要性
1. 按实际用户任务、故障风险与运维预算选必要的指标、日志、追踪、性能剖析及合成探测；不强制小型项目建设昂贵统一平台。
2. **验收**：每个常驻信号均有独立判断用途、可查询来源与实际使用角色

### BE-001 核验合同

- **BE-001-P · 输入/动作与合格判据：** 逐信号说明判断用途并从存储查询→角色和来源真实。
- **BE-001-F · 直接失败变异：** 无用途常驻采集却耗费用泄隐私→失败。
- **BE-001-N · 合法邻例：** 小项目可不用昂贵观测平台。

## 二、业务完成与协议成功
1. 区分 HTTP 受理、数据库提交、消息确认、工作流状态、外部接收和客户业务生效；技术层健康或 200 不得代替实际订单及资金结果。
2. **验收**：用领域权威状态和外部结果准确计算实际成功率

### BE-002 核验合同

- **BE-002-P · 输入/动作与合格判据：** 同订单对HTTP/DB/消息/外部权威核对→成功分母按业务终点。
- **BE-002-F · 直接失败变异：** 200或工作流绿冒资金到账→失败。
- **BE-002-N · 合法邻例：** 内部任务可按自己明确终点完成。

## 三、部署拓扑与依赖故障域
1. 使用当前已部署资源版本梳理 Gateway、服务、RPC、Broker、存储与第三方依赖，标注用户入口、环境和共享故障域；不能用过时架构图替代事实。
2. **验收**：定位共同故障域和实际受影响业务，避免假根因

### BE-003 核验合同

- **BE-003-P · 输入/动作与合格判据：** 从在线资源版查实际依赖故障域→影响可定位。
- **BE-003-F · 直接失败变异：** 旧架构图冒当前部署事实→失败。
- **BE-003-N · 合法邻例：** 无某组件不强加图节点。

## 四、Metrics/Logs/Traces/Profiles 信号职责
1. Metrics 用于聚合趋势，Logs 记录必要原始事件，Traces 解释具体执行链，Profiles 在技术支持时诊断资源热点；高价值业务结果不依赖随机抽样信号。
2. **验收**：基于独立权威事实仍可核验业务结果

### BE-004 核验合同

- **BE-004-P · 输入/动作与合格判据：** 随机丢trace仍查业务权威→诊断与结果证据分开。
- **BE-004-F · 直接失败变异：** 抽样日志缺失推断业务没发生→失败。
- **BE-004-N · 合法邻例：** 低风险任务可采用轻量日志。

## 五、Resource 与版本标识
1. 信号关联服务、环境、部署/构建版本、地域、实例、进程和真实授权租户；按选定 OTel Resource 及语义约定标注，不把 Pod ID 当领域对象键。
2. **验收**：准确区分版本和环境下真实故障指标

### BE-005 核验合同

- **BE-005-P · 输入/动作与合格判据：** 不同环境/构建/实例信号混入→Resource准确分组。
- **BE-005-F · 直接失败变异：** Pod ID当订单主键或客户属性覆盖环境→失败。
- **BE-005-N · 合法邻例：** 无OTel可用等价受控版本标识。

## 六、Trace Context 传播与安全
1. 采用 W3C Trace Context 2021 Recommendation 时验证 traceparent/tracestate，Level 2 仍为 Candidate Recommendation Draft；外部追踪 ID 与 Baggage 不是可信身份和操作授权。
2. **验收**：跨服务追踪保真，但非法 Trace 数据不扩大业务访问权

### BE-006 核验合同

- **BE-006-P · 输入/动作与合格判据：** 伪traceparent/tracestate经边界→解析正确且不扩授权。
- **BE-006-F · 直接失败变异：** 追踪ID当身份或把Level2草案当已采用正式版→失败。
- **BE-006-N · 合法邻例：** 外部trace可按合同重建信任关联。

## 七、异步、批量与因果跨度
1. 消息发布、各消费者、重投、回放与长任务分别建立独立 Span/Span Link 及业务操作关联，避免把传输尝试和合法领域动作混为一体。
2. **验收**：每个消费者和其副作用有可独立核对的关联

### BE-007 核验合同

- **BE-007-P · 输入/动作与合格判据：** 同事件多消费者/重投/回放→独立Span/Link和业务关联。
- **BE-007-F · 直接失败变异：** 每attempt当新业务效果或全归同父失因果→失败。
- **BE-007-N · 合法邻例：** 合法独立订阅均保留自身处理记录。

## 八、结构化日志与错误通道
1. 按真实运维职责记录时间、事件类别、版本、操作身份、执行阶段、错误原因与必要关联，敏感栈和诊断细节只存授权运维渠道；前端及导出遵守业务受众限制。
2. **验收**：客户仅看到有效业务原因和操作，内部诊断不泄露

### BE-008 核验合同

- **BE-008-P · 输入/动作与合格判据：** 故障日志到客户错误通道→用户只见可操作业务信息。
- **BE-008-F · 直接失败变异：** SQL栈/密钥进公开响应→失败。
- **BE-008-N · 合法邻例：** 授权运维可查必要内部诊断。

## 九、失败、拒绝与未知语义
1. 区分合法业务拒绝、对象无权、取消、超时未知提交、远端永久失败和系统缺陷；HTTP 状态或 Span Status 不能单独表达最终业务结论。
2. **验收**：按照权威回执/幂等操作键标记已完成或未知

### BE-009 核验合同

- **BE-009-P · 输入/动作与合格判据：** 拒绝/超时/提交后丢ACK→业务状态按回执归类。
- **BE-009-F · 直接失败变异：** Span ERROR就自动反向标订单失败→失败。
- **BE-009-N · 合法邻例：** 读取失败不改变既存业务事实。

## 十、指标名称、单位与字段定义
1. 指标需明确对象、单位、维度、窗口和计算契约；Prometheus 命名/单位指南与 OTel 语义约定按项目实际选用，不自动互相覆盖。
2. **验收**：跨采集器和仪表盘的单位及数值一致

### BE-010 核验合同

- **BE-010-P · 输入/动作与合格判据：** 同数据经采集/面板换单位→指标定义一致。
- **BE-010-F · 直接失败变异：** 毫秒当秒或分母窗口错位→失败。
- **BE-010-N · 合法邻例：** 项目可选择合适命名约定但须明确。

## 十一、Counter Reset 与 Temporality
1. 区分 Counter、Gauge、Histogram 和 OTLP Cumulative/Delta；进程重启、导出重复及 StartTime 影响序列的累计语义，禁止简单差分得负吞吐。
2. **验收**：重启和累计转换后的业务样本复算准确

### BE-011 核验合同

- **BE-011-P · 输入/动作与合格判据：** 计数器重启/重复导出/cumulative转delta→重算无负吞吐。
- **BE-011-F · 直接失败变异：** 简单相减跨StartTime→失败。
- **BE-011-N · 合法邻例：** Gauge可合法下降不按Counter处理。

## 十二、总体分位与直方图
1. P50/P95/P99 的计算明确样本量、分桶、误差和时间窗口；Prometheus Classic/Native Histogram 及 Summary 能力按部署版本核对，禁止平均多个实例 P99。
2. **验收**：可合并分布与真正总体采样结果吻合

### BE-012 核验合同

**必要机制补充：** 只合并同指标、同单位/窗口、相容桶与有效计数的分布；Summary分位和各实例P99不能求平均得到总体P99。记录桶内近似误差、样本量与缺失。

- **BE-012-P · 输入/动作与合格判据：** 两实例异分布合并→总体分布按桶/样本重算。
- **BE-012-F · 直接失败变异：** 平均各实例P99当全局P99→失败。
- **BE-012-N · 合法邻例：** 可合并直方图要报告桶误差。

## 十三、基数预算与可变维度
1. Metric 标签不放无界用户/订单/Trace ID、个人邮件及任意 URL；以受控 Trace/日志与业务查询处理单对象溯源，按基数和费用预算限制。
2. **验收**：并发和用户增长后指标基数仍受约束

### BE-013 核验合同

- **BE-013-P · 输入/动作与合格判据：** 大量用户/订单/任意URL输入→指标基数有界。
- **BE-013-F · 直接失败变异：** 无限Label或邮箱入metric→失败。
- **BE-013-N · 合法邻例：** 单对象溯源可走权限受控日志。

## 十四、缺失数据、空流量与零值
1. 区分没有请求、所有请求成功、Scrape 掉线、遥测落后、服务退役与数据延迟；分母不足不能显示确定 100% 可用率。
2. **验收**：观测盲区和真实服务零错误分别可查

### BE-014 核验合同

- **BE-014-P · 输入/动作与合格判据：** 零流量/抓取掉线/延迟样本→无数据与零错误分清。
- **BE-014-F · 直接失败变异：** 分母0显示确定100%可用→失败。
- **BE-014-N · 合法邻例：** 真实0错误且分母充分可报告成功率。

## 十五、SLI 分子分母与业务口径
1. 为可用性、时延、数据正确性及异步履约定义可复算的成功事件、分母、截止点和合法排除项；不能悄悄移除高失败率租户。
2. **验收**：固定事件集人工复核与自动口径一致

### BE-015 核验合同

- **BE-015-P · 输入/动作与合格判据：** 固定事件集按口径手算→分子/分母/排除项一致。
- **BE-015-F · 直接失败变异：** 悄删失败租户或只算成功ACK→失败。
- **BE-015-N · 合法邻例：** 经权威定义的无效请求可合法排除并记理由。

## 十六、SLO、窗口与 Error Budget
1. SLO、观察窗口、可接受失败、适用用户和内部/客户合同界限由有权业务主体批准；SRE Workbook 为方法指南，示例目标不可自动变成强制指标。
2. **验收**：按当时有效版本和完整事件重算每个窗口

### BE-016 核验合同

- **BE-016-P · 输入/动作与合格判据：** 相同事件不同窗口/规则版本→SLO和预算可重算。
- **BE-016-F · 直接失败变异：** 复制SRE示例阈值当客户合同→失败。
- **BE-016-N · 合法邻例：** 内部SLO与外部SLA可不同且明确。

## 十七、多窗口 Burn Rate 告警
1. 基于实际 SLI 与样本量配置短/长窗 Error Budget Burn Rate、恢复和严重等级，兼顾大规模突发与长期低概率失败；不用未经批准的默认 Page 阈值。
2. **验收**：长短窗组合发现可行动的真实预算损失

### BE-017 核验合同

- **BE-017-P · 输入/动作与合格判据：** 短突发与长期低错误分别注入→多窗告警可行动。
- **BE-017-F · 直接失败变异：** 低样本噪声无限Page或恢复条件缺失→失败。
- **BE-017-N · 合法邻例：** 不同业务可选择不同有权阈值。

## 十八、黑盒用户探测与白盒原因
1. 合成请求从真实入口验证必要用户路径，内部指标解释锁、队列、资源和依赖；合成写入和资金路径不得污染真实客户数据。
2. **验收**：真实业务入口探测与内部故障归因相互印证

### BE-018 核验合同
