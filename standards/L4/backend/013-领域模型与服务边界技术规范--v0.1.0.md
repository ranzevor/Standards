# L4 领域模型与服务边界技术规范

**文档ID：** STD-L4-BACKEND-013　**版本：** 0.1.0　**状态：** adopted　**生效日期：** 2026-10-30

## 技术范围、现行依据与方法参考

本专项定义**如何发现、表达、保护和演进业务领域的模型及服务边界**，覆盖单体、模块化单体、Worker、Serverless、多服务及复杂业务系统。重点是领域身份与业务语义、聚合一致性边界、命令与查询、模块所有权、跨上下文契约、拆分和迁移中的业务保真。没有复杂领域规则的简单 CRUD、纯数据搬运与一次性研究原型，可以选择更轻量的函数／数据模型；不强制 DDD 类层级、微服务或事件总线。
组合采用 [L4 后端与分布式系统领域通用基线](007-后端与分布式系统领域通用基线--v0.1.0.md)（后端与分布式系统领域通用基线）、[L3 通用工程规范](../../L3/001-通用工程规范--v0.1.0.md)（L3 工程）、[L2 人类与 Agent 团队组织协作规范](../../L2/001-人类与-Agent-团队组织协作规范--v0.1.0.md)（L2 团队协作）与 [L1 全局治理补充规范](../../L1/001-全局治理补充规范--v0.1.0.md)（L1 治理）。有效业务目标、内容和实际数据权利由真实有权主体决定并在项目 L6 固定；冲突按 L1 处理。本专题不得通过设计模式改变业务批准权；项目 L6 负责所选技术机制及实际验收。
**方法参考（均为设计经验与指导材料，非 IETF/W3C 等协议型强制行业标准）**：
- [Martin Fowler — Bounded Context](https://martinfowler.com/bliki/BoundedContext.html)：上下文的语言与模型边界。
- [Martin Fowler — DDD Aggregate](https://martinfowler.com/bliki/DDD_Aggregate.html)：聚合与聚合根的一致性方法。
- [Martin Fowler — Domain Event（草稿性设计说明）](https://martinfowler.com/eaaDev/DomainEvent.html)：领域事件思想，不能据此强制事件溯源。
- [Microsoft Azure Architecture — Domain Analysis](https://learn.microsoft.com/en-us/azure/architecture/microservices/model/domain-analysis) 与 [Tactical DDD](https://learn.microsoft.com/en-us/azure/architecture/microservices/model/tactical-ddd)：可选建模方法和微服务边界示例；示例并不限制本规范只用于 .NET。
- [Microsoft Learn — Designing a microservice domain model](https://learn.microsoft.com/dotnet/architecture/microservices/microservice-ddd-cqrs-patterns/microservice-domain-model)：实体、值对象、聚合的技术讨论，允许简单服务不采用复杂对象模型。
- 对真实 API／事件的描述按项目需要引用 [OpenAPI 3.2.1](https://spec.openapis.org/oas/v3.2.1.html)、[RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html) 或 [CloudEvents v1.0.2](https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/spec.md)。这些只在选用相应协议时具有相应作用，不代替领域行为合同。

## 核验口径与消费接口

维护者负责落实本文机制，领域/API/存储提供者负责其权威保证，验收者从实际受支持入口观察结果。输入固定源码/构建、配置、数据/协议版本、角色/租户、目标平台、故障时序和预算；权威观察对象为**权威需求版本、领域身份/单位/不变量、命令结果与消费接口**。真实执行入口为**状态机/属性测试、真实持久化与跨入口差异样例、输入到导出逐字段对照**。逐章 P/F/N 分别为正常输入及判据、破坏该机制的直接失败变异、应继续成立的合法邻例；本章原有每项规则、原有验收与新增合同共同约束，不用单一通用案例替代具体子项。每个子项须在案例输入中保留其适用条件，并以自身原文规定的输出/不变量判定；复合章应拆记录各个观察量，不能以一个成功掩盖其他失败。

证据产物包括真实命令/用户动作、原始响应或事件、权威状态前后值、版本、时序、失败及恢复；尚无对应真实运行证据的场景状态为 `not-run`，标准库示例仅证明列明的局部边界。具体输入与命令见[执行入口](../../../examples/web-backend/RUNBOOK.md)，条款索引见[规范条款登记](../../../registry/requirements.json)，来源的有限支持命题见[逐命题来源映射](../../../sources/web-backend/claims.json)。

本文的跨组件约束与正例、失败反例、合法邻例由本规范综合定义；外部来源支持的机制及适用边界见来源表。项目架构、预算和业务规则由实际需求确定。L5 实现应映射到所选框架、SDK 或引擎；L6 按具体版本的提供者保证与受支持矩阵验收项目能力。

## 一、模型复杂度与设计投入
1. 对需求按业务规则密度、状态变化、用户／客户角色差异、跨角色交接、历史数据和预期维护成本评估复杂度；纯 CRUD 不必为 DDD 模式建立空壳聚合或 Repository。
2. 复杂度应由业务变化与必须维持的不变量证明。领域模型可使用对象、函数、代数数据类型、状态表或规则引擎，只要职责、输入、结果和约束可被验证。
3. 研发原型的临时简化不得静默成为正式产品的业务范围限制。由项目 L6 记录实际支持的行为、排除范围和从实验升级正式交付的触发条件。
4. **验收**：能说明每项抽象保护何种真实规则或变化，并能证明未引入没有价值的部署单元、配置或模型层。

### BE-001 核验合同

- **BE-001-P · 输入/动作与合格判据：** 列每个抽象保护的规则和变化样例→职责与成本可解释。
- **BE-001-F · 直接失败变异：** 纯CRUD堆空壳聚合却漏真实规则→失败。
- **BE-001-N · 合法邻例：** Transaction Script可满足简单业务。

## 二、领域发现与权威需求
1. 先恢复已批准的真实用户任务、业务术语、样本数据、状态、例外、权利主体及客户合同；现有代码、表字段名和模型训练输出只是证据或线索。
2. 根据使用场景辨认动作前置条件、合法输入差异、处理步骤、完成标准、失败补偿和受影响下游角色，不将单个页面或 API 视为完整业务。
3. 没有被授权作出的产品决定应保留问题及受影响范围，不用工程常见值、框架缺省值或统计均值代替。
4. **验收**：用真实或经批准的匿名业务样例逐步说明从输入到状态改变、通知／外部交付的条件，能定位决策责任与数据来源。

### BE-002 核验合同

- **BE-002-P · 输入/动作与合格判据：** 从权威需求样例走到下游交付→守卫/例外/决策主体可查。
- **BE-002-F · 直接失败变异：** 以当前表名或模型输出代产品决定→失败。
- **BE-002-N · 合法邻例：** 匿名合成样例可按授权用途验证。

## 三、统一语言与上下文词汇
1. 同一个术语在单一上下文内必须有确定的业务含义、身份、单位、允许状态和适用范围；不同上下文允许同名异义，避免强行用一个全局对象包揽所有概念。
2. 外部协议字段名、用户业务名、内部标识和数据库字段是不同层次的语言。保留需要的转换和语义映射，不为迎合框架或英文范式损害产品语言。
3. 关键词义变化应检查服务端行为、测试、前端展示、导出、事件和历史数据；术语字面相同不能成为兼容性证明。
4. **验收**：对存在歧义的示例能准确说明语义依赖的上下文与数据来源；业务读者与实施者指向同一组规则。

### BE-003 核验合同

- **BE-003-P · 输入/动作与合格判据：** 同名术语跨上下文对照→含义/单位/映射明确。
- **BE-003-F · 直接失败变异：** 同字段名即认同义并静默换单位→失败。
- **BE-003-N · 合法邻例：** 不同上下文允许同名异义。

## 四、子域分析和 Bounded Context 划界
1. 根据业务能力、规则变更原因、数据拥有者、权限、生命周期及事务一致性识别子域与有界上下文；上下文是模型意义适用范围，**不必一一对应微服务或部署进程**。
2. 核对两个候选上下文是否具有独立身份、模型规则与变化频率；若必须频繁同步内部数据才能完成普通任务，重新评估边界。
3. 在一个上下文内部可以继续模块化；不同上下文可以由同一人／Agent 实现，并在同一进程或仓库运行，不能由组织结构或 Agent 数量反推服务数。
4. **验收**：能给出每个上下文的核心业务能力、所有权、进入／离开契约及至少一个边界失效案例。

### BE-004 核验合同

- **BE-004-P · 输入/动作与合格判据：** 比较两能力生命周期和事务边界→上下文与部署独立说明。
- **BE-004-F · 直接失败变异：** 组织/Agent数量决定微服务数→失败。
- **BE-004-N · 合法邻例：** 多个上下文可同进程运行。

## 五、上下文关系和跨边界语义映射
1. 识别上下游及平级上下文的输入／输出依赖，区分共享且稳定的协议数据、上下游翻译、消费方适配与业务决策重新解释。
2. 可采用防腐层（Anti-Corruption Layer）、适配器或映射函数，隔离不稳定外部业务概念；是否实现成独立服务由复杂度与部署要求决定。
3. 避免在跨上下文接口中直接泄漏内部实体、ORM 对象、缓存键和私有状态机；公开契约须明确字段的实际业务语义与兼容责任。
4. **验收**：上游字段名、版本或内部实现变化时能定位受影响的下游映射，并验证业务信息不会静默丢失或错误重解释。

### BE-005 核验合同

- **BE-005-P · 输入/动作与合格判据：** 上游字段/版本变更经过适配→下游必要业务信息保留。
- **BE-005-F · 直接失败变异：** 直接暴露ORM私有状态并无兼容责任→失败。
- **BE-005-N · 合法邻例：** 稳定协议可共享无需独立适配服务。

## 六、实体身份与生命周期
1. 按业务连续性确定实体身份与生命周期；数据库自增值、外部供应商 ID、订单号和自然键可能代表不同作用域，不能互相替代。
2. 明确创建、激活、停用、合并、转移、撤销、归档与删除的合法条件；同一 ID 在不同租户或时间区间的可见范围按真实业务契约处理。
3. 实体身份映射到外部系统时须保留来源、版本、有效期与冲突规则，禁止以“同名”“同手机号”等弱证据无授权合并业务主体。
4. **验收**：重复创建、数据导入、身份变更、跨租户访问及历史实体读取中，身份一致性与领域行为正确。

### BE-006 核验合同

- **BE-006-P · 输入/动作与合格判据：** 创建/合并/迁移/重建同号实体→作用域与历史关联准确。
- **BE-006-F · 直接失败变异：** 同邮箱无授权合并跨租户主体→失败。
- **BE-006-N · 合法邻例：** 合法合并有权利批准及映射记录。

## 七、值对象、单位和数值精度
1. 值对象按业务意义及组成值判断等价性；金额、币种、数量、计量单位、时间范围、时区和地址等不得仅为提高代码复用而混成无类型字符串。
2. 值对象或等价函数必须验证合法范围、格式、精度、单位换算与不可变语义；对不适用对象模型的语言可采用类型与纯函数建立同等契约。
3. 存储和传输转换不得改变金额舍入、时区边界、度量精度或业务默认值；显示格式与实际计算须区分。
4. **验收**：单位不匹配、负值、超出界限、精度边界和不同货币的计算必须获得符合批准规则的结果或拒绝。

### BE-007 核验合同

- **BE-007-P · 输入/动作与合格判据：** 跨币种/负值/小数/时区转换→保留单位精度或拒绝。
- **BE-007-F · 直接失败变异：** 金额与数量共用无类型默认值→失败。
- **BE-007-N · 合法邻例：** 纯函数与类型可替代对象模型。

## 八、聚合边界与事务不变量
1. 只有需要**一起保护的一组业务不变量**才形成聚合；聚合不是泛用 List，也不能机械地以数据库表或 API 路由作为聚合根。
2. 采用聚合模式时，对外修改通过受控入口保护内部不变量；批量修改或 ORM 自动写回不能绕过已批准的领域状态转换。
3. 聚合范围应尽量与必须同步保持的业务一致性相匹配。把大量无关实体锁在同一事务会增加竞争，过度拆分则可能使必须原子保证的规则丢失。
4. 对跨聚合的真正规则，先确认是否需要同步约束及其有权数据来源，再决定同步协调、异步工作流、预留／确认或补偿；**不能把“最终一致”无条件套用所有跨聚合业务**。
5. **验收**：关键命令在并发、事务故障、版本冲突与重复执行后，聚合内不变量仍成立，跨聚合差异按实际批准的业务一致性要求处理。

### BE-008 核验合同

- **BE-008-P · 输入/动作与合格判据：** 并发关键命令与跨聚合失败→需要同步的不变量守住。
- **BE-008-F · 直接失败变异：** 所有跨聚合都宣称最终一致无需约束→失败。
- **BE-008-N · 合法邻例：** 可延期的跨域投影可异步收敛。

## 九、状态机与业务转换
1. 对具有多个稳定阶段的核心业务对象明确合法状态、触发动作、转换守卫、不变条件、有效时间与失败结果；不存在的业务阶段不必为流程图完整性添加。
2. 区分领域状态、异步处理中间态、UI 展示态、数据库事务状态和外部结算状态，不能让按钮动画或任务队列 ACK 成为永久业务完成。
3. 取消、撤销、退款、驳回、超时、过期和重开是否为不同状态，由实际业务合同决定；不能在代码中将其合并为一个泛化布尔量导致权益丢失。
4. **验收**：从每个合法阶段输入允许与禁止动作，实际输出、保存和回滚结果必须有独立测试，重要分支可追踪到原始需求。

### BE-009 核验合同

- **BE-009-P · 输入/动作与合格判据：** 每个合法阶段分别输入允许/禁止动作→守卫和持久状态一致。
- **BE-009-F · 直接失败变异：** 取消/退款/过期压成同boolean丢权益→失败。
- **BE-009-N · 合法邻例：** 不存在的业务阶段无需添加。

## 十、命令与查询的职责边界
1. 将引发业务状态变化的命令与读取业务事实的查询从语义上区分；是否采用独立的 CQRS 物理存储或服务由复杂度决定。
2. 命令须携带真实业务主体、操作身份、版本前提和合法必要参数；服务端在提交时校验当前状态及权限，不信任调用者预先验证结果。
3. 查询可以使用衍生表示，但必须规定来源、新鲜度、权限、排序、分页和局部数据缺失；不允许在查询过程中意外执行收费或改变状态的操作。
4. **验收**：读写分离、缓存命中和索引滞后均不使查询伪装成权威写入或错误升级为“已完成”。

### BE-010 核验合同

- **BE-010-P · 输入/动作与合格判据：** 重复查询与带版本命令→读不执行用户未请求写，写校验当前权威。
- **BE-010-F · 直接失败变异：** 缓存命中当已付款或查询隐式发货→失败。
- **BE-010-N · 合法邻例：** CQRS语义分离不强制两套物理存储。

## 十一、应用用例编排与领域决策
1. 应用层负责接收命令、授权、启动事务、调用领域决策、持久化及协调外部系统；业务规则和状态转移应留在可独立验证的领域职责或等价纯函数中。
2. 对简单项目允许清晰的 Transaction Script。避免为了形式让只有 CRUD 的项目出现空洞 Controller/Service/Repository 多级转发。
3. 领域服务（如采用）承载不自然归属某一实体／值对象的跨对象领域规则；不能让“Service”后缀本身授予其跨业务上下文的决定权。
4. **验收**：同一用例经 Web、API、CLI、Agent/MCP 或计划任务入口调用时，执行相同的必要授权与业务规则，避免多个入口各复制不同实现。

### BE-011 核验合同

- **BE-011-P · 输入/动作与合格判据：** Web/API/CLI/任务同输入→同一必要授权和领域决定。
- **BE-011-F · 直接失败变异：** 每入口复制不同余额规则→失败。
- **BE-011-N · 合法邻例：** 简单用例可单事务脚本。

## 十二、基础设施适配与依赖方向
1. 将数据库、消息队列、HTTP 客户端、文件系统、外部模型及收费提供方的具体实现从领域规则中隔离；领域层不应为了技术框架升级改变业务语义。
2. 可使用接口／端口与适配器，在真实替换或测试价值足够时引入；不强制每个数据库查询都包一层无意义接口。
3. 数据加载中的失效、并发、数据库事务边界和远端失败均须通过应用编排与真实基础设施合同约束；领域对象测试通过不能自动证明持久层正确。
4. **验收**：更换适配器或模拟失败时核心业务决策保持一致；有正式部署时仍运行真实持久化与外部系统的必要集成验证。

### BE-012 核验合同

- **BE-012-P · 输入/动作与合格判据：** 更换适配器并注入真实持久失败→规则语义不变且未知可查。
- **BE-012-F · 直接失败变异：** 领域单测绿冒数据库集成正确→失败。
- **BE-012-N · 合法邻例：** 无真实替换价值不强制接口包层。

## 十三、数据所有权与跨上下文访问
1. 明确某种业务状态的**唯一权威写入上下文**及其他消费者的读取／订阅方式；物理共用数据库也不代表任意模块可直接改写对方拥有的业务字段。
2. 在共享数据库或跨服务直接查询不可避免时，记录实际授权、依赖与模式演进成本，逐步建立有契约的访问边界。
3. 跨上下文引用尽量使用稳定身份及明确的映射，避免绕过拥有者直接修改内部关联结构；需要同步保证的不变量按实际协调设计。
4. **验收**：一个上下文单独改变存储 Schema、归档或访问策略时，其他消费者不在无通知情况下静默损坏状态或丢失字段。

### BE-013 核验合同

- **BE-013-P · 输入/动作与合格判据：** 一上下文改内部Schema→消费者合同仍保持或明确升级。
- **BE-013-F · 直接失败变异：** 共用数据库就任意改他方权威字段→失败。
- **BE-013-N · 合法邻例：** 授权且契约化跨模块读可存在。

## 十四、领域事件与集成事件
1. 事件名称须表达实际已发生、具有业务意义的事实；内部领域事件和对外集成事件的身份、字段与订阅者不可混同。
2. 采用领域事件时，明确产生时机、事务提交关系、重复处理、失败补偿、访问控制及历史演进；事件对象创建不代表已可靠交付下游。
3. 如跨服务使用 CloudEvents，只对已选择的版本使用其格式契约，不能将其当作 Outbox、ACK 或 Exactly-Once 的替代品。
4. 简单服务若无需事件，不强制制造领域事件层。事件溯源（Event Sourcing）是另一项重大持久化架构决定，不能因存在事件类而自动启动。
5. **验收**：事务提交成功但事件发送失败、事件晚到、重放和消费者重复时，来源领域状态仍正确，业务接受和下游交付分别有证据。

### BE-014 核验合同

- **BE-014-P · 输入/动作与合格判据：** 事务回滚/提交后发事件失败/历史回放→事实与可靠交付分开。
- **BE-014-F · 直接失败变异：** 创建事件对象即宣布下游已收到→失败。
- **BE-014-N · 合法邻例：** 无事件需求不引入事件溯源。

## 十五、跨边界权限与商业责任
1. 模型边界不等于安全边界；租户、对象、资金、供应方授权和数据再使用权限仍应在实际请求入口及写入决定时核验。
2. 客户／合作方拥有的独立决定不能被开发团队或 Agent 改造成内部技术开关；跨上下文传输须最小化客户资料和长期凭据。
3. 业务身份与数据库标识、Web Session、JWT 声明和 Agent 角色可能不同，必须按实际权利主体映射和验证。
4. **验收**：从另一个上下文、旧 API、异步重放或内部管理入口调用同一操作，不得绕过领域及对象授权。

### BE-015 核验合同

- **BE-015-P · 输入/动作与合格判据：** 旧API/异步/内部管理调用同命令→对象与商业授权一致。
- **BE-015-F · 直接失败变异：** 内部服务身份冒客户资金决定权→失败。
- **BE-015-N · 合法邻例：** 合法委派按资源动作范围执行。

## 十六、时间、版本与可追溯事实
1. 业务生效时间、事件发生时间、记录写入时间、外部确认时间和读取快照时间须按项目业务意义区分；不把服务器当前时间自动当成所有操作的法律时间。
2. 版本控制覆盖乐观并发前提、领域事件／消息版本和外部协议版本；语义改变须考虑历史数据的解释方式及兼容时间窗口。
3. 对重要领域决定应能追踪对应的批准规则版本、输入、决定主体及结果；审计信息只向有权限的技术和业务角色披露。
4. **验收**：晚到事件、时区边界、旧快照、迁移后回放与数据更正不造成错误状态或虚构历史结果。

### BE-016 核验合同

- **BE-016-P · 输入/动作与合格判据：** 迟到事件/更正/迁移回放→发生/提交/生效/读取时间不混。
- **BE-016-F · 直接失败变异：** 用当前时间覆盖原业务生效时刻→失败。
- **BE-016-N · 合法邻例：** 仅有记录时刻的普通对象不虚构法律时间。

## 十七、派生查询模型与 CQRS（按需）
1. 当读写规模、用户任务或复杂查询确有差异时可为查询建立专门投影，必须记录来源、投影生成规则、回放和数据新鲜度。
2. 查询模型不拥有它所投影的业务事实的修改权限；多个消费者各自持有的摘要不能互相覆盖来源真相。
3. 大量读者可通过缓存／搜索索引优化查询，但源数据删除、权限撤销与精确金额应在允许窗口内正确传播；必要强一致数据应优先从权威位置读取。
4. **验收**：异步投影落后、重建、丢消息、权限变化和跨版本迁移时，用户看到的状态准确标明其有效性并保持应有信息。

### BE-017 核验合同

- **BE-017-P · 输入/动作与合格判据：** 投影延迟/删除/重建→新鲜度和权限边界明确。
- **BE-017-F · 直接失败变异：** 查询投影反向改权威源或丢墓碑→失败。
- **BE-017-N · 合法邻例：** 无读写规模差异不强制CQRS。

## 十八、同步与异步业务编排
1. 跨上下文工作流应按实际业务节点明确命令、前提、被谁确认、可重试性、最长等待、可能补偿和无法撤销的副作用。
2. 不能仅凭两个模块都写入成功就视为客户任务完成；需要第三方发货、结算、确认或通知时，应分别保存其权威确认。
3. 选择同步跨服务调用前评估依赖可用性、延迟和故障扩散；选择异步事件前评估数据新鲜度、恢复成本和用户认知。
4. **验收**：任何节点失败后的已有状态、客户权益、资源预留与恢复路径都可复核；不把 UI 乐观结果当作后端完成。

### BE-018 核验合同

- **BE-018-P · 输入/动作与合格判据：** 任一步失败并查各域回执→预留/权益/补偿路径可查。
- **BE-018-F · 直接失败变异：** 两模块写成就当客户已收货→失败。
- **BE-018-N · 合法邻例：** 可接受同步调用时不强制消息。

## 十九、模块边界、依赖图与演进
1. 模块依赖遵循真实领域关系，防止双向编译依赖、跨模块直接写内部模型、共用数据库对象使所谓独立边界流于形式。
2. 低成本可逆调整可由项目常规变更处理；破坏性边界调整须列出调用关系、数据消费者、持久身份与兼容回退条件。
3. 多个 Agent 并行修改不同上下文时，共享契约与权威写入由 L2 明确责任人；不得以并行方便制造两个业务事实来源。
4. **验收**：单独修改一个业务模块及其内部实现时，其他模块的已确认合同仍能通过独立测试；必要公共接口变化有明确升级方案。

### BE-019 核验合同

- **BE-019-P · 输入/动作与合格判据：** 改模块内部实现并做合同回归→依赖与权威写入不冲突。
- **BE-019-F · 直接失败变异：** 为并行开发造两个当前业务真相→失败。
- **BE-019-N · 合法邻例：** 单人可维护多个隔离模块。

## 二十、从单体拆分或合并服务
1. 单体分拆需有实际部署、扩缩、独立发布、安全隔离或业务治理价值；功能拆成多个网络调用会新增故障、权限与成本，不能只为“现代化”而实施。
2. 拆分时先固定原业务状态、身份、数据拥有者、协议消费者、事务与真实环境，再选择功能迁移、兼容代理或逐步切换策略。
3. 并行读写、双数据源迁移与数据回填应有版本身份、对账与故障恢复；不应在缺少数据完整性证据时删除旧系统权威数据。
4. 对反复造成分布式协调开销却无独立价值的服务，可在授权下重新合并；此技术选择需要受测运行证据。
5. **验收**：迁移前后相同合法业务输入得到等效可验结果，受支持旧消费者仍安全工作，产出、可靠性及成本按目标比较。

### BE-020 核验合同

- **BE-020-P · 输入/动作与合格判据：** 拆分/合并前后同合法输入对照→身份/事务/产出/成本等效。
- **BE-020-F · 直接失败变异：** 双写未对账便删旧权威数据→失败。
- **BE-020-N · 合法邻例：** 无独立部署价值可保留单体。

## 二十一、模型错误与信息保真的回归
1. 为历史缺陷记录触发条件、原业务不变量、错误发生的代码或数据边界、根因及回归样本，避免将错误行为测试固化为正式契约。
2. 检查领域字段从请求、模型、持久存储、聚合、事件、导出到下游参与者的传递，特别是金额、数量、权限、状态、来源与有效期。
3. 使用属性测试、状态机测试、合约测试及跨模块集成检查实际所需的不变量；工具链具体做法交由 L5/L6 决定。
4. **验收**：原故障能够由测试反事实重现，修复后在相同场景和邻近边界行为中确实被阻断。

### BE-021 核验合同

- **BE-021-P · 输入/动作与合格判据：** 重现历史反例并跑邻近合法值→真实规则恢复且字段链保真。
- **BE-021-F · 直接失败变异：** 把历史BUG的输出固化为正式oracle→失败。
- **BE-021-N · 合法邻例：** 合法不同金额/期限应产生不同结果。

## 二十二、可审查领域设计的最小证据
完成一个有复杂领域规则的技术变更时，现有仓库 Issue/PR、源码和测试应能回答：业务概念与适用上下文是什么、哪一主体批准规则、哪些数据属于权威、哪些不变量必须同步成立、通过何种命令修改、重要消费者和兼容窗口为何、失败后如何恢复、实际测试了什么。
单纯的数据读取工具不需要为每项工作创建完整上下文地图。证据可存在于已授权的权威仓库或系统中，不新增与其冲突的第二套“当前状态”数据库。

### BE-022 核验合同

- **BE-022-P · 输入/动作与合格判据：** 从变更证据反查上下文、权威、不变量与消费者→最小材料足够。
- **BE-022-F · 直接失败变异：** 另建冲突当前状态数据库代证据→失败。
- **BE-022-N · 合法邻例：** 简单只读工具无需完整上下文地图。

## 二十三、技术失败模式与静态验收矩阵
| 具体场景 | 验证的领域边界 | 预期的真实工程结果 |
| --- | --- | --- |
| 单一简单 CRUD 无复杂规则 | 设计开销与模型复杂度 | 允许轻量数据模型，不强制聚合／微服务形式 |
| 两个上下文都使用“账户”一词 | 词义、字段所有权与变更 | 各上下文使用自身定义，映射有契约，不错误共用全局类 |
| 合法状态变化被 DTO 转换删掉 | 端到端语义与数据保真 | 所有必要条件保留，下游行为不同且正确 |
| 不同租户实体拥有同样外部 ID | 身份及租户作用域 | 无法越权合并、读取和修改另一租户资源 |
| 不同货币金额直接相加 | 值对象、单位与不变量 | 被规则明确拒绝或经过有权批准的汇率转换 |
| ORM 绕过聚合根直接改子对象 | 聚合一致性和封装 | 事务最终不得处于不合法业务状态 |
| 两个聚合需要共享库存约束 | 业务一致性范围 | 明确定义预留／确认及并发处理，不错误默认最终一致即可 |
| 取消和退款被建成相同状态 | 状态机与客户权益 | 真实规则保持区别，历史和下游处理准确 |
| CLI 与 API 各实现一套业务校验 | 多入口领域决策归属 | 共同权威规则，无法绕过权限或业务前提 |
| 上游改名但业务含义未变化 | 防腐层与上下文映射 | 消费方按受支持版本保持兼容 |
| 共享数据库导致他域字段被擅改 | 数据拥有者及访问边界 | 只有有权上下文执行写入，已有读者正确恢复 |
| 事件创建但发送失败 | 领域事件与集成事件 | 真实业务状态与下游交付分别可核对及恢复 |
| 投影索引滞后于权威数据 | CQRS 和缓存新鲜度 | 准确提示延迟，不能虚构永久状态或丢失权限 |
| 原事务已提交但调用超时 | 命令身份与重复副作用 | 查询已提交结果，重试不重复扣费或发信 |
| 同步调用依赖服务不可用 | 服务边界与失败传播 | 明确安全降级或受控失败，不用假成功掩盖 |
| 拆分服务后旧消费端仍在线 | 上下文版本和迁移 | 支持窗口内兼容或安全失败，必要数据不丢失 |
| 跨版本回放历史领域事件 | 时间、Schema、历史语义 | 状态重建保留已批准历史含义，不能篡改原证据 |
| 多 Agent 修改相同权威模型 | 共享写入与语义冲突 | 按 L2 协调唯一写入或版本控制，不能盲目覆盖 |
| 实验性 DDD 重构使接口全部变慢 | 设计收益与运行成本 | 基于真实负载审查取舍，保留正确行为并可撤回无效拆分 |
| 复杂实体删除时其他上下文仍引用 | 生命周期及关联数据权利 | 依约处理归档、撤销、孤儿引用和必要历史记录 |
## 二十四、批准与项目采用边界
1. 本专项负责**领域模型、语义和服务边界**，不代替后续 HTTP/RPC 传输专项、事务锁／幂等、可靠消息、分布式补偿、认证和可观测性专项。领域约束可与邻接规范联合使用，但各自的标准版本及验收责任保持独立。
2. HTML/CSS 及前端页面的用户行为归 Web L4；物理表结构和数据库迁移归数据库 L4；加密及认证协议归安全 L4；具体实现语言、依赖注入框架、ORM 与测试工具归 L5。
3. 业务规则批准者、法律与数据权利人、Agent 权限及实际项目源码都不能被本规范覆盖。审批仅确认规范条文效力，未对任何项目执行代码、服务、数据迁移、安全、负载及端到端验收；项目落地按 L6 单独验证。
