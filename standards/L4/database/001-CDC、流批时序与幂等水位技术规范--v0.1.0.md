# L4 CDC、流批时序与幂等水位技术规范

**文档ID：** STD-L4-DATABASE-001　**版本：** 0.1.0　**状态：** adopted　**生效日期：** 2026-10-30

## 一、适用范围与现行规范分工

本技术专题属于 L4「数据库与数据工程」第 11 项。仅在项目确有源数据变更捕获、增量事件同步、持续流计算或流批衔接需求时适用；单次 CSV、定时全量导入与无流式业务的小型系统不承担部署 CDC 连接器、Kafka、Flink 或独立数据平台的默认义务。

本规范深化**从选定源数据库提交日志/变更流至事件时间处理、目标数据可见结果**的技术契约：快照—增量衔接、源日志位点、消息消费位置、Event Time/Processing Time/Watermark、迟到和重放、去重状态、Sink 提交与资源边界。

与现行 L4 的分工：数据库物理 WAL/崩溃一致性规范负责源引擎的日志持久性；复制/高可用规范负责副本追赶与选主；第 10 项导入/ETL/ELT 规范负责批量来源解析、批次转换与质量；后端消息事件规范负责业务消息投递、Outbox/Inbox 及外部副作用。本文不将 CDC 行变更自动认定为有业务授权的领域事件，不让源 LSN、Broker Offset、Flink Checkpoint、事件时间 Watermark 和业务完成水位互相替代。第 12—14 项列式湖仓、元数据血缘与数据安全仍各自独立。L5 按真实产品/连接器/驱动版本选择实现；L6 确定数据权利、合同、费用、环境与最终客户业务验收。

## 三、48 项 CDC 与流批时序机制及可验证断言

以下每项均提供可由真实项目按其选用技术和授权执行的验收断言；验收需区分源规范审查、隔离流水线和真实业务结果。

### §01 适用性与源更新模型
**机制：** 先识别实际需要连续更新的源/目标及更新频率。一次性文件导入不必引入 CDC；按源数据库日志、API 变更流或周期差量读取的真实能力选择。
**验收：** 能说明是否需要流式捕获、允许延迟和不采用 CDC 时的完整性策略。

**核验合同与来源：** [cdc-R01](#cdc-R01)；本条对应的失败输入见下文验证矩阵。

### §02 来源身份、数据权利与最小捕获
**机制：** 对数据库/表/列/租户、源系统账号、捕获用户及消费目的形成明确授权；读到 Binlog/WAL 不等于有权外发所有行。
**验收：** 越权行、字段和跨租户 CDC 事件不会被复制到未授权目标。

**核验合同与来源：** [cdc-R01](#cdc-R01)；本条对应的失败输入见下文验证矩阵。

### §03 变化覆盖与失效语义
**机制：** 明确选定源只覆盖哪些 Insert/Update/Delete、DDL、截断及非事务操作；捕获范围不能凭产品名推断。
**验收：** 未覆盖操作、过滤表和非持久源写入均有可检测的合同偏差。

**核验合同与来源：** [cdc-R01](#cdc-R01)；本条对应的失败输入见下文验证矩阵。

### §04 初始基线快照的一致性
**机制：** 快照要绑定源一致性读视图、捕获时点和源端日志位点；不能先全量扫描完再随意从当前日志尾续读。
**验收：** 快照期间并发修改不会产生永久遗漏，且快照与日志位点能复现。

**核验合同与来源：** [cdc-R01](#cdc-R01)；本条对应的失败输入见下文验证矩阵。

### §05 快照与增量流的衔接
**机制：** 明确初始快照/增量快照时捕获窗口的打开、关闭、缓冲与去重算法，不将采集开始时间等同于提交位点。
**验收：** 快照扫描同一主键期间发生更新、删除和重插时目标最终状态正确。

**核验合同与来源：** [cdc-R01](#cdc-R01)；本条对应的失败输入见下文验证矩阵。

### §06 快照中断与再初始化门禁
**机制：** 首次快照、中断重启和丢失位置后的重新快照应分别处理，分区范围和完成标记必须持久、可恢复。
**验收：** 重启后既不把部分快照当作完整，也不会无条件删除既有目标。

**核验合同与来源：** [cdc-R01](#cdc-R01)；本条对应的失败输入见下文验证矩阵。

### §07 PostgreSQL 逻辑槽与 LSN
**机制：** PostgreSQL 18 逻辑 Slot/LSN 表示数据库变更流进度；崩溃后槽可能从较早检查点重新发出数据。LSN 不是所有行事件的全局唯一 ID，同一事务/记录附近可有多个合法行事件；按实际输出协议保存源实例/世代、事务及记录内序号或连接器提供的完整源 Offset，确认消费进度与业务去重分别治理。

**验收：** 将同一源事务的两行变更置于相同 LSN 作用域并重复交付：两个不同事件都生效、重复事件无二次副作用；切主/重建源世代不同不能误去重。由源位点恢复捕获不等于目标可见或付款完成。

**核验合同与来源：** [cdc-R02](#cdc-R02)；本条对应的失败输入见下文验证矩阵。

### §08 PostgreSQL Replica Identity
**机制：** UPDATE/DELETE 的旧值取决于 REPLICA IDENTITY 和表键；不能假设所有无主键表都带可用的 before 全行。
**验收：** 对键缺失及旧值不足的删除/更新明确拒绝、补充配置或受控降级。

**核验合同与来源：** [cdc-R02](#cdc-R02)；本条对应的失败输入见下文验证矩阵。

### §09 PostgreSQL Slot 留存与切主
**机制：** Slot 阻止所需 WAL 清理并可能占满磁盘；PG18 Failover Slot 同步依配置和实际同步状态，不是零条件自动继承。
**验收：** 断连增长、WAL 占用和切主后的槽可恢复性分别有门禁。

**核验合同与来源：** [cdc-R02](#cdc-R02)；本条对应的失败输入见下文验证矩阵。

### §10 MySQL Binlog 定位与 GTID
**机制：** Binlog 文件+位置或 GTID 是 MySQL 提供的源变更游标，与 Kafka Offset、业务事件序号不同；跨服务器/切主须核对连续性。
**验收：** Binlog 轮转、GTID 变化和事务回放不会跳过合法源变更。

**核验合同与来源：** [cdc-R03](#cdc-R03)；本条对应的失败输入见下文验证矩阵。

### §11 MySQL Row Image 与 DDL
**机制：** ROW/STATEMENT/MIXED、row image/metadata、DDL 和列过滤会改变可观测信息；按 MySQL 8.4 实际配置与连接器版本判定。
**验收：** 删列、变更键和特殊值更新时不会默默破坏目标映射。

**核验合同与来源：** [cdc-R03](#cdc-R03)；本条对应的失败输入见下文验证矩阵。

### §12 SQL Server CDC 有效 LSN 区间
**机制：** SQL Server CDC 的捕获实例可用范围受异步采集与清理影响，All Changes/Net Changes 与闭区间边界不同。
**验收：** 断档 LSN、闭区间重复边界及前后影像均按选定函数正确处理。

**核验合同与来源：** [cdc-R03](#cdc-R03)；本条对应的失败输入见下文验证矩阵。

### §13 MongoDB Resume Token 与 Invalidate
**机制：** MongoDB 8.0 Change Stream 恢复使用可用 Resume Token；Oplog 超保留或集合 Drop/Invalidate 后不能盲目使用旧 resumeAfter。
**验收：** 失效 Token、重命名/删除和重新订阅均显式处理，禁止假成功。

**核验合同与来源：** [cdc-R03](#cdc-R03)；本条对应的失败输入见下文验证矩阵。

### §14 DynamoDB Streams Shard 与保留
**机制：** DynamoDB Streams 保存期为 24 小时；Shard 具有父子继承次序，只保证同一 Item 的顺序，不能推导全表顺序。
**验收：** 父分片未处理完、断连超 24 小时、跨 Item 乱序得到明确处理。

**核验合同与来源：** [cdc-R03](#cdc-R03)；本条对应的失败输入见下文验证矩阵。

### §15 源事件信封与 Schema
**机制：** 捕获事件明确 Source、表/集合、键、操作类型、before/after、源位点和版本；CloudEvents source+id 不自动保证事务回放成功。
**验收：** 未知操作类型、空值与 schema 版本变更不会被当作合法更新。

**核验合同与来源：** [cdc-R04](#cdc-R04)；本条对应的失败输入见下文验证矩阵。

### §16 源事务边界与跨表顺序
**机制：** 源事务中的多行变更可分多个事件交付；确需跨表原子可见的目标要保存事务标识及完成边界。
**验收：** 同一交易分表事件乱序或中断不会被提前发布为完整业务事实。

**核验合同与来源：** [cdc-R04](#cdc-R04)；本条对应的失败输入见下文验证矩阵。

### §17 主键变更、删除和 Tombstone
**机制：** 区分 Key Update、DELETE、Truncate、Kafka Tombstone/压缩标记；物理删除语义须由源/目标协议确定。
**验收：** 更新键后旧键不留幽灵行，Tombstone 不会误作 null 字段更新。

**核验合同与来源：** [cdc-R04](#cdc-R04)；本条对应的失败输入见下文验证矩阵。

### §18 源进度心跳与静默源
**机制：** 无业务变更与采集器停滞是不同状态；心跳和来源健康信号不能替代真实消息的源端完整性检查。
**验收：** 空闲源仍能检测日志断档，繁忙源不会用心跳覆盖实际 Offset。

**核验合同与来源：** [cdc-R04](#cdc-R04)；本条对应的失败输入见下文验证矩阵。

### §19 源日志位点与 Broker Offset 分离
**机制：** 数据库 LSN/GTID/Resume Token、消息 Topic/Partition/Offset、作业 Checkpoint 与业务水位各有不同拥有者。
**验收：** 任一进度指标缺失都不会由另一指标自动填充或推进。

**核验合同与来源：** [cdc-R04](#cdc-R04)；本条对应的失败输入见下文验证矩阵。

### §20 消费者位点提交时序
**机制：** 消费 Offset 的提交必须相对于结果持久化安排；先确认再写目标可能丢数据，先写后确认会有重放窗口。
**验收：** 在提交前后注入宕机，记录可识别的重放或遗漏范围。

**核验合同与来源：** [cdc-R04](#cdc-R04)；本条对应的失败输入见下文验证矩阵。

### §21 分区重平衡与旧 Worker 隔离
**机制：** Consumer Group 租约变更和分区撤销时旧 Worker 可能继续写；目标写入需要租约 Epoch、Fencing 或等价可证明控制。
**验收：** 双消费者并发写同一键不会让过期 Worker 覆盖新提交。

**核验合同与来源：** [cdc-R04](#cdc-R04)；本条对应的失败输入见下文验证矩阵。

### §22 重试、重放与幂等消费
**机制：** At-least-once 源或连接器恢复可能重复输出；业务去重必须按源事件身份、目标对象及生效作用域设置。
**验收：** 超时重试、重放和重复 Kafka 记录不会造成重复账款或状态倒退。

**核验合同与来源：** [cdc-R04](#cdc-R04)；本条对应的失败输入见下文验证矩阵。

### §23 Exactly-Once 的真实系统边界
**机制：** Kafka Streams 事务可原子关联所支持 Kafka 输入 Offset、状态与 Kafka 输出；Flink Checkpoint 保证依来源/目标连接器和配置，均不自动覆盖外部邮件/付款。
**验收：** 一次外部支付仍有可能与数据管道提交分离，验收能指出边界。

**核验合同与来源：** [cdc-R04](#cdc-R04)；本条对应的失败输入见下文验证矩阵。

### §24 背压、积压与日志保存预算
**机制：** 监控源日志保留、Broker Retention、消费延迟、重试积压及下游吞吐；超过可重放时长须停机/补数决策，不能盲目推进进度。
**验收：** 暂停消费超过保留期会触发缺口告警，而非自动跳到最新记录。

**核验合同与来源：** [cdc-R04](#cdc-R04)；本条对应的失败输入见下文验证矩阵。

### §25 事件时间与处理时间
**机制：** Event Time 来源于业务事件，Processing Time 为算子机器时钟，Ingestion Time 视框架定义；不得用接收时间替代交易发生时间。
**验收：** 网络延迟、旧消息回放不会改变业务所属时间窗。

**核验合同与来源：** [cdc-R05](#cdc-R05)；本条对应的失败输入见下文验证矩阵。

### §26 时间戳来源、时区与时钟漂移
**机制：** 区分源提交时间、业务有效时间、Debezium 处理时间；保留时区、精度和非法/缺失时间的处理契约。
**验收：** DST 切换、时钟倒拨及旧交易晚入库不造成不可解释的窗口迁移。

**核验合同与来源：** [cdc-R05](#cdc-R05)；本条对应的失败输入见下文验证矩阵。

### §27 事件时间 Watermark 生成
**机制：** Watermark 估计事件时间进度，不是源数据库日志提交 LSN；选择单调或乱序延迟策略需基于实际来源事件时间分布。
**验收：** 离群未来时间戳不能错误推动水位导致正常迟到数据被丢弃。

**核验合同与来源：** [cdc-R05](#cdc-R05)；本条对应的失败输入见下文验证矩阵。

### §28 空闲分区与时间推进
**机制：** Flink 多分区输入通常取活跃输入最小 Watermark；withIdleness 可把超时静默分区暂时排除。Idle 不是该分区永远完成或后续消息不会迟到的证明；重新活跃时旧事件可能晚于已推进水位，必须按 allowed lateness、旁路修正或有界重算处理，不能把全局水位倒退作为恢复算法。

**验收：** 测试分区空闲、其他分区推进窗口及原分区恢复旧事件三段序列；分别核对及时窗口、迟到侧输出/补偿和最终业务对账。合法空闲分区不应无限阻塞，但不能以静默丢弃恢复事件换取低延迟。

**核验合同与来源：** [cdc-R05](#cdc-R05)；本条对应的失败输入见下文验证矩阵。

### §29 多源 Watermark 合并策略
**机制：** JOIN/UNION 不同源的 Watermark 合并可能取最慢一路；Spark 多水位默认 min 与可选 max 的取舍须独立审批。
**验收：** 单路延迟或被强制加速时，损失/延迟范围可量化。

**核验合同与来源：** [cdc-R05](#cdc-R05)；本条对应的失败输入见下文验证矩阵。

### §30 迟到数据截止与保留契约
**机制：** Allowed Lateness、迟到阈值、窗口最终关闭、丢弃/旁路修正分别定义；超阈值的批次不能无限重开历史结果。
**验收：** 法定补录和业务修订事件有明确补偿路径而非静默丢弃。

**核验合同与来源：** [cdc-R05](#cdc-R05)；本条对应的失败输入见下文验证矩阵。

### §31 窗口边界与时间历法
**机制：** 固定、滑动、会话窗口按业务时区、闭开边界和夏令时约定，不能将自然日等价为固定 86400 秒。
**验收：** DST 23/25 小时日和边界毫秒数据能正确进入窗口。

**核验合同与来源：** [cdc-R06](#cdc-R06)；本条对应的失败输入见下文验证矩阵。

### §32 Trigger 与早晚多次输出
**机制：** Beam Trigger 可能早发、准时发、迟发；Accumulating/Discarding 模式影响下游是否需要撤销或增量计算。
**验收：** 同一窗口多次 Pane 不被错误累计成多笔独立交易。

**核验合同与来源：** [cdc-R06](#cdc-R06)；本条对应的失败输入见下文验证矩阵。

### §33 状态保留与去重有效期
**机制：** 有状态 JOIN/去重需按 Watermark、TTL 和真正重复间隔设置边界；过短导致再入、过长导致无界状态。
**验收：** 迟到超过去重 TTL 与状态清理后的再投递都有明确结果。

**核验合同与来源：** [cdc-R06](#cdc-R06)；本条对应的失败输入见下文验证矩阵。

### §34 流流 JOIN 时间约束
**机制：** 流流 JOIN 要明确事件时间范围、双侧水位及状态清理机制；不能直接对无限流做无界 JOIN 并期待资源稳定。
**验收：** 其中一侧停滞、另一侧积压时不会无限增长或错配其他日期事件。

**核验合同与来源：** [cdc-R06](#cdc-R06)；本条对应的失败输入见下文验证矩阵。

### §35 变更表与撤回输出
**机制：** 动态表更新/撤销流需要目标支持 UPDATE/DELETE/Retraction；仅追加 Sink 无法正确表达历史聚合修正。
**验收：** 迟到更正会更新或撤回旧计数，而不是永久保留双份冲突值。

**核验合同与来源：** [cdc-R06](#cdc-R06)；本条对应的失败输入见下文验证矩阵。

### §36 批流一致性与有界重算
**机制：** 同一逻辑在批量重算与实时流执行中使用一致的事件时间、过滤条件、映射版本、迟到策略及输入边界；不把 Batch 终止等同流终止。
**验收：** 相同封闭输入区间在受控重算后的结果差异可以解释或归零。

**核验合同与来源：** [cdc-R06](#cdc-R06)；本条对应的失败输入见下文验证矩阵。

### §37 目标写入版本与幂等键
**机制：** 目标条件更新和去重键绑定租户、源实例/世代、源对象键、事件身份及协议定义的可比较版本。LSN/GTID/Token 仅在各自源协议和有效世代内比较，不对不同源数值全序；删除及同键重建须保存可区分的世代/删除版本，避免旧 tombstone 或旧补数覆盖新实体。

**验收：** 交错重放旧值、删除、同键重建及不同源/租户同 ID：拒绝旧版本、保留全部独立合法对象；事件去重与业务操作幂等分别核对。无法确定可比顺序时进入冲突/对账而非任选较大数。

**核验合同与来源：** [cdc-R07](#cdc-R07)；本条对应的失败输入见下文验证矩阵。

### §38 结果提交与进度原子边界
**机制：** 消费位点或 Flink Checkpoint 与 Sink 持久结果必须有事务/提交协议或可审计补偿；S3/HTTP 等外部系统不能默认保证同一原子事务。
**验收：** 目标写成功但 Checkpoint 失败、反向顺序发生时可恢复而无永久漏账。

**核验合同与来源：** [cdc-R07](#cdc-R07)；本条对应的失败输入见下文验证矩阵。

### §39 外部副作用的业务幂等
**机制：** 支付、邮件、通知和客服操作由业务授权规则控制；CDC 行事件只是触发候选，不能绕过现行后端消息与 Outbox/Inbox 约束。
**验收：** 重播历史变更不会重复发送对账款或触发二次退款。

**核验合同与来源：** [cdc-R07](#cdc-R07)；本条对应的失败输入见下文验证矩阵。

### §40 删除、软删与 Tombstone 目标一致性
**机制：** 目标 Snapshot、Upsert、软删除和物理删除的语义须明确；Kafka Compaction 的空值 Tombstone 与数据库业务 NULL 不同。
**验收：** 同一实体删除后重新创建、键更新及 Tombstone 重放得到正确的最终版本。

**核验合同与来源：** [cdc-R07](#cdc-R07)；本条对应的失败输入见下文验证矩阵。

### §41 CDC Schema 演化与消费兼容
**机制：** CDC 记录格式、源字段重命名/类型改变、主键迁移和历史版本解码要先验证旧新 Reader、Sink 的兼容窗口。
**验收：** 流中途 DDL 变更不会误把新金额列当作旧字符串或丢失删除键。

**核验合同与来源：** [cdc-R07](#cdc-R07)；本条对应的失败输入见下文验证矩阵。

### §42 目标业务可见性与阶段完成
**机制：** 采集成功、消息写入、目标提交、物化视图刷新和客户可见状态分别验收，不能仅凭源 Offset 前进宣布业务完成。
**验收：** 下游索引尚未刷新时用户不会收到错误的“同步完成”状态。

**核验合同与来源：** [cdc-R07](#cdc-R07)；本条对应的失败输入见下文验证矩阵。

### §43 历史回放的范围、批准与版本
**机制：** 受权重放需明确源位点/时间区间、数据版本、目标隔离与是否替换/覆盖原结果；不得将生产全历史回放视作无害只读。
**验收：** 误指定头尾位点、跨租户批量重播被阻断并保留授权证据。

**核验合同与来源：** [cdc-R08](#cdc-R08)；本条对应的失败输入见下文验证矩阵。

### §44 补数与在线流交叠的冲突
**机制：** Backfill 与实时 CDC 同时运行时需分离范围并验证合并版本顺序；补数完成不能自动将进度推进到实时最新。
**验收：** 补数覆盖最新订单状态和重复派生行能被检测和纠正。

### §45 去重保留期与无界历史
**机制：** 事件 ID、LSN 组合或业务版本去重所需状态保留期按源重放能力及法律保留制定，不能无限缓存原文或仅靠短 TTL。
**验收：** 超过去重期限的合法修复回放按审批重新重建，而不是不可知重复。

### §46 Checkpoint/Savepoint 升级兼容
**机制：** 算子状态 Schema、序列化格式、连接器版本与 Checkpoint/Savepoint 恢复能力独立验收；升级失败不能通过重置游标静默跳过。
**验收：** 版本升级+并行度变更后输入进度、状态与目标写入保持连续。

### §47 CDC 可观测性与缺口证明
**机制：** 源端提交到捕获、Broker 到达、消费、物化、业务可见的各级延迟分别度量；低 Lag 不代表源权限或历史完整。
**验收：** 空转消费、日志断档和故障切主能被区分并触发正确恢复。

### §48 L5/L6 验证与真实权限边界
**机制：** 按实际选定引擎/连接器/数据流版本执行隔离数据库和消息系统的故障测试；真实源与目标、资源费用、敏感数据和客户权益仍经 L6 独立授权。
**验收：** 静态样例、沙箱流水线、生产同步及客户业务验收分别记录，不用一项覆盖其他层。

## 五、审批、真正实施与 L5/L6 验收

1. 本版为 **48 项独立机制、60 项静态失败输入**；每项机制至少被直接失效场景覆盖，末两组提供跨源、跨消息系统、流时间和目标业务组合检查。

3. L5 必须记录实际数据库、日志保留、源连接器、消息系统、流框架、目标 Sink 的准确版本及所用语义；L6 才能基于真实租户、项目权限和生产成本决定故障注入、数据回放、客户结果与批准。静态覆盖和 CI 成功均不代表完成真实环境的 60 项实测。
