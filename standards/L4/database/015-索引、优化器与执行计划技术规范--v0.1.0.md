# L4 索引、优化器与执行计划技术规范

**文档ID：** STD-L4-DATABASE-015　**版本：** 0.1.0　**状态：** adopted　**生效日期：** 2026-10-30

## 一、适用范围与相邻规范责任

本专项为 L4「数据库与数据工程」第 04 项具体技术专题。它适用于确实选择关系数据库、嵌入式 SQL、分析引擎和相应索引/优化器的项目，目标是控制**索引访问方法、统计估计、计划选择、查询执行测量、读写代价和回归风险**。按项目实际技术和负载选择条款；不强制上线 PostgreSQL、MySQL、SQLite、SQL Server、DuckDB 或任何单独数据库优化服务。

相应 L4 数据库通用基线、[数据模型与 Schema](013-数据模型、键与-Schema-兼容技术规范--v0.1.0.md)、[SQL 方言与查询](002-SQL-方言、查询语义与数据访问技术规范--v0.1.0.md)、[事务隔离与锁](004-事务、隔离、MVCC-与锁竞争技术规范--v0.1.0.md)分别负责数据权威与生命周期、键约束、表达式语义、锁/MVCC；本专项仅补充**物理查询访问路径及其可复现效能与安全验证**。WAL/崩溃恢复、分区分片、复制高可用、DDL/迁移及备份/PITR由[领域目录](README.md)中的相应独立规范承担。L5 负责具体数据库/SDK/引擎版本，L6 负责真实数据权利、典型工作负载、成本阈值、执行与业务验收。

## 三、48 项独立技术机制与可验证条件

### §01 适用查询及存储工作负载
**机制：** 仅为实际存在的查询入口、数据集合、变更频率和延迟预算选择必要索引与计划验证；不能为遵守规范无条件增加索引、缓存、数据库集群或性能监控外部服务。

**验收：** 每个候选索引均可关联真实查询、合法数据对象、实际数据规模与读写成本。

**核验合同与来源：** [index-R01](#index-R01)；本条对应的失败输入见下文验证矩阵。

### §02 业务语义与性能决策分层
**机制：** SQL 查询专项负责正确结果、分页和权限，事务隔离专项负责锁/MVCC；本专题只治理物理索引、访问路径、统计估计、计划与资源取舍，任何优化不得改变业务键、数据权利或正确返回集合。

**验收：** 对比优化前后不只检查耗时，还对照行/字段、排序、权限与业务最终结果。

**核验合同与来源：** [index-R01](#index-R01)；本条对应的失败输入见下文验证矩阵。

### §03 索引选择与写读权衡
**机制：** B-tree、Hash、GIN、GiST、SP-GiST、BRIN、Zonemap 与 ART 属不同引擎/访问方法，按数据类型、谓词、更新率、大小及查询分布评估，禁止把索引存在等于优化器必用。

**验收：** 用所选引擎计划和真实读写负载证明访问方法价值，保留未选原因。

**核验合同与来源：** [index-R01](#index-R01)；本条对应的失败输入见下文验证矩阵。

### §04 聚簇主键与二级索引回表
**机制：** MySQL InnoDB 主键与二级索引的行定位关系、PostgreSQL heap/index 以及 SQL Server 聚集/非聚集架构不同；错误主键宽度和重复索引会增加存储与写放大。

**验收：** 大行、宽键、二级查找和 INSERT/UPDATE 成本按真实数据验证。

**核验合同与来源：** [index-R01](#index-R01)；本条对应的失败输入见下文验证矩阵。

### §05 复合索引列序与匹配范围
**机制：** 多列 B-tree 一般优先利用前导列等值和适用范围；不能仅按 WHERE 条件书写顺序判断索引列序，PG 18 的 skip scan/不同访问方法及 MySQL/SQLite 规则按版本检查。

**验收：** 等值/范围/排序混合查询通过真实计划及扫描行数复核列序选择。

**核验合同与来源：** [index-R01](#index-R01)；本条对应的失败输入见下文验证矩阵。

### §06 排序、过滤与索引序的协同
**机制：** 索引列方向、NULL 位置、Collation、等值前缀和排序需求决定是否省去 Sort，跨数据库默认方向不同；有索引不能保证无 ORDER BY 的输出顺序。

**验收：** 同排序业务键下结果正确，实际计划标明 Sort 是否被避免及成本。

**核验合同与来源：** [index-R01](#index-R01)；本条对应的失败输入见下文验证矩阵。

### §07 部分/过滤索引的适用谓词
**机制：** PG Partial Index、SQL Server Filtered Index 等仅覆盖特定子集，谓词蕴涵和 Planner 的参数未知值/泛化计划会影响选用，不依赖任意动态 WHERE 自动命中。

**验收：** 查询可证明满足过滤条件时才使用相应索引，不漏未覆盖的合法行。

**核验合同与来源：** [index-R02](#index-R02)；本条对应的失败输入见下文验证矩阵。

### §08 表达式、生成列与函数索引
**机制：** 表达式索引、生成列索引依函数确定性、数据类型、Collation 和 SQL 表达式等价规则；未核对数据库版本时不能声明随意函数均可加索引。

**验收：** 查询表达式改写、区域变化和函数版本变动后可复核相同合法结果。

**核验合同与来源：** [index-R02](#index-R02)；本条对应的失败输入见下文验证矩阵。

### §09 覆盖索引与 INCLUDE 列
**机制：** Index-only/Covering 的支持依引擎及投影列，PostgreSQL 需要可见性映射足够有利并可能 Heap Fetch；MySQL covering read 与 ICP、PG INCLUDE、SQL Server included columns不应混为同一结构。

**验收：** 真实读写数据分布下计划中的回表/heap fetch 与执行耗时有测量。

**核验合同与来源：** [index-R02](#index-R02)；本条对应的失败输入见下文验证矩阵。

### §10 主键唯一、外键辅助与自动索引
**机制：** 唯一/PK 索引首先承担数据正确性和引用约束；MySQL invisible 索引仍维护且 UNIQUE 仍生效，SQLite 自动索引/必要 PK 及 SQL Server 约束关联有各自行为。

**验收：** 索引被隐藏或优化策略变化时约束不破坏，实际冗余索引有证据后才处理。

**核验合同与来源：** [index-R02](#index-R02)；本条对应的失败输入见下文验证矩阵。

### §11 全文、空间、JSON 与专用访问方法
**机制：** 全文检索、数组/JSON、地理/空间、向量等依真实项目需求及引擎专用 Operator Class/Extension/Index Method；不将普通 B-tree 或文本 LIKE 的速度外推为专用索引通用性能。

**验收：** 每种索引只在所支持的操作符、距离/相似度与安全语义内进行验证。

### §12 BRIN、Zonemap 与数据聚集顺序
**机制：** 范围摘要类索引适用于可跳过大量块的数据分布，字段和物理行顺序相关性改变会影响效果；DuckDB Zonemap 及 PG BRIN 的创建/维护机制不同。

**验收：** 有序和打乱顺序样本的扫描块/行数及真实时间分别核对。

### §13 Bitmap/多索引组合与回查
**机制：** PG BitmapIndexScan/BitmapHeapScan、MySQL Index Merge、SQLite OR 优化等依各产品，可丢失原排序并产生重检；不能以两个单列索引必然等于高效复合索引。

**验收：** 多谓词选择性、Bitmap Recheck/回表和 SORT 成本有可复验结果。

**核验合同与来源：** [index-R02](#index-R02)；本条对应的失败输入见下文验证矩阵。

### §14 索引谓词及 NULL、大小写行为
**机制：** NULL 位置、IS NULL、OR、NOT、前缀匹配、隐式类型转换与 Collation 会影响索引选择；表达式包装、非索引前导通配及目标数据库差异不能擅自假定可索引。

**验收：** 无匹配、NULL、Unicode、非法类型及旧格式数据都保持查询正确且资源有界。

**核验合同与来源：** [index-R02](#index-R02)；本条对应的失败输入见下文验证矩阵。

### §15 统计基数、选择率及数据分布
**机制：** 优化器使用估计行数、宽度、频率和数据相关性决定路径；均匀合成样本不代表真实长尾、热点或多租户不均分布；记录采样来源和更新时间。

**验收：** 估计与实际行数按算子比较，显著误差能定位数据分布与统计来源。

**核验合同与来源：** [index-R03](#index-R03)；本条对应的失败输入见下文验证矩阵。

### §16 PostgreSQL 多列扩展统计
**机制：** PG CREATE STATISTICS 的 dependencies、ndistinct、MCV/表达式统计按查询类型和引擎支持判断，并非任意 Join 估计均得到修正；创建对象后需收集统计。

**验收：** 列相关/反相关样本中估算偏差改善或明确记录未改善。

### §17 MySQL Histogram 与统计限制

**验收：** 真实生产样本替代的统计来源、安全与计划估计能在目标实例上回读。

### §18 SQLite ANALYZE 与 sqlite_stat 来源
**机制：** SQLite Query Planner 使用 sqlite_stat1（条件性 stat4）等统计，运行 ANALYZE/PRAGMA optimize 的语义随版本与构建参数变化；不要未经许可修改生产统计以模拟更好计划。

**验收：** stats 更新前后选择访问路径的变化及数据结果可隔离复验。

### §19 优化器成本单位与计划估计
**机制：** PostgreSQL cost 是任意单位、MySQL/SQL Server 的估计模型各不同，不能用不同引擎 cost 数值直接排名；估计执行计划不证明 I/O 或真实业务延迟。

**验收：** 每份计划保存真实数据库版本、统计状态、参数和估计/实测的独立结论。

### §20 EXPLAIN 与 ANALYZE 的执行边界
**机制：** PG EXPLAIN ANALYZE、MySQL EXPLAIN ANALYZE、DuckDB EXPLAIN ANALYZE 可能真实执行 SQL；带副作用的语句即使包裹数据库事务回滚，也无法保证外部发送/非事务性副作用回滚。

**验收：** 有执行风险的计划分析只在获准隔离环境运行，绝不由静态审查授权生产写入。

**核验合同与来源：** [index-R04](#index-R04)；本条对应的失败输入见下文验证矩阵。

### §21 PG EXPLAIN BUFFERS/WAL/TIMING/MEMORY
**机制：** PostgreSQL 18 支持按选项观测共享/临时块、WAL、部分内存等，计时探针本身有开销，缓存命中不等于零磁盘风险；不能只从 plan cost 推断运行耗时。

**验收：** 冷热缓存、I/O、临时文件、运行开销有必要的实际样本和解释。

**核验合同与来源：** [index-R04](#index-R04)；本条对应的失败输入见下文验证矩阵。

### §22 MySQL EXPLAIN ANALYZE TREE 执行算子
**机制：** MySQL 8.4 的 EXPLAIN ANALYZE 使用 TREE 显示 iterator 实际/估计行数、耗时与 loops；不是所有计划格式都等价，普通 EXPLAIN 的 rows 属估计。

**验收：** 涉及 Join 多循环的算子总工作量按 loops 而不是单一行数字段评价。

**核验合同与来源：** [index-R04](#index-R04)；本条对应的失败输入见下文验证矩阵。

### §23 SQLite EXPLAIN QUERY PLAN 输出稳定性
**机制：** SQLite EQP 的 SCAN/SEARCH、USING COVERING INDEX 适用于人工诊断，其输出布局可能随版本改变，不能把解释文本当应用 API 的持久格式/约束。 可对规范化后的计划特征作有版本范围的诊断断言，但返回行集合和排序须独立校验；不因 SQLite 合法升级的 EQP 文本变化宣布数据错误。

**验收：** 升级 SQLite 后不因诊断字符串变化错误判断业务测试失败或兼容。

**核验合同与来源：** [index-R04](#index-R04)；本条对应的失败输入见下文验证矩阵。

### §24 SQL Server 估计/实际计划与 Query Store
**机制：** SQL Server 实际计划、估计计划和 Query Store 的计划历史/运行统计具有不同数据来源、选项及保留条件，不能将 Query Store 数据缺失解释为没有执行或没有业务对象。

**验收：** 实际 Query Store 数据库选项与对应版本的运行证据能够明确区分计划、时延和客户完成。

**核验合同与来源：** [index-R04](#index-R04)；本条对应的失败输入见下文验证矩阵。

### §25 扫描路径与访问基数差异
**机制：** Seq Scan/Index Scan/Index-Only Scan/Bitmap/Columnar Scan 等的实际性能随选择率、缓存与数据量改变；全表扫描不自动等于错误，也不以一定要命中某个索引作为所有 SQL 的质量门禁。

**验收：** 对小表、大表、选择率高低等样本测量访问路径及结果而非单纯检查 Index Scan 字样。

**核验合同与来源：** [index-R05](#index-R05)；本条对应的失败输入见下文验证矩阵。

## 五、审批、技术版本与项目验收

1. 本版包含 **48 项独立技术机制和 60 项静态失效场景**，10 组案例关联完整 §01—§48；L5/L6 数据库操作、数据权利、外部业务与客户验收不自动生效。
L6 选择真实租户、数据规模、查询/写入预算、授权、执行环境和真实业务验收。
3. 此处的技术机制、EXPLAIN/执行计划、静态检查、CI 及场景数量**不是已通过的生产性能或客户业务测试**，不授权任何生产 SQL/索引 DDL、真实财务操作、敏感数据导出或额外付费资源。
4. 数据模型/Schema、SQL 查询语义、事务/MVCC、物理存储/WAL、迁移回填、业务工作流和外部履约仍按各自 L4/L5/L6 权威执行，本专项只规定索引和优化器的选择、诊断与性能/正确性验证。
