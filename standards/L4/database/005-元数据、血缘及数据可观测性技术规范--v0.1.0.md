# L4 元数据、血缘及数据可观测性技术规范

**文档ID：** STD-L4-DATABASE-005　**版本：** 0.1.0　**状态：** adopted　**生效日期：** 2026-10-30

## 一、适用范围与相邻规范职责

本规范是 L4「数据库与数据工程」领域第 13 项独立技术专题。只对实际需要数据集目录、表/字段依赖、处理追溯、数据质量趋势或管道元信息可观测性的项目激活对应规则；小型或单次数据任务可以沿用已有项目记录，不强制新建 DataHub、OpenMetadata、OpenLineage 平台或额外云资源。

本专题聚焦 **Catalog 资产与来源身份、PROV 证据关系、Job/Run/Dataset 事件、列级血缘准确性、元数据状态收敛、采集覆盖、数据质量观测和实际影响分析**。相应数据库领域第 1—12 项分别负责数据模型、SQL、事务与 WAL、Schema/存储、ETL、CDC、列式湖仓的真实执行语义；后端可观测性专项负责通用 Trace/Metric/Log 运行协议；本文仅规定元数据和血缘特有的正确性与证据边界。第 14 项负责更完整的数据安全、保留和导出执行。L5 确定实际 SDK/Catalog/Reader 和采集方式，L6 决定真实数据权利、项目业务指标和客户验收。

## 三、48 项独立元数据和血缘技术机制

下列断言以合法的具体 L5/L6 业务和数据来源为前提。机制覆盖、事件采集、Catalog 完整和客户业务正确分别验收，不可互相代替。

### 机制组 1：元数据资产与目录身份

### §01 领域启用与平台成本
**机制：** 按实际存在的目录、血缘和数据审计需求决定元数据范围；小型应用不默认部署独立 Catalog 或订阅治理 SaaS。

**验收：** 可用已有版本记录核实必要血缘与来源，不增加无关成本

**核验合同与来源：** [metadata-R01](#metadata-R01)；本条对应的失败输入见下文验证矩阵。

### §02 Dataset 身份及命名空间
**机制：** 用数据源、环境、命名空间和逻辑名称区分资产；同名不同库或租户不得合并，实际采用 OpenLineage 时按其命名规范构造。

**验收：** 资产能在多个环境和租户下保持唯一可追踪身份

**核验合同与来源：** [metadata-R01](#metadata-R01)；本条对应的失败输入见下文验证矩阵。

### §03 Catalog/对象地址分离
**机制：** Catalog 元信息、逻辑 Dataset、Distribution、对象存储位置和真实数据访问权分别识别；底层 URL 可读并非事务版本或发布授权。

**验收：** 按权威 Catalog 和实际数据权利确认可见版本

**核验合同与来源：** [metadata-R01](#metadata-R01)；本条对应的失败输入见下文验证矩阵。

### §04 负责人和元数据声明权限
**机制：** 区分数据使用权利人、业务规则批准人、Catalog 维护者、Agent 采集身份及下游接收者；采集器不得自行确定业务 Owner。

**验收：** 责任归属的记录与真实授权相符

**核验合同与来源：** [metadata-R01](#metadata-R01)；本条对应的失败输入见下文验证矩阵。

### §05 字段身份与 Schema 版本
**机制：** 列名、稳定字段 ID、嵌套路径及实际 Schema/数据集版本关联；Rename、Drop、Recreate 不应依据相同列名继承旧身份。

**验收：** 旧新字段关系可按真实 Schema 演化恢复

**核验合同与来源：** [metadata-R01](#metadata-R01)；本条对应的失败输入见下文验证矩阵。

### §06 DCAT Dataset 与 Distribution
**机制：** 采用跨目录互操作时区分 Dataset、Series、Version、Distribution 与数据访问服务；只公开描述不得直接开放底层内容。

**验收：** 发现元数据与合法获取数据的权限分别核对

**核验合同与来源：** [metadata-R01](#metadata-R01)；本条对应的失败输入见下文验证矩阵。

### 机制组 2：PROV 来源语义与证据界限

### §07 Entity/Activity/Agent 三类主体
**机制：** 使用 PROV 模型时区分产出实体、变换活动与参与 Agent，处理主体不等于原数据授权人。

**验收：** 每个证据含真实实体/活动/参与者身份

**核验合同与来源：** [metadata-R02](#metadata-R02)；本条对应的失败输入见下文验证矩阵。

### §08 Used/Generated/Derived 关系
**机制：** used、wasGeneratedBy、wasDerivedFrom 的边根据真实输入、输出与衍生操作记录；仅访问某表不能证明所有输出字段源自它。

**验收：** 值衍生与控制访问的证据分开

**核验合同与来源：** [metadata-R02](#metadata-R02)；本条对应的失败输入见下文验证矩阵。

### §09 版本化来源与处理定义
**机制：** 保留输入 Dataset Snapshot/分区、转换定义版本、运行标识及实际观察时间，不以今天的 SQL 代替历史数据的真实计算。

**验收：** 结果可追溯当次的源码版本和源状态

**核验合同与来源：** [metadata-R02](#metadata-R02)；本条对应的失败输入见下文验证矩阵。

### §10 静态声明与运行观测分离
**机制：** Manifest 的声明依赖、扫描推断、人工登记和运行 Event 归属于不同来源类型；没有执行不应标记为生产已生效。

**验收：** 事实具有静态/推断/人工/运行证据类别

**核验合同与来源：** [metadata-R02](#metadata-R02)；本条对应的失败输入见下文验证矩阵。

### §11 未知、缺失与确定无依赖
**机制：** 未启用采集器、失去权限、黑盒 UDF、缺失事件与确实不存在上游分别表达，不把空图自动视为已证明没有影响。

**验收：** 缺口及真正无依赖有不同状态与恢复步骤

**核验合同与来源：** [metadata-R02](#metadata-R02)；本条对应的失败输入见下文验证矩阵。

### §12 SHACL 约束的选用条件
**机制：** 仅 RDF 元数据图需要时用 SHACL 2017 Shape/Validation Report；其他图数据库使用实际 Schema 约束，不把 SHACL 1.2 Working Draft 当已正式标准。

**验收：** 约束失效会给出可定位验证报告，非 RDF 系统不承担新栈负担

**核验合同与来源：** [metadata-R02](#metadata-R02)；本条对应的失败输入见下文验证矩阵。

### 机制组 3：OpenLineage 运行事件与 Facet

### §13 Job、Run、Dataset 实体区分
**机制：** Job 定义、Run 执行和 Dataset 资产各有独立身份；同一作业多次运行不得复用 RunId 作为唯一历史记录。

**验收：** 同 Job 各 Run 的输入输出能逐次还原

**核验合同与来源：** [metadata-R03](#metadata-R03)；本条对应的失败输入见下文验证矩阵。

### §14 重试与 Run Attempt 的归属
**机制：** 调度重试、补跑和重新触发明确记录原始 Run/Attempt 与合法版本，不能按事件到达顺序随意重置运行身份。

**验收：** 运行历史、重试和输出资产版本可独立追踪

**核验合同与来源：** [metadata-R03](#metadata-R03)；本条对应的失败输入见下文验证矩阵。

### §15 Run 终态与观测缺口
**机制：** START、COMPLETE、FAIL、ABORT 等按协议记录；只有 START 不等于成功，未收到终态需区分失联和真正持续运行。

**验收：** 超时、未观察、失败及成功可准确区分

**核验合同与来源：** [metadata-R03](#metadata-R03)；本条对应的失败输入见下文验证矩阵。

### §16 Parent/Root Run 的可信来源
**机制：** 跨 Scheduler/SQL/Spark/Beam 的 ParentRunFacet 显式关联父/根 Run；子 Run 转发的父 Facet 不是父事件的权威替代。

**验收：** 真实父 Run 证据和转发信息一致

**核验合同与来源：** [metadata-R03](#metadata-R03)；本条对应的失败输入见下文验证矩阵。

### §17 Dataset 与 Input/Output Facet 分离
**机制：** Schema/Version 等 Dataset Facet 与单次读写分区及 Input/Output Statistics 的运行范围分开；不以当次局部统计覆盖全量数据集。

**验收：** 静态资产描述和单次观测数值各有范围

**核验合同与来源：** [metadata-R03](#metadata-R03)；本条对应的失败输入见下文验证矩阵。

### §18 Facet Producer/Schema 版本
**机制：** 自定义或新旧 Facet 记录 producer、schemaURL 和所选 OpenLineage 版本；未知扩展不能导致受支持的核心事件被全部丢弃。

**验收：** 可隔离未知 Facet 并继续解析合法核心字段

**核验合同与来源：** [metadata-R03](#metadata-R03)；本条对应的失败输入见下文验证矩阵。

### 机制组 4：列级血缘及真实依赖

### §19 源列/目标列身份映射
**机制：** 表级边不足以证明字段级来源。输出列记录其真实 Dataset/字段身份集合、版本及转换表达式；常量列可以没有源列，多输入表达式可以依赖多个真实字段。过滤/控制依赖与值依赖分开，不能强迫每列匹配一个同名源列，也不能把解析未知写成已确认无来源。

**验收：** 用常量输出、两列求和、仅过滤列、同名不同租户列和黑盒 UDF 分别检查 lineage facet：0/多输入是合法邻例；每个声称的来源可回到准确版本，未解析部分标 unknown 并保留补证路径。

**核验合同与来源：** [metadata-R04](#metadata-R04)；本条对应的失败输入见下文验证矩阵。

### §20 值依赖与筛选控制依赖
**机制：** 直接投影、算术、聚合、Join 和 WHERE/CASE 影响不是同一种列值来源，必要时区分取值转换和结果可见性依赖。

**验收：** 控制字段和被变换数值字段语义分开

**核验合同与来源：** [metadata-R04](#metadata-R04)；本条对应的失败输入见下文验证矩阵。

### §21 动态 SQL 和 SELECT * 的版本
**机制：** 解析视图、CTE、SELECT *、列别名须以实际执行期 Schema 展开；未知 UDF/动态输入标记不完整，不能凭旧 Schema 补边。

**验收：** 实际 Schema 版本或无法解析范围可核查

**核验合同与来源：** [metadata-R04](#metadata-R04)；本条对应的失败输入见下文验证矩阵。

### §22 一个 Job 多输出的非笛卡尔依赖
**机制：** 一项作业多输入/多输出时用 Job/Dataset Lineage Facet 明确每个目标真正的来源，不能简单计算所有 inputs×outputs。

**验收：** 不存在的跨表边不会出现在影响分析中

**核验合同与来源：** [metadata-R04](#metadata-R04)；本条对应的失败输入见下文验证矩阵。

### §23 UDF/API/模型黑盒未知粒度
**机制：** 无权查看 SQL 函数、远程 API 或模型内部时只描述有证据的输入输出与未知字段，不凭字段相似度伪造内容级依赖。

**验收：** 未知依赖有证据状态且可由授权人员补充

**核验合同与来源：** [metadata-R04](#metadata-R04)；本条对应的失败输入见下文验证矩阵。

### §24 Fuzzy/Strict 与人工补录证据
**机制：** DataHub 模糊/严格列匹配及 OpenMetadata 手工补录均属各自采集或推断，必须保留来源、置信及修改责任，不能当作运行中观察到的事实。

**验收：** 手工、推断与真实运行观测分别可审计

**核验合同与来源：** [metadata-R04](#metadata-R04)；本条对应的失败输入见下文验证矩阵。

### 机制组 5：元数据采集和图状态

### §25 dbt Manifest/Catalog/Run Results 不同
**机制：** Manifest 属声明/解析依赖，Catalog 依实际仓库查询获取列信息，Run Results 只记已执行节点；读取实际 metadata.dbt_version/dbt_schema_version、invocation_id 及 resource unique_id 对应；网页 ?version 参数不证明返回了固定旧版本说明，以实际产物 schema 和工具版本为准，不因缺席推断删除。

**验收：** 声明、采集和执行三个不同层次可核对

**核验合同与来源：** [metadata-R05](#metadata-R05)；本条对应的失败输入见下文验证矩阵。

### §26 元数据事件幂等与重复
**机制：** 采集网络重试及重复投递按来源事件身份、版本和 Facet 去重，同一测试失败不得累加为多次真实运行。

**验收：** 重复消费后边与结果仍保持一致

**核验合同与来源：** [metadata-R05](#metadata-R05)；本条对应的失败输入见下文验证矩阵。

### §27 事件乱序及当前有效版本
**机制：** 来源事件时间、采集时间、数据集版本分开，迟到旧 Schema/Event 可保留历史但不能覆盖较新已确认状态。

**验收：** 当前状态和历史时间线保持一致

**核验合同与来源：** [metadata-R05](#metadata-R05)；本条对应的失败输入见下文验证矩阵。

### §28 Rename/Drop/Overwrite 生命周期
**机制：** 元数据 CREATE、RENAME、DROP、OVERWRITE 属不同生命周期；表改名不自动等于删除重建，物理删除也不能仅由 Facet 推断。

**验收：** 真实生命周期与新旧身份关系一致

**核验合同与来源：** [metadata-R05](#metadata-R05)；本条对应的失败输入见下文验证矩阵。

### §29 图环路与有界影响遍历

**验收：** 按预期集合插入一个漏采对象、一个已删除对象、一个合法空集合：分别出现缺口、按版本退出及 N/A；恢复 Collector 后对账事件/资产集合，不以队列清空替代全量覆盖。

| Custom Facet 版本不兼容导致全部 Run Event 被丢弃，误判生产未执行 | §18、§26、§38 | 核心事件解析降级与真实 Run 状态核对 |
| Prometheus RunId 高基数且 SQL Facet 带秘密，造成成本和凭证风险 | §39、§40、§46 | 标签预算与敏感内容最小化 |
| 质量 Metrics 捕获时间更新而源 Snapshot 未变，误报业务数据新鲜 | §31、§33、§42 | 区分数据最后更新与采集时间 |
| Snowflake 无 Enterprise 许可，团队编造 Access History 的列级血缘审计 | §10、§11、§23、§43 | 许可覆盖与未知来源如实记录 |
| 旧图手工误边使合法删除的数据可通过历史 Facet 继续对外公开 | §24、§43、§46、§47 | 纠错、历史权限、删除及传播条件整体验收 |

## 五、版本批准、采集授权与 L5/L6 真实验收

1. 本规范包含 48 项独立机制、60 项静态失败场景。前八组对 §01—§48 直接覆盖，后两组给出 12 项跨域组合故障。
静态覆盖不能代替实际 60 次生产或集成测试。
3. L5 根据实际采用产品和版本核查 Catalog、Collector、SDK、Facet、权限、内存与费用；L6 独立确认数据主体授权、真实业务数据、客户报表与部署验收。数据血缘存在不代表数据已获授权或客户任务完成。

### metadata-R01
