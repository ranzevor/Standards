# L4 物理存储、WAL 与崩溃一致性技术规范

**文档ID：** STD-L4-DATABASE-014　**版本：** 0.1.0　**状态：** adopted　**生效日期：** 2026-10-30

## 一、作用域、职责边界与必要场景

本规范是 L4「数据库与数据工程」第 05 项具体技术专题，规定真实选用的数据库内核/本地存储在**页/文件与日志持久化顺序、事务确认、检查点、崩溃一致性及受控恢复**方面需要核对的工程契约。不要求所有项目安装特定数据库、额外独立服务器、冗余存储或实验性日志系统。SQLite 单文件应用、关系数据库及嵌入式 KV/LSM 系统按实际类型激活相应条款。

本专项**不重编数据库引擎算法**。相应数据库领域基线、数据模型/Schema、SQL 查询、事务隔离/MVCC、索引/执行计划及后端事务/消息/工作流保留其数据权利、语义、并发与业务副作用职责。数据库领域**复制高可用、分区分片、DDL 迁移、备份/PITR**各自有独立专题；本专项仅验证单引擎物理数据一致性、同步及本地 Crash Recovery。L5 选定数据库版本、驱动、文件系统与设备；L6 确定真实 RPO/RTO、权限、介质、环境与业务验收。

## 三、48 项独立物理持久化技术机制与验收

### §01 权威数据与存储恢复目标
**机制：** 对具体数据库、实例/文件组和业务事实定义权威持久状态、允许丢失窗口、故障等级及实际恢复后不变量，不把单纯服务重启或副本响应视为已恢复。

**验收：** 在获准隔离环境中能列出故障前确认事务、待确认事务、恢复后的数据集及未履约业务。

**核验合同与来源：** [wal-R01](#wal-R01)；本条对应的失败输入见下文验证矩阵。

### §02 WAL、Redo、Undo 与业务事件区分
**机制：** WAL/Redo、Undo、复制日志、CDC/消息事件、审计账本的职责与确认点不同；单有某一种日志并不自动保证另外的外部系统一致。

**验收：** 每种日志明确生产者、权威位置、持久等级、回放主体和保留依赖。

**核验合同与来源：** [wal-R01](#wal-R01)；本条对应的失败输入见下文验证矩阵。

### §03 先写日志后落盘数据的依赖顺序
**机制：** 采用 WAL 的引擎必须按实际实现让必要的 Redo 记录达到规定持久状态，才能将对应脏数据页安全落盘；不得将日志写入缓冲区等同存储介质已确认。

**验收：** 注入乱序写入或故障时恢复不出现缺少必要 Redo 的已落盘数据页。

**核验合同与来源：** [wal-R01](#wal-R01)；本条对应的失败输入见下文验证矩阵。

### §04 事务成功与同步落盘确认
**机制：** 区分应用返回、COMMIT 逻辑完成、WAL 已写入、WAL 已同步、数据页落盘与外部签收；选定数据库的持久选项决定可向用户承诺的成功语义。

**验收：** 在各已批准模式下区分已持久、可丢失与未知提交，不凭 HTTP 200 直接承诺灾后不丢。

**核验合同与来源：** [wal-R01](#wal-R01)；本条对应的失败输入见下文验证矩阵。

### §05 进程崩溃、内核重启与断电等级
**机制：** process crash、OS crash、容器消失、宿主机/存储掉电、介质损毁各有不同缓存和持久风险；容器或 VM 重启不等价于验证电源故障。

**验收：** 测试报告将故障注入层次与实际存储持久条件绑定，不越级声称通过。

**核验合同与来源：** [wal-R01](#wal-R01)；本条对应的失败输入见下文验证矩阵。

### §06 存储控制器缓存及写入屏障
**机制：** 操作系统 page cache、存储控制器写回缓存、设备掉电保护、flush/barrier 和虚拟化存储可能改变同步边界；不能仅凭一次成功 fsync 推断所有介质可靠。

**验收：** 按实际设备/文件系统/云存储契约记录 flush 能力及异常恢复条件。

**核验合同与来源：** [wal-R01](#wal-R01)；本条对应的失败输入见下文验证矩阵。

### §07 脏页缓冲、刷盘与提交时序
**机制：** 数据页在 Buffer Pool/Shared Buffer 里修改、被标脏和后台刷出，不等于该事务已获得持久确认；Checkpoint 与写缓冲策略按实际引擎配置核对。

**验收：** 中途强停、后台刷页与提交交错后恢复数据满足已承诺不变量。

**核验合同与来源：** [wal-R02](#wal-R02)；本条对应的失败输入见下文验证矩阵。

### §08 LSN、顺序号与日志边界
**机制：** PostgreSQL LSN、MySQL InnoDB LSN、SQL Server LSN 与 RocksDB sequence 等不同，不能跨引擎混用，也不能把同一编号当客户业务顺序或授权证明。

**验收：** 对于实际故障有可复核的日志位置/检查点起点与恢复终点对应关系。

**核验合同与来源：** [wal-R02](#wal-R02)；本条对应的失败输入见下文验证矩阵。

### §09 Checkpoint 及 Redo 起点
**机制：** Checkpoint 是按具体引擎记录安全回放边界或推进数据页同步的机制，并非为所有后续事务完成永久备份；错误截断前置 WAL 将破坏恢复链。

**验收：** 能回读选择的检查点和恢复所需最早日志，断点后不缺失依赖。

**核验合同与来源：** [wal-R02](#wal-R02)；本条对应的失败输入见下文验证矩阵。

### §10 日志分段、循环复用和空间依赖
**机制：** WAL/Redo 的分段、归档、重用与删除受 Checkpoint、备份、复制和故障恢复依赖控制；PG max_wal_size 不是所有情况下的硬上限。

**验收：** 突增写量或归档异常不会在未预警下无限占满存储或抢先删除必要日志。

**核验合同与来源：** [wal-R02](#wal-R02)；本条对应的失败输入见下文验证矩阵。

### §11 文件同步与目录元数据
**机制：** 文件内容的 fsync/fdatasync、目录项的 durable rename/create、设备 Flush 与故障窗口必须依据操作系统和文件系统实际承诺核对；不可将 rename 原子性等于必然断电持久。

**验收：** 保存的文件、目录和索引指针在受支持介质/故障模式下具有效的落盘确认。

**核验合同与来源：** [wal-R02](#wal-R02)；本条对应的失败输入见下文验证矩阵。

### §12 页撕裂与 Partial Write
**机制：** 数据库页大小可能超过实际原子写入单元，断电中途可造成旧新扇区混合；PG full_page_writes 与 MySQL doublewrite 等方案不能直接相互替代。

**验收：** 含 Torn Page 的受控故障样本能被发现、正确恢复或明确止损。

**核验合同与来源：** [wal-R02](#wal-R02)；本条对应的失败输入见下文验证矩阵。

### §13 数据页/日志校验和覆盖
**机制：** PostgreSQL 数据页 Checksums、WAL CRC、SQL Server Page Checksum 等覆盖对象不同，校验成功不是内容语义正确或已有可恢复备份；不能把 CRC 说成纠错能力。

**验收：** 静态位翻转/截断时错误可定位并保留原始证据，不静默宣布业务通过。

**核验合同与来源：** [wal-R02](#wal-R02)；本条对应的失败输入见下文验证矩阵。

### §14 写入错误与不可信缓存状态
**机制：** 磁盘写回失败、EIO、ENOSPC、部分同步与内核缓存脏页丢失可能使同一文件状态不可信，盲目重试成功不能证明缺失数据已补回。

**验收：** I/O 错误明确切换只读/停机或修复，恢复来源和失败范围能追踪。

**核验合同与来源：** [wal-R02](#wal-R02)；本条对应的失败输入见下文验证矩阵。

### §15 PostgreSQL full_page_writes 边界
**机制：** PG 18 检查点后首次修改页写 Full Page Image 以防 Torn Page，关闭可能引起崩溃后腐败；仅在满足真实受保护文件系统/风险批准时评估例外。

**验收：** FULL PAGE 配置和真实 Checkpoint/故障样本对应，不能以性能提升替代数据完整性。

**核验合同与来源：** [wal-R03](#wal-R03)；本条对应的失败输入见下文验证矩阵。

### §16 PostgreSQL fsync 与同步方法
**机制：** PG 18 fsync、wal_sync_method 与底层持久设备协同；关闭 fsync 可能导致 OS crash 后严重破坏，不能把该选项等同逐事务异步提交。

**验收：** 实际有效配置和存储 Flush 行为有记录，已确认提交按约定故障等级持久。

**核验合同与来源：** [wal-R03](#wal-R03)；本条对应的失败输入见下文验证矩阵。

### §17 PostgreSQL synchronous_commit 的风险窗
**机制：** PG 同步提交和异步提交具有不同成功语义，异步模式可能丢掉近期已返回成功的事务，但正常 WAL 恢复保证数据库内部一致性；支付等外部动作不得依赖未持久事实。

**验收：** 同步与异步模式断点后可列出允许丢失范围和外部副作用补偿路径。

**核验合同与来源：** [wal-R03](#wal-R03)；本条对应的失败输入见下文验证矩阵。

### §18 PostgreSQL Unlogged/临时数据
**机制：** UNLOGGED 表、临时表和部分文件不受和普通持久表相同的 WAL/崩溃承诺约束；不为业务账本或关键审计隐式启用非持久数据。

**验收：** 故障重启后临时/UNLOGGED 状态与实际规范一致，关键业务对象不会依赖其恢复。

**核验合同与来源：** [wal-R03](#wal-R03)；本条对应的失败输入见下文验证矩阵。

### §19 PostgreSQL Checkpoint、WAL 容量和写放大
**机制：** checkpoint_timeout、max_wal_size、full_page_writes 和日志刷新等调参影响刷盘压力、WAL 量和恢复耗时；更频繁 Checkpoint 并非永远更安全或更快。

**验收：** 真实写入峰值与 Checkpoint 时间/Redo 体量可测，容量余量和正确性兼顾。

**核验合同与来源：** [wal-R03](#wal-R03)；本条对应的失败输入见下文验证矩阵。

### §20 PostgreSQL WAL 留存与归档依赖
**机制：** Crash Recovery、物理备份 PITR、WAL archive、复制槽及故障后恢复依赖不同；缺归档导致 WAL 累积，删除日志不构成合法止损方案。

**验收：** 归档或槽积压触发有界处理并保留必需日志及可恢复的业务区间。

**核验合同与来源：** [wal-R03](#wal-R03)；本条对应的失败输入见下文验证矩阵。

### §21 MySQL InnoDB Redo 日志
**机制：** InnoDB Redo 支持脏页崩溃恢复，Redo Log Capacity/Checkpoint LSN 的选择要与写入速度和存储空间匹配，不与 Binary Log/Undo 混为一个承诺。

**验收：** 在隔离 MySQL 8.4 实例上可识别 Redo 依赖、重启后可恢复的已提交事务。

**核验合同与来源：** [wal-R04](#wal-R04)；本条对应的失败输入见下文验证矩阵。

### §22 MySQL innodb_flush_log_at_trx_commit
**机制：** 实际值决定提交时写日志/同步的持久级别；不能在 0/2 等非每事务 Sync 方案下向客户承诺宿主机断电后不丢最近确认事务。

**验收：** 采用设置及宿主故障类型对应允许丢失范围，未确认写入单独记录。

**核验合同与来源：** [wal-R04](#wal-R04)；本条对应的失败输入见下文验证矩阵。

### §23 MySQL Doublewrite 与页完整性
**机制：** Doublewrite Buffer 旨在恢复 Torn Page，而不是复制多台节点或替代 Redo；具体配置、加密/压缩和存储设备支持需按 MySQL 8.4 实现核对。

**验收：** 损坏页对照样本能检测或通过适用 Doublewrite/Redo 机制恢复。

**核验合同与来源：** [wal-R04](#wal-R04)；本条对应的失败输入见下文验证矩阵。

### §24 MySQL Redo 与 Binlog 边界
**机制：** InnoDB Redo 与 MySQL Binary Log 用于不同目的，当开启 Binlog/复制与外部消费时需明确本地事务恢复和 Binlog 持久设置的联合目标，不能由 redo 已写推出下游收到。

**验收：** Redo/Binlog 状态和业务结果独立可核对，断电恢复时没有无解释的已确认副作用。

**核验合同与来源：** [wal-R04](#wal-R04)；本条对应的失败输入见下文验证矩阵。

### §25 MySQL Buffer Pool、Checkpoint 与写放大
**机制：** InnoDB 脏页刷新、Checkpoint Age、Redo Log Capacity、Doublewrite 会影响写延迟/容量，不能为压低 P99 任意牺牲数据持久选项。

**验收：** 峰值写入及刷盘积压时有测量和止损，不超出批准的恢复目标与资源预算。

**核验合同与来源：** [wal-R04](#wal-R04)；本条对应的失败输入见下文验证矩阵。

### §26 MySQL Crash Recovery 与 Undo
**机制：** InnoDB 崩溃重启需依据 Redo、Doublewrite、Undo 等机制恢复与回滚未完成事务；数据库能启动不表示外部通知/交易履约正确。

**验收：** 故障前已确认、未知、未提交三类业务事务在恢复后真实分类并回读。

### §27 MySQL 故障强制恢复模式
**机制：** innodb_force_recovery 等故障应急选项为特定恢复/导出场景，存在严重风险；不能作为常规自动重启或恢复数据正确性的默认开关。

### §28 SQLite WAL、SHM 与主 DB 文件
**机制：** SQLite WAL 模式中主 DB 与尚未 checkpoint 的 -wal 共同承载已提交持久状态，单独复制 .db 可能遗漏事务。-shm 是可重建的 WAL-index/协调状态，不是必须永久归档的独立恢复真相；不得任意删除活跃连接的 sidecar，在线快照采用受支持的 Backup API 或经验证的一致文件组/连接关闭方案。

**验收：** 保持源连接打开并关闭自动 checkpoint，提交后比较仅复制主文件与 Backup API 的恢复结果；前者不能因文件可打开就宣称完整，后者需核对预期键/值和 integrity_check。测试只证明所测 SQLite/文件系统边界，不等于断电耐久试验。

**核验合同与来源：** [wal-R05](#wal-R05)；本条对应的失败输入见下文验证矩阵。

### §29 SQLite synchronous FULL/NORMAL/OFF
**机制：** 同步保证必须联合 journal_mode、synchronous、SQLite 构建/VFS、文件系统及设备记录。WAL 下 FULL 比 NORMAL 多提交同步；NORMAL 在正常进程崩溃后通常保留事务，但掉电/系统崩溃可能丢失近期已确认提交且仍保持一致；OFF 在系统故障时可能损坏。Rollback DELETE journal 下 FULL 也不无条件保证最后提交的断电耐久；EXTRA 额外同步删除日志后的目录，对相应模式耐久有意义，WAL 下 EXTRA 与 FULL 相同。

**验收：** 逐连接读取 PRAGMA journal_mode、synchronous、foreign_keys、compile_options 和实际 sqlite_version，不能以设置语句未报错证明参数生效（未知 PRAGMA 可被忽略）。分别记录进程、系统及电源故障的实际执行范围，未执行掉电不得标为通过。

**核验合同与来源：** [wal-R05](#wal-R05)；本条对应的失败输入见下文验证矩阵。

| 存储日志风暴写满磁盘，DB 返回成功但新数据不可恢复 | §41 | ENOSPC 和恢复容量门禁 |
| 校验/读写 EIO 被统一转成空结果，客户端认为不存在订单 | §42 | 存储损坏与合法零记录明确分开 |

## 五、组织审批、版本与实际项目验证

1. 本规范包含 **48 项独立技术机制和 60 项静态失效场景**；10 组输入对全部 §01—§48 形成直接或组合覆盖，来源版本和静态场景审查保留。项目 L5 实现和 L6 实际持久化、权限、生产故障及客户业务验收仍独立执行。
选用引擎/SDK 和 FileSystem 的 L5 实施规范与 L6 项目真实存储授权、RPO/RTO、费用、事故和业务验收不得混淆。
4. 完整数据备份、PITR、跨节点复制、数据重分布、跨版本发布、合法客户资金/消息副作用及灾难恢复由相邻 L4 专项和具体项目另行验证，本规范的本地 Crash Recovery 不越权替代。

### wal-R01

**条款范围：** §01、§02、§03、§04、§05、§06

**目标工具/输入：** 实际引擎版本与持久配置读回；提交确认/故障时间轴。权威数据、已确认事务、进程/内核/掉电及不诚实设备分别建模

**判据：** 日志顺序/同步承诺与故障等级对应，HTTP或进程重启不证明设备耐久

**合法邻例：** 有明确允许丢失窗口的非关键缓存可异步提交，不能误标零RPO

**恢复：** 保护原介质/日志，记录未知结果，按权威数据和业务身份恢复

**来源：** [PG-W](https://www.postgresql.org/docs/18/runtime-config-wal.html)、[SQ-P](https://www.sqlite.org/pragma.html#pragma_synchronous)、[MY-W](https://dev.mysql.com/doc/refman/8.4/en/innodb-parameters.html)。关系：implementation-and-organisation-synthesis

<a id="wal-R02"></a>

### wal-R02

**条款范围：** §07、§08、§09、§10、§11、§12、§13、§14

**目标工具/输入：** 日志/页/检查点/空间/校验与I/O错误记录。日志先后顺序错、删除前置段、torn page、EIO后继续信任缓存

**判据：** 恢复链及页完整性与校验范围分别成立；校验不自动修复

**合法邻例：** 正常未checkpoint脏页不是损坏，冗余日志存在不自动允许删除

**恢复：** 暂停受影响写入、隔离副本并按完整链恢复，不用容错模式掩盖损失

**来源：** [PG-W](https://www.postgresql.org/docs/18/runtime-config-wal.html)、[MY-W](https://dev.mysql.com/doc/refman/8.4/en/innodb-parameters.html)、[SQ-W](https://www.sqlite.org/wal.html)。关系：implementation-and-organisation-synthesis

### wal-R03

**条款范围：** §15、§16、§17、§18、§19、§20

**目标工具/输入：** SHOW fsync/full_page_writes/wal_sync_method/synchronous_commit；WAL归档状态。off提交、禁fsync、首次页修改、归档堵塞与max_wal_size误当硬限

**判据：** 区分异步耐久窗与损坏风险，checkpoint不是备份或全部可清理

**合法邻例：** 明确暂存unlogged数据允许崩溃后重建，不可当权威持久账本

**恢复：** 恢复受支持配置/可用基线，补连续归档；不得先删唯一所需WAL

**来源：** [PG-W](https://www.postgresql.org/docs/18/runtime-config-wal.html)、[PG-B](https://www.postgresql.org/docs/18/continuous-archiving.html)。关系：implementation-and-organisation-synthesis

### wal-R04

**条款范围：** §21、§22、§23、§24、§25、§26、§27

**目标工具/输入：** SELECT @@innodb_flush_log_at_trx_commit,@@sync_binlog；SHOW ENGINE INNODB STATUS。redo已刷binlog未刷、禁doublewrite、日志空间满与force recovery误用

**判据：** 本地redo、binlog复制链及页保护独立，0/2不是固定准确一秒丢失上限

**合法邻例：** 可重建非权威数据允许选择风险模式，但不得借此证明零RPO

**恢复：** 按官方支持模式在隔离副本恢复并对账；强制恢复只救援不证明无损

**来源：** [MY-W](https://dev.mysql.com/doc/refman/8.4/en/innodb-parameters.html)、[MY-HA](https://dev.mysql.com/doc/refman/8.4/en/replication-semisync.html)。关系：implementation-and-organisation-synthesis

### wal-R05

### wal-R06

**条款范围：** §33、§34、§35、§36

**目标工具/输入：** 目标SQL Server版本/恢复模型/日志DMV与耐久选项。延迟耐久成功后宿主故障、日志文件缺失、checkpoint冒充log backup

### wal-R07

**条款范围：** §37、§38、§39、§40
