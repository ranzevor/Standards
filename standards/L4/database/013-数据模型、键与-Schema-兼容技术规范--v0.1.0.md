## 一、适用范围与分层

本专项位于 L4 第 03 领域，深化相应[数据库与数据工程通用基线](012-数据库与数据工程领域通用基线--v0.1.0.md)中的身份、主外键、字段语义、Schema 演化及跨格式兼容。应用领域服务、API/RPC、消息、事务、迁移和实际业务结果仍归原有 L4 专题；具体 SQL/SDK、数据权限、费用及运行验收归 L5/L6。按项目真实选用的数据库、文档格式和活跃客户端启用条款，不预设必需部署某种存储引擎或 Schema Registry。

## 三、42 项技术机制

### §01 业务实体与权威
**机制：** 区分真实业务对象、权威记录、派生快照与外部数据；实体身份与存储表名不强制一一对应。

**验收：** 按合法写入操作键追溯权威记录及业务终态。

**核验合同与来源：** [model-R01](#model-R01)；本条对应的失败输入见下文验证矩阵。

### §02 概念与物理分层
**机制：** 区分领域实体关系、逻辑字段和数据库物理布局；实际项目可合并无必要的重复文档。

**验收：** 换存储位置与索引结构不改变业务含义。

**核验合同与来源：** [model-R01](#model-R01)；本条对应的失败输入见下文验证矩阵。

### §03 对象标识生命周期
**机制：** 规定身份创建、合并、拆分、转移、归档及重建的稳定性与保留要求。

**验收：** 旧引用与历史事件仍能定位正确对象。

**核验合同与来源：** [model-R01](#model-R01)；本条对应的失败输入见下文验证矩阵。

### §04 自然键与代理键
**机制：** 根据可变性、外部来源、隐私和引用成本选择自然/代理/公开键，不能把展示值自动当主键。

**验收：** 重命名、第三方导入与迁移不误绑定实体。

**核验合同与来源：** [model-R01](#model-R01)；本条对应的失败输入见下文验证矩阵。

### §05 租户与范围唯一性
**机制：** 确定全局、租户、父对象和时间范围的唯一性；在约束和查询中采用相同作用域。

**验收：** 跨租户同编码无冲突，域内重复受控拒绝。

**核验合同与来源：** [model-R01](#model-R01)；本条对应的失败输入见下文验证矩阵。

### §06 ID 生成及排序
**机制：** 序列、UUID 等按真实环境选用；RFC 9562 UUIDv7 时间信息不证明业务顺序、授权或无碰撞。

**验收：** 并发、时钟变化、离线生成与复制不会创建非法重复。

**核验合同与来源：** [model-R01](#model-R01)；本条对应的失败输入见下文验证矩阵。

### §07 复合键及关联记录
**机制：** 对关系表、明细、版本记录选择稳定键；可变展示字段不应未经判断变成身份。

**验收：** 复合键更新及跨表关联无悬空引用。

**核验合同与来源：** [model-R02](#model-R02)；本条对应的失败输入见下文验证矩阵。

### §08 外部 ID 映射与回收
**机制：** 保留外部来源、版本、租户和历史映射；外部 ID 重用不得授权到先前对象。

**验收：** 删除重建、批量导入和供应方换 ID 不误合并。

**核验合同与来源：** [model-R02](#model-R02)；本条对应的失败输入见下文验证矩阵。

### §09 主键变动与级联影响
**机制：** 主键替换、FK 传播与外部缓存/事件使用具有独立兼容窗口。

**验收：** 键变更后旧业务引用合法或明确拒绝。

### §10 主键引擎差异

**验收：** 空值、多条软删除行及并发插入满足业务唯一范围。

### §12 外键实际启用
**机制：** MySQL 外键限制、SQLite 每连接 PRAGMA foreign_keys、PostgreSQL 约束按版本核对。

**验收：** 父缺失、非法子引用与禁用约束时的结果明确。

**核验合同与来源：** [model-R02](#model-R02)；本条对应的失败输入见下文验证矩阵。

### §13 引用动作与删除
**机制：** CASCADE、SET NULL、RESTRICT 需符合保留和数据权利，不由本库删除推断外部副作用完成。

**验收：** 父子删除/变更不会误删客户记录和资金证明。

### §14 关系基数与可选性

## 四、静态失败场景与对应验收

### 1. 业务身份与键
| 失败输入 | 机制关联 | L6 预期检查 |
| --- | --- | --- |
| 以报表镜像更新覆盖源订单状态 | §01 | 根据真实领域权威判定写入有效性 |
| 迁移数据库后物理 rowid 变化使业务对象被认作新实体 | §02 | 逻辑身份不随物理布局变化 |

## 五、组织审批、分层接入及版本责任

1. 本版包含 **42 项独立技术机制、54 项静态失效场景**；项目应固定官方协议版本、厂商实现差异及相邻技术职责。审批不代替任何 L5/L6 项目的真实数据读写、迁移、恢复、资金或业务验收。
2. 正式标准原文和实际厂商实现是相应技术的权威；本文只规定实际领域契约、键作用域、读写兼容组合、失效断言与项目验收边界。数据库内核、索引、SQL 查询优化及数据迁移工具由相邻 L4 专项进一步细化；L5 锁定具体 SDK/引擎版本，L6 保留各环境/租户/数据权利、原始测试证据及例外审批。
42项机制与54项场景的文本覆盖和实际运行结果分别登记；真实生产数据库迁移、客户数据操作与业务端到端验收须使用各自的环境、权限、数据和恢复判据。

### model-R01
