# L4 复制、高可用与读写一致性技术规范

**文档ID：** STD-L4-DATABASE-009　**版本：** 0.1.0　**状态：** adopted　**生效日期：** 2026-10-30

## 一、适用范围及与相邻规范的职责边界

本专项是 L4 数据库与数据工程领域第 07 项具体技术规范，聚焦真实选用的副本、同步/异步确认、主从切换、故障域、读一致性和业务合法恢复。**并不强制每个系统部署高可用副本或产生新增服务器费用。** 相应 L4 数据库通用基线、数据模型/Schema、SQL 查询、事务/MVCC、索引/计划、WAL/崩溃恢复、分区/分片各自保持领域权威、查询正确性、单节点持久化、数据分布职责；后端事务/业务工作流与安全规范继续决定跨系统副作用、权限及真实客户结果。备份/PITR与Schema迁移分别由[领域目录](README.md)中的对应独立规范承担。L5 确认选用引擎/驱动与设置，L6 以项目数据权利、费用预算和真实业务完成证据独立验收。

## 三、48 项复制、高可用和读写一致性机制

以下验收条件属于项目测试设计，不是已完成的生产故障注入或用户业务验收。

### §01 适用业务与可用性需求
**机制：** 按实际业务中断、数据丢失、读延迟、费用和地域权利定义复制价值；规范不强制单机项目购买 HA 集群。

**验收：** 可列举每个副本承担的真实请求、故障域、RPO/RTO 和费用阈值。

**核验合同与来源：** [ha-R01](#ha-R01)；本条对应的失败输入见下文验证矩阵。

### §02 副本、分片、缓存与备份的差异
**机制：** 副本通常重演同一权威数据，分片划分键空间，缓存可重建，备份保留历史；副本也可能复制误删，不能代替 PITR。

**验收：** 节点崩溃、错误删除、跨区中断等各自选择正确恢复机制。

**核验合同与来源：** [ha-R01](#ha-R01)；本条对应的失败输入见下文验证矩阵。

### §03 唯一写入主权和合法入口
**机制：** 明确单主、共识多副本或允许冲突的多写者模型及其对象作用域。对要求单一权威/线性化的对象，主节点自认 Primary 不证明仍持有写权，必须验证任期及目标生效侧隔离。Cassandra 等显式多主可在分区两侧接受不同副本写入，但必须声明冲突合并、可用性和非线性化边界；不能把这种能力直接用于需要唯一扣款的不变量。

**验收：** 单权威模式隔离旧主后，旧授权不能再使同一对象生效；合法多写者模式可接受并发写但须按声明冲突规则收敛，且不得被标为已经满足单权威账本。

**核验合同与来源：** [ha-R01](#ha-R01)；本条对应的失败输入见下文验证矩阵。

### §04 物理副本与独立故障域
**机制：** 多副本处于同一宿主、供电、可用区或依赖路径时，不自动获得相应容灾等级；跨区放置受数据驻留合同约束。

**验收：** 独立切断节点/故障域后列出真实可写、可读副本和风险范围。

**核验合同与来源：** [ha-R01](#ha-R01)；本条对应的失败输入见下文验证矩阵。

### §05 RPO、RTO 和证据等级
**机制：** RPO 是允许丢失区间，RTO 是业务恢复目标；健康探测和一次测试耗时不能替代实际授权故障演练。

**验收：** 各故障等级记录成功/未知写入、丢失区间和用户实际恢复时间。

**核验合同与来源：** [ha-R01](#ha-R01)；本条对应的失败输入见下文验证矩阵。

### §06 复制日志与 WAL 的职责
**机制：** PG WAL、MySQL Binlog/Relay Log、Mongo Oplog、Cassandra Mutations 的接收和回放语义不同，不能由一类日志 ACK 推断其他日志持久。

**验收：** 确定生产者、位置、水位、所涵盖的对象及接收/Apply 阶段。

**核验合同与来源：** [ha-R01](#ha-R01)；本条对应的失败输入见下文验证矩阵。

### §07 异步、半同步、同步确认
**机制：** 异步允许主写成功后副本尚未收到；半同步接收 ACK、远端 Flush 与 Apply 的强度和等待成本不同。

**验收：** 每一种启用的模式均测量故障前已确认事务可恢复的真实范围。

**核验合同与来源：** [ha-R02](#ha-R02)；本条对应的失败输入见下文验证矩阵。

### §08 收到、落盘、回放与业务可见
**机制：** 副本收到数据、写入 OS 缓存、同步介质、Apply、面向客户端可查是不同阶段，外部履约再另行判断。

**验收：** 在各阶段停止副本后分别核对数据耐久、可读性与业务确认。

**核验合同与来源：** [ha-R02](#ha-R02)；本条对应的失败输入见下文验证矩阵。

### §09 选举、Quorum 和网络分区
**机制：** 选举/共识阈值、复制 ACK 数和客户端读写一致性级别不是同一门槛。采用单权威共识的对象在无有效法定人数/租约时不得继续权威写入；显式采用多主最终一致模型的系统可按其产品协议继续接受冲突写，但不得承诺分区期间全局线性化、无冲突唯一性或跨对象原子性。

**验收：** 分别断开投票成员和数据副本，核对实际产品的可用写侧与确认阶段；允许的多主冲突写是合法邻例，前提为冲突恢复及业务不变量明确，不以拒绝所有并发写充当通用通过条件。

**核验合同与来源：** [ha-R02](#ha-R02)；本条对应的失败输入见下文验证矩阵。

### §10 投票成员、Arbiter 和实际副本
**机制：** Arbiter/Witness 可影响选举但不等于完整存储副本；增加票数不总增加可用的数据副本数。

**验收：** 实际投票、承载数据成员、容错节点数和写入门槛有对应关系。

**核验合同与来源：** [ha-R02](#ha-R02)；本条对应的失败输入见下文验证矩阵。

### §11 Split Brain 防护与 Fencing
**机制：** 对于单权威写入，旧主隔离后仍可能接受请求，需要在生效端验证任期/Epoch，或采用可靠撤权、STANDBY、Fencing 等控制；Ping 失败不足以证明旧主停止。对于显式多写者模式，治理对象是越权写和冲突合并，不将有权多主本身称为 Split Brain。

**验收：** 旧主恢复后，旧任期请求不能覆盖新权威提交；合法多写者按声明的冲突协议恢复且能区分已收请求、实际生效和业务认可的结果。

**核验合同与来源：** [ha-R02](#ha-R02)；本条对应的失败输入见下文验证矩阵。

### §12 主从提升与写入授权切换
**机制：** Promotion 必须核对备节点同步资格、路由、更替后的只读/读写状态以及旧主停止；DNS/VIP 更新不代表旧主已降级。

**验收：** 切换窗口既有已确认记录可追溯，客户端写入路由指向唯一正确主库。

**核验合同与来源：** [ha-R02](#ha-R02)；本条对应的失败输入见下文验证矩阵。

### §13 Term、Timeline、GTID 与日志位置
**机制：** PG Timeline/LSN、MySQL GTID、Mongo Term/Optime、SQL Server LSN 等不在同一个序列空间，不能跨产品直接比较或当作业务全局时间。

**验收：** 旧日志历史、不同 Epoch 和重新入组时能找到合法复制位置及分叉。

**核验合同与来源：** [ha-R02](#ha-R02)；本条对应的失败输入见下文验证矩阵。

### §14 未知 COMMIT 与幂等恢复
**机制：** 连接中断或 Failover 期间未收到 ACK 不表示交易必然未提交；重试前应按权威业务操作键回查，外部支付/消息由相邻业务规范约束。

**验收：** 新主恢复后未知、已确认、失败三类交易无重复客户副作用。

**核验合同与来源：** [ha-R02](#ha-R02)；本条对应的失败输入见下文验证矩阵。

### §15 客户端发现、路由和连接池
**机制：** 代理、DNS/VIP、Listener、驱动拓扑和连接池缓存可能滞后；切主后旧连接不应保持写权限或携带上个租户状态。

**验收：** 断线、半开连接及新旧路由混用时客户端正确失败或恢复。

**核验合同与来源：** [ha-R03](#ha-R03)；本条对应的失败输入见下文验证矩阵。

### §16 读己之写 Read-Your-Writes
**机制：** 若业务要求提交后立刻读取自己刚写入的数据，必须读权威源或基于实际水位/会话一致性策略；任意异步副本不保证此语义。

**验收：** 写入→副本读取→路由切换链能获得预期内容或有界等待/拒绝。

**核验合同与来源：** [ha-R03](#ha-R03)；本条对应的失败输入见下文验证矩阵。

### §17 单调读取和版本回退
**机制：** 用户连续读两个不同落后副本可能看到版本回退；只有选择合适会话/水位约束才能声称 Monotonic Reads。

**验收：** 跨副本切换、延迟突变后不会在不允许的场景退回更早有效版本。

**核验合同与来源：** [ha-R03](#ha-R03)；本条对应的失败输入见下文验证矩阵。

### §18 因果读取与会话水位
**机制：** 因果依赖、Cluster Time 和数据库会话 Token 要按所选引擎的受支持接口传播，客户端本地时钟不足以代替因果保证。

**验收：** 写 A→读 B→写 C 的实际依赖在跨副本读取后保持业务顺序。

**核验合同与来源：** [ha-R03](#ha-R03)；本条对应的失败输入见下文验证矩阵。

### §19 陈旧窗口和数据有效期限
**机制：** Max Staleness、Replay Lag 和 Exact/Bounded Read Timestamp 具有不同意义，陈旧数据不能被无条件用于余额、授权和失效判断。

**验收：** 超出合法陈旧边界时明确等待、回退权威读或拒绝。

**核验合同与来源：** [ha-R03](#ha-R03)；本条对应的失败输入见下文验证矩阵。

### §20 跨对象快照与全局读取
**机制：** 多个表、分片及副本独立读可能使用不同时间点，即使每次返回成功也不构成统一事务快照或业务账本对账。

**验收：** 跨行汇总使用受支持一致时间戳或标示允许的最终一致口径。

**核验合同与来源：** [ha-R03](#ha-R03)；本条对应的失败输入见下文验证矩阵。

### §21 跨区域读流量和费用
**机制：** 本地读取可能降低延迟，跨区复制可能增加写入 RTT、带宽和运维成本；地理落点不自动赋予数据处理权。

**验收：** 真实业务地域、复制链路、预算及权限均有约束。

**核验合同与来源：** [ha-R03](#ha-R03)；本条对应的失败输入见下文验证矩阵。

### §22 滞后指标及空洞数据
**机制：** Send/Receive/Flush/Replay/Apply 和复制线程心跳属于不同监测项；监测断联不等于 Lag=0。

**验收：** 每个副本水位、上次采样时间、断链区间及数据可见性明确可追溯。

**核验合同与来源：** [ha-R03](#ha-R03)；本条对应的失败输入见下文验证矩阵。

### §23 复制日志留存和恢复空间
**机制：** Replication Slot、Relay Log、Oplog、Hints 的积压会消耗磁盘；为减轻占用擅删必需 WAL/日志会使后续恢复失效。

**验收：** 复制中断及 ENOSPC 条件下，安全停写或止损仍保留受承诺的恢复数据。

**核验合同与来源：** [ha-R03](#ha-R03)；本条对应的失败输入见下文验证矩阵。

### §24 PG Streaming、Replay 与 Standby 可见性
**机制：** PostgreSQL 18 Streaming 默认异步；送达、Flush 和 Replay LSN 不同，Hot Standby 查询可见性取决于实际 Replay。

**验收：** 按 pg_stat_replication 与 WAL Receiver/Replay 水位核对真实副本查询内容。

**核验合同与来源：** [ha-R04](#ha-R04)；本条对应的失败输入见下文验证矩阵。

### §25 PG synchronous_commit 确认阶段
**机制：** PostgreSQL 18 的 synchronous_commit 有效值为 off、local、remote_write、on、remote_apply；remote_flush 不是该设置的合法值。fsync=on 且配置有效同步候选时，remote_write 等待同步备库写入操作系统、on 等待同步备库持久刷写、remote_apply 进一步等候回放从而使该备库查询可见；local 只等本地刷写，off 不等本地刷写。synchronous_standby_names 为空时，非 off 级别只体现本地耐久，不能宣称远端同步；各级确认仍不证明外部付款/业务完成。

**验收：** 保存 SHOW synchronous_commit、SHOW synchronous_standby_names、SHOW fsync 和 pg_stat_replication 的 sync_state/write_lsn/flush_lsn/replay_lsn，逐项延迟远端写入/刷写/回放并读取指定备库。空同步名单是合法单机邻例，只能承诺其本地边界；未知客户端 COMMIT 结果按业务键对账，不盲重发付款。

**核验合同与来源：** [ha-R04](#ha-R04)；本条对应的失败输入见下文验证矩阵。

### §26 PG 同步副本 FIRST/ANY 策略
**机制：** synchronous_standby_names 的 FIRST 优先顺序和 ANY Quorum 使用不同选择策略；当可用同步副本不足时可能阻塞 COMMIT，而不能默默承诺零损失且持续可写。

## 五、组织审批、运行版本和 L6 完成范围

1. 本规范包含 **48 项独立技术机制和 60 项静态失败场景**；10 组失败输入关联全部 §01—§48，来源需按实际版本、适用条件和证据范围复核。具体数据库选型、生产数据权限、HA 演练与 L5/L6 客户业务验收仍独立执行。
静态案例与 CI 只能提供设计证据，不属于实际数据库、跨区网络故障或客户业务验收。
3. L5 采用具体产品/版本、驱动、同步/异步和托管服务选项，L6 确定合法用户请求、RPO/RTO、客户业务完成、机房/区域、付费资源、数据驻留和故障注入权限；不得自动修改生产复制配置、停机或新建收费资源。
4. 相应数据库数据模型、SQL/MVCC、WAL 崩溃恢复与分区/分片只负责其既定条款；Schema 迁移及备份/PITR 由相邻专题规定。数据库恢复、外部付款、消息 ACK 和客户履约不可因副本同步而互相替代。
