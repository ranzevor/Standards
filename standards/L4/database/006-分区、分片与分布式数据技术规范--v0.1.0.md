# L4 分区、分片与分布式数据技术规范

**文档ID：** STD-L4-DATABASE-006　**版本：** 0.1.0　**状态：** adopted　**生效日期：** 2026-10-30

## 一、技术范围、组织权威及不重复的边界

本专项属于 L4 第 03 类数据库与数据工程领域第 06 项具体技术规范，聚焦**实际选用的逻辑表分区、跨节点 Shard/Tablet/Split、分区键选择、路由元数据、数据放置、热点、分片内/跨分片查询及再分布的正确性**。它不强制单机项目升级分布式数据库，不把分区表、分布式高可用、副本数、跨区域数据驻留视为同一技术目标。数据/租户权利不由物理位置自动决定。

已有 L4 数据库通用基线、数据模型与 Schema、SQL 查询、事务/MVCC、索引/优化器、物理 WAL/Crash Recovery 专项继续负责数据权威、查询语义、数据库事务与单实例持久化；后端领域事务/消息与工作流负责跨系统业务幂等及客户结果。这里仅对**分区规则、真实键空间/数据分布、路由/再分片与跨片一致性边界**提出技术断言。第 07 项「复制、高可用与读写一致性」、第 08 项「Schema 迁移、回填与兼容收缩」及第 09 项「备份、PITR 与恢复演练」分别具有独立专题。技术采用状态及项目实施状态分别登记。

## 三、48 项独立技术机制与 L6 可验收判断

所有机制按项目真实使用的分布策略、数据库版本、合法租户、地理位置及费用条件选择启用。每项“验收”是需要设计或执行的检查，不是既成运行结果。

### §01 真实业务需要与不强制分片
**机制：** 识别真实增长、CPU/IO、热点、隔离、地域驻留和保留/归档需要。分区或分片应有可解释的收益与成本证据，不默认要求分布式；合法驻留隔离、按期归档或已知增长规划可以在当前性能尚足够时采用，不必等现有索引/缓存全部失效才允许分区。

**验收：** 对比单实例/不分区方案与所需容量、驻留、保留或延迟约束，记录选型理由和资源预算。小型单机是合法正例；当前无瓶颈但有明确生命周期分区需求也是合法邻例，不能仅按规模小一律拒绝。

**核验合同与来源：** [partition-R01](#partition-R01)；本条对应的失败输入见下文验证矩阵。

### §02 逻辑数据集与物理归属分离
**机制：** 领域业务对象、租户身份和数据权利不会因其所处 Partition、Shard、Tablet、Split 或副本而改变；任何物理位置和路由都不得反向决定合法用户身份。

**验收：** 重定位和扩容后按相同业务键获取相同合法对象及授权。

**核验合同与来源：** [partition-R01](#partition-R01)；本条对应的失败输入见下文验证矩阵。

### §03 分区、分片、副本和表格式区别
**机制：** 同实例表分区、跨节点分片、只读/多活副本、对象文件分区及分析表快照不同；单机分区不会自动增加写入节点或消除单点故障。

**验收：** 每层的写主、数据范围、复制关系和独立失败域均可画出且由真实部署证实。

### §04 业务键、分区键及作用域
**机制：** 分区/分片键不必等于对象全局唯一键或租户授权键；若二者分离，应有稳定可验证的路由映射，避免用存储桶编号代替业务自然身份。

**验收：** 同一业务对象在分片迁移及不同租户场景不会错误合并或越权。

**核验合同与来源：** [partition-R01](#partition-R01)；本条对应的失败输入见下文验证矩阵。

### §05 键选择、基数及数据分布
**机制：** 评估键的基数、热点、写入单调性、时间分布、租户偏斜和查询过滤情况；均匀行数不等于均匀 QPS/IO 或 CPU，禁止凭 ID 是否随机直接判定容量。

**验收：** 采用真实热键/冷键与倾斜租户样本测量分布和不利热点。

### §06 Range、Hash、List 取舍
**机制：** Range 便于范围扫描但单调写入可能热端集中；Hash 可能分散写入但区间查询会跨分片；List/地域分配便于定位但容易形成规模不均衡；不得声称 Hash 自动消除单一 Key 热点。

**验收：** 对点查、时间范围、地域筛选及热点写入分别给出目标分片数与 Fan-out 成本。

### §07 分片键变更与稳定对象身份
**机制：** 记录用于路由的键是否可修改及更新引发的跨分片移动，校验目标数据库版本是否支持直接更改/Reshard；不可把新路由 Key 视为重建业务对象的授权。

**验收：** 分片键修改前后版本、关系引用和历史事件均能定位合法对象。

### §08 租户数据隔离及复合键
**机制：** 租户 ID 在复合键、查询路由、缓存键、导出和迁移中具有一致性要求；在部分引擎中租户维度不作为分片键仍须在查询及数据访问层验证授权。

**验收：** 同一个外部编码分属两个租户时完整保留各自数据，路由更改不扩大权限。

**机制：** 唯一索引、PK、UK 以及外部业务 ID 的全局/租户内唯一要求可能超出单物理分区的索引覆盖能力；必要时由可证明的全局约束或受权威写入路径实现。

**验收：** 同一业务标识被并发写入不同分片不能合法重复，违反唯一时有明确拒绝。

### §11 PostgreSQL 18 Unique/PK 分区限制
**机制：** PostgreSQL 18 声明式分区表的 UNIQUE/PK 必须包含所有分区键列，且分区键不能使用表达式或函数调用来满足该全表约束；子分区局部唯一性不是任意字段全局唯一。

**验收：** 真实 DDL 可实现所需唯一性，重复样本跨两个分区被拒绝或有独立校验方案。

### §12 PostgreSQL 分区裁剪及参数
**机制：** Partition Pruning 依分区键边界而非必须存在分区键索引；PG 18 可按计划或执行时的参数裁剪，约束排除与 Pruning 不完全等同。

**验收：** 参数查询的实际扫描分区与合法数据结果对应，非等值过滤仍能解释 Fan-out。

**核验合同与来源：** [partition-R03](#partition-R03)；本条对应的失败输入见下文验证矩阵。

### §13 PostgreSQL 路由、默认及边界
**机制：** INSERT 会按分区定义路由，缺少覆盖目标值的分区时应按实际引擎规则报错，Default Partition 或扩容需明确合法范围；分区键变更可能导致跨子分区移行。

**验收：** 边界时间、NULL、超出范围及新旧分区交接不会静默丢行或混租户。

**机制：** MySQL 8.4 用户定义 InnoDB 分区表不能含外键引用，也不能成为外键引用的目标；NDB 的分区行为不同，不可用测试成功的 NDB 结论代表 InnoDB。

## 五、组织审批、版本边界和 L6 验收

1. 本规范包含 **48 项独立技术机制及 60 项静态失效场景**，10 组失败输入对 §01—§48 有直接或组合覆盖，来源需按实际版本、适用条件和证据范围复核。实际 L5/L6 数据权限、生产变更、跨分片交易和客户业务验收独立进行。
不能以数据库分区/分片、节点副本、迁移切换的语法存在即宣称真实生产可用、地理合规、跨 Shard 原子性和隔离均成立。
4. 分布式复制/HA、恢复/备份 PITR、业务事务幂等/工作流、源到目标迁移与权限合同均保持相邻 L4 专题的独立责任。静态覆盖不是运行实验，也不是 60 次真实分片故障已验收。

### partition-R01

**条款范围：** §01、§02、§03、§04、§05、§06

**目标工具/输入：** partition/shard设计、真实键分布和目标负载/驻留/保留合同。无需求强制八节点、分区与副本混淆、边界重叠/空洞

**判据：** 逻辑对象与物理归属分离，键分布/范围/Hash成本对应实际需要

**合法邻例：** 当前性能够但按保留周期分区合法；小型单机不分片也合法

**恢复：** 保留逻辑身份，修复边界/路由前验证全量键集合与成本，不重编号伪修复

**来源：** [PG-P](https://www.postgresql.org/docs/18/ddl-partitioning.html)、[MY-PK](https://dev.mysql.com/doc/refman/8.4/en/partitioning-limitations-partitioning-keys-unique-keys.html)、[TI-P](https://docs.pingcap.com/tidb/stable/partitioned-table/)。关系：implementation-and-organisation-synthesis
