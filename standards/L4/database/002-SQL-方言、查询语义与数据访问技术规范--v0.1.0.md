# L4 SQL 方言、查询语义与数据访问技术规范

**文档ID：** STD-L4-DATABASE-002　**版本：** 0.1.0　**状态：** adopted　**生效日期：** 2026-10-30

## 一、技术对象、适用边界与既有责任

本专项属于 L4「数据库与数据工程」第 02 项具体技术专题，深化[相应数据库通用基线](012-数据库与数据工程领域通用基线--v0.1.0.md)与[数据模型、键与 Schema 兼容专项](013-数据模型、键与-Schema-兼容技术规范--v0.1.0.md)的查询、表达式、结果集及数据读取责任。对使用 SQL 或 SQL 风格查询接口的实际系统适用；无 SQL 的项目不需要建设模拟 SQL 兼容层。

相应 L4 后端服务边界、API/RPC、应用事务与幂等、消息、流量治理、可观测性、Schema 迁移及端到端测试仍分别负责领域行为、事务写入、发布与用户业务结果。本专项只细化 **SQL 方言差异、查询语义、数据访问安全、读取结果正确性与有界资源**；数据物理索引与优化器、数据库锁/MVCC、备份/PITR、CDC与Schema DDL实施分别由[领域目录](README.md)中的相应独立规范承担。L5 锁定语言/驱动/数据库版本，L6 根据实际用户、权限、数据规模和业务终点设定测试与验收。

**验收：** 同为 NULL、一方 NULL、非空相等及不同的分支均有明确定义。

**机制：** 对 LEFT/RIGHT/FULL JOIN 的条件放在 ON 与 WHERE 有不同结果，不能把过滤位置挪动当纯性能改写；需评估是否消除 NULL 延伸行。

**机制：** 存在性、半连接/反连接与普通 JOIN 的结果基数不同；NOT IN 子查询包含 NULL 时可能变 UNKNOWN，不能机械改写为 NOT EXISTS。

**验收：** 无匹配、空集合、NULL 结果和重复子查询值都按具体业务语义判定。

### §17 标量子查询行数约束
**机制：** 标量子查询的基数语义按引擎区分：PostgreSQL 18 无行产生 NULL、多行报错；SQLite 将结果第一行作为标量值，不能依赖其自动拒绝多行。业务本应唯一时由唯一约束或显式基数检查保证，LIMIT 1/first() 不能掩盖重复；合法“选最新一条”须另有确定排序和业务合同。

**机制：** 相关子查询对外层字段引用须明确资格名称、相关键与数据规模；执行计划可影响资源，但不能擅自改变其集合语义和越权过滤。

**验收：** 同名字段和跨租户相关列在不同数据量下均生成正确合法结果。

### §20 SQL_MODE 与非确定性分组扩展
**机制：** MySQL 可按 sql_mode 关闭 ONLY_FULL_GROUP_BY，SQLite 允许 bare columns；不能因此声明跨系统兼容，ORDER BY 不会使 MySQL 裸列在聚合前按指定行选择。

**验收：** 同一聚合样本在不同会话模式和数据分布下仍满足领域合法性或明确不支持。

### §21 WHERE、HAVING 与分组筛选
**机制：** WHERE 用于行级预筛选、HAVING 用于组级断言；将 HAVING 变为 WHERE 会改变聚合输入及结果，空分组与无 GROUP BY 聚合另测。

**验收：** 极值组、全空输入和部分合法组的结果可按业务条件独立计算。

**机制：** COUNT(*)、COUNT(expr)、COUNT(DISTINCT expr) 的 NULL 与重复行为不同，SUM/AVG 等空输入可能返回 NULL；结果是否应转为 0 由领域语义决定。

**验收：** 空表、NULL 列及重复订单不会误报活跃用户数、销售额或收费人数。

### §23 顺序敏感聚合
**机制：** string_agg/array_agg/json_agg 等输出可能依赖聚合输入顺序，应在函数允许的语法中明确 ORDER BY；普通外层排序不证明元素顺序。

**验收：** 等价输入在可变执行计划和并行模式下能得到被要求的序列/JSON 集合。

### §24 条件聚合及 GROUPING 扩展
**机制：** FILTER、CASE、ROLLUP、CUBE、GROUPING SETS/多维分组的可用性和 NULL 汇总层标识按实际方言定；不能把小计行误计为客户真实记录。

**验收：** 报表维度、汇总小计和过滤缺省值具有可靠标记，不重复算账。

### §25 窗口分区、顺序与聚合范围
**机制：** 窗口函数 PARTITION BY、ORDER BY 与最终输出 ORDER BY 是不同语义；分区选择和排序键必须由业务合同定义，不能认为窗口排序保证客户端结果顺序。

**验收：** 跨租户分区、相同排序值和最终输出结果具有被批准的可重算行为。

### §26 窗口帧 ROWS、RANGE、GROUPS
**机制：** last_value/nth_value/累计和等依赖窗口 frame；PostgreSQL 默认帧及 peer 行可能造成 last_value 不是分区末行，跨数据库并不保证所有 IGNORE NULLS 行为。

**验收：** 同值排序、跨日期窗口和空帧分别满足精确分组、帧范围及 NULL 规则。

### §27 排名、相同值与稳定先后
**机制：** ROW_NUMBER/RANK/DENSE_RANK 等对 peer 的处理不同；返回有业务身份作用的第 N 名时必须固定 tie-breaker，不依赖不稳定数据读取次序。

**验收：** 完全相同的排名键不会随机决定获益、授信或唯一客户。

| 查询模拟测试通过而断开的流式导出仍向非授权端发送数据 | §01、§39、§45、§46、§48 | 真实取消及用户业务边界核验 |

## 五、版本、生效与项目验收

项目 L5 运行实现和 L6 客户业务、生产数据与资金验收仍独立执行。
标准按 ISO、官方版本化数据库规格与实际 SDK 实现分别引用；项目 L5 决定数据库、驱动及支持的 SQL 特性，L6 决定实际调用者、租户、数据与业务验收。
4. 数据模型/Schema、应用事务、消息、物理索引、MVCC 与备份恢复保留相邻 L4 专项的独立责任；本版不授权生产数据库操作、客户数据导出、费用或外部合同变更。
