# L4 游戏开发与数字内容领域通用基线

**文档ID：** STD-L4-GAME-003　**版本：** 0.1.0　**状态：** adopted　**生效日期：** 2026-10-30

**领域：** 09 游戏开发与数字内容

## 一、定位与适用范围

本基线面向具有交互循环、游戏状态、实时或回合式模拟、关卡/场景、玩家输入、游戏视听反馈或游戏内容资产的工程项目，包括单机、多人、2D、3D、文字/卡牌、模拟、严肃游戏、交互叙事和采用游戏引擎的实时数字体验。项目只适用与其实际玩法、平台和已批准产品承诺有关的条款。

领域序号用于分类，不表示优先级。本文不强制采用特定引擎、语言、渲染 API、物理引擎、资产格式、商店、联网服务或多人架构。无多人、无联网、无云存档、无 XR、无 Mod、无用户生成内容或无实时物理的项目不必实现相应机制；但不能把已承诺功能未验证的状态写成“不适用”。

本基线聚焦游戏特有的运行语义与内容链路：输入到游戏动作的映射、游戏时钟和模拟状态、物理/动画/关卡转换、存档恢复、资产导入与运行时引用、视听反馈、可访问性、目标平台性能及实际构建运行。通用需求、源码与版本控制、通用测试、安全、依赖和发布证据由实际采用的通用工程规范承接；桌面和移动规则按各项目已明确采用的范围组合；对外制品摘要、来源证明、签名、SBOM 与发行消费者核验按实际采用的软件供应链规范约束；工具/Agent 的外部动作按实际采用的相关技术规范约束；法律权利和商业发行决定仍由具备权限的主体确认。

下文“应”“不得”是规范性要求；项目采用时须明确准确版本、适用范围及有权主体。技术状态机的暂停、拒绝或回退与项目治理中的范围变更分别管理。

## 四、36 项游戏开发与数字内容共性机制

### A. 游戏产品合同与运行边界

### §01 游戏形态与适用特征
**机制：** 项目应记录实际形态、核心玩法、运行模式、受支持平台和关键依赖，并明确是否包含实时模拟、存档、联网、多人、XR、Mod、用户生成内容及可下载内容。  
**验收：** 对每项未采用的特征，能够指出其在已批准范围中不存在；已承诺特征不得仅因当前实现缺失而标为不适用。

### §02 可验证的核心玩法循环
**机制：** 核心玩法应能表示为可追踪的输入、规则处理、状态变化、反馈与下一步可行动状态。纯叙事、回合制和无实时物理玩法可使用不同的状态循环，不强制采用统一架构。  
**验收：** 从真实玩家入口执行一个代表性玩法循环，能够核对触发输入、状态变化、可见/可听反馈及完成条件；只有场景加载成功不算玩法通过。

### §03 游戏状态所有权与真相来源
**机制：** 应区分权威游戏状态、表现状态、临时输入状态、派生 UI 状态和缓存状态；动画、粒子、HUD 或本地预测不能未经规则确认反向修改权威进度。  
**验收：** 将表现层重置或重建后，游戏规则状态仍可由权威状态恢复；仅更改 HUD 数值不能完成任务或改变持久进度。

### §04 玩家可见结果与内部事件
**机制：** 应区分事件已触发、规则已接受、状态已提交、保存已持久化和玩家已看到反馈等阶段。音效播放、动画完成、网络 ACK 或日志输出不能单独证明玩家动作已成功。  
**验收：** 在动作中断、资源加载失败或反馈播放失败时，仍能判定规则结果，并提供与实际状态一致的后续操作。

### B. 模拟、时钟、物理与状态转换

### §05 游戏时间与现实时间
**机制：** 应区分模拟时间、渲染帧时间、现实时间及必要的单调时钟；暂停、慢动作、时间缩放、后台挂起和恢复的影响应由玩法规则明确。  
**验收：** 在低帧率、暂停、窗口失焦和恢复场景中，计时器、冷却、动画和玩法计时按其定义运行，不因墙钟跳变或渲染帧数意外加速。

### §06 帧率独立与更新顺序
**机制：** 对依赖时间的运动、插值和冷却，应明确固定步长、可变步长或混合更新的职责；输入采样、模拟更新、物理求解、动画与渲染之间的顺序必须可解释。  
**验收：** 在目标帧率范围及短时帧率波动下，同一合法输入序列不得因时间步长或帧率变化而意外引入关键事件的重复、丢失或顺序错乱；若玩法明确允许某种差异，须预先声明适用范围、容差及验证方法。

### §07 物理规则与碰撞边界
**机制：** 使用物理模拟的项目应定义坐标系、单位、碰撞层、触发器、连续/离散碰撞选择、穿透修正和运动主体所有权；不使用物理模拟的项目不适用本机制。  
**验收：** 对高速运动、贴边接触、薄障碍、重叠生成和碰撞层配置执行边界测试，关键对象不会无故穿透、重复触发或被错误过滤。

### §08 随机性与可复现状态
**机制：** 随机掉落、程序化关卡、敌人行为或战斗计算应明确随机源、种子生命周期和重置边界；如需复现，记录足以重建输入、规则版本与随机序列的材料。  
**验收：** 固定种子和相同输入在声明的可复现范围内产生一致结果；未声明跨平台确定性时，不得把不同硬件/运行时的浮点逐位一致作为默认承诺。

### §09 状态机与非法转换
**机制：** 玩家、敌人、关卡、任务、菜单和会话等关键状态应定义允许转换、进入/退出副作用及非法转换的处理；不得让同一实体同时进入互斥状态。  
**验收：** 对死亡/复活、暂停/恢复、胜负结算、关卡切换和重复触发执行测试，非法转换被拒绝或归一化，不产生双重奖励、重复结算或不可操作状态。

### §10 模拟、动画与表现解耦
**机制：** 动画、过场、音效和粒子可表达玩法状态，但应明确它们是否影响碰撞、输入锁定、伤害判定和任务完成；表现时间不得无意成为唯一的规则时钟。  
**验收：** 动画被跳过、资源缺失、帧率下降或混合树切换时，玩法规则仍符合定义；需要等待表现完成的机制有明确超时/恢复路径。

### C. 输入、交互与可访问性

### §11 输入动作抽象
**机制：** 玩家操作应经由有名称和语义的游戏动作映射到设备输入；键鼠、手柄、触控、辅助设备或语音只在产品声明支持时纳入，不将硬编码按键当作唯一动作定义。  
**验收：** 对已声明支持的输入设备执行同一核心动作，触发等价的玩法意图；不支持的设备/输入被清楚处理，不伪报动作成功。

### §12 输入重映射与设备状态
**机制：** 项目应明确是否支持按键重映射、轴反转、死区、灵敏度、输入冲突和热插拔；保存的映射应与玩家/配置身份绑定，并能恢复默认值。  
**验收：** 修改映射后，界面提示、游戏实际动作与保存设置一致；拔除或断开设备不会把持续输入永久卡住。

### §13 输入采样、缓冲与边缘事件
**机制：** 跳跃、确认、攻击、交互等离散动作应明确按下、持续、释放、缓冲和消费时点；一个物理输入事件不得因多次轮询或帧重试被重复消费。  
**验收：** 在低帧率、快速连按、菜单与游戏切换、焦点丢失及暂停恢复时，输入不会无故重复、丢失或从暂停前泄漏到恢复后的玩法。

### §14 UI 焦点与玩法控制权
**机制：** 应明确菜单、对话框、过场、文本输入和游戏操控之间的焦点及控制权；UI 操作不得意外触发背景中的游戏动作，游戏动作也不得绕过确认中的关键 UI。  
**验收：** 打开菜单、输入文本、关闭弹窗和恢复游戏后，焦点与控制权归属符合设计；一次确认不会同时提交 UI 动作和背景攻击/移动。

### §15 视听提示的语义对应
**机制：** 重要状态、危险、目标变化和交互结果应采用适合玩法的反馈通道；颜色不得成为唯一的关键信息通道，音效、振动、字幕或图形提示按项目承诺选用。  
**验收：** 关闭某个可选反馈通道后，玩家仍可通过产品承诺的替代方式理解必要的玩法状态；装饰性效果不冒充权威状态。

### §16 可访问性与玩家可配置选项
**机制：** 应根据实际玩法评估字幕/文字、对比度、可读性、控制重映射、难度或辅助选项、闪烁与镜头运动、音量分组和 UI 导航。只对产品声明和玩法实际存在的能力设定要求，不要求所有游戏提供同一套选项。  
**验收：** 对产品已承诺的可访问性设置逐项验证实际效果；关闭字幕或某项辅助功能只有在产品承诺必须保留该通道、或关闭后没有任何已承诺的替代方式且导致必要信息不可理解时，才判为失败。若产品允许玩家主动关闭字幕/辅助通道，应验证该选择生效、可重新开启，并且其他仍承诺的必要信息通道保持可用；设置不得仅改变菜单显示而未改变实际行为。

### D. 关卡、场景与内容资产

### §17 关卡入口、出口与转换
**机制：** 关卡/场景转换应定义触发条件、进入/退出副作用、加载失败处理、玩家状态保留和可恢复入口；异步加载不得暴露半初始化的可交互场景。  
**验收：** 从每个已支持入口进入关卡，资源加载成功后才开放交互；加载失败或取消时保留有效的上一状态或明确恢复路径。

### §18 实体生成、销毁与资源所有权
**机制：** 实体、场景实例和运行时资源应有清晰的所有者、生成条件、销毁时点和事件订阅生命周期；复用池中的实体必须重置上一使用者的状态。  
**验收：** 重复进入/离开关卡、快速生成销毁和对象池复用不会残留旧碰撞、计时器、输入、特效、事件订阅或玩家数据。

### §19 资产身份与导入链路
**机制：** 关键资产应能追溯源文件、内容身份、导入器/插件版本、导入设置、派生资源及目标平台变体。运行时引用必须指向构建中实际存在的资源，不以编辑器中可见代替打包后可用。  
**验收：** 从干净环境重建导入产物后，资源清单和关键派生关系可解释；移除或替换源资产时，过期缓存不会静默继续提供旧内容。

### §20 资产权利与来源元数据
**机制：** 对外部素材、字体、音效、音乐、模型、纹理、动作、代码、生成内容和用户提交内容，应记录实际来源、权利/许可依据、必要署名及允许用途；法律权利争议由有权主体处理。  
**验收：** 对任一随游戏分发的第三方资产，能找到对应来源和使用依据；来源未知或用途不符的资产不会被默认视为可公开发行。

### §21 内容引用完整性与缺失回退
**机制：** 关卡、对话、任务、材质、动画、音频和本地化资源之间的引用应可验证；缺失资源的回退方式必须符合其业务意义，不能把缺失的关键目标静默替换为无效占位。  
**验收：** 构建检查能识别悬空引用；运行时遇到可选装饰资源缺失时可受控降级，关键玩法资源缺失时则阻止进入不完整状态或给出可恢复错误。

### §22 内容版本与导入器迁移
**机制：** 引擎、导入器、压缩器、着色器或内容工具版本改变时，应识别会改变资源字节、运行时解释或画面结果的迁移，并保留重建与回退依据。  
**验收：** 升级工具链后对关键资产执行差异检查；资源变化可追溯到源文件、导入设置或工具版本，而非无法解释的缓存差异。

### §23 关卡可达性与软锁
**机制：** 项目应区分意外软锁、可恢复失败、已声明的失败/终局状态和有意设计的挑战状态。对于仍处于可继续游玩的状态，关键路径不得因不可达目标、错误出生点、永久关闭的门、必需道具丢失、NPC 停滞或互斥任务状态而意外失去可达性。若设计允许软锁、失败终局或不可逆选择，应明确触发条件、规则、玩家反馈及退出方式；依产品承诺，退出方式可以是恢复点、重置、回到标题或开始新局，不强制把所有终局转换成可继续的当前局。  
**验收：** 对声明可继续的关键路径验证入口、必需目标和退出条件均可达；注入状态异常或资源加载失败时，不得静默困住玩家。对已声明的失败/终局或设计性软锁，验证其状态可识别、反馈符合规则，且玩家可通过声明的恢复、重置、返回标题或新开局入口离开该状态。合法的设计性软锁或明确终局不因当前局无法继续而自动判失败。

### §24 本地化与内容变体
**机制：** 有多语言、地区或平台变体时，应明确文本/字体/音频/图像资源的回退、占位与缺失策略；文本长度、字形覆盖和字幕时间应纳入实际布局与播放验收。  
**验收：** 每个声明支持的语言和内容变体均能完成关键流程；缺失翻译不会导致关键操作不可理解、按钮不可见或资源引用错位。

### E. 存档、恢复与在线状态

### §25 存档原子性与进度归属
**机制：** 存档应区分玩家/档位/角色/关卡等实际作用域，定义保存触发、提交成功、失败恢复和并发写入规则；部分写入不得被识别为完整有效存档。  
**验收：** 在保存过程中强制中断后，加载结果是完整旧版本、完整新版本或明确的可恢复失败，不出现混合字段、幽灵进度或静默重置。

### §26 存档格式与版本迁移
**机制：** 持久化游戏状态应带有可识别的格式/规则版本；格式变更应定义迁移、向后兼容、拒绝未知版本和恢复策略，不把任意旧数据按当前结构强制解析。  
**验收：** 使用已支持的历史存档执行升级路径，关键进度与身份保持；使用损坏、截断或不支持版本时，不覆盖原始存档并给出明确恢复选择。

### §27 暂停、崩溃与继续游戏
**机制：** 应明确暂停、系统挂起、进程终止、断电、切换场景和退出时哪些状态需要保存或重建；自动保存、检查点与用户主动保存应有可区分语义。  
**验收：** 在每个声明支持的恢复点强制中断后，恢复位置、资源、任务状态和可操作性符合产品承诺；不得把“进程重启成功”当作游戏进度恢复成功。

### §28 联网与共享模拟的权威状态
**机制：** 若存在网络参与者、共享世界状态或跨设备同步，应按实际拓扑与权威模型定义状态所有者、输入顺序、冲突处理和可验证结果。客户端/服务端预测、回滚、P2P 共识或权威节点、锁步及本地同屏输入汇聚是不同架构选项；只有项目实际采用某一机制时，才要求验证其对应契约。不得把任意客户端状态直接作为其他玩家或共享进度的权威事实。
**验收：** 先记录项目实际拓扑、权威状态和采用的同步算法，再针对其契约注入延迟、重复/乱序消息、节点退出或非法状态；结果须符合该架构声明的冲突与恢复规则。离线本地同屏可通过输入归属、暂停/控制权和共享状态测试验收，无须虚构服务器权威或网络回滚。

### §29 联网请求、云存档与会话恢复
**机制：** 只要游戏操作涉及远端服务、在线单人进度、云存档、账号绑定或跨设备状态，即应区分本地提交、远端已提交、明确失败和提交结果未知；请求身份、玩家/存档归属、幂等键或等效去重策略、查询结果与重连策略应按实际协议定义。查询未找到不等于旧请求从未提交或已停止在途；去重须绑定玩家/目标/操作与参数，并覆盖目标接受/处理窗口，不能仅因本地派发未过期就重试。离线单机且没有远端状态的项目不适用网络恢复义务；联网单人游戏不能因没有其他玩家而视为离线单机。
**验收：** 对实际存在的远端写入，在请求发出后、服务端提交前后及响应丢失时分别验证状态判定；重连/重试必须能区分安全重试、先查询状态和禁止重放，不能产生重复进度、覆盖其他账号存档或创建重复会话。旧连接控制权在权威端按世代失效后才完成接管；这不限制同一玩家按玩法拥有多个合法实体。对云存档须验证设备切换、账号切换、冲突选择和恢复结果；纯离线项目只需证明不存在远端状态路径，不要求模拟不存在的服务端。

### §30 录像、事件回放与模拟可重放
**机制：** 应分别声明交付物属于渲染视频、事件记录、输入记录、状态快照或可重放模拟。渲染视频的最低契约是可播放、可识别来源/内容身份并符合产品承诺的音画完整性；只有当项目承诺从输入或事件重建模拟时，才要求绑定足以解释重放的规则/内容版本、必要的初始状态、输入序列及确定性范围；实际使用随机性时，另绑定随机算法/版本和起始随机状态，或足够重建该状态的材料。没有随机源的确定性游戏无需新增随机种子。跨平台浮点、并行执行和物理行为只在实际验证的确定性范围内承诺。不得将纯视频说成可重放模拟，也不得要求纯视频记录不存在的随机种子或确定性状态。
**验收：** 视频类交付物验证可解码播放、时长/音轨（如有）、内容身份和文件完整性；模拟重放类交付物则在声明兼容范围内验证状态/事件重建，并在缺少必要版本、初始状态或随机性输入时明确拒绝确定性重放。两类证据分别记录，不以视频可播放证明模拟可重现。

### F. 画面、声音、性能与实际发行

### §31 渲染质量与显示模式
**机制：** 应记录产品声明的显示模式、分辨率/缩放、画质等级、帧率限制、HDR/VRR 或其他可选图形能力；不支持的能力应受控回退。  
**验收：** 在受支持配置中切换窗口/全屏、分辨率和画质选项后，输入可用、UI 可读且实际渲染状态与界面显示一致。

### §32 音频状态与视听同步
**机制：** 应区分主音量、音乐、音效、语音/对话和必要的空间音频通道；音频资源加载、暂停、场景切换及输出设备变化不得破坏游戏状态。若玩法依赖节奏或同步，需明确允许误差。  
**验收：** 暂停/恢复、切换设备、快速进入/离开场景和资源缺失后，不产生不可停止的音频、旧场景残留或错误的关键声音提示。

### §33 目标平台性能与资源预算
**机制：** L6 应针对已声明的平台和典型玩法场景定义帧时间、加载时延、内存、显存、存储、网络和电量/温度等适用预算；预算应反映真实目标而非所有项目通用固定数值。  
**验收：** 使用目标平台和代表性场景测量关键分位/峰值与资源趋势；平均帧率不能掩盖长帧、内存峰值、卡死或持续热降频。

### §34 兼容性与功能降级
**机制：** 应明确硬件能力检测、图形/音频后端、控制设备、操作系统版本和可选功能之间的兼容关系；降级必须保留核心玩法契约，不能静默关闭已承诺功能。  
**验收：** 在最低支持配置和缺失可选能力的环境中，游戏能按支持合同运行或给出可操作的拒绝原因；不将未测试的平台宣称为兼容。

### §35 内容包、Mod 与用户生成内容
**机制：** 如支持 DLC、资源包、Mod 或用户生成内容，应定义版本兼容、缺失/卸载、依赖关系、冲突优先级和信任边界；外部内容不得默认拥有脚本执行、文件、网络或账户权限。  
**验收：** 缺少可选内容时，核心游戏仍按声明运行；冲突/不可信内容不能覆盖核心存档、取得未授权权限或使内容来源无法追溯。不支持扩展内容的项目不适用。

### §36 发布候选与实际运行一致性
**机制：** 候选发布应把源码版本、构建配置、导入后资产、关卡/本地化清单、内容包和实际制品绑定；对发行前变更的资产或配置重新执行受影响验收。  
**验收：** 从最终发行制品启动并完成代表性核心流程，实际加载的资源与发布清单一致；编辑器成功、开发构建通过或商店上传成功不能单独代表发行候选验收通过。

## 五、静态失败场景与边界反例

下列反例用于审查规范实现是否遗漏游戏特有边界。每项应能映射到相应机制；适用性按真实项目确定，静态检查不能替代目标平台、真实玩家路径或业务验收。

| 编号 | 对应机制 | 失败场景 | 检查入口／证据 | 完成标准 | 判定 |
| --- | --- | --- | --- | --- | --- |
| F01 | §01, §02 | 以场景加载成功声称核心玩法循环通过，但玩家无法触发任何有效动作 | 从游戏入口执行核心循环；记录输入、状态和反馈 | 玩家动作可触发并完成声明的规则循环，且反馈与权威状态一致 | 失败 |
| F02 | §01, §11, §14 | 将未实现的多人功能标为不适用，尽管产品已承诺多人模式 | 对照已批准功能范围和平台清单，核验多人/联网适用性 | 已承诺多人功能有可执行入口与验收证据；仅未承诺功能可标不适用 | 失败 |
| F03 | §03 | 通过修改 HUD 数值直接增加玩家经验或奖励 | 重建表现层并比较权威状态与持久进度 | 仅修改 HUD/动画/粒子不能增加权威进度或奖励 | 失败 |
| F04 | §04, §25 | 音效播放成功被当作购买/奖励状态已提交的唯一证据 | 对照状态提交记录、持久化回执与玩家反馈 | 结果由权威提交状态决定；音效/动画不能单独证明提交 | 失败 |
| F05 | §05, §06 | 帧率从 120 降到 30 后，移动速度随帧数成比例下降 | 在声明帧率档运行同一输入序列并比较模拟速度 | 帧率变化不得意外改变按时间定义的移动/冷却结果 | 失败 |
| F06 | §05 | 系统时间回拨导致冷却或计时器倒退/重复触发 | 注入墙钟回拨/跳变并检查计时基准 | 墙钟变化不得造成冷却倒退、重复触发或超时误判 | 失败 |
| F07 | §05, §09 | 暂停期间仍累计不应推进的游戏模拟时间 | 暂停时检查模拟时钟、冷却和定时器 | 只有按已声明暂停策略应推进的时钟继续推进 | 失败 |
| F08 | §07 | 高速物体穿过已声明必须阻挡的薄障碍且无纠正机制 | 对高速运动和薄障碍执行碰撞边界测试 | 必须阻挡的障碍符合声明碰撞契约，无无故穿透 | 失败 |
| F09 | §07, §09 | 碰撞层配置错误导致必需的触发区域永远不触发 | 检查碰撞层并触发必需区域 | 必需触发器在声明条件下可触发，配置有可追踪证据 | 失败 |
| F10 | §13 | 同一输入在轮询重试后消费两次并造成双重攻击 | 记录单次输入事件的采样、缓冲和消费次数 | 离散输入按声明至多消费一次，不重复触发副作用 | 失败 |
| F11 | §13, §14 | 在产品声明恢复时应清空持续输入的策略下，暂停前的移动输入未经新输入仍继续生效 | 按产品声明的暂停/恢复输入策略测试并记录输入状态 | 清空策略下无新输入不得继续移动；保持策略下行为须与明示规则一致 | 失败 |
| F12 | §12 | 只更改菜单按键映射，实际玩法仍读取旧硬编码按键 | 修改映射后执行真实玩法输入并重启/重载配置 | 菜单、持久化设置和实际动作采用同一有效映射 | 失败 |
| F13 | §14 | UI 文本输入时，背景游戏同时响应相同按键 | UI 文本输入期间注入游戏控制键并记录动作 | UI 拥有焦点时不得触发未授权的背景玩法动作 | 失败 |
| F14 | §15, §16 | 关键危险只用颜色表示，产品承诺的辅助提示通道缺失 | 关闭颜色提示并核验已承诺的其他反馈通道 | 必要状态至少由产品承诺的可用通道表达 | 失败 |
| F15 | §15, §16 | 对目标玩家和已承诺的字幕/替代通道而言，关闭字幕或辅助选项后必要剧情/玩法指令无任何可用理解方式 | 按目标玩家测试字幕/辅助关闭、重开及替代通道 | 只有违反已承诺通道或缺少必要替代时判失败；允许关闭的设置按声明生效 | 失败 |
| F16 | §17, §21 | 场景尚未完成必需资源初始化就允许玩家操作 | 在必需资源尚未初始化时尝试进入并操作场景 | 未初始化场景不接受玩法操作，并有明确失败/恢复入口 | 失败 |
| F17 | §18 | 对象池复用实体后仍保留上一玩家的碰撞、计时器或奖励状态 | 重复生成/销毁和对象池复用，检查所有权状态 | 复用实体不保留前一使用者的碰撞、计时器或奖励 | 失败 |
| F18 | §19, §22 | 资源被替换后仍静默加载旧缓存且构建清单未能识别差异 | 替换源资产并检查导入缓存及最终资源清单 | 构建反映源资产变化，不静默使用过期派生资源 | 失败 |
| F19 | §20 | 随包分发的第三方素材无来源或使用依据，仍被标记为可发行 | 抽查最终发行资产清单的来源、许可和署名字段 | 每个第三方资产有可定位的使用依据，否则排除发行 | 失败 |
| F20 | §21 | 关卡引用已删除资源，打包后以无意义空对象替代必需玩法内容 | 执行悬空引用扫描并启动缺失资源关卡 | 悬空引用被检出；关键资源缺失不伪装成功 | 失败 |
| F21 | §19, §22 | 导入器升级改变碰撞网格或材质结果，却没有变更身份或回归检查 | 比较导入器升级前后的派生身份和实际结果 | 变化可追溯至源、设置或工具版本，并完成受影响回归 | 失败 |
| F22 | §23 | 关卡目标不可达且无重置/恢复路径，玩家被永久软锁 | 从关键路径入口到必需目标，并注入状态异常 | 可继续状态保持可达；终局/设计性软锁有规则、反馈和退出入口 | 失败 |
| F23 | §24 | 本地化文本溢出遮住关键操作，仍以原语言截图验收全部语言 | 对声明支持的每种语言执行关键 UI 和字幕流程 | 关键操作在每个声明支持语言下可理解、可见且可操作 | 失败 |
| F24 | §25 | 保存中断后将半写入存档当作最新完整进度加载 | 在存档写入各阶段中断后尝试加载 | 只能加载完整旧版、完整新版或明确恢复失败，不得读混合状态 | 失败 |
| F25 | §26 | 新版本把未知存档字段静默丢弃并覆盖原文件 | 用历史、损坏和未知版本存档执行升级/加载 | 不得静默丢弃/覆盖原数据；迁移或拒绝路径可核验 | 失败 |
| F26 | §27, §25 | 崩溃恢复后玩家位置恢复，但任务完成状态和消耗物品来自不同时间点 | 在保存/检查点阶段注入崩溃并比较状态版本 | 恢复的玩家位置、任务状态和物品消耗来自一致的状态版本 | 失败 |
| F27 | §28 | 客户端伪造共享战斗结果后直接获得服务端奖励 | 按实际网络拓扑对共享状态注入篡改/延迟/乱序 | 共享状态依声明的权威与同步架构结算，不套用未采用的预测/回滚要求 | 失败 |
| F28 | §29, §25 | 网络重试造成同一任务奖励或比赛结算重复执行 | 对远端写入在提交前、提交后、响应丢失时断网并重连 | 能区分安全重试、先查状态和禁止重放；云存档按账号/设备归属无重复覆盖 | 失败 |
| F29 | §29, §28 | 重连使旧控制实例与新实例重复驱动同一角色，重复结算奖励 | 断开并重连同一账号/玩家，记录连接世代、控制实例、实体归属及重连前后的事件/奖励；另测RTS或多角色合法多实体 | 连接重建不新增未授权控制实例，不重复驱动或结算；玩家可按玩法合同拥有多个合法实体，旧连接的控制权按世代失效 | 失败 |
| F30 | §30, §08 | 回放文件缺少规则/内容版本，却被宣称可跨版本确定重现 | 读取回放清单，检查规则/内容版本、初始状态、输入序列和所需随机性材料；按声明的跨版本范围尝试重放 | 承诺可重放时，所需材料齐全并在声明兼容范围内重建；材料缺失或不兼容时明确拒绝确定性重放，不伪称通过 | 失败 |
| F31 | §31 | 全屏切换后输入失效，或 UI 显示的分辨率与实际渲染不一致 | 切换窗口/全屏、分辨率/缩放与画质，记录实际显示模式、渲染分辨率、输入事件和 UI 布局 | 实际输出与界面状态一致；输入仍可用、UI 可读，不支持的能力按声明受控降级 | 失败 |
| F32 | §32 | 场景切换后旧场景音乐持续播放且无法由玩家控制 | 暂停/恢复、切换场景、切换输出设备并检查播放实例、音量状态和旧场景音轨 | 音频按设置与场景生命周期正确停止/恢复；无不可停止的旧场景残留，玩家仍可控制承诺的音频通道 | 失败 |
| F33 | §33 | 平均 FPS 达标，但长帧/内存峰值持续导致核心操作卡死 | 在目标设备与代表性场景记录帧时间分位/峰值、内存/显存峰值、卡顿和持续资源趋势 | 测量满足 L6 声明的场景与目标预算；均值不得掩盖超预算长帧、峰值、卡死或持续降频 | 失败 |
| F34 | §34 | 低配设备缺少可选图形能力后，核心玩法被静默禁用 | 在最低支持配置及缺少可选图形能力的环境运行核心流程，并记录能力检测、降级路径和玩家反馈 | 核心玩法按支持合同保持可用，或给出可操作的拒绝原因；不得静默关闭已承诺功能或夸大未测平台兼容 | 失败 |
| F35 | §35 | 外部 Mod 获得未授权的宿主文件或账户访问权限 | 加载不可信 Mod/UGC，尝试访问宿主文件、账户数据、网络接口及修改核心存档，记录权限拦截 | 外部内容仅获得明确授予的能力；未授权访问被阻止，核心存档和账户状态保持完整 | 失败 |
| F36 | §36, §19, §22 | 最终发行包与测试构建加载不同资产，却沿用测试构建通过结果 | 比较最终候选的源码版本、构建配置、导入器版本、资产清单与运行时实际加载资源，并核对变更后的验收记录 | 最终制品身份与实际加载资产可追溯且一致；相关源码/配置/资产变化已执行受影响验收，不沿用不匹配构建的通过结论 | 失败 |
| F37 | §18, §09 | 关卡切换时旧实体事件订阅未清理，触发已退出场景的副作用 | 重复进入/退出关卡并记录实体生命周期、事件订阅/退订、回调来源及退出后触发次数 | 退出场景的实体已释放/退订，不再接收事件或触发副作用；重复切换不会累积订阅 | 失败 |
| F38 | §08 | 项目承诺该随机生成问题可复现，却未保留所需种子、生成器/规则版本或输入记录 | 检查复现承诺与诊断契约，核对实际保留的种子、生成器/规则版本、输入序列和状态快照；按声明范围重放 | 承诺复现时，必要材料足以在声明范围内重建问题；未承诺确定性复现时按诊断契约保留证据，不因缺少不存在的承诺自动判失败 | 失败 |

| F40 | §09, §10 | 过场跳过后，必须提交的任务状态没有执行或被执行两次 | 在过场播放、跳过、自然结束及重复触发分支记录任务状态提交、奖励和副作用次数 | 跳过/结束按契约提交必要状态恰好一次，不丢失、不重复，后续状态转换有效 | 失败 |
| F41 | §19, §21, §17 | 资源下载完成被当作资源已验证、可加载并已在关卡中生效 | 从下载完成开始逐段核对内容身份/完整性验证、导入/解码、可加载性、运行时引用及关卡实际使用结果 | 只有内容通过验证、可加载且被实际引用/生效后才报告可用；下载完成不得单独作为资产生效证据 | 失败 |
| F42 | §04, §36 | 发布渠道显示上传成功，但实际安装包无法启动或缺少核心资源 | 比较商店上传/分发回执与最终安装包实际安装、启动、核心资源加载和代表性玩法运行证据 | 最终发行包实际安装并启动，必需资源存在且核心流程按声明完成；渠道成功不能替代运行验收 | 失败 |

### 合法邻例与条件边界

连接唯一性不等于实体数量为一：RTS、多角色及召唤物允许同一玩家合法拥有多个实体；重连检查针对重复控制、重复事件消费和重复结算。

| 编号 | 合法邻例 | 必要证据与判定标准 |
| --- | --- | --- |
| N01 | 单人联网游戏使用云存档，没有其他玩家 | §29 仍适用；以账号/存档归属、提交结果未知、重连查询和去重证据验收，不因单人模式跳过远端状态处理 |
| N02 | 离线本地同屏双人游戏，无服务器或远端状态 | §28 按本地输入归属、共享状态、暂停/控制权与分屏/同屏玩法验收；不要求服务端权威、网络回滚或云重连 |
| N03 | P2P 对战采用确定的主机/权威节点而非客户端预测回滚 | §28 按实际 P2P 拓扑、权威选举/失效、状态冲突和重连契约验收；不强制加入未采用的客户端/服务端预测机制 |
| N04 | 锁步模拟要求参与节点按同一输入序列推进 | §28 验证输入序列、同步边界和节点失联后的已声明处理；不强制回滚架构，除非项目实际采用 |
| N05 | 纯渲染录像只承诺可播放和来源追溯，不承诺从录像重建模拟 | §30 验证可解码、音轨/时长（如有）、身份与完整性；不要求随机种子、初始模拟状态或确定性重放 |
| N06 | 可重放模拟承诺跨同一规则版本重建事件 | §30 绑定该承诺所需的规则/内容版本、初始状态、输入和随机性；缺项时明确标为不可确定重放 |
| N07 | 游戏声明暂停恢复时清空输入 | §13–§14 验证恢复后持续输入已清除；无新输入不得继续移动 |
| N08 | 游戏明确声明暂停时保持按住状态，恢复后继续移动 | §13–§14 验证该保持行为是产品明示策略，恢复状态与输入设备实际状态一致，且焦点丢失/断连不会造成卡键 |
| N09 | 玩家主动关闭字幕，产品未承诺字幕必须始终开启，但保留已承诺的音频/视觉替代提示 | §15–§16 验证关闭选择生效、可重新开启，必要信息仍经承诺的替代通道可理解；不自动判失败 |
| N10 | 程序生成玩法不承诺逐种子确定性复现，但会保留错误日志和生成器版本用于诊断 | §08/§30 按声明的诊断义务验收，不因未保存随机种子自动判失败 |

| N12 | 物理模拟使用固定步长，渲染帧率变化但模拟步序不变 | §06–§07 验证渲染波动不会意外引入事件重复/丢失，且固定步长策略与实际执行一致 |

## 六、验收证据与生效边界

1. **玩法合同：** 对每个已承诺的核心玩法，记录输入、前置状态、规则结果、可见反馈、失败分支及恢复入口。
2. **状态与时序：** 选择与玩法相符的状态转换、暂停/恢复、时间步长、碰撞、随机性和关卡切换测试；不把帧截图或单次演示替代状态验证。
3. **存档与联网：** 对实际支持的保存、迁移、崩溃恢复、断线/重连、多人权威和回放路径执行边界测试；不支持的功能明确记录适用性依据。
4. **内容资产：** 校验来源/使用依据、导入配置、资源引用、派生内容、目标平台变体、缺失资源和最终打包清单；权利批准和技术完整性分别留证。
5. **视听、可访问性与性能：** 在 L6 声明的玩家输入、设备、画面/声音设置和目标平台上验证实际效果；预算必须绑定场景、设备、构建和测量方法。
6. **发行候选：** 记录准确源码 Revision、工具链、配置、资产清单、构建制品身份、实际安装/启动和核心玩法结果；CI 成功不等于发行批准或实际用户验收。
7. **版本与验收：** 项目按准确规范版本确定适用条款，并分别记录实施检查与业务验收结果。符合性判断覆盖全部适用要求。

## 七、验收清单

- [ ] L6 已定义目标玩家、核心玩法、平台与可选特征。
- [ ] 核心玩法循环、状态所有权、输入映射和非法状态转换可验证。
- [ ] 游戏时钟、暂停/恢复、物理和随机性符合声明的模拟契约。
- [ ] 关卡、资产引用、导入结果、来源/使用依据和内容版本可追溯。
- [ ] 存档、迁移、崩溃恢复与联网状态（如适用）通过对应边界测试。
- [ ] 可访问性、视听反馈、性能预算与兼容性已在声明目标上验证。
- [ ] 最终发行制品与测试的资产/配置/源码版本一致。
- [ ] 技术审查、候选检查、实施验收和正式生效分别有证据。

## 领域契约与完整专题接口

非目标：不强制特定引擎、多人拓扑、随机性/物理、云存档或XR；不把模拟测试当真实物理/媒体/设备验收。

输入/控制、模拟/表现、资产/场景、存档/权威进度与最终消费是不同技术对象。模拟状态不由HUD/音效/ACK裁决；状态推进由规则执行器，存档由实际存储提交，联网/结算由目标业务权威确认。
