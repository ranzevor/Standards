# L4 弹性调度、资源容量与性能边界技术规范

**文档ID：** STD-L4-CLOUD-009　**版本：** 0.1.0　**状态：** adopted　**生效日期：** 2026-10-30

## 一、目标、适用与非目标

**目标：** 证明真实可服务容量、尾延迟、故障降级及资源成本在选定边界内。

**适用：** 调度/Requests/Limits、HPA/VPA/KEDA、节点与云扩缩、Serverless、Worker/队列/连接池。

**非目标：** 不强制闲置热备，不把Desired/Max配置当已供应容量或严格费用上限。

本 L4 云基础设施与 DevOps 第 9 项管理实际服务、批任务与异步队列中的容量建模、调度可行性、工作负载/节点弹性、资源约束、共享瓶颈、性能边界与容错。固定单机、小型云服务和自托管服务器可在既有预算内采用受控固定容量，不因为使用云而强制增加 Kubernetes、KEDA、Karpenter、Service Mesh、多区集群或付费自动扩缩服务。仅在真实弹性需求和既有授权下选用对应机制。

相应云运行隔离专题负责容器/宿主安全执行，云 IAM/网络/IaC 负责身份、入口与资源声明，CI/Runner 负责构建执行，发布编排专题负责流量切换、Canary 与版本回退。此专题只回答“**目标工作能否真正被调度并在既定容量/性能/预算内完成**”：请求、限制、资源供给、扩缩反馈、队列/连接池约束与性能实证。后续可观测性专题负责监控系统完整架构、事件响应专题负责事故管理，成本治理专题负责计费与退役，本项只确定扩缩和资源决策必需的指标和上限。应用业务事务、外部 API、数据与消息幂等继续由对应后端/数据库规范管理；L5 按选定平台版本实施，L6 批准生产资源、资金、客户目标与实际业务结果。

### 用语、强度与权威状态

Desired/Admitted/Scheduled/Ready/Serving为不同状态；并发不等RPS；Quota拒绝与Pending不可调度分开；分位数为统计估计。

OPC指单人组织/单人公司画像；真实有权自然人可兼任多个职责，不因此虚构额外审批者或由工具角色取代业务授权。

“必须/不得”为本规范适用条件成立时的强制要求；“应/优先”为需给出可复核理由方可偏离的建议；“可”为许可选项。原有机制句及其验收为规范性合同，直接失败与合法邻例约束解释范围。外部来源的MUST/SHOULD保留其原强度，本规范自行加强的门禁不得倒称外部原文要求。

**共同不变量：** 请求接纳不得无界放大重试/资源；缺数与冷启动单列；缩容前在途任务提交/ACK另核；共享下游总连接含旧新副本。

**状态词：** 未开始、已受理、执行中、成功、失败、取消请求、结果未知分别记录；Timeout/取消请求不自动证明目标未执行。输出至少绑定对象不可变ID/版本、实际主体、目标环境、操作ID、观察时点及所见范围，秘密值不进入共享证据。

**兼容原则：** 选定OS/机型/控制器/Gate/Region和代表性负载分别验；无GPU/Serverless项目不强制引入，指标桶/单位/窗口不兼容不可合并。

## 三、技术机制与逐条可观察合同

### §01 适用负载与弹性必要性
<a id="CLD-CAP-01"></a>

**稳定条款：** `CLD-CAP-01`（保留 `§01`）。

**机制：** 按实际服务的交互请求、队列任务、批处理、常驻进程或 GPU 计算选择固定容量、定时扩缩或按需求弹性；不以云服务使用本身强制引入 HPA、KEDA、Kubernetes 或付费调度平台。

**验收：** 每项自动扩缩机制与真实负载变化、维护能力及成本边界关联；可满足目标的低复杂度系统不被迫新增基础设施。

**主体、前置与输入：** 本条针对“适用负载与弹性必要性”；执行者必须具有目标范围的实际权限，消费 `CLD-CAP-T1` 的固定输入：RPS/在途/队列年龄/任务时长、平台/实例/配置、峰谷/突发、租户份额。

**权威状态与输出：** 实际业务工作单位/SLO与受权资源/费用上限。输出本条验收的原始观察及 `CLD-CAP-T1` 产物：适用负载基线、容量拐点/上限与有界拒绝/降级。不能从期望配置/请求成功越级推断该输出。

**并发、超时、未知与恢复：** 配额或预算触顶不自行扩采购；模型变更重测，不据平均CPU推全部瓶颈。记录本条对象版本与操作身份；冲突/部分成功/未观测项不并入成功，不以新请求覆盖原请求的未知结果。

**正例及判据：** 在上述明确目标/主体/版本和有效前置下，按项目负载采用有证据的最小容量方案而非无依据采购；本条具体可观察验收仍为“每项自动扩缩机制与真实负载变化、维护能力及成本边界关联；可满足目标的低复杂度系统不被迫新增基础设施。”。合法操作与应有拒绝均须由实际目标结果而非仅配置文本确认。

**直接失败：** 无需外部可伸缩业务的小型服务被强制增加付费 KEDA 集群。此时必须得到上述预期检查/失败诊断，不得登记本条整体通过。

**合法邻例与兼容：** 稳定低负载可用固定容量与有界接纳，不必运行Autoscaler。 与本条适用条件相容；不得为拒绝该合法情形而扩大外部规范或供应商限制。不同目标平台/版本的等效实现须保留同一输出不变量。

**真实检查入口：** 消费[ `CLD-CAP-T1` ](#CLD-CAP-T1)中的命令/API/项目入口，在同一隔离画像分别运行正例、上述失败输入和合法邻例；逐项比对本条验收，不以退出0单独替代资源、权限、业务或费用读回。有限来源命题：`K8S-RESOURCES`、`COST-CAP`；只支持第二节所列命题，不为整条实施结果背书。

**并发、超时、未知与恢复：** 配额或预算触顶不自行扩采购；模型变更重测，不据平均CPU推全部瓶颈。记录本条对象版本与操作身份；冲突/部分成功/未观测项不并入成功，不以新请求覆盖原请求的未知结果。

**正例及判据：** 在上述明确目标/主体/版本和有效前置下，按真实峰值和处理时间复核容量，不以均值覆盖突发；本条具体可观察验收仍为“同样的平均 CPU 但峰值 RPS/任务服务时间不同，容量估算能识别区别并标明适用样本。”。合法操作与应有拒绝均须由实际目标结果而非仅配置文本确认。

**合法邻例与兼容：** IO型负载CPU低仍可能饱和，按实际工作单位建模。 与本条适用条件相容；不得为拒绝该合法情形而扩大外部规范或供应商限制。不同目标平台/版本的等效实现须保留同一输出不变量。

### §03 性能目标与技术门禁
<a id="CLD-CAP-03"></a>

**稳定条款：** `CLD-CAP-03`（保留 `§03`）。

**机制：** L4 只要求能把真实业务目标映射到所选负载、错误率、尾延迟、排队时长和吞吐指标；具体 SLO/客户承诺及容量成本由 L6 决定，不把厂商默认阈值写成组织统一性能要求。

**验收：** 目标延迟与允许失败比例有明确来源和受影响路径，调度策略有可复核指标与失败处理。

**主体、前置与输入：** 本条针对“性能目标与技术门禁”；执行者必须具有目标范围的实际权限，消费 `CLD-CAP-T1` 的固定输入：RPS/在途/队列年龄/任务时长、平台/实例/配置、峰谷/突发、租户份额。

**权威状态与输出：** 实际业务工作单位/SLO与受权资源/费用上限。输出本条验收的原始观察及 `CLD-CAP-T1` 产物：适用负载基线、容量拐点/上限与有界拒绝/降级。不能从期望配置/请求成功越级推断该输出。

**并发、超时、未知与恢复：** 配额或预算触顶不自行扩采购；模型变更重测，不据平均CPU推全部瓶颈。记录本条对象版本与操作身份；冲突/部分成功/未观测项不并入成功，不以新请求覆盖原请求的未知结果。

**正例及判据：** 在上述明确目标/主体/版本和有效前置下，指标与真实业务目标对应，关键路径需单独覆盖；本条具体可观察验收仍为“目标延迟与允许失败比例有明确来源和受影响路径，调度策略有可复核指标与失败处理。”。合法操作与应有拒绝均须由实际目标结果而非仅配置文本确认。
