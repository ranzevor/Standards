# L4 报价库存、支付尝试与订单履约技术规范

**文档ID：** STD-L4-COMMERCE-002　**版本：** 0.1.0　**状态：** adopted　**生效日期：** 2026-10-30

## 适用与非目标

本专题深化[基线](001-商业交易与计费系统领域通用基线--v0.1.0.md)M01、M03—08、M16、M18—20，管理报价、稀缺资源、订单、渠道尝试与履约。价格、税务适用、退款权与会计政策由真实有权主体在L6决定；技术状态不提供法律/支付安全认证。无支付、无库存的路径分别排除相应对象，不要求象征性扣款。[L3 v0.1.0](../../L3/001-通用工程规范--v0.1.0.md)提供一般未知结果/交付接口。

必须/不得是适用必要条件，应是可解释偏离的建议，可是选择。`quote`承诺的商业快照与实时目录不同；`order_id`、`intent_id`、`attempt_id`、`channel_object_id`、`fulfillment_id`不同。授权hold、capture、结算、payout到账、退款、争议、履约有各自权威，不能用一个success字段替代。

## 逐条合同

### COM-Q01 报价确认与不可漂移快照

**对象与责任：** 定价/税费接口负责人生成报价，订单服务验证客户/商户/环境及确认范围；客户确认不能由后台改价代替。

**输入/输出/权威：** 输入为商品/版本、数量、币种与精度、价格/汇率/优惠/税费规则身份、客户资格、有效期和是否锁库存；输出为精确报价快照/摘要及被接受或过期的确认。权威是客户确认的不可变快照与服务端订单记录，页面展示缓存不是当前承诺。

**必要机制与不变量：** 提交时原子核报价身份、有效期与参数未漂移；订单保存足够重算的行项、金额、条件、规则版本与接受时点。目录、汇率或资格变化不得静默更改已确认总额；必须重新报价/确认或依明示锁价合同继续。金额按金额专题规范，客户端总额仅作对照不作权威。

**失败、并发、超时与恢复：** 过期/改量/失效优惠给可判拒绝与新报价，不沿旧确认自动买新条件。接受后丢响应按原意图查订单；并发提交同报价是否可多个订单由合同决定并原子执行，不靠UI禁按钮。

**兼容：** 实时不锁价询价可明确到期重新确认；历史规则解释器/快照须保留，不把现价重算成旧订单金额。免费报价仍保留订单/履约条件。

**验收与产物：** T-COM-HTTP在报价与提交间改价/汇率/数量/优惠并跨到期点；查询订单快照、原确认字节和报价状态，断言无未确认变价，合法有效报价可完成。

**正例 / 直接失败 / 合法邻例：** 正例为有效快照金额写入订单；直接失败为后台改价使已确认订单多扣；合法邻例为明确未锁价的询价到期后客户重新确认新报价。

**来源：** 组织合成商业不变量，不声称引用渠道文档决定锁价或税务适用。

### COM-Q02 稀缺资源预留与支付跨期竞争

**对象与责任：** 库存/名额权威定义供给、预售额度和预留状态；订单与支付协调者处理预留到期时的资金结果，不虚构跨渠道原子事务。

**输入/输出/权威：** 输入为资源/批次、数量、reservation_id、到期、订单、付款事实与版本；输出为reserved/committed/released/expired以及异常补偿。库存事务账和实际供给是权威，客户端可售数不是承诺。

**必要机制与不变量：** 可售=获准供给减有效占用（预售另明示）；原子检查/预留，最后一个名额不得同时承诺两次。预留只允许一次从reserved转 committed或released/expired；重复到期任务不能释放已售。付款跨预留到期必须定义重获库存、等待、退款等路径，不能一面承诺交付一面无货。

**失败、并发、超时与恢复：** 付款成功与到期释放竞争由可核事务/版本边界裁决；未知支付不自动释放所有追踪信息。恢复回放以reservation身份去重，旧释放任务不能作用于后续新预留。

**兼容：** 数字无稀缺资源可不部署库存引擎；明示预售按独立额度/日期承诺，不等同无界超卖。多仓/分批交付需逐资源占用，不合成一个总布尔。

**验收与产物：** T-COM-CONCURRENT同步两请求争最后名额，再交错到期、迟到支付和重复释放；读取库存流水与订单承诺，守恒且只有有效占用者获承诺，异常资金保留独立处置。

**正例 / 直接失败 / 合法邻例：** 正例为一个成功一个无库存拒绝；直接失败为重复释放已售名额；合法邻例为客户已知且额度内的独立预售路径。

**来源：** 组织合成，消费数据库真实隔离/事务接口，渠道接受不证明库存已提交。

### COM-Q03 意图、尝试与未知付款的闭合

**对象与责任：** 订单服务持久登记逻辑意图，渠道适配器绑定商户/环境/操作与幂等作用域，恢复者核全部可能生效尝试。

**输入/输出/权威：** 输入为客户/商户/环境、intent/attempt、规范化参数摘要、渠道对象及幂等窗/迟到接受保证；输出为未派发、在途、已应用、确定永不应用、未知。渠道原交易/操作查询及内部持久账是权威，不以单次HTTP错误判断未扣。

**必要机制与不变量：** 派发前持久写尝试与参数，重发沿用同一逻辑意图/原渠道幂等身份且条件未变。超时保持未知，按原attempt/渠道对象核对；只有所有仍可能生效的尝试均被权威证明未应用且不会未来应用，或渠道保证同意图幂等可安全合并时才允许新尝试。新尝试B未应用不证明旧未知A未应用。去重窗到期不得换新键盲补。[C01]

**失败、并发、超时与恢复：** 并发派发通过单准入/原子比较或渠道强幂等防多效果；参数漂移、跨商户/环境同键拒绝。丢响应与查询延迟冲突时保留未决，禁止不安全再次付款并给可查恢复责任；查询暂未找到并非“永不应用”。

**兼容：** 同参数的独立新购买有新intent并可合法再买。渠道API v1/v2和错误类型分别固定，不能把一个供应商缓存500或24小时策略推广全部渠道。

**验收与产物：** 本地尝试模型及T-COM-FAULT分别注入提交后丢响应、A未知+B未应用、迟到A成功、键清除、参数漂移和明确未执行；读取所有attempt/渠道对象/金额效果，既无重复扣也不吞合法新意图。

**正例 / 直接失败 / 合法邻例：** 正例为相同key同参数重传只回原效果；直接失败为A未知时用B的not-found关闭并再扣；合法邻例为权威证明A不可再执行后按合同的新尝试，或独立新购买。

**来源：** C01仅支持所读Stripe v1/v2差异及有限幂等窗；全尝试闭合、持久准入与未知状态是组织合成。

### COM-Q04 渠道事件入站、验签与事实归并

**对象与责任：** 入站适配器验证供应商原始消息，业务消费者核商户/对象/环境，持久事件账负责接收与处理分离。

**输入/输出/权威：** 输入为原始请求字节、签名头、签名版本/容限、event_id、account、livemode/环境和对象引用；输出为拒绝、耐久受理、处理待核或事实更新。供应商对象查询与本地已处理意图账为权威，事件到达顺序不是事实顺序。

**必要机制与不变量：** 按选定SDK/协议在解析改写前验证原始签名材料和时间范围；验签成功仍核对象归属和用途。耐久写入后才回接收ACK，处理失败可安全重投；重复event去重与同对象/业务效果去重分别记录。乱序/缺失/同秒事件触发权威核对，不按created或arrival覆盖已确认事实。[C02]

**失败、并发、超时与恢复：** ACK丢失可重复入站但不得重复履约/入账；同event不同原始摘要隔离并调查。签名轮换按当前有效窗；旧环境/商户消息即便签名有效也拒绝。无法查单保留待核，不能将旧失败覆盖已捕获款。

**兼容：** snapshot/thin事件格式与事件生成API版本分开固定；新旧schema路由只在声明兼容窗内，未知事件类型可耐久隔离而不执行未知副作用。

**验收与产物：** T-COM-WEBHOOK发送伪签名、被改写body、重复/乱序/同秒、错商户/环境和响应丢失；观察原事件账、查单调用、对象状态及一次性效果。仅HTTP2xx不是处理成功。

**正例 / 直接失败 / 合法邻例：** 正例为乱序通知查单后保留真实当前状态；直接失败为旧失败通知反向撤销已确认成功或同成功发两次货；合法邻例为重复事件只返回已受理且原处理可继续。

**来源：** C02 Stripe Webhooks的签名、重复、顺序与API版本小节；本地耐久ACK和业务去重是组织合成。

### COM-Q05 授权、捕获、资金与履约前置

**对象与责任：** 渠道适配器负责支付事实，订单/履约负责人定义何事实足以进行哪一步；登录、支付令牌持有、业务购买批准和渠道授权不同。

**输入/输出/权威：** 输入为订单快照、买方/付款主体关系、商户/币种/金额、渠道授权/capture对象与履约合同；输出为资金各阶段、订单业务状态、独立履约结果。渠道对象、仓储/权益实际效果与结算账分别权威。

**必要机制与不变量：** 执行前核所用支付材料归属/用途；授权hold不等于capture，capture不等于payout到账或履约。允许部分capture时记录累计、剩余额与过期；void只撤未捕获授权，不伪装refund。履约以固定业务前置与唯一fulfillment身份发起，外部发货/发信不可由数据库回滚自动撤回。

**失败、并发、超时与恢复：** capture和取消、分批履约与退款竞争按原订单权威状态裁决；未知资金不新开付款，未知履约不新ID盲重发。支付成功履约失败保持两事实，按合同补发/退款/人工处置，不能删除已发记录。

**兼容：** 零价订单无支付可有合法履约；获准共享付款主体按明确授权范围，不因客户ID不同一律拒绝。不可撤销已交付材料不假称退款后自动收回。

**验收与产物：** T-COM-HTTP/FAULT覆盖仅授权、部分capture、capture后响应丢失、履约失败/重复、void与refund分支及零价订单；逐状态查询和效果计数一致，不使用浏览器success页当资金证明。

**正例 / 直接失败 / 合法邻例：** 正例为满足前置后一次履约；直接失败为success回跳即发货而支付失败；合法邻例为合同允许在获准信用/零价条件下不等待capture履约。

**来源：** 组织合成事实/前置合同，具体渠道状态由L5选定版本绑定，不从某个status名称推出通用资金终点。

### COM-Q06 风险、版本与环境隔离

**对象与责任：** 业务/风控权限所有者核限制范围和恢复，适配器固定商户、API版本/环境、回调、凭据引用和账户；迁移者负责历史解释不变。

**输入/输出/权威：** 输入为风险信号及版本、真实商户/环境、订单/事件schema、计价版本和有效权限；输出为允许、需动作、暂限、拒绝或待核。有效策略决定与实际资源/资金结果为权威，不把风险分数当已证欺诈。

**必要机制与不变量：** 测试/生产ID、秘密、事件和权益命名空间隔离；错环境事件不得驱动真实权益。改价、退款、导出、结算账户变更分别授权。风险限制有原因/范围/期限及合法申诉/恢复；API升级重核幂等、事件、金额与错误语义，旧订单解释器保留。

**失败、并发、超时与恢复：** 风控不可用执行预定限界，不默许高风险动作；取消旧渠道仍保留必要查单/退款跟踪，不遗弃在途。迁移失败回退须保持历史金额/尝试身份和审计，不全量重放POST。

**兼容：** 旧schema在承诺兼容窗内路由；不承诺的未知版本隔离而不猜字段。合法无支付业务不强制风控平台。

**验收与产物：** T-COM-HTTP送错environment/account、旧schema、并发撤权和API版本差异夹具，查询权益、订单与资金账确认无串扰；合法迁移历史总额/解释保持。产物含版本矩阵、拒绝证据及未决资金清单。

**正例 / 直接失败 / 合法邻例：** 正例为隔离测试事件仅作用测试权益；直接失败为沙箱event激活生产权益；合法邻例为声明兼容且正确路由的旧订单回调。

**来源：** C01/C02只支持渠道语义需版本固定；风控权利、环境隔离与迁移恢复为组织合成。

## 真实目标工具合同（全部 not-run）

L6固定确切服务/渠道API版本、商户/环境、合成账号和故障注入点；未固定时不产生真实请求。

- **T-COM-HTTP：** `curl --config "$TEST_AUTH_CONFIG" --request "$METHOD" --header 'Content-Type: application/json' --data-binary @"$CASE_JSON" --dump-header "$HEADERS" --output "$REPLY" "$BASE$PATH"`；随后对原order/intent/attempt/payment/fulfillment的只读权威接口查询。凭据由隔离测试设施引用，不写真实卡号、Token或秘密进日志。
- **T-COM-CONCURRENT：** 项目固定测试运行器使用屏障同步两提交，并查询数据库真实事务/库存事件；Python单进程模型只能示范原子准入，不证明数据库隔离。
- **T-COM-FAULT：** 受控代理在渠道/履约目标已经接受后丢响应；查单须绑定原对象及全部attempt，保留渠道原始状态、请求ID和效果分母。若无适用沙箱/目标，仅记录待执行，不以合成状态自证渠道保证。
- **T-COM-WEBHOOK：** 用供应商固定SDK产生隔离签名材料，`curl --data-binary @"$RAW_EVENT" --header @"$SIGNATURE_HEADER_FILE" "$BASE$WEBHOOK_PATH"`；服务日志与只读对象查询核真实验签/耐久受理/处理。仅手造HMAC模型不能算供应商SDK通过。

本地有限模型运行：`python3 -m unittest discover -s tests -p 'test_sec_edge_commerce_models.py' -v`。[来源](../../../sources/commerce-billing.md)及[模型假设](../../../examples/security-edge-commerce/README.md)分别记录。
