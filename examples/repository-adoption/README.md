# 软件仓库采用合成示例

以下示例用于区分分发、维护和发行状态，并演示仓库文件与平台控制的组合。项目名和状态均为合成内容，没有实际采用、审查、发布或平台配置结果。

## 示例一：公开发行的命令行工具

`ExampleArchiveCLI` 的仓库为 public，自有代码已由权利主体选择 Apache-2.0，维护状态为 active，正式发行入口为项目的 Release 页面。对应机器记录见[公开发行 profile](public-open-source.json)。

- README 给出受支持的 Python 版本、从正式发行包开始的安装命令、最小查询和失败恢复。
- LICENSE 覆盖自有代码；第三方通知逐项列随包依赖和许可证。
- CONTRIBUTING、SECURITY、缺陷/提案 Issue 模板和 PR 模板提供公共协作入口。
- 锁文件或等价摘要固定运行与开发依赖；CI 检查准确候选，第三方 Action 固定完整提交 SHA。
- 平台规则要求当前候选的必需检查和审查通过；实际规则从平台读回。
- 发行绑定标签、源码提交、制品清单和摘要，并从真实下载入口完成安装验收。

该示例只有在上述对象和实际结果都存在时才能标为 published；模板齐全本身不产生该状态。

## 示例二：私有开发中的服务

`InternalQueuePrototype` 为 private，维护状态 active，没有公开分发决定，包元数据保持 private，许可证状态为 not-selected。对应机器记录见[私有开发 profile](private-development.json)。

- README 只面向获准开发者给出本地构建、测试和内部接口，不使用开源许可证或公开发行徽章。
- 依赖、测试、PR 和内部安全报告入口仍按风险配置。
- 不要求为尚不存在的公共用户建立公开 Issue、下载渠道或支持承诺。
- 若以后改为 public 或开始分发，先核权利、许可、秘密、第三方材料和公开入口，再改变状态。

未选择许可证在该范围内是合法状态；把仓库公开并宣称可再分发而仍保持 not-selected 才是分发阻断。

## 示例三：已归档的开源库

`LegacyFormatReader` 已发布 `v2.4.1`，后续由 `CurrentFormatReader` 替代。原仓库为 public，维护状态 archived，既有许可证继续适用于已授权材料。对应机器记录见[归档 profile](archived-open-source.json)。

- README 首屏写最终版本、停止维护范围、替代项目和迁移入口。
- 最终标签、发行附件、源码、许可证和第三方通知仍可定位。
- 安全说明准确写明是否仍接收敏感报告，不延续不存在的响应承诺。
- 平台禁止普通合并，但归档不被描述为删除、撤回许可或消费者全部迁移完成。
- 原始运行日志按保留策略位于独立证据存储；仓库只保留必要历史、恢复说明和正式成果。

## 直接失败输入

| 失败输入 | 应观察的结果 |
| --- | --- |
| public README 显示 MIT 徽章，但没有有权主体选择的 LICENSE | 分发状态不得判 open-source 或 ready-to-publish |
| PR 模板只有摘要和测试勾选，没有基线、候选、风险、恢复和未执行项 | 模板接口检查失败，不能由创建 PR 补成实质审查 |
| 工作流使用 `actions/checkout@v4`，却声称自动化依赖已固定 | 依赖身份检查失败；更新为经过审查的完整提交 SHA |
| README 逐日追加实施进度、内部交接和原始测试输出 | 当前用途、状态和首次使用入口不再满足读者任务；过程材料移出公开入口 |
| archived 仓库删除唯一许可证和最终源码，只保留替代链接 | 历史保全和既有权利入口失败，恢复准确最终对象后重新核验 |

模板入口见[软件仓库模板包](../../templates/repository/README.md)，条款选择见[软件仓库采用指南](../../guides/SOFTWARE-REPOSITORY-ADOPTION.md)。
