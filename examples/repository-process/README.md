# 可填写的仓库流程示例

本页提供合成的技术提案、缺陷报告、PR 说明及完整变更案例，用于填写项目自己的工作项与审查材料。示例中的 B0、C1、C2、M2 是场景标签，实际工作使用准确 commit/tree 和真实运行结果。

## 规范提案：可变名称不作为源身份

- 目标与触发：离线复现由多个组件组成的工具时，防止可变分支名取代固定输入；不要求每次复现都升级远端。
- 现有接口：[L3 CE-04](../../standards/L3/001-通用工程规范--v0.1.0.md)固定各组件身份，[PGR-02](../../standards/project-governance/004-仓库命名目录与内容归属规范--v0.1.0.md)划分内容归属，[PGQ-05](../../standards/project-governance/011-测试质量门禁与证据规范--v0.1.0.md)规定原始证据保全。
- 必要机制：每个组件登记路径、固定摘要及来源。历史快照按其字节复现；远端当前状态另行读取，发布者身份和材料权利分别核对。
- 失败与恢复：摘要不符不能默认为正常更新；并行替换输入先保留原对象和差异，核准确来源后重新固定身份与验收。
- 正例：两个离线组件分别固定摘要，按其准确版本构建。
- 直接失败：把组件A的当前分支内容替换为旧登记输入，却继续引用旧验证通过。
- 合法邻例：多仓或离线快照不因不是单一最新远端分支而被拒。
- 可运行检查：`python -m unittest discover -s tests -p test_source_identity.py -v`。预期是固定对象匹配通过、摘要或路径直接变异失败、合法多组件通过；本记录没有单独运行结果或产品验收结果。
- 来源与限制：工程合同为组织设计；摘要与路径检查用于识别对象，远端新鲜度、信任和材料权利另行核对。
- 交付范围：正文合同、直接模型和正反例；不修改其他项目、远端访问方式或实际发布设置。

## 缺陷报告：旧未知被新未执行覆盖

- 对象：[运行操作账AUT-EFFECT-04/05](../../standards/L4/automation/004-耐久操作账、目标栅栏与未知结果技术规范--v0.1.0.md)与其有限SQLite夹具。
- 初始状态：一个合成意图有尝试a1；目标可能已提交，但本地尚未获得可靠终态。
- 最小输入：a1=unknown，随后同意图a2=not-applied；再交付a1迟到的可信已提交结果。
- 独立预期：a2的未执行只证明a2，不关闭a1；意图在覆盖全部相关尝试和可继续生效条件前仍unknown。迟到已提交事实按原身份归并，不产生第二份效果。
- 直接失败反例：把`operation.state`无条件赋为“最近一次尝试的状态”，因此错误显示整体未执行并创建新商业意图。
- 合法邻例：有已核幂等合同的同意图重复传输可进行；不能把所有重试一律拒绝。
- 复现入口：`python -m unittest discover -s tests -p test_runtime_examples.py -v`，检查旧 `unknown` 保持、权威确认和效果次数。本节提供报告结构，执行日志为空。
- 影响与恢复：所有按操作级结果恢复的消费者可能受影响；真实目标、去重保留期和权限须在项目采用时固定。

## PR说明：补输入类型与合法邻例

- 技术目标：在合成Python适配中区分整数、布尔和超界输入，保持有效零值；不修改业务金额规则。
- 精确对象：从[唯一目录](../../registry/standards.json)选择Python适配准确版本/hash；源差异仅限对应条款、夹具和回归，实际提交时补准确base/head身份。
- 机制与兼容：Python的bool可呈整数关系，业务若只接受严格整数需显式检查；接受规则来自业务而不是强制所有整数API都拒bool。现有合法零值不应因真值判断丢失。
- 直接失败：以`isinstance(value, int)`代替严格业务合同后，`True`被误接受。
- 合法邻例：需求允许的`0`与边界合法整数保持可用；非整数按明确错误返回，不静默归零。
- 验证入口：`python examples/stacks/python_case.py` 及对应回归。实际 PR 列运行版本、退出码、原始输出、影响范围与完整回归；本记录的产品结果为 `not-run`。
- 来源：实际 Python 版本的官方类型文档；类型注解不在运行时检查输入，不可信 JSON 仍需运行时验证。
- 审查与状态：作者检查、独立技术审查、规范采用和实际产品验收分别记录；提案或PR建立本身不改变任何一轴。


## 完整案例：修复制品成员门禁

合成工具 `demo-reader` 承诺分发模块、空 `py.typed`、许可证和当前候选版本元数据。缺陷 QG-001 的触发条件是删除类型标记后重新计算包内清单；只比较清单与包会遗漏这项错误。验收依据是打包合同，具体运行场景见[独立预期示例](../repository_engineering/README.md)。

| 阶段与责任 | 操作及准确对象 | 接受条件或恢复 |
| --- | --- | --- |
| 问题归类：变更负责人 | QG-001 记录预期成员、删标记并重算清单的输入、使用者缺失类型声明的影响 | 重算清单后仍拒绝缺失；完整包与合法新版本继续接受 |
| 基线：作者 | 识别工作区和索引，取得目标 main 的 B0，从 B0 建开发分支 | 无关修改保留；远端或目录身份不明时先解决该输入 |
| 验收设计：作者与验收者 | 从源码和打包声明独立生成预期，区分制品自述清单与来源文件身份 | 反例在包成员判据失败，不能只因摘要过时被先行拒绝 |
| 首次候选：作者 | C1 加入成员及字节映射比较，同步测试与打包说明 | 旧反例被拒绝；成员顺序变化仍合法 |
| 独立审查：审查者 | 对准确 C1 检查成员、源码字段关系及版本演进；用矛盾的源码身份字段输入检查 | 若该字段仍被忽略，形成明确开放发现，C1 不进入合并 |
| 修复与复核：作者、审查者 | C2 增加来源字段关系检查，列出 C1→C2 差异 | 重跑该字段反例及相关合法输入；成员逻辑未变的既有证据可按身份和命题复用 |
| PR：作者 | 目标 main、基线 B0、候选 C2，列兼容、检查和恢复信息 | 原始日志位于独立证据位置；独立审查与作者自查分别关联候选 |
| 合并前：有权维护者 | 再读目标 HEAD、C2、开放发现、批准和平台必需检查；生成对应集成候选 M2 | 目标变化后核实际集成影响，不能仅凭 C2 曾通过认定 M2 通过 |
| 合并后：集成者 | 核实际集成提交/tree、内容和检查 | 实际结果与预期不符时新增修复或按共享历史执行回退 |
| 发行：发行责任人 | 在发行授权范围内从准确集成提交构建，固定版本、标签与制品 | 正式渠道下载、安装及最小任务通过后确认交付；安装失败按原对象恢复 |
| 收尾：工作项负责人 | 将 QG-001 关联最终提交、实际验收与用户需要的变更说明 | 缺陷处置绑定已验证修复；其他未达验收项继续保留具体责任与恢复动作 |

这个修复改变检查器对错误制品的识别，保持原有有效包、来源声明和版本规则。恢复入口是前一有效工具版本及其准确制品；对已错误接受的包，另行按独立预期重新核其内容，不能只更新“已核验”标记。

本案例的定向入口为：

```sh
python -X utf8 -B -m unittest tests.test_repository_engineering.IndependentPackageTests -v
```

提交可使用 `fix(packaging): 拒绝缺少承诺成员的发行包`；正文说明独立预期来源、拒绝行为、合法输入兼容及该候选的实际验证。PR 按[现有模板](../../templates/repository/PULL_REQUEST_TEMPLATE.md)记录运行结果，不把上表的接受条件填写成已经完成的事件。
