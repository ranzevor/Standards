# Repository naming, directories and content placement

## Objects, terms and prerequisites

Applies to original repositories, forks, platform-special repositories, packages, documentation and generated artifacts; different identifiers follow their respective technical constraints, rather than imposing repository-name rules on domain names or package managers. A current entry point is the single body/source-code coordinate readers should use; historical objects retain old identities without competing with the current entry point. Maintainers own naming and content boundaries; package/brand owners confirm their respective coordinates. Depends on [PGF](framework.md) and [PGT](requirements-traceability.md).

## PGR-01 Name repositories, packages and brands separately

**Inputs and prerequisites:** Project role, original/fork/platform constraints, official brand and consumers of package/domain names.

**Procedure:** Original repositories use PascalCase, retaining uppercase acronyms such as MCP/API/SDK/CLI and the official brand's spelling. Distinguish repository identifiers, brands, package coordinates, domain names and installation commands. For forks, platform-reserved names and ecosystem requirements, record the exception type and actual constraints; necessary name suffixes must correspond to distinct responsibilities.

**Outputs and acceptance:** Active repository names do not contain versions, dates, temporary states or meaningless sequence numbers; packages and domain names are checked against their respective ecosystems. Exceptions include the object, reason and downstream consumption impacts.

**Failure and recovery:** If renaming conflicts or the platform rejects it, retain the current coordinate, decide a new name and recheck consumers; do not unarchive or rewrite a brand without authority.

**Positive example:** AtlasSDK is a separate SDK repository, while its npm package still uses a lowercase package name permitted by that ecosystem.

**Direct failure example:** Treating AtlasSdkV2Final as the default conforming name for an original repository.

**Valid adjacent case:** `.github` is retained under platform-special repository rules, not renamed Github.

**Checking entry point:** Existing `checks/repository_naming.py` checks expressible grammar/roles/exceptions; brand rights and semantic necessity require manual checking.

## PGR-02 Directory responsibilities and file classification

**Inputs and prerequisites:** Project components, build entry points, formal deliverables and evidence types.

**Procedure:** Describe responsibilities, authoritative sources and rebuild methods by directory and file type for source, formal documentation, proposals, guides, examples, tests, generated artifacts and caches. Git manages file versions and historical differences; generated artifacts identify generation commands and input identities, and disposable caches must not become the only source. Specification projects place bodies awaiting review in proposals; the formal adoption entry point contains only its exact decided objects.

**Outputs and acceptance:** A path has no conflicting responsibilities; new files fit defined categories; only caches and temporary outputs are ignored, without misclassifying necessary source or irreplaceable evidence as disposable.

**Failure and recovery:** If a file is misplaced in an output directory, first restore its authoritative source and references, then move it; files whose provenance cannot be confirmed remain unclassified and are not automatically deleted.

**Positive example:** `src/` contains source, `dist/` is generated by a fixed command, and test inputs are retained separately.

**Direct failure example:** The only design document is kept in a cache directory labeled safe to clean.

**Valid adjacent case:** Generated API documentation is tracked for convenient release, with explicit inputs and reproducibility checks.

**Checking entry point:** Directory rules check paths, categories and generation entry points; necessary retention conditions follow [PGX](materials-evidence-lifecycle.md).

## PGR-03 Single current entry point and separate history

**Inputs and prerequisites:** Current registrations, old paths, compatibility consumers and exact content identities.

**Procedure:** Designate a single current entry point for each specification body, user guide and package source; historical objects are located by Git commit/tree or exact release versions. Moving a body updates relative links, catalogs and specification identities, while Git preserves file-path changes. Where consumers are affected, provide migration instructions identifying old and replacement entry points and necessary actions. Project adoption records continue to pin original identities and cannot silently adopt new content because of a move.

**Outputs and acceptance:** The same ID/version does not identify two different bodies; current links resolve; historical entry points clearly direct readers or locate old objects rather than masquerading as current versions.

**Failure and recovery:** If old and new identities conflict, stop updating that adoption reference and determine authority from full bytes and the migration decision; identical filenames or matching paragraph excerpts do not establish object identity.

**Positive example:** A new draft is in proposals and the old approved body remains at its exact historical entry point, with their versions and effect distinguished.

**Direct failure example:** Putting a copy of old text in a new directory and reusing the old hash to claim approval.

**Valid adjacent case:** An entry page linking briefly to the single body is not a second body.

**Checking entry point:** The single specification registry, duplicate IDs/hashes, paths and links are checked automatically; full-text review assesses whether migration preserves obligations.

## PGR-04 Place content according to purpose

**Inputs and prerequisites:** Proposed text, code, examples or constraints and their intended readers.

**Procedure:** Product entry points explain use and navigation; specifications state technical obligations; guides give execution steps; examples present synthetic business cases and observations; review materials identify objects, findings and rechecks; dedicated constraint files contain execution permissions, usage limits and tool restrictions. Commits/PRs explain specific changes in this project, without unrelated conversations, scheduling language or self-explanations. Review complete paragraphs and appended final sentences by purpose, rather than deleting by keyword.

**Outputs and acceptance:** Readers can use the product without internal conversations; legitimate Agent coordination, permission boundaries, research limitations and evidence topics remain in the relevant technical responsibilities.

**Failure and recovery:** Move misplaced content to its correct dedicated location or remove useless copies; retain technical obligations related to failure mechanisms and recheck context and links.

**Positive example:** A security specification explains that a timeout does not undo external side effects that have already occurred; this is a recovery contract, not an executor's self-justification.

**Direct failure example:** Appending “I will keep working and wait for the next scheduling instruction” to a README as product content.

**Valid adjacent case:** A review report records an actual failure and its repair; this is the report's proper content.

**Checking entry point:** Content placement is manually reviewed paragraph by paragraph; automated tools can only list locations and inspect dedicated directories, not declare violations merely because content includes “MUST NOT.”

## PGR-05 Source, generated artifacts and content identity

**Inputs and prerequisites:** Build/generation commands, inputs, tool versions and the expected output set.

**Procedure:** Identify hand-maintained sources and generated outputs; Git repositories pin source inputs with the actual candidate tree, and release builds generate complete output manifests delivered with the packages. Compare complete outputs after generation without ignoring appended content. Fix necessary configuration, text encoding, line endings and case/path compatibility requirements under project conventions; digests identify actual bytes, not normalized bytes claimed to be verbatim identical.

**Outputs and acceptance:** The same inputs and tools yield predefined equivalent or byte-for-byte outputs, with equivalence criteria specified in advance; output directories contain no unregistered files, and generation does not overwrite hand-written content.

**Failure and recovery:** On nondeterminism, source drift or generation failure, retain the old valid output and failure results; correct the source or explicitly adopt a new generator, then recheck. Do not manually edit generated results to make checks green.

**Positive example:** A catalog is generated from the single registry, and check mode rejects missing rows, extra rows and digest mismatches.

**Direct failure example:** Computing a digest for only the first half of a file and ignoring appended permission clauses.

**Valid adjacent case:** A semantic comparison explicitly permitting JSON key-order changes may be used for that interface, but cannot be called byte-for-byte reproduction.

**Checking entry point:** Git objects, specification registries, generators and release manifests verify content identity; generator semantics and output adequacy are reviewed separately.

## PGR-06 Path and entry-point migration

**Inputs and prerequisites:** Old and new directory/repository/package coordinates, consumers, builds/releases and data locations.

**Procedure:** List internal links, installation commands, import paths, CI/Action, submodules, deployments, documentation and external consumers separately. Test new coordinates by category and record the disposition of old coordinates; use platform redirects only within their actual guarantees, without assuming every reference migrates automatically.

**Outputs and acceptance:** Affected consumers can find old and new entry points and necessary actions in migration instructions, while Git reproduces file-path differences. Necessary consumers have executable migration paths within the compatibility window; caches and history are not treated as new entry points.

**Failure and recovery:** If a remaining consumer is discovered, maintain the established window or restore the old compatibility entry point; irreversible changes to public coordinates need an explicit forward fix, not an overwrite of the original release identity.

**Positive example:** After a repository rename, check package installation, documentation links and submodule URLs separately.

**Direct failure example:** Concluding that all pinned Action references have migrated because the repository web page opens.

**Valid adjacent case:** A local directory rearrangement with no external consumers checks only actual internal references, without inventing remote migration.

**Checking entry point:** Local links and registrations are checked automatically; actual platforms/consumers undergo target-environment acceptance under the [deprecation and migration specification](deprecation-retirement.md).
